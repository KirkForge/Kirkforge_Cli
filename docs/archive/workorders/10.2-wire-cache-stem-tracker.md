# Workorder 10.2 — Wire WO 9.5 CacheStemTracker into Executor + Adapter

## Status: Done (`3f6e19d`; metric event wired, adapter short-circuit skipped — Anthropic API requires full content)

## Problem
WO 9.5 shipped `CacheStemTracker` in `src/session/prompt/cache_stem.rs`
(334L) with 6 unit tests, ADR-052, and a new `PlanDecisionKind::CacheStemReuse`
metric variant (`src/shared/metrics.rs:135`). The workorder Status is
`Done`. But the tracker is never called from anywhere outside its own
test module:

```
$ grep -rn "CacheStemTracker\|is_stable\|record_prefix_hash" --include="*.rs"
src/session/prompt/mod.rs:1            pub mod cache_stem;
src/session/prompt/cache_stem.rs:*    (definition + tests)
src/shared/metrics.rs:132              /// `CacheStemTracker` (ADR-052) ... (doc comment only)
```

No call site in `src/session/executor/turn.rs`, `src/session/prompt/mod.rs`'s
build path, or `src/adapters/anthropic.rs`. The WO 9.5 done condition
"Adapter skips re-serializing cache-stable stem content" is **not met**.
What shipped is the *measurement* (a tracker struct + a metric variant),
not the *optimization* (the adapter still re-serializes the full stem
every turn). This is the same shape as the third-pass "parallel tool
batching" finding: API surface shipped, implementation did not.

The state.md entry for 9.5 is honest about this ("wiring into
`Executor::turn` is a follow-up WO") but the workorder Status is `Done`
and the grade-relevant claim ("prompt-cache stem reuse shipped")
overstates what landed. This WO closes the gap and corrects the
overclaim.

## Root cause
WO 9.5 built the tracker as a self-contained module but stopped short of
wiring it into the turn loop. The `PlanDecisionKind::CacheStemReuse`
variant was added to `metrics.rs:135` but no `MetricEvent::PlanReason`
emission site uses it. The Anthropic adapter emits `cache_control:
{type: "ephemeral"}` markers on the last two prefix messages
(`src/adapters/anthropic.rs:127, 188`) — that's the server-side cache
enablement, unchanged. The client-side stem-reuse signal (the metric
event + the optional adapter short-circuit) was never connected.

## Files to touch
- `src/session/executor/turn.rs` — instantiate a `CacheStemTracker` on
  the executor (one per session). In the turn loop, after the prompt
  builder produces the message list, call `tracker.is_stable(messages,
  prefix_len)`; if stable, emit
  `MetricEvent::PlanReason { decision_kind: PlanDecisionKind::CacheStemReuse }`.
  Then call `tracker.record_prefix_hash(messages, prefix_len)` to
  advance the recorded hash for the next turn.
- `src/session/prompt/mod.rs` — accept an optional `&mut CacheStemTracker`
  (or expose the prefix_len the builder used, so the executor can call
  `is_stable` with the right prefix_len). The builder already knows the
  system-message boundary; expose it as a `pub fn prefix_len(&self) ->
  usize` or pass the tracker in.
- `src/adapters/anthropic.rs` — optional optimization: when
  `tracker.is_stable()` is true and the model `supports_cache`, the
  adapter can omit the *content* of the cache-stable prefix messages
  (send only the `cache_control` marker + a minimal reference). **The
  Anthropic API requires the full content to compute the cache key on
  the first hit** — so this short-circuit is only valid on turns 2+ where
  the prior turn already sent the full content. Check the Anthropic
  Messages API docs before implementing this; if the API does not
  support content-omission, leave the adapter unchanged and ship only
  the metric event (the measurement is still valuable; the server-side
  cache still hits).
- `src/session/prompt/cache_stem.rs` — add an integration test that
  builds a 5-turn conversation through the executor and asserts the
  `PlanReason { decision_kind: CacheStemReuse }` event is emitted on
  turns 2-5 (stable stem) and not on turn 1 (no prior hash) or when the
  system message changes.
- `docs/workorders/9.5-prompt-cache-stem-reuse.md` — correct the Status
  line: change from "Done" to "Done (partial — tracker shipped, adapter
  wiring deferred to WO 10.2)". Add a note pointing to this WO.
- `docs/adr/052-cache-stem-reuse.md` — update the "Status" if the ADR
  claimed the wiring was complete; clarify that the measurement shipped
  in 9.5 and the wiring shipped in 10.2.

## Approach
1. **Decide `prefix_len` semantics.** The cache stem is "the system
   message + the tool definitions + the first N user/assistant turns,
   excluding the trailing volatile tail." The prompt builder at
   `src/session/prompt/mod.rs` assembles messages as
   `[system, ...history, ...tool_results, trailing_user]`. The stable
   prefix is everything except the trailing user turn. Pass
   `prefix_len = messages.len() - 1` (or the index of the last
   `Role::User` message, whichever is smaller) to `is_stable` /
   `record_prefix_hash`.
2. **Wire into `Executor::turn`.** Add `cache_stem: CacheStemTracker` to
   the executor struct (default-initialized). In the turn loop, after
   `prompt_builder.build(...)` returns the message list:
   ```rust
   let prefix_len = messages.len().saturating_sub(1);
   if self.cache_stem.is_stable(&messages, prefix_len) {
       record(MetricEvent::PlanReason {
           decision_kind: PlanDecisionKind::CacheStemReuse,
       });
   }
   self.cache_stem.record_prefix_hash(&messages, prefix_len);
   ```
3. **Adapter short-circuit (optional, API-dependent).** Read the
   Anthropic Messages API docs: can a request omit the content of a
   message that was sent in a prior turn and rely on the server-side
   cache? If yes, implement the short-circuit in
   `src/adapters/anthropic.rs` when `is_stable()` is true and
   `ModelInfo.supports_cache`. If no, skip this step and document why
   in the ADR (the server-side cache still hits; the client-side
   saving is the metric event, not the wire bytes).
4. **Test.** Add an integration test in `cache_stem.rs` or
   `executor/tests/mod.rs` that builds a 5-turn conversation, asserts
   `PlanReason { CacheStemReuse }` is emitted on turns 2-5, and is NOT
   emitted on turn 1 or when the system message changes. Use the
   existing `MetricEvent` recording harness (a test sink that captures
   `record()` calls — check `src/shared/metrics.rs` for the test
   pattern).

## Notes
- The `ponytail:` annotations in `cache_stem.rs` (lines 15-18: "no new
  dependency. The hash is cheap (one pass over the message bytes)") must
  be preserved.
- `DefaultHasher` is `SipHash-1-3` with a fixed key — fine for cache-stem
  comparison (deterministic within a process, not adversarial). Do NOT
  "harden" this to `Sha256` without an ADR; it would add a dep for no
  security benefit (Pass 13 finding #5).
- If the Anthropic API does not support content-omission for cached
  messages, document that honestly in the ADR and ship only the metric
  event. The server-side cache still hits (the `cache_control` markers
  are unchanged); the client-side saving is the observability, not the
  wire bytes. That is still a real improvement over 9.5 (which shipped
  neither the wiring nor the metric emission).
