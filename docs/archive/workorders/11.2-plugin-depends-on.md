# Workorder 11.2 — Plugin Manifest `depends_on` (Plugin Dependency Graph)

## Status: Done (commit pending)

## Problem
A plugin manifest (`kirkforge.toml`) declares `name`, `version`,
`description`, `trust`, `api_version`, `capabilities`, `metadata` —
but no `depends_on` field. There is no way for plugin B to declare "I
require plugin A to be loaded first" or "I require plugin A's tools to
be available."

Real example: the `stratum` plugin's `session-start` hook emits the
active compression ruleset; the `kirkforge-plugin3` (budget) plugin's
hooks read the ruleset to decide when to compact. WO 8.6 wired the
Stratum+Budget coordination (`stratum-budget-coordination`, ADR-051)
at the executor level — but the manifest has no way to declare the
dependency. If a user enables `kirkforge-plugin3` without `stratum`,
the budget hooks run with no ruleset and silently degrade (no
compaction). If a user disables `stratum` while `kirkforge-plugin3` is
active, the budget hooks keep running with a stale ruleset.

The 12th-pass review noted "Plugin system consolidation" (ADR-050)
shipped two-path dispatch — but the dependency graph between plugins
is implicit (coded into the executor's hook wiring), not declared in
the manifests.

## Root cause
The manifest schema (`crates/kirkforge-plugin/src/lib.rs:40-60`
`PluginManifest`) was built for standalone plugins. The folded plugins
(Stratum, Plugin3, Draw, Video) were developed independently and wired
together at the executor level in WO 8.6. The manifest never grew a
`depends_on` field because the dependencies were enforced by feature
flags (the `budget` feature compiles in `kirkforge-plugin3` which
already knows about `stratum` at compile time). But for external
(community) plugins, there is no way to declare a dependency.

## Files to touch
- `crates/kirkforge-plugin/src/lib.rs` — add `pub depends_on:
  Vec<String>` to `PluginManifest` (default empty; serde `#[serde(default)]`).
  Add a `validate_dependencies(loaded: &[&str]) -> Result<(), Vec<ValidationError>>`
  method that checks every name in `depends_on` is in `loaded`.
- `crates/kirkforge-plugin/src/lib.rs` `validate()` — extend to check
  `depends_on` names are valid plugin names (regex, same as `name`).
- `crates/kirkforge-plugin-host/src/lib.rs` — in the plugin-load path,
  after loading all manifests, run a topological sort: a plugin whose
  `depends_on` includes a name not in the loaded set is rejected with a
  clear error ("plugin B requires plugin A, which is not enabled"). A
  cycle in `depends_on` (A → B → A) is rejected with a cycle-path error.
- `src/session/plugin_tools/loader.rs` — when `load_plugin_registry`
  builds the registry, respect `depends_on` ordering: load dependencies
  before dependents (so dependent hooks see their dependencies' state).
- `plugins/kirkforge-plugin3/kirkforge.toml` — add `depends_on =
  ["stratum"]` (the real dependency from WO 8.6).
- `docs/adr/` — new ADR (058 or next free) documenting the
  `depends_on` field, the load-order semantics, and the cycle-rejection
  rule.
- `docs/TECHNICAL.md` — plugin system section: document `depends_on`.

## Approach
1. **Add the field.** `pub depends_on: Vec<String>` with
   `#[serde(default)]` so existing manifests without the field still
   parse.
2. **Validate names.** In `validate()`, check each `depends_on` entry
   matches the plugin-name regex (same as the `name` field validation).
3. **Load-order topological sort.** In the host's load path, after
   collecting all manifests, do a topological sort: a plugin is loaded
   only after all its `depends_on` are loaded. If a dependency is
   missing (not in the enabled set), reject the dependent with a clear
   error. If a cycle is detected (DFS finds a back-edge), reject with
   the cycle path (e.g. "A → B → C → A").
4. **Hook ordering.** Within a single lifecycle event (e.g.
   `session-start`), hooks fire in dependency order: dependencies first,
   dependents after. This is the WO 8.6 coordination requirement made
   explicit — Stratum's `session-start` hook (which emits the ruleset)
   fires before Plugin3's `session-start` hook (which reads the
   ruleset).
5. **Real dependency: plugin3 → stratum.** Add `depends_on =
   ["stratum"]` to `plugins/kirkforge-plugin3/kirkforge.toml`. This
   makes the implicit WO 8.6 dependency explicit in the manifest.
6. **Tests.** Unit tests for: empty `depends_on` (no change), valid
   dependency (B loads after A), missing dependency (B rejected with
   "A not enabled"), cycle (A → B → A rejected with cycle path),
   transitive (C → B → A loads in order A, B, C).

## Done condition

- `validate()` checks `depends_on` names are valid
- Host rejects a plugin whose `depends_on` is not in the enabled set,

- Host rejects a dependency cycle with the cycle path

- Depends on: nothing (the manifest schema is the only prerequisite)

## Notes
- Backward compatibility: existing manifests without `depends_on`
  parse and load unchanged (the field defaults to empty).
- Do NOT break the WO 8.6 Stratum+Budget coordination. The executor-level
  wiring stays; `depends_on` makes the dependency explicit in the
  manifest so the loader can enforce it and order hooks correctly.
- The `depends_on` field is a list of *plugin names*, not feature flags.
  A plugin depending on a folded plugin (e.g. `kirkforge-plugin3`
  depending on `stratum`) declares the *plugin name*; whether the
  dependency is satisfied by the compiled-in path or the shell-out
  path is the loader's concern, not the manifest's.
- The `ponytail:` annotations in the plugin manifest code must be
  preserved.
