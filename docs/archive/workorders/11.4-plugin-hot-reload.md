# Workorder 11.4 — Plugin Hot-Reload via File Watcher

## Status: Done (commit pending)

## Problem
Plugin management is reactive, not proactive. The `/plugins reload`
slash command (`src/tui/commands/plugins/mod.rs:113`) rescans the
plugins directory and reloads the registry — but only when the user
asks. If a developer is iterating on a plugin's `kirkforge.toml` or
its tool scripts, they must `/plugins reload` after every change to
see the effect. There is no automatic reload on file change.

The config hot-reload path (SIGHUP, `src/tui/mod.rs:319`) reloads the
*config* (which includes `enabled_plugins`), but it does not watch
the `plugins/` directory for manifest or script changes. A developer
adding a new tool to a plugin's `kirkforge.toml` must `/plugins
reload` manually.

The 12th-pass review named "config hot-reload" as a shipped feature
(it is, for config) — but plugin hot-reload (watching the plugin
dir) is the missing half.

## Root cause
The plugin loader (`src/session/plugin_tools/loader.rs`) is a
scan-on-demand function. There is no file-watcher on the `plugins/`
directory. The `notify` crate (or `inotify` directly) is not a dep;
the existing file-watcher is on the config file (SIGHUP-based, not
inotify-based).

## Files to touch
- `Cargo.toml` (root) — add `notify` (or `notify-debouncer-mini` for
  a simpler API) as a dep. Check the size impact; the size-optimized
  release profile should keep it small (notify is ~50KB).
- `src/session/plugin_tools/loader.rs` — add a
  `spawn_plugin_watcher(plugins_dir, reload_tx)` function that uses
  `notify` to watch the `plugins/` directory for changes to
  `kirkforge.toml` or tool/hook scripts. On a change, debounce (500ms
  to coalesce editor save-many-files), then send a reload signal on
  `reload_tx` (the existing `plugin_reload_tx` channel the TUI uses).
- `src/tui/mod.rs` — spawn the plugin watcher alongside the existing
  config SIGHUP watcher. The watcher runs in a background tokio task;
  on a change, it triggers the same reload path `/plugins reload`
  uses.
- `src/main/mod.rs` — for headless mode (NDJSON), the watcher can be
  optional (a headless run is typically short-lived; the watcher is
  for long-running TUI sessions). Gate behind a `--watch-plugins`
  flag or always-on for TUI mode, opt-in for headless.
- Tests — the watcher is hard to unit-test (file-system timing), but
  an integration test can write a manifest, verify the watcher fires,
  modify the manifest, verify the reload happens. Use a temp dir +
  `std::thread::sleep(100ms)` to let the watcher debounce.

## Approach
1. **Choose the watcher crate.** `notify-debouncer-mini` is simpler
   (built-in debounce); `notify` is lower-level (you write the
   debounce). Pick `notify-debouncer-mini` for less code.
2. **Spawn the watcher.** In `src/tui/mod.rs` startup, after the
   config SIGHUP watcher, spawn a plugin watcher on the resolved
   `plugins_dir()`. The watcher callback sends a `ReloadPlugins`
   message on the existing `plugin_reload_tx` channel.
3. **Debounce.** 500ms — coalesce a multi-file save (a plugin's
   `kirkforge.toml` + tool scripts are often saved together by an
   editor). The debouncer handles this; the reload fires once per
   burst.
4. **Reload path.** The reload uses the same path as `/plugins
   reload`: rebuild the registry, swap it into `AppState`, refresh
   the skill registry, update the status bar. No new code — just a
   new trigger.
5. **Headless mode.** For `kirkforge run` (NDJSON / non-interactive),
  the watcher is opt-in via `--watch-plugins` (or off by default —
  a short CI run doesn't need it; a long-running daemon might). The
  TUI always has it on.
6. **Test.** An integration test: create a temp `plugins/` dir with a
   mock plugin, start the watcher, modify the manifest, assert the
   reload signal fires within ~1s. The test is timing-sensitive; use
   a generous timeout (2s) and document the flake risk.

## Gate
```
cargo fmt --check && cargo clippy --all-targets -- -D warnings &&
cargo test --locked --workspace --no-fail-fast --all-features
cargo test -p kirkforge --lib session::plugin_tools -- --ignored   # the watcher integration test
cargo bloat --release --crates -- | grep -E "notify"   # check size impact
```

## Done condition
- A change to a plugin's `kirkforge.toml` (or tool/hook script) in the
  `plugins/` directory triggers an automatic registry reload in the TUI
  within ~1s (500ms debounce + reload time)
- The reload uses the same path as `/plugins reload` (no new reload
  logic)
- `notify` (or `notify-debouncer-mini`) dep added; binary size impact
  documented and acceptable (under ~100KB in the size-optimized profile)
- Headless mode: `--watch-plugins` flag (off by default for short CI
  runs; on for the TUI)
- Integration test (marked `#[ignore]` if timing-flaky) verifies the
  reload fires on manifest change
- ADR-059 (or next free) documenting the file-watcher decision, the
  debounce window, and the headless opt-in
- `docs/TECHNICAL.md` plugin section documents the hot-reload
- Depends on: nothing (the reload path exists)

## Notes
- The watcher is for *development* (iterating on a plugin). In
  production (a user running released `kirkforge`), the plugins are
  stable and the watcher is wasted CPU. Gate the TUI watcher behind a
  config flag (`tools.watch_plugins`, default true for TUI, false for
  headless) if the CPU cost is non-trivial. Measure first; `notify`
  on a single small directory is cheap (inotify on Linux, FSEvents on
  macOS, ReadDirectoryChangesW on Windows).
- Do NOT watch `node_modules/` or `target/` — only the `plugins/`
  directory and its subdirectories. Filter by `kirkforge.toml` and
  script file extensions.
- The `ponytail:` annotations in the loader code must be preserved.
- This is a P2 WO — developer ergonomics, not a correctness gap.
