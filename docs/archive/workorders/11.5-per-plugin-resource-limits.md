# Workorder 11.5 — Per-Plugin Resource Limits (Extend SandboxConfig)

## Status: Done (commit pending)

## Problem
WO 9.8 shipped `SandboxConfig` (`src/shared/mod.rs`) with rlimits
(`RLIMIT_CPU`, `RLIMIT_AS`, `RLIMIT_FSIZE`) applied to the bash tool's
child shell in a `pre_exec` hook. But the plugin tool path
(`src/session/plugin_tools/wrapper.rs`) spawns plugin tool scripts
via `Command::new(script_path)` with no resource limits. A plugin
tool script (e.g. a `video_pipeline` shell-out that invokes FFmpeg)
can run forever, allocate unbounded memory, or write unbounded files
— the same risks WO 9.8 closed for the bash tool.

The plugin host's `SandboxPolicy` (`crates/kirkforge-plugin-host/src/sandbox.rs`)
maps capability kinds to trust tiers (skill=ReadOnly, tool=Shell,
hook=Shell, verifier=ReadOnly) — but this is *trust* filtering (which
capabilities are exposed), not *resource* limiting (how much CPU/memory/
file a running plugin tool can consume). Trust + sandbox are orthogonal;
both are needed.

A `trust = "shell"` plugin can run arbitrary shell commands. Without
rlimits, a buggy or malicious plugin tool can OOM the host. The
`curated_env` (`crates/kirkforge-plugin-host/src/env.rs`) cleans the
environment (good for secret hygiene) but doesn't cap resources.

## Root cause
`SandboxConfig` was built for the bash tool only. The plugin tool
wrapper (`PluginToolWrapper::run`) spawns a subprocess without
applying `setup_rlimits`. The `SandboxConfig` is on `Bash` (the tool
struct); `PluginToolWrapper` has no equivalent field.

## Files to touch
- `src/session/plugin_tools/wrapper.rs` — `PluginToolWrapper` gains an
  optional `sandbox: Option<SandboxConfig>` field. In `run`, when
  spawning the plugin script, apply `setup_rlimits` (the same
  `pre_exec` hook from WO 9.8) when `sandbox.harden` is true.
- `src/session/plugin_tools/loader.rs` — when constructing
  `PluginToolWrapper` instances in `all_plugin_tools`, pass the
  `SandboxConfig` from the shared config (`cfg.security.sandbox`).
- `crates/kirkforge-plugin-host/src/sandbox.rs` — extend the
  `SandboxPolicy` (or add a new `ResourcePolicy`) to optionally carry
  per-plugin resource limits: a plugin manifest can declare
  `resource_limits = { cpu_secs = 60, memory_mb = 512 }` which
  overrides the global `SandboxConfig` for that plugin's tools. This
  is opt-in; the global default applies if the manifest doesn't
  declare limits.
- `crates/kirkforge-plugin/src/lib.rs` `PluginManifest` — add an
  optional `resource_limits: Option<ResourceLimits>` field (serde
  `#[serde(default)]`). `ResourceLimits { cpu_secs: Option<u64>,
  memory_mb: Option<u64>, filesize_mb: Option<u64> }`.
- `src/shared/mod.rs` `SandboxConfig` — add a
  `merge_with(plugin_limits: &Option<ResourceLimits>) -> SandboxConfig`
  method that produces a per-plugin config: if the manifest declares
  a limit, use it; otherwise use the global default.
- Tests — extend the WO 9.8 `bash_harden_kills_cpu_burn_with_sigxcpu`
  test pattern to a plugin tool: a mock plugin with a CPU-burn script
  and `resource_limits.cpu_secs = 2` is killed by SIGXCPU in ~2s.

## Approach
1. **Extend `SandboxConfig` to the plugin wrapper.** The
  `PluginToolWrapper::run` method already spawns a `Command`; add
  `setup_rlimits(&mut cmd, &sandbox)` before the spawn, mirroring the
  bash tool's path in `src/session/bash_runner/mod.rs:113-152`.
2. **Per-manifest overrides.** The manifest's `resource_limits` field
  is optional. When present, it overrides the global `SandboxConfig`
  for that plugin's tools. When absent, the global default applies.
  This lets a heavy plugin (e.g. video with FFmpeg) declare a higher
  memory limit than the global default, while a light plugin (e.g.
  draw render) uses the default.
3. **Trust-tier gating.** Only apply rlimits when the plugin's
  effective trust is `Shell` or higher (a `ReadOnly` plugin tool
  doesn't spawn a subprocess — it's a skill prompt). This is already
  enforced by `SandboxPolicy::required_tier` (tool = Shell), so the
  rlimit path only runs for shell-tier tools.
4. **Test.** A mock plugin with `resource_limits.cpu_secs = 2` and a
  tool script `while true; do :; done` is killed by SIGXCPU in ~2s.
  Extend the existing `bash_harden_kills_cpu_burn_with_sigxcpu` test
  pattern.
5. **ADR.** Document the per-plugin resource limits decision: global
  default + per-manifest override, trust-tier gating, the rlimit seam
  reused from WO 9.8.

## Done condition
- `PluginToolWrapper` applies `setup_rlimits` when `SandboxConfig.harden`
  is true (Unix); Windows no-op with the same one-shot warning as
  bash (WO 9.8)
- `PluginManifest.resource_limits` field exists (optional, serde
  backward-compatible); when present, it overrides the global default
  for that plugin's tools
- Test: a mock plugin with `resource_limits.cpu_secs = 2` + a
  CPU-burn script is killed by SIGXCPU in ~2s (extend the WO 9.8 test
  pattern)
- ADR-060 (or next free) documenting the per-plugin resource limits
- `docs/TECHNICAL.md` plugin section documents the resource-limit
  contract (global default + per-manifest override)
- Depends on: WO 9.8 (`SandboxConfig` + `setup_rlimits` exist)

## Notes
- The `ponytail:` annotations in `src/session/bash_runner/mod.rs` (the
  rlimit seam) and in `crates/kirkforge-plugin-host/src/sandbox.rs`
  must be preserved.
- Do NOT apply rlimits to `ReadOnly` plugin tools (skills) — they
  don't spawn subprocesses. The trust-tier gating handles this.
- The per-manifest override is opt-in. The global `SandboxConfig`
  default applies to all plugins that don't declare `resource_limits`.
  This is the least-surprise path: a user who sets `--harden` gets
  rlimits on bash AND plugin tools; a plugin author who needs more
  headroom declares it in the manifest.
- The Windows no-op path must match WO 9.8's: one-shot `OnceLock`
  warning, not a crash, not a silent no-op.
