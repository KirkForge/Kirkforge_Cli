# Workorder 14.0 — Bench Baseline Ollama-Pull Retry (Fix the Real Red CI Gate)

## Status: Done (commit pending)

## Problem
The scheduled `Bench Baseline` CI workflow (`.github/workflows/
bench-baseline.yml`) has failed 3 consecutive days (runs 30519743850,
30428460480, 30334886974 — all `schedule` events, all `failure`). The
failure is the Ollama model pull hitting the registry redirect flake
documented in AGENTS.md §7 and `state.md` "Known CI issues":

```
realm host "ollama.com" does not match original host "registry.ollama.ai"
```

The Pass-14 REVIEW (`REVIEW-KirkForge-Cli.md` line 9) cites "main is
CI-red on Windows" as the A− holdback, but that line is **stale** —
the latest `main` CI run (30333478766) is `success`, and the Windows
`test_cache_results` path-separator issue it names is already fixed
(`src/shared/minify/mod.rs:345` uses a single write + process-unique
temp path, locked in by the regression comment at lines 370-377). The
*actual* red gate today is the scheduled bench job, not Windows.

The `ollama pull` step (lines 62, 111, 224 of `bench-baseline.yml`) has
no retry. Ollama's registry occasionally serves a redirect that the
CLI rejects as a realm mismatch. A retry clears it (AGENTS.md §7:
"Re-running the workflow typically succeeds"). The fix is to make
the workflow self-healing instead of operator-dependent.

## Root cause
The workflow treats `ollama pull` as a one-shot step. The registry
redirect is a transient external-service failure; the workflow has no
retry, so a transient failure becomes a red CI badge for days until
an operator manually re-runs. This is a CI robustness gap, not a code
regression.

## Files to touch
- `.github/workflows/bench-baseline.yml` — wrap the three `ollama pull`
  invocations (lines 62, 111, 224) in a retry loop (3 attempts, 30s
  backoff). The pattern:
  ```bash
  for attempt in 1 2 3; do
    if ollama pull "${BENCH_MODEL}"; then break; fi
    echo "ollama pull attempt $attempt failed; retrying in 30s"
    sleep 30
  done
  curl -fsS http://localhost:11434/api/tags | grep -q "${BENCH_MODEL}" \
    || { echo "model still missing after 3 retries"; exit 1; }
  ```
  The post-retry `curl | grep` is the real gate — it verifies the
  model is usable, not just that `pull` returned 0. Extract this into
  a reusable step or composite action if the duplication bothers
  reviewers, but a literal loop in each of the 3 steps is fine.
- `state.md` "Known CI issues" — after the fix lands and 3 consecutive
  scheduled runs are green, remove the Ollama-pull flake entry (it's
  no longer a "known issue" once the workflow self-heals).

## Approach
1. **Add a retry loop to each `ollama pull` step.** 3 attempts, 30s
   backoff. The loop must `break` on success and `exit 1` only after
   the final attempt fails AND the `curl | grep` health check fails.
   The `curl | grep` is the authoritative check — `ollama pull` can
   return 0 while leaving the model in a half-pulled state; the
   `/api/tags` check confirms the model is actually registered.
2. **Do not add `continue-on-error: true` to the pull step.**
   AGENTS.md §6 forbids `|| true` to make red go green. The retry must
   genuinely attempt to recover, not swallow the failure. The step
   fails the job only if all 3 attempts + the health check fail.
3. **Keep `continue-on-error: true` on the downstream artifact-download
   steps** (lines 118, 128, 135, 166) — those are already correct
   (first-run-has-no-baseline is a real state, not a flake).
4. **Verify** by waiting for 3 consecutive scheduled runs to pass, OR
   by triggering the workflow manually
   (`gh workflow run bench-baseline.yml`) and confirming the retry
   fires. Past the fix, the scheduled job should be green for a week
   straight before this WO is marked Done.
