# Workorder 14.1 — First-Run Onboarding Banner

## Status: Done

## Problem
The Pass-14 REVIEW (§1, "Onboarding — Grade: C+") names the silent
first run as the weakest link in the UX. `load_or_create_config()`
at `src/session/config/mod.rs:131` writes a default config file on
first run but emits only a `tracing::info!` (line 166) — which goes
to the log file, not stdout. A new user runs `kirkforge run`, gets a
config file they never see, then hits a missing-model error with no
guidance. `Config::default()` has `default_model: ""`, so the next
failure is "model unreachable" with no hint that they need to set a
model.

The README quick start (line 16) shows `kirkforge run` with no `-m`
flag, which reproduces the trap. opencode's `/init` walks the user
through setup; KirkForge's `/init` exists (`slash_commands.rs:163`)
but its help text says only "Initialize project configuration" — no
detail on what it does or that the user needs a model.

This is the highest-impact, lowest-effort UX fix in the REVIEW's
priority list (item 1, "10 lines of code, massive onboarding
improvement").

## Root cause
The first-run path was written for a user who already knows the
config layout — the `tracing::info!` is a developer log, not a user
message. The surface assumes the user will find `config.toml.example`
(a 326-line masterclass in documented config that most users never
open). The empty `default_model` is the trap door.

## Files to touch
- `src/session/config/mod.rs:131-179` — `load_or_create_config()`:
  when `!exists`, after the successful write, print a first-run
  banner to **stdout** (not `tracing::info!`). Content:
  ```
  Config created at ~/.local/share/kirkforge/config.toml
  Next: set a model. Try `kirkforge run -m qwen3:32b:cloud` or
  edit `default_model` in the config file. See config.toml.example
  for all options.
  ```
  Keep the `tracing::info!` for the log file (operators want it); add
  the `println!` for the user. Gate the banner behind `!exists` so it
  fires exactly once per install.
- `README.md:14-17` — quick start: change `kirkforge run` to
  `kirkforge run -m qwen3:32b:cloud` (or `qwen2.5:0.5b` for local
  Ollama). One concrete example is worth more than the 326-line
  example file. Add a one-line "Getting Started" pointer above the
  code block: "First run? Set a model with `-m <name>` or edit
  `~/.local/share/kirkforge/config.toml`."
- `src/tui/keys/slash_commands.rs:163` — `/init` usage string: fill
  in the empty `usage: ""` with a concrete description of what it
  creates (`AGENTS.md`, project config skeleton). This overlaps with
  WO 14.2 (help usage strings) — coordinate so the same edit doesn't
  land twice.
- Tests: `src/session/config/mod.rs` tests — add a test that captures
  stdout during a first-run `load_or_create_config` with a temp
  `KIRKFORGE_DATA_DIR` and asserts the banner contains "Config
  created" and the `-m` hint. Use the existing `set_test_path` /
  `clear_test_path` helpers from `metrics.rs` (per WO 10.2 notes) for
  isolation.

## Approach
1. **Banner to stdout.** The `tracing::info!` stays for the log; add
   a `println!` for the user. Use `print!` + flush if the banner
   should appear before any TUI takeover (the TUI clears the screen,
   so a `println!` before TUI init is visible only in line mode — but
   the banner matters most in line mode and `--non-interactive`,
   where stdout is the user's whole surface). In TUI mode the banner
   is lost; that's acceptable because the TUI has its own status bar.
   If we want it visible in TUI mode, inject it as a system message
   in the chat on first run — but that's a bigger change; start with
   stdout.
2. **README concrete model.** Pick `qwen2.5:0.5b` (the bench model,
   widely available via Ollama) as the example so a new user can
   literally copy-paste and get a working session in 30 seconds.
3. **`/init` usage.** Fill the empty `usage` with what it does. This
   is a 1-line edit in the `COMMANDS` table.
4. **Test the banner.** The test must not race with other config tests
   — use the process-unique temp path pattern from
   `minify/mod.rs:345` (WO 10.6 / the Windows fix) so the first-run
   detection is deterministic.

## Gate
```
cargo fmt --check && cargo clippy --all-targets -- -D warnings &&
cargo test --locked --workspace --no-fail-fast &&
cargo test -p kirkforge --lib session::config -- --exact first_run_banner
```

## Done condition
- A first run (no config file) prints a banner to stdout naming the
  config path + a concrete `-m` hint
- The banner fires exactly once (second run with the file present
  prints nothing) — test asserts this
- README quick start shows a concrete `-m <model>` command
- `/init` slash command has a non-empty `usage` string
- `state.md` / `TECHNICAL.md`: no doc change needed (this is surface
  polish, not architecture)
- ADR not needed (UX message, not a pinned decision)
- Depends on: nothing (can land before or after 14.2)

## Notes
- The REVIEW's "empty model by default" point is real but fixing
  `Config::default().default_model` to a non-empty value is a
  behavior change (it would route to a model the user didn't pick).
  Keep the empty default; the banner + `-m` hint is the fix.
- Do NOT add an interactive wizard here. opencode's `/init` wizard is
  out of scope for the 14-series (it's a multi-file feature). The
  banner is the 10-line fix the REVIEW asked for.
- If the banner is invisible in TUI mode (because the TUI clears
  stdout), document that in `lessons.md` and consider a follow-up WO
  to inject it as a chat system message. Start with the simplest fix.
