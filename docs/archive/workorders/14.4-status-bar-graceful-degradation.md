# Workorder 14.4 — Status Bar Graceful Degeneration on Narrow Terminals

## Status: Done

## Problem
The Pass-14 REVIEW (§2, "TUI Interaction — Grade: A−") names the
status bar as a rough edge: "On 80-col terminals, 15+ pieces of
information compete for space... On narrow terminals, items clip
with no truncation indicator." The spacer calculation at
`src/tui/widgets/status.rs:140-144` sets `space = 1` when room is
tight, causing the right-side spans (sandbox, tool-calls, skills,
plugins, sent, received, cost, elapsed) to overlap the left info
with only a single space between them.

The REVIEW's fix (item 7): "Priority-based rendering on narrow
terminals. Drop plugin/skill counts first. 30 lines."

The existing test `status_bar_includes_cost_and_elapsed_on_80_cols`
(lines 205-217) asserts cost + elapsed are visible at 80 cols, but it
does NOT test below 80, and it does NOT test that items don't overlap
(it only checks `contains`, not rendering order). So the current code
passes its test while still overlapping on narrow terminals.

## Root cause
The status bar renders a fixed list of spans left-to-right with a
single computed spacer. There's no priority system — when the sum of
left + right spans exceeds the width, the code sets `space = 1` and
hopes. Ratatui's `Paragraph` widget will happily render spans past the
area boundary, clipping or overlapping depending on the backend. The
bar was designed for wide terminals (the test is 80 cols, which is the
*upper* bound of "narrow"); it doesn't degrade gracefully below that.

## Files to touch
- `src/tui/widgets/status.rs:108-165` — `render_status()`:
  - Define a priority order for the right-side spans. Suggested
    (highest priority = last to drop):
    1. `elapsed_span` (always show — it's the session heartbeat)
    2. `cost_span` (always show — users watch cost)
    3. `sent_span` + `received_span` (token counts — useful but
       compressible to "↑N ↓N" if space is tight)
    4. `plugin_span` (drop first — least critical, and `/plugins` is
       a command away)
    5. `skills_span` (drop second)
    6. `tool_calls_span` (drop third)
    7. `collapse_span` (Ctrl+T indicator — drop fourth; it's a
       toggle hint, the user can press Ctrl+T blind)
    8. `sandbox_span` (UNSANDBOXED warning — NEVER drop; it's a
       safety indicator. If it's present, it stays even at 40 cols.)
  - Replace the single `space = 1` fallback with a loop: compute the
    total right-side width; if it + left + 2 > area.width, drop the
    lowest-priority droppable span; recompute; repeat until it fits or
    only the never-drop spans (elapsed, cost, sandbox) remain.
  - If it still doesn't fit at the floor, set `space = 1` and accept
    the overlap — but now it's the *minimum* overlap, not every span
    piled up.
- `src/tui/widgets/status.rs:167-218` — tests:
  - Keep `status_bar_includes_cost_and_elapsed_on_80_cols`.
  - Add `status_bar_drops_plugin_count_below_70_cols` asserting the
    plugin span text disappears at width 60 while cost + elapsed
    remain.
  - Add `status_bar_keeps_unsandboxed_warning_at_40_cols` asserting
    the `⚠️ UNSANDBOXED` span is present even at width 40 (when
    state is unsandboxed).
  - Add `status_bar_no_overlap_at_60_cols` — render at 60, read the
    buffer, assert the cost span appears BEFORE the elapsed span
    (i.e. they didn't get clipped into each other). This is the test
    the current code lacks.

## Approach
1. **Priority list.** Encode it as a `const DROP_ORDER: &[StatusSpan]`
   or a slice of closures / enum variants. Keep it readable — a
   reviewer should see the priority at a glance.
2. **Drop loop.** Pure function of (area.width, left_len, spans) →
   filtered spans. No allocation in the hot path if possible (use a
   fixed bitmask over the 8 spans; the loop is 8 iterations max).
3. **Never-drop set.** `sandbox_span` (when UNSANDBOXED), `elapsed`,
   `cost`. These stay even if the bar overflows. The `⚠️` emoji is
   wide (2 cells) — account for that in the width math (the existing
   code uses `.content.chars().count()` which counts emoji as 1;
   verify this is correct for the sandbox span — it may already be
   off-by-one on emoji width, which is a separate bug worth noting in
   `lessons.md` but not blocking).
4. **Tests at multiple widths.** The existing 80-col test is the
   ceiling; add 60, 40. Use the `status_row` helper that already
   exists (line 187).
5. **Don't touch the left `left_info` span.** It carries the model
   name + connection state — always show it. If it's too long, that's
   a separate truncation problem (out of scope; the REVIEW doesn't
   name it).

## Done condition
- `render_status()` drops low-priority spans (plugin, skills,
  tool-calls, Ctrl+T) before overlapping; keeps elapsed, cost, and
  the UNSANDBOXED warning at all widths
- At 60 cols: plugin + skills spans are gone, cost + elapsed present
- At 40 cols: only elapsed, cost, and (if unsandboxed) the warning
  remain; no crash, no panic
- 3 new tests pass (drop-plugin-below-70, keep-unsandboxed-at-40,
  no-overlap-at-60)
- `docs/TECHNICAL.md` TUI section: one-line note that the status bar
  degrades by priority on narrow terminals (doc-sync per §9 — the
  status bar is user-visible surface)
- ADR not needed (presentation policy, not architecture)
- Depends on: nothing

## Notes
- The REVIEW's "no terminal resize graceful degradation" point
  overlaps with this; the fix here (priority-based rendering) handles
  resize because `render_status` is called on every frame, so a
  resize to 40 cols immediately re-runs the drop loop.
- The emoji-width off-by-one (`chars().count()` on `⚠️`) is a real
  but separate issue. Note it in `lessons.md` if confirmed; don't
  fix it here unless it makes the drop loop math wrong (it might —
  if the sandbox span reports 13 chars but renders 14 cells, the
  "fits" check is off by one). If so, fix the width calculation to
  use `unicode-width::UnicodeWidthStr::width` if that crate is
  already a dep (grep Cargo.toml — ratatui pulls it transitively, so
  it's likely free), else account for the known emoji manually.
- Preserve any `ponytail:` / `ceiling:` annotations in `status.rs`
  (grep first — the test at line 205 has a comment but no ponytail).
