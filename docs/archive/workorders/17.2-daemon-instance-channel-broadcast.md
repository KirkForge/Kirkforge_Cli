# Workorder 17.2 — Daemon Instance Control Channel + Event Broadcast

## Status: Done

## Problem
vix's daemon keeps one long-lived control connection per vix *instance* (TUI
window) for its whole lifetime and pushes process-level events —
`threads_changed`, `jobs_changed`, `quit` — to every window exactly once,
independent of chat threads (`internal/daemon/server.go:109-237`,
`BroadcastToInstances`, `handleInstance`). A window with no open thread still
sees live cross-window updates.

KirkForge's daemon (`src/daemon/server.rs:203-267`) is strictly
one-line-request → one-line-response. No persistent connection, no instance
registry, no push path. The TUI only touches it on fork/resolve
(`src/tui/commands/fork.rs:203,214`) and re-lists sessions by polling. Live
cross-window refresh does not exist.

## Root cause
The `Request`/`Response` enum (`src/daemon/mod.rs:121,146`) models only
request/response ops (`Ping`/`List`/`Resolve`/`Touch`/`Shutdown`). There is no
long-lived registration op and no broadcast state on `DaemonState`. The TUI
connection layer (`src/tui/connection.rs`) is an Ollama probe, not a daemon
event stream — so even if the daemon pushed, nothing subscribes.

## Files to touch
- `src/daemon/mod.rs` — add `Request::InstanceRegister` to the enum and an
  `InstanceEvent` frame type (`ThreadsChanged`, `JobsChanged`, `Quit`). Add
  `instances: Arc<Mutex<Vec<UnboundedSender<InstanceEvent>>>>` to `DaemonState`
  (the instance registry). Add `DaemonState::broadcast(ev)` that clones the
  senders and `try_send`s, dropping dead ones.
- `src/daemon/server.rs` — a new `handle_instance_register` that holds the
  `UnixStream` open in a `tokio::spawn` loop, creates an `mpsc::UnboundedChannel`
  for that instance, pushes its sender into the registry, and runs a single
  writer task that drains the channel and writes NDJSON frames to the stream
  (one writer per connection — see Notes on why). On disconnect, drop the
  sender from the registry.
- `src/jobs/daemon.rs` — when a scheduled job runs, call
  `state.broadcast(InstanceEvent::JobsChanged)` (the `jobs_changed` push vix
  fires at `server.go:398-410`). Today `daemon.rs:254-258` treats `List` as a
  reload trigger only.
- `src/daemon/server.rs` `Touch` handler — call
  `state.broadcast(InstanceEvent::ThreadsChanged)` whenever `recent` mutates,
  so all open TUIs re-list instead of polling.
- `src/tui/connection.rs` (or a new `src/tui/daemon_events.rs`) — the TUI side:
  on startup, open the instance connection, spawn a reader task that maps
  `InstanceEvent` frames to `AppState` events (e.g. set a "sessions dirty" flag
  the draw loop re-lists on, or a `jobs_dirty` flag the Jobs tab re-reads).
- Tests: `src/daemon/server.rs` `#[cfg(test)]` — register two fake instances,
  `broadcast(JobsChanged)`, assert both receive; drop one, broadcast again,
  assert only the live one receives and the dead sender was pruned.

## Approach
1. **One writer per connection.** vix dedicates a single writer goroutine per
   instance (`server.go:712-718`) so concurrent broadcasts never interleave
   NDJSON frames. Mirror this: each registered instance owns an
   `UnboundedSender<InstanceEvent>`; a single writer task owns the `UnixStream`
   and serializes frames. Do not write to the stream from multiple `tokio::spawn`
   tasks — that races.
2. **Backpressure is `try_send`.** `broadcast` uses `try_send`; a full/slow
   instance is dropped from the registry rather than blocking the broadcaster.
   This matches vix's non-blocking fanout.
3. **NDJSON framing.** Reuse the existing newline-delimited JSON convention
   the request/response path already uses — `InstanceEvent` serializes as one
   JSON object per line. Keep the registration handshake one line in, then the
   stream switches to push-only.
4. **TUI re-lists lazily.** The reader task sets dirty flags; the draw loop
   re-fetches on the next tick. Do not block the TUI event loop on a daemon
   RPC per frame.
5. **No auth yet.** This channel is unauthenticated in this WO. 17.3 adds the
   auth token that gates it. Land the channel first so 17.3 has something to
   protect.

cargo fmt --check && cargo clippy --all-targets -- -D warnings &&

## Done condition
- Two `kf-code` windows open: a job running in one is visible in the other's
  Jobs tab without manual refresh; forking a session in one updates the
  other's session list.
- A registered instance whose socket closes is pruned from the registry; a
  subsequent broadcast does not try to write to it.
- The writer-per-connection guarantee holds: a stress test firing many rapid
  broadcasts produces no interleaved/malformed NDJSON frames on the wire.
- The TUI event loop is not blocked by the daemon event reader (dirty-flag,
  not synchronous RPC, per frame).
- Depends on: nothing (foundation). 17.3 (hardening) and 17.9 (threads
  overview) depend on this.

## Notes
- This is the foundation for 17.3 (auth/version/quit/ownership all ride this
  channel) and 17.9 (a Threads-overview tab needs `ThreadsChanged`).
- Keep `DaemonState` growth bounded: the registry is one `Arc<Mutex<Vec<…>>>`.
  Do not build a generic pub/sub framework — one registry, one event type,
  `try_send`. YAGNI until a second event stream appears.
- The `jobs_changed` broadcast in `jobs/daemon.rs` is the user-visible win;
  wire it early so the feature is demonstrable before 17.3 lands.
