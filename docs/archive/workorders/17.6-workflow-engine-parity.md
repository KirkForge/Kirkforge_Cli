# Workorder 17.6 — Workflow Engine Parity: bash/tool/if/fan_out/fork_from/on_error/budget

## Status: Done

## Problem
vix's workflow engine (`internal/workflow/workflow.go` + `internal/daemon/workflow.go`)
supports `agent`, `bash`, and `tool` step types with `if` conditional branching,
`fan_out`/`fan_in` parallelism, `fork_from` history forking, per-step `on_error`
routing, a per-workflow `budget` (`max_tokens`/`max_seconds`/`max_iterations` +
`on_exceeded`), and `$()` typed-variable expansion with JSON-output extraction.

KirkForge's `crates/kf-workflow/src/lib.rs` is a static DAG of *agent-only*
steps with `depends_on` and `${var}` flat string interpolation. Concretely:
- Only `agent` steps (`Step` at `lib.rs:40` has `prompt`+`persona`); no
  `bash`/`tool` step kinds (`workflow.go:60-79`).
- No `fan_out`/`fan_in`; `WorkflowExecutor::run` (lib.rs:171) computes a
  `ready_steps` frontier and exposes `run_batch`, but the production runner
  `TaskSpawnerStepRunner` (`src/tools/workflow.rs:192`) is explicitly serial
  ("we do not fan out here") and the TUI runner (`src/tui/commands/workflow.rs:254`)
  doesn't override `run_batch`.
- No `fork_from` — every step spawns a fresh isolated subagent with no
  inherited history (`workflow.go:66` `ForkFrom`).
- No `if` conditional step; only static `depends_on` edges (`workflow.go:84-87`).
- No `on_error` per-step routing; `WorkflowExecutor::run` (lib.rs:249) bails
  the whole workflow on any step error (`workflow.go:82` `OnError`).
- No `budget`; a runaway workflow runs until the runner returns
  (`workflow.go:109-114` `Budget`).
- `interpolate_vars` (`src/tools/workflow.rs:134`) does flat `${name}`
  substitution only — no typed var pool, no JSON extraction, no `$()`
  (`workflow.go:68` `$()`, `daemon/workflow.go:1152/1522`).

## Root cause
kf-workflow was built as a linear agent-pipeline runner; vix's was built as a
general programmable pipeline. The `Step` struct and executor need to grow the
missing step kinds and control flow without becoming a Turing-complete DSL.

## Files to touch
- `crates/kf-workflow/src/lib.rs` — extend `Step` with a `kind` enum
  (`Agent`/`Bash`/`Tool`) and the new fields: `if: Option<Condition>`,
  `fork_from: Option<StepId>`, `on_error: Option<StepId>`. Add a `Budget` block
  on `Workflow` (`max_tokens`/`max_seconds`/`max_iterations`/`on_exceeded`).
  Add `fan_out`/`fan_in` step kinds (with `over`/`as`/`max_parallel`,
  mirroring `workflow.go:83-98`). Validate the schema in `Workflow::validate`.
- `crates/kf-workflow/src/lib.rs` `WorkflowExecutor::run` — implement parallel
  `run_batch` via `tokio::spawn` per ready step (the frontier already exists);
  route `Err` to `on_error` instead of returning; check `budget` between
  batches and route to `on_exceeded` once; support `if` by evaluating the
  condition and taking `then`/`else` edges.
- `src/tools/workflow.rs` — `TaskSpawnerStepRunner`: implement `run_batch`
  with real parallelism (drop the "we do not fan out here" serial comment);
  add `Bash` step dispatch (reuse `crate::tools::bash`) and `Tool` step
  dispatch (reuse the tool registry); implement `fork_from` by cloning the
  named step's agent handle into the new step.
- `src/tools/workflow.rs` `interpolate_vars` — add `$()` expansion and a
  typed-var pool so a step can consume a prior step's structured output
  (e.g. a JSON list for `fan_out` to iterate). Add JSON-output extraction
  (`json_output`/`display_key`).
- `src/tui/commands/workflow.rs` — override `run_batch` in `TuiStepRunner` to
  match (currently it inherits the serial default).
- Tests: `crates/kf-workflow` — `fan_out` runs N branches in parallel and
  `fan_in` waits on all; `if` takes the right branch; `on_error` routes a
  failing step instead of aborting; `budget.max_seconds` routes to
  `on_exceeded`; `fork_from` resumes from a prior step's history;
  `$()` expands a prior step's JSON output.

## Approach
1. **Step kinds first.** Add `Agent`/`Bash`/`Tool` to `Step` and dispatch in
   `run`. `Bash` reuses the existing bash tool; `Tool` reuses the registry. No
   new execution engine — reuse what exists.
2. **Parallel `run_batch`.** The frontier (`ready_steps`) is already there;
   `spawn` each ready step, `join_all`, collect. This is the cheap win vix has
   and kf-code explicitly punted on.
3. **`fork_from` needs a cloneable agent handle.** Thread a cloneable handle
   through `StepRunner` so a step can resume from a prior step's conversation
   rather than starting fresh. This is the cross-phase history vix clones at
   `daemon/workflow.go:878`.
4. **`if`/`on_error`/`budget` are graph edges + a guard.** `if` adds conditional
   edges; `on_error` routes `Err`; `budget` is one check between batches
   routing to `on_exceeded`. Keep them as edges/guards, not a new interpreter.
5. **Typed vars + `$()`.** A typed-var pool (HashMap<String, Value>) is
   populated by step outputs; `$()` expands a prior step's JSON field;
   `fan_out.over` iterates a list value. Keep `${name}` flat interpolation
   alongside it.
6. **Don't build a DSL.** Conditions are shell-evaluated (vix uses bash
   `condition`); branching is declarative edges. No general expression
   language.

## Done condition
- A workflow can run `bash` and `tool` steps, not just `agent` steps.
- `fan_out` runs branches in parallel and `fan_in` joins them (verified by
  timing + ordering in tests).
- `if` branches on a condition; `on_error` routes a failing step to a
  declared step instead of aborting the whole workflow.
- `budget.max_seconds`/`max_tokens`/`max_iterations` routes to `on_exceeded`
  once when exceeded.
- `fork_from` resumes a step from a prior step's conversation history.
- `$()` expands a prior step's JSON output; `fan_out.over` iterates a list.
- `docs/TECHNICAL.md` (Workflows section) documents the new step kinds and
  control flow; a short ADR if the `Step` shape change warrants it.
- Depends on: nothing. 17.7 (jobs↔workflow) builds on this.

## Notes
- This is a big workorder. Land step-kinds + parallel `run_batch` first (the
  cheapest, highest-user-visible wins), then `on_error`/`budget`/`if`, then
  `fork_from` + typed vars (the most involved). Each can be a sub-PR.
- `fork_from` and 17.5's shared stem interact: a forked step shares the stem
  (cached) but forks the conversation tail. Confirm the stem stays
  byte-identical across forks so the cache still hits.
- Keep `kf-workflow` a library; the `TaskSpawnerStepRunner`/`TuiStepRunner`
  are the only execution backends. Do not invent a third.
- Do not add a visual workflow editor (Series 18 at earliest); this WO is the
  engine + schema.
