# Workorder 17.8 — E2E Test Harness: Binary Driver + Mock Provider + PTY + Regression Catalog

## Status: Done

## Problem
vix has a real binary-driving e2e harness (`e2e/harness/`): `start.go` spawns
the real `vixd` + `vix` binaries per test in an isolated HOME/workdir/socket
tree; `ui.go` drives the TUI inside a tmux server (`send-keys`/`capture-pane`);
`mock.go` is an in-process HTTP server speaking three provider dialects
(Anthropic Messages, OpenAI Responses, OpenAI Chat Completions) with scripted
`Reply`s and request history; `confirm.go` drives the approval panel;
`shard.go` shards across CI runners; and `e2e/scenarios/` has ~53 named
regression scenarios each tied to an issue.

KirkForge tests the executor *in-process* only:
- `tests/smoke_test.rs` runs `kf-code metrics`/`completions`/`--help` — no
  agent loop, no TUI.
- `tests/integration_test.rs` is `#[ignore]`-gated raw HTTP against a *real*
  Ollama; `tests/mock_ollama.rs` mocks Ollama NDJSON for a raw reqwest parser,
  never pointing the real `kf-code` binary at it.
- `src/session/executor/tests/` use an in-process `MockAdapter` + `MockTool`,
  never spawning `kf-code` and never touching the TUI.
- TUI "tests" are `ratatui::backend::TestBackend` widget-buffer asserts — no
  key-event driving, no full-app loop.
- No binary-driving harness, no mock provider server the real binary uses, no
  TUI/PTY driver, no regression catalog, no sharding, no on-failure artifact
  dump.

## Root cause
Testing was done at the unit/integration layer because that's cheap; nobody
built the binary-driving layer that catches wire-format, adapter, TUI, and
daemon integration regressions. vix's harness is the model.

## Files to touch
- `tests/e2e/` (new) — the harness:
  - `harness/mod.rs` — `start()` builds an isolated env (tempdir HOME + XDG
    dirs + config + a temp socket dir), spawns `kf-code daemon` and `kf-code
    run` via `std::process::Command` (or `cargo`'s `CARGO_BIN_EXE_kf-code` for
    dev runs), and tears down on drop.
  - `harness/mock.rs` — an in-test `axum` (or `wiremock`) server exposing
    `/v1/messages` (Anthropic), `/v1/chat/completions` (OpenAI-compat), and
    `/api/chat` (Ollama NDJSON), with scripted `StreamEvent` responses, a
    request-history recorder, and an `http_error` injector for the retry
    classifier. Point `kf-code` at it via `OLLAMA_HOST` / the provider base_url
    config so the *real binary* hits the mock.
  - `harness/ui.rs` — a PTY driver. Launch `kf-code run` in a tmux server
    (`tmux -S <sock>`) or `portable-pty`; `send_keys`, `capture-pane`, wait-for
    / contains / wait-stable helpers. (tmux is what vix uses and is simplest;
    prefer it unless Windows parity is needed, then `portable-pty`.)
  - `harness/confirm.rs` — detect the approval modal and send `y`/`n` so
    tool-approval flows don't hang.
  - `harness/shard.rs` — a `shard_gate(name)` keyed on `KF_SHARD_INDEX` /
    `KF_SHARD_TOTAL` (hash the test name) so the suite fans across CI runners.
  - `harness/artifact.rs` — on failure, dump the PTY screen, the mock request
    history, and the `kf-code` log to a per-test artifact dir.
- `tests/e2e/scenarios/` (new) — one file per regression, each spawning the
  binary against the mock and pinning the user-visible behavior. Start with a
  small catalog (5–8) covering: a plain chat turn, a tool approval round-trip,
  a fork, a scheduled job firing, an adapter retry on a mock 5xx, a TUI tab
  switch. Tie each to a past bug where one exists.
- `tests/e2e/fixtures.rs` — seed `config.toml`, hooks dirs, MCP server specs,
  and `.kirk/` state into the isolated HOME before launch (vix's
  `WithSettings`/`WithHomeFile`/`{{MOCK_URL}}`).
- `Cargo.toml` — add dev-deps: `axum` or `wiremock` (whichever is already a
  dep — `wiremock` is, per `tests/mock_ollama.rs`), `portable-pty` if not
  using tmux, `chrono` (likely already present).

## Approach
1. **Mock provider server is the keystone.** Without it the binary can't run
   deterministically. Serve all three dialects from one `axum`/`wiremock` app;
   scripted replies via a queue; record every request for wire assertions.
   Point the real `kf-code` at it through config/env, not a test-only code
   path — the goal is to exercise the real adapter code.
2. **Binary driver via `CARGO_BIN_EXE_kf-code`.** Each test gets an isolated
   HOME/socket/config so tests don't collide; tear down on drop. This is what
   `crates/kf-budget-cli/tests/end_to_end_smoke.rs` already does for the
   sidecar — generalize it to the main binary.
3. **PTY driver: tmux first.** `tmux -S <sock> new-session -d`, `send-keys`,
   `capture-pane -p`. It's what vix uses and gives faithful rendering. Only
   reach for `portable-pty` if Windows TUI testing becomes a goal.
4. **Approval driver.** Detect the modal text the approval component renders
   (grep `src/tui/components/approval.rs` for the rendered strings) and send
   the right key. This is what lets tool-approval flows complete in e2e.
5. **Regression catalog grows over time.** Start small (5–8), one per past
   bug, each pinned. The point is the *harness*, not 53 scenarios on day one.
6. **Sharding is a one-function gate.** `shard_gate(test_name)` returns true
   if this runner owns the test. CI sets `KF_SHARD_INDEX`/`KF_SHARD_TOTAL`.
7. **On-failure artifacts.** A failed e2e test should leave a screen capture,
   the mock request log, and the binary log — not just cargo stdout. This is
   what makes e2e failures debuggable.

## Gate
```
cargo fmt --check && cargo clippy --all-targets -- -D warnings &&
cargo test --locked --workspace --no-fail-fast &&
cargo test --test e2e -- --test-threads=1   # isolated envs, serial at first
```

## Done condition
- A `tests/e2e/` harness spawns the real `kf-code daemon` + `kf-code run`
  binaries against an in-test mock provider in an isolated HOME; the binaries
  are exercised end to end (adapter wire format + executor + TUI), not just
  the executor in-process.
- The mock server serves Anthropic/OpenAI-compat/Ollama dialects with scripted
  replies, records request history, and can inject HTTP errors.
- A PTY driver launches `kf-code run` in tmux, sends keystrokes, and asserts
  on `capture-pane` output — including driving the approval modal to
  completion.
- A starter regression catalog (5–8 scenarios) pins real user-visible
  behaviors, each tied to a past bug where one exists.
- `KF_SHARD_INDEX`/`KF_SHARD_TOTAL` shards the suite across runners.
- On failure, a per-test artifact dir holds the screen, mock history, and log.
- Depends on: nothing strictly, but 17.1 (working Anthropic adapter) and 17.2
  (daemon channel) make the harness more representative — land this alongside
  them, not blocked on them.

## Notes
- This is the highest-leverage testing work in the series and the safety net
  for 17.1–17.7. Land the mock server + binary driver first; the PTY driver and
  regression catalog can grow incrementally.
- Start serial (`--test-threads=1`); isolated envs make parallelism safe but
  tmux sockets and ports need care. Parallelize once stable.
- Reuse `wiremock` (already a dep) for the mock server rather than pulling
  `axum` if it covers the dialects — fewer new deps (ponytail). Switch only if
  streaming NDJSON/SSE needs it.
- The `crates/kf-budget-cli/tests/end_to_end_smoke.rs` subprocess pattern is
  the local precedent — generalize, don't reinvent.
- Do not build a test framework; build a harness with a few helpers. YAGNI on
  golden-master comparison libraries etc.
