# Workorder 19.2 — Testdoctor: Public API Surface, Not Just Line Counting

## Status: Planned

## Problem

`diagnose` counts `pub fn`, `pub struct`, `pub enum`, `pub trait` at line starts.
This misses:
- `pub const` and `pub type` aliases
- Methods inside `impl` blocks (the most common form of public API)
- `pub mod` re-exports
- `pub(crate)` and `pub(super)` items (which are not public API but count as "pub")

A 50-line file with 1 public method and 10 tests shows "high density" but tests one thing.
A 500-line file with 20 public methods and 10 tests shows "low density" but tests many
things. The metric is backwards.

## Root cause

The regex in `diagnose.rs` matches `^pub (fn|struct|enum|trait)\b` at line start.
This is a reasonable first approximation but conflates visibility with API surface.

## Fix

### 1. Count `impl` block methods as public API

Add a second pass that counts methods inside `impl TypeName { ... }` blocks where
`TypeName` matches a `pub struct` or `enum` already counted. This captures the real
API surface.

### 2. Exclude `pub(crate)` and `pub(super)` from the count

These are not public API. Only `pub` (unrestricted) should count.

### 3. Report `api_surface` instead of `pub_item_count`

Rename the metric from `pub_items` to `api_surface` = `pub fn/struct/enum/trait` +
`impl methods` - `pub(crate)` - `pub(super)`. Recompute `test_density` as
`test_count / api_surface * 100` instead of `test_count / lines * 100`.

### 4. Update `ROI` metric

`ROI = api_surface * (1 - test_density/100)`. High ROI = many public APIs with few
tests. This is a better prioritization signal than the current `lines * (1 - density/100)`.

## Verification

- `kf-testdoctor diagnose` now reports `api_surface` and `test_density` per API (not per line)
- Files with many `impl` methods show higher `api_surface` than before
- Files with only `pub(crate)` items show lower `api_surface`
- Top-25 ROI list prioritizes files that need tests most
