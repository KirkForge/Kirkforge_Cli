# Workorder 19.6 — E2E TUI Scenarios: Activate the Dormant TmuxDriver

## Status: Planned

## Problem

The e2e harness has a `TmuxDriver` and `confirm.rs` module in `tests/e2e/harness/`
that were built for interactive TUI testing, but **zero scenarios actually use them**.
All current e2e scenarios run `--no-tui --non-interactive`. The TUI has 459 unit tests
for individual components, but no test exercises the TUI as a running application.

This means: tab switching, approval modal, plugin toggle, chat input, slash commands —
all untested end-to-end. The TUI is the user's primary interface and has no e2e coverage.

## Root cause

The `TmuxDriver` was built as part of WO 17.9 (TUI parity pass) but no scenarios
were written to use it. The `ui.rs` module can send keystrokes and read screen content,
but nothing drives it.

## Fix

### Phase 1: Wire up one TUI scenario (minimal viable)

Add `tests/e2e/scenarios/tui_chat.rs` that:

1. Starts `kf-code run` (no `--no-tui`) via `IsolatedEnv`
2. Uses `TmuxDriver` to send a chat message
3. Verifies the response appears on screen
4. Sends `/quit`

This proves the harness works end-to-end. Even one scenario is a huge improvement
over zero.

### Phase 2: Approval flow

Add `tests/e2e/scenarios/tui_approval.rs` that:

1. Starts `kf-code run` with auto_approve=false
2. Sends a message that triggers a bash tool call
3. Verifies the approval modal appears
4. Presses 'y' to approve
5. Verifies the tool result appears

### Phase 3: Slash commands

Add `tests/e2e/scenarios/tui_slash.rs` that:

1. Starts `kf-code run`
2. Sends `/plugins list`
3. Verifies the plugin list appears on screen
4. Sends `/help`
5. Verifies help text appears

### Implementation notes

- All TUI scenarios should be `#[ignore]` by default (require a display server or
  headless tmux) and run in CI with `--include-ignored` in a dedicated job
- Use `IsolatedEnv::command(&["run"])` (without `--no-tui`)
- The `TmuxDriver` in `tests/e2e/harness/ui.rs` already has `send_keys`, `read_screen`,
  `wait_for_content` methods
- The `confirm.rs` module has `wait_for_approval_prompt` and `approve_current`

## Verification

- `cargo test --test e2e -- tui_chat` passes (manually, with display server)
- `cargo test --test e2e -- tui_approval` passes
- CI job runs TUI scenarios in headless tmux
