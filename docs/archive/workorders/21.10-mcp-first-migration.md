# Workorder 21.10 — MCP-First Migration

## Status: Done

## Problem

The cross-review's named strategic error is still standing in code: the bespoke
plugin system (hooks with veto, verifier bus, trust tiers, minisign) and MCP
coexist as **peers**, doubling the extension surface and locking plugin authors
into a kf-code-only format while the rest of the industry (Claude Code, Cursor,
opencode, VSCode) is MCP-native. WO 20.0.10 *wrote* the decision (MCP-first
overlay) and `TECHNICAL.md` now mentions MCP ~11× — but the architectural change
was **not shipped**: both systems still coexist as peers in code. This workorder
ships the MCP-first overlay the decision calls for, folds hooks/verifiers into
it, and deprecates the bespoke-as-peer path behind a flag with a removal WO —
with the two concrete behavior gaps the review names (shell-hook `tool_result`
visibility, post-turn timing) resolved by routing through the overlay.

**Note on the decision:** WO 20.0.10's own prose recommended "Option B" (keep
both, document). This workorder supersedes that toward **Option A (MCP-first
overlay)** per the owner direction recorded in the 21.0 overview row — the
bespoke system's differentiators (veto, verifier bus, trust tiers) become a thin
`kf-code.toml` overlay on MCP servers rather than a parallel path.

## Source

Review reality-check §4.7 ("bespoke+MCP as peers — DECISION WRITTEN, NOT
SHIPPED") + §4.3 MCP capability gaps + WO 20.0.10 decision doc. The MCP
*capability surface* (resources/prompts/sampling/roots) is delivered by 21.5-R3
/ R4; this workorder consumes that surface to land the migration.

## Targets

### 21.10-R1 — Ship the MCP-first overlay: hooks/verifiers via MCP, deprecate bespoke-as-peer (HIGH · est L · dep: 21.5-R3, 21.5-R4)

**Reality check (`a870571`):** "§4.7 bespoke+MCP as peers — 🟡 PARTIAL @
`a870571`: decision now *written* in
`docs/workorders/20.0.10-strategic-mcp-plugin-decision.md` (MCP-first overlay),
and `TECHNICAL.md` now mentions MCP ~11× (was 1× in 775 lines). The
architectural change is **not yet shipped** — both systems still coexist as
peers in code." The bespoke system lives in `src/session/hooks.rs` /
`src/session/plugin_tools/` (hooks, trust tiers, minisign, topological load);
MCP lives in `src/session/mcp_client/`. Both are documented as the primary
extension mechanism.

**Scope:** a new MCP-overlay layer that exposes hooks (pre-tool/post-tool veto,
post-turn) and the verifier bus as MCP middleware over MCP servers; the bespoke
dispatch path; `kf-code.toml` trust-tier overlay; `TECHNICAL.md` plugin-strategy
section; a deprecation feature flag + a removal WO ID.

**Success (done):**
- Hooks and verifier integration execute **via the MCP overlay path in
  production** (a pre-tool hook can veto a tool call, and a verifier fires after
  a file-modifying tool call, both routed through the MCP overlay — not the
  bespoke-as-peer path).
- A test asserts a named hook (e.g. a deny-veto hook) fires through the MCP
  overlay and actually vetoes the tool call end-to-end; an existing bespoke
  plugin is shown working unchanged through the overlay (migration parity).
- The bespoke-as-peer path is moved behind a `deprecated-bespoke-plugins`
  feature flag with a removal WO ID recorded inline + in `state.md` "pending"
  (AGENTS.md rule #11 defer-disclosure); the default build routes through MCP.
- `TECHNICAL.md` documents the MCP-first model and the deprecation/removal
  timeline.

**Failure (regression / not-done):**
- An overlay added but the bespoke-as-peer path still runs by default in
  production (both still peers) = FAIL (the migration did not happen).
- A hook veto routed through MCP silently fails-open (veto lost) = FAIL (safety
  regression on the veto surface — the bespoke system's load-bearing feature).
- Bespoke path deprecated with no removal WO ID / no `state.md` pending entry =
  FAIL (silent deferral, AGENTS.md rule #11).

**Defer:** DEFER-2110-R1 — full *removal* of the bespoke path is a separate
follow-up WO (record the ID here once opened); the migration (overlay ships,
bespoke flagged off-by-default) must land in this series. R1 may stage: (1)
overlay ships alongside, (2) default flips, (3) bespoke flagged — each gated and
disclosed.

### 21.10-R2 — Resolve shell-hook `tool_result` visibility via the overlay (MEDIUM · est M · dep: 21.10-R1)

**Reality check (`a870571`):** "Shell hooks cannot see `tool_result` content —
admitted in `hooks.rs:46-63. Still true." Re-verified: **partially resolved** —
`src/session/hooks.rs:56-61` now gives *in-process* hooks a
`tool_result: Option<String>` field ("the key field that shell hooks could NOT
access — it gives in-process hooks like the budget guard real visibility"), but
*shell* hooks still receive only env vars. The MCP overlay is the path that
gives every hook (including shell-out equivalents) result visibility uniformly.

**Scope:** the MCP overlay's post-tool hook contract (result content passed to
the hook server), `src/session/hooks.rs` (shell-hook parity via the overlay).

**Success (done):**
- A hook served by an MCP server receives the tool-result content (the budget/
  verifier hook can see what the tool returned) and can act on it — demonstrated
  by a hook that vetoes based on result content.
- A test asserts a result-content-aware veto fires through the MCP overlay
  (parity with the in-process `tool_result` path), closing the shell-hook
  visibility gap the review names.

**Failure (regression / not-done):**
- Overlay ships but post-tool hooks still receive only env-var args (no result
  content) = FAIL (the named gap stays open).
- Result content leaked to an untrusted MCP server without a trust-tier gate =
  FAIL (security regression — result content can be sensitive).

**Defer:** none.

### 21.10-R3 — Fix post-turn hook timing: fire before turn commit, not async-after (MEDIUM · est M · dep: 21.10-R1)

**Reality check (`a870571`):** "Post-turn hooks fire async after the turn
commits (`turn.rs:39-59`) — observational only. Still true." Re-verified:
`src/session/executor/turn.rs:39-59` is `PostTurnHookGuard::drop`, which
`tokio::spawn`s the hook run so it fires asynchronously after the turn has
already committed — a post-turn hook therefore cannot gate or modify the turn,
only observe it. STILL TRUE.

**Scope:** `src/session/executor/turn.rs:39-59` (move post-turn hooks onto a
synchronous, pre-commit point in the turn loop — or a defined gate the overlay
can veto through), the MCP overlay's post-turn contract.

**Success (done):**
- A post-turn hook fires at a defined point where it can still influence the
  turn outcome (e.g. veto / force a follow-up), not purely async-observational
  after commit; the MCP overlay exposes this timing.
- A test asserts a post-turn hook's effect is observable *within* the turn (e.g.
  it blocks or amends the committed result), proving it is no longer
  fire-and-forget.

**Failure (regression / not-done):**
- Hooks moved earlier but still async (race: the turn commits before the hook
  resolves) = FAIL.
- Making post-turn hooks synchronous regresses turn latency measurably with no
  bounded timeout = FAIL (must keep a bounded gate).

**Defer:** DEFER-2110-R3 — a hook that genuinely needs fire-and-forget
observational behavior may keep an async mode behind a flag; the
*pre-commit/veto-capable* timing must exist as the default.
