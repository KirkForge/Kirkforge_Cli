Five architecture-level issues from the review: per-session offload store
scoping, inconsistent token estimation, monolithic AppState, hook return type
split, CorrectionResult missing file/line, and verifier findings not pinned
in compaction tail.

Review Part 4 §4.6 (architecture smells). WO 22.0 overview §22.6.

### 22.6-R1 — Unify token estimation (HIGH · est S · dep: —)

**Reality check:** Before the subagent fix, token estimation used `chars/4` in
4 separate call sites (`prompt/mod.rs`, `prompt/compaction.rs`,
`prompt/microcompaction.rs`, `prompt/summarizer.rs`) with no shared function.

**What was done (subagent):** All 4 call sites now route through
`count_tokens()` in `src/session/prompt/mod.rs:20-25`. The function is
`pub(crate)` and provides a single source of truth. All callers use
`super::count_tokens()` or `crate::session::prompt::count_tokens()`.

**Remaining:**
- Verify no remaining `chars / 4` or `.len() / 4` token estimation outside
  the unified function.
- Consider renaming `count_tokens` to `estimate_tokens` to clarify it's an
  estimate, not an exact count.

**Scope:** `src/session/prompt/mod.rs`, `src/session/prompt/compaction.rs`,
`src/session/prompt/microcompaction.rs`, `src/session/prompt/summarizer.rs`,
`src/session/memory/mod.rs`.

**Success criteria:**
- All token estimation goes through `count_tokens()` — no inline `chars / 4`
  or `.len() / 4` in production code.
- `cargo clippy` and `cargo test` green.

**Failure criteria:** Any inline token estimation outside `count_tokens()`.

**Estimate:** S (done)

**Defer note:** none.

### 22.6-R2 — Per-session offload store (HIGH · est L · dep: —)

**Reality check:** `src/session/stratum.rs:21` —
`static SESSION_OFFLOAD_STORE: OnceLock<Arc<InMemoryOffloadStore>> = OnceLock::new()`
is process-global. All sessions share the same offload store, meaning a
long-lived process with multiple sessions accumulates entries forever with no
eviction. The same pattern appears in `budget.rs:22-23` for
`SHARED_BUDGET`/`SHARED_STORE`.

**What was done (subagent):** No change was made. The `OnceLock` pattern
remains process-global.

**Remaining:**
- Replace `SESSION_OFFLOAD_STORE` OnceLock with a session-scoped store
  (passed through the `Executor` or `Session` struct, not a global).
- Add an LRU cap (e.g. max 1000 entries, evict oldest when full) to prevent
  unbounded growth.
- Same for `SHARED_STORE` in `budget.rs`.
- The `session_offload_store()` function should take a session ID or be a
  method on a session-scoped struct.

**Scope:** `src/session/stratum.rs`, `src/session/budget.rs`,
`src/session/executor/mod.rs`, `src/main/run_session.rs`.

**Success criteria:**
- Offload store is per-session (not `OnceLock` global).
- LRU cap prevents unbounded growth (configurable, default 1000).
- Existing tests pass (they create `InMemoryOffloadStore::new()` per test,
  which is already session-scoped).
- No process-global mutable state for offload storage.

**Failure criteria:** OnceLock global still in production. Unbounded store
growth. Test regression.

**Estimate:** L

**Defer note:** DEFER-226-R2 — requires refactoring the Executor/Session
lifecycle to thread the store through. Large change, high risk of regression.
Tracked in PONYTAIL-DEBT.md.

### 22.6-R4 — Hook return type split (MEDIUM · est M · dep: —)

**Reality check:** Hook functions currently return `HookDecision` (which has
`Allow`, `Deny`, `Modify` variants). Post-hooks don't use `Deny` or `Modify`
— they only need to signal success/failure for logging. The return type is
over-specified for post-hooks.

**What was done (subagent):** No change was made.

**Remaining:**
- Split hook return type: pre-hooks keep `HookDecision`, post-hooks return
  `()` (or `Result<(), HookError>`).
- Update all post-hook call sites to use the simpler return type.
- Update hook trait documentation.

**Scope:** `src/session/hooks/`, `src/session/executor/`.

**Success criteria:**
- Pre-hooks return `HookDecision`.
- Post-hooks return `()` or `Result<(), HookError>`.
- No post-hook returns `HookDecision::Deny` or `Modify`.

**Failure criteria:** Post-hooks still return `HookDecision`. Test regression.

**Estimate:** M

**Defer note:** DEFER-226-R4 — API improvement, not a bug. The current return
type works, it's just over-specified. Tracked in PONYTAIL-DEBT.md.

### 22.6-R5 — CorrectionResult file/line fields (MEDIUM · est S · dep: —)

**Reality check:** `src/session/verifier/correction.rs:142-147` —
`CorrectionResult` has `verifier`, `success`, `message`, `fix` fields but
no `file` or `line` fields. When a verifier flags an error in a specific file
and line, that information is lost in the `CorrectionResult` — it's only in
the `Verdict::Fixable`/`Verdict::Unfixable` inner data, which the correction
loop doesn't propagate to `CorrectionResult`.

**What was done (subagent):** No change was made to `CorrectionResult` struct.

**Remaining:**
- Add `file: Option<PathBuf>` and `line: Option<u32>` fields to
  `CorrectionResult`.
- Populate them from the `Verdict::Fixable`/`Unfixable` data when constructing
  `CorrectionResult` in the correction loop.
- Display file:line in the TUI correction output.

**Scope:** `src/session/verifier/correction.rs`,
`src/session/verifier/handler.rs`, `src/session/executor/dispatch.rs`,
`src/tui/`.

**Success criteria:**
- `CorrectionResult` has `file: Option<PathBuf>` and `line: Option<u32>`.
- Correction loop populates these from verdict data.
- TUI displays file:line when available.

**Failure criteria:** `CorrectionResult` still lacks file/line. Verifier
findings are not surfaced to the user with location info.

**Estimate:** S

**Defer note:** DEFER-226-R5 — UX improvement, not a bug. The `message` field
currently contains file:line info as a string. Structured fields are better
but not blocking. Tracked in PONYTAIL-DEBT.md.

### 22.6-R6 — Pin verifier findings in compaction tail (LOW · est M · dep: —)

**Reality check:** When the conversation is compacted (summarized), verifier
findings from earlier turns are lost — they're in the compacted-away portion
of the conversation. The model then has no context that a file was flagged.

**What was done (subagent):** No change was made.

**Remaining:**
- When compaction occurs, pin unresolved verifier findings (from
  `CorrectionResult`) into the compaction tail — append a summary block to the
  compacted conversation so the model still knows about flagged files.
- This requires the compaction path to access the correction loop's pending
  findings.

**Scope:** `src/session/prompt/compaction.rs`, `src/session/verifier/`,
`src/session/executor/turn.rs`.

**Success criteria:**
- After compaction, the conversation includes a summary of unresolved verifier
  findings.
- Model can see which files were flagged even after compaction.

**Failure criteria:** Verifier findings lost after compaction.

**Estimate:** M

**Defer note:** DEFER-226-R6 — important for long sessions but not a
ship-blocker. Compaction is rare for short sessions. Tracked in PONYTAIL-DEBT.md.
