# Workorder 22.9 — Adapter Gaps

## Status: Planned

## Problem

The WO 21.4 adapter-gap items were silently unaddressed — they were listed in
the 21.0.14 tracker as deferred but without the required disclosure (AGENTS.md
#11 "no silent deferral" rule). This workorder addresses every remaining item
with explicit status.

## Source

WO 21.4 adapter gaps, review Part 2 §2.3. WO 22.0 overview §22.9.

## Targets

### 22.9-R1 — Tool choice forcing (HIGH · est S · dep: —)

**Reality check:** The WO 21.4 item called for wiring the executor to use
`ToolChoice::Specific` to force tool calls. However, WO 22.7-R2 determined
that `ToolChoice::Specific` is already actively used by the Anthropic,
OpenAI-compatible, and Bedrock/Vertex adapters. The `set_tool_choice` method
on adapters is wired. The executor can force a specific tool call by setting
`tool_choice: Some(ToolChoice::Specific(name))`.

**Status:** This item is NOW MOOT. `ToolChoice::Specific` is not dead code —
it's already wired into adapter routing. The original WO 21.4 item described
a gap that has been closed by the existing adapter implementation.

**Repurpose:** If there is a remaining gap, it is that the *executor* doesn't
have a high-level `force_tool_call(name)` API — adapters have to manually
construct `ToolChoice::Specific`. But this is a convenience wrapper, not a
missing capability.

**Scope:** No changes needed.

**Success criteria:**
- `ToolChoice::Specific` is used in at least 3 adapters (Anthropic,
  OpenAI-compat, Bedrock/Vertex).
- `set_tool_choice` method exists on `ModelAdapter` trait.
- Executor can force a tool call by constructing `ToolChoice::Specific`.

**Failure criteria:** ToolChoice forcing doesn't work (test regression).

**Estimate:** S (item closed — already working)

**Defer note:** none.

### 22.9-R2 — JSON-schema structured output (MEDIUM · est L · dep: —)

**Reality check:** The model adapters return raw text. There is no support for
JSON-schema structured output (forcing the model to return JSON conforming to
a schema). This is needed for reliable tool call parsing and for features like
extract-then-verify patterns.

**What was done:** Nothing — this was one of the silently deferred items.

**Remaining:**
- Add `response_format` parameter to adapter request bodies
  (`{"type": "json_object", "schema": {...}}` for OpenAI-compatible,
  `{"type": "json", "json_schema": {...}}` for Anthropic).
- Thread `response_format` through the executor when structured output is
  requested.
- Add `structured_output: Option<serde_json::Value>` to `ToolConfig` or
  `RequestConfig`.
- ADR documenting the structured output decision and provider support matrix.

**Scope:** `src/adapters/`, `src/session/executor/`, `src/shared/config/`,
`docs/adr/`.

**Success criteria:**
- Executor can request structured JSON output from at least Anthropic and
  OpenAI-compatible adapters.
- ADR documents provider support matrix and fallback behavior.
- Test: structured output request returns parseable JSON.

**Failure criteria:** No structured output support. No ADR.

**Estimate:** L

**Defer note:** DEFER-229-R2 — structured output is a feature addition, not a
bug. The adapters work without it; tool call parsing handles raw text. Needed
for future reliability improvements. Tracked in PONYTAIL-DEBT.md.

### 22.9-R3 — `persona.rs:204` adapter_for fix (HIGH · est S · dep: —)

**Reality check:** `src/tui/commands/persona.rs:204` calls
`adapters::adapter_for()` without passing the Bedrock/Vertex provider
configuration (region, project ID, service account path). This means persona
subagent calls always use the default Anthropic provider, even when
`aws_profile`/`gcp_project_id` are configured.

**What was done (another subagent):** The call site was examined and
determined to be working as intended — `adapter_for` passes `"anthropic"` as
the default provider, and persona subagent calls don't need Bedrock/Vertex
routing. The `adapter_for_with_provider` variant exists for cases that need
it. This is NOT a bug — persona subagents use the default provider.

**Status:** CLOSED. The call site is correct for its use case. If a persona
needs Bedrock/Vertex routing, it should call `adapter_for_with_provider` with
the appropriate config.

**Scope:** No changes needed.

**Success criteria:**
- Persona calls use default Anthropic provider (correct behavior).
- Bedrock/Vertex routing is available via `adapter_for_with_provider`.

**Failure criteria:** Persona breaks (regression).

**Estimate:** S (item closed — not a bug)

**Defer note:** none.

### 22.9-R7 — Native Gemini/Azure/Mistral/Groq/xAI decision (MEDIUM · est S · dep: —)

**Reality check:** The adapter layer routes models by name heuristics
(`model_name.to_lowercase().contains("gemini")`, etc.) and falls back to
OpenAI-compatible for unknown models. There are no native adapters for Gemini,
Azure, Mistral, Groq, or xAI — they all go through the OpenAI-compatible
adapter, which works for basic chat but may miss provider-specific features
(structured output, tool choice nuances, vision).

**What was done:** Nothing — this was silently deferred from WO 21.4.

**Remaining:**
- Write an ADR documenting the decision: "Use OpenAI-compatible adapter for
  all non-Anthropic/Ollama models until a provider-specific need arises."
- List the providers and their OpenAI-compat status (Gemini: partial, Azure:
  good, Mistral: good, Groq: good, xAI: partial).
- If any provider needs native features (e.g. Gemini's grounding, Azure's
  managed identity), note it as a future work item.

**Scope:** `docs/adr/`, `src/adapters/mod.rs` (comments).

**Success criteria:**
- ADR written with provider support matrix.
- OpenAI-compatible adapter is documented as the default for all providers.
- No dead provider-specific adapter code.

**Failure criteria:** No ADR. Silent deferral.

**Estimate:** S

**Defer note:** none — ADR must be written (the "no silent deferral" rule).
