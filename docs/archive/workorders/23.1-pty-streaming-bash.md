# Workorder 23.1 — PTY + Streaming for Bash

## Status: Planned

## Problem

`bash` captures stdout/stderr via pipes (`Stdio::piped`). Interactive commands (`vim`, `top`, `python REPL`, anything expecting a TTY) hang or misbehave because there is no PTY allocation. The codebase has a `ponytail:` comment at `bash.rs:13-17` explicitly deferring this, noting the ~2 MB binary cost of `portable-pty`.

Without PTY:
- Interactive commands deadlock (no stdin forwarding, no TTY sizing).
- Partial output is invisible until the process exits — long-running commands appear to hang.
- The model cannot interact with REPLs, debuggers, or anything that needs terminal capabilities.

## Source

Review #16 (Phase 2). `bash.rs:13-17` ponytail deferral. Review §4.3: "bash still no PTY/streaming."

## Scope

1. `src/tools/bash.rs` — add `cfg(feature = "pty")` path that spawns via `portable-pty` instead of `Command`
2. `src/tools/bash_runner/mod.rs` — PTY-aware command execution; stream partial output via channel
3. `src/tools/bash_runner/landlock.rs` — landlock must compose with PTY (sandbox + PTY)
4. `src/tools/bash_minify.rs` — no changes (output agnostic)
5. `Cargo.toml` — add optional `portable-pty` dependency under `[features]`
6. `docs/TECHNICAL.md` — document PTY feature flag

## Targets

### 23.1-R1 — Add `portable-pty` dependency behind feature flag (est S)

**Reality check:** `bash.rs:13-17` documents the deferral. `portable-pty` adds ~2 MB to the release binary. The existing pipe-based path works for all non-interactive commands.

**Plan:**
- Add `portable-pty` as an optional dependency in `Cargo.toml` under `[features]` as `pty = ["portable-pty"]`
- Release profile remains `default-features = false` — PTY is opt-in at build time
- Document in `docs/TECHNICAL.md`

**Success criteria:**
- `cargo build` (no `--features pty`) produces same binary size as current
- `cargo build --features pty` compiles green
- `cargo test --workspace` green both with and without `--features pty`

**Failure criteria:** Binary size regression on default build. Compile failure with `--features pty`.

**Estimate:** S

### 23.1-R2 — PTY execution path (est L)

**Reality check:** `bash.rs:230-330` uses `Command::new` with `Stdio::piped()`. The PTY path needs to:
1. Allocate a PTY via `portable-pty`
2. Set terminal size (default 80x24, configurable)
3. Stream output incrementally through a channel (not wait for exit)
4. Forward stdin if the command is interactive
5. Compose with landlock sandbox (pre-exec must still apply)

**Plan:**
- Add `PtyRunner` struct in `bash_runner/pty.rs` (gated by `cfg(feature = "pty")`)
- `PtyRunner::run()` allocates PTY, spawns child, returns a channel for streaming output
- Wire into `Bash::run()`: if `cfg!(feature = "pty")` and `--interactive` flag is set, use PTY path; otherwise existing pipe path
- Add `interactive: bool` parameter to bash tool schema (default `false`)
- Compose with landlock: `PtyRunner` accepts a `pre_exec` closure like the existing path

**Success criteria:**
- `bash` tool with `interactive=false` (default) works identically to current pipe-based execution
- `bash` tool with `interactive=true` + `--features pty` allocates a PTY, streams partial output
- Interactive commands (`python3 -c "print('hello')"` at minimum) produce visible output before exit
- Landlock sandbox still applies on PTY path
- Timeout and deny-list still work on PTY path

**Failure criteria:** PTY path hangs on interactive commands. PTY path bypasses sandbox. Default (non-PTY) path regresses.

**Estimate:** L

### 23.1-R3 — Stream partial output to TUI (est M)

**Reality check:** Currently `bash` waits for process exit, then returns full output. For long-running commands, the model and user see nothing until the command finishes.

**Plan:**
- Add `TurnEvent::BashPartialOutput { job_id, output }` event type
- In PTY mode, forward incremental PTY output through `event_tx` so the TUI can show progress
- In non-PTY mode, no change (existing behavior)
- TUI renders partial bash output in the existing tool-result card with a `[streaming...]` indicator

**Success criteria:**
- Long-running command in PTY mode shows partial output in TUI before completion
- Non-PTY mode is unchanged
- Partial output events don't leak into the conversation log (they're display-only)

**Failure criteria:** Partial output corrupts conversation log. Non-PTY mode regresses.

**Estimate:** M

**Defer note:** R3 can be deferred independently — streaming output is UX polish, not a correctness fix. R1+R2 are the core PTY capability.
