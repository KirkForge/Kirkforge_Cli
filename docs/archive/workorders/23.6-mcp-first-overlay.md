# Workorder 23.6 — MCP-First Overlay (ADR-050 Decision, Not Shipped)

## Problem

The cross-review identified that the bespoke plugin system and MCP coexist as peers, doubling the extension surface area. WO 20.0.10 wrote the strategic decision (Option B: "keep both, document clearly, MCP-first for new integrations"), and WO 22.3 added MCP resource URI validation + capability advertisement. But the code still has two parallel systems:

- **Bespoke**: minisign verification, trust tiers, hook veto, verifier integration, topological load, hot-reload (`kf-plugin-host`)
- **MCP**: `tools/list` + `tools/call` on stdio + HTTP/SSE, resources, prompts (newly surfaced), sampling/roots absent

The "both as peers" state is the strategic liability. The decision exists but is not implemented.

## Source

Review #27 (Phase 3). `docs/workorders/20.0.10-strategic-mcp-plugin-decision.md` — Option B recommendation. `src/session/mcp_client/mod.rs` — MCP client. `src/session/plugin_tools/` — bespoke plugin system. Review §4.7: "bespoke+MCP still coexist as peers."

## Scope

1. `docs/adr/0050*` — formalize the MCP-first decision as an ADR (if not already an ADR)
2. `docs/TECHNICAL.md` — document when each system is used, and the migration path
3. `src/session/plugin_tools/` — annotate bespoke paths with `ponytail:` migration notes
4. `src/session/mcp_client/mod.rs` — add MCP sampling capability (or document why deferred)
5. `src/session/executor/mod.rs` — ensure MCP tools take priority in tool resolution when both exist

### 23.6-R1 — Formalize ADR-050 and document strategy (est S)

**Reality check:** `20.0.10-strategic-mcp-plugin-decision.md` is a workorder, not an ADR. It recommends Option B but doesn't carry ADR weight. TECHNICAL.md mentions MCP 11x but doesn't explain the dual-system strategy or migration path.

**Plan:**
- Promote the decision to a proper ADR (`docs/adr/0050-mcp-first-overlay.md`) with Status: Accepted
- Update `docs/adr/README.md` index table with the new ADR
- Add a "Plugin Strategy" section to `docs/TECHNICAL.md`:
  - Bespoke plugins: existing differentiators (hook veto, verifier bus, trust tiers, hot-reload)
  - MCP: primary for new tool integrations, no bespoke plugin format needed
  - Migration path: future work to fold hooks/verifiers as MCP middleware
- Add `ponytail:` migration notes on bespoke plugin paths: `# ponytail: bespoke path — migrate to MCP overlay per ADR-050 when middleware exists`

**Success criteria:**
- ADR-050 exists with Status: Accepted in both file header and index table
- TECHNICAL.md has a "Plugin Strategy" section explaining the dual system and migration path

**Failure criteria:** ADR status mismatch. No strategy section in TECHNICAL.md. No migration notes.

**Estimate:** S

### 23.6-R2 — MCP tool priority in resolution (est S)

**Reality check:** When a bespoke plugin and an MCP server both provide a tool with the same name, the resolution order is undefined. The model sees duplicates or gets the wrong one.

**Plan:**
- In `CompositeToolset::resolve` (or equivalent), when both bespoke and MCP provide the same tool name, MCP takes priority per ADR-050
- Log a warning when a duplicate name is detected (bespoke + MCP providing the same tool)
- Add a config override: `plugin_priority: "mcp_first" | "bespoke_first" | "mcp_only"` defaulting to `mcp_first`

**Success criteria:**
- When a tool name exists in both bespoke and MCP, the MCP version is used
- A warning is logged for duplicate names
- Config override works
- No regression in tool resolution for non-duplicate names

**Failure criteria:** Tool resolution changes for non-duplicate names. No warning on duplicates.

**Estimate:** S

### 23.6-R3 — Document MCP sampling/roots deferral (est S)

**Reality check:** `UNSUPPORTED_CAPABILITIES` was reduced to `["sampling"]` by WO 22.3. Roots capability is also absent. These are real gaps but not ship-blockers.

**Plan:**
- Update `UNSUPPORTED_CAPABILITIES` comment to document each omitted capability with a `ponytail:` ceiling and upgrade path
- `# ponytail: sampling capability deferred — requires bidirectional MCP message loop; upgrade path: implement sampling via MCP client-to-server request channel`
- `# ponytail: roots capability deferred — requires workspace root awareness; upgrade path: add roots from sandbox config`
- No code change — documentation only

**Success criteria:**
- Each omitted MCP capability has a `ponytail:` comment explaining the ceiling and upgrade path
- No overclaim (no comment saying "we support" something we don't)

**Failure criteria:** Missing `ponytail:` ceiling. Overclaim in comments.

**Estimate:** S

**Defer note:** The full MCP-first migration (folding hooks/verifiers into MCP middleware) is a LARGE effort that should be a separate workorder series. This WO formalizes the decision and fixes the resolution priority. The actual middleware work is deferred per ADR-050.
