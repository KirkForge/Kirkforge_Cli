# Workorder 23.8 — Doom-Loop Remediation: Hard Circuit-Breaker

## Problem

The current doom-loop detection (`src/session/executor/loop_.rs:28-111`) detects repeated tool errors (3 identical failures in 5 observations) and injects a hint as a `Role::User` message. But the hint is just that — a hint. In unattended mode, the model can ignore it and keep looping. The review calls this out: "doom-loop is hint-only (loop_.rs:99-111), no hard auto-remediation. Burns tokens indefinitely in unattended runs" (§4.1).

The TUI shows a doom-loop banner (`DoomLoopState` at `app.rs:544-554`) with Break/Plan/Continue actions, which is good for attended mode. But the executor itself has no hard circuit-breaker — after emitting `TurnEvent::DoomLoopDetected`, it just continues the turn loop.

## Source

Review #29 (Phase 3). `src/session/executor/loop_.rs:28-111` — `DoomLoopTracker` detects but does not remediate. `src/session/executor/cost_tracking.rs:75-86` — emits `DoomLoopDetected` event and metric. Review §4.1: "doom loop is hint-only, no hard circuit-breaker."

## Scope

1. `src/session/executor/loop_.rs` — add hard circuit-breaker after N doom-loop hits

## Targets

### 23.8-R1 — Add hard circuit-breaker: auto-plan-mode after N hits (est M)

**Reality check:** `DoomLoopTracker::observe` at `loop_.rs:99-111` returns `Some(DoomHit)` when 3 identical errors occur. The executor at `cost_tracking.rs:75-86` emits `TurnEvent::DoomLoopDetected` and a metric. The TUI shows a banner. But the executor continues the turn.

**Plan:**
- Add `doom_loop_max_hits: usize` to `Config` (default: 3 — same as the current `DoomLoopTracker::THRESHOLD`)
- In `cost_tracking.rs`, track cumulative doom-loop hit count per session (not just per tool-error pattern)
- When cumulative hits reach `doom_loop_max_hits`:
  1. Auto-switch to plan mode (`set_plan_mode(true)`)
  2. Emit `TurnEvent::DoomLoopRemediation { action: "auto_plan_mode", hits: N }`
  3. Log the remediation with `tracing::warn`
- The auto-plan-mode switch is the same as the user pressing `Plan` on the doom-loop banner — it restricts the model to read-only tools
- If already in plan mode when the circuit breaker fires, emit a harder remediation: halt the current turn and return an error message

**Success criteria:**
- After `doom_loop_max_hits` (default 3) doom-loop detections, the executor auto-switches to plan mode
- The TUI shows the remediation event ("Auto-switched to plan mode after 3 doom-loop hits")
- Cumulative hit count persists across tool types (3 hits on `bash` + 0 on `edit_file` = 3 total)
- Config `doom_loop_max_hits = 0` disables the circuit-breaker (current behavior)
- Existing doom-loop detection and banner are unchanged

**Failure criteria:** Circuit-breaker fires too early (1-2 hits). Circuit-breaker doesn't fire at all. Plan mode switch doesn't actually restrict tools. Banner behavior changes.

**Estimate:** M

### 23.8-R2 — Add hard halt after plan-mode circuit-breaker (est S)

**Reality check:** If the model is already in plan mode when doom-loop hits accumulate, auto-plan-mode is a no-op. The model can still loop with read-only tools (e.g., `read_file` the same path 10 times).

**Plan:**
- If already in plan mode when circuit-breaker fires, emit `TurnEvent::Error("Doom loop detected in plan mode. Halting turn.")` and return `Ok(())` from the turn
- This is a hard halt — the model stops generating, and the user sees the error message
- The user can continue the session by typing a new prompt (same as Ctrl+C behavior)

**Success criteria:**
- Doom loop in plan mode produces a clear error and halts the turn
- The session is still usable after the halt (user can type a new prompt)
- No data loss (conversation log is checkpointed before halt)

**Failure criteria:** Session becomes unusable after halt. Conversation data lost.

**Estimate:** S

### 23.8-R3 — Configurable remediation action (est S)

**Reality check:** Different users may want different remediation: auto-plan, auto-halt, or just warn. The current behavior is "just warn."

**Plan:**
- Add `doom_loop_action: "auto_plan" | "halt" | "warn_only"` to `Config`, defaulting to `"auto_plan"`
- `"auto_plan"`: switch to plan mode (R1 behavior)
- `"halt"`: immediately halt the turn (R2 behavior, regardless of plan mode)
- `"warn_only"`: current behavior (just emit the event)
- Document all three modes in TECHNICAL.md

**Success criteria:**
- Each mode produces the documented behavior
- Default `"auto_plan"` matches R1 behavior
- `"warn_only"` matches current (pre-WO) behavior

**Failure criteria:** Mode doesn't match documented behavior. Default changes.

**Estimate:** S

**Defer note:** R3 can be deferred — `auto_plan` as the single hard-coded action is the 80/20. Configuration is polish.
