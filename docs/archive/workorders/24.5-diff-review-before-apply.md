# Workorder 24.5 — Add Diff-Review-Before-Apply Safety Gate

## Problem

The review (#35) identifies this as Claude Code's main safety advantage: before applying an edit, the model sees the diff and can reject it. KirkForge's `edit_file` and `write_file` tools apply changes directly after the user's approval gate (TUI diff preview + approve/reject). But the model itself never sees a pre-apply diff — it just sends the edit, and if the edit is wrong (e.g., wrong line range, unintended deletion), the verifier loop catches it *after* the fact.

The gap: there is no programmatic diff review *before* the edit is applied. The user sees a diff in the TUI approval dialog (`approval.rs:108-125`, using `diff_preview::format_edit_diff_preview`), but the model's edit is applied as-is. A diff-review-before-apply step would:
1. Compute the diff the edit would produce.
2. Check the diff for obvious errors (empty diff, deletion of too many lines, unintended changes outside the target region).
3. Abort or flag the edit before it reaches the filesystem.

This is *not* replacing the user approval gate — it's adding a programmatic safety check that catches obviously wrong edits (wrong line range, unintended large deletions) before they're applied, even in non-interactive mode.

## Root cause

`src/tools/edit_file.rs` applies edits immediately after approval. There is no intermediate "dry run → diff check → apply" step. The verifier loop catches broken edits *after* application (build/clippy/test), which is reactive, not proactive.

## Scope

1. `src/tools/edit_file.rs` — add pre-apply diff review
2. `src/tools/write_file.rs` — add pre-apply diff review (for overwrites)
3. `src/tools/bash_minify.rs` — may need adjustment for sandbox checks
4. `src/session/executor/turn.rs` — wire diff-review result into the outcome
5. `src/shared/mod.rs` — add config flag for diff-review strictness

## Plan

### 24.5-R1 — Add diff-review-before-apply to `edit_file`

- Before writing the edit to disk, compute the diff the edit would produce.
- Check for obvious errors:
  1. **Empty diff**: the edit changed nothing (wrong line content or already applied).
  2. **Large deletion**: the edit removes more lines than intended (e.g., wrong line range).
  3. **Unintended scope**: the edit touches lines outside the target function/region.
- If any check fails, return a `CorrectionResult` with `success: false` and a message explaining what went wrong — *without* applying the edit.
- Add a config flag `diff_review: bool` (default: true in release, false in debug for speed).
- The check runs *after* user approval but *before* filesystem write.

**Success criteria:**
- `edit_file` with a wrong line range (e.g., deleting 50 lines when 2 were intended) returns an error without modifying the file.
- `edit_file` with a correct edit applies successfully.
- Empty diff (re-applying an already-applied edit) returns a message, not a file write.
- Config flag `diff_review` controls the behavior.
- All existing `edit_file` tests pass.

**Failure criteria:** Edit is applied before diff review. Large unintended deletions reach the filesystem.

**Estimate:** L

**Defer note:** This is the largest item in WO 24. The diff-review logic must be careful not to reject valid edits (false positives are worse than no check). Start with the empty-diff and large-deletion checks; scope creep can be deferred.

### 24.5-R2 — Add diff-review-before-apply to `write_file`

- For `write_file` overwriting an existing file, compute a diff between the current and new content.
- Check for: (a) complete file replacement when only a small change was intended, (b) content that doesn't match what the model described in its tool-call reasoning.
- If the diff is suspicious (e.g., >90% of lines changed), return a warning in the outcome.

**Success criteria:**
- `write_file` overwriting an existing file with >90% line change includes a warning.
- New file creation is not affected.

**Failure criteria:** `write_file` refuses valid overwrites.

**Estimate:** M

**Defer note:** Can be deferred if R1 is sufficient. `write_file` is used less than `edit_file` and is inherently riskier (full replacement).

### 24.5-R3 — Add `diff_review` config flag and documentation

- Add `diff_review: bool` to `Config::Security` or `Config::Session` (default: true).
- Document the flag in `TECHNICAL.md` and `cli.rs` help text.
- Add an ADR documenting the diff-review-before-apply decision.

**Success criteria:** ADR exists. Config flag documented. Default is on in release.

**Failure criteria:** Flag is undocumented or defaults to off.

**Estimate:** S (included in R1)

**Defer note:** none.
