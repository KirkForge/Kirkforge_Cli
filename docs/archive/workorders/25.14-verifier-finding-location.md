# Workorder 25.14 — Verifier Finding Location Data (`line` field plumbing)

## Status: Done

## Priority: P1 — model UX + verifier usefulness

## Problem

`CorrectionResult` has `file: Option<PathBuf>` (populated) and
`line: Option<u32>` (always `None`). The model sees "secret detected in
foo.rs" with no line number, forcing a full-file re-read to locate the
issue — wasting tokens and degrading fix accuracy. The `line` field
exists downstream (`src/session/verifier/correction.rs:158-165`) but is
never populated because the upstream types `FixSuggestion` and
`VerificationError` (`src/session/verifier/types.rs:299-314`) lack a
`line` field entirely.

## Source

- `src/session/verifier/correction.rs:158-165` — `CorrectionResult.line`
  always `None`.
- `src/session/verifier/types.rs:299-314` — `FixSuggestion`,
  `VerificationError` have no `line` field.

## Requirements

### R1 — Add `line` to upstream types

- Add `line: Option<u32>` to `FixSuggestion` and `VerificationError`.
- Update `Default` impls / construction literals.

### R2 — Populate `line` at every construction site

- Enumerate every constructor of `FixSuggestion` and `VerificationError`.
- Populate `line` where the underlying source has one:
  - Secret-scanner: line number of the regex match.
  - Lint verifier: line from the clippy/rustc diagnostic span
    (Rust path; non-Rust path depends on WO 25.9-R6).
  - AST verifier: tree-sitter node span start line.
- Where the underlying source genuinely has no line (e.g., whole-file
  verdict), leave `None` explicitly — never fabricate.

### R3 — Propagate into `CorrectionResult`

- In the correction builder, copy `line` from the upstream type into
  `CorrectionResult.line`.

### R4 — Test

- Assert that a verifier finding with a known line location (e.g., a
  planted secret on line N of a test fixture) produces a
  `CorrectionResult` with `Some(N)`.

## Success criteria

- Secret-scanner findings populate `line` from the regex match.
- Clippy/lint findings populate `line` from the diagnostic span.
- AST verifier findings populate `line` from the node span.
- `CorrectionResult.line` is `Some` whenever the upstream source had a
  line.
- Test in R4 passes.
- `cargo test --workspace` green.

## Failure criteria

- R2 populates `line` with fabricated values (e.g., `Some(1)`) to
  satisfy R4's test.
- R3 drops the line during propagation (silently re-introduces the bug).
- A new construction site added later bypasses R2 (no compile-time pin
  is possible since `Option<u32>` defaults to `None` — call this out in
  a code-review checklist item).
