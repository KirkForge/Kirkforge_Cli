# Workorder 25.3 — kf-testdoctor Optimization

## Status: Done (R3+R4 deferred)

## Problem

`kf-testdoctor` (WO 12.4) provides test diagnostics: per-test timings, flaky detection, coverage-gap analysis, and smart auto-suggest. But its own runtime is unmeasured, and for a diagnostic tool that should be fast, speed matters — developers won't run diagnostics that take as long as the tests themselves.

## Root cause

`kf-testdoctor` was built for functionality, not speed. It may scan the entire workspace tree including `target/`, non-Rust files, and build artifacts. No parallelism in directory scanning. No caching between runs.

## Scope

1. `crates/kf-testdoctor/src/` — all source files
2. Benchmarking methodology
3. File parsing optimization
4. Directory scanning parallelism
5. Result caching

### 25.3-R2 — Lazy file parsing (skip non-Rust files, skip `target/`) (MEDIUM · est S · dep: R1)

**Reality check:** File walking is I/O-bound. Scanning `target/` (build artifacts) and non-Rust files (README, docs, assets) is wasted work for a test diagnostic tool.

**What to do:**
- Ensure the file walker skips `target/` directories explicitly (not just via `.gitignore`).
- Skip files without `.rs` extension.
- Skip files that are not test files (no `#[test]` or `#[tokio::test]` patterns). This requires a quick content scan — if the file doesn't contain test attributes, skip detailed parsing.
- Measure the time savings from R1's baseline.

**Scope:** `crates/kf-testdoctor/src/` file walking/parsing code.

**Success criteria:**
- `target/` and non-Rust files are skipped.
- Non-test `.rs` files are skipped (quick content check).
- Measured time reduction from R1 baseline.

**Failure criteria:** Still scanning `target/`. No measurable improvement.

**Estimate:** S

**Defer note:** none.

### 25.3-R3 — Parallel directory scanning (MEDIUM · est M · dep: R2)

**Reality check:** Directory scanning is embarrassingly parallel — each directory can be scanned independently. On a multi-core machine (which CI runners are), parallelism can reduce wall-clock time by 2-4x for the scanning phase.

**What to do:**
- Use `rayon::par_iter` or `walkdir` parallel features to scan directories in parallel.
- If adding `rayon` as a dependency, check if it's already in the workspace. If not, consider `std::thread::scope` (Rust 1.63+) as a lighter alternative.
- Ensure thread safety: file parsing results should be collected into a thread-safe container (e.g., `Mutex<Vec<_>>` or `crossbeam-channel`).

**Scope:** `crates/kf-testdoctor/src/`, `crates/kf-testdoctor/Cargo.toml`.

**Success criteria:**
- Directory scanning runs on multiple threads.
- Measured time reduction from R2 baseline.
- No data races (pass `cargo test -p kf-testdoctor`).

**Failure criteria:** Still single-threaded. Data race introduced.

**Estimate:** M

**Defer note:** If `rayon` isn't already a workspace dependency and `std::thread::scope` is sufficient, don't add `rayon`. Prefer stdlib (ponytail ladder rung 3).

### 25.3-R4 — Cache results between runs (MEDIUM · est M · dep: R3)

**Reality check:** Running testdoctor twice on an unchanged codebase should be near-instant. Currently it re-scans everything. A simple cache (hash of file contents → parsed results) eliminates redundant work.

**What to do:**
- Implement a file-content-hash cache: for each `.rs` file, compute a quick hash (e.g., `std::hash::Hash` of file size + mtime, or a partial content hash of the first/last N bytes + size).
- Store the cache in a well-known location (e.g., `target/.testdoctor-cache` or `~/.cache/kirkforge-testdoctor`).
- On subsequent runs, skip files whose hash hasn't changed.
- Invalidate the cache on `cargo clean` (the cache lives in `target/`, so it's cleaned too).
- Measure: second run should be < 1 second on unchanged codebase.

**Scope:** `crates/kf-testdoctor/src/`, cache logic.

**Success criteria:**
- Second run on unchanged codebase completes in under 1 second.
- Cache invalidated when source files change.
- Cache cleared on `cargo clean`.

**Failure criteria:** Cache serves stale results. Second run is not faster.

**Estimate:** M

**Defer note:** If the lazy parsing (R2) + parallel scanning (R3) already bring the runtime under 2 seconds, caching may not be worth the complexity. Re-evaluate after R3 measurements.
