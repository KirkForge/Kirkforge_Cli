## Scope

### R1 — Debug the `run_line_mode` startup hang OR convert the 7 e2e scenarios to in-process
**Approach A (debug):** add strategic `eprintln!("[ckpt N]")` checkpoints in `src/main/run_session.rs` (around `try_touch` line 222 + the context-index build) and `src/main/line_mode.rs::run_line_mode` (before/after plugin registry load, before/after MCP manager setup, before/after the first `next_line().await`, before/after `run_turn_collecting`). Run one scenario with `KF_CODE_LOG_STDERR=1`, read which checkpoint didn't print. The hang is between session-index WARN and the first turn (per the 2026-08-11 trace). Prime suspects:
- `daemon::client::try_touch` at `run_session.rs:222` — does NOT auto-start, but if a stale daemon holds the socket from a prior test...
- plugin registry load — `session::plugin_tools::load_plugin_registry` may spawn a Node subprocess that waits for stdin.
- MCP manager startup — `McpClientManager::new` may try to connect to configured servers (none in e2e, but defaults may leak).
**Approach B (convert):** rewrite the 7 scenarios as in-process tests modeled on `wiremock_integration.rs` — build the executor via `make_executor`, call `run_turn_collecting` directly, assert on events. No subprocess to orphan. Loses binary-CLI coverage but the in-process test is more reliable. **Recommended if Approach A doesn't surface the cause in one debug session.**
