# Workorder 27.4 — Plugin Trust Default (H9)

## Status: Done (`plugin_trust_workspace` config field shipped; default enforces signatures)

## Problem

`src/session/plugin_tools/loader.rs:86-91` `local_trust_policy()` sets `verify_signatures: false` for workspace plugins (loaded via `cfg.tools.plugin_sources`). The test at `loader.rs:497` (`local_trust_policy_bypasses_signature_verification`) confirms this is intentional. The rationale ("local-trust bypass") is defensible IF workspace plugin dirs are trusted — but there's NO enforcement that they are. A model with `write_file` access can drop a `kf-code.toml` + tool script into a workspace path (e.g. `.kf-code/plugins/evil/`) and, on next `/reload` or session restart, the plugin loads WITHOUT signature verification. Combined with C1 (no landlock) + H3 (bypassable deny-list), a loaded plugin runs as the user. This is a persistence + privilege-escalation vector.

## Reality-check (verified 2026-08-11)

- Workspace plugins skip sig verification by default.
- Data-dir plugins (`plugin_signature_validation` defaults `true` per `config.tools`) but `plugin_public_key_path` defaults `None` — verification enabled with no key, so it cannot validate (need to check whether this fails-closed or fails-open in `kf-plugin-host`).
- The trust tiers (`ReadOnly`/`Shell`/`Network`/`Unsafe`) ARE enforced at dispatch (`wrapper.rs:229-251`); the gap is the signature gate, not the tier enforcement.

## Scope

### R1 — Require explicit operator opt-in for workspace-plugin signature bypass
- `src/shared/config/tools.rs` — add `plugin_trust_workspace: bool` (default `false`).
- `src/session/plugin_tools/loader.rs:86-91` — `local_trust_policy` reads the config; if `plugin_trust_workspace == false`, workspace plugins MUST be signed (fail-closed on missing/invalid signature). If `true`, log a `tracing::warn!` and bypass as today.
- `config.toml.example` — document the new field with a security warning.
- On first run with workspace plugins present + `plugin_trust_workspace == false`, emit a one-time notice: "Workspace plugins are unsigned and will not be loaded. Set `plugin_trust_workspace = true` in config.toml to trust them (unsafe if a model can write to the workspace)."

### R2 — Verify the data-dir path fails-closed on missing key
- Read `crates/kf-plugin-host/src/lib.rs` — confirm `TrustPolicy { verify_signatures: true, public_key: None }` REJECTS unsigned plugins, not silently accepts. If it fails-open, that's a separate bug (escalate to its own item).
- The production loader call at `src/session/plugin_tools/loader.rs:79` builds `TrustPolicy` via struct literal — verify it passes the configured key.

### R3 — ADR + doc-sync
- ADR-013 (or a new ADR-0073) — document the workspace-trust boundary: workspace plugin dirs are NOT trust roots by default; opt-in required.
- `docs/TECHNICAL.md` plugin section — note the default + the escape hatch.
- `state.md` — close H9.

## Success criteria

1. With default config (`plugin_trust_workspace = false`), dropping a plugin into the workspace + `/reload` does NOT load it (logs a warning instead).
2. With `plugin_trust_workspace = true`, plugins load as today (bypass) with a `tracing::warn!`.
3. Data-dir plugins with no public key configured fail-closed (reject unsigned).
4. `config.toml.example` documents the field with a security warning.
5. ADR updated.

## Failure criteria

- Defaulting to trust (silently keeping the bypass) — that's the current bug, not a fix.
- Breaking the legitimate signed-plugin load path.
- Making the opt-in a CLI flag instead of a config field (operators set it once; flag is churn).
