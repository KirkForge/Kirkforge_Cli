## Problem

Seven binary-spawn e2e scenarios wedge inside `run_line_mode` startup and were
`#[ignore]`-gated to WO 27.2 to unblock CI green. The hang is **upstream of the
adapter**: the in-process regression guard
(`src/session/executor/tests/wiremock_integration.rs`) drives the same adapter +
executor to completion in ~2s, so the bug is in binary startup (daemon touch,
plugin registry load, MCP manager init, approval-handler spawn) — not the turn
loop. The trace goes silent after the session-index WARN and before the first
`run_turn_collecting`.

gitnexus evidence — `gitnexus trace main→run_line_mode -r Kirkforge_Cli`:
```

  →CALLS→ run_session (src/main/run_session.rs:34)        [conf 0.85]
  →CALLS→ run_line_mode (src/main/line_mode.rs:35)        [conf 0.85]
```

`run_line_mode` is 326 LOC (`line_mode.rs:35-361`); the stall sits somewhere in
its setup block (executor construction, context-index attach, MCP sampling wiring,
approval-handler spawn at `:101-105`, `LineReader::new` at `:113`).

## Scope

### Approach A — Debug with checkpoints (try FIRST; budget 1 session)

Sprinkle **temporary** `eprintln!("[ckpt N] ...")` in `src/main/run_session.rs`
(around `daemon::client::try_touch` near `:222` + the context-index build) and
`src/main/line_mode.rs::run_line_mode`:
- before/after `Executor::with_log_and_undo_and_plugins` (`:61`)
- before/after `set_context_index` / `set_trace` (`:77-84`)
- before/after the MCP sampling wiring (`:93-99`)
- before/after `spawn_non_interactive_approval_handler` / line-mode handler (`:101-105`)
- before/after `LineReader::new` (`:113`)
- before/after the first `next_line().await` + `run_turn_collecting`

Run ONE scenario with `KF_CODE_LOG_STDERR=1`:
`cargo test --test e2e plain_chat -- --ignored --nocapture`
Read which checkpoint never printed. Prime suspects (from WO 27.2):
1. `daemon::client::try_touch` (`run_session.rs:222`) — does not auto-start, but a
   stale daemon holding the socket from a prior test blocks the connect.
2. `session::plugin_tools::load_plugin_registry` — may spawn a Node subprocess
   parked on stdin.
3. `McpClientManager::new` — may try connecting to configured servers even with
   none configured (default leak).

**Discipline:** checkpoints are SCRATCH — they MUST be removed before commit
(AGENTS.md §5/§6 forbid `eprintln!` in committed code). Use `workplan.md` for
the findings, not the source.

### Approach B — Convert the 7 to in-process (fallback / recommended if A stalls)

Rewrite each scenario as an in-process test modeled on
`src/session/executor/tests/wiremock_integration.rs`: build the executor via the
test `make_executor` helper, drive `run_turn_collecting` directly against a
wiremock server, assert on `TurnEvent`s. No subprocess to orphan, no daemon
socket, no plugin subprocess. Each scenario becomes a `#[tokio::test]` in a
`tests/` module under `src/session/executor/tests/`.

**Tradeoff:** loses binary-CLI coverage (clap arg parsing, stdin piping, the
real `run_session` → `run_line_mode` glue). That glue is partially covered by
`config_isolation` + `daemon_ping` (which PASS) and can be fully covered by a
single thin `tests/cli_smoke.rs` that runs ONE scenario end-to-end with proper
orphan handling.

### Recommendation

**Try A for one focused session** (cheap, high-information). If the root cause
does not surface in one pass, **switch to B** and convert all 7 — the in-process
form is more reliable and the binary-spawn coverage was always fragile. Do not
let the hang block the WO 28 series.
