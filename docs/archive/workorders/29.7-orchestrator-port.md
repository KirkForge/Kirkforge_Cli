# Workorder 29.7 — Port Orchestrator Delegation + Decompose + Correction Loop

## Status: In progress — R1+R2+R3+R4+R5 ported; R6+R7+ModelClient production wiring deferred (branch `wo29g`)

## Problem
The TS orchestrator (7955 LOC, 36 files) is the delegation/classification/correction pipeline. It resolves providers, classifies tasks, recalls memory, builds briefs, dispatches to mode executors (hard-prompt/schema-contract/artifact), runs verifiers, and persists observations. Rust `kf-workflow` is a generic step runner — it does NOT have the classifier + memory + correction loop.

## Source
- Inventory: orchestrator full function/type/dependency map. 28 re-exported types + 19 re-exported values + the `Orchestrator` class.
- The pure decision functions (decideCorrection, computeFinalVerdict, classifyTask) are ported in WO 29.3.
- The EventBus + AuditLogger are ported in WO 29.4.
- The memory store is ported in WO 29.6.

## Scope

### R1 — Port the mode executors (hard-prompt, schema-contract, artifact)
Port `executeHardPrompt`, `executeSchemaContract`, `executeArtifact` from `modes.ts` + `artifact-mode.ts`. These make model calls via `Agent` — in Rust, use the existing `Executor::run_turn_collecting` or a lighter-weight adapter. Port `parseJsonlArtifacts`, `persistCodeblocks`.

### R2 — Port the delegation pipeline
Port `Orchestrator::delegate` — resolve provider → classify → recall memory → build brief → dispatch to mode executor → finalize (verifiers + memory write). This is the main orchestration loop.

### R3 — Port the decompose pipeline
Port `decomposeTask` + `executeDecomposition` + `parseDecomposition` (the canonical version from `orchestrator-decompose.ts`, not the legacy `decompose.ts`). Uses model calls + Zod validation → in Rust use `serde_json` + `serde_path_to_error` or manual validation.

### R4 — Port the correction loop
Port `runCorrectionLoop` — iterate delegate → validator → decideCorrection; persist correction memory. The impure counterpart to 29.3's pure `decideCorrection`.

### R5 — Port the workspace management
Port `WorkspaceManager` (isolated workspace creation + baseline snapshots + cleanup). Uses `cpSync`/`rmSync` → Rust `tokio::fs::copy`/`remove_dir_all`.

### R6 — Port the SLO monitor
Port `SloMonitor` + `AuthPolicySloMonitor` (compute SLOs, persist state, restore). Ring-buffer 100k.

### R7 — Port the security emitter integration
Wire the Rust security emitter (WO 29.2) into the orchestrator's verify cycle. The TS `createVerificationEmitters` factory becomes a Rust factory.

## Success criteria
1. The delegation pipeline produces the same classification + delegation + verification + memory-write as the TS version.
2. The correction loop converges (test: a failing task gets corrected within N iterations).
3. No TS imports remain in the Rust orchestrator crate.
4. The orchestrator works against the in-process `Executor` (not a subprocess).

## Failure criteria
- Porting the health-server in this WO (it's WO 29.8).
- Making model calls via Node (must use the Rust adapter/executor).
- Breaking the decompose JSON schema (decomposition results must validate the same shape).

## Estimate
L (2+ weeks). This is the biggest porting target — 7955 LOC of stateful orchestration logic. Do R1-R2 first (the core delegation), then R3-R4 (decompose + correction), then R5-R7.

## Defer note
R6 (SLO monitor) is the lowest-value piece — defer to 29.7-R6-later if time-boxed.
