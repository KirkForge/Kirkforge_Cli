# Workorder 29.8 — Port Health-Server (HTTP + Auth + Rate-Limit + Prometheus)

## Status: Skipped — not needed for CLI use case

The Rust daemon (`src/daemon/server.rs`) is a Unix-socket session registry
(NDJSON JSON-RPC over `UnixListener`), not an HTTP server. The CLI is
process-per-invocation; there is no Kubernetes liveness or SLO-dashboard
consumer for an HTTP health endpoint. Porting the TS health-server (axum/hyper
+ JWT auth + rate-limit + Prometheus) would add a heavy HTTP framework to a
size-optimized binary for a feature no consumer needs. Re-open this WO only if
kf-code grows a long-running HTTP-serving mode.

## Problem
The TS orchestrator ships a health-server: HTTP/HTTPS with OIDC JWT auth, API-key auth, RBAC permission checks, token-bucket rate-limiting, Prometheus metrics, and OpenAPI spec. Rust has no health server (the CLI is process-per-invocation). This WO is needed only if the Rust binary should expose a health/monitoring endpoint (e.g., for Kubernetes liveness or SLO dashboards).

## Source
- Inventory: health-server full file/function map. `health-server.ts` (314), `health-server/handlers.ts` (441), `health-server/auth.ts` (194), `health-server/rate-limit.ts` (177), `health-server-shared.ts` (120), `health-server/response.ts` (27).
- RBAC + JWT ported in WO 29.5. EventBus + AuditLogger ported in WO 29.4.

## Scope

### R1 — Port the HTTP server using axum (or hyper)
Port `HealthServer::start/stop`. Rust `axum` is the natural framework (routing, extractors, middleware). If `axum` is too heavy, `hyper` directly.
- Port the route table from `handlers.ts` (health, ready, live, metrics, openapi).
- Port the Prometheus metrics format.

### R2 — Port the auth middleware
Port `AuthMiddleware` using the Rust RBAC (WO 29.5): `authenticate(header)`, `checkPermission(actor, perm)`, `checkTenantAccess`. Wire to `axum` middleware.

### R3 — Port the rate limiter
Port `RateLimiter` (token-bucket + body-size enforcement). Straightforward Rust.

### R4 — Port the security headers
Port `SECURITY_HEADERS` (CSP, X-Frame-Options, etc.).

## Success criteria
1. Health-server responds to GET /health, /ready, /live, /metrics with the same shapes as TS.
2. Auth middleware rejects unauthenticated + unauthorized requests.
3. Rate limiter enforces the token-bucket.

## Failure criteria
- Adding `axum` if it's too heavy for a CLI binary (check binary-size impact — the release profile is opt-level=z).
- Exposing the health server by default (it should be opt-in via config/flag).

## Estimate
M (3-5 days). The HTTP framework + auth wiring is the work; the route handlers are thin.

## Defer note
This WO is OPTIONAL — only needed if the Rust binary should expose a health endpoint. If the CLI stays process-per-invocation with no long-running server, SKIP this WO entirely and note it as "not needed for the CLI use case."
