### Refuted / overstated (NO workorder — documented here)

1. **"Permissions are tool-centric, not resource-centric" — REFUTED.**
   `src/shared/permission.rs` implements exactly the model the review
   claims is missing: ordered allow/ask/deny rules matching
   `tool + argument key + anchored glob pattern` — the review's own
   example (`bash` / `command` / `"git status *"` → allow) works today.
   Deny rules get prefix+`**` promotion (`rm -rf /` denies
   `rm -rf /home` and chained variants); allow rules stay anchored so
   `git status` allow does NOT permit `git status; rm -rf /` (tested,
   `permission.rs:761-787`). The reviewer missed this file. The real,
   narrower gaps: no formal permission classes for web/LSP/MCP/subagent
   spawning, and `RiskTier` is display-only. Not workorder-worthy now
   (rules can already key any tool name + arg).
2. **Sandbox stack order** — actual order is rlimits → netns → Landlock
   → seccomp (`bash_runner/mod.rs:162-236`), not Landlock → seccomp →
   rlimits. Substance right, ordering wrong.
3. **kf-rbac as part of the security posture** — the crate exists but is
   NOT consumed by the binary (zero `kf_rbac` in src/). The advertised
   posture includes an unwired component.
4. **Test counts** — "~390 source files" holds for the whole repo
   (390), not src+crates (356); "~150 test files" undercounts (276
   files contain test fns). Direction of the finding (integration
   gaps) still stands.
5. **AgentNode/DAG as first-class object** — direction agreed, but the
   repo already has the pieces (TaskManager, WorktreeSession,
   CancellationToken machinery, personas); the gap is wiring and
   semantics (WO 35.1-35.3), not a new abstract type. Build the
   runtime behavior first; extract the DAG object only if a second
   consumer appears (YAGNI).
