# WO 37.1 — BashJobRegistry hardening: owner ids, remove(), phantom jobs

## Status: Done

## Problem

Three defects in the WO 36.2-shipped registry code:

1. **Owner-id collision across managers.** `TaskManager` mints
   `format!("task-{}", self.next_id)` (`src/tools/task.rs:281`) —
   per-manager counters. Two managers (e.g. the TUI session's manager
   and an orchestrator-spawned one) both mint `task-1`;
   `cancel_by_owner("task-1")` reaches both tasks' jobs. Disclosed as
   a ceiling in 36.2; it's cheap to fix properly.
2. **`remove()` parks on the watcher mutex.** 36.2 fixed `cancel()`
   (flip status first, kill by pid on contention) but `remove()` on a
   still-running job still takes the child mutex the watcher holds
   across `wait().await` — it blocks until the process exits
   naturally.
3. **Phantom job on spawn failure.** The registry inserts the Running
   record (`bash_jobs.rs:195`) BEFORE `proc.spawn()?` (:240). Spawn
   failure returns early and leaves a Running job with no child and no
   watcher (`:273` comment is aware). `/jobs` shows a ghost; caps and
   eviction count it.

## Root cause

Insert-before-spawn ordering + per-manager id namespace + the
`remove()` path not getting 36.2's flip-first treatment.

## Approach

1. Owner ids: make the tag globally unique — process-global atomic
   counter prefix (e.g. `task-{pid}-{counter}` or a `OnceLock`
   counter shared by all managers). Smallest change: a `static`
   counter in task.rs both the manager id minters use. Update the
   `ponytail: ceiling` comments at the call sites (they're now
   resolved — removing a resolved ceiling comment is correct, keep any
   that remain true).
2. `remove()`: mirror `cancel()`'s pattern — if the job is Running,
   flip status / kill by pid on contention rather than locking the
   held mutex. Read 36.2's `cancel()` implementation and reuse its
   helpers.
3. Phantom job: insert AFTER successful spawn (reorder under the same
   lock discipline — the cap-check/eviction/insert comment at :158
   explains why they share a lock; preserve that invariant), or
   remove the record on spawn failure before returning. Pick the
   smaller diff; test both paths.
4. Tests: (a) two managers, same sequence numbers, disjoint cancels;
   (b) `remove()` on a running job returns promptly (bounded, kills or
   detaches the child — decide + document which); (c) spawn failure
   (e.g. nonexistent binary path) leaves no registry entry.
