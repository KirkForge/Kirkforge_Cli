# WO 40.4 — Sleep elimination (30+ tests)

## Status: Done (residual sleeps documented)

## Audit summary (final pass)

Full codebase grep found 26 `sleep()` calls inside `#[cfg(test)]` modules.
Classification:

- **15 poll-interval sleeps** in bounded poll loops — the CORRECT pattern
  (replaced blind sleeps in commit 941377a3). `while cond { check; sleep(10ms) }`
  with a hard deadline. Files: tui/commands, tools/bash, tools/task,
  session/hooks, session/task_spawner, session/parallel_orchestrator,
  session/bash_jobs, session/plugin_tools/wrapper,
  session/verifier/correction.
- **3 mock-behavior sleeps** — the sleep IS the behavior under test:
  `SleepingBatchRunner` and `ConcurrencyTrackingRunner` in kf-workflow
  (timing/concurrency is the test subject); `CooperativeSpawner` in
  tools/task.rs (cancel-flag poll loop simulates cooperative work).
- **2 documented unconvertible race-test delays** (ponytail: comments):
  `line_mode.rs:842` (80ms — blocking syscall entry race, no readiness
  signal from `libc::poll()`); `mcp_client/http.rs:1057` (20ms — Windows
  socket close race, `ponytail:` comment explains the ceiling).
- **3 `#[ignore]` tests** waiting for real subprocess timeouts (hooks,
  bash_runner, bash_jobs). These are genuine production-timeout waits,
  not test-sync sleeps. Already `#[ignore]` so they don't slow CI.
- **1 string literal** in kf-testdoctor (not a real sleep call).

This commit eliminated the last 2 gratuitous test-sync sleeps:
1. `caching.rs:1008` — 5ms sleep in `CountingAdapter` mock between stream
   events. Replaced with a `tokio::sync::Notify` gate: the test fires
   `notify_one()` once, receives one event, drops the consumer; the
   forwarder aborts on `tx_out.closed()`. Fully deterministic, no
   wall-clock wait.
2. `parallel_orchestrator.rs:708` — 10ms sleep in `PipelineProbe::execute`
   simulating model latency. Removed: pipeline ordering is structural
   (sequential by design), not timing-dependent. The sleep added 30ms
   of wall-clock time for zero test value.

## Problem (GPT doc items 1-18, Phase 1: kill wall-clock waits)

30+ tests use `sleep()`, `thread::sleep()`, `from_secs()`,
`from_millis()` as synchronization — paying wall-clock time for
what should be event-driven. The GPT doc lists them by file. The
flake audit (WO 38.12) independently found 6 sleep-race tests and
7 wall-clock-threshold tests. This WO kills them ALL.

## Approach

For each test: replace the sleep with the structural synchronization
that the GPT doc recommends per-item:
- **Bash/process tests**: use a gated start signal (oneshot channel
  fired after the process is Running), not a fixed delay. The
  `GatedSleepTool` pattern (loop_.rs) and the `wait_for_job_done`
  poll pattern are templates.
- **Cache/concurrency tests** (caching.rs 5-60ms sleeps): replace
  with barriers/channels (`tokio::sync::Barrier`, `Notify`).
- **Hook/plugin tests** (200ms + 3s timeout): wait on the
  watcher/plugin event, not time.
- **TUI tests** (50-100ms): event-driven test synchronization via
  the existing channel/state-assertion harness.
- **Daemon/client tests** (20-50ms polling): explicit readiness
  handshake — wait for socket bind, not sleep.
- **Executor loop tests** (150ms sleep, configurable sleep_ms): use
  `tokio::time::pause()` / deterministic time advancement where
  the behavior IS about timing; use barriers where it's about
  ordering.
- **Verifier tests** that spawn real cargo: mock the command runner
  (GPT item 25); keep one real cargo integration test.
- **Context-index 1s mtime sleep** (item 1, 🔴 Huge): inject an
  explicit modification timestamp; don't test filesystem mtime
  resolution.
- **E2E harness 500ms/2s polling** (items 2-3): readiness probe
  (poll until process emits known state), not `wait_stable()`.

Prioritize the 🔴 Huge items first: context-index mtime, e2e harness
polling, bash_jobs real processes, caching concurrency, hooks,
bash_runner, tools/bash.rs.
