# WO 43.30 — Pre-tool hook veto ineffective for file tools

## Status: Done (`1d3cbdb4`)

## Problem

Fresh segment audit (round 4). In `pre_run_verdict`, file tools
(`read_file`, `write_file`, `edit_file`) return `PreRunVerdict::Spawn(tool,
Some(resolved))` at `src/session/executor/pre_run.rs:283` from the path-guard
branch — BEFORE the pre-tool hook block at `pre_run.rs:300-318` (which only
runs for non-file tools; the comment says file hooks are deferred to
`record_tool_result`). But `record_tool_result` is the Phase 3 recorder
(`turn.rs:602`), which runs AFTER the tool body has already executed in Phase
2.5 (`dispatch.rs:480 run_prepared_call`).

Consequence: a pre-tool hook that returns `Deny` for `write_file`/`edit_file`
fires after the file mutation has already been applied — the veto only
suppresses the recorded result, not the write. This defeats a hook configured
as a pre-write security gate and contradicts the deny-veto contract. The model
sees "hook denied" in the conversation while the disk already changed — a
silent security bypass.

## Root cause

File tools short-circuit to `Spawn` in `pre_run` before the hook, and their
hook denial is deferred to a phase that runs after execution.

## Approach

Route file tools through the same pre-tool hook gate that non-file tools use,
so a `deny` verdict blocks the spawn before the mutation. Preserve the
path-guard resolution order (resolve the path first, then run the hook). Add a
pinning test: a pre-tool hook returning `deny` for `edit_file` results in the
file being unchanged.
