# WO 43.34 — Context-index retrieval smears unresolved edges (inflated prompts)

## Status: Done

## Problem

Fresh crates audit (round 4). The index has two retrieval result builders with
divergent filters. `to_retrieval_result` (`crates/kf-context-index/src/lib.rs:1167-1170`)
was fixed to only count edges whose `resolved_file == Some(&sym.file)`; its doc comment
(`:1156-1163`) explicitly says the old `is_none_or` filter "smeared every unresolved edge
in the index into every result, which on a large repo produced multi-MB system prompts
(7MB / >1M tokens observed)". But the primary substring API `retrieve()` (the fallback
path of `retrieve_hybrid`, `:1150`) still uses
`e.resolved_file.as_ref().is_none_or(|rf| rf == &sym.file)` (`:1057`). Any edge with
`resolved_file == None` (stdlib/external imports — the majority) is attributed to EVERY
matched symbol. On a substring query over a large repo this re-inflates every result's
`imported_by` to near-whole-index size — the exact multi-MB-prompt regression the code
comment says was already fixed.

## Root cause

The fix was applied to one retrieval builder (`to_retrieval_result`) but the sibling
`retrieve()` path retained the pre-fix smearing filter.

## Approach

Change `retrieve()`'s `imported_by` filter to match `to_retrieval_result`:
`e.resolved_file.as_ref() == Some(&sym.file)` (and, for consistency, the `called_by`
filter if it has the same shape). Add a regression test: an index with an unresolved
edge must NOT attribute that edge to an unrelated matched symbol.

## Files

- `crates/kf-context-index/src/lib.rs`

## Gate

`cargo test -p kf-context-index`, `cargo clippy --all-targets -- -D warnings`,
`cargo fmt --check`. New regression test green.

## Done

`retrieve()` and `to_retrieval_result()` apply the same resolved-file-only
attribution; no unresolved edge inflates unrelated symbols' `imported_by`.
