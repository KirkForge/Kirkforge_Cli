# WO 43.37 — Verifier pending_corrections dead-queue growth + MCP pending-map leak

## Status: Done

## Problem

Fresh segment audit (round 4). Two unbounded in-memory growth issues, one of
them a latent double-apply risk.

1. **`VerifierBus.pending_corrections` dead queue**
   (`src/session/verifier/handler.rs:184-189`): `verify_event` pushes EVERY
   `Fixable` `FixSuggestion` into `self.pending_corrections`, but the only
   readers are `#[cfg(test)] drain_corrections` calls. The
   `CorrectionLoop::run` applies the decisive fix directly
   (`correction.rs:66-144`) and never drains the queue. Every fixable event
   therefore leaks an unbounded `Vec<FixSuggestion>` for the session lifetime;
   if any future producer (parallel orchestration, batch) drains and applies
   them, the same fix is applied twice (the first re-apply is guarded only by
   `content.contains(original)` in `apply_text_fix`). The queue is otherwise
   dead state.

2. **MCP pending-map entry leak on channel-close without reader exit**
   (`src/session/mcp_client/mod.rs:971-976`): in `stdio_send_request`, the
   `Ok(Err(_))` branch (oneshot receiver dropped) logs and returns
   `McpError::ChannelClosed` but does NOT remove the id from the pending map —
   the timeout branches at `:961` and `:978` DO. If the receiver is dropped
   because the caller abandoned the future (not because the reader exited),
   the sender stays in `pending` until the next response or `fail_all_pending`
   — slow unbounded growth across many abandoned requests.

## Root cause

1. `pending_corrections` is written but never consumed in production; its
   fix-application responsibility was superseded by the correction loop.
2. One of three `send_request` exit branches forgets the `pending.remove(&id)`
   cleanup the other two perform.

## Approach

1. Either wire `pending_corrections` into a real consumer (batch/correction
   apply) or remove it; do not leave write-only production state that risks a
   future double-apply. If kept, drain + dedup against applied fixes.
2. Add `self.pending.lock().await.remove(&id)` to the `Ok(Err(_))` branch,
   matching the timeout branches.
