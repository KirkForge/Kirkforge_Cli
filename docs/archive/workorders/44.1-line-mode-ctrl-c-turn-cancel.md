## Problem

WO 43.18 (Done) claims: "Ctrl-C in line mode cancels gracefully (executor
stops, carryover saved, children killed)" and its manual gate is "run
`sleep 300` via bash tool in `--no-tui` mode, Ctrl-C, confirm the child is
killed". The signal handler, carryover save, and audit flush all landed —
but the turn-cancellation half of the contract did not. Verified in this
checkout:

- The main loop awaits the turn plainly — `src/main/line_mode.rs:427-429`
  (`executor.run_turn_collecting(&input, &approval_tx, &cancelled).await`)
  with no race against the `shutdown` notify; the flag is read only
  *between* iterations (`line_mode.rs:440-443` "If SIGINT fired during the
  turn, stop after this iteration").
- For parent-session turns the `cancelled` flag is only snapshotted into a
  token at dispatch time (`tool_cancel_token`,
  `src/session/executor/helpers/mod.rs:85-93`), whose own doc admits: "a
  cancel arriving after dispatch is only observed via the collect-loop
  handle aborts — bounded by each tool's own timeout". The collect loop
  aborts only *un-awaited* handles (`dispatch.rs:394-403`); the awaited
  in-flight tool runs to completion or its timeout. Default
  `tool_timeout_secs` = 120 (`src/shared/config/tools.rs:18-20`).
- The TUI does not have this gap: it installs a live per-turn token via
  `set_cancel_token` and races the turn against `cancel_rx`
  (`src/session/executor/loop_.rs:511-546`, WO 36.3/36.4). Line mode
  never calls `set_cancel_token` (only `task_spawner.rs:479` and the TUI
  loop do).
- The handler is one-shot (`spawn_line_mode_sigint_handler`,
  `line_mode.rs:50-68`) and its doc comment overclaims ("so
  `run_turn_collecting` aborts in-flight tool calls"). Once tokio's signal
  driver owns SIGINT, repeated Ctrl-C is inert — during a long in-flight
  tool the only escape is SIGKILL, which re-creates the abrupt-exit
  scenario 43.18 existed to remove (carryover for the current turn lost;
  audit lines survive only thanks to 43.21's per-entry fsync).

Net effect: Ctrl-C during e.g. a `sleep 300` bash call in `--no-tui`/`-p`
mode leaves the process visibly hung for up to 120s while the child keeps
running, and repeated Ctrl-C does nothing. The pinned test
(`line_mode.rs:969-1001`) only asserts flag+notify, not turn abort — so
the gap ships green.

Not covered by in-flight WO 43.23 (PDEATHSIG/parent-death orphans —
different seam: this is live-process turn cancellation) and not the vague
WO 38.10-P2 "Ctrl-C polish" bucket (that predates and was superseded by
43.18's specific contract).

## Root cause

43.18 wired the signal to the *flag* but line mode consumes the flag only
at phase boundaries and between turns; the live-token + turn-race pattern
the TUI built (WO 36.3/36.4) was not carried over, so a mid-turn cancel
cannot reach an in-flight tool call.

## Approach

1. In `run_line_mode`, before each turn install a fresh per-turn
   `CancellationToken` via `executor.set_cancel_token(Some(token.clone()))`
   and clear it after (`set_cancel_token(None)`) — mirroring
   `loop_.rs:511-519, :547`.
2. Race the turn: wrap the `run_turn_collecting(...).await` in a
   `tokio::select!` against `shutdown.notified()`; on notify, cancel the
   turn token and set `cancelled` (mirrors `loop_.rs:534-546`). Per-tool
   child tokens derive from the live root token, so in-flight tools abort
   and `kill_on_drop` reaps their children promptly.
3. Keep the existing post-iteration flag check and carryover flush as the
   fallback path.
4. Pinning test (event-driven, no sleeps): a turn with a
   never-completing stub tool resolves promptly once the token is
   cancelled — extend the `line_mode.rs:969` test to assert the turn
   future completes, not just that the flag flipped.
