# WO 44.36 — Surface executor-task death: event loop busy-spins on closed channel and drops all user input silently

## Status: Done

## Problem

The TUI event loop never observes executor-task death, and the shape of its
`select!` turns that omission into a 100%-CPU busy spin with a live-looking
but dead UI.

1. **Executor death is log-only.** `spawn_executor` runs `exe.run(...)` on a
   background task and handles `Err` with a `tracing::error!`
   (`src/tui/mod.rs:789-808`). Tracing writes to `kf-code.log`
   (`src/main/cli_dispatch.rs:89-98`) — invisible inside the alternate
   screen. The failure is reachable: `Executor::run` propagates
   conversation-log IO errors from the `/compact` tail-pin append
   (`src/session/executor/loop_.rs:480-487`, `append_async(...).await?` —
   disk-full, ENOSPC, read-only FS).

2. **Closed `event_rx` is an always-ready select arm.** When the executor
   task exits, `event_tx` drops and `event_rx.recv()` returns
   `Ready(None)` on *every* poll. The loop arm
   (`src/tui/mod.rs:914-916`) stores `None` into `first_executor_event`,
   the drain is gated on `is_some()` (`src/tui/mod.rs:961`), so the body
   no-ops and loops. With `biased;` polling this arm wins immediately
   every iteration → the loop spins at full speed forever. Each spin
   iteration also runs the per-iteration job polls
   (`src/tui/mod.rs:1002-1007`) — including the synchronous
   scheduled-job disk walk (WO 44.37) at unbounded rate.

3. **Input is silently discarded.** Typed input goes `input_tx.send(...)`;
   with the executor gone the receiver is dropped and `send_or_warn!`
   (`src/shared/mod.rs:6-12`) logs to the file. The user sees a responsive
   TUI that eats every keystroke and never responds, with one core pegged.

Nothing else covers this: `handle` is only observed in `teardown`
(`src/tui/mod.rs:428-435`), the kb-reader shutdown `Notify` is unrelated,
and the panic hook only fires on panics, not error returns.

## Root cause

`recv() == None` (channel closed) is treated as a no-op wake instead of a
terminal condition, and the executor `JoinHandle` is never checked between
setup and teardown — so the two halves of the session (UI task, executor
task) can desynchronize with no reconciliation path.

## Approach

1. In `run_event_loop`, treat `event_rx.recv() == None` as fatal: push a
   system entry ("⚠️ Session executor exited unexpectedly (see kf-code.log
   for the error). Exiting.") and set `state.session.should_exit = true`,
   reusing the standard exit path (terminal restored, carryover saved).
2. Do the same in the `approval_rx` arm only if `event_rx` is also closed
   (approval_tx has a second owner in the MCP manager, so its closure alone
   is not proof of death) — or simply leave `approval_rx` alone; the
   `event_rx` check is sufficient.
3. Add a regression test following the existing select-shape pattern
   (`shutdown_notify_wakes_select`, `src/tui/mod.rs:1727-1770`): race a
   closed `mpsc::Receiver::recv()` against a slow tick and assert the
   closed arm resolves immediately (documenting the spin hazard), plus a
   test on the extracted decision helper if the None-handling is pulled
   into a named function.

## Done

- `src/tui/mod.rs`: the `event_rx.recv()` arm of `run_event_loop`'s
  `select!` now treats `None` (channel closed = executor task exited)
  as fatal instead of a no-op wake. A new pure helper
  `handle_executor_channel_closed(&mut AppState) -> bool` pushes a
  system entry ("⚠️ Session executor exited unexpectedly (see
  kf-code.log for the error). Exiting.") and returns `true`; the arm
  then sets `state.session.should_exit = true`, and the top-of-loop
  guard `break Ok(())` falls through to the standard teardown path
  (terminal restored, carryover saved) — the same path the SIGHUP /
  kb-reader shutdown arm uses. No sleep, no retry, no polling-rate
  throttle: this is a channel-closed → terminal-state transition.
- `approval_rx` arm left alone (approval_tx has a second owner in the
  MCP manager, so its closure alone is not proof of death); the
  `event_rx` check is sufficient.
- Two regression tests added next to `shutdown_notify_wakes_select`:
  - `closed_event_rx_resolves_immediately` races a closed
    `mpsc::Receiver::recv()` against a 125ms slow tick with `biased;`
    and asserts the closed arm wins immediately (documents the busy-spin
    hazard; a regression that re-introduces no-op `None` handling would
    hang until the 1s safety net trips).
  - `handle_executor_channel_closed_marks_exit` asserts the helper
    pushes the system entry and signals exit.
