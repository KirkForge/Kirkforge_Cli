# WO 44.38 — PTY streaming appends to the wrong chat entry (ToolStart is emitted at record time, not run time)

## Status: Done

## Problem

The TUI's live-streaming bash card targets "the last tool entry", but the
executor never creates a tool entry for a call until after its body has
finished running.

1. **`ToolStart` fires at record time.** The only producers are inside
   `record_tool_result` (`src/session/executor/turn.rs:602`): the file-tool
   arm (`src/session/executor/turn.rs:770-778`) and the non-file arm
   (`src/session/executor/turn.rs:862-870`), each emitting
   `ToolStart` immediately before that tool's `ToolResult` — after the
   body already ran. `spawn_batch` emits nothing when it spawns the calls
   (`src/session/executor/dispatch.rs:298-335`).

2. **PTY chunks flow during the body.** The bash PTY reader
   `try_send`s `BashPartialOutput` while the command runs
   (`src/session/bash_runner/pty.rs:52-61`) — i.e. before any `ToolStart`
   for that call exists.

3. **The TUI appends to whatever is last.** `BashPartialOutput` mutates
   `messages.back_mut()` whenever `last.role == "tool"`
   (`src/tui/events.rs:454-490`) — with no identity check:
   - **First tool of a turn** (previous entry is the assistant message):
     `last.role != "tool"` → every chunk is silently dropped. The
     streaming card never appears; the 64 KiB tail logic from WO 43.25 is
     dead code on this path.
   - **Follow-on call after a completed tool** (e.g. parallel batch
     `[A, bash]`, awaited in input order per `dispatch.rs:349-357`, or a
     second batch in the same turn): `last` is A's *completed* card
     ("🔧 A (done) — …"). The chunks are appended to it,
     `last.streaming = true` (`events.rs:461`), and at >64 KiB its content
     is rewritten with the tail marker — permanently corrupting A's
     summary. `TurnComplete` clears `streaming` only on assistant entries
     (`events.rs:509-514`), so the vandalized card renders a spinner
     forever.

4. **The unit test enshrines the wrong order.**
   `bash_partial_output_streams_into_running_tool_card`
   (`src/tui/events.rs:908-943`) dispatches `ToolStart` *before* the
   chunks — an ordering the executor never produces.

Verified not already tracked: 43.19 (cursor units), 43.25 (boundary fix
inside this same arm), 38.11 (the tail cap) all treat the entry-targeting
as correct; none audit it.

## Root cause

`ToolStart` moved to record time (mid-batch persistence + input-order
recording) while the PTY streaming path and the TUI's back()-targeting
still assume a placeholder card exists while the body runs. The display
contract (start card → stream → finalize) and the event contract (all
events at completion) disagree.

## Approach

1. Executor: emit `ToolStart` when a call is dispatched — in
   `spawn_batch`, before `tokio::spawn(run_prepared_call(prep))` (and
   before the sequential/deterministic run), and before Phase 2.5 runs
   deferred file calls — and delete the two record-time `ToolStart`
   emissions. `ToolResult` timing stays unchanged (input-order recording
   is what the log depends on).
2. TUI hardening (defense in depth): in the `BashPartialOutput` arm, only
   append when `last.role == "tool" && last.streaming`; otherwise push a
   fresh streaming card ("🔧 bash …") so chunks always land somewhere
   sane. The existing `ToolResult` dedup (placeholder-or-streaming,
   `events.rs:199-208`) already finalizes either shape.
3. `TurnComplete` should clear `streaming` on tool entries too (one-line
   loop change, `events.rs:509-514`) so no tool card can spin forever.
4. Fix the test at `events.rs:908` to cover both orders, and add a
   regression: chunks arriving after a *completed* card must not touch it.
5. Verify ripple: `run_turn_collecting` replay records consume
   `ToolStart` events (`src/session/executor/turn.rs:215-240`) — same
   event set, earlier order; confirm `RecordedToolCall` pairing
   (`src/main/turn_events.rs`, `src/session/replay.rs`) tolerates
   all-starts-then-results.

## Done

- **Executor** (`src/session/executor/dispatch.rs`): `spawn_batch` now
  emits `ToolStart` at dispatch time — before `tokio::spawn` for non-file
  calls and before `run_prepared_call` for deferred file calls in Phase
  2.5. The two record-time `ToolStart` emissions in `turn.rs` (file-tool
  arm ~772, non-file arm ~862) are deleted. `ToolResult` timing is
  unchanged (input-order recording preserved).
- **TUI** (`src/tui/events.rs`): `ToolStart` now marks its placeholder
  entry `streaming = true` so the `BashPartialOutput` append path finds
  it. `BashPartialOutput` only appends when `last.role == "tool" &&
  last.streaming`; otherwise pushes a fresh streaming card so chunks
  always land somewhere sane. `TurnComplete` clears `streaming` on tool
  entries too (was assistant-only) so no tool card can spin forever.
- **Tests**: `bash_partial_output_streams_into_running_tool_card`
  rewritten to cover both orders (ToolStart-first = real order post-fix;
  chunks-first = defense in depth). New
  `bash_partial_output_after_completed_card_does_not_corrupt_it`
  regression asserts chunks after a completed card push a fresh card
  instead of corrupting the completed one.
- **Ripple verified**: `run_turn_collecting` (turn.rs:215-240) pairs
  ToolStart→placeholder, ToolResult fills it via
  `iter_mut().rev().find()` — tolerates all-starts-then-results.
  `emit_turn_events` (turn_events.rs:66-78) already drops stale
  `in_flight` timers defensively. `bench.rs` counts ToolStart events —
  same count, earlier order. `collect_batch` skipped calls already
  carry ToolResult (not ToolStart) in their event vec.
