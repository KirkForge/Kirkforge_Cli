# WO 44.39 — Terminal left in raw mode when TUI setup fails between enable_raw_mode and the TerminalGuard

## Status: Done

## Problem

The panic-hook restore from WO 38.2 covers panics, and `TerminalGuard`
covers everything after its creation — but both startup paths have a
fallible window *before* the guard exists, and an error return there
leaves the user's terminal in raw mode (no echo, no line buffering) with
no restore.

- `run_tui` (`src/tui/mod.rs:536-548`):
  `install_panic_hook(); enable_raw_mode()?;` then five fallible steps —
  `execute!(stdout, EnterAlternateScreen)?`, conditional
  `EnableMouseCapture?`, `EnableBracketedPaste?`, `Terminal::new(...)?` —
  and only then `let _guard = TerminalGuard;` (line 548). Any `?` failure
  in that window (EPIPE when the spawning terminal died, a pty teardown
  race — the same conditions the kb-reader retry logic at
  `src/tui/mod.rs:268-316` was built for) returns `Err` with raw mode
  still enabled. The guard never materializes; the panic hook does not
  fire (not a panic); the error propagates to `cli_dispatch`
  (`src/main/cli_dispatch.rs:242-248`) which prints and exits without
  touching the terminal.
- `run_session_picker_sync` (`src/tui/mod.rs:208-214`) has the identical
  window: `enable_raw_mode()?` (209) → `EnterAlternateScreen?` (211) →
  `Terminal::new(...)?` (213) → guard (214).

`TerminalGuard::drop` is already idempotent and unconditional — it writes
`DisableBracketedPaste`/`DisableMouseCapture`/`LeaveAlternateScreen` plus
the raw-ANSI `force_terminal_reset` even when those modes were never
enabled (`src/tui/mod.rs:86-150`) — so creating it earlier is safe.

## Root cause

The guard was positioned after the terminal object it protects instead of
after the first irreversible state change (raw mode). Later additions
(mouse gate, bracketed paste, `Terminal::new`) widened the window; WO 38.2
fixed the panic path only.

## Approach

1. In `run_tui`: move `let _guard = TerminalGuard;` to the line
   immediately after `enable_raw_mode()?` (before `EnterAlternateScreen`).
2. Same one-line move in `run_session_picker_sync`.
3. Testable seam (match the `SharedBuf` pattern at `src/tui/mod.rs:1657`):
  extract the post-raw-mode setup over a generic writer —
  `fn write_terminal_setup<W: io::Write>(w: &mut W, mouse: bool) ->
  anyhow::Result<()>` — and unit-test that a failing writer returns
  `Err` while the guard's drop output still contains the disable/reset
  sequences. (Keep it lazy: if the extraction fights the `execute!`
  macro, the line moves alone plus the existing
  `force_terminal_reset_writes_ansi_escape_sequences` tests are
  acceptable — the fix is the ordering.)

## Files

- `src/tui/mod.rs`

## Gate

`scripts/test-fast.sh`, `cargo clippy --all-targets -- -D warnings`,
`cargo fmt --check`. If the seam is extracted: a test where the first
write fails must assert both the `Err` return and the reset sequences in
the guard's output.

## Done

Moved `let _guard = TerminalGuard;` to immediately after `enable_raw_mode()?`
in both TUI startup paths (`run_tui` at src/tui/mod.rs:558, and
`run_session_picker_sync` at src/tui/mod.rs:209), before any fallible
terminal setup (`EnterAlternateScreen`, `EnableMouseCapture`,
`EnableBracketedPaste`, `Terminal::new`). The guard's drop is already
idempotent and unconditional (writes Disable/Reset sequences even when those
modes were never enabled), so creating it earlier is safe. An error return in
the previously-unguarded window now drops the guard, which restores the
terminal.

Per the WO's lazy clause, the testable-seam extraction (item 3) was not done:
the `execute!` macro borrows the writer mutably and is not trivially generic
over `&mut W` without fighting crossterm's type inference, and the existing
`force_terminal_reset_*` tests already pin the guard's drop output. The fix is
the ordering, which is now correct.
