# WO 44.48 — Docker bash path maps failing exit codes to success on non-Unix (Windows)

## Status: Done

## Problem

`Bash::run`'s Docker branch synthesizes an `ExitStatus` from the container's
exit code (`src/tools/bash.rs:410-435`). On Unix it uses
`ExitStatusExt::from_raw(code)` (`bash.rs:417-421`). The `#[cfg(not(unix))]`
branch (`bash.rs:422-426`) does `let _ = code; std::process::ExitStatus::default()`
— and `ExitStatus::default()` is status 0, i.e. SUCCESS. So on Windows with
`docker.enabled`, every failing containerized command (non-zero exit) is
reported as `ToolOutcome::Success` (`bash.rs:450`) with the command's stdout,
exit code 0 (`bash.rs:511` reads back the synthesized status). The model is
told a failing build/test succeeded — the worst-case exit-code propagation
failure, silent and in the success direction.

Reachability is real though secondary: Windows is a first-class target
(cross-compile gate in `scripts/ci-local.sh`, 25+ `fix(windows)` commits) and
Docker Desktop on Windows is a supported deployment for sandboxed bash
(`docker_config` plumbed from config).

The signal-death case is also lost on Windows: `run_docker` returns
`status.code().unwrap_or(-1)` (`bash.rs:246`), and `-1` is not a valid
`from_raw` input either — on Unix `from_raw(-1 as u32)` yields a nonsense
wait status rather than the intended "killed by signal" marker.

## Root cause

`std::process::ExitStatus` has no portable constructor from a raw code; the
Unix path used `ExitStatusExt` and the non-Unix fallback picked `default()`
(success) instead of encoding the failure. The status should not be
reconstructed at all — the branch only needs `success()` and `code()`.

## Approach

1. Replace the `ExitStatus` synthesis with a tiny local struct or a
   branch-owned `(success: bool, code: i32)` carried into the existing
   match (`bash.rs:448-519` reads only `output.status.success()` and
   `output.status.code()`), OR keep `ShellOutput.status` but construct
   per-platform: Unix `from_raw(code as u32)`; Windows
   `std::os::windows::process::ExitStatusExt::from_raw((code as u32) << 8)`
   (the encoding `std` uses for `code()` round-trips).
2. Preserve "signal death" as a distinguishable non-success with the
   existing `-1` sentinel documented at the `run_docker` boundary.
3. Tests: pure unit test on the mapping helper for codes 0/1/127 (cfg-gated
   per platform); assert the failure branch produces
   `ToolOutcome::Failure` with the right `exit_code` by factoring the
   match input so the test doesn't need a Docker daemon.

## Done

Fixed `src/tools/bash.rs:422-426` (`#[cfg(not(unix))]` branch of the Docker
exit-status synthesis). The branch returned `ExitStatus::default()` (exit 0
= SUCCESS) for non-zero docker exit codes, so failing containerized
commands on Windows were reported as `ToolOutcome::Success` with exit_code 0.

Replacement: `std::os::windows::process::ExitStatusExt::from_raw(code as u32)`.

Verified from std source (`sys/process/windows.rs:709-722`): Windows
`ExitStatus` is `pub struct ExitStatus(u32)` — raw code stored directly,
`success()` == `(code == 0)`, `code()` == `Some(self.0 as i32)` (round-trips
the u32). So `from_raw(1u32)` → `success()==false`, `code()==Some(1)` — the
contract the match at `bash.rs:448-519` already relies on.

Note on the WO spec's `<< 8` suggestion: that is a Unix wait-status encoding
and would be WRONG on Windows (it would make `code()` return `Some(256)` for
exit 1). The correct Windows call is `from_raw(code as u32)` directly.

Signal-death sentinel: `run_docker` returns `-1` for signal-killed
(`bash.rs:246`). `(-1i32) as u32 == 0xFFFFFFFF` → `success()==false`,
`code()==Some(-1)` — preserved as the intended non-success marker, matching
the Unix-path behavior the `bash_harden_kills_cpu_burn_with_sigxcpu` test
asserts (`exit_code.is_none() || exit_code == Some(-1)`).

The `code == 0` early-return at `bash.rs:414` is unchanged (correct fast
path on both platforms — `default()` is exit 0 on both).

No new deps. `std::os::windows::process::ExitStatusExt::from_raw` is stable
since Rust 1.12.0.
