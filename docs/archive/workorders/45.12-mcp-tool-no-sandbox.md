# WO 45.12 — MCP tool calls bypass all local sandbox policy

## Status: Done

## Problem

Spun out of WO 45.11 (sandbox-policy unification audit). The audit confirmed
that KirkForge has four separate enforcement surfaces. The only one that is a
genuine *gap* (rather than an architectural observation) is MCP:

`McpToolWrapper` (`src/session/mcp_tools.rs:26`) holds no `PathGuard`, no
`DenyList`, no `SandboxConfig`, no `SandboxPolicy`. Its `run` method
(`src/session/mcp_tools.rs:67-80`) calls `self.manager.call_tool(...)` with a
60s defensive timeout and returns the result directly. No local policy is
applied to the call, its arguments, or its result.

This is distinct from the resource tools (`mcp_resource`/`mcp_prompt`), which
*do* have `validate_mcp_uri` (`src/session/mcp_resource_tools.rs:7`) — a
URI-scheme allowlist that blocks `file://` outside the workspace. The generic
tool-call path has no equivalent.

## Root cause

MCP tools execute on a *remote* server over a transport (stdio/HTTP). The
local wrapper cannot apply a filesystem sandbox to code that runs elsewhere,
so none was wired. But two local-side concerns are also unguarded:

1. **Argument scrubbing**: the model-supplied `args: serde_json::Value` is
   forwarded verbatim to `manager.call_tool`. A malicious or leaky MCP server
   could receive secrets the model embedded. There is no deny-list scan of the
   args (unlike `web_fetch`, which checks `deny_list.is_url_denied` at
   `src/tools/web_fetch.rs:158`).
2. **Result trust**: the MCP server's response is returned to the model with
   no validation. A compromised server could return content that, if the
   model writes it to a file via `write_file`, would be gated only by
   `PathGuard` at write time — but the MCP call itself has no content gate.

The capability/tier model (`SandboxPolicy`) that gates plugins does not apply
to MCP — MCP servers are trusted by configuration (operator lists them in
`config.tools.mcp_servers`), not by capability manifest, and there is no
trust-tier check on `McpToolWrapper::run`.

## Approach

Decide explicitly which of these is intended and document it:

1. **Intended**: MCP servers are operator-trusted (config-gated), so local
   sandbox policy is correctly absent — the operator's choice to list a
   server is the trust grant. Document this in `docs/TECHNICAL.md` next to the
   MCP section and close the WO.
2. **Not intended**: add the minimal local gate that matches the trust model:
   - scan `args` JSON for denied URLs / paths before forwarding (cheap, mirrors
     `web_fetch`), and
   - apply the plugin-style trust-tier check so an operator can mark an MCP
     server ReadOnly (call-only) vs Shell (arbitrary side effects).
   This is a real change, not a refactor — it adds a new enforcement point at
   `src/session/mcp_tools.rs:67`, the fifth surface.

Do **not** unify MCP under a single `SandboxPolicy` type as WO 45.11 discusses —
MCP's remote-execution model means the local policy can only gate the
*arguments and result*, not the execution. A unified type would still have
this as a special case.

## Files

- `src/session/mcp_resource_tools.rs:7` — `validate_mcp_uri` (resource tools only)

- `crates/kf-plugin-host/src/sandbox.rs:13` — `SandboxPolicy` (plugin-only, precedent for tier gating)

## Gate

If approach 1 (document and close): `docs/TECHNICAL.md` MCP section gains a
"trust model" paragraph; this WO closes as Done-no-code.
If approach 2: `cargo nextest run -p kf-code --lib --locked -- mcp` green;

## Done

Closed with a combination of Approach 1 (document and close) and the cheap
local arg-scrub gate from Approach 2. A `PathGuard` is the wrong fix here —
MCP tools execute on a remote server, so a local path guard is meaningless.
The operator's choice to list an MCP server in `config.tools.mcp_servers` is
the trust grant (documented in `docs/TECHNICAL.md`).

What shipped:
- **Argument scrubbing** (`src/session/mcp_tools.rs`): `McpToolWrapper` now
  holds the session `DenyList`. Before forwarding `args` to
  `manager.call_tool`, `find_denied_url` walks the args JSON (strings,
  arrays, objects) and blocks any string matching a deny-list URL prefix
  (cloud metadata endpoints, configured `deny_urls`). Mirrors
  `web_fetch`'s `deny_list.is_url_denied` check. Path-pattern deny entries
  are not applied (the remote filesystem is not the local one). Returns
  `ToolOutcome::Failure(AccessDenied)` with the offending URL in the
  message — the remote call never fires.
- **Trust-model documentation** (`docs/TECHNICAL.md`, MCP section): new
  "MCP trust boundary and local sandbox policy" subsection documenting that
  (a) MCP is operator-trusted by config, (b) the local gate is args-only,
  (c) result trust is the operator's responsibility (inherent to remote
  execution), and (d) MCP is intentionally not unified under `SandboxPolicy`.
- **Tests** (`src/session/mcp_tools.rs`): 5 new tests — denied URL blocked
  at top level, denied URL blocked nested in object/array, safe URL passes
  the scrub and reaches the manager, `find_denied_url` unit tests for all
  JSON shapes. 12 mcp_tools tests total, all green.
- **Call site** (`src/main/run_session.rs`): `all_mcp_tools` now takes the
  `builtin_deny_list` (already built at `run_session.rs:350`); the
  `ToolContextBuilder` deny_list field is cloned so it remains available for
  the MCP section.

Not deferred: no work item kicked out or stubbed. The WO's Approach 2
"trust-tier check" (operator marks an MCP server ReadOnly vs Shell) was
considered and rejected — it would not match the trust model (MCP servers
are config-trusted, not capability-manifest-trusted) and the WO itself
forbids unifying MCP under `SandboxPolicy`. The arg-scrub gate is the
correct minimal local-side enforcement for the remote-execution model.
