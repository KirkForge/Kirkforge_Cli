# WO 45.63 — Pricing table is stale; missing all current Anthropic model families

## Status: Done

## Problem

`PRICING_TABLE` (`src/shared/mod.rs:770-870`) has entries through
`claude-opus-4`, `claude-sonnet-4`, `claude-haiku-4`, plus 3.x legacy
rows and GPT rows — nothing for `claude-sonnet-5`, `claude-opus-4-8`,
`claude-haiku-4-5`, or any newer model family.

The fallback is longest-prefix matching with a sentinel `model_prefix:
""` entry (rates all 0.0) plus a `warn_unmapped_model` log line. So:
- `claude-opus-4-8` partially matches `claude-opus-4` prefix → gets
  OLD Opus-4 pricing (wrong rates, not $0)
- `claude-sonnet-5` matches nothing → falls to $0 with a warning

Cost tracking doesn't lie (it warns), but it silently underreports for
unmapped models and misreports for partial-match models. The warning is
log-only — not surfaced in the TUI — so nobody notices until a bill
doesn't match.

## Root cause

Same as WO 45.62: model-identity logic hardcoded to specific name
strings. The pricing table requires a manual update every time a model
is released. The partial-match issue (`claude-opus-4-8` matching
`claude-opus-4`) is a design flaw in longest-prefix matching when newer
models in the same family have different pricing.

## Approach

1. Add pricing rows for current Anthropic model families
   (`claude-sonnet-5`, `claude-opus-4-8`, `claude-haiku-4-5`, etc.).
   Verify rates against Anthropic's current pricing page.
2. Make the $0-fallback louder: surface the `warn_unmapped_model` warning
   in the TUI status bar (or as a session-startup check) so the user
   knows cost tracking is incomplete for their model.
3. Consider: change the matching from longest-prefix to exact-model-id
   lookup with a family-level fallback, so `claude-opus-4-8` doesn't
   silently inherit `claude-opus-4` pricing.
4. Add a test that verifies every model name in the `supports_thinking`
   capability table (WO 45.62) has a pricing entry — cross-DRIFT between
   the two tables.

## Done

- Added pricing rows for current Anthropic model families ahead of the
  family-prefix rows so longest-prefix matching picks the specific
  (newest) rate:
  - `claude-opus-4-8` → $15/$75 (opus tier; was wrongly inheriting
    `claude-opus-4` pricing via partial prefix match).
  - `claude-sonnet-5` → $3/$15 (was falling to the $0 sentinel).
  - `claude-haiku-4-5` → $1/$5 (was falling to the $0 sentinel).
  - `claude-3-7-sonnet` → $3/$15 (found by the cross-DRIFT test: the
    first thinking-capable model had NO pricing row — fell to $0 while
    the app already knew it was a real Claude).
  Rates approximate per Anthropic's published pricing; marked
  `ponytail:` so a future exact-rate pass is tracked, not lost. Cache
  rates follow the standard 1.25x write / 0.1x read multipliers.
- Extracted `resolve_table_row` (longest-prefix table match) and added
  a public `model_has_pricing_row` predicate so the startup check and
  the cost calc agree on what "mapped" means (DRY — one matching path).
- Made the $0-fallback louder: `warn_unmapped_model` is now
  `pub(crate)` and its message states the concrete consequence ("cost
  tracking will report $0 for this model ... or cost totals will
  underreport"). Added an EAGER session-startup check in
  `Executor::new` that fires the warn BEFORE the first turn (was lazy —
  only fired after turn 1's cost calc). The once-per-model dedup makes
  the later turn-time call a no-op for the startup model.
- Cross-DRIFT test (`thinking_capability_models_have_pricing_rows`):
  enumerates real Anthropic model ids across every priced family and
  asserts each resolves to a non-zero rate. Mirrors the capability
  predicate so a future capability-table change (WO 45.62) surfaces any
  newly-covered id that lacks a pricing row. Plus
  `current_model_families_resolve_nonzero_rates` (rate-tier guard:
  opus-4-8 = $90, not just non-zero) and `unmapped_model_has_no_pricing_row`
  (predicate negative branch).
- DEFERRED (disclosed): TUI status-bar surfacing of the unmapped-model
  warning. Plumbing a flag through `ProviderState` (app.rs) + setting
  it at ollama-probe/model-switch (tui/mod.rs) + render (status.rs) +
  selftest/chat/tabs fixtures is a multi-file TUI change beyond the
  smallest-diff, and `state.md` is off-limits. The WO explicitly
  permits the fallback ("at minimum make the warning more visible
  (e.g. log at warn level with a clear message)") — satisfied via the
  eager startup warn + improved message. Remaining work to finish the
  TUI path: add a `pricing_known: bool` (or reuse `model_info`) to
  `ProviderState`, compute it in `probe_ollama_connection` + the
  `/model` swap path, render `⚠ $0-MODEL` in `render_status` after the
  sandbox warning, and update the status.rs/selftest.rs/chat test
