# Workorder 8.2 — TUI Parity: Doom Loop Recovery and Session Navigation

## Status: Done

## Problem
The TUI has several gaps vs the planned feature set (listed as "open cleanup items" in state.md):
- **Doom loop recovery**: when the model enters a repetitive error loop (same error N turns in a row), the TUI should detect it and offer to break out or switch to plan mode
- **Session child/parent navigation**: `/fork` creates child sessions but there's no TUI navigation to traverse the fork tree
- **Scout subagent**: a lightweight read-only exploration subagent that doesn't fork a full session

## Root cause
These are TUI parity items deferred during the core feature push (6.x-7.x).

## Files to touch
- `src/tui/app.rs` — doom loop detection state (track last N error messages, detect repetition)
- `src/tui/events.rs` — emit a `DoomLoopDetected` event when repetition threshold hit
- `src/tui/commands/` — add `/sessions tree` command for fork-tree navigation
- `src/session/executor/loop_.rs` — track error repetition count, expose via metric
- `src/tui/widgets/` — doom loop warning banner

## Approach
1. Track the last 5 tool error messages in the executor. If 3+ are identical, emit a `DoomLoopDetected` event.
2. The TUI shows a warning banner with options: break (stop the loop), plan (switch to /plan), continue.
3. Session tree: query the session index for child/parent relationships and render as a tree.
4. Scout subagent: a stripped-down `/explore` that doesn't fork — runs a single read-only query in-process.
