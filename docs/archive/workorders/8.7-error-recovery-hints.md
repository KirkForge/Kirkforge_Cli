# Workorder 8.7 — Error Recovery: Structured Retry with Context

## Status: Done

## Problem
The error recovery system (`src/session/error_recovery.rs`) analyzes tool errors and maps them to retry strategies, but the retry doesn't carry context about WHY the error happened. The model gets the error message but has to re-derive the cause. For common errors (borrow checker, missing import, type mismatch), the recovery could inject a structured hint.

## Root cause
Error recovery was built as a message classifier (categorize error → suggest retry) but doesn't inject structured context into the retry prompt.

## Files to touch
- `src/session/error_recovery.rs` — add `ErrorHint` enum:
  - `BorrowConflict { original_ref, conflicting_ref }` — suggest cloning or restructuring
  - `MissingImport { symbol, suggested_module }` — suggest the import line
  - `TypeMismatch { expected, found }` — suggest a conversion
  - `MissingMethod { type_name, method_name, suggested_traits }` — suggest implementing a trait
- `src/session/executor/turn.rs` — when a tool error is classified, inject the `ErrorHint` as a structured tool result alongside the raw error
- `src/session/verifier/build.rs` — parse build errors into `ErrorHint` variants
- `src/session/verifier/lint.rs` — parse clippy errors into `ErrorHint` variants

## Approach
1. Extend the error classifier to extract structured data from the error message (regex or pattern matching on compiler output)
2. Build `ErrorHint` from the classified error
3. Inject the hint as a formatted note appended to the tool result: "Hint: this looks like a borrow conflict. The original reference `x` is still alive when `y` tries to borrow it mutably. Consider cloning `x` or restructuring the borrows."
4. The model sees both the raw error and the structured hint
