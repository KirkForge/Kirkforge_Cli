# Workorder 9.5 — Prompt Cache Stem Reuse

## Status: Done (partial — tracker shipped; adapter wiring deferred to WO 10.2)

> WO 10.2 wired the `CacheStemTracker` into `Executor::stream_iteration`
> so `is_stable` / `record_prefix_hash` are now called from the turn
> loop and `PlanReason::CacheStemReuse` is emitted on stable-stem turns.
> The adapter short-circuit (content-omission) was not implemented —
> the Anthropic API requires the full content on every request, so the
> useful client-side signal is the metric event, not a wire-bytes
> saving. See ADR-052.

## Problem
The Anthropic adapter marks the last two prefix messages and the last system
block with `cache_control: {type: "ephemeral"}` (`adapters/anthropic.rs:127,
188`). This enables Anthropic-side prompt caching. But there is no
*client-side stem-reuse logic*: when the conversation grows turn-by-turn, the
prompt builder rebuilds the full message list each turn and the cache stem
(the stable prefix) is not explicitly identified, deduplicated, or
short-circuited. If the stem is large (system prompt + tool definitions +
early turns), every turn re-sends it. `docs/archive/ideas/prompt-cache-stem.md` (52L)
is a note; the only code reference is a comment in `prompt/mod.rs:36` about
"the same `Message` object (and therefore the same cache stem)."

Vix's differentiator is stem-agent cache reuse + tree-sitter VFS for token
efficiency. The cache *markers* are shipped; the *reuse logic* is not.

## Root cause
The prompt builder (`src/session/prompt/mod.rs`) builds messages fresh each
turn. It doesn't track which prefix messages are cache-stable (sent
identically in the prior turn) vs. cache-broken (changed or new). Without
that tracking, the adapter can't skip re-serializing the stable stem.

## Files to touch
- `src/session/prompt/mod.rs` — add a `CacheStemTracker` that records the
  hash of the prefix messages sent in the prior turn. On the next turn, if
  the prefix hash matches, mark those messages as `cache_stable: true` so the
  adapter knows it can skip serializing them (or send a cache-hit token
  instead of the full content, depending on adapter API support)
- `src/adapters/anthropic.rs` — when `cache_stable` messages are present,
  send only the cache_control marker + a reference, not the full content
  (if the Anthropic API supports cache-hit references; if not, this is still
  a client-side optimization: skip serializing the stem in the request body,
  rely on the server-side cache)
- `src/adapters/mod.rs` — the OpenAI-compat path may not support this; gate
  the stem-reuse behind `ModelInfo.supports_cache`
- `docs/archive/ideas/prompt-cache-stem.md` — update from "idea" to "implemented" with
  the approach taken
- `docs/adr/` — new ADR for the cache-stem-reuse decision

## Approach
1. Hash the prefix messages (system + tools + first N user/assistant turns)
   each turn
2. If the hash matches the prior turn's prefix hash, mark those messages as
   cache-stable
3. In the adapter, for cache-stable messages: send `cache_control` marker +
   a minimal reference (or omit content if the API allows it)
4. Measure: log the request body size with and without stem-reuse on a
   10-turn conversation; confirm the stem bytes are not re-sent
5. Test: a unit test that builds a 5-turn conversation, confirms the prefix
   hash is stable across turns 2-5, and the adapter omits the stem content
   on turns 2-5
