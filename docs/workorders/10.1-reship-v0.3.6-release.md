# Workorder 10.1 — Re-ship v0.3.6 Release After Windows Green

## Status: Done (release run 30239782875 success; 6 binaries + SHA256SUMS + cosign sig + .pem published)

## Problem
`v0.3.6` was tagged at commit `9158bb0` by WO 9.3, but the release workflow
failed and no artifacts were published:

- `gh run view 30228618640 --json jobs` (Release workflow on `9158bb0`)
  shows `Verify main CI is green: failure` (because the `windows` CI job
  failed on the same commit), `Create GitHub release: skipped`,
  `Build release binaries: skipped`.
- `gh release view v0.3.6` → "release not found." No 6-platform binaries,
  no SHA256SUMS, no cosign signature.

WO 9.3's done condition was "gh release view v0.3.6 shows 6 platform
binaries" — that condition was NOT checked before marking the WO Done.
This is the same merge-discipline failure the review series has flagged
since the third pass: code ships, tracking doesn't. A release that's
tagged but not actually shipped is a process finding.

## Root cause
WO 9.3 bumped `Cargo.toml` (`0.3.0` → `0.3.6`), added the `CHANGELOG.md`
section, created the annotated tag, and pushed. The release workflow's
first job (`Verify main CI is green`) gates on the CI workflow being
green on the tagged commit. The CI workflow's `windows` job failed
(the bug WO 10.0 fixes), so the gate failed and the rest of the release
was skipped. WO 9.3 did not run `gh run watch` on the release workflow
before marking itself Done — the AGENTS.md "Check CI after every push"
rule was not followed for the tag push.

## Files to touch
None (process + git tags only). Optionally:
- `state.md` — update the WO 9.3 line to note the release was re-shipped
- `CHANGELOG.md` — if the re-ship happens after the v0.3.6 section, add a
  one-liner "v0.3.6 release artifacts published (re-triggered after
  Windows CI fix)" under the existing `[0.3.6]` section

## Approach
1. **Verify WO 10.0 is done first.** `gh run view <latest-main-ci-id>
   --json jobs` must show `windows: success` on the current `main` HEAD.
   Do not start this WO until 10.0 is green.
2. **Decide whether to re-tag `v0.3.6` or cut `v0.3.7`.** Options:
   - **Re-tag `v0.3.6`** (move the existing tag to the Windows-fix commit).
     Cleaner changelog (no new version section), but moves a tag —
     `git push --force origin v0.3.6` and `git tag -f v0.3.6 <fix-sha>`.
     Acceptable because v0.3.6 was never published (no one has the
     artifacts), so re-tagging is honest about "what v0.3.6 actually is."
   - **Cut `v0.3.7`** (new tag on the Windows-fix commit). Avoids
     force-pushing a tag. Adds a CHANGELOG section. More honest if the
     Windows fix is materially a new release, but the Windows fix is a
     test-only change (no behavior change), so re-tag is more accurate.
   - **Recommend: re-tag `v0.3.6`.** The artifacts never shipped; the
     tag points at a commit that doesn't build on Windows; moving it to
     the fix commit makes the tag honest. Document the re-tag in the
     CHANGELOG.
3. **Push the tag** (or re-push after force-update): `git push origin
   v0.3.6` (or `git push --force origin v0.3.6` if re-tagging).
4. **Watch the release workflow**: `gh run watch <release-run-id>`.
   Verify `Verify main CI is green: success`, `Create GitHub release:
   success`, `Build release binaries: success`.
5. **Verify artifacts**: `gh release view v0.3.6 --json assets` shows 6
   platform binaries + `SHA256SUMS` + `SHA256SUMS.sig` (or `.pem`).

## Gate
```
# After WO 10.0 is green on main:
gh run view <latest-main-ci-id> --json jobs | jq '.jobs[].conclusion'
# all must be "success" (or "skipped" for changelog)

# After pushing the (re-)tag:
gh run watch <release-run-id>   # exit 0 on success
gh release view v0.3.6 --json assets | jq '.assets[].name'
# expect: kirkforge-x86_64-unknown-linux-gnu, ...-aarch64-apple-darwin,
#         ...-x86_64-pc-windows-msvc.exe, etc. (6 binaries)
#         SHA256SUMS, SHA256SUMS.sig (or .pem)
```

## Done condition
- `gh release view v0.3.6` shows 6 platform binaries + SHA256SUMS +
  cosign signature (the WO 9.3 done condition that was not met)
- The Release workflow run that published is `success` (verify via
  `gh run view <id> --json conclusion`)
- `state.md` updated: WO 9.3 line notes "release artifacts published
  (re-triggered after Windows CI fix in WO 10.0/10.1)"
- `CHANGELOG.md` has a one-liner under `[0.3.6]` if the release was
  re-tagged (note the re-tag and why)
- Depends on: WO 10.0 (Windows CI must be green first)

## Notes
- If re-tagging: `git tag -f v0.3.6 <fix-sha>` then `git push --force
  origin v0.3.6`. Force-pushing a tag is acceptable here because the tag
  never shipped (no consumer has it); it's the honest correction. Do NOT
  force-push `main` or `dev` — only the tag.
- If the release workflow fails for a reason other than the Windows CI
  gate (e.g. a cross-compile target breaks), do NOT mark this WO Done —
  fix the release workflow first. The done condition is the artifacts,
  not the workflow trigger.
- Do NOT bump `Cargo.toml` to `0.3.7` unless you choose the cut-new-tag
  path. The version in `Cargo.toml` must match the tag that ships.
