# Workorder 10.7 — HTTP MCP: Session-Id Tracking + Resumable Streams

## Status: Planned

## Problem
The HTTP/SSE MCP transport (`src/session/mcp_client/http.rs`, 598L)
shipped in WO 6.x as a real streamable-HTTP client (GET `/sse` opens the
event stream, POST `/messages` sends JSON-RPC, SSE `message` events
routed back by id). But it has a documented gap at `http.rs:395`:

```rust
// We do not yet track session ids in this minimal implementation; the server
// is expected to route by the open SSE connection.
```

The MCP streamable-HTTP spec recommends sending an `Mcp-Session-Id`
header on POST requests once the server provides it (via the SSE
`endpoint` event). The current client omits the header, which means:

1. **No session resumption.** If the SSE connection drops mid-session,
   the client cannot reconnect with the same session id — the server
   treats the new connection as a fresh session, losing any server-side
   state (initialized capabilities, subscriptions, in-flight requests).
2. **No server-side routing for stateful servers.** Some MCP servers
   (e.g. the Sourcegraph one) use the session id to route requests to
   the right backend; without it, requests may go to the wrong backend
   or fail.
3. **No `Last-Event-ID` resumption.** The SSE spec supports
   `Last-Event-ID` header on reconnect to resume from the last received
   event id; the client does not send it.

The 12th pass review listed "HTTP/SSE MCP transport" as shipped (it
is), but the session-id gap was not flagged. This WO closes it.

## Root cause
The HTTP MCP client was built for the minimal case: open SSE, POST
JSON-RPC, read responses. Session-id tracking was deferred as "minimal
implementation" because the spec recommends (not requires) the header
and most local MCP servers don't need it. But remote/stateful MCP
servers do, and the gap is documented in the code.

## Files to touch
- `src/session/mcp_client/http.rs` —
  - Parse the `endpoint` SSE event for a session-id URL parameter or
    header (the spec sends `endpoint: /messages?session_id=<id>` or
    similar; check the MCP streamable-HTTP spec for the exact format)
  - Store the session id on the `HttpClient` struct
  - On `post_request`, add the `Mcp-Session-Id: <id>` header
  - On SSE reconnect (if the stream drops), send `Last-Event-ID: <last
    event id>` header to resume
  - Track the last event id from the SSE reader (`id: <...>` lines in
    the SSE stream)
- `src/shared/mod.rs` `McpServerConfig` — optional: add a
  `session_id: Option<String>` field for config-provided session ids
  (advanced; may not be needed if the server always provides it)
- `src/session/mcp_client/mod.rs` — tests for the new header behavior

## Approach
1. **Read the MCP streamable-HTTP spec** for the exact session-id
   format. The spec is at <https://modelcontextprotocol.io/specification>
   (or the GitHub spec repo). The `endpoint` event carries the POST
   URL, which may include a `session_id` query param; alternatively the
   server sends a `Mcp-Session-Id` header on the initial SSE response.
   Implement whichever the spec mandates; document the choice in a
   comment.
2. **Parse the session id.** In the SSE reader (`run_sse_reader`),
   when the `endpoint` event arrives, extract the session id (from the
   URL or the event payload) and store it on the client. If the spec
   uses a header, parse it from the initial GET response.
3. **Send the header on POST.** In `post_request`, if the session id is
   known, add `Mcp-Session-Id: <id>` to the request headers.
4. **Track last event id.** In `run_sse_reader`, parse `id: <...>`
   lines (SSE spec) and store the last seen id. On reconnect, send
   `Last-Event-ID: <id>` on the GET request.
5. **Reconnect logic.** If the SSE stream drops (network blip, server
   restart), the client should reconnect with the session id + last
   event id, not start a fresh session. Add a retry loop with backoff
   (e.g. 1s, 2s, 5s, 10s, max 30s) and a max-retry count (e.g. 5).
6. **Test.** Add unit tests for:
   - Session-id parsed from `endpoint` event
   - `Mcp-Session-Id` header sent on POST when session id is known
   - `Last-Event-ID` header sent on reconnect
   - Reconnect retries with backoff, gives up after max retries
   Use a mock SSE server (the existing test pattern in `http.rs` tests
   — check what's there).

## Done condition
- `Mcp-Session-Id` header sent on POST requests when the server
  provides a session id (verified by a test that asserts the header is
  present)
- `Last-Event-ID` header sent on SSE reconnect (verified by a test)
- Session id parsed from the `endpoint` event (or the spec-mandated
  header) and stored on the client
- Reconnect with backoff: retries up to max-retry count, then fails
  with a clear error (not a silent hang)
- Existing HTTP MCP tests pass (the minimal-implementation tests should
  still pass when no session id is provided — backward compatible)
- ADR-055 (or the next free number) written: documents the
  session-id-tracking decision, the spec reference, and the
  reconnect/Last-Event-ID behavior
- Depends on: nothing (the HTTP transport exists)

## Notes
- The MCP streamable-HTTP spec is the source of truth for the exact
  header names and the `endpoint` event format. Read it before
  implementing; do not guess.
- Backward compatibility: if the server does not send a session id,
  the client must not send the header (some servers reject unknown
  headers). The test suite must cover both "server sends session id"
  and "server does not send session id" cases.
- The `ponytail:` annotations in `http.rs` (if any — check) must be
  preserved.
- This is a P2 WO. It does not block the release (10.0/10.1) or the
  cache-stem wiring (10.2). It closes a documented gap in the HTTP MCP
  transport that affects remote/stateful MCP servers.
