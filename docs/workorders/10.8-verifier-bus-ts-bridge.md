# Workorder 10.8 — Verifier Bus: TS Orchestrator → Rust VerifierBus NDJSON Bridge

## Status: Planned

## Problem
WO 9.6 promoted ADR-028 from "Accepted (partially implemented)" to
"Accepted" after confirming the *plugin-verifier* path is code-complete:
plugins declaring `Capability::Verifier` register into the Rust
`VerifierBus` via `register_plugin_verifiers_into_bus`, and
`emit_tool_event_and_correct` (`dispatch.rs:900-921`) converts each
`Severity::Error` `VerdictEntry` into a `CorrectionResult` handled by
the single correction loop. The 9.6 integration test
(`plugin_verifier_triggers_correction_result`) proves this path.

But the **cross-language NDJSON wire bridge** — the TS plugin
orchestrator's emitters (`lint`/`types`/`security`/`graph`/`imports`/
`changes`) feeding verdicts into the Rust `VerifierBus` via a
JSON-RPC/NDJSON protocol — is still future work. ADR-028's ponytail
says: "the plugin-verifier bridge is complete while the cross-language
NDJSON wire bridge remains future work." The TS orchestrator
(`npm/kirkforge-plugin/packages/orchestrator/`) is still a separate
system: it runs its own correction loop on its own emitters, and the
Rust executor does not see TS-orchestrator verdicts unless a plugin
declares `Capability::Verifier` and shells out.

The 12th pass listed "Two verifier buses still not unified at the code
level" as a P3. WO 9.6 closed the *plugin-verifier* half; this WO
closes the *TS-orchestrator* half.

## Root cause
The TS orchestrator was built first (the "Vix merge" half). The Rust
runtime bus was built second (the Claude-Code half). They were never
unified because unification requires deciding (a) which bus is
authoritative (the Rust `VerifierBus`, per WO 9.6's ADR-028), and (b)
how the TS orchestrator's emitter events map to `VerdictEntry` structs
the Rust bus can consume. The plugin-verifier path (WO 7.7/9.6) shells
out to a plugin process and reads its stdout; the TS orchestrator runs
in a Node subprocess via the plugin host, and its emitter events are
JSON shapes that need a translator.

## Files to touch
- `src/session/verifier/bus.rs` — add a `TsOrchestratorBridgeVerifier`
  that implements `BusVerifier` by shelling out to the TS orchestrator
  (via the existing plugin-host subprocess) and translating its emitter
  JSON output to `Vec<VerdictEntry>`. The bridge runs the TS
  orchestrator's emitters (`lint`/`types`/`security`/`graph`/`imports`/
  `changes`) on the verify context's file set and collects their
  findings.
- `npm/kirkforge-plugin/packages/orchestrator/src/` — add a
  `BridgeEmitter` (or reuse the existing emitters) that emits verdicts
  in the NDJSON wire format the Rust bridge expects. The format is a
  stream of JSON objects: `{"verifier": "security", "severity":
  "error", "file": "<path>", "line": <n>, "message": "..."}`. The
  existing emitters already produce similar shapes internally; the
  bridge emitter wraps them for the wire.
- `src/session/verifier/plugin.rs` (or wherever the plugin-host
  subprocess is invoked) — extend the plugin-verifier invocation to
  support the TS orchestrator: when a plugin declares the orchestrator
  capability, the bridge verifier runs the orchestrator's emitters via
  the plugin host and collects the NDJSON verdicts.
- `src/session/verifier/correction.rs` — no changes expected; the
  correction loop already handles `VerdictEntry` from any
  `BusVerifier`. The bridge verifier is just another `BusVerifier`.
- `docs/adr/0028-kvb-verifier-bus-bridge.md` — update the ponytail:
  "cross-language NDJSON wire bridge shipped in WO 10.8" (or the
  number you land on). Update the Status if it changes.
- `docs/TECHNICAL.md` — document the unified bus: "The Rust
  `VerifierBus` is authoritative. Built-in verifiers (lint, rustfmt,
  security, git, build, test) register directly. Plugin-declared
  verifiers register via `register_plugin_verifiers_into_bus`. The
  TS orchestrator emitters register via the `TsOrchestratorBridgeVerifier`
  which shells out to the orchestrator and translates NDJSON verdicts
  to `VerdictEntry`."

## Approach
1. **Define the NDJSON wire format.** A stream of JSON objects, one
   per line:
   ```json
   {"verifier": "security", "severity": "error", "file": "src/foo.rs",
    "line": 42, "message": "eval() call detected", "rule": "no-eval"}
   ```
   This is a strict subset of the TS orchestrator's existing emitter
   output. The bridge verifier parses each line into a `VerdictEntry`.
   Document the format in the ADR.
2. **Implement `TsOrchestratorBridgeVerifier` in `bus.rs`.** It holds a
   reference to the plugin-host subprocess (or spawns one on demand).
   On `verify(ctx)`, it invokes the TS orchestrator with the verify
   context's file set, reads the NDJSON verdict stream from stdout, and
   translates each line to a `VerdictEntry`. Errors in translation
   (malformed JSON, unknown verifier name) become `Severity::Warn`
   verdicts with a descriptive message (do not silently drop).
3. **Register the bridge.** In the executor setup, after
   `register_plugin_verifiers_into_bus`, also register the
   `TsOrchestratorBridgeVerifier` if the TS orchestrator plugin is
   loaded. Gate behind the existing plugin-enable check (the
   orchestrator is a plugin; if the user disabled it, the bridge
   does not register).
4. **Integration test.** A mock TS orchestrator plugin that emits one
   `security` error verdict via the NDJSON wire format; the test
   asserts the `TsOrchestratorBridgeVerifier` produces a `VerdictEntry`
   with `Severity::Error` and the correction loop emits a
   `CorrectionResult`. Mirror the 9.6 test shape.
5. **Update ADR-028.** Status stays "Accepted"; the ponytail changes
   from "cross-language NDJSON wire bridge remains future work" to
   "cross-language NDJSON wire bridge shipped in WO 10.8; format
   documented above."
6. **Update `docs/TECHNICAL.md`.** The verifier-bus section should now
   describe the unified bus, not two separate systems.

## Notes
- The TS orchestrator runs in a Node subprocess via the plugin host.
  The bridge verifier shells out to that subprocess and reads its
  stdout. This is the same pattern as the existing plugin-verifier
  path (`register_plugin_verifiers_into_bus`), just with a different
  protocol (NDJSON verdicts instead of plugin-stdout JSON).
- Do NOT unify the two `Verifier` traits (the event-driven `Verifier`
  and the sync `BusVerifier`). They coexist by design (AGENTS.md §7).
  This WO adds a new `BusVerifier`, not a trait unification.
- The `ponytail:` annotations in `bus.rs` (the "Future work: migrate
  the async verifiers to implement BusVerifier" comment at line 185)
  must be preserved unless this WO actually does that migration. It
  does not — this WO adds a *new* `BusVerifier` for the TS orchestrator,
  it does not migrate the existing async verifiers.
- This is a P2 WO. It does not block the release (10.0/10.1) or the
  cache-stem wiring (10.2). It closes the second half of the
  verifier-bus unification that WO 9.6 documented but did not
  implement.
