# Workorder 10.9 — Bench Harness: Leaderboard Publish + Regression Gate + Multi-Model PR Delta

## Status: Done (`bc41e8c`; `--fail-on-regression` flag, `bench-leaderboard` scheduled job with `[skip ci]`)

## Problem
The bench harness shipped the multi-model leaderboard
(`handle_bench_run_models` in `src/main/mod.rs:386`,
`write_model_comparison` in `crates/kirkforge-bench/src/lib.rs:449`)
and the PR-delta comment job (WO 9.2,
`.github/workflows/bench-baseline.yml` `bench-pr-delta` job). But three
depth gaps remain:

1. **The leaderboard is not published anywhere.** `write_model_comparison`
   produces a markdown table, but it's only printed to stdout or
   written to a local file. There is no tracked artifact (e.g.
   `docs/bench/leaderboard.md` committed on each scheduled run) and no
   GitHub Pages site. A contributor opening the repo cannot see "how
   does model X compare to model Y on the current main?" without
   re-running the bench. The 12th pass listed "no CI benchmark deltas on
   every PR" — WO 9.2 closed the PR-delta half, but the leaderboard
   publish half is still open.
2. **No regression gate.** `ci.yml:305` emits a soft `::warning::
   Benchmark success rate below 10% — possible regression` but does not
   fail the PR. A bench regression (e.g. a refactor that drops the
   success rate from 80% to 40%) is reported as a warning, not a
   failure. The PR can merge with a broken bench. The 12th pass named
   "CI benchmark deltas on every PR" as a P1-long-2 follow-up; the
   delta is posted as a comment (9.2) but the gate is not enforced.
3. **PR-delta is single-model.** The `bench-pr-delta` job runs
   `bench run --model qwen2.5:0.5b` only. A regression that affects one
   model but not another (e.g. a tool-call parsing change that breaks
   `qwen2.5:0.5b` but not `llama3.2:1b`) is caught; a regression that
   only shows up on a second model is missed. The leaderboard exists
   for multi-model comparison; the PR-delta job does not use it.

## Root cause
The bench harness was built incrementally: 6.x shipped the runner, 8.1
shipped the multi-model comparison, 9.2 shipped the PR-delta comment.
Each WO closed a specific gap but did not wire the pieces into a
complete CI-gate-and-publish loop. The leaderboard publish and the
regression gate are the missing pieces.

## Files to touch
- `.github/workflows/bench-baseline.yml` —
  - **Leaderboard publish:** add a `bench-leaderboard` job in the
    `schedule` branch that runs `bench run-models --models
    qwen2.5:0.5b,llama3.2:1b,...` and commits the resulting
    `bench-leaderboard.md` to `docs/bench/leaderboard.md` on `main`.
    Use `stefanzweifel/git-auto-commit-action` or a manual
    `git commit && git push`. Gate behind the schedule trigger only
    (not on every push — the leaderboard is a daily snapshot, not a
    per-PR artifact).
  - **Multi-model PR delta:** extend the `bench-pr-delta` job to run
    two models (`qwen2.5:0.5b` and a second, e.g. `llama3.2:1b` if the
    runner has RAM) and post a multi-model delta table. If the second
    model pull is too slow for the PR job, document the trade-off and
    keep single-model on PR (the scheduled leaderboard covers
    multi-model).
  - **Regression gate:** add a step that parses the bench-delta and
    fails the job (not just warns) if the success rate drops by more
    than a configurable threshold (default 10 percentage points). Use
    `bench compare --fail-on-regression <threshold>` (add the flag in
    `crates/kirkforge-bench/src/lib.rs` if it does not exist).
- `crates/kirkforge-bench/src/lib.rs` —
  - Add `compare_with_threshold(baseline, current, threshold) ->
    CompareResult` that returns a `RegressionDetected` flag if the
    success rate delta exceeds the threshold.
  - Add a `--fail-on-regression <pct>` CLI flag to `bench compare` that
    exits non-zero on regression.
- `docs/bench/leaderboard.md` (new) — the published leaderboard. First
  version is generated by the schedule job; subsequent runs overwrite
  it. Add a header noting "Auto-generated by the bench-leaderboard
  scheduled job; do not edit manually."
- `docs/TECHNICAL.md` — document the bench CI loop: scheduled
  leaderboard, PR-delta comment, regression gate, multi-model
  comparison.

## Approach
1. **Add `compare_with_threshold` to `kirkforge-bench`.** The existing
   `compare_reports` produces a `DeltaReport`; add a
   `RegressionDetected: bool` field (or a helper that checks the
   success-rate delta against a threshold). Add a `--fail-on-regression
   <pct>` flag to the `bench compare` CLI that exits 1 if the
   regression is detected.
2. **Add the regression gate to `bench-baseline.yml`.** In the
   `bench-pr-delta` job, after `bench compare`, check the exit code
   and fail the job if non-zero. The job is already `if: always()` so
   the comment posts either way; the job conclusion becomes `failure`
   on regression, blocking the PR merge (if branch protection requires
   the job).
3. **Add the leaderboard publish job.** In the `schedule` branch (and
   optionally on `push` to `main`), add a `bench-leaderboard` job that
   runs `bench run-models` with the model list, writes
   `bench-leaderboard.md` to `docs/bench/`, and commits it to `main`
   via `git-auto-commit-action`. Use a separate job (not the
   `bench-baseline` job) so a leaderboard commit does not re-trigger
   the bench workflow (use `[skip ci]` in the commit message or path
   filters to avoid the loop).
4. **Multi-model PR delta (optional).** Extend `bench-pr-delta` to run
   two models. If the second model pull adds too much time (the
   `ollama pull` step is already slow), keep single-model on PR and
   document that the scheduled leaderboard is the multi-model
   comparison. Prefer correctness over coverage here.
5. **Test.** Add unit tests for `compare_with_threshold` (no
   regression, regression within threshold, regression beyond
   threshold). The existing `write_model_comparison` tests cover the
   markdown table; the new tests cover the gate logic.

## Notes
- The leaderboard commit must not trigger the bench workflow again.
  Use `[skip ci]` in the commit message OR add `paths-ignore:
  ['docs/bench/**']` to the `push` trigger. Test the loop avoidance
  by manually triggering the schedule job and verifying only one run
  happens.
- The regression threshold is a policy decision. 10 percentage points
  is a reasonable default (80% → 70% is a regression; 80% → 79% is
  noise). Make it configurable via a workflow input or a repo
  variable, not hardcoded.
- If the second model pull is too slow for the PR job (the
  `ollama pull` step can take 2-5 minutes per model), keep single-model
  on PR and rely on the scheduled leaderboard for multi-model. Document
  this trade-off in `docs/TECHNICAL.md`.
- This is a P2 WO. It does not block the release (10.0/10.1) or the
  cache-stem wiring (10.2). It closes the P1-long-2 follow-up the 12th
  pass named, turning the bench harness from "runs and reports" into
  "runs, reports, gates, and publishes."
