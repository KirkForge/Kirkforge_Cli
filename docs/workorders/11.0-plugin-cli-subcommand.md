# Workorder 11.0 — Plugin CLI Subcommand (`kirkforge plugin`)

## Status: Done (commit pending)

## Problem
Plugin management is TUI-only. The `/plugins` slash-command family
(`src/tui/commands/plugins/mod.rs`) provides `list`, `enable`, `disable`,
`toggle`, `reload`, `trust`, `setup`, `sources`, `add`, `remove` — but
only inside the interactive TUI. There is no `kirkforge plugin ...` CLI
subcommand for headless / scripted / CI use cases.

A user running `kirkforge run` non-interactively (NDJSON mode, CI, cron,
or a wrapper script) cannot enable a plugin, list active plugins,
validate a manifest, or check plugin health without launching the TUI.
The 12th-pass review noted "no IDE/LSP integration" as a gap; the
plugin-management gap is the headless-mode equivalent: a headless user
has no plugin control surface.

The 12th-pass also said "Plugin toggle persistence shipped" — true in
the TUI (`src/tui/commands/plugins/mod.rs:476-490` `toggle_plugin`
mutates `cfg.enabled_plugins` and persists). But there is no CLI path
to do the same.

## Root cause
The plugin management operations were built as TUI slash-commands first.
The `clap` CLI (`src/cli.rs`) has subcommands for `run`, `bench`,
`replay`, `workflow`, `draw`, `doctor`, `mcp` — but no `plugin`
subcommand. The `/plugins` TUI commands call into `PluginRegistry` and
`session::plugin_tools::loader` directly; there is no shared "plugin
ops" layer that both the TUI and a CLI subcommand could call.

## Files to touch
- `src/cli.rs` — add a `Plugin` subcommand enum with variants for
  `list`, `enable <name>`, `disable <name>`, `toggle <name>`,
  `validate <path>`, `reload`, `sources`, `add <name> <path>`,
  `remove <name>`, `doctor`. Mirror the `PluginsOp` enum in
  `src/tui/commands/plugins/mod.rs:34-46`.
- `src/main/mod.rs` — add a `handle_plugin` dispatch that reads the
  shared config, runs the plugin op, and prints the result to stdout
  (for headless mode) or exits with a non-zero code on error.
- `src/tui/commands/plugins/mod.rs` — extract the core logic of each
  `PluginsOp` variant into a shared function (e.g.
  `plugin_ops::list(cfg) -> String`, `plugin_ops::enable(cfg, name) ->
  Result<...>`) so both the TUI and the CLI call the same code. The TUI
  keeps its `async fn handle_plugins_op` wrapper; the CLI calls the
  shared functions directly.
- `src/session/plugin_tools/mod.rs` or a new `src/session/plugin_ops.rs`
  — the shared plugin-ops layer. Functions take `&SharedConfig` and
  return `Result<String>` (human-readable output) or `Result<()>` (for
  mutations that just print "ok"/"failed").

## Approach
1. **Extract the shared ops.** In `src/tui/commands/plugins/mod.rs`,
   each `PluginsOp` variant's handler currently inlines
   `PluginRegistry` + `SharedConfig` manipulation. Extract the pure
   logic (no `AppState`, no `mpsc` channel) into a new
   `src/session/plugin_ops.rs` module:
   - `list(cfg: &SharedConfig) -> String` — format the active/blocked/
     available plugin list (mirror the TUI `list` output).
   - `enable(cfg: &mut SharedConfig, name: &str) -> Result<String>`
     — add to `enabled_plugins`, persist, return a status message.
   - `disable(cfg: &mut SharedConfig, name: &str) -> Result<String>`
     — remove from `enabled_plugins`, persist.
   - `toggle(cfg: &mut SharedConfig, name: &str) -> Result<String>`
     — flip the enable state.
   - `validate(path: &Path) -> Result<String>` — load the manifest, run
     `validate()`, print any errors.
   - `sources(cfg: &SharedConfig) -> String` — list `plugin_sources`.
   - `add_source(cfg: &mut SharedConfig, name, path) -> Result<String>`
   - `remove_source(cfg: &mut SharedConfig, name) -> Result<String>`
   - `doctor(cfg: &SharedConfig) -> String` — run the plugin health
     check (probe each enabled plugin's binary/script existence).
2. **Wire the TUI to the shared layer.** The TUI `handle_plugins_op`
  keeps the `AppState` + `mpsc` plumbing but delegates the formatting +
  config mutation to the shared functions.
3. **Add the CLI subcommand.** In `src/cli.rs`:
   ```rust
   #[derive(Subcommand, Debug)]
   pub enum PluginCommand {
       List,
       Enable { name: String },
       Disable { name: String },
       Toggle { name: String },
       Validate { path: PathBuf },
       Reload,
       Sources,
       Add { name: String, path: PathBuf },
       Remove { name: String },
       Doctor,
   }
   ```
   Add a `Plugin(PluginCommand)` variant to the top-level `Command`
   enum. In `src/main/mod.rs`, add `handle_plugin(cmd, shared_config)`
   that dispatches to the shared functions and prints the result.
4. **Test.** The shared `plugin_ops` functions are pure (take `&Config`,
   return `String`/`Result`) — unit-test them directly. The CLI
   subcommand is tested via `assert_cmd` or a manual `kirkforge plugin
   list` invocation in an integration test.

## Done condition
- `kirkforge plugin list` works from the CLI (prints active/blocked/
  available plugins to stdout, exits 0)
- `kirkforge plugin enable/disable/toggle <name>` mutate
  `enabled_plugins` in the config and persist (the same persistence
  the TUI uses)
- `kirkforge plugin validate <path>` loads a manifest and reports
  validation errors
- `kirkforge plugin doctor` runs the health check (probes each enabled
  plugin's binary/script existence)
- The TUI `/plugins` commands still work (they call the same shared
  functions)
- Unit tests for the shared `plugin_ops` functions
- ADR-056 (or next free number) documenting the shared plugin-ops layer
  and the CLI subcommand
- `docs/TECHNICAL.md` updated: the plugin system section now lists the
  CLI subcommand alongside the TUI slash commands
- Depends on: nothing (the plugin system exists)

## Notes
- The TUI `handle_plugins_op` uses an `mpsc` channel
  (`plugin_reload_tx`) to trigger a registry reload after a mutation.
  The CLI path does not have a live registry to reload — it just
  mutates the config and prints "ok; restart kirkforge to apply" (or
  "ok; the next `kirkforge run` will load the new set"). Document this
  honestly: CLI plugin ops are config mutations, not live-registry
  reloads.
- Do NOT duplicate the plugin-ops logic in the CLI. The point of this
  WO is to extract a shared layer so TUI and CLI share one
  implementation.
- The `ponytail:` / `ceiling:` annotations in
  `src/tui/commands/plugins/mod.rs` (if any) must be preserved.
