# Workorder 11.3 — Surface Trust-Tier Downgrades in `/plugins list`

## Status: Planned

## Problem
`apply_policy` (`crates/kirkforge-plugin-host/src/lib.rs:486-505`)
implements the trust-tier downgrade path:

```rust
let effective = if policy.max.permits(plugin.manifest.trust) {
    plugin.manifest.trust
} else {
    policy.max   // downgrade: cap at the host max
};
let plugin = filter_capabilities(plugin, effective, &mut warnings);
```

When `reject_on_excess = false` and a plugin's requested trust exceeds
the host max, the plugin's effective trust is capped at the host max
and the capabilities requiring higher trust are filtered out. The
warnings are generated (`policy_warnings`) and surface in the load
warnings — but the `/plugins list` TUI command
(`src/tui/commands/plugins/mod.rs:165-215`) shows the *requested*
trust tier, not the *effective* tier after downgrade. A user who sets
`max_plugin_trust = "read-only"` and loads a `trust = "shell"` plugin
sees "shell" in the list, not "read-only (downgraded from shell)".

The gap is visibility: the downgrade happens (capabilities are
filtered), but the user doesn't see it. A user wondering "why doesn't
this plugin's shell tool work?" sees "shell" in the list and is
confused. The downgrade is silent at the UI level.

## Root cause
`/plugins list` reads the *manifest* trust tier (from the loaded
`PluginManifest.trust`), not the *effective* trust tier (from
`HostedPlugin.effective_trust` after `apply_policy`). The
`HostedPlugin` struct has `effective_trust` (lib.rs:490), but the TUI
list command doesn't surface it.

## Files to touch
- `src/tui/commands/plugins/mod.rs` — the `list` handler (around
  line 165-215): when displaying a plugin, show both the manifest
  trust and the effective trust if they differ. Format:
  `trust: shell (downgraded to read-only)` or
  `trust: shell (effective: read-only)`. When they're equal, show
  just `trust: shell` (no noise).
- `src/tui/commands/plugins/mod.rs` — also show the *filtered
  capabilities*: if `apply_policy` removed any capabilities (e.g. a
  `network` tool was filtered because the host max is `shell`), list
  them as "filtered: 1 capability (network tool) hidden by trust tier".
  This requires the `HostedPlugin` to expose the filtered-capability
  count (or the host to record what was filtered and surface it).
- `crates/kirkforge-plugin-host/src/lib.rs` — `HostedPlugin` may need
  a `filtered_capabilities: Vec<Capability>` field (or the
  `apply_policy` warnings already contain this — check). If the
  warnings are sufficient, the TUI can display them.

## Approach
1. **Check what `apply_policy` records.** If `policy_warnings`
   contains the filtered-capability info (e.g. "network tool hidden by
   trust tier"), the TUI can display it directly. If not, extend
   `HostedPlugin` to record the filtered capabilities.
2. **Expose effective trust.** `HostedPlugin.effective_trust` already
   exists (lib.rs:490). The `PluginRegistry` needs a way to surface it
   to the TUI — either a `pub fn effective_trust(&self, name: &str) ->
   Option<TrustTier>` accessor, or the registry's `list` output
   includes it.
3. **Update `/plugins list`.** For each active plugin, show the
   effective trust tier. When it differs from the manifest trust,
   annotate: `shell (effective: read-only)`. When capabilities were
   filtered, add a line: `filtered: N capabilities hidden by trust
   tier (use /plugins trust <name> <tier> to raise)`.
4. **Add a CLI equivalent** (if WO 11.0 lands first, the CLI `plugin
   list` should show the same downgrade info).
5. **Test.** A unit test: load a plugin with `trust = "shell"` under a
   host max of `read-only` + `reject_on_excess = false`; verify the
   list output shows "shell (effective: read-only)" and the filtered
   capability count.

## Gate
```
cargo fmt --check && cargo clippy --all-targets -- -D warnings &&
cargo test --locked --workspace --no-fail-fast --all-features
cargo test -p kirkforge --lib tui::commands::plugins
```

## Done condition
- `/plugins list` shows the effective trust tier when it differs from
  the manifest trust (e.g. "shell (effective: read-only)")
- Filtered capabilities are surfaced (count + hint to raise the tier)
- Unit test: a downgraded plugin shows the annotation; a non-downgraded
  plugin shows no noise
- (If WO 11.0 lands first) `kirkforge plugin list` shows the same info
- `docs/TECHNICAL.md` plugin section updated to document the
  downgrade visibility
- Depends on: nothing (the downgrade path exists; this is surfacing it)

## Notes
- This is a P3 visibility WO. The downgrade already works; the user
  just can't see it.
- Do NOT change the downgrade semantics (the `reject_on_excess` /
  `effective = policy.max` logic is correct and ADR-050-documented).
  Only the display changes.
- Keep the non-downgraded case quiet: a plugin loaded at its requested
  trust should show `trust: shell`, not `trust: shell (effective:
  shell)` — the annotation is only when they differ.
