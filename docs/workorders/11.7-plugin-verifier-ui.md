# Workorder 11.7 — Plugin Verifier Results in `/verify` Panel + Cost Report

## Status: Planned

## Problem
Plugin-declared verifiers (`Capability::Verifier`) register into the
Rust `VerifierBus` via `register_plugin_verifiers_into_bus`
(WO 7.7/9.6, ADR-028) and flow into the correction loop as
`CorrectionResult` structs. The integration test
`plugin_verifier_triggers_correction_result` (WO 9.6) proves the
path: a plugin verifier's error verdict becomes a `CorrectionResult`
the correction loop acts on.

But the verifier results are not surfaced in the UI or the cost
report. A user running `kirkforge run` sees the correction loop fix
the error (good), but:
1. **No `/verify` panel.** There is no TUI slash command or panel that
  shows "here are the verifier verdicts from the last turn: lint (pass),
  types (pass), security (plugin:my-plugin: 2 errors), graph (pass)."
  The verdicts flow into the correction loop and disappear.
2. **No cost-report attribution.** The `MetricEvent::Verifier`
  (`src/shared/metrics.rs`) records `name` + `verdict` but does not
  include the `VerifierSource` (built-in vs plugin:name). The cost
  report (NDJSON metrics) can't distinguish a built-in security
  verifier finding from a plugin-declared one.
3. **No `/verify` CLI command.** A headless user can't ask "what did
  the verifiers say on the last turn?" without parsing the NDJSON
  metrics log.

The 12th-pass review named the verifier bus as "documented as
complete" (ADR-028 Accepted) — the *path* is complete, the
*observability* is not.

## Root cause
The verifier-bus path was built for the correction loop (consumer),
not for the UI (display). `VerifierBus` collects verdicts and routes
them to the correction loop; there is no query API for "what were the
last turn's verdicts?" The `MetricEvent::Verifier` records name +
verdict but not the source, so the cost report can't attribute.

## Files to touch
- `src/session/verifier/bus.rs` — add a `last_verdicts() ->
  Vec<VerdictEntry>` (or a `TurnVerdictReport` struct) that returns the
  verdicts from the last `verify()` call. The bus already runs the
  verifiers; it just doesn't retain the results for querying.
- `src/session/verifier/mod.rs` or `src/session/verifier/correction.rs`
  — after the correction loop runs, the verdicts are available; expose
  them to the executor, which exposes them to the TUI.
- `src/tui/commands/` — add a `/verify` slash command that displays the
  last turn's verifier verdicts: `verifier | source | verdict | file:line
  | message`. Group by verifier (lint, types, security, etc.) and show
  pass/fail counts.
- `src/shared/metrics.rs` `MetricEvent::Verifier` — add a `source:
  String` field (or `source: VerifierSource`) so the cost report
  distinguishes built-in vs plugin verifiers. Update the serialization
  (NDJSON) and the cost-report reader.
- `src/cli.rs` / `src/main/mod.rs` — add a `kirkforge verify` CLI
  subcommand (or a `--verify-report` flag on `kirkforge run`) that
  prints the last turn's verdicts to stdout (headless mode). If WO
  11.0 lands first, this can be `kirkforge plugin verify` or a
  standalone `kirkforge verify`.
- Tests — assert the `/verify` output includes a plugin verifier
  verdict when a plugin verifier reports an error. Assert the
  `MetricEvent::Verifier` includes the source.

## Approach
1. **Retain verdicts on the bus.** `VerifierBus::verify(ctx)` returns
  `Vec<VerdictEntry>` (it already does); the executor can retain this
  list per-turn. Add a `last_turn_verdicts: Vec<VerdictEntry>` field to
  the executor (or a `TurnVerdictReport` struct stored alongside the
  turn record).
2. **`/verify` TUI command.** A new slash command that reads the
  retained verdicts and renders them as a table. Format:
  ```
  Verifier        Source          Verdict   File:Line              Message
  lint            built-in        pass      —                      —
  types           built-in        pass      —                      —
  security        plugin:secpol   fail      src/foo.rs:42          eval() call
  graph           built-in        pass      —                      —
  ```
3. **Metric source field.** `MetricEvent::Verifier` gains a `source:
  String` (the `VerifierSource::Display` already exists at bus.rs:31).
  Update the NDJSON serialization (additive — old entries have no
  `source`, default to `"built-in"`).
4. **CLI.** `kirkforge verify` (or `--verify-report`) prints the same
  table to stdout for headless mode. This requires the executor to
  expose the retained verdicts; for a headless run, the verdicts are
  per-turn and the report can be printed at the end (or per-turn if
  `--verify-report per-turn`).
5. **Test.** A test that loads a mock plugin with a `security`
  verifier that reports an error; assert the `/verify` output (or the
  CLI report) includes the `plugin:<name>` source and the error.

## Gate
```
cargo fmt --check && cargo clippy --all-targets -- -D warnings &&
cargo test --locked --workspace --no-fail-fast --all-features
cargo test -p kirkforge --lib session::verifier::bus
cargo test -p kirkforge --lib shared::metrics   # the Verifier source field
```

## Done condition
- `/verify` TUI slash command shows the last turn's verifier verdicts
  with the source (built-in vs plugin:name), verdict, file:line, and
  message
- `MetricEvent::Verifier` includes the `source` field; the cost report
  distinguishes built-in vs plugin verifiers
- `kirkforge verify` CLI (or `--verify-report`) prints the same report
  to stdout for headless mode
- Test: a plugin verifier's error appears in the report with the
  `plugin:<name>` source
- ADR-062 (or next free) documenting the verifier-result surfacing
- `docs/TECHNICAL.md` verifier section documents the `/verify` command
  and the report format
- Depends on: WO 9.6 (the plugin-verifier path exists)

## Notes
- The `ponytail:` annotations in `src/session/verifier/bus.rs` (the
  `VerifierSource::Display` impl) must be preserved.
- The metric `source` field is additive (serde `#[serde(default)]`) so
  old NDJSON logs without `source` still parse (default to
  `"built-in"`).
- This is a P2 WO — observability, not correctness. The correction
  loop already works; this WO makes it visible.
