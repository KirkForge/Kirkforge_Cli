# Workorder 11.8 — Plugin Init Scaffolding Command (`kirkforge plugin init`)

## Status: Done (commit pending)

## Problem
Plugins are hand-authored. A developer who wants to create a new
plugin must manually:
1. Create a directory under `plugins/<name>/` (or
   `~/.local/share/kirkforge/plugins/<name>/`).
2. Write a `kirkforge.toml` manifest with the right schema (name,
   version, description, trust, api_version, capabilities).
3. Write tool/hook scripts (e.g. `tools/my_tool.sh`).
4. Make them executable (`chmod +x`).
5. Add the plugin to the config's `enabled_plugins` list (or use
   `/plugins enable <name>`).

There is no scaffolding command. A new plugin author has to read an
existing plugin's manifest to learn the schema, copy it, and modify.
The 12th-pass review noted "no IDE/LSP integration" — the plugin
authoring gap is the ecosystem equivalent: there's no "hello world"
path for a new plugin.

The `kirkforge plugin` CLI subcommand (WO 11.0) is the management
surface; this WO is the authoring surface.

## Root cause
The plugin system was built for the in-tree plugins (Stratum, Plugin3,
Draw, Video, kirkforge-plugin). Those were written by the core team
who knew the schema. The manifest validation (`PluginManifest::validate`,
WO 8.8) catches schema errors after the fact, but there's no
scaffolding to get a valid plugin in the first place.

## Files to touch
- `src/cli.rs` — if WO 11.0 lands, add an `Init { name, path }` variant
  to the `PluginCommand` enum. If 11.0 doesn't land, add a standalone
  `kirkforge plugin init <name>` subcommand.
- `src/main/mod.rs` — `handle_plugin_init(name, path)` scaffolds a
  new plugin directory:
  - `<path>/<name>/kirkforge.toml` — a minimal valid manifest with
    `name`, `version = "0.1.0"`, `description = "<name> plugin"`,
    `trust = "read-only"`, one `[[capabilities]]` skill entry with a
    placeholder prompt.
  - `<path>/<name>/tools/` — empty dir (with a `.gitkeep`).
  - `<path>/<name>/hooks/` — empty dir (with a `.gitkeep`).
  - `<path>/<name>/README.md` — a one-liner pointing to
    `docs/TECHNICAL.md` for the manifest schema.
  - Print "plugin scaffolded at <path>; edit kirkforge.toml and run
    `kirkforge plugin enable <name>` to activate."
- `docs/TECHNICAL.md` — add a "Creating a plugin" section pointing to
  `kirkforge plugin init` and the scaffolded layout.
- `docs/adr/` — new ADR (063 or next free) documenting the scaffolding
  decision (template manifest, default trust tier, directory layout).

## Approach
1. **Decide the default trust tier.** `read-only` is the safest
   default (a scaffolded plugin can only read files, not run shell
   commands). The author bumps it to `shell` or `network` when they
   add a tool that needs it. Document this in the scaffolded
   `README.md`.
2. **Template manifest.** The scaffolded `kirkforge.toml` is a
   minimal valid manifest:
   ```toml
   name = "<name>"
   version = "0.1.0"
   description = "<name> plugin"
   trust = "read-only"

   [[capabilities]]
   type = "skill"
   trigger = "/<name>"
   prompt = """
   You are the <name> plugin. The user invoked /<name>.

   TODO: implement this skill. Replace this prompt with the skill's
   instructions for the model.

   User request: {{args}}
   """
   model-hint = "default"
   ```
3. **Directory layout.** The scaffolded plugin has `tools/` and
   `hooks/` directories (empty, with `.gitkeep`) so the author can add
   tool/hook scripts without creating the dirs.
4. **Path.** Default path: `plugins/<name>/` (in-tree, for plugins
   that will ship with kirkforge). Override: `--path
   ~/.local/share/kirkforge/plugins/` (user-local, for community
   plugins). Print the resolved path.
5. **Enable hint.** After scaffolding, print:
   "Plugin scaffolded at <path>. Edit `kirkforge.toml`, then run
   `kirkforge plugin enable <name>` (or `/plugins enable <name>` in
   the TUI) to activate."
6. **Test.** An integration test: `kirkforge plugin init my-plugin
   --path <tmpdir>` creates the expected files; `kirkforge plugin
   validate <tmpdir>/my-plugin/kirkforge.toml` passes (the scaffolded
   manifest is valid).

## Done condition
- `kirkforge plugin init <name>` scaffolds a new plugin directory with
  a valid `kirkforge.toml` (passes `kirkforge plugin validate`),
  `tools/` + `hooks/` dirs, and a `README.md`
- The scaffolded manifest uses `trust = "read-only"` (safest default)
  and a placeholder skill prompt
- `kirkforge plugin validate <scaffolded path>` passes (the scaffolded
  manifest is valid out of the box)
- Test: scaffolding + validation in one flow
- `docs/TECHNICAL.md` "Creating a plugin" section documents the
  scaffolding command + the directory layout
- ADR-063 (or next free) documenting the scaffolding decision
- Depends on: WO 11.0 (the `kirkforge plugin` CLI subcommand) — or
  standalone if 11.0 hasn't landed

## Notes
- This is a P3 developer-ergonomics WO. It does not block the release
  or the verifier/sandbox work. It lowers the barrier for community
  plugins.
- Do NOT scaffold a `.kirkforge.sig` (signature file) — that's for
  the author to create with `minisign -S` after they've written the
  plugin. The scaffolded manifest documents the signature step in the
  `README.md`.
- The default `trust = "read-only"` means a scaffolded plugin can't
  run shell commands until the author bumps the trust tier. This is
  least-surprise: a copy-pasted scaffold can't accidentally run
  arbitrary shell.
- If WO 11.0 (plugin CLI) hasn't landed, this WO can stand alone with
  a `kirkforge plugin init` subcommand defined directly in `src/cli.rs`.
