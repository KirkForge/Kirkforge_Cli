# Workorder 12.6 — Testdoctor: Smart Auto-Suggest (Real Heuristics + Fix Application)

## Status: Done

## Problem
The current `kirkforge-testdoctor` suggest command
(`crates/kirkforge-testdoctor/src/suggest.rs`) uses crude string
matching on the binary/suite name:

```rust
fn suggestions_for(binary: &str, suite: &str) -> Vec<String> {
    if suite.starts_with("tests/") { /* suggest #[ignore] + mock */ }
    if binary.contains("sleep") { /* suggest tokio::time::pause */ }
    if binary.contains("ollama") { /* suggest wiremock */ }
    // generic fallback
}
```

This is a v1: it works for the obvious cases (integration tests that
spawn subprocesses, tests with "sleep" in the name) but misses the real
signal. A test named `test_env_guard_restores_prior_value_some_branch`
doesn't contain "sleep" or "ollama" but is flaky under tarpaulin due to
a temp-dir race — the suggest command gives it the generic fallback
("exclude it from the coverage suite") which doesn't help.

The 12.5 per-test timings give the suggest command real data: which
test is slow, how slow, and what it imports. The 12.6 suggest command
uses that data to produce specific, actionable suggestions — and
optionally applies them.

## Root cause
The suggest command was built with string-matching heuristics because
per-test timings (WO 12.5) didn't exist. Without knowing which test is
slow, the suggestions had to be generic. With per-test timings +
import analysis, the suggestions can be specific: "test X takes 3.2s,
imports `tempfile` + `tokio::time`, and spawns a subprocess → suggest
`tokio::time::pause` + mock the subprocess."

## Files to touch
- `crates/kirkforge-testdoctor/src/suggest.rs` — rewrite
  `suggestions_for` to use:
  1. **Per-test timings** (from WO 12.5): a test with `duration_ms >
     2000` gets "move behind `#[ignore]`"; a test with `duration_ms >
     500` gets "consider mocking."
  2. **Source analysis**: read the test's source file, look for
     patterns: `std::process::Command` (spawns a subprocess → suggest
     mock), `tokio::time::sleep` (suggest `tokio::time::pause` +
     `#[tokio::test(start_paused = true)]`), `std::fs::write` to a temp
     dir (suggest `tempfile::NamedTempFile` for race-safety),
     `std::env::set_var` (suggest `EnvGuard` from WO 10.0), network
     calls (suggest `wiremock`).
  3. **Import analysis**: parse the test file's `use` statements to see
     what it depends on; suggest mocks for the deps that are slow to
     instantiate (e.g. `headless_chrome::Browser` → suggest `FakeTab`).
- `crates/kirkforge-testdoctor/src/apply.rs` (new) — an optional
  `apply` command that takes a suggestion + the test file path and
  applies the fix: add `#[ignore = "slow: ..."]` annotation, wrap the
  test in `#[tokio::test(start_paused = true)]`, replace
  `tokio::time::sleep` with `tokio::time::pause`. Use `syn` to parse +
  rewrite the Rust source (check if `syn` is already a dep; if not, add
  it behind a feature flag — it's a large dep, ~500KB, but it's a
  dev-tool, not a runtime dep). If `syn` is too heavy, the apply
  command can be text-based (regex + string replacement) with a
  warning that it's not as robust as a real parser.
- `src/cli.rs` — add `Doctor::SuggestDetailed` (uses per-test data) +
  `Doctor::Apply { suggestion: String, test: String }` (applies a fix).
- Tests — for each suggestion heuristic, a test with a fixture source
  file that triggers the heuristic.

## Approach
1. **Source analysis.** Read the test file, scan for the patterns
   above. This is regex-based (not a full parser) for v1; upgrade to
   `syn` if the apply command needs to rewrite code.
2. **Suggestion format.** Each suggestion is `{ test, severity, fix,
   rationale }`. Example:
   ```
   test_env_guard_restores_prior_value_some_branch:
     severity: high (3.2s, flaky under tarpaulin)
     fix: replace `std::env::set_var` with `EnvGuard::set` (WO 10.0)
     rationale: the test mutates process-global env vars; under
       tarpaulin instrumentation the temp-dir race widens. EnvGuard
       serializes env access under a mutex.
   ```
3. **Apply.** The `apply` command takes a suggestion id + the test
   file path, applies the fix (add annotation, wrap attribute, replace
   call). For v1, text-based with a warning; for v2, `syn`-based.
4. **Test.** Fixture test files (one per heuristic) + assertions that
   the suggest command produces the expected suggestion + the apply
   command produces the expected diff.

## Done condition
- `kirkforge doctor suggest` uses per-test timings + source analysis to
  produce specific suggestions (not just string-matched generics)
- Each heuristic (subprocess, sleep, temp-dir, env-var, network) has a
  fixture test
- `kirkforge doctor apply --suggestion <id> --test <path>` applies a
  fix (text-based for v1; `syn`-based for v2 if the dep is justified)
- Unit tests for each heuristic + the apply path
- ADR-0029 updated: smart suggest + apply shipped
- `docs/TECHNICAL.md` documents the new doctor subcommands
- Depends on: WO 12.5 (per-test timings exist)

## Notes
- The `syn` dep is large (~500KB). For a dev-tool (the testdoctor is a
  separate bin, not in the main binary's release profile), the size
  is acceptable. If the testdoctor is a lib dep of the main bin (WO
  12.4), gate `syn` behind a `doctor-apply` feature so it's not in the
  default build.
- The apply command is opt-in and potentially destructive (it rewrites
  source files). Always show the diff + require `--yes` to apply. Do
  not silently rewrite test files.
- The `ponytail:` annotations in the testdoctor code must be preserved.
- This is a P2 WO — developer ergonomics. The 12.1-12.3 coverage work
  can proceed without it; 12.6 makes future coverage work faster.
