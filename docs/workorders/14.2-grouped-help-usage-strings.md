# Workorder 14.2 — Grouped Help + Fill Empty Usage Strings

## Status: Done

## Problem
The Pass-14 REVIEW (§3, "Help System — Grade: B+") calls the help
"comprehensive but undifferentiated." `src/tui/keys/slash_commands.rs`
defines 24 commands in a single flat `COMMANDS` array (lines 29-177).
The `help_text()` generator (lines 182-191) emits them as one flat
list with no grouping. Six commands have empty `usage: ""` fields
(`/memory`, `/metrics`, `/verify`, `/gh`, `/init`, `/plugins`) — the
user learns the command exists but not how to use it.

The REVIEW's recommended fix (item 3 + 4): add section headers
("Session", "Model", "Safety", "Workflow") and fill the empty usage
strings. ~30 lines of code, high UX payoff. The depth is there; the
organization is missing.

## Root cause
The table-driven design (one `SlashCommand` struct, one `COMMANDS`
const, one generator) was built for *consistency* — adding a command
is one row + one match arm. The design optimized for "help stays in
sync" (the `help_text_includes_every_command_trigger` test enforces
it) but not for *scanability*. There's no `group` field on
`SlashCommand`, so the generator can't section the output.

## Approach
1. **Add `group` field.** Update the struct + all 24 rows. Clippy will
   catch any row that forgets the field (struct init is positional in
   the const array — consider making it `..SlashCommand::default()`
   style or keep positional; match the existing style).
2. **Group the generator.** Iterate groups in a fixed order (the
   order you want them to appear), filter `COMMANDS` by group, emit
   header + commands. Avoid `HashMap` (non-deterministic order); use
   a `const GROUPS: &[&str]` array.
3. **Fill usage strings.** Grep each command's match arm in
   `dispatch_slash_command` to confirm the real syntax before writing
   the usage string. A wrong usage string is a regression.
4. **Line-mode help.** Cheapest honest fix: print the grouped
   `help_text()` output if reachable, else the pointer. Don't
   duplicate the 5-command list.
5. **Tests.** The grouping test is the new gate — it catches any
   future command that forgets a `group` field (the command would
   land in no group and the group-header test would still pass, so
   also assert every command appears in exactly one group).
