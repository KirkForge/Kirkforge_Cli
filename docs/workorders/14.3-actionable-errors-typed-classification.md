# Workorder 14.3 — Actionable Error Messages + Typed Error Classification

## Status: Planned

## Problem
The Pass-14 REVIEW (§5, "Error Handling UX — Grade: C+") names error
messages "functional but opaque." Two concrete issues:

1. **String-based error classification.** `KirkForgeError::from(anyhow)`
   at `src/main/mod.rs:154-180` lowercases the error message and
   matches substrings ("connection refused", "denied", "config parse").
   The TODO at line 156-157 acknowledges this should use
   `downcast_ref`. A sandbox denial phrased "operation not permitted"
   is caught, but a new error type with a novel phrase is misclassified
   as `General` → wrong exit code (1 instead of 4), no actionable hint.

2. **No actionable guidance.** `eprintln!("kirkforge: {e}")` at line
   321 prints the anyhow chain verbatim. A model connection failure
   shows "kirkforge: model unreachable" with no hint to check Ollama
   or set `ollama_host`. The doom-loop detector is a standout (the
   REVIEW calls it excellent), but the *initial* error path is opaque.

The REVIEW's fix (item 6): "Wrap connection/config errors with
suggestions. 20 lines per error type."

## Root cause
The error path was built for the operator (a developer who knows
what "model unreachable" means), not the user (who needs to know
*what to check*). The `KirkForgeError` enum exists and has the right
shape (`ModelUnreachable`, `AccessDenied`, `ConfigParse`, `General`
with exit codes 3/4/5/1), but the classifier is string-matching and
the printer is a raw `eprintln!`. The typed structure is there; the
*suggestions* and the *typed downcast* are missing.

## Files to touch
- `src/main/mod.rs:113-194` — `KirkForgeError`:
  - Add a `hint(&self) -> Option<&'static str>` method returning a
    suggestion string per variant:
    - `ModelUnreachable` → `"Check that the model provider is running
      (e.g. `ollama serve` for Ollama) or set `ollama_host` /
      `anthropic_api_key` in ~/.local/share/kirkforge/config.toml.
      See config.toml.example for all provider options."`
    - `AccessDenied` → `"The sandbox or permission policy blocked
      this. Check the `security.permission_rules` and
      `sandbox` sections in config.toml, or run with `--auto-approve`
      for trusted commands."`
    - `ConfigParse` → `"The config file at
      ~/.local/share/kirkforge/config.toml failed to parse. Compare
      against config.toml.example for the expected format."`
    - `General` → `None` (no generic hint; don't fake one).
  - Update the `eprintln!` at line 321 to print the hint if present:
    ```rust
    eprintln!("kirkforge: {e}");
    if let Some(h) = err.hint() {
        eprintln!("hint: {h}");
    }
    ```
- `src/main/mod.rs:154-180` — `From<anyhow::Error>`:
  - Keep the string-matching as a fallback (some errors genuinely are
    untyped `anyhow` chains), but add `downcast_ref` checks for the
    concrete error types the codebase already defines. Grep for
    `thiserror` / `Error` enum definitions in `src/` and `crates/` to
    find the typed errors worth downcasting. Likely candidates:
    - The plugin host's manifest-validation error type
    - The LSP client pool's error type
    - The MCP client's error type
  - For each typed error that has a clear category (connection,
    permission, config), add a `downcast_ref::<TypedError>()` branch
    before the string fallback. Remove the TODO at line 156 once at
    least 2 typed errors are downcast (the TODO says "as more library
    calls return typed errors, replace these" — this WO starts that
    replacement; it doesn't need to finish it).
- Tests: `src/main/mod.rs` tests — add tests for `hint()` per variant
  (assert `ModelUnreachable.hint()` contains "ollama", etc.) and a
  test that a typed error downcasts to the right `KirkForgeError`
  variant (not `General`). The existing string-classification tests
  (if any — grep `KirkForgeError` in tests) must still pass.

## Approach
1. **Add `hint()`.** Pure method on the enum, no I/O. The strings are
   `&'static str` (compile-time constants). Keep them short — 2 lines
   max on an 80-col terminal. Point to `config.toml.example` not the
   326-line file itself (the user can grep it).
2. **Print the hint.** One `eprintln!` addition. The hint goes to
   stderr alongside the error (not stdout) so it doesn't pollute
   piped output in `--non-interactive` mode.
3. **Downcast what's typed.** Grep first; don't invent error types.
   If the codebase has no typed errors for a category, leave the
   string match for that category and note it in `lessons.md` as
   "follow-up: add typed error for <category>". The goal is to start
   the downcast migration, not complete it.
4. **Test the hints.** The hint strings are part of the UX contract —
   a future refactor must not silently change "check that Ollama is
   running" to something vague. Pin them with assertions on substrings
   ("ollama", "config.toml", "permission_rules").
5. **Don't touch the doom-loop detector.** It's the standout; leave it.

## Notes
- The REVIEW's "Anyhow messages are developer-facing" point
  (`"serialize daemon request"` is meaningless to a user) is real
  but fixing it requires wrapping every anyhow conversion — out of
  scope. The hint layer is the pragmatic fix: the raw message stays
  for debuggability, the hint adds the user-facing guidance.
- Do NOT replace the string classifier wholesale. The downcast
  migration is incremental; a big-bang rewrite risks miscategorizing
  errors the string match currently handles. Add downcasts for
  errors you can verify, keep strings for the rest.
- The `ponytail:` / `ceiling:` annotations in `main/mod.rs` (if any
  — grep first) must be preserved. The error-classification TODO is
  itself a `ceiling:`-style note; update it, don't delete it
  silently.
