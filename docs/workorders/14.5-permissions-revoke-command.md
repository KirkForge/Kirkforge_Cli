# Workorder 14.5 — `/permissions` Command (List + Revoke `[A]lways` Rules)

## Status: Done

## Problem
The Pass-14 REVIEW (§4, "Approval Dialog — Grade: A−", rough edges)
 names: "No undo for `[A]lways`: Once a permission rule is persisted,
 there's no TUI command to revoke it. Must edit `config.toml` manually."
 The REVIEW's fix (item 9): "`/permissions` command: List and revoke
 permission rules created by `[A]lways`. 40 lines."

The `[A]lways` approval path at `src/tui/approval_keys.rs:188-206`
 calls `push_rule_unique(&mut cfg.security.permission_rules, rule)`
 and persists to disk. The rules work (the bang path tests at
 `src/tui/commands/bang.rs:282,306,320` prove `permission_rules` is
 consulted), but the only way to *see* or *remove* a rule is to open
 `config.toml` in an editor. A user who clicks `[A]lways` on the wrong
 command is stuck with it.

## Root cause
The approval dialog adds rules; nothing surfaces them. The
 `plugin_ops` pattern (WO 11.0) showed the way: a shared ops layer
 over `&Config` / `&mut Config` that both the TUI slash command and a
 future CLI can call. Permissions have no such layer — the rules live
 in `SecurityConfig.permission_rules` and are mutated only by the
 approval path.

## Files to touch
- `src/tui/keys/slash_commands.rs` — add a `/permissions` row to
  `COMMANDS` (group: "Safety", per WO 14.2). Usage:
  `"/permissions list | revoke <i> | clear"`.
- `src/tui/keys/slash_commands.rs` `dispatch_slash_command` — add the
  `/permissions` match arm. Subcommands:
  - `list` (default if no arg) — print the rules with indices.
  - `revoke <i>` — remove rule at 1-indexed position `i`; persist;
    print "Revoked rule #i: <rule summary>".
  - `clear` — remove all rules; persist; print "Cleared N rule(s)".
- `src/tui/commands/mod.rs` (or a new `src/tui/commands/permissions.rs`)
  — a small pure helper module `permission_ops` mirroring `plugin_ops`:
  - `pub fn list(cfg: &Config) -> String` — formatted table.
  - `pub fn revoke(cfg: &mut Config, index: usize) -> Result<String>`
    — bounds-check, remove, return summary.
  - `pub fn clear(cfg: &mut Config) -> String` — drain, return count.
  Keep it pure (no I/O in the ops layer; the caller persists via the
  existing config-write path). This mirrors the WO 11.0 plugin_ops
  split and leaves room for a future `kirkforge permissions` CLI.
- `src/session/config/mod.rs` `save_config` — already exists (line
  182); the TUI caller uses it. No change here.
- Tests:
  - `src/tui/commands/permissions.rs` tests — `list` on empty +
    populated config, `revoke` in-bounds + out-of-bounds (error),
    `clear` on empty + populated.
  - A TUI integration test (if the harness exists for slash commands
    — grep `dispatch_slash_command` in tests) asserting `/permissions
    list` output contains the rule summary format.

## Approach
1. **Ops layer first.** Pure functions over `&Config` / `&mut Config`.
   `list` formats the rules as `# | tool | args | action` rows. `revoke`
   uses `Vec::remove` with a 1-indexed → 0-indexed conversion and a
   bounds-check returning `anyhow!("rule {i} does not exist; {n} rules
   configured")`. `clear` uses `drain`. No I/O.
2. **TUI wiring.** Add the `/permissions` row + match arm. The match
   arm parses the subcommand + arg, calls the ops layer, prints the
   result, and persists via `save_config` (the existing
   `Config`-write path the approval path already uses). Persist only
   on `revoke` / `clear` — `list` doesn't mutate.
3. **Index stability.** The `list` output is the source of truth for
   the index the user passes to `revoke`. Print the index in the list;
   don't let the user guess. 1-indexed (matches `/jobs` and `/fork
   list` conventions — grep those to confirm the existing indexing
   style).
4. **Rule summary.** The `PermissionRule` struct (grep its definition
   in `src/shared/` or `src/session/`) — format it as
   `bash:command=cargo test → allow` or similar. Check the existing
   rule display in the approval dialog (`approval.rs`) for the format
   the user already sees, and reuse it for consistency.
5. **Don't touch the approval path.** `[A]lways` still works; this WO
   only adds the revoke surface.

## Done condition
- `/permissions list` prints each rule with a 1-indexed number + a
  human-readable summary
- `/permissions revoke <i>` removes rule `i`, persists, confirms
- `/permissions clear` removes all rules, persists, confirms
- Out-of-bounds `revoke` returns a clear error (not a panic)
- The ops layer is pure (no I/O) and testable without a TUI
- `docs/TECHNICAL.md` TUI section: one-line note on `/permissions`
  (doc-sync per §9 — new user-visible command)
- ADR not needed (command surface, not architecture)
- Depends on: WO 14.2 (for the `group` field on `SlashCommand`) —
  if 14.2 lands first, `/permissions` gets the group tag; if not,
  add the row without a group and 14.2 backfills it. Coordinate to
  avoid a double-edit.

## Notes
- The REVIEW's "no undo for `[A]lways`" is the user pain; this is the
  fix. The 40-line estimate is optimistic — the ops layer + tests +
  match arm + formatting is closer to 100-150 lines. Budget for that.
- Do NOT add rule *editing* (change allow → deny in place). That's a
  bigger surface and the user can revoke + re-approve. Keep this WO
  to list + revoke + clear.
- The `permission_rules` field on `SecurityConfig` is the single
  source of truth; the ops layer mutates it in place. No shadow
  state.
- If a future `kirkforge permissions` CLI subcommand is wanted
  (mirroring `kirkforge plugin`), the ops layer makes it a 20-line
  wrapper. Out of scope here; the ops layer is the foundation.
