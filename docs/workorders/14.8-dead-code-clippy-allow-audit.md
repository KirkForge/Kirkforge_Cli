# Workorder 14.8 — Dead-Code + `#[allow(...)]` Audit (Internal Stability)

## Status: Planned

## Problem
The Pass-14 REVIEW (§7, "Demand elegance") and AGENTS.md §5 both
 demand "no dead code" and "match the existing style." A grep of the
 current codebase shows the elegance contract is partially violated:

- `src/session/mod.rs:2` — `#![allow(dead_code)]` (module-wide)
- `src/shared/mod.rs:2` — `#![allow(dead_code)]` (module-wide)
- 12 `#[allow(clippy::too_many_arguments)]` annotations across
  `src/tui/`, `src/session/prompt/`, `src/session/executor/`,
  `src/tools/`, `src/main/` (per the grep in the 14-series analysis)
- Scattered `#[allow(dead_code)]` on individual fields/items in
  `src/tui/commands/persona.rs:51,63`, `src/tui/app.rs:25`,
  `src/adapters/anthropic.rs:656`, `src/tools/read_file.rs:9`,
  `crates/kirkforge-lsp/src/lib.rs:1399`,
  `crates/kirkforge-video/src/orchestrator/*.rs`

The two module-wide `#![allow(dead_code)]` are the biggest risk: they
 *silence* the dead-code lint for an entire module, so any genuinely
 dead code added later is invisible. The 12 `too_many_arguments`
 allows are a smell (the REVIEW §5: "A change that adds 100 lines to
 fix a 3-line bug is probably wrong" — a function taking 8+ args is
 often a missing struct), but they're localized and documented.

This is the "raise the polishlevel / quality of code" axis the user
 named for the 14-series: internal stability by removing blanket lint
 suppressions and either deleting the dead code they hide or
 downgrading them to targeted `#[allow]` with a `// reason: ` comment.

## Root cause
The module-wide `#![allow(dead_code)]` were added during rapid
 development (Series 6-9) to avoid churn on half-built modules. They
 were never revisited. The individual `#[allow]` annotations
 accumulated function-by-function as clippy fired; each was a
 pragmatic local fix, not a design decision. Neither pattern was
 audited after the features stabilized (Series 10-11 shipped without
 touching them).

## Files to touch
- `src/session/mod.rs:2` — remove `#![allow(dead_code)]`. Run
  `cargo clippy --all-targets -- -D warnings` and fix every dead-code
  warning it surfaces in `src/session/`. For each:
  - If the item is genuinely unused, delete it (preferred — dead code
    is a liability).
  - If the item is part of a public API used by tests or other crates,
    either `pub(crate)` it (if it should be crate-internal) or keep it
    and add a targeted `#[allow(dead_code)] // used by <consumer>`
    comment so the next audit knows why it's there.
  - If the item is conditionally-compiled (feature-gated), gate the
    `#[allow]` to the feature: `#[cfg_attr(not(feature = "x"),
    allow(dead_code))]`.
- `src/shared/mod.rs:2` — same process. This module holds `Config`,
  `Message`, `Role`, etc. — much is public API; the dead items are
  likely few. Audit + delete/target.
- The 12 `#[allow(clippy::too_many_arguments)]` — for each, decide:
  - If the function genuinely needs 8+ args (e.g. a render function
    that takes every span), keep the allow + add a `// reason: render
    function, spans are independent` comment so the next audit
    doesn't re-litigate.
  - If the args could be a struct (e.g. 4 token-count args → one
    `TokenCounts` struct), refactor. This is the "small, pure,
    well-named functions" demand from AGENTS.md §5. Do NOT force a
    refactor if it's risky — the comment + keep is acceptable for
    this WO; the refactor is a follow-up if the struct is obvious.
- `crates/kirkforge-lsp/src/lib.rs:1399`,
  `crates/kirkforge-video/src/orchestrator/slideshow_risk.rs:119,145`,
  `crates/kirkforge-video/src/orchestrator/animated_explainer.rs:397`
  — audit each `#[allow(dead_code)]`; delete the dead item or target
  the allow with a reason comment. The video crate is non-default
  feature; its dead code may be feature-gated leftovers.
- Tests: no new tests needed; the gate is "clippy stays clean after
  the allows are removed." If removing an allow surfaces a warning,
  the fix is the test.

## Approach
1. **Remove the two module-wide allows first.** These are the high-
   risk suppressions. Run clippy, capture the warning list, triage
   each. Expect 10-40 warnings per module (the allow has been there
   for many WOs). Budget time — this is the bulk of the WO.
2. **Delete over allow.** When a warning points to genuinely dead
   code, delete it. This is the "no dead code" demand. Don't keep
   dead code "in case it's useful" — that's the anti-pattern the
   REVIEW §5 names.
3. **Target + comment over delete (when public/feature-gated).** If
   the item is `pub` and used by a downstream crate or test, or
   feature-gated, a targeted `#[allow]` with a reason comment is
   correct. The reason comment is the contract: the next auditor
   reads it and knows the item is intentionally retained.
4. **Triage the 12 `too_many_arguments`.** Don't refactor all 12 —
   only the ones where a struct is obvious (3+ args of the same
   type). For the rest, add the reason comment. This WO is about
   *visibility* (every allow has a reason) not *refactoring* (that's
   a separate series).
5. **Verify the gate.** `cargo clippy --all-targets -- -D warnings`
   must stay clean. This is 3-4 min per run (AGENTS.md §7) — budget
   for multiple runs as warnings surface one-by-one.

## Gate
```
cargo fmt --check && cargo clippy --all-targets -- -D warnings &&
cargo test --locked --workspace --no-fail-fast &&
cargo check --workspace --all-targets
# The clippy run is the primary gate; it must stay clean with the
# module-wide allows removed.
```

## Done condition
- `src/session/mod.rs` and `src/shared/mod.rs` no longer have
  `#![allow(dead_code)]`; every dead-code warning they hid is either
  fixed (deleted) or has a targeted `#[allow]` + reason comment
- Every remaining `#[allow(clippy::too_many_arguments)]` has a
  `// reason: <why>` comment (or is refactored into a struct if
  obvious)
- `cargo clippy --all-targets -- -D warnings` stays clean
- `lessons.md`: note how many warnings each module-wide allow hid
  (data point for future audits)
- `state.md`: no change (internal cleanup, not a state-level item)
- `docs/TECHNICAL.md`: no change (internal quality, not architecture)
- ADR not needed (lint policy, not architecture) — but if the
  "every `#[allow]` must have a reason comment" rule is to be
  enforced going forward, pin it in AGENTS.md §5 (fold into the
  existing "Demand elegance" section, don't create a new ADR)
- Depends on: nothing

## Notes
- This WO is unglamorous but it's the "stable" axis the user named.
  Module-wide lint suppressions are technical debt that compounds;
  removing them is the stability work.
- Budget clippy time: AGENTS.md §7 warns 3-4 min per run. Removing a
  module-wide allow will surface N warnings; fix N, re-run clippy, fix
  the next batch. Don't run the full gate after every single edit.
- Do NOT add new `#[allow]` to suppress warnings the audit surfaces.
  The whole point is to fix or target, not re-suppress. If a warning
  is genuinely spurious, document why in the comment; if it's real,
  fix it.
- The video crate's dead code may be feature-gated leftovers from
  WO 6.9. Check `#[cfg(feature = "video")]` boundaries before
  deleting — a "dead" item under `video` feature off is live under
  `video` on.
- Preserve `ponytail:` / `ceiling:` annotations — they're often on
  the same items as `#[allow]`; don't delete a ponytail while
  removing an allow. Grep before editing each item.
