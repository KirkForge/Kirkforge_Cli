# Workorder 15.0.0.1 — Bucketlist: Cross-Review Findings (5-Reviewer Pass)

## Status: Planned

## Problem
Five independent reviews of the `dev` branch (DeepSeek V4 Pro, MiniMax M3,
GLM 5.2, and two webchat instances) all found real dead code, bugs,
errors, security gaps, and doc-drift. The findings overlap
substantially (all 5 flagged dead code / stale docs; 3 of 5 flagged
the CI gate theater; 2 of 5 flagged the Bedrock envelope buffer /
cloud-provider gaps). This workorder is the consolidated bucketlist —
every finding from every review, deduplicated, verified against
current code, graded by severity, and prioritized. It is the
single-source backlog for Series 15.

The user asked: "all 5 found deadcode and bugs and errors..so write
it into workorder 15.0.0.1 so we have a bucketlist."

## Root cause
The codebase grew across 14 workorder series (~4,600 tests, 84 ADRs,
16 crates). Each series shipped gated, but the reviews surface the
class of issue that gates don't catch: CI steps that look like gates
but don't gate, security holes in paths the maintainer doesn't hit
on Ollama, doc-drift between state.md / ADRs / TECHNICAL.md, and
stale test counts. The gates prove behavior at the seams they cover;
the reviews prove the seams have gaps.

## Evidence grounding (all verified against HEAD `8926fe2`)
Every finding below was checked against current code. Findings the
reviews named that are already fixed are NOT included (e.g. review-1's
"C-1 uncommitted changes" was the mid-session `src/tui/keys/mod.rs`
edit that has since been committed; the Windows `test_cache_results`
flake is fixed at `4bdc13f`). Only live findings are in the bucketlist.

## Tier 1 — Honesty / Safety violations (fix first)

### 1.1 CI gate theater: `ci.yml:294` "Fail if success rate drops below 10%" never fails
- **Source:** review-3 (C3), webchat-2
- **Evidence:** `.github/workflows/ci.yml:294-306` — the step is named
  `Fail if success rate drops below 10%` but the `if` branch only emits
  `::warning::` then exits 0. A sub-10% bench success rate passes CI.
- **Root cause:** The real regression gate lives in
  `bench-baseline.yml:170` (`bench-pr-delta` with
  `--fail-on-regression 10`); this step is vestigial AND misleadingly
  named.
- **Fix:** Rename to "Warn if..." OR make the `if` branch `exit 1`.
- **AGENTS.md §4 violation:** yes (`|| true`-style gate theater).

### 1.2 CI gate theater: `ci.yml:388` `cargo audit || true` masks all RUSTSEC advisories
- **Source:** review-3 (H11), webchat-2
- **Evidence:** `.github/workflows/ci.yml:388` — `cargo audit || true`
  swallows the exit code. Any dependency vulnerability passes CI.
- **Fix:** Replace `|| true` with `continue-on-error: true` on the
  step (visible in the run UI, doesn't hide the exit code), OR make it
  a real gate.
- **AGENTS.md §4 violation:** yes.

### 1.3 `load_from_dir` skips `PluginManifest::validate()` on the primary bulk-load path
- **Source:** review-3 (C2)
- **Evidence:** `crates/kirkforge-plugin-host/src/lib.rs:175` calls
  only `validate_api_version()`, never `validate()`. `load_one` (line
  322) DOES call `validate()` and surfaces every error as a warning —
  but `load_from_dir` is the path the plugin loader uses in
  production. Manifest schema errors (bad name, bad semver, duplicate
  triggers, unknown hook events, untrusted command paths) are silently
  accepted during normal plugin load.
- **Fix:** Add `if let Err(errs) = plugin.manifest().validate() {
  for e in errs { warnings.push(format!("{}: {}", path.display(), e));
  } continue; }` after line 178.
- **Defeats:** WO 8.8 "show every issue at once" contract.

### 1.4 `computer_use` `evaluate` runs model-supplied JS with no network sandbox → SSRF via browser
- **Source:** review-3 (C1)
- **Evidence:** `src/tools/computer_use.rs:453-456` —
  `args["expression"]` is passed straight to
  `session.evaluate(expression)`. The URL gate
  (`host_is_literal_internal_ip`) runs on the `url` arg of
  `open`/`navigate` only. Once a page is loaded, `evaluate` can run
  `fetch('http://169.254.169.254/...')` from inside the browser,
  bypassing the host-level check. Chrome has no `--proxy-server` /
  `--host-resolver-rules` (see `src/main/chrome_launcher.rs`).
- **Fix:** Launch Chrome with `--proxy-server`/`--host-resolver-rules`
  that block RFC1918 + link-local, OR sandbox `evaluate` to deny
  `fetch`/`XMLHttpRequest` to non-allowlisted hosts.

### 1.5 `web_fetch` has no DNS-rebinding check; only literal-IP hosts are blocked
- **Source:** review-3 (H1), review-2 (S4)
- **Evidence:** `src/tools/web_fetch.rs:91-95`, acknowledged at
  `:176-178` as a `ceiling:`. A model fetching
  `http://attacker.example.com/` whose A record resolves to
  `127.0.0.1` or `169.254.169.254` defeats the prefix-match deny-list.
- **Fix:** Pin the resolved IP and re-check it (the code comment already
  names the fix; it's just not implemented).

### 1.6 `bash` Docker bind-mount string built from user `workdir` with no sanitization
- **Source:** review-3 (H2)
- **Evidence:** `src/tools/bash.rs:62-63` —
  `format!("{workdir_str}:/work")`. If the model passes
  `workdir: "/tmp/evil:/etc:ro"`, Docker parses the first `:` as the
  host/container split and mounts `/tmp/evil` at `/etc`. Worse: the
  Docker branch (`run_docker`) does NOT call
  `check_bash_command_str` at all — only the foreground path does.
- **Fix:** Canonicalize + sandbox-contains-check the workdir before
  string-formatting the bind mount; route the inner `cmd` through
  `check_bash_command_str` on the Docker path too.

### 1.7 state.md "Deferred items" falsely lists `use_workflow_run` as deferred
- **Source:** review-3 (M19)
- **Evidence:** `state.md:52` says `use_workflow_run` is deferred ("No
  `Tool` impl exists for `kirkforge-workflow`"). But WO 9.1 is Done
  (`docs/workorders/9.1-workflow-tool-wrapper.md:3`), `WorkflowTool`
  exists (`src/tools/workflow.rs:24`), and
  `benches/tasks/use_workflow_run.toml` exists. state.md L5 even says
  "the `use_workflow_run` task shipped in WO 9.1" — contradicting L52
  in the same file.
- **Fix:** Delete the row from the Deferred items table (it's done).
- **AGENTS.md §7 anti-pattern:** "Multiple items listed as 'open'
  turned out to be already shipped."

## Tier 2 — Real correctness bugs (fix soon)

### 2.1 Bedrock `parse_bedrock_event_stream` unbounded `envelope_buffer` + drops multi-event chunks
- **Source:** review-3 (H3), review-2 (S7)
- **Evidence:** `src/adapters/anthropic_bedrock.rs:127` —
  `envelope_buffer.extend_from_slice(chunk)` grows without limit. If
  `extract_payload` returns `None`, the buffer is never cleared → OOM.
  `:140-145` — if a chunk contains multiple event-stream frames, only
  the first is parsed; the rest are discarded by `clear()`. Mid-turn
  tool-call deltas are silently dropped. The downstream
  `parse_anthropic_stream` has `MAX_SSE_BUFFER_BYTES = 8 MiB`; this
  outer buffer has no cap.
- **Fix:** Cap the buffer at 8 MiB (match the inner parser); loop
  `extract_payload` until it returns None before clearing.

### 2.2 Vertex `service_account_token` silently returns `""` on token-fetch failure
- **Source:** review-3 (H4)
- **Evidence:** `src/adapters/vertex_auth.rs:44` —
  `Ok(token.token().unwrap_or_default().to_string())`. A `None` token
  becomes `""`; the adapter sends `Authorization: Bearer ` (empty); GCP
  returns a generic 401 and the actual cause is hidden.
- **Fix:** `token.token().ok_or_else(|| anyhow!("service account token
  endpoint returned None"))?`.

### 2.3 `dispatch_tool_call_batch` Phase 2 spawns tasks after `cancelled` flips, leaking detached tasks
- **Source:** review-3 (H7)
- **Evidence:** `src/session/executor/turn.rs:1066-1096`. When
  cancellation arrives mid-spawn, already-spawned `JoinHandle`s in
  `running` are abandoned by the `break` and never awaited — the tasks
  run to completion detached, holding subprocess/network resources for
  up to `tool_timeout_secs` (default 30s, max 3600s).
- **Fix:** Propagate `cancelled` into `run_prepared_call` and abort
  un-awaited handles on `break`.

### 2.4 `CorrectionResult.verifier` hard-coded to `"verifier"` on the event-driven path
- **Source:** review-3 (M1)
- **Evidence:** `src/session/verifier/correction.rs:107-126`. The
  executor writes `tool_name: format!("verifier:{}", cr.verifier)`, so
  the model sees `verifier:verifier` for every correction — useless
  for diagnosing which verifier (lint/build/git/rustfmt/test) fired.
  The `BusVerifier` path (`dispatch.rs:161`) does it right.
- **Fix:** Replace `"verifier".into()` with the decisive verifier's
  `name()`.

### 2.5 `format_verdict_report` slices `&file_line[..23]` without checking char boundaries
- **Source:** review-3 (L1)
- **Evidence:** `src/session/verifier/bus.rs:193-197`. Panics on a path
  containing a multi-byte UTF-8 char at byte index 22 (e.g. `café.txt`).
- **Fix:** Use `is_char_boundary` before slicing (the
  `truncate_tool_output` helper in `helpers/mod.rs:195-199` does it
  right; this site doesn't).

### 2.6 `EventBus` idempotency key for `BashExec` is `command` only — repeated commands dedup
- **Source:** review-3 (M2)
- **Evidence:** `src/session/event_bus.rs:130-132, 402-426`. Two
  `git add .` calls in a batch produce the same idem key; the second
  dispatch's handlers (including the git verifier) never see the event.
- **Fix:** Include `exit_code`/`stdout_len`/`stderr_len` in the
  `BashExec` idem key; same for `FileWrite` (currently
  `path + content_length`).

### 2.7 Phase 3 `record_tool_result` re-runs `path_guard.check_write(path)` (TOCTOU + double `git check-ignore`)
- **Source:** review-3 (M3)
- **Evidence:** `src/session/executor/turn.rs:723-737`. Wastes a second
  canonicalize + sandbox-contains check + a second `git check-ignore`
  subprocess spawn per edit. TOCTOU window where a parallel tool flips
  the guard state between Phase 1 and Phase 3.
- **Fix:** Carry `resolved` from Phase 1 into Phase 3 and skip the
  re-check (the `pre_run_verdict` docstring already claims it does).

### 2.8 Phase 2.5/Phase 3 double-records `AccessDenied` for denied file edits
- **Source:** review-3 (M4)
- **Evidence:** `src/session/executor/turn.rs:1163-1214, 1223-1300`.
  A deferred file call denied by the read gate inserts
  `ToolOutcome::Failure(AccessDenied)` into `results`; Phase 3 then
  re-runs the path guard + read gate and emits a fresh denial message.
  The model sees two identical "Access denied" tool results for one
  failed edit.
- **Fix:** Skip Phase 3 re-check when Phase 2.5 already recorded a
  denial.

### 2.9 Shell pattern scanner flags documentation/comments as secrets
- **Source:** review-2 (S1)
- **Evidence:** `src/session/verifier/security.rs:269-276`. Patterns
  like `rm -rf /` and `:(){ :|:& };:` are substring-matched in ALL file
  content, including comments and docstrings. Returns
  `Verdict::Unfixable`, blocking the correction loop.
- **Fix:** Parse file type before applying substring patterns; skip
  comment/docstring content for shell-pattern checks.

### 2.10 Git worktree check flags staged files as `Unfixable`
- **Source:** review-2 (S3)
- **Evidence:** `src/session/verifier/git.rs:166-193`. After `git add`,
  staged files appear as "dirty worktree" errors. The model can commit
  them, but the error presentation is misleading.
- **Fix:** Distinguish "staged" from "dirty" in the error message;
  staged files are not a worktree violation.

### 2.11 `bash_minify::extract_file_path` reads files outside the sandbox/deny-list
- **Source:** review-3 (M13)
- **Evidence:** `src/tools/bash_minify.rs:345-357`. `try_minify_bash_output`
  extracts a path from the command string and calls
  `minify_source_safe` which reads the file from disk — bypassing
  `PathGuard::check_read` and `DenyList`. A symlink target like
  `~/.ssh/id_rsa` is followed with no recheck.
- **Fix:** Route the extracted path through `PathGuard::check_read`
  before reading.

### 2.12 `computer_use.rs` triple lock acquisition — stale boolean between acquisitions
- **Source:** review-2 (C4)
- **Evidence:** `src/tools/computer_use.rs`. The same
  `Mutex<Option<BrowserSession>>` is locked, checked, dropped,
  re-locked, and re-locked again in a single `run()` call. Between
  acquisitions, the boolean is stale.
- **Fix:** Hold the lock through the check-and-use, or restructure to
  a single acquisition.

### 2.13 `git_sanitation` reads only the first 1 MiB of each file
- **Source:** review-3 (M25)
- **Evidence:** `src/session/git_sanitation.rs:22`
  (`SCAN_CAP_BYTES = 1024*1024`). A secret placed after the 1 MiB mark
  in a large generated file passes the scan.
- **Fix:** Either scan the full file (with a larger cap) or document
  the 1 MiB limit in the commit-blocker message.

### 2.14 `trufflehog_scan` runs with no timeout
- **Source:** review-3 (M26)
- **Evidence:** `src/session/verifier/security.rs:175-208`. If
  `trufflehog` hangs (network, git fetch) the verifier blocks the
  correction loop indefinitely.
- **Fix:** Add a timeout to the `trufflehog` spawn.

### 2.15 `Bash::run_docker` calls `.expect("docker_config is Some")` on `Option`
- **Source:** review-3 (H5)
- **Evidence:** `src/tools/bash.rs:50`. The current caller guards, but
  the invariant is implicit. A future call site panics.
- **Fix:** Use `?` or return `ShellError::Spawn`.

### 2.16 `ResponseCache::get` reads the disk file with no size cap
- **Source:** review-3 (M6)
- **Evidence:** `src/adapters/cache.rs:64` —
  `std::fs::read(&path).ok()?`. A corrupted or crafted multi-GB cache
  file is read entirely into memory before `serde_json::from_slice`
  fails → OOM.
- **Fix:** Check file size before reading; cap at a reasonable limit
  (e.g. 64 MiB).

### 2.17 Anthropic `parse_anthropic_stream` EOF drops a pending tool_use with no input silently
- **Source:** review-3 (M8)
- **Evidence:** `src/adapters/anthropic.rs:454-461`. If
  `content_block_start` arrives but the connection drops before any
  `partial_json`, `pending_tool.input.is_none()` is true and the tool
  is dropped. The executor sees a `Done` with no preceding `ToolCall`
  and assumes the turn was empty.
- **Fix:** Emit a `ToolCall` with an empty `input` (or a
  `StreamEvent::Error`) so the executor knows the tool was attempted.

### 2.18 `init_default_verifiers` spawns bus-handler registration fire-and-forget
- **Source:** review-3 (H8)
- **Evidence:** `src/session/executor/mod.rs:518-548`. The
  `rt.spawn(async { if let Err(e) = bus.register(h).await { ... } })`
  is not awaited. The returned `count` includes the handler even if
  registration later fails. The executor reports "6 verifiers
  registered" when only 5 are.
- **Fix:** Await the registration, or adjust `count` on failure.

### 2.19 `PluginTool::execute` (host crate) does NOT apply rlimits — only `PluginToolWrapper` does
- **Source:** review-3 (M11)
- **Evidence:** `crates/kirkforge-plugin-host/src/tool.rs:73-79`
  spawns with plain `Command::new`, no `setup_rlimits`. ADR-060 says
  rlimits apply to "plugin tools" but the host-crate `PluginTool` is a
  separate, unhardened spawn path.
- **Fix:** Call `setup_rlimits` in `PluginTool::execute` too, or
  document the divergence in ADR-060.

### 2.20 Bundled `kirkforge-plugin3` manifest declares a hook event not in `KNOWN_EVENTS`
- **Source:** review-3 (H6)
- **Evidence:** `plugins/kirkforge-plugin3/kirkforge.toml:94` declares
  `event = "post-tool-write_file"`, but
  `crates/kirkforge-plugin/src/lib.rs:297-305` `KNOWN_EVENTS` only
  allows `session-start, pre-turn, post-turn, pre-tool-bash,
  post-tool-bash, pre-compact, post-compact`. The runtime emits
  `post-tool-write_file` (`src/session/budget.rs:664`), so the hook
  set is correct but the validator allowlist is stale. Masked by 1.3
  (the `validate()` call that would catch this is skipped on the
  primary load path).
- **Fix:** Add `post-tool-write_file` (and any other emitted-but-
  unlisted events) to `KNOWN_EVENTS`.

### 2.21 `apply_ignore_slow` regex matches any `fn test_foo(` — not anchored to a test attribute
- **Source:** review-3 (M22)
- **Evidence:** `crates/kirkforge-testdoctor/src/apply.rs:67`. Matches
  any `fn test_foo(` on its own line without checking the line above is
  `#[test]`/`#[tokio::test]`. A non-test helper named `test_foo` gets
  an `#[ignore]` added.
- **Fix:** Check the line above for a test attribute before applying.

### 2.22 `apply_env_guard` does not add the `use EnvGuard` import
- **Source:** review-3 (M23)
- **Evidence:** `crates/kirkforge-testdoctor/src/apply.rs:170-185`.
  `apply --yes` produces code that won't compile without a manual
  `use` addition.
- **Fix:** Either add the import or refuse to write.

### 2.23 Bench `verify_only` reports SKIP as `success: true`
- **Source:** review-3 (M17)
- **Evidence:** `crates/kirkforge-bench/src/lib.rs:466-478`. A
  `requires_model` task returns `success: true, error: Some("skipped
  (requires model)")`. A CI gate that sums `success` counts SKIPs as
  passes.
- **Fix:** Add a `skipped: bool` field (or `status: enum`) so consumers
  can distinguish SKIP from PASS.

### 2.4 `compare_with_threshold` uses `< -threshold` (strict) — an exactly-10pp drop is NOT a regression
- **Source:** review-3 (M18)
- **Evidence:** `crates/kirkforge-bench/src/lib.rs:377`. An exactly-
  10pp drop (80% → 70%, delta = -0.10) is `-0.10 < -0.10` = false →
  not a regression. Off-by-one in the boundary condition.
- **Fix:** Use `<= -threshold` if a 10pp drop should be a regression,
  or document the strict-inequality as intentional.

## Addendum — webchat hands-on findings (2026-07-31, post-review)

The webchat reviewer actually built and ran the code (npm install +
tsc --build + vitest + kirkforge verify-workspace). Two new findings
from running, not reading:

### 5.1 (HIGH) `enabled_plugins` toggle is cosmetic for compiled-in Stratum/Budget

- **Source:** webchat-2 (hands-on)
- **Evidence:** `src/main/mod.rs` registers Stratum/Budget tools under
  `#[cfg(feature = "stratum")]` / `#[cfg(feature = "budget")]` with NO
  runtime `cfg.tools.enabled_plugins.contains("stratum")` check. Same
  for the in-process hooks (`StratumSessionStartHook`,
  `PostToolBashHook`, etc.) in `src/session/executor/mod.rs` — no
  `enabled_plugins` gate in their `handle()` bodies. `enabled_plugins`
  (per `plugin_ops.rs`) gates only the external shell-plugin loader and
  drives the `/plugins list` display. So on the default build (features
  on), `/plugins disable stratum` updates the config + display but
  Stratum's tools and hooks stay live in the toolset regardless.
- **User impact:** the TUI toggle the user asked for ("the TUI/CLI
  itself should have a toggle so they can be toggled on/off") exists
  but is cosmetic for the two folded subsystems that matter most.
- **Fix:** Thread `cfg.tools.enabled_plugins.contains("stratum")` (and
  `"budget"`) into the `#[cfg(feature = ...)]` blocks in `main.rs` and
  into the hook registration in `executor/mod.rs`. The config struct is
  already plumbed; this is a small contained change, not a redesign.

### 5.2 (MEDIUM) TS orchestrator bridge test drift — 2 failing tests on the exact seam that connects TS verifiers to the Rust correction loop

- **Source:** webchat-2 (hands-on — ran `npx vitest run`)
- **Evidence:** `npm/kirkforge-plugin` is a 24.7k-line TS monorepo with
  per-language lint packages (tool-lint-ts/py/go/rs/c/sh/sql +
  tool-tsc + tool-pyright). 999/1001 tests pass. The 2 failures are in
  `packages/orchestrator`:
  1. `bridge-emitter.test.ts` expects the security emitter to produce
