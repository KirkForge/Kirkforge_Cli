# Workorder 17.1 — Anthropic Auth + Per-Provider Env Resolution

## Status: Done

## Problem
The plain Anthropic adapter is non-functional against `api.anthropic.com`.
`src/adapters/anthropic.rs:79-102` sets only `anthropic-version` and
`content-type` headers — it never sends `x-api-key` or `Authorization`, and
there is no `ANTHROPIC_API_KEY` env support anywhere in the crate. A user who
points `kf-code` at the real Anthropic endpoint gets 401s.

By contrast `vix-main/internal/config/keyring.go` resolves per-provider API
keys via env → keychain → `.env` for `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`,
`OPENROUTER_API_KEY`, `DEEPSEEK_API_KEY`, … (see `providers.json` `env_var`
fields). KirkForge resolves exactly one key — `opencode_zen_api_key` —
stored cleartext in TOML (`src/shared/config/model.rs:58`), and
`src/session/config/env_overrides.rs:335` honors only
`KF_CODE_ANTHROPIC_PROVIDER`.

## Root cause
Auth is hardcoded to a single bespoke key path. There is no per-provider
env-var resolution layer, so adapters have no place to pull their own
credentials from. The Anthropic adapter was written against an OpenCode-Zen
proxy that injects auth upstream, and was never given a direct-Anthropic path.

## Files to touch
- `src/adapters/anthropic.rs` — in `stream`, resolve the key and add the
  `x-api-key` header (and `Authorization: Bearer` when an OAuth token is
  present, though OAuth itself is Series 18). Source the key via the new
  resolver (below), not a new env read inline.
- `src/adapters/mod.rs` (or a new `src/adapters/auth.rs`) — a
  `resolve_api_key(provider: &str) -> Option<String>` helper implementing the
  env resolution order: config field → `<PROVIDER>_API_KEY` env → (keychain,
  stubbed to `None` for now; keychain is Series 18). One function every adapter
  calls.
- `src/session/config/env_overrides.rs` — extend the env layer so the standard
  per-provider env vars (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`,
  `DEEPSEEK_API_KEY`, `GEMINI_API_KEY`, `KIMI_API_KEY`, …) feed each adapter's
  auth, not just `KF_CODE_ANTHROPIC_PROVIDER`.
- `src/adapters/deepseek.rs`, `gemini.rs`, `kimi.rs`, `glm.rs` — route their
  existing key reads through `resolve_api_key` so the env order is uniform.
  (These are the four near-identical adapters flagged in the ponytail audit;
  collapsing them is separate work — here only thread the key through.)
- `config.toml.example` — document `anthropic_api_key` and the
  `ANTHROPIC_API_KEY` env var.
- Tests: `src/adapters/anthropic.rs` `#[cfg(test)]` — assert the `x-api-key`
  header is present when `ANTHROPIC_API_KEY` is set, absent when unset (and
  that the adapter errors cleanly with "no Anthropic API key" rather than
  sending an unauthenticated request).

## Approach
1. **Resolver first.** `resolve_api_key(provider)` returns the first non-empty
   of: the config field for that provider, `<UPPERPROVIDER>_API_KEY`, and a
   keychain hook (`None` for now). Pure function, unit-testable without a TUI.
2. **Anthropic header.** `AnthropicAdapter::stream` calls the resolver; if
   `None`, return `anyhow!("no Anthropic API key set (ANTHROPIC_API_KEY or
   [providers].anthropic_api_key)")` — fail loud, not silent-401. If `Some`,
   set `x-api-key`. Keep `anthropic-version` + `content-type` as-is.
3. **Mirror to the four ollama-style adapters** only insofar as they already
   read a key — point them at the resolver so env precedence is consistent.
   Do not refactor the four into one here (that's the ponytail-audit
   collapse, separate WO).
4. **No OAuth, no keychain yet.** Those are Series 18. The resolver's keychain
   arm returns `None` and a `// TODO(Series 18): keyring::Entry` comment marks
   the seam. This WO only makes the adapter actually authenticate.

## Done condition
- `kf-code run` against `api.anthropic.com` authenticates with
  `ANTHROPIC_API_KEY` set in the env (no proxy required).
- A missing key produces a clear error before any HTTP request, not a 401.
- Every adapter that takes a key reads it through `resolve_api_key`, so env
  precedence is uniform across providers.
- `config.toml.example` documents the Anthropic key + env var.
- ADR: add a short note to `docs/TECHNICAL.md` (Providers section) that
  direct-Anthropic auth is now supported and the keychain/OAuth expansion is
  planned. No new ADR — this is a defect fix.

## Notes
- This is the P0 of the series — the adapter is currently broken, not merely
  behind. Do it first; everything auth-related (Series 18 OAuth, keychain,
  new adapters) builds on the resolver.
- Do NOT add the OAuth/PKCE/device-code flows here. Each is a full adapter
  (callback server, RFC 8628 polling, token refresh) and belongs in Series 18.
- Do NOT introduce a provider catalog JSON or an `AuthProvider` trait registry
  here — those are Series 18 once the resolver surface is proven.
- Coordinate with the ponytail-audit adapter collapse (four ollama-style
  adapters): if that lands first, the resolver threads through the single
  collapsed adapter instead of four. Either order works.
