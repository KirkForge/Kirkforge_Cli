# Workorder 17.7 — Jobs↔Workflow Integration + Alert Persistence + Per-Job Policy

## Status: Done

## Problem
vix's scheduled jobs (`internal/daemon/jobs/spec.go` + `job_runner.go`) run
inline workflow defs, persist a synthetic alert thread on failure, materialize
declarative spec files into the job dir, and carry per-job permissions /
timeout / `skip_if_empty`. KirkForge's `src/jobs/` is a cron/once/restart
runner for `bash` commands only, with an unimplemented `Skill` stub, ephemeral
TUI notifications, UTC-only cron, and no per-job policy.

Concretely:
- `src/jobs/schedule.rs:51` `JobKind` has `Bash { command }` and a stub
  `Skill` ("not implemented" per `runner.rs`). A job cannot run a
  kf-workflow (`spec.go:88-92` lets vix run an inline `workflow.Def` or named
  `workflow_id`).
- On failure, `src/tui/commands/jobs.rs:659` (`notify_completed_scheduled_jobs`)
  pushes an ephemeral TUI notification only — nothing is persisted to session
  history. vix's `job_runner.go:348` `writeJobAlertThread` persists a synthetic
  thread explaining the failure, reviewable later.
- `src/jobs/store.rs` persists only `job.json` + run artifacts; a job needing a
  script must rely on it already existing on disk. vix's `spec.go:59-101`
  declaratively materializes `Files []SpecFile` into the job dir at save/load.
- `src/jobs/schedule.rs` has no per-job permission flags, no `skip_if_empty`,
  no per-job timeout. vix's `spec.go:47-51,95` has `Permissions` (`auto_write`/
  `auto_dirs`), `SkipIfEmpty`, `Timeout`.
- `src/jobs/schedule.rs:36` `ScheduleSpec` has `Cron`/`Once`/`Restart` but no
  timezone — `compute_next_run` evaluates in UTC. vix's `spec.go:37-42` `Trigger`
  supports `cron` with `tz` and one-shot `at`.

## Root cause
The job runner was built for "run this bash command on a cron"; vix's was
built as "this scheduled thing is a full agent pipeline with policy." The
`JobKind` enum and runner need a `Workflow` variant plus a few policy fields.

## Files to touch
- `src/jobs/schedule.rs` — add `JobKind::Workflow { template, vars }` (or a
  `workflow_id` ref); add `tz: Option<Tz>` to the `Cron` variant; add per-job
  policy fields to `ScheduledJob`: `auto_write`/`auto_dirs` (permissions),
  `skip_if_empty: bool`, `timeout: Option<Duration>`, `files: Vec<SpecFile>`.
- `src/jobs/runner.rs` — implement the `Workflow` variant by dispatching via
  `WorkflowTool` / `kf-workflow` (built in 17.6); honor `timeout` per job
  (wrap in `tokio::time::timeout`); honor `skip_if_empty` (skip the run if the
  last run produced no change); apply `auto_write`/`auto_dirs` to the bash path
  too. Remove the `Skill` stub or wire it — don't leave a dead "not
  implemented" branch (ponytail: dead code).
- `src/jobs/schedule.rs` `compute_next_run` — apply `tz` when present
  (`chrono_tz::Tz`) so non-UTC users can express human schedules; default UTC
  unchanged.
- `src/jobs/store.rs` — materialize `SpecFile { path, content, mode }` into
  the job dir on `save`, with a path-escape guard (mirror vix's
  `safeSpecFilePath`) so a `files` entry can't write outside the job dir.
- Alert persistence: on scheduled-job failure, write a synthetic transcript
  entry into the session index (reuse `src/session/session_index.rs`) so
  failures are reviewable later, not just notified once. The ephemeral TUI
  notification stays for immediate feedback; the persisted entry is the
  record.
- `src/tui/commands/jobs.rs` — surface the persisted alert entries in the Jobs
  tab alongside the live notifications.
- Tests: `src/jobs/` — a `Workflow` job runs the workflow and records the
  outcome; `timeout` aborts a long job; `skip_if_empty` skips a no-op run;
  `tz` schedules in a non-UTC zone correctly; `files` materializes a script
  and refuses a `../` escape; a failing job writes a persisted alert entry.

## Approach
1. **`Workflow` job kind first** (needs 17.6). A scheduled job that runs a
   full pipeline is the self-evolving promise; it's the headline item. Dispatch
   through the same `WorkflowTool` the TUI uses so there's one execution path.
2. **Alert persistence is the second win.** Reuse `session_index.rs` to append
   a synthetic entry on failure. Don't build a separate "alert store" — the
   session index is the record.
3. **Per-job policy is a handful of fields + checks.** `timeout` is a
   `tokio::time::timeout` wrap; `skip_if_empty` compares last-run output;
   `auto_write`/`auto_dirs` gate unattended writes. Small, orthogonal.
4. **`tz` is one `chrono_tz` field.** Default UTC; `tz` opts in. Don't build a
   timezone inference layer.
5. **`SpecFile` materialization with the escape guard.** vix's `safeSpecFilePath`
   is the model — confine to the job dir, reject `..`. Write on save, not run,
   so the files exist before the workflow starts.

## Gate
```
cargo fmt --check && cargo clippy --all-targets -- -D warnings &&
cargo test --locked --workspace --no-fail-fast &&
cargo test -p kf-code --lib jobs::
```

## Done condition
- A scheduled job can run a kf-workflow (inline template or named id), not
  just bash.
- A failed scheduled job writes a persisted, reviewable alert entry (via
  `session_index`); the Jobs tab shows it alongside live notifications.
- `timeout` aborts an overrunning job; `skip_if_empty` skips a no-op run;
  `auto_write`/`auto_dirs` gate unattended writes.
- `cron` with `tz` fires in the user's local time, not just UTC.
- `files` materializes scripts into the job dir on save and rejects path
  escapes.
- The `Skill` stub is either implemented or removed (no dead "not implemented").
- `docs/TECHNICAL.md` (Jobs section) documents the `Workflow` kind + policy
  fields.
- Depends on: 17.6 (the `Workflow` job kind dispatches through it).

## Notes
- "Watchers" (filesystem-event triggers) are NOT in scope — vix doesn't
  materially implement them either (only `cron` + `at` triggers; the
  "watchers" marketing maps to scheduled jobs + alert threads). Don't file an
  fs-watcher trigger here.
- Keep the job runner single-execution-path: `bash` and `workflow` both go
  through the runner, not separate engines.
- The persisted alert entry is the record; the ephemeral TUI notification is
  the nudge. Both, not one or the other.
- `skip_if_empty` needs a "did the last run change anything" signal — reuse
  the git-dirty / file-mtime check the verifier already has rather than
  inventing one.
