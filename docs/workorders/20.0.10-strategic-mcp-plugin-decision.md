# Workorder 20.0.10 — Strategic: MCP-First Plugin Architecture

## Problem

The cross-review identified a strategic error: the bespoke plugin system and
MCP coexist as peers, doubling the extension surface area and locking plugin
authors into a kf-code-only format. MCP is the industry standard (Claude Code,
Cursor, opencode, VSCode all MCP-native).

The bespoke system's real differentiators (hooks with veto, verifier
integration, trust tiers) could be delivered as a thin `kf-code.toml` overlay
on top of MCP servers.

This WO is **strategic, not mechanical** — it needs a design decision before
implementation.

## Current State

- **Bespoke plugin system**: minisign crypto, trust tiers, hook veto,
  verifier integration, topological load, hot-reload
- **MCP**: `tools/list` + `tools/call` on stdio + HTTP/SSE transports. No
  resources, prompts, sampling, or roots.
- **Overlap**: both provide tool registration, both have their own config,
  both are documented as the primary extension mechanism
- **Comment at `mcp_client/mod.rs:95-96`** falsely claims "reading resources"
  — not implemented
- **Shell hooks cannot see `tool_result` content** — admitted in `hooks.rs:46-63`
- **Post-turn hooks fire async after the turn commits** — observational only

## The Decision

**Option A: MCP-first.** Bespoke system becomes a thin config layer on top of
MCP servers. Hooks and verifier integration delivered as MCP middleware.
Trust tiers remain as a `kf-code.toml` overlay.

**Option B: Keep both, document clearly.** State when each is used. Make MCP
the primary for new tool integrations. Freeze bespoke plugin development.

**Option C: Status quo.** Both as peers, no decision.

## Recommendation

Option B is the pragmatic path — no breaking change, clear direction, allows
incremental migration. The bespoke system's real differentiators (veto hooks,
verifier bus, trust tiers) are valuable and don't map cleanly to MCP today.
