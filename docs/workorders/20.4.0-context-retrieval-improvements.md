# Workorder 20.4.0 — Context Index & Retrieval Improvements

## Source

Cross-review §4.4 + §1.2.

## Problem

The context index is the project's "compiler backend" — everything depends on
it. The tree-sitter index is real and good, but TF-IDF embeddings are toy,
doc comments aren't wired, the index rebuilds on every git commit, and LSP
isn't federated.

## Targets

### R1. Wire doc comments into `Symbol.doc` (HIGH)

- `embeddings.rs:82-100` — `DocLookup` slot + doc-tokenization plumbing exists
  but `Symbol` has no `doc` field; every caller passes `None`
- Cannot find `UserAccount` from query "customer profile" unless names overlap
- The plumbing is there, the field just isn't populated
- **Fix:** Add `doc: Option<String>` to `Symbol`. Extract doc comments during
  tree-sitter walks. Wire into `DocLookup` scoring. This is the highest-ROI
  retrieval improvement — it turns name-only TF-IDF into name+doc TF-IDF.

### R2. Federate LSP with context index (MEDIUM)

- Name-based call-graph resolution (`lib.rs:860`) conflates same-named methods
  across types
- Never asks a running rust-analyzer for ground-truth definitions/refs
- **Fix:** When LSP is connected, use `lsp_query.goto_definition` and
  `lsp_query.find_references` to validate and enrich the index's call graph.
  Fall back to name-based resolution when LSP is unavailable.

### R3. Incremental index rebuilds (MEDIUM)

- Index rebuilds on every git commit (HEAD-keyed invalidation)
- No incremental/mtime path — full rebuild on every `HEAD` change
- Slow on large repos
- **Fix:** Track file mtimes. On `HEAD` change, diff the changed files and
  re-index only those. Only rebuild the full index if the tree-sitter grammar
  changes.

### R4. `compaction_use_llm` is a misnomer (LOW)

- Flag flows to `deterministic_compaction_summary` (`microcompaction.rs:228`)
  which is heuristic keyword extraction, not LLM
- `compaction_use_llm` name implies LLM call
- **Fix:** Rename to `compaction_use_heuristic` or add a doc comment explaining
  the current behavior.

### R5. Stratum compression pipeline has zero registered transforms (HIGH)

- `CompressionPipeline` has a `Transform` trait + `register_content_transform`,
  but `register_content_transform` is NEVER called in production
  (only in `examples/library_usage.rs`)
- Every production site runs `CompressionPipeline::new()` empty
- The only thing it does is bloat offload (and that's broken — P0-4)
- `TECHNICAL.md:383-389` claims "content-type-specific transforms with offload
  storage and query-based relevance filtering" — overclaim
- **Fix:** Either register real transforms (markdown code block extraction,
  comment stripping, etc.) or remove the pipeline and update TECHNICAL.md to
  reflect reality: "minify + head/tail truncation with bloat offload."

### R6. Memory never auto-populates (LOW)

- No tool/hook writes facts to persistent memory
- The entire subsystem can silently no-op
- **Fix:** Add a `remember` tool + system-prompt instruction that writes facts
  to the memory store after significant turns. Add a `MemoryHook` that writes
  cost/latency data after each session.

### R7. Index coverage: add Python, Go, C/C++ tree-sitter grammars (LOW)

- Currently supports Rust, TS/TSX, Python (basic), Go (basic)
- Missing: Java, Kotlin, Swift, Ruby, PHP
- **Fix:** Add tree-sitter grammars for the top 10 languages by usage. Each
  grammar needs: symbol extraction, import resolution, and query patterns.

## Verification

- `Symbol.doc` populated for Rust source files in the index
- TF-IDF query "customer profile" returns `UserAccount`-like structs
- LSP query enriches index call graph
- Index rebuild is incremental (only changed files re-indexed)
- `compaction_use_llm` name reflects reality
- `CompressionPipeline::new()` either has real transforms or is removed
