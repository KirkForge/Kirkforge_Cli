# Workorder 22.13 — Multi-Turn Streaming Subagents

## Status: Planned

## Problem

The `task` tool has a multi-turn loop (`task.rs:458-483`) but it's broken: every
iteration re-sends the original user prompt instead of letting the subagent
continue from tool results. The subagent's conversation log already contains
tool results from the previous turn, but `run_turn_collecting(&prompt, …)`
appends the same prompt again — producing duplicate user messages and no
tool-result feedback cycle.

Additionally: background tasks have no completion notification (the parent
must poll `task_output`), no streaming of partial results, and the concurrency
semaphore cap (4) is hardcoded rather than configurable.

## Source

WO 20.1.0 items A1 + A2. The loop exists but is semantically single-turn.

## Root cause

`task.rs:458-483` — the `for turn_num in 0..max_turns` loop passes
`&prompt` (the original user prompt) to every `run_turn_collecting` call. On
turn 1+, this duplicates the user message in the conversation. The subagent
never sees a continuation prompt; it sees the same instruction again.

The real multi-turn contract should be: turn 0 sends the user prompt; turn N>0
sends a continuation (empty string or "continue") so the executor picks up the
tool results already in the conversation log and generates the next assistant
response.

## Targets

### 22.13-R1 — Fix multi-turn prompt loop (HIGH · est S · dep: —)

**Reality check:** `task.rs:458-483` loop passes `&prompt` on every iteration.
On turn 0 this is correct (initial user message). On turn 1+, the conversation
log already has the prompt + assistant response + tool results, so the next
call should pass a continuation message, not the same prompt.

**Fix:**
- `src/tools/task.rs:456-483` — change the loop so turn 0 sends `&prompt` and
  turns 1+ send a continuation string (e.g. `"continue"` or an empty string,
  depending on what `run_turn_collecting` does with empty input). The simplest
  correct approach: pass the prompt only on the first call; subsequent calls
  pass `"continue"` so the model processes the tool results already in the log.
- `src/tools/task.rs:458` — extract the prompt into a variable that changes per
  iteration: `let input = if turn_num == 0 { prompt.as_str() } else { "continue" };`
- Verify that `run_turn_collecting` handles a "continue" message correctly
  (i.e., it doesn't duplicate or reject it).

**Success criteria:**
- A `max_turns=3` task that calls a tool on turn 1 completes all 3 turns
  without duplicating the user prompt.
- The conversation log shows: [user prompt, assistant+tools, tool results,
  "continue", assistant+tools, tool results, "continue", final assistant].
- Existing single-turn (`max_turns=1`) behavior unchanged.
- `cargo test -p kf-code -- tools::task` green.

**Failure criteria:**
- Any test regression.
- Duplicate user messages in the conversation log on turn 2+.

### 22.13-R2 — Background task completion notification (MEDIUM · est M · dep: R1)

**Reality check:** `task.rs:199-208` — `tokio::spawn` runs the background task
and writes the result to `TaskHandle`. The parent has no way to know when the
task finishes except polling `task_output`. No event, no callback.

**Fix:**
- `src/tools/task.rs:24-27` — add a `completed: Option<tokio::sync::Notify>`
  (or `tokio::sync::watch`) field to `TaskHandle`. When the background task
  finishes writing the result, it sends a notification.
- `src/tools/task.rs:230-282` — `TaskOutput::run` returns the result if
  available, "still running" if not. Add an async `wait_for` method or extend
  `TaskOutput` to support awaiting completion (the TUI can subscribe to the
  notify/watch channel).
- `src/tools/task.rs:199-208` — after writing the result/error to
  `TaskHandle`, send the completion notification.

**Scope:** `src/tools/task.rs` (TaskHandle struct, TaskOutput tool, background
spawn).

**Success criteria:**
- `TaskHandle` has a completion signal (Notify or watch channel).
- Background task sends the signal when done.
- `TaskOutput` can report completion status; a future/awaitable API exists
  for TUI integration.
- Existing `task_output` polling still works (backward compatible).
- All existing tests green.

**Failure criteria:**
- `task_output` polling breaks.
- Completion signal never fires.

### 22.13-R3 — Configurable background concurrency limit (LOW · est S · dep: —)

**Reality check:** `task.rs:73-80` — `bg_semaphore` is hardcoded to 4 permits.
Config has no `max_concurrent_background_tasks` field.

**Fix:**
- `src/shared/config/mod.rs` — add `max_concurrent_background_tasks: usize`
  field to the relevant config section (default: 4).
- `src/tools/task.rs:73-80` — read the config value when constructing `Task`.
  The semaphore permit count should come from config, not be hardcoded.
- `src/tools/task.rs:191-198` — update the error message to include the
  configured limit.
- `src/shared/config/tools.rs` (or equivalent) — add the field with default.

**Scope:** `src/shared/config/mod.rs`, `src/shared/config/tools.rs`,
`src/tools/task.rs`.

**Success criteria:**
- `max_concurrent_background_tasks` is in config with default 4.
- `Task::new()` reads it from `SharedConfig` or accepts it via constructor.
- Error message includes the actual limit, not hardcoded "4".
- Existing tests green.

**Failure criteria:**
- Config field missing or default wrong.
- Semaphore still hardcoded to 4.
