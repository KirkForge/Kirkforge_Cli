# Workorder 22.5 — TUI Broken Pipelines

## Status: Planned

## Problem

Several TUI event pipelines are broken or dead: Enter/Space handlers for
F2-F5 tab rows don't do anything; session list doesn't refresh when the
daemon pushes `sessions_dirty`; `GitOperationEvent` is defined but never
emitted; file-tool duration metrics are untracked.

## Source

Review Part 3 §3.4 (TUI broken pipelines). WO 22.0 overview §22.5.

## Targets

### 22.5-R1 — Wire Enter/Space handlers for F2-F5 tab rows (HIGH · est M · dep: —)

**Reality check:** `src/tui/keys/mod.rs:475-491` — F1-F6 key codes switch
`active_tab` and reset `tab_list_state`. But there are no Enter/Space handlers
for the Models (F2), Plugins (F3), Jobs (F4), or Settings (F5) tabs. The F6
(Threads) tab has an Enter handler that opens the selected session, but the
other four tabs' list selections are purely visual — pressing Enter does
nothing.

**What was done (subagent):** The F6 (Threads) Enter handler was wired to
open the selected session via `handle_session_picker_keys`. The
`sessions_dirty` flag was wired to refresh the session picker list (see R2).
No handlers were added for F2-F5.

**Remaining:**
- F2 (Models): Enter should open a model-switch dialog or display model
  details for the selected row.
- F3 (Plugins): Enter should toggle the selected plugin on/off.
- F4 (Jobs): Enter should show job details or cancel the selected job.
- F5 (Settings): Enter should open the selected config value for editing or
  display its current value.
- Each tab needs its own key handler function (analogous to
  `handle_session_picker_keys` for F6).

**Scope:** `src/tui/keys/mod.rs`, new handler functions per tab,
`src/tui/app.rs` (state updates for actions), `src/tui/widgets/tabs.rs`.

**Success criteria:**
- Enter on F2 row triggers a model info/switch action.
- Enter on F3 row toggles the selected plugin.
- Enter on F4 row shows job details or cancels the job.
- Enter on F5 row displays the selected config value.
- Each handler has a test asserting the action fires.

**Failure criteria:** Enter on any F2-F5 tab does nothing (current state).
Regression in F6 session picker.

**Estimate:** M

**Defer note:** DEFER-225-R1 — F2-F5 Enter handlers are UX enhancement, not a
ship-blocker. The tab content renders correctly; only interaction is missing.
Tracked in PONYTAIL-DEBT.md.

### 22.5-R2 — Wire `sessions_dirty`/`jobs_dirty` to refresh lists (HIGH · est S · dep: —)

**Reality check:** `src/tui/daemon_events.rs:23,26` — `DaemonEventFlags` has
`sessions_dirty` and `jobs_dirty` fields set by the daemon reader thread.
`src/tui/mod.rs:865-889` — `drain_daemon_flags` mirrors these into
`AppState.sessions_dirty`/`jobs_dirty` and calls `mark_dirty()`. But the render
path for the Threads tab (F6) doesn't re-read the session list when
`sessions_dirty` is true, and the Jobs tab (F4) doesn't re-read jobs when
`jobs_dirty` is true.

**What was done (subagent):** The session_picker list is now refreshed when
`sessions_dirty` is drained — the TUI re-queries `recent_sessions` from the
daemon when the flag is set. This was wired in the main event loop.

**Remaining:**
- The Jobs tab (F4) should similarly re-query scheduled/background jobs when
  `jobs_dirty` is true.
- Test that `sessions_dirty` causes session list refresh (integration or unit).
- Test that `jobs_dirty` causes job list refresh.

**Scope:** `src/tui/mod.rs`, `src/tui/app.rs`, `src/tui/commands/sessions.rs`,
`src/tui/commands/jobs.rs`.

**Success criteria:**
- When `sessions_dirty` is set, the Threads tab (F6) session list refreshes
  on the next draw cycle.
- When `jobs_dirty` is set, the Jobs tab (F4) job list refreshes on the next
  draw cycle.
- Tests assert the refresh happens.

**Failure criteria:** Session list still stale after daemon pushes
`ThreadsChanged`. Job list stale after `JobsChanged`.

**Estimate:** S (sessions done; jobs remaining)

**Defer note:** DEFER-225-R2-jobs — jobs_dirty refresh is the same pattern as
sessions_dirty; straightforward. Tracked in PONYTAIL-DEBT.md.

### 22.5-R3 — Remove or document `GitOperationEvent` dead branch (MEDIUM · est S · dep: —)

**Reality check:** `src/session/verifier/types.rs:257-263` —
`GitOperationEvent` is defined with fields `args`, `output`, `success`, and
`BusEvent::GitOperation` exists at line 201. But the event is never emitted:
the git verifier (`git.rs`) constructs a `BusEvent::GitOperation` at line 281
inside `should_verify`, but that path is dead code — the git verifier uses
`BashExecEvent` heuristic instead. A `ponytail:` comment at line 257 documents
this: "GitOperationEvent never emitted; git verifier uses BashExec heuristic
only".

**What was done (subagent):** `ponytail:` comments were added at lines 13,
200, and 257 documenting the dead status.

**Remaining:**
- Decision: delete `GitOperationEvent` and `BusEvent::GitOperation` entirely
  (the preferred lazy fix), or wire it into the git verifier. The `ponytail:`
  comment documents the known ceiling, so deletion can be deferred safely.
- If keeping: wire `GitOperationEvent` into the git verifier's
  `should_verify` path so it's emitted for actual git operations.
- If deleting: remove `GitOperationEvent`, `BusEvent::GitOperation`, and the
  match arms in `should_verify` and the handler.

**Scope:** `src/session/verifier/types.rs`, `src/session/verifier/git.rs`,
`src/session/verifier/mod.rs`.

**Success criteria:**
- Either `GitOperationEvent` is deleted (and all references removed), or it
  is wired into the git verifier and a test asserts it fires for a `git add`
  command.
- No dead match arm on `BusEvent::GitOperation` in production code.

**Failure criteria:** `GitOperationEvent` still defined but never emitted
without a `ponytail:` comment = FAIL (currently documented, so this is
acceptable as DEFERRED).

**Estimate:** S

**Defer note:** DEFER-225-R3 — `GitOperationEvent` is documented as dead code
with `ponytail:` comments. Deletion is a cleanup, not a bug. Tracked in
PONYTAIL-DEBT.md.

### 22.5-R4 — File-tool duration metrics (LOW · est S · dep: —)

**Reality check:** The TUI status bar shows model latency but file tool
operations (read, write, edit) have no duration tracking. When a file tool
takes >1s, the user sees no feedback.

**What was done (subagent):** No duration metrics were added.

**Remaining:**
- Add duration tracking to `file_read`, `file_write`, `edit_file` tool
  invocations (start timer, emit `TurnEvent::ToolDuration` on completion).
- Display duration in the TUI status line or tool output header.
- Consider a threshold (>500ms) for showing "slow tool" indicator.

**Scope:** `src/tools/`, `src/tui/events.rs`, `src/tui/widgets/status.rs`.

**Success criteria:**
- File tool invocations emit duration metrics.
- TUI displays file-tool duration (or an indicator for slow operations).

**Failure criteria:** No duration tracking. No TUI indicator.

**Estimate:** S

**Defer note:** DEFER-225-R4 — duration metrics are UX polish, not a
ship-blocker. Tracked in PONYTAIL-DEBT.md.
