# Workorder 23.4 — Wire LSP into Context Index (Federation)

## Problem

The context index (`kf-context-index`) resolves call-graph edges by name matching — `CallEdge { caller, callee }` where both are string-based symbol names. The LSP (`kf-lsp`) provides ground-truth definitions, references, and type information that the name-based approach cannot match. When both exist in the same process, not federating them means the index produces false positives (same-name symbols conflated) and false negatives (cross-file calls missed because the name didn't match).

The `lsp_query` tool (`src/tools/lsp_query.rs`) already has a production LSP pool with 7 operations. The index (`crates/kf-context-index/src/lib.rs`) does not call it.

## Source

Review #23 (Phase 3). `crates/kf-context-index/src/lib.rs:180-229` — `index_file` parses with tree-sitter only. `src/tools/lsp_query.rs` — 7 LSP operations available. Review §4.4: "LSP not federated with index (name-based call-graph resolution)."

## Targets

### 23.4-R1 — Add LSP definition grounding to context retrieval (est L)

**Reality check:** `kf-context-index/src/lib.rs:192-229` parses each file with tree-sitter and extracts symbols, imports, and call edges. The call edges are name-based — `caller: "foo", callee: "bar"` — with no resolution to actual definitions. When `lsp_query` can provide `go_to_definition`, the index can ground those name references to file:line locations.

**Plan:**
- Add `federate_lsp` option to `ContextIndex::retrieve_hybrid` (or a new `retrieve_hybrid_with_lsp` method)
- When LSP is available, call `go_to_definition` for top-k symbols returned by TF-IDF retrieval
- If LSP returns a definition, boost that symbol's relevance score and add the definition's doc comment to the result
- If LSP is unavailable (no configured server for the language), fall back to current name-based behavior silently
- Gate behind `cfg(feature = "lsp-federation")` in `kf-context-index`

**Success criteria:**
- With LSP configured: retrieval results include definition-grounded symbols with higher relevance
- Without LSP: retrieval behavior is identical to current (no regression)
- LSP timeout (10s per query) does not block retrieval — fall back gracefully
- All existing context-index tests pass unchanged

**Failure criteria:** LSP federation blocks retrieval on timeout. LSP federation produces wrong results. Non-LSP retrieval regresses.

**Estimate:** L

### 23.4-R2 — Add LSP call-edge resolution (est M)

**Reality check:** `CallEdge { caller, callee }` in the index is name-based. The LSP's `find_references` operation can resolve which actual definition a call site refers to, disambiguating same-name symbols across files.

**Plan:**
- After tree-sitter produces call edges, optionally resolve each `callee` name via LSP `go_to_definition`
- If resolution succeeds, annotate the `CallEdge` with the resolved definition's file:line
- Store resolved edges separately so retrieval can prefer them over unresolved ones
- This is a build-time enhancement (indexing step), not a query-time enhancement

**Success criteria:**
- Call edges for resolved symbols include `definition_file` and `definition_line`
- Unresolved symbols fall back to name-only (no regression)
- Index build time increase is <2x for a typical Rust project

**Failure criteria:** Index build time >3x. Resolution produces incorrect file:line. Build fails when LSP is unavailable.

**Estimate:** M

**Defer note:** R2 can be deferred until R1 is proven stable. Name-based resolution works today; LSP grounding is a quality improvement, not a correctness fix.
