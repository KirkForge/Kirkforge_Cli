# Workorder 23.7 — Real Concurrency Limit for `task(background=true)` (Semaphore)

## Problem

`task(background=true)` spawns a new `tokio::spawn` for each background task with no concurrency limit beyond a hardcoded `Semaphore::new(4)` at `src/tools/task.rs:80`. The semaphore exists but is not configurable, and there's no backpressure mechanism — if 20 `task(background=true)` calls arrive, 16 queue behind the semaphore, but they all allocate executor state (conversation, adapter, toolset) before being throttled.

The review calls this out: "20 `task(background=true)` = 20 concurrent executors, no semaphore" (§4.1). The semaphore at line 80 is a start, but it's hardcoded, unconfigured, and the acquire happens after the executor is already constructed.

## Source

Review #28 (Phase 3). `src/tools/task.rs:73-89` — hardcoded `Semaphore::new(4)`. Review §4.1: "no concurrency limit (20 `task(background=true)` = 20 concurrent executors, no semaphore)."

## Scope

1. `src/tools/task.rs` — make semaphore size configurable, add backpressure
2. `src/shared/config/` — add `max_background_tasks` config field
3. `src/session/config/mod.rs` — parse and validate the config field
4. `src/tools/task.rs` — return a clear error when the semaphore is full instead of silently queuing
5. `docs/TECHNICAL.md` — document the new config field

## Targets

### 23.7-R1 — Make `bg_semaphore` configurable via `Config` (est S)

**Reality check:** `task.rs:80` creates `Arc::new(tokio::sync::Semaphore::new(4))` — hardcoded to 4. The `Task::with_manager` constructor at line 84 also hardcodes 4. Neither reads from `Config`.

**Plan:**
- Add `max_background_tasks: usize` to `Config` (under `[tools]` or a new `[executor]` section) with default `4`
- Thread the config value through `Task::new()` and `Task::with_manager()` so the semaphore size comes from config
- Validate: clamp to `1..=64` (1 minimum = serial, 64 maximum = generous)
- Add `KF_CODE_MAX_BACKGROUND_TASKS` env override (consistent with existing `KF_CODE_MAX_CONCURRENT_SCHEDULED_JOBS`)

**Success criteria:**
- `max_background_tasks` defaults to 4 (no behavioral change)
- Setting it to 1 serializes background tasks
- Setting it to 0 is invalid (clamped to 1)
- Env override `KF_CODE_MAX_BACKGROUND_TASKS` works
- All existing task tests pass

**Failure criteria:** Default behavior changes. Config value ignored. Env override doesn't work.

**Estimate:** S

### 23.7-R2 — Add backpressure: return error when semaphore is full (est S)

**Reality check:** Currently `task(background=true)` acquires the semaphore and queues. If 20 tasks arrive and the semaphore is 4, 16 are queued with no feedback to the model. The model sees a "task started" response for all 20, then 16 sit waiting.

**Plan:**
- Add `task_concurrency_mode: "queue" | "reject"` to `Config`, defaulting to `"queue"` (current behavior)
- In `"reject"` mode: `try_acquire` on the semaphore; if full, return `ToolOutcome::Failure` with a clear message: "Background task concurrency limit reached (4 running). Use `task_output` to check running tasks or increase `max_background_tasks`."
- In `"queue"` mode: current behavior (`acquire` waits)
- Document both modes in TECHNICAL.md

**Success criteria:**
- `"queue"` mode: current behavior, no regression
- `"reject"` mode: returns a clear error when semaphore is full
- Model sees a useful error message it can act on
- No executor state leaked on rejection (conversation/adapter not constructed)

**Failure criteria:** `"queue"` mode regresses. `"reject"` mode panics. Executor state leaked on rejection.

**Estimate:** S

### 23.7-R3 — Construct executor state after semaphore acquire (est M)

**Reality check:** `task.rs` constructs the full executor (conversation log, adapter, toolset) before acquiring the semaphore. If the semaphore is contended, 16 executors' worth of memory and init work is done before any of them runs.

**Plan:**
- Move executor construction to after semaphore acquisition
- Acquire the semaphore first, then construct the executor
- This requires restructuring `Task::run()` so the `Arc<Semaphore>` is acquired before the heavy `Executor::new()` call
- On semaphore acquisition failure (in `"reject"` mode), no executor is constructed

**Success criteria:**
- No executor state is constructed before the semaphore is acquired
- Memory profile: only `max_background_tasks` executors exist at any time
- All existing task tests pass

**Failure criteria:** Executor constructed before semaphore acquire. Test regression.

**Estimate:** M

**Defer note:** R3 can be deferred — the current behavior (construct then queue) works correctly, it just wastes memory under high concurrency. R1+R2 give the immediate wins (configurable limit + clear feedback).
