# Workorder 24.3 — Make Missing Sandbox Config a Refusal in Production Mode

## Problem

The review (#33) requires: missing sandbox configuration should be a refusal in production mode, not a warning. Currently, `refuse_if_production_unsandboxed` (`src/session/access/mod.rs:584`) already refuses in release builds (`cfg!(not(debug_assertions))`) **unless** the operator passes `--i-accept-unsandboxed` (`shared/mod.rs:317-320`). The review asks for the escape hatch to be removed in release builds, making the refusal unconditional.

The current flow (`executor/mod.rs:162-168`):
- `--harden` → `refuse_if_unsandboxed` (always refuses)
- Release + no `--i-accept-unsandboxed` → `refuse_if_production_unsandboxed` (refuses)
- Release + `--i-accept-unsandboxed` → `warn_if_unsandboxed` (allows, with warning)
- Debug → `warn_if_unsandboxed` (allows, with warning)

The review's position: the escape hatch undermines the security posture in production. If you're running a release build, you should have a sandbox configured — period. The `--i-accept-unsandboxed` flag should be debug-only.

## Root cause

`shared/mod.rs:317-320` (`accept_unsandboxed: bool`) and `executor/mod.rs:164` allow release builds to bypass sandbox refusal via CLI flag. This creates an easy opt-out that defeats the security boundary.

## Scope

1. `src/shared/mod.rs` — remove or gate `accept_unsandboxed` to debug builds
2. `src/session/executor/mod.rs` — remove the `accept_unsandboxed` escape hatch from the release path
3. `src/session/access/mod.rs` — remove `refuse_if_production_unsandboxed`'s acceptance of the flag (or make the function always refuse in release)
4. `src/session/config/mod.rs` — remove `accept_unsandboxed` from config parsing in release builds
5. `src/main/run_session.rs` — update CLI arg handling
6. `src/cli.rs` — update help text

## Plan

### 24.3-R1 — Remove `--i-accept-unsandboxed` from release builds

- Gate `accept_unsandboxed` behind `#[cfg(debug_assertions)]` so the flag is only available in debug builds.
- In release builds, `refuse_if_production_unsandboxed` always refuses (no escape hatch).
- In debug builds, `--i-accept-unsandboxed` still works (for local development without sandbox).
- Update `executor/mod.rs:162-168`: remove the `accept_unsandboxed` check from the release branch.
- Update `cli.rs:28` exit codes doc — `4` (permission/sandbox denied) is now unconditional in release.
- Update tests: existing tests that use `accept_unsandboxed` should be debug-only (or adjust them to provide a sandbox).

**Success criteria:**
- Release build refuses to start without sandbox config, regardless of `--i-accept-unsandboxed`.
- Debug build still allows `--i-accept-unsandboxed`.
- All existing tests pass.
- `cli.rs` help text reflects the change.

**Failure criteria:** Release build allows unsandboxed operation via any flag. Tests regress.

**Estimate:** M

**Defer note:** Depends on WO 22.1 (landlock) being confirmed working. Refusing unsandboxed operation is only reasonable if sandbox confinement actually works on Linux. If landlock is still broken, this refusal locks users out entirely.

### 24.3-R2 — Add default sandbox config in release mode

- When no `sandbox_dir` or `allowed_write_dirs` is configured, instead of refusing with just an error message, offer a concrete remediation: suggest `sandbox_dir = "."` (current directory) as the minimal safe default.
- Update `refuse_if_production_unsandboxed` error message to include the suggestion.
- This reduces the UX friction of R1 while maintaining the security gate.

**Success criteria:** Error message includes actionable remediation.

**Failure criteria:** Error message is unhelpful.

**Estimate:** S (included in R1)

**Defer note:** none.
