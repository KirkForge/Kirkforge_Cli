# Workorder 25.0 — WO 25 Series Overview: Test Infrastructure + Deferred Work Closure

## Status: Planned

## Problem

Two problem axes, both blocking honest verification:

**Test infrastructure (25.1-25.8).** The test suite has grown to ~3000+
tests in `kf-code` alone, plus tests across 5 workspace crates
(`kf-budget-core`, `kf-testdoctor`, etc.). `cargo test --workspace` takes
10+ minutes locally and frequently times out in CI. Known pre-existing
test failures (see `state.md` "Known pre-existing test failures") add
noise. The AGENTS.md §4 gate requires the full test suite before every
commit — this blocks development velocity and makes agents reluctant to
run the gate. CI is also affected: the `test` job is the longest single
step in the pipeline.

**Deferred work closure (25.9-25.18).** Three verification agents audited
the codebase against `state.md` and the prior reviews. They confirmed
multiple deferred items remain open (some with state.md overclaims), and
uncovered new issues: dead code surviving behind `#[allow(dead_code)]`,
stale binary/path references in user-facing config, an MCP protocol gap,
a Bedrock/Vertex persona-routing bug the prior review falsely claimed
fixed, and a `cached_tokens` fork-reset inconsistency. WO 25 has not
begun coding, so the deferred + newly-uncovered work is folded into this
series rather than spawning a new one.

## Source

Developer frustration (10+ min test wall). CI job timing data. `state.md`
known pre-existing test failures + "Deferred items" sections. Three-agent
verification audit (post-WO-22). `kf-testdoctor` crate (WO 12.4) exists
as a diagnostic tool but has not been optimized for speed.

## 25.0-R3: Test integrity audit — doom-loop "hard halt" is unimplemented

**Priority:** HIGH — the test suite is lying about what it verifies.

### Bug description

The CHANGELOG claims WO 23.8-R2 shipped "Hard halt when circuit breaker fires while already in plan mode — turn stops with clear error message." This is false. The halt behavior was never implemented.

**Evidence:**

- `observe_tool_outcome` call sites (`src/session/executor/turn.rs:1035`, `:1139`, `src/session/executor/mod.rs:741`, `src/session/executor/cost_tracking.rs:86`) never read `self.plan_mode` in the doom-loop path.
- The `DoomLoopAction::AutoPlan` handler calls `self.set_plan_mode(true)` unconditionally — a no-op if already in plan mode, not a halt.
- The action is determined purely from static config (`cfg.tools.doom_loop_action`), never from runtime state.

**The test that hides it:**

`doom_loop_circuit_breaker_halts_in_plan_mode` (`src/session/executor/tests/loop_.rs:880`) does NOT test halt-in-plan-mode behavior. Its own body asserts "default config action is AutoPlan regardless of plan_mode state" with an inline comment: "The wrapper no longer sets plan_mode... (plan_mode is not changed by observe_tool_outcome in R3)."

The test name asserts a safety guarantee (no infinite loop between doom-detection and plan-mode re-entry). The test body and its own comments then disprove that guarantee.

**Actual risk:** With `doom_loop_action = auto_plan` while already in plan mode, read-only tools can still fail repeatedly. The circuit breaker fires every `doom_loop_max_hits` cumulative hits, injects a hint message, and no-ops `set_plan_mode(true)` again — burning turns/tokens without ever halting.

### Scope

- Rename `doom_loop_circuit_breaker_halts_in_plan_mode` to reflect what it actually verifies, OR restore the real halt-in-plan-mode check if that was the intended behavior.
- Correct or remove the stale R2 changelog claim.
- Add a test that actually verifies halt-in-plan-mode if that behavior is wanted.

### Success criteria

- No test name asserts a guarantee that the test body disproves.
- CHANGELOG and workorder status accurately reflect shipped behavior.

### Status: Done

Test renamed to `doom_loop_circuit_breaker_default_action_is_auto_plan`. CHANGELOG corrected with honest description. No production code changed; no halt-in-plan-mode behavior added (that is a separate feature, not this task's scope).

### Failure criteria

- Test renamed but no actual halt behavior added (the infinite-loop risk remains).
- Changelog corrected but the misleading test name kept.
