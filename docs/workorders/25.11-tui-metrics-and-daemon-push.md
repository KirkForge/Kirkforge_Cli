# Workorder 25.11 — TUI Metrics & Daemon Push Gaps

## Status: Planned

## Priority: P1 — telemetry correctness + daemon staleness

## Problem

Two verified-open telemetry/UX gaps. (T4) File-tool metrics hardcode
`duration_ms: 0` even though the calling function receives real timing —
metrics systematically underreport file-tool latency, hiding slow tool
calls. (T1) Daemon push marks `sessions_dirty` but never triggers a
sessions-list re-fetch — daemon clients (other TUIs, headless viewers)
display stale session state until the next full poll.

## Source

- T4: `src/session/executor/turn.rs:1066` — file-tool branch drops the
  `duration_ms` param. Non-file path at `:1169` correctly passes it.
  `record_tool_result` receives the real value as a parameter.
- T1: `src/tui/mod.rs:888-891` — sets `sessions_dirty = true` but no
  `refresh_jobs_output`-equivalent exists for sessions.

## Requirements

### R1 (T4) — Pass `duration_ms` through file-tool branch

- The file-tool match arm at `turn.rs:1066` calls `record_tool_result`
  with `duration_ms: 0` while the surrounding function holds the real
  elapsed time. Pass the real value.
- Single-line fix in the match arm.
- Add a unit test asserting that a file-tool call with non-zero elapsed
  time produces a metric event with `duration_ms > 0`.

### R2 (T1) — Sessions-list refresh on dirty

- Add a sessions-list refresh equivalent to `refresh_jobs_output`,
  triggered by `sessions_dirty`.
- Either piggyback on the existing daemon poll loop (mark dirty → next
  poll observes and refreshes) or add a dedicated refresh path.
- A session-state change (new session, fork, close) must propagate to a
  connected daemon client within one poll interval.

## Success criteria

- File-tool metric events carry non-zero `duration_ms` for tool calls
  that took >0 wall time (verified by test).
- Daemon clients observe session-list changes within one poll interval
  of the change.
- No new tight poll loop introduced (refresh is dirty-triggered, not
  busy-polled).
- Existing tests pass; new tests cover both R1 and R2.

## Failure criteria

- R1 fix causes metrics to report fabricated durations on tools that
  haven't completed.
- R2 fix busy-polls (adds a tight refresh loop) instead of refreshing
  on dirty.
- R2 refresh path duplicates the existing jobs refresh logic instead
  of sharing it.

## Estimate

S-M (R1 ~1h; R2 ~4-6h).
