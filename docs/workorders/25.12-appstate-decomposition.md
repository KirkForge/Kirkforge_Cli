# Workorder 25.12 — AppState Decomposition + `cached_tokens` Fork-Reset Bug

## Status: Done (R1 deferred)

## Priority: P2 — large refactor; R2 (the bug) is shippable standalone first

## Problem

AppState has 68 pub fields (`src/tui/app.rs:214-545`) grouped implicitly
by concern. The fork path uses a `mem::take` dance
(`src/tui/mod.rs:990-1008`) that is **inconsistent**:
`tokens_sent` / `received` / `cumulative_cost` / `turn_cost` reset on
fork, but `cached_tokens` does NOT — despite being documented as
"Cumulative cache-read tokens across the session". Forked sessions
inherit the parent's cache-read stats, producing misleading cost reports
in the fork.

## Source

- `src/tui/app.rs:214-545` — 68 pub fields.
- `src/tui/mod.rs:990-1008` — `mem::take` fork-reset block.

## Requirements

### R1 — Decompose AppState into sub-structs

- Group the 68 fields by concern into sub-structs:
  `ConversationState`, `RenderingState`, `ApprovalState`, `BudgetState`
  (incl. ALL token/cost fields), `GenerationState`, `SearchState`,
  `TabsState`, `SessionState`.
- AppState becomes a struct of these (target: ≤12 top-level fields).
- Preserve the public API where TUI consumers depend on it — add
  accessors or `Deref` shims if a call site breaks.

### R2 — Fix `cached_tokens` fork-reset

- Include `cached_tokens` in the budget-reset block at `mod.rs:990-1008`
  so forked sessions start at 0 cache reads — consistent with the other
  cumulative fields.
- If cumulative-across-fork is actually intended (unlikely given the doc
  string), re-document the field explicitly with the reason.

### R3 — Fork-reset unit test

- Add a test that asserts ALL documented "per-session" budget fields
  reset to their initial values on fork. The test must fail if any new
  budget field is added to BudgetState without being added to the reset
  block (compile-time or runtime pin).

## Success criteria

- AppState has ≤12 top-level fields, each a sub-struct.
- `cached_tokens` resets on fork consistently with the other cumulative
  budget fields (or is re-documented as fork-inheriting with a clear
  reason).
- Fork-reset unit test covers every field that should reset.
- TUI behavior unchanged (manual smoke: open session, fork, observe
  state — token counters, cost, active tab, scroll position).
- `cargo test --workspace` green.

## Failure criteria

- Decomposition breaks TUI rendering (visual regression).
- R2 "fix" resets `cached_tokens` when it should legitimately persist
  (or vice versa) without a test pinning the intent.
- `mem::take` dance preserved unchanged (refactor skipped).
- R1 swaps the field-blob for an opaque `HashMap<String, ...>` (hides
  the structure instead of clarifying it).

## Estimate

L (~1-2 days; high-touch refactor across many TUI call sites).

## Defer note

None — but **recommendation: ship R2 + R3 first as a scoped commit**
(fix the bug + pin it with a test), then attempt R1 as a separate PR.
R1's refactor risk is high; R2 is a one-line fix that should not wait.
