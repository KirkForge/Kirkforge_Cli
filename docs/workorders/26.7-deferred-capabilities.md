# Workorder 26.7 — Deferred Capabilities (bash streaming, MCP sampling, memory widget, computer_use)

## Status: R1+R2+R3 done (R4 re-deferred with disclosure)

## Priority: P2

## Problem

Four capability items were deferred from WOs 25.x with concrete reasons.
Each is independently shippable. This WO prevents them from rotting by
giving each a tracking home with explicit requirements and gates.

## Source

state.md "Deferred items" — 25.18-R1, 25.15-R2/R3, 25.18-R3, 25.18-R2.

## Requirements

### R1 (25.18-R1) — Bash streaming UX

- Add `TurnEvent::BashPartialOutput` variant to the event enum.
- Forward PTY output through `event_tx` as partial-output events during
  command execution.
- Render a streaming indicator (spinner or incremental text) in the TUI
  tool-result card while the command runs.
- Non-PTY command path unchanged; this only affects the PTY output path.

### R2 (25.15-R2/R3) — MCP sampling/createMessage

- Add approval-gated handler for `sampling/createMessage` MCP requests.
- Headless mode policy: auto-approve or auto-deny based on config flag
  (default: deny, matching current tool approval behavior).
- ADR documenting the sampling trust model and approval flow.
- Gate: handler must not bypass the existing approval bus — wire through
  the same `ToolApproval` mechanism.

### R3 (25.18-R3) — TUI memory visibility widget

- Add a memory indicator to the TUI status bar showing memory entry count
  and last-updated turn number.
- Config flag (`memory.show_in_status` or equivalent) to toggle display,
  defaulting to ON.
- Gate: indicator must update in real-time as memory entries are added
  during a session.

### R4 (25.18-R2) — Anthropic computer_use beta

- Opt-in beta path routed to Anthropic's computer_use API, gated behind
  a feature flag (`computer_use`).
- Coordinate-vision model integration for screen understanding.
- Feature flag defaults OFF — computer_use is a meaningful capability and
  cost surface; users opt in explicitly.
- Gate: no computer_use API calls made when flag is OFF.

## Success criteria

- R1: bash output visibly streams in the TUI during long-running commands
  (manual smoke test).
- R2: sampling/createMessage requests route through the approval bus;
  headless policy is configurable.
- R3: memory widget renders in status bar; config flag toggles visibility.
- R4: computer_use beta works end-to-end behind a feature flag that
  defaults OFF (or is re-deferred with reason).

## Failure criteria

- Any R-item silently stubbed to mark the WO "done" (AGENTS.md §11 violation).
- R2 bypasses the approval bus — sampling requests must go through the
  same trust model as tool calls.
- R4 ships computer_use without the feature flag — security/cost surface
  ungated.

## Estimate

L (each R-item is M; total ~1-2 weeks if all shipped).

## Defer note

Each R-item is independently deferrable. If an R-item is shipped smaller
than specified, it MUST carry an explicit deferral entry in state.md
naming the remaining work and tracking location. No silent deferral.
