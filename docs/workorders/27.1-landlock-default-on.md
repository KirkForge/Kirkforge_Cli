# Workorder 27.1 — Landlock Default-On + Actually Applied (C1, CRITICAL)

## Status: Planned

## Problem

The deep review's headline finding (C1): the landlock filesystem sandbox is **never applied in production builds.** `src/session/bash_runner/landlock.rs:178` gates `apply_landlock` (and all path-rule helpers at lines 92-128) behind `#[cfg(test)]`. `setup_rlimits` (`src/session/bash_runner/mod.rs:130`) takes `_landlock_paths: Option<&landlock::LandlockPaths>` — the leading underscore confirms it's unused; the body only calls `setrlimit` + optional `unshare(CLONE_NEWNET)`. The `landlock` Cargo feature is off by default (`Cargo.toml:233` `default = ["stratum", "budget"]`).

Net effect: a model-driven `bash` command can read/write anything the `kf-code` user can, subject only to the `safety.rs` substring deny-list (H3 — bypassable via `$()` substitution, variable indirection, base64 payloads). The 4th-ed review's "landlock ABI correct" claim was true-but-irrelevant. This is the single biggest safety gap vs codex-cli (which ships landlock default-on).

## Reality-check (verified 2026-08-11)

- `apply_landlock` exists ONLY in test builds. `rg "apply_landlock" src/` returns matches only inside `landlock.rs` (definition + test module).
- The `landlock` feature currently gates only `cfg!(all(unix, feature="landlock"))` type signatures — enabling it changes nothing about whether confinement runs.
- The function works when called: tests at `landlock.rs:307-359` prove the confinement logic.

## Scope

### R1 — Move `apply_landlock` (+ helpers) out of `#[cfg(test)]`
- `src/session/bash_runner/landlock.rs:178` — remove `#[cfg(test)]` from `apply_landlock`, `landlock_add_path_rule`, `landlock_restrict`, `add_path`, `landlock_available`, `resolve_paths`, `LandlockPaths`.
- Gate the module itself behind `cfg(target_os = "linux")` (landlock is Linux-only; on macOS/Windows the module compiles to a no-op stub).

### R2 — Wire `apply_landlock` into the production pre-exec path
- `src/session/bash_runner/mod.rs:130` `setup_rlimits` — stop discarding `_landlock_paths`. Call `apply_landlock(&paths)` inside the `pre_exec` closure (where rlimits + `unshare` already run). The syscall must happen in the child process after `fork`/before `exec`.
- The two non-test overloads at `mod.rs:173`/`:210` currently take `Option<&()>` — give them real `Option<&LandlockPaths>` signatures (or a typed wrapper).

### R3 — Default-on for Linux; fail-closed on supported kernels
- `Cargo.toml:233` — change `default` to `["stratum", "budget", "landlock"]` **gated by `cfg(target_os = "linux")`** (Cargo doesn't support per-target defaults directly; use `[target.'cfg(target_os="linux")'.dependencies]` + a build-script-set cfg, OR keep the feature and enable it in `scripts/install.sh` + the release workflow for Linux targets).
- Fail-closed: if `landlock_restrict_self` returns an error on a kernel that *should* support it (Linux ≥5.13, capability check passes), the bash spawn must FAIL with a clear error, not silently fall back to unconfined. The workorder `22.1-critical-landlock.md` already specifies this.

### R4 — Allow-list design
- `resolve_paths` at `landlock.rs` already computes the paths to allow (workdir + config dirs + the binary + its deps). Verify it covers: `sandbox_dir`/`allowed_write_dirs`, the conversation-log dir, the undo tmp dir, the plugin dirs, `~/.local/share/kf-code/` (read), `/tmp` (the offload store).
- ADR: document the allow-list contract + the operator override (`KF_CODE_LANDLOCK_ALLOW` env var for extra paths).

### R5 — ADR + doc-sync
- Update ADR-0022 to reflect "default-on, fail-closed" (was "feature-gated, opt-in").
- `docs/TECHNICAL.md` security section: change "landlock (feature-gated, opt-in)" → "landlock (default-on Linux, fail-closed)".
- `state.md`: close the C1 pending item.
- `kf-code-review.md` 6th edition: bump the Verification/budget/sandbox score back toward 8.0.

## Success criteria

1. `cargo build --release` on Linux produces a binary that, on a `bash` tool call, applies landlock (verifiable: a model-driven `cat ~/.aws/credentials` fails with EACCES; `ls` of the workdir succeeds).
2. `cargo test --lib -p kf-code bash_runner::landlock` — the existing landlock tests still pass, now against the non-test-gated function.
3. `kf-code run` on a kernel <5.13 (or without caps) logs a clear warning and falls back to unconfined (not fail-closed there — fail-closed only on supported-but-rejected).
4. The `--i-accept-unsandboxed` flag (already debug-gated per WO 24.3) remains the only documented escape hatch.
5. ADR + TECHNICAL.md updated in the same commit.

## Failure criteria (anti-patterns to avoid)

- Removing `#[cfg(test)]` but forgetting to actually CALL `apply_landlock` in the pre-exec path (the bug re-appears).
- Enabling the feature but failing-open on `restrict_self` errors (silently unconfined — same as today).
- Breaking the existing 30+ `safety.rs` / `bash.rs` tests (the deny-list still runs; landlock is a second layer, not a replacement).
- Allowing the binary itself but forgetting its dynamic-linker deps → spawn fails with ENOENT.
