# Workorder 27.6 — TUI Themes (NEW, polish)

## Status: Planned

## Problem

The TUI has no theme support — a single hard-coded color scheme. The 5th-ed review flagged "no themes" as a competitive gap vs Cursor/Claude Code. Users on light terminals, in sunlight, or with color-vision differences have no escape. The rendering layer (`src/tui/rendering/`) uses `ratatui::style::Color` literals scattered across the codebase.

## Source

- `kf-code-review.md` 5th edition, scorecard TUI/UX row + Part 4 matrix ("TUI mouse/themes: scroll-only / ❌ themes").
- `src/tui/rendering/mod.rs` + `table.rs` + `format.rs` — the color-literal sites.
- `src/shared/config/*` — `DisplayConfig` lives here (the `display.*` config fields).

## Reality-check

- `rg "Color::" src/tui/` — color literals are scattered (each widget picks its own).
- `ratatui::style::Color` is the type; `Style::default().fg(Color::Cyan)` is the pattern.
- No central palette struct exists today.

## Scope

### R1 — `Theme` struct + central palette
- New `src/tui/theme.rs`:
  ```rust
  pub struct Theme {
      pub user_msg: Color,
      pub assistant_msg: Color,
      pub tool_call: Color,
      pub tool_result: Color,
      pub error: Color,
      pub warning: Color,
      pub success: Color,
      pub dim: Color,        // prompts, hints
      pub accent: Color,     // selected, focused
      pub border: Color,
      pub bg: Color,
      // ...cover the ~12 distinct roles used across rendering/
  }
  ```
- Replace the scattered `Color::Foo` literals in `src/tui/rendering/` with `theme.<role>` lookups. The `AppState` (or a new `ThemeState`) carries the active `Theme`; render functions take `&Theme`.

### R2 — Ship 3-4 built-in themes
- `Theme::default()` — current colors (back-compat).
- `Theme::dark()` — high-contrast on dark bg (the current implicit assumption, made explicit).
- `Theme::light()` — readable on white/light terminals (swap Cyan→Blue, Yellow→DarkYellow, etc.).
- `Theme::monokai()` — a popular palette (exercise the generality).
- Each defined as a `const` in `theme.rs`.

### R3 — Config field + `/theme` slash command
- `src/shared/config/display.rs` (or wherever `DisplayConfig` lives) — add `pub theme: String` (default `"default"`). Accept `"default" | "dark" | "light" | "monokai"`.
- `src/tui/keys/slash_commands.rs` — add `/theme [name]` (no-arg = cycle, with-arg = set). Persist selection to config.toml on next `/save` or session exit.
- On unknown theme name, print the available list.
- `ponytail:` comment naming the ceiling (no user-defined custom themes yet — that's a follow-up if requested; `Theme::custom(palette: HashMap)` is the upgrade path).

### R4 — Docs
- `docs/TECHNICAL.md` TUI section — document the theme system + the built-in list.
- `config.toml.example` — `theme = "default"` with the comment listing options.
- ADR if the `Theme` struct becomes load-bearing (it's a polish feature; an ADR may be overkill — a TECHNICAL.md section is enough).

## Success criteria

1. `/theme light` produces a readable TUI on a white-background terminal (screenshot in the PR / verification).
2. `/theme` (no arg) cycles through default→dark→light→monokai→default.
3. The selection persists across sessions via `config.toml`.
4. Zero `Color::` literals remain in `src/tui/rendering/` (all go through `Theme`).
5. `cargo test --lib -p kf-code tui::` passes (the existing TUI tests don't assert specific colors; they should still pass — if any DO assert colors, update them to assert against `Theme::default()`).

## Failure criteria

- Hard-coding a 4th theme instead of generalizing (the 5th theme should be a 1-line addition).
- Breaking the existing rendering on the default theme (back-compat is required).
- Adding a runtime color-picker UI (out of scope — config + slash command is enough).

## Estimate

M (3-5 days). R1 is the substantive refactor (find every color literal); R2/R3 are additive; R4 is docs.

## Defer note

Custom user-defined themes (loaded from a TOML palette file) are explicitly out of scope — the `Theme::custom(...)` upgrade path is noted but not built. Ship the 4 built-ins first; add custom-theme loading only if a user asks.
