# Workorder 27.7 — TUI Mouse Support (NEW, polish)

## Status: Planned

## Problem

The TUI is mouse-scroll-only — click and drag don't work. The 5th-ed review flagged "Mouse scroll-only (no click/drag)" as a competitive gap vs Cursor/Claude Code/opencode. `src/tui/events.rs` handles `MouseEventKind::ScrollDown/ScrollUp` but ignores `Down/Up/Drag`. crossterm mouse capture may not even be enabled.

## Source

- `kf-code-review.md` 5th edition, TUI/UX scorecard + Part 4 matrix.
- `src/tui/events.rs` — the event loop + mouse handling.
- `src/main/run_session.rs` — where crossterm is initialized (look for `EnableMouseCapture`).

## Reality-check (verify before starting)

- `rg "MouseEventKind|EnableMouseCapture|DisableMouseCapture" src/tui/ src/main/` — confirm which event variants are handled + whether capture is enabled at startup.
- `src/tui/events.rs` likely has a `match event` on `KeyEvent` + a separate branch for `MouseEvent` that only handles scroll.
- ratatui + crossterm both fully support click/drag; this is wiring, not a capability gap.

## Scope

### R1 — Enable mouse capture + route click/drag events
- `src/main/run_session.rs` (or wherever the terminal is set up) — ensure `crossterm::execute!(stdout, EnableMouseCapture)` runs at startup alongside `EnterAlternateScreen`. Restore `DisableMouseCapture` on shutdown (the cleanup path already exists for the screen).
- `src/tui/events.rs` — extend the `MouseEvent` match to handle:
  - `MouseEventKind::Down(MouseButton::Left)` — click: focus the panel under the cursor, OR position the cursor in the prompt/approval input.
  - `MouseEventKind::Drag(MouseButton::Left)` — drag: scroll the history/chat panel by the delta.
  - `MouseEventKind::Up(MouseButton::Left)` — end drag / commit click.
  - `MouseEventKind::ScrollDown/ScrollUp` — already handled (verify).
- Coordinate translation: crossterm gives row/column; map to the active panel's scroll offset via the layout rects the renderer already computes.

### R2 — Click-to-focus + click-to-position
- Panel focus: clicking on a panel (chat / input / jobs / etc.) sets it as the focused pane (the existing tab/F2-F5 handlers switch panes; mouse-click is the equivalent).
- Cursor positioning: clicking inside the prompt/approval input moves the text cursor to the clicked column (rustyline-style; may need the LineReader's editor to accept a position).

### R3 — Config gate (for users who hate mice)
- `src/shared/config/display.rs` — add `pub mouse_enabled: bool` (default `true`). When `false`, skip `EnableMouseCapture` (saves terminal scrollback hijacking, which some users dislike).
- `config.toml.example` — document the field.

### R4 — Docs
- `docs/TECHNICAL.md` TUI section — document click/drag/scroll behavior + the opt-out.

## Success criteria

1. Clicking on the chat panel focuses it (subsequent scroll/PgUp affects chat, not input).
2. Clicking in the prompt input positions the text cursor.
3. Drag scrolls the active panel smoothly (no flicker; ratatui's render-on-dirty handles this).
4. `mouse_enabled = false` disables all of it + doesn't enable mouse capture (terminal scrollback works normally).
5. Existing keyboard-only flows unchanged (mouse is additive, not a replacement).
6. `cargo test --lib -p kf-code tui::events` passes.

## Failure criteria

- Hijacking terminal scrollback without the `mouse_enabled` opt-out (some users will be furious).
- Breaking the existing scroll handling.
- Mouse-capture left enabled on panic/shutdown (the terminal becomes unusable — ensure `DisableMouseCapture` runs in the cleanup path even on unwind).

## Estimate

M (3-5 days). R1 is the substantive wiring; R2 is the UX refinement (cursor positioning may be fiddly); R3/R4 are small.

## Defer note

R2's cursor-positioning (click-in-prompt-to-move-caret) is the hardest part — if rustyline doesn't expose a set-position API cleanly, defer R2-cursor to 27.7-R2-later and ship R1 (panel focus + drag-scroll) first. Panel focus + drag-scroll alone close the competitive gap.
