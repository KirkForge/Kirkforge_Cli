# Workorder 28.4 — Fix the TypeScript Plugin-SDK Cycles

## Status: Planned

## Problem

gitnexus reports **5 import cycles** in `npm/kf-plugin/packages/`. Four are the
same shape — a barrel `index.ts` (or `types.ts`) that owns the types also
re-exports an implementation module, while that implementation module imports the
types back. The fifth is a type-owner re-exporting from an impl. All five block
clean tree-shaking, confuse IDE go-to-definition, and make the SDK packages
harder to extract independently.

```
core-events:   audit-chain-hash.ts -> audit.ts -> audit-chain-hash.ts
core-rbac:     index.ts -> jwt-verify.ts -> index.ts
core-sandbox:  index.ts -> runner.ts -> index.ts
memory-palace: adapters/file.ts -> types.ts -> sqlite-adapter.ts -> index.ts -> adapters/file.ts
orchestrator:  classifier-nlp.ts -> classifier-persistence.ts -> classifier-nlp.ts
```

## Source

- gitnexus reindex (2026-08-12) `check --cycles` (the five paths above).
- New finding — not in the 5th-edition review (which was Rust-focused).

### gitnexus evidence + per-cycle root cause (verified at `5296f41`)

**Cycle 1 — `core-events` (`audit-chain-hash ↔ audit`)**
- `audit-chain-hash.ts:2` imports `type { AuditEvent } from "./audit.js"`.
- `audit.ts:145` re-exports it back: `export { initialHash, chainHashOf } from "./audit-chain-hash.js"`.
- `audit.ts:11` explicitly calls itself *"a thin barrel: types live here,
  implementations live in `audit-sinks/*` and `audit-chain-hash.ts`."* The barrel
  re-export is the cycle.

**Cycle 2 — `core-rbac` (`index ↔ jwt-verify`)**
- `jwt-verify.ts:7` imports `type { OidcConfig, JwtClaims, GroupRoleMapping } from "./index.js"`.
- `index.ts:422-423` re-exports `export { verifyJwt, clearJwksCache } from "./jwt-verify.js"` + the `VerifyJwtOptions` type.

**Cycle 3 — `core-sandbox` (`index ↔ runner`)**
- `runner.ts:6-16` imports `SandboxConstraints`, `SandboxResult`, `validateConstraints`, … from `./index.js`.
- `index.ts:387-393` re-exports `export { … } from "./runner.js"`.

**Cycle 4 — `memory-palace` (4-node)**
- `adapters/file.ts:6` imports adapter interfaces from `../types.js`.
- `types.ts:4` re-exports `export type { BackupMetadata } from "./sqlite-adapter.js"` ← a *type* file depending on an *impl*.
- `sqlite-adapter.ts:3` imports interfaces from `./index.js` (the barrel) instead of from `./types.js`.
- `index.ts:22` re-exports `FileAdapter` from `./adapters/file.js`.

**Cycle 5 — `orchestrator` (`classifier-nlp ↔ classifier-persistence`)**
- `classifier-nlp.ts:13` imports `type { ClassifierMemory } from "./classifier-persistence.js"`.
- `classifier-persistence.ts:9` imports the value `{ resetNlpModel } from "./classifier-nlp.js"`.

## Reality-check (verified against code at `5296f41`)

- Cycles 1-3 are **purely type-vs-re-export**: the impl imports types from the
  barrel, the barrel re-exports the impl. TypeScript tolerates this (types erase;
  values lazy-load), but it is an architectural cycle and breaks tooling that
  respects the dep graph (gitnexus, madge, eslint-plugin-import).
- Cycle 4 has two distinct defects: `types.ts` reaching into an impl for
  `BackupMetadata`, and `sqlite-adapter.ts` importing from the barrel instead of
  the types file.
- Cycle 5 is a genuine value-level cycle (persistence calls `resetNlpModel` at
  runtime when retraining), not just a type cycle — but the *import* cycle is
  still driven by the `ClassifierMemory` type living on the wrong side.
- All five packages build today (`tsc` resolves the cycles); the goal is
  architectural cleanliness + unblocking per-package extraction, not fixing a
  build break.

## Scope

### R1 — `core-events`: extract `audit-types.ts`
- New `npm/kf-plugin/packages/core-events/src/audit-types.ts` holding `AuditEvent`,
  `AuditAction`, `AuditOutcome`, `AuditSink`, `AuditSinkConfig`.
- `audit.ts` and `audit-chain-hash.ts` both import from `./audit-types.js`.
- Drop `audit.ts:145`'s re-export of `initialHash`/`chainHashOf`; consumers
  import the hash fns directly from `./audit-chain-hash.js` (or a new
  `index.ts` barrel that imports from *both* leaves without creating a cycle).

### R2 — `core-rbac`: extract `types.ts`
- New `npm/kf-plugin/packages/core-rbac/src/types.ts` holding `OidcConfig`,
  `JwtClaims`, `GroupRoleMapping`, `Actor`, `Role`, `Permission`.
- `jwt-verify.ts:7` and `index.ts` both import types from `./types.js`.
- Keep `index.ts:422` re-export of `verifyJwt` (a barrel may re-export an impl
  *if the impl no longer imports back from the barrel*).

### R3 — `core-sandbox`: extract `types.ts`
- New `npm/kf-plugin/packages/core-sandbox/src/types.ts` holding
  `SandboxConstraints`, `SandboxResult`, `SandboxContext`, `SandboxViolation`,
  and the pure validators (`validateConstraints`, `isCommandAllowed`,
  `isReadPathAllowed`, `isWritePathAllowed`, `createSandboxContext`) — or split
  validators into `constraints.ts` if a types file shouldn't hold logic.
- `runner.ts:6` imports from `./types.js` (or `./constraints.js`); `index.ts`
  keeps its runner re-export at `:387` (no longer cyclic).

### R4 — `memory-palace`: move `BackupMetadata` + fix the barrel import
- Move the `BackupMetadata` **definition** from `sqlite-adapter.ts` into
  `types.ts` (it is a type; `types.ts:4` becomes the definer, not a re-exporter).
- Change `sqlite-adapter.ts:3` to import adapter interfaces from `./types.js`
  instead of `./index.js`.
- Both changes are required; either alone leaves a cycle.

### R5 — `orchestrator`: extract `ClassifierMemory` into a types file
- Move the `ClassifierMemory` **interface** from `classifier-persistence.ts`
  into a new `classifier-types.ts` (or into an existing shared types module).
- `classifier-nlp.ts:13` imports `ClassifierMemory` from `./classifier-types.js`;
  `classifier-persistence.ts` imports it from the same place.
- `classifier-persistence.ts:9`'s runtime call to `resetNlpModel` now points one
  way only (persistence → nlp) — no cycle.

## Success criteria

1. `gitnexus check --cycles` reports **0 cycles** under
   `npm/kf-plugin/packages/`.
2. Each package's `tsc` build + existing unit tests pass unchanged.
3. `eslint` (already wired per WO 26.6-R3) reports no new circular-import
   warnings; if `eslint-plugin-import` is configured, `import/no-cycle` is clean.
4. The public API of each package is unchanged — every type/fn previously
   importable from `index.ts` still is (via re-export from the new location).
5. No new runtime dependency introduced (these are type-file extractions +
   import-path fixes; zero new packages).

## Failure criteria (anti-patterns to avoid)

- Breaking the public API by removing a re-export that downstream consumers
  (other packages, the Rust `TsOrchestratorBridgeVerifier` NDJSON contract) rely
  on — keep re-exports at the barrel, just fix where types *live*.
- Introducing a `types.ts` that imports from `index.ts` (re-creating the cycle
  one hop away).
- "Fixing" cycle 5 by injecting a `resetNlpModel` callback through every
  persistence call site — over-engineered; the type extraction is the smaller,
  correct fix.
- Splitting packages into sub-packages (monorepo workspace changes) — out of
  scope; this WO is file-level.

## Estimate

**M (~3 days).** Five independent cycles, each small (extract a types file,
rewire 2-3 imports, update the barrel). The work is parallelizable across the
five packages (five subagents, one per cycle, no file overlap). Budget half a
day per cycle + half a day for the cross-package `tsc` + eslint gate.

## Defer note

None. All five cycles are independently shippable — if one package's extraction
proves contentious (e.g. cycle 4's `BackupMetadata` move ripples into the sqlite
migration code), ship the other four and defer only that cycle to
`28.4-R4-later` with a `state.md` note. Do not batch-defer the whole WO for one
cycle.
