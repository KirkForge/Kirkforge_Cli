# Workorder 29.0 — WO 29 Series Overview: TS→Rust SDK Migration

## Status: Planned

## Problem

The TypeScript plugin SDK (`npm/kf-plugin/`, ~16k LOC across 5 packages + SDK core + apps) is a parallel runtime surface that brings: a Node runtime dependency, node_modules bloat, a separate build/lint/test system (tsc/eslint/npm), a Rust↔TS serialization boundary, 5 circular imports (gitnexus-confirmed), and an undeclared monorepo-hoist dependency (`core-enterprise` in `core-sandbox/runner.ts`). The deep inventory (3 subagents, 2026-08-12) confirmed the Rust binary calls exactly ONE TS path (the `bridge-emitter.ts` NDJSON security verifier); everything else is consumed only by TS-side callers (`apps/cli`, `apps/mcp`). The bundled `plugins/kf-plugin/` is 7 POSIX shell scripts that each `exec node $CLI`.

The migration eliminates the Node runtime entirely by porting the verification + orchestration surface to Rust and folding the bundled plugin into compiled-in tools.

## Source

- 3 exhaustive inventory subagent reports (2026-08-12): security packages, capability packages, Rust plugin architecture.
- gitnexus reindex (17,665 nodes): 5 TS cycles confirmed; `bridge-emitter.ts` is the sole Rust↔TS integration point.
- ADR-050 (plugin system consolidation): "Porting to Rust would not eliminate the external dependency on [ESLint, Ruff, etc.]" — the linters stay external; the orchestration moves to Rust.
- The user's directive: "make wo29 a SDK migration to Rust so we can loose that npm cirkus and dependencies."

## Architecture decisions (from the inventory findings)

1. **No JSON-RPC to preserve.** The plugin protocol is env-var + exit-code + stdout. A Rust plugin is just an executable that reads `KIRKFORGE_TOOL_ARGS_JSON` and writes stdout. This simplifies the migration dramatically.
2. **`core-sandbox` is DEAD** (zero consumers). Delete, don't port. The Rust binary already has landlock + rlimits + curated env.
3. **The bundled plugin** (`plugins/kf-plugin/`) folds into compiled-in Rust tools (like stratum/kf-budget via ADR-050). The 6 commands shell out to the same external linters (ESLint/Ruff/Pyright/Bandit) but the wrapper logic is Rust.
4. **The bridge-emitter** is replaced by a Rust security emitter that writes the same NDJSON format (6 fields: verifier, severity, file, line, message, rule). The Rust consumer (`TsOrchestratorBridgeVerifier`) is already in place.
5. **The orchestrator** (7955 LOC, 36 files) is the biggest porting target. ~1700 LOC is pure modules (no model calls, no fs, no event bus) ready for direct translation. The impure modules (delegation, decompose, correction loop, health-server) require design decisions and are deferred to later phases.
6. **External linters stay external.** ADR-050 is explicit: Rust cannot replace ESLint/Ruff/Pyright. The Rust orchestration shells out to them, same as the TS does today.

## Ordering + dependencies

```
29.1 (fold bundled)     ─── unblocks 29.2 (the bridge becomes internal)
29.2 (security emitter) ─── standalone; replaces the only Rust→TS call
29.3 (pure modules)     ─── foundation for 29.7; no deps
29.4 (EventBus+Audit)   ─── foundation for 29.7
29.5 (RBAC+JWT)         ─── foundation for 29.8
29.6 (memory-palace)    ─── foundation for 29.7
29.7 (orchestrator)     ─── depends on 29.3+29.4+29.6
29.8 (health-server)    ─── depends on 29.4+29.5
29.9 (cleanup)          ─── LAST; after everything else ports
```

Phase 1 (29.1-29.2) can ship independently — it eliminates the bundled-plugin Node dependency without porting the orchestrator. Phase 2-3 port the foundation. Phase 4 is the orchestrator. Phase 5 deletes the TS code.

## The global rule (carried from WO 21/27)

Every WO carries: root cause, scope (exact files + R-items), success criteria, failure criteria, estimate, defer note. No silent deferral. Run the gates. Commit per WO.

## What this series is NOT

- NOT a port of the linters themselves (ESLint/Ruff/Pyright stay external — ADR-050).
- NOT a unified plugin protocol change (the env-var + exit-code contract stays).
- NOT a rewrite of `kf-plugin-sdk`/`kf-plugin-host` (those are already Rust — they're the manifest + trust + loader, not the verification runtime).
- NOT a single mega-PR. Phased, each WO independently shippable + reversible.
