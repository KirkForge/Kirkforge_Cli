# Workorder 29.2 — Rust Security Emitter (Replace bridge-emitter.ts)

## Status: Planned

## Problem
The Rust `TsOrchestratorBridgeVerifier` (`src/session/verifier/bus.rs:362-495`) spawns `npm/kf-plugin/packages/orchestrator/src/bridge-emitter.ts` as a Node subprocess to get security findings. The bridge reads `KF_CHANGED_FILES`, runs `SecurityEmitter` (14 regex rules across JS + Python), maps severities, and writes NDJSON to stdout. This is the ONLY Rust→TS call path. Replacing it with a Rust-native emitter eliminates the last Node dependency for the verifier bus.

## Source
- Inventory: bridge-emitter wire format (6 fields: verifier, severity, file, line, message, rule), severity mapping, SecurityEmitter RULES array.
- `src/session/verifier/bus.rs:306-495` — the Rust consumer (NdjsonVerdict struct, severity mapping, malformed-line tolerance).
- `npm/kf-plugin/packages/orchestrator/src/security-emitter.ts` (223 LOC) — the 14 regex rules + the emit logic.
- `npm/kf-plugin/packages/orchestrator/src/bridge-emitter.ts` (99 LOC) — the NDJSON stdout writer.

## Reality-check
- The Rust consumer already parses NDJSON + tolerates malformed lines + maps severity. It just needs the PRODUCER to be Rust.
- The SecurityEmitter has 14 rules (JS: eval/Function/setTimeout-immediate/bracket-notation/innerHTML; Python: eval/exec/ pickle.loads/subprocess; shared: hardcoded-secrets/API-key-patterns).
- The bridge passes changed files via both `KF_CHANGED_FILES` env AND positional argv.

## Scope

### R1 — Port the SecurityEmitter regex rules to Rust
- New module `src/session/verifier/security_emitter.rs` (or extend `src/session/verifier/security.rs`):
  - Define the 14 rules as a static array of `(pattern: &str, severity: Severity, rule_id: &str, message: &str)`.
  - The emit function: for each changed file, read it, strip comments (line-level `//` and `#` + block `/* */`), scan for each regex pattern, collect findings.
  - Mirror the TS severity mapping: `critical/high → Error`, `medium → Warning`, `low → Info`.

### R2 — Replace the bridge invocation
- `src/session/verifier/bus.rs`: `TsOrchestratorBridgeVerifier` currently spawns the TS bridge command. Change it to call the Rust `security_emitter::emit(files)` directly (compiled-in function, no subprocess).
- The output: `Vec<VerdictEntry>` (the same struct the NDJSON parser produces). No NDJSON serialization needed — the function returns typed structs.
- Delete the `TsOrchestratorBridgeVerifier` struct (it becomes a direct call, not a subprocess verifier). OR keep the struct as a thin wrapper that delegates to the Rust emitter.

### R3 — Delete the TS bridge + security-emitter
- After the Rust emitter is verified: delete `npm/kf-plugin/packages/orchestrator/src/bridge-emitter.ts` + remove its test (`tests/bridge-emitter.test.ts`).
- The `security-emitter.ts` stays until WO 29.7 (orchestrator port) since the orchestrator uses it internally for its own verify cycle.

## Success criteria
1. Security verifier findings are produced by Rust (no Node subprocess spawned for verification).
2. The 14 rules produce the same findings as the TS version (port the test fixtures from `security-emitter.test.ts`).
3. `TsOrchestratorBridgeVerifier` is either deleted (preferred) or reduced to a 3-line wrapper around the Rust emitter.
4. The verifier bus tests pass.

## Failure criteria
- Changing the NDJSON contract (the consumer must still work if a plugin verifier emits NDJSON).
- Dropping any of the 14 rules.
- Adding a regex dep that isn't already in the workspace (`regex` is already a dep).

## Estimate
S (1-2 days). The regex rules are straightforward; the Rust verifier bus already handles the output shape.

## Defer note
None. This is Phase 1; it eliminates the last Rust→TS call path.
