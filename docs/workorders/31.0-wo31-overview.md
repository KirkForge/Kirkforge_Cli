## Problem

The verification loop currently only fires for Rust projects (`cargo build`/`clippy`/`test`/`rustfmt`). When kf-code works on Python, JS/TS, Go, or any non-Rust project, the verifiers return `Skipped` — the generate→execute→verify→correct loop degrades to generate→execute→hope. The first real-world dogfood test (kf-code against KirkForge-MCP, a Python project, 2026-08-13) proved the agent can find bugs but can't auto-verify its fixes.

## Source

- Dogfood test output (2026-08-13): agent found 7 real issues in KirkForge-MCP but noted "the verification loop didn't fire because it's Python."
- The verifier architecture (`src/session/verifier/`) is already split by concern: `build.rs`, `lint.rs`, `test.rs`, `rustfmt.rs`, `git.rs`, `security.rs`. Each is a `Verifier` trait impl.
- The `VerifierSlots` registration (`src/session/executor/mod.rs:init_default_verifiers`) is where new verifiers plug in.

## Architecture decision

**Detection-based, not config-based.** The verifiers should DETECT the project language from the workspace (presence of `pyproject.toml`/`setup.py` → Python; `package.json` → Node; `go.mod` → Go; `Cargo.toml` → Rust) and run the appropriate tools. No config flag needed — the verifier sniffs the project type.

## Success criteria

1. kf-code editing a Python file → pytest auto-runs after the edit → failures fed back as `Verdict::Fixable` → agent corrects → pytest re-runs → passes.
2. Same for Node (tsc + eslint) and Go (go test + go vet).
3. Rust projects unchanged (the existing verifiers fire as before).
4. Mixed-language projects: only the relevant verifiers fire per file.

## Failure criteria

- Running Rust verifiers on a Python project (noise + wrong output).
- Blocking the turn if pytest/tsc/go are not installed (should skip gracefully).
- Breaking the existing Rust verification flow.

## Gate

`cargo test --lib -p kf-code verifier::` — existing tests pass + new verifier tests pass.

## WO 31.6 — TUI Selftest Harness

### Status: DONE (2026-08-13, branch `wo31tui`)
`src/tui/selftest.rs` ships the harness (`TuiTestHarness` + `render_to_string`)
+ 10 spec scenarios + 2 bonus tests (12 total, all green). `render_frame`'s
closure body extracted to `pub(crate) fn render_app` so the harness drives the
exact production layout. The `token_stream_stress` scenario surfaced a real
latent bug (auto_scroll doesn't pin for long single-paragraph assistant
messages; `max_scroll` uses pre-`.wrap()` `Line` count) — pinned with a guard
assertion, fix deferred (out of harness scope), tracked in `state.md`.

### Problem
TUI bugs (thinking-stream rendering, layout overflow, panic-on-render, state desync) are found manually by running kf-code in a real terminal. This is slow, unrepeatable, and can't run in CI. The existing TUI unit tests check individual widgets in isolation but don't exercise the full render pipeline with realistic event sequences.

### Solution
A selftest harness that drives the COMPLETE TUI render pipeline (all widgets, all panels) with mock events, renders to an in-memory Buffer (no terminal/PTY/tmux needed), and asserts on the output. Runs in <1s as a `cargo test` target.

### Architecture
```
src/tui/selftest.rs (#[cfg(test)] module)
├── harness: build AppState + feed events + render to test Buffer
├── scenarios:
│   ├── token_stream_stress (500 tokens, verify no overflow/panic)
│   ├── thinking_block_wordwrap (long thinking, verify proper wrapping)
│   ├── tool_call_card_render (tool call + result, verify card layout)
│   ├── approval_prompt_display (approval request, verify prompt)
│   ├── budget_indicator_update (budget events, verify indicator)
│   ├── scroll_100_messages (many messages, verify scroll + no lag)
│   ├── slash_command_menu (command list, verify rendering)
│   ├── search_overlay (Ctrl+F, verify search panel)
│   ├── doom_loop_banner (doom detection, verify banner)
│   └── empty_state (no messages, verify welcome)
├── assertions: buffer contains expected text, no panic, dimensions OK
└── snapshot: dump the buffer as text for debugging on failure
```

### R-items
- R1: `TuiTestHarness` struct — builds AppState, feeds `TurnEvent`s, renders via a test `Backend<Buffer>`, exposes the rendered text for assertions.
- R2: The 10 scenarios above, each as a `#[test]` function.
- R3: A `render_to_string(state, width, height) -> String` helper that renders the full TUI to a string (for debugging + snapshot comparison).
- R4: Integration with `cargo test` — all scenarios runnable via `cargo test --lib tui::selftest`.

### Gate
`cargo test --lib -p kf-code tui::selftest` — all scenarios pass. Each scenario exercises a real rendering path and catches the bug class it targets.

### Estimate
M (the harness + 10 scenarios). The harness is the hard part; the scenarios are incremental once it works.
