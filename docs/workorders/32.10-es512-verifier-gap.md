# Workorder 32.10 — ES512 (P-521 ECDSA) Signature Verification Gap

## Status: Pending

## Problem

ES512 (P-521 ECDSA) signature verification is unsupported in
`crates/kf-rbac/src/jwt.rs:25-35`. ES512 is listed in the
`ALLOWED_ALGORITHMS` policy set, so tokens claiming ES512 pass the
policy gate — but the verifier then rejects them because `jsonwebtoken`
has no ES512 variant. The result is a policy/verifier mismatch: a
token is allowed in policy, denied in fact, with no path to make it
work. Open since WO 29.5.

The `ponytail:` comment at `jwt.rs:32-33` already names the two viable
upgrade paths — this WO picks one.

## Root cause

`jsonwebtoken` only covers HS/RS/ES256/ES384/EdDSA. ES512 needs a
P-521 ECDSA path that crate does not provide. The verifier was ported
in WO 29.5 against `jsonwebtoken`'s surface and the P-521 gap was
deferred, then never closed.

## Approach

Pick one of the two `ponytail:` upgrade paths:

1. Add the `p521` crate + a manual ES512 verify branch in `jwt.rs`
   (keeps `jsonwebtoken` for the other algs; smallest dep surface).
2. Switch to a fuller JOSE crate (e.g. `josekit`) that covers ES512
   natively (replaces `jsonwebtoken`; larger dep, bigger diff).

Default to option 1 (smaller diff, the release profile is
size-optimized — every dep earns its place). Only go option 2 if the
`p521` manual branch proves unworkable. Document the choice in an ADR.

## Files to touch

- `crates/kf-rbac/src/jwt.rs` — ES512 verify branch (option 1) or full
  crate swap (option 2)
- `crates/kf-rbac/Cargo.toml` — add `p521` (option 1) or `josekit`
  (option 2)
- `docs/adr/` — new ADR documenting the ES512 backend choice

## Gate

- `cargo test -p kf-rbac`

## Done condition

ES512 tokens verify successfully. The `ALLOWED_ALGORITHMS` policy and
the verifier agree on ES512. No silent downgrade of other algorithms.
The backend choice is documented in an ADR.
