# Workorder 32.13 — Streaming Idle Timeout Configurable Per-Adapter

## Status: Done (`d6e507e`; default 180s)

## Problem

`STREAM_IDLE_TIMEOUT` is a 180s `const` at
`src/adapters/mod.rs:35`. The earlier "too aggressive" bug (timeout
firing mid-stream) is fixed by the 180s value, but the value is now
hardcoded — a slow model or a long tool sub-turn can still hit it, and
operators cannot tune it without a recompile.

The `ponytail:` upgrade path at `src/adapters/mod.rs:34` already names
the fix: "per-adapter configurable idle timeout from
`config.model.request_timeout_secs`."

## Root cause

The timeout was shipped as a `const` because that was the fastest path
to the "too aggressive" fix. The config plumbing to feed a per-adapter
value down to the stream loop was not wired at the time and was
deferred.

## Approach

1. Add `request_timeout_secs` (default 180) to the per-model / per-adapter
   config block. Per AGENTS.md §7, a `Config` field addition touches
   ALL of: `Default` impl, struct def, test `Config` literals
   (especially `executor/tests/mod.rs`), `adapter_for_with_provider`
   call sites, `adapter_for` wrapper, test calls.
2. Replace the `STREAM_IDLE_TIMEOUT` const read with the configured value
   threaded down from the adapter. Keep 180s as the `Default`.
3. Preserve the `const` as the default source-of-truth value (or fold
   it into the `Default` impl) so nothing silently changes for operators
   who don't set the field.

## Files to touch

- `src/adapters/mod.rs`
- `src/shared/config/`

## Gate

- `cargo check --workspace`

## Done condition

The streaming idle timeout is configurable via
`config.model.request_timeout_secs` (or equivalent). Default is 180s
(unchanged behavior for operators who don't set it). The `const` is no
longer the only source of the value.
