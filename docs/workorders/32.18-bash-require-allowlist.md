# Workorder 32.18 — WO 28.17 R2 — bash.require_allowlist Config

## Status: Pending

## Problem

WO 28.17 R2 deferred an optional `bash.require_allowlist` config field
(default `false`). When `true`, bash commands must match an operator-defined
allowlist (`bash.allowlist = ["git", "cargo", ...]`) or be denied. The
deferral was semantic, not technical: allowlist matching needs operator input
on three policy questions — glob vs prefix vs regex, compound-command
handling (`git status && rm -rf x`), and whether the match targets the
command head or the full argv.

## Root cause

R1 shipped the bash tool's base deny/allow plumbing. R2 was deferred because
the allowlist matching policy was unspecified, and shipping a guessed policy
would lock operators into semantics they can't override. The fix is to pick a
default policy (prefix-match on command head, compound commands denied unless
each clause matches), make it configurable, and document the choice.

## Approach

1. Add `bash.require_allowlist: bool` (default `false`) and `bash.allowlist:
   Vec<String>` to the config (per AGENTS.md §7 — update `Default` impl,
   struct def, test `Config` literals, `adapter_for_with_provider` and
   `adapter_for` call sites, test calls).
2. Default match policy: prefix-match on the command head (first token).
   Compound commands (`&&`, `;`, `|`) require EVERY clause to match or the
   whole command is denied. Document this as the chosen semantics, not a
   guess.
3. Deny path returns a `Verdict` / access-denied result naming the offending
   clause so operators see why.
4. `require_allowlist = false` (default) preserves current behavior — no
   regression for existing operators.

## Files to touch

- `src/shared/config/` — `bash.require_allowlist`, `bash.allowlist` fields
- `src/session/access/` — allowlist matcher + deny-on-miss in the access layer

## Gate

## Done condition

The allowlist mode exists, is configurable (default-OFF), and denies
non-allowlisted commands — including compound commands where any clause is
off. Default `false` behavior is unchanged. Matching policy is documented,
not guessed.
