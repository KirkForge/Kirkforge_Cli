# Workorder 32.19 — WO 29.7 R6 + R7 — SloMonitor + Security Emitter Wiring

## Status: Pending

## Problem

Two deferrals from WO 29.7 were tracked but never started:

1. **R6 — SloMonitor + AuthPolicySloMonitor.** Compute SLOs, persist state,
   restore on restart. Ring-buffer of 100k events. Deferred as the
   "lowest-value piece" per 29.7:52.
2. **R7 — wire the Rust security emitter (WO 29.2) into the orchestrator's
   verify cycle.** The emitter exists but is not invoked from the verify
   loop, so security findings never reach it.

Both are legitimate work that was sequenced last, not work that was rejected.

## Root cause

R6 and R7 were the tail of WO 29.7's scope. R6 was judged lowest-value at the
time; R7 depends on R6-adjacent state plumbing that wasn't built. Neither is
blocked — both are unstarted. The risk of leaving them open is another
re-deferral; the risk of building R6 if no operator consumes SLOs is YAGNI.

## Approach

1. **R6**: implement `SloMonitor` with a 100k ring-buffer, persist-on-stop,
   restore-on-start. `AuthPolicySloMonitor` wraps it for auth-specific SLOs.
   If during implementation no consumer is found for the SLO numbers, disclose
   as YAGNI per AGENTS.md §11 (state what was cut, why, where it's tracked) —
   do not ship a metrics sink nobody reads.
2. **R7**: invoke the WO 29.2 security emitter from the orchestrator's verify
   cycle so security findings flow to it. This is wiring, not new surface.
3. Update `docs/TECHNICAL.md` in the same commit if R6/R7 alter the verifier
   bus or orchestrator surface (AGENTS.md doc-sync rule).
