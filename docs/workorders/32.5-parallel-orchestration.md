# Workorder 32.5 — Parallel Agent Orchestration (Scout/Coder/Reviewer)

## Status: Accepted (partially implemented)

## Problem

WO 30.3 planned a scout/coder/reviewer fan-out pattern: Scout (read-only
worktree) explores, Coder (write worktree) implements, Reviewer (read-only)
verifies. WO 30.1 + 30.2 shipped the prerequisites (worktree isolation +
TaskManager lifecycle), but the parallel orchestration itself was never started.
`src/tui/commands/workflow.rs:7` explicitly states: "we do NOT spawn parallel
subagent orchestrators." Workflows run steps sequentially via `StepRunner`.

This is the L-sized item that's been open since WO 30.3. It depends on WO 32.4
(CWD confinement) — without FS confinement per subagent, parallel bash calls
could interfere.

## Root cause

Not a bug — a capability gap. The infrastructure exists (worktrees, TaskManager,
approval forwarding) but the orchestration layer that spawns N subagents in
parallel and collects their results doesn't exist.

## Approach

1. New `ParallelOrchestrator` struct in `src/session/` that:
   - Spawns a Scout subagent (read-only worktree, `auto_approve` inherited)
   - Spawns a Coder subagent (write worktree, approval forwarded to parent)
   - Spawns a Reviewer subagent (read-only worktree, runs verifiers)
2. Each subagent gets its own TaskManager entry (WO 30.2 lifecycle).
3. Results collected via the existing approval/event channels.
4. Sequential fallback if `--worktree` not enabled.

## Gitnexus impact

`TaskManager` (LOW risk, 0 impacted) — safe to extend. The `dispatch_tool_call_batch`
hot path (HIGH risk) is not affected — parallel orchestration spawns new turn
loops, not new tool dispatches within a turn.

## Files to touch

- `src/session/parallel_orchestrator.rs` — new file
- `src/session/mod.rs` — register module
- `src/tui/commands/workflow.rs` — wire parallel mode
- `src/tools/task.rs` — TaskManager entries for parallel subagents

## Gate

- `cargo test --workspace`
- `cargo clippy --all-targets -- -D warnings`
- Manual: run a workflow with `--parallel`, verify scout/coder/reviewer spawn

## Done condition

A workflow can spawn scout/coder/reviewer subagents in parallel, each in its own
TaskManager entry, with results collected. Sequential fallback works when worktrees
disabled.

## Deferrals

- **Per-subagent worktree (each subagent in its OWN worktree)**: DEFERRED. The
  session's worktree (when `worktree_enabled`) provides CWD confinement via
  `sandbox_dir` + landlock. Creating 3 separate worktrees adds git worktree
  overhead and merge complexity. The current `InProcessTaskSpawner` already
  inherits `sandbox_dir` from config. Remaining: create 3 `WorktreeSession`
  instances in `ParallelOrchestrator::spawn_role`, thread each path into the
  subagent's config. Tracked here (this workorder, status "partially implemented").
- **Reviewer running verifiers (BusVerifier)**: DEFERRED. The Reviewer uses the
  `plan` persona (read-only) and produces an LLM critique summary. Actually
  running the verifier bus inside the subagent requires wiring the bus into the
  subagent's executor — a larger change. Remaining: inject `VerifyContext` into
  the subagent `Executor` and call `BusVerifier::verify`. Tracked here.
