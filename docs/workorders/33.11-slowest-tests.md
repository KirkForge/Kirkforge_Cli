# WO 33.11 — Report: Top-20 Slowest Tests

## Status: Done (measurement)

## Method

Per-package runs of `cargo nextest run -p <pkg> -j4 --no-fail-fast --message-format libtest-json-plus`
(env `NEXTEST_EXPERIMENTAL_LIBTEST_JSON=1`), parsing the `exec_time` field of each
finished test event. 14 packages measured: `kf-budget-core kf-compress-core kf-workflow
kf-bench kf-lsp kf-plugin-host kf-plugin-sdk kf-context-index kf-memory-store kf-routing
kf-orchestrator kf-rbac kf-testdoctor` (small, each completed in <60s) plus `kf-code --lib`
(the large crate, 3267 tests).

**Total tests captured: 4271** (4271 finished events with a duration).
- kf-code lib: 3267
- 13 other crates: 1004 combined

**Note on `--format json`**: the task brief used `--format json`, which does not exist in
nextest 0.9.114. The correct flag is `--message-format libtest-json-plus` (experimental,
requires `NEXTEST_EXPERIMENTAL_LIBTEST_JSON=1`). The `exec_time` field (seconds, float)
carries the per-test wall-clock.

**Note on nextest per-test timeout**: the brief suggested `--config
'profile.default.timeout-period="60s"'`. This does **not** work — `--config` is a Cargo
flag (overrides `Cargo.toml`), not a nextest flag, and `timeout-period` is not a nextest
key. The nextest timeout is `slow-timeout` (defined in `.config/nextest.toml` per
`[profile.X]` and selected with `--profile <name>`). The repo already ships
`.config/nextest.toml` with `ci-fast` (60s), `ci-full` (120s), `integration` (300s),
`e2e` (600s). **Action item for WO 33.5/33.11**: use `cargo nextest run --profile ci-fast`
for profiling, not ad-hoc `--config` flags.

## Packages that hang

**`kf-code --lib` hangs on exactly 3 tests** in the approval executor:
`session::executor::tests::approval::{auto,deny}::*`. These ran ~856-875s each before
being killed by the 900s wall timeout I imposed on the run. They are genuine
deadlock/infinite-loop bugs in the executor's `run_turn_collecting` path under the
`AlwaysApprove` + deny/allow-permission-rule interaction, not test-debt (no sleep, no
env mutation, no subprocess). They are the single biggest source of test wall-clock in
the entire workspace and also serialize the rest of the kf-code lib suite (see
"Scheduling contention" below).

**`cargo nextest run --workspace --lib` will hang** because it includes kf-code lib,
which includes these 3 tests. This confirms the WO 33.11 brief's warning. Do not run
workspace-wide without either fixing the 3 hangers or excluding them with a nextest
filter (`-E '!test(/.../)'`).

## Scheduling contention (important secondary effect)

The 3 hangers don't just waste ~860s each. Under `-j4 --no-fail-fast`, nextest holds 3 of
the 4 worker slots for the full ~860s, squeezing the remaining ~3264 tests through a
single slot. This inflated the apparent wall-clock of every other kf-code lib test.
Example: the `approval::auto::*` (non-hanging) tests measured ~3.2s during the
contended run but **~2.5s in isolation** (verified by re-running
`test(/approval::auto/) & !test(/dedups_repeated_calls/)` without the hanger). The
~0.7s/test inflation × ~3264 tests is most of the kf-code lib wall-clock beyond the
hangers themselves.

## Findings beyond test debt

1. **The 3 hangers are product bugs, not test debt.** They deadlock/loop in
   `run_turn_collecting` under `AlwaysApprove` + permission rules. They should be filed
   as a P0 workorder (suggest WO 33.18 or a hotfix), not deferred to 33.12-33.14. They
   are the #1, #2, #3 slowest tests AND they serialize the entire kf-code lib suite.

2. **`check_bash_command_str` recompiles regexes per call** (~2.6s for 8 string checks).
   This is a production hot-path performance issue, not just a slow test. The same fix
   (`OnceLock<Regex>`) speeds up the test and the product.

3. **`run_turn_collecting` has a ~2.5s fixed cost per mocked turn.** ~30 tests pay this.
   This is likely a real executor performance issue (checkpoint/log setup, doom-loop
   scan, or a hidden delay), not just test overhead. Worth profiling in isolation as a
   separate workorder.

4. **The nextest per-test timeout flag in the brief was wrong.** `--config
   'profile.default.timeout-period="60s"'` is a Cargo flag with a non-existent nextest
   key. Use `cargo nextest run --profile ci-fast` (the repo already configures 60s
   `slow-timeout` in `.config/nextest.toml`). Had the correct profile been used, the 3
   hangers would have been killed at 60s instead of 860s, and the scheduling contention
   on the rest of the suite would not have occurred.

5. **`cargo nextest run --workspace --lib` hangs.** Confirmed by the 3 hangers in
   kf-code lib. The WO 33.11 brief's per-package fallback is correct and necessary
   until the 3 hangers are fixed.
