# WO 34 — TUI Information Architecture Reset

## Status: In Progress

## Problem

The TUI exposes every capability simultaneously through a persistent 6-tab
bar (F1-F6), 30 slash commands, and a status bar overloaded with 12+
indicators. The result is "admin application" density where the primary
experience (AI coding conversation) competes with secondary UI for
attention.

The TUI engine is sound — `AppState` is decomposed into 11 sub-structs,
rendering is separated from key handling, and the slash command table is
data-driven. The problem is information architecture, not engineering.

## Guiding principle

"Show the user what they need for the current task; hide everything else
until requested."

Level 1 (always visible): conversation, input, model, context, ready/busy
Level 2 (one shortcut away): models, sessions, jobs, help, command palette
Level 3 (advanced): plugins, MCP, routing, metrics, verifier, raw settings

## Source

External TUI UX analysis (`gpt-test_and_ci.md` follow-up). 70% of the
analysis recommendations were validated against the actual codebase; the
remaining 30% (visual language, interaction model consistency, view-model
extraction) were overstated — the codebase already has a theme system,
consistent key dispatch, and AppState separation.

## Gate

- `cargo clippy -p kf-code --lib --tests -- -D warnings`
- `cargo fmt --check`
- `cargo nextest run -p kf-code --lib tui::`
- TUI visual regression: the chat surface must render identically before
  and after the tab bar removal (screenshot comparison or render-output
  diff)

## Done condition

Chat is the permanent primary surface. Secondary views are overlays
reached via Ctrl+K or direct shortcuts. The status bar shows only
model + context + cost + ready. /help opens an overlay, not a conversation
entry. Settings shows semantic controls, not config field names.
Documentation is current.
