# WO 35.4 — Sandbox posture indicator (real layer state)

## Status: Done

## Problem

The TUI's sandbox signal — `⚠️ UNSANDBOXED` on the status bar
(`src/tui/widgets/status.rs:57-64`) and the `/status` sandbox label —
reflects ONLY the PathGuard write-sandbox:
`state.provider.unsandboxed = !path_guard.is_sandboxed()`
(`src/tui/mod.rs:217`). Zero `landlock`/`seccomp` references exist in
`src/tui`. On default Linux the actual posture is Landlock-on +
seccomp-off (feature default-off, `Cargo.toml:283-288`), but the user
has no way to see that. A user can believe seccomp is active when it
isn't, or believe they're unsandboxed when Landlock + PathGuard are
holding.

## Root cause

The indicator was built around the PathGuard gate that exists in the
TUI's own state; the bash-runner sandbox layers (Landlock, seccomp,
CLONE_NEWNET, rlimits — `bash_runner/mod.rs:151-236`) live in the
executor process and were never surfaced upward.

## Approach

1. Compute the active posture once at session start (the layers are
   static per process): Landlock (linux && module compiled — always
   true on Linux), seccomp (`cfg!(feature = "seccomp")`), network
   namespace (`--no-network` flag), PathGuard (sandbox_dir set),
   worktree (session worktree active).
2. Render it in `/status` as the checklist:

   ```
   Sandbox:
     PathGuard    ✓ (sandbox_dir=...)
     Landlock     ✓
     seccomp      ✗ (build with --features seccomp)
     network ns   ✗ (pass --no-network)
     worktree     ✓
   ```

3. Keep the status-bar `⚠️ UNSANDBOXED` as-is (it correctly means "no
   write scope"); optionally add a compact `seccomp ✗` hint to the
   bar only when running as root or in hardened configs — otherwise
   the bar stays quiet (WO 34.3 discipline).
4. The seccomp line doubles as discoverability for the opt-in feature
   without changing its default.
