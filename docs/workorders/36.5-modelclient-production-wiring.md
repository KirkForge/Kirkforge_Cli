# WO 36.5 — Production-wire the ModelClient seam (orchestration unification)

## Status: Pending

## Problem

WO 35.6 built `impl ModelClient for ExecutorAdapter` + ADR-075, but
the adapter has ZERO production callers — the exact criticism the
external review made about kf-orchestrator ("framework with a missing
production seam") now applies to the adapter itself. Until something
real calls it, the rusqlite dep (WO 36.1) and the whole crate link
into the binary for nothing.

## Root cause

WO 35.6 scoped the wiring out (EventSink bridge, ParallelOrchestrator
reimplementation were "follow-ups"). This WO is that follow-up.

## Approach

Make the seam real in three steps, smallest first; each must land or
be explicitly killed with a reason — no third unwired layer:

1. **ParallelOrchestrator executes roles through `ExecutorAdapter`.**
   `spawn_role` currently calls `InProcessTaskSpawner::run_task`
   directly. Re-route it via the adapter (`execute(&TaskBrief)`), and
   extend `TaskBrief`/adapter minimally so the WO 35.2/35.3 semantics
   survive: persona selection, worktree + patch artifact return
   (expose the patch — e.g. `Emission` gains an optional
   `artifacts: Vec<String>` or the adapter exposes a side-channel
   keyed by call), and cancellation (adapter accepts a token or the
   brief carries one). If `TaskBrief` extension fights ADR-075,
   update the ADR (both status spots + index) rather than warping the
   design.
2. **kf-orchestrator `delegate()` becomes reachable end-to-end**: an
   integration test (default gate, wiremock) that runs
   `Orchestrator::delegate` with the real adapter through a
   hard-prompt mode and asserts the DelegationResult carries the
   Emission content. This proves the crate is not just compiled but
   drivable from the binary's own executor.
3. **WO 36.6 fold-in**: `EventSink` bridged to the binary's event bus
   (or a logging sink if the bus types don't line up — honest
   smallest step, disclosed).

If step 1 proves architecturally wrong mid-flight (e.g. the adapter
per-call executor construction fights the worktree lifecycle), STOP,
land steps 2+3, and disclose step 1 with the concrete blocker — a
documented kill is acceptable, a silently unwired adapter is not.

## Files to touch

- `src/session/parallel_orchestrator.rs`, `src/session/executor_adapter.rs`,
  `crates/kf-orchestrator/src/{model.rs,types.rs}` (TaskBrief/Emission
  extension), `src/shared/event_bus.rs` or a small bridge module
- `docs/TECHNICAL.md` orchestration section; ADR-075 if touched
  (both status spots); `docs/workorders/35.6` follow-up list marked
  resolved where true

## Gate

- `cargo clippy --workspace --all-targets -- -D warnings` (the real
  one — this change spans crates), `cargo fmt --check`
- `cargo nextest run -p kf-orchestrator` (71+) +
  `cargo nextest run -p kf-code --lib --no-fail-fast` +
  the new delegate integration test
- `git grep -n "run_task" src/session/parallel_orchestrator.rs` shows
  the adapter path (or the disclosed blocker)

## Done condition

The adapter has a production caller and a drivable delegate path; the
"two orchestration systems" criticism is answered with one execution
seam, or answered with a documented decision.
