# WO 40.4 — Sleep elimination (30+ tests)

## Status: Pending

## Problem (GPT doc items 1-18, Phase 1: kill wall-clock waits)

30+ tests use `sleep()`, `thread::sleep()`, `from_secs()`,
`from_millis()` as synchronization — paying wall-clock time for
what should be event-driven. The GPT doc lists them by file. The
flake audit (WO 38.12) independently found 6 sleep-race tests and
7 wall-clock-threshold tests. This WO kills them ALL.

## Approach

For each test: replace the sleep with the structural synchronization
that the GPT doc recommends per-item:
- **Bash/process tests**: use a gated start signal (oneshot channel
  fired after the process is Running), not a fixed delay. The
  `GatedSleepTool` pattern (loop_.rs) and the `wait_for_job_done`
  poll pattern are templates.
- **Cache/concurrency tests** (caching.rs 5-60ms sleeps): replace
  with barriers/channels (`tokio::sync::Barrier`, `Notify`).
- **Hook/plugin tests** (200ms + 3s timeout): wait on the
  watcher/plugin event, not time.
- **TUI tests** (50-100ms): event-driven test synchronization via
  the existing channel/state-assertion harness.
- **Daemon/client tests** (20-50ms polling): explicit readiness
  handshake — wait for socket bind, not sleep.
- **Executor loop tests** (150ms sleep, configurable sleep_ms): use
  `tokio::time::pause()` / deterministic time advancement where
  the behavior IS about timing; use barriers where it's about
  ordering.
- **Verifier tests** that spawn real cargo: mock the command runner
  (GPT item 25); keep one real cargo integration test.
- **Context-index 1s mtime sleep** (item 1, 🔴 Huge): inject an
  explicit modification timestamp; don't test filesystem mtime
  resolution.
- **E2E harness 500ms/2s polling** (items 2-3): readiness probe
  (poll until process emits known state), not `wait_stable()`.

Prioritize the 🔴 Huge items first: context-index mtime, e2e harness
polling, bash_jobs real processes, caching concurrency, hooks,
bash_runner, tools/bash.rs.

## Files to touch

30+ files across `src/`, `crates/`, `tests/` — the GPT doc lists
each one. Group by subsystem; one commit per subsystem.

## Gate

`grep -rn 'sleep\|from_secs\|from_millis\|thread::sleep' --include=
"*.rs" src/ crates/ tests/ | grep -v '#\[ignore\]\|//\|timeout\|
VERIFIER_TIMEOUT\|FETCH_TIMEOUT\|APPROVAL_TIMEOUT\|REQUEST_TIMEOUT
\|TEST_DEFAULT_TIMEOUT\|IDLE_TIMEOUT\|READER_IDLE\|const.*TIMEOUT
\|Duration::from_secs(.*).as_timeout\|tokio::time::sleep.*cancel
\|tokio::time::sleep.*deadline\|tokio::time::sleep.*poll'` shows
ZERO results in test code (production timeouts are fine; test sleeps
are not).

## Done condition

No test pays wall-clock time for what it could wait for
structurally. The fast profile (`ci-fast`) runs in under 2 minutes.
