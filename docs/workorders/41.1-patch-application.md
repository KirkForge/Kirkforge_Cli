# WO 41.1 — Apply the coder patch + rename ParallelOrchestrator

## Status: Pending

## Problem (verified: CONFIRMED)

The Coder subagent runs in an isolated worktree, captures `git diff
HEAD` as a patch, returns it in `ParallelResult.coder_patch` — and
nothing applies it. A grep for `coder_patch` consumers returns zero
outside `parallel_orchestrator.rs`. With `worktree_enabled=true`,
`/workflow run foo --parallel` reports a successful Coder change while
the user's repository is unchanged. The patch is text in a struct that
nobody reads.

Secondarily, `ParallelOrchestrator` / `run_parallel` / `ParallelResult`
are stale names — the pipeline is sequential (WO 35.1 collapsed
run_parallel/run_sequential into one pipeline). The name misleads.

## Approach

1. **Apply the patch**: after the pipeline completes, if
   `coder_patch.is_some()`, present it to the user (or auto-apply
   with an approval gate). Two modes:
   - `worktree_enabled=true` + `auto_apply_patch=false` (default):
     the TUI shows the patch summary and offers `/apply` to apply it
     to the parent workspace.
   - `worktree_enabled=true` + `auto_apply_patch=true`: the patch is
     `git apply`'d to the parent workspace automatically after the
     Reviewer phase, with the existing approval gate as backstop.
   The apply is a real `git apply` in the parent repo's CWD; failure
   (conflict, dirty tree) surfaces as an error event, not silent loss.
2. **Rename**: `ParallelOrchestrator` → `PipelineOrchestrator`,
   `run_parallel` → `run_pipeline` (the internal name already is
   `run_pipeline`), `ParallelResult` → `PipelineResult`. Update all
   call sites and tests. The public TUI command stays
   `/workflow run --parallel` (the flag means "worktree isolation",
   not "concurrent execution" — update the help text to say so).
3. **Test**: end-to-end — run a pipeline with worktree isolation,
   verify the patch is applied to the parent workspace and `git diff`
   shows the change; run with `auto_apply_patch=false`, verify the
   patch is surfaced but NOT applied; verify a conflicting dirty tree
   produces an error, not silent loss.

## Files to touch

- `src/session/parallel_orchestrator.rs` (rename + patch application)
- `src/tui/commands/workflow.rs` (consume coder_patch, apply or surface)
- `src/shared/config/session.rs` (auto_apply_patch knob)
- `config.toml.example` ([session] section)
- All call sites referencing ParallelOrchestrator/ParallelResult
- `docs/TECHNICAL.md` orchestration section

## Gate

Standard clippy (Linux + Windows cross-compile), fmt, nextest. New
tests: patch applied to parent, patch surfaced not applied, dirty-tree
conflict error. Existing pipeline sequencing tests stay green.

## Done condition

A `/workflow run --parallel` with worktree isolation either applies
the Coder's patch to the parent workspace or surfaces it for explicit
application — never silently discards it. The orchestrator name
matches its behavior.
