# WO 41.3 — Permission docs fix (undersell → accurate)

## Status: Pending

## Problem (verified: CONFIRMED — our fault, not the reviewer's)

The reviewer keeps claiming "permissions are tool-centric, not
resource-centric" because our docs describe a less-capable system
than the one that exists:

- **ADR-004** (Accepted, no amendment) describes the old ReadOnly vs
  Destructive tier model — that IS tool-centric. No amendment notes
  the `permission_rules` engine that supersedes it.
- **config.toml.example** has zero `[[permission_rules]]` examples.
  The approval knobs shown are `auto_approive` (boolean) and flat
  deny lists. Nothing shows tool+key+pattern+action.
- **TECHNICAL.md** has no Permissions section. The one mention is
  `/permissions list` (line 400). The WO 38.1 paragraph documents
  the compound-clause fix but never introduces the base model.
- **src/shared/permission.rs** module doc comment is fully accurate —
  but a reviewer reading docs, not source, never sees it.

## Approach

1. **config.toml.example**: add a `# Permission rules (allow / ask /
   deny)` section with the 3-rule example from the permission.rs doc
   comment (bash/command/cargo test* → allow; edit_file/path/src/**/*.rs
   → allow; bash/command/rm -rf ** → deny). This is the file reviewers
   and operators read first.
2. **ADR-004**: amend the "Approval tiers" section noting that
   `permission_rules` supersedes the tier as the primary gate, with
   the tier serving as the default when no rule matches. Alternatively,
   create ADR-077 "Permission Rule Engine" and supersede ADR-004.
3. **TECHNICAL.md**: add a "Permissions" subsection introducing the
   engine: four fields (tool, key, pattern, action), ordered
   first-match-wins, three actions (allow/ask/deny), `[A]lways`
   exact-match behavior, deny prefix promotion, compound-clause
   evaluation (WO 38.1), env-secret scrubbing (WO 38.1). Link to
   `src/shared/permission.rs` doc comment.

## Files to touch

- `config.toml.example` (permission_rules example block)
- `docs/adr/004-tool-use-and-execution-sandbox.md` (amendment) or
  new ADR-077
- `docs/TECHICAL.md` (Permissions section)

## Gate

`cargo test -p kf-budget-core --test adr_xref_drift` (if ADR-077
added, count + index must match). `bash scripts/check-artifact-
consistency.sh`. No code changes.

## Done condition

A reviewer reading config.toml.example, TECHNICAL.md, or ADR-004
understands the permission engine is tool+arg+glob allow/ask/deny
with ordered matching — not just ReadOnly/Destructive tiers. The
"tool-centric" claim can no longer be made in good faith from the
docs.
