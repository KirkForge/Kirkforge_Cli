# WO 42.5 — MCP .mcp.json content-based re-approval

## Status: Done

## Problem

`src/session/mcp_project.rs` persisted per-project `.mcp.json` approvals
keyed by project *path* only (WO 39.2). After initial approval, a modified
`.mcp.json` under the approved path spawned without re-gating. Attack:
anyone who can modify `.mcp.json` (a compromised dependency, a malicious
collaborator, a rogue tool) adds a malicious MCP server entry, and it
spawns silently on the next launch. The original implementation carried
a `ponytail:` deferral explicitly noting this gap.

## Approach

Store a content hash (sha256 hex of the `.mcp.json` bytes) alongside each
approved path in `approved_mcp_projects.json`. On load, `is_approved`
recomputes the hash and compares: a mismatch (or a missing stored hash
on a present file) → treat as unapproved → re-gate. `sha2` and `hex` are
already direct deps (no new dependency).

- New ledger format: `Vec<ApprovedProject>` where `ApprovedProject = {
  path, content_hash: Option<String> }`.
- Backward-compatible load: a legacy `Vec<String>` ledger is parsed
  leniently into entries with `content_hash: None`, which `is_approved`
  treats as "needs re-approval" when a file is present (safe default).
- File absent at approval time → stored `None`; file still absent at
  load → approved (nothing to spawn, no re-gate needed). File absent at
  load but a hash was stored → not approved (file was deleted; safe-fail).
- `record_approval` / `is_approved` signatures unchanged (`&Path`), so
  the sole caller in `run_session.rs` needs no change.
