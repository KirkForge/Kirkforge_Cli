# WO 43.17 — Content-hash consent binding for plugin trust

## Status: Done

## Problem

The backlog's "bundleContentHash pattern" already exists in-tree — WO 42.5 shipped it for MCP projects, not plugins: `ApprovedProject { path, content_hash }` (`src/session/mcp_project.rs:112-117`), `current_content_hash` = sha256 of `.mcp.json` (mcp_project.rs:128-135), `record_approval` stamps the hash (169-195), and `is_approved` re-gates on mismatch (200-213: `entry.content_hash.is_some_and(|h| h == current)`).

Drift note: the claim presumes plugin consent prompts exist. They do not. Plugin loading (`load_plugin_registry`, `src/session/plugin_tools/loader.rs:212-218`) loads everything under `plugins_dir()` (loader.rs:68 — `~/.local/share/kf-code/plugins`) gated only by `trust_policy_from_config` (loader.rs:80 — trust-tier cap + optional minisign signature per ADR-057). There is no approval ledger and no content binding: a plugin that passed its trust tier once stays trusted after its scripts are rewritten on disk (signature verification is opt-in via key config; when off, any edit to the bundle loads silently). WO 42.11's `content_hash` wiring is unrelated (verifier verdict cache, `src/session/verifier/handler.rs:35`).

## Root cause

The MCP approval ledger (WO 42.5) was never mirrored on the plugin load path; plugin trust is evaluated per-load from manifest metadata, not from the bytes actually on disk.

## Approach

Mirror `mcp_project.rs` 1:1 for plugins — do not invent a new format:

1. New `approved_plugins.json` ledger in the data dir: `ApprovedPlugin { name, root, content_hash }` with the same lenient-legacy read as `load_approved_projects` (mcp_project.rs:141-164).
2. `bundle_hash(plugin_root)` = sha256 over `manifest.toml` + every file the plugin declares as capabilities (command/hook/verifier scripts) — reuse the sha2 dep already in kf-code (mcp_project.rs:131).
3. In `load_plugin_registry` (loader.rs:215) and `load_one` workspace path (loader.rs:198): hash mismatch or missing entry → skip the plugin with a warning naming the approval command.
4. `record_plugin_approval(name, root)` behind a `/plugins approve <name>` TUI command (extend `src/tui/commands/plugins/`); approval stamps the current bundle hash.
5. Tests: edit a script after approval → plugin skipped; re-approve → loads; signature-verified plugins may opt out of the ledger (keep both gates independent).

## Files

- `src/session/plugin_tools/loader.rs`
- `src/session/plugin_tools/approval.rs` (new, ~120 lines mirroring mcp_project.rs)
- `src/tui/commands/plugins/mod.rs` (+ approve subcommand)

## Gate

`cargo nextest run -p kf-code --lib --locked -- plugin` + full local gate.

## Done

A plugin whose bundle content changes after approval is not loaded until re-consent; the ledger format matches the MCP one.
