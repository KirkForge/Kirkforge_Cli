# WO 43.25 — UTF-8 byte-slice panic hardening (executor + TUI streaming)

## Status: Planned

## Problem

Fresh segment audit (round 4). Three sites slice a `String` at a raw byte
offset without an `is_char_boundary` guard. When the offset lands mid-way
through a multi-byte character (non-ASCII paths, CJK logs, tool error text),
the slice expression panics. Two are on the executor task OUTSIDE the tool
`catch_unwind`, so the panic unwinds through `run_turn` and terminates the
session. The codebase already owns the correct pattern
(`truncate_tool_output`, `src/session/executor/helpers/mod.rs:213-228`,
walks `is_char_boundary`) — these three sites predate or bypass it.

1. **`DoomLoopTracker::observe`** (`src/session/executor/loop_.rs:70-77`):
   `&error[..Self::ERROR_TRUNCATE]` (200). `observe` is called via
   `cost_tracking::observe_tool_outcome` from the executor turn path
   (`turn.rs:800,904`) — production, not inside `catch_unwind`. Error text
   comes from `ToolError::Error { message }` (bash stderr / provider output),
   which can be non-ASCII. WO 43.16 covers `.expect`/panic sites but not this
   slice.

2. **`build_stream_preamble`** (`src/session/executor/stream.rs:111`):
   `format!("{} [...truncated]", &content[..cap])` — `cap` is `stem_file_cap`
   (default 4096). `content` is arbitrary UTF-8 read from repo files
   (`stream.rs:95`). Runs in `stream_iteration` on the executor task, not
   under tool `catch_unwind`. A non-ASCII char straddling the cap boundary
   panics the turn.

3. **PTY tail cut** (`src/tui/events.rs:472-484`): computes `start = total -
   PTY_TAIL_BYTES` (64KiB), then does `&last.content[start..]` (line 477)
   BEFORE the boundary-fixup `char_indices().next()` at line 478 — the fixup
   is dead code because the slice at `start` already panicked if `start` lands
   mid-character. 43.19 misclassified `events.rs:477` as "boundary-safe"; it
   is not. Any streaming tool output >64KiB with a multibyte char straddling
   the offset reaches this.

## Root cause

Byte-vs-char indexing was applied to `String`/`&str` without the codebase's
own `is_char_boundary` guard. Two sites share the truncation intent of the
existing safe helper; one (TUI) is a prior-audit misclassification.

## Approach

1. Replace all three raw slices with char-boundary-safe truncation (reuse the
   existing `truncate_tool_output` helper, or a `while !s.is_char_boundary(b)
   { b -= 1; }` walk). For stream.rs the helper already takes cap semantics.
2. Add one pinning unit test each that feeds a non-ASCII string with the cut
   point mid-character and asserts no panic + char-aligned output.

Not doing: no char-iteration rewrite of the streaming path; no panic-hook
changes (fix the source).
