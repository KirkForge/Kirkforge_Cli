# WO 43.27 — Atomic-write permission preservation + undo-ordering bug

## Status: Planned

## Problem

Fresh segment audit (round 4). Two tool-layer bugs.

1. **Atomic write clobbers target permissions** (`src/tools/atomic_write.rs:57`):
   the temp file is opened with only `write(true).create_new(true)` — no
   `.mode()`. On Unix it is created with `0666 & ~umask` (typically 0644) then
   renamed over the target. Any pre-existing target's permissions (an
   executable script at 0755, or a 0600 secrets file like `.env`) are silently
   reset to the umask default. `write_file`/`edit_file` route every overwrite
   through this, so editing an executable strips its exec bit and editing a
   0600 secret widens it to world-readable. WO 43.2 only covers EINTR retry on
   the same line; permission preservation is unaddressed.

2. **`notebook_edit` pushes an undo snapshot before the write**
   (`src/tools/notebook_edit.rs:182-196`): the `UndoKind::Write` snapshot is
   pushed BEFORE `atomic_write`. If the write fails, the undo stack still
   holds an entry for an edit that never happened; `/undo` later performs a
   no-op restoration and the stack drifts. `edit_file` (`edit_file.rs:410`) and
   `write_file` (`write_file.rs:167`) correctly push only after a successful
   write.

## Root cause

1. `OpenOptions` default (umask) mode is used instead of copying the target's
   existing mode.
2. Undo-push ordering inconsistent with the sibling file tools.

## Approach

1. `atomic_write`: when the target exists, stat it and apply the existing
   mode (`std::fs::metadata(...).permissions().mode()`) to the temp file before
   rename (Unix). Fall back to default on missing target.
2. `notebook_edit`: push the undo snapshot only after `atomic_write` succeeds
   (match `edit_file`/`write_file`).

## Files

- `src/tools/atomic_write.rs`
- `src/tools/notebook_edit.rs`

## Gate

`scripts/test-fast.sh`, `cargo clippy --all-targets -- -D warnings`,
`cargo fmt --check`. New tests: overwrite an 0755 file keeps 0755; a failed
notebook write leaves no undo entry.

## Done

Overwrites preserve target permissions; undo stack only records successful
edits.
