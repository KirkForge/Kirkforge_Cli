# WO 43.31 — Doom-loop banner renders wrong selection

## Status: Planned

## Problem

Fresh TUI audit (round 4). The doom-loop banner's render ignores the user's
arrow-key selection. The key handler (`src/tui/keys/mod.rs:139-155`) mutates
`state.doom.doom_loop_selection.index` with Left/Right and Enter executes
`doom_loop_selection.selected()`, but `render_if_active` calls
`render_doom_banner(f, area, dl, DoomLoopSelection { index: 0 })`
(`src/tui/widgets/doom_banner.rs:172`) — a fresh literal, never reading the
stored selection. The banner's highlighted action is ALWAYS "Break"
regardless of navigation, while Enter executes the hidden user-chosen action.
A user navigating to "Plan" sees "Break" highlighted but Enter runs "Plan" —
executing a different tool-approval/cancel action than displayed.

## Root cause

The render path constructs a hardcoded `DoomLoopSelection { index: 0 }`
instead of passing the selection state the key handler mutates on the same
`app_state` argument.

## Approach

Pass `app_state.doom.doom_loop_selection` into `render_doom_banner` instead
of the literal. Add a pinning render test asserting the highlighted index
matches the stored selection.

## Files

- `src/tui/widgets/doom_banner.rs`
- `src/tui/keys/mod.rs` (verify the field is read consistently)

## Gate

`scripts/test-fast.sh`, `cargo clippy --all-targets -- -D warnings`,
`cargo fmt --check`. Render test green.

## Done

The banner highlights the same doom-loop action that Enter executes.
