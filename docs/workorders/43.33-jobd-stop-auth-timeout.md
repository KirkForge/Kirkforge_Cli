# WO 43.33 — jobd stop/pid hygiene (auth + no timeout + pid removal on reject)

## Status: Planned

## Problem

Fresh segment audit (round 4). The `jobd` (`--stop`) client is broken against
an auth-enabled daemon and can delete a live daemon's pid file.

1. **No auth token** (`src/jobs/client.rs:13,24`): `send_shutdown`/`send_command`
   craft `Request::Shutdown { auth_token: None }`, while the jobd daemon's
   `check_auth` (`jobs/daemon.rs:245`) uses the same `KF_CODE_DAEMON_TOKEN_FILE`
   as the session daemon. With auth configured, every `kf-code jobd --stop` is
   rejected "authentication required".

2. **No response validation / no timeout** (`jobs/client.rs:30-37`):
   `send_command` parses the response but returns `Ok` regardless of status,
   and `read_line_limited` has no read timeout (the session-daemon client has a
   30s `READ_TIMEOUT`). A hung jobd makes `--stop` block forever.

3. **pid removed on failure** (`src/jobs/daemon.rs:344-353`):
   `stop_job_daemon` calls `send_shutdown` (which, per #2, returns Ok even on
   auth error) then unconditionally removes the pid file. A live daemon stays
   running while its pid file is deleted and the user is told the command
   succeeded; subsequent `--stop`/health checks keep failing while the pid is
   deleted each time.

## Root cause

The jobd client was written against an auth-less assumption and ignores both
the daemon's `Error` response and any read timeout; `stop_job_daemon` trusts
the client's Ok return before deleting the pid.

## Approach

1. Read the daemon token and send it (mirror the session-daemon client).
2. Add a read timeout and validate the response status before returning `Ok`.
3. Only remove the pid file when the daemon actually acknowledged the stop.

## Files

- `src/jobs/client.rs`
- `src/jobs/daemon.rs`

## Gate

`scripts/test-fast.sh`, `cargo clippy --all-targets -- -D warnings`,
`cargo fmt --check`.

## Done

`jobd --stop` authenticates, times out instead of hanging, and only removes
the pid file when the daemon actually stopped.
