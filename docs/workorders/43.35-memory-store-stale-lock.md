# WO 43.35 — kf-memory-store stale-lock latch after crash

## Status: Planned

## Problem

Fresh crates audit (round 4). `FileAdapter::acquire_lock`
(`crates/kf-memory-store/src/adapters/file.rs:115-130`) creates the lock file
with `create_new(true)` and only releases it via `LockGuard::Drop`. If the
process is SIGKILLed/crashes while holding the lock, the `.lock` file persists
on disk with no staleness detection (no PID-liveness or age check). Every
subsequent write/read re-enters the retry loop and times out after 3s
(`started.elapsed() >= timeout`, `:127`), returning an error permanently — the
adapter becomes unusable with no self-heal.

## Root cause

The lock file is treated as advisory-only within the process's lifetime but
persists across crashes with no staleness/recovery.

## Approach

Add staleness detection: on `AlreadyExists`, read the PID from the lock file;
if the PID is no longer alive (or the file is older than a threshold), remove
the stale lock and retry. Mirror the `git` index-lock pattern. Add a pinning
test that writes a stale PID, re-acquires, and confirms the lock is taken over.

## Files

- `crates/kf-memory-store/src/adapters/file.rs`

## Gate

`cargo test -p kf-memory-store`, `cargo clippy --all-targets -- -D warnings`,
`cargo fmt --check`. New stale-lock test green.

## Done

A crashed writer's `.lock` is reclaimed; the store self-heals instead of
latching permanently.
