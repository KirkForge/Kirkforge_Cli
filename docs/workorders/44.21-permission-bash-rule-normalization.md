# WO 44.21 — Permission bash rules match raw text: whitespace/quote evasion of deny rules

## Status: Planned

## Problem

The bash-command permission matchers run globs against the RAW clause text.
`deny_command_matches` (src/shared/permission.rs:250-265) does glob +
prefix matching on un-normalized clauses from `split_compound_clauses`
(which trims clause ends only — bash_safety.rs:377-379), and
`allow_command_matches` (permission.rs:275-281) likewise. The only
normalization applied is `normalize_command_pattern` (permission.rs:291),
which rewrites `*`→`**` in the PATTERN — nothing normalizes the VALUE.

The codebase already has the right tool: `normalize_for_safety`
(src/shared/bash_safety.rs:106-147) collapses whitespace runs, strips
single/double quotes and backslash escapes, and lowercases — and the
safety gate uses it. The permission layer does not.

Verified bypasses of a user-written deny rule `rm -rf /` (documented and
unit-tested as prefix-blocking at permission.rs:798-845 — but only ever
tested with single-space, unquoted, lowercase inputs):

- `rm  -rf  /home/user` (double spaces): glob fails (pattern has single
  spaces), prefix `starts_with("rm -rf /")` fails.
- `rm "-rf" /home/user` (quoted flag): quote bytes break the literal match.
- `RM -RF /home/user`: no case folding.

The downstream safety gate does not backstop these: `check_bash_command_str`
normalizes and would catch `rm -rf /` (exact), but `rm -rf /home/user` is
not in `DANGEROUS_SHELL_COMMANDS` and passes the gate by design — the
user's deny rule was the only line of defense. Deny rules are the
user-authored security boundary (`action = "deny"` refuses without asking);
trivial quoting/spacing defeats them.

## Root cause

WO 38.1 added clause-splitting and `*`→`**` promotion to the permission
matchers but reused raw clause text; the normalization helper that the
safety gate already depends on was not applied on the value side.

## Approach

1. In `deny_command_matches` and `allow_command_matches`, run each clause
   through `normalize_for_safety` before glob/prefix matching (export it
   `pub(crate)` from bash_safety — it is currently private).
2. Lowercase the pattern for the deny prefix comparison to match the
   lowercased clause (glob patterns stay case-sensitive: patterns are
   config-authored, values are now lowercased — document that command
   rules match case-insensitively).
3. Keep the fail-closed property: normalization makes MORE commands match
   (both allow and deny side) — for deny that closes the bypasses above;
   for allow it matches user intent (`git "status"` under `git status`).
   Compound-splitting still runs first, so chained payloads stay blocked.
4. Tests: the three bypass strings above must be denied by
   `rm -rf /`; tab-separated variant; `git  status` must match an allow
   rule `git status` (previously silently fell to Ask).
5. `ponytail:` ceiling: `normalize_for_safety` is a dangerous-command
   preprocessor (strips quotes, collapses whitespace, lowercases), not a
   shell lexer. It is sound for deny/allow VALUE matching because the
   command verb stays the first token (`echo "git status"` normalizes to
   `echo git status` which does NOT match a deny `git status` — prefix
   mismatch). The upgrade path is argv-tokenization (shell lexer →
   structured argv → permission matcher compares argv, not raw text);
   defer until a bypass survives quote-aware normalization. Document
   this ceiling in a comment at the call site.
