# WO 44.24 — Audit scrubber misses github_pat_/glpat-/AIza/ya29 token literals

## Status: Planned

## Problem

`scrub_free_text` (WO 43.3) redacts credential-shaped `NAME=value` pairs
and a fixed set of token literals (src/shared/audit.rs:1006-1012):

```
Bearer\s+[A-Za-z0-9_\-\.=]+ | sk-[A-Za-z0-9_\-]+ | ghp_[A-Za-z0-9]+ |
AKIA[0-9A-Z]+ | xox[bp]-[A-Za-z0-9\-]+
```

Four common token shapes are absent, so bare occurrences survive into
`audit.ndjson` via the three free-text fields that reach the scrubber
(bash `command` at audit.rs:943-949, plugin `args_summary` at :111, hook
`reason` at :96):

- `github_pat_[A-Za-z0-9_]+` — GitHub fine-grained PATs (only classic
  `ghp_` is matched; the existing test at audit.rs:1291 pins `ghp_` only)
- `glpat-[A-Za-z0-9\-_]{20,}` — GitLab PATs
- `AIza[0-9A-Za-z_\-]{35}` — Google API keys
- `ya29\.[A-Za-z0-9_\-]+` — Google OAuth access tokens (the existing
  test at audit.rs:1287 passes only because that sample sits behind a
  `Bearer ` prefix; a bare `ya29.` literal is not matched)

The audit log is the persistent forensic record (survives the session,
per-entry fsync); a fine-grained GitHub PAT echoed into a hook reason or
bash command line today lands on disk in cleartext.

## Root cause

The literal list in WO 43.3 was transcribed from the most common shapes
in the original incident; the provider coverage was never completed and
the tests only exercise the shapes that are covered.

## Approach

1. Extend the `literals` alternation in `scrubber()` (audit.rs:1011) with
   the four shapes above. Keep alternation ordering safe (the regex is a
   single alternation; no lookarounds needed since these prefixes are
   distinct from `sk-`/`ghp_`).
2. Tests: each new shape, BARE (no `Bearer` prefix, no `NAME=`), must
   vanish from `scrub_free_text` output and produce `[REDACTED]`; a
   non-token `AIzaphenia` style false-positive check (`AIza` + short
   suffix should NOT be redacted — keep the 35-char length quantifier).
