# WO 44.30 — `max_tool_result_chars` never applies to file tools (read_file can flood the context)

## Status: Planned

## Problem
`truncate_tool_output` (`src/session/executor/helpers/mod.rs:213-238`) only truncates
`ToolOutcome::Success`; every other variant hits `other => other` and passes through
untouched. It is also only called on the **non-file** branch of
`Executor::record_tool_result` (`src/session/executor/turn.rs:874-883`). The file-tool
branch (`src/session/executor/turn.rs:619-857`) never calls it.

Consequences, with the default `max_tool_result_chars = 4000`
(`src/shared/config/tools.rs:23-25`):

1. `read_file` returns `ToolOutcome::FileContent` (`src/tools/read_file.rs:186-190`) with a
   model-controlled `limit` (default 200, unbounded above; `read_file.rs:72`,
   `end = min(offset+limit, raw_total)` at `:98`). `read_file(path="huge.log",
   limit=500000)` appends the entire file to the conversation via
   `handle_tool_outcome` (`src/session/executor/helpers/outcome.rs:59-79`, no cap) — a
   single call can inject tens of MB into the context regardless of the configured cap.
   Auto-minify only strips comments/whitespace (`read_file.rs:126-134`) — a log or data
   file minifies to nearly itself, so it does not bound this.
2. `GrepMatches` output likewise bypasses truncation (`other => other` in
   `truncate_tool_output`).
3. The only other guard, `apply_budget_slice`, slices `FileContent` solely when the budget
   state is `Approaching`/`Over` (`src/session/budget.rs:256-258`) and requires the
   `budget` feature — so with a healthy budget the result is unconditionally unbounded.

Net: the documented always-on knob (`max_tool_result_chars`) is a no-op for the tool most
capable of returning megabytes, and one oversized read can blow the provider context
window (turn-fatal error) before compaction triggers.

## Root cause
`truncate_tool_output` predates the structured outcome variants (`FileContent`,
`GrepMatches`, `FileEdit`, `Image`) and was never extended to reduce them to their text
projection; the file-tool recording branch in `record_tool_result` was split off (Phase 3)
without inheriting the truncation call the non-file branch kept.

## Approach
1. In `truncate_tool_output` (`src/session/executor/helpers/mod.rs:213`), handle
   `FileContent` (truncate `content`, force `truncated: true` when cut) and `GrepMatches`
   (truncate the rendered output) using the existing char-boundary-safe slicing. Leave
   `FileEdit`/`Image`/errors as passthrough (diffs and base64 have their own caps).
2. Call `truncate_tool_output` on the file-tool branch of `record_tool_result`
   (`src/session/executor/turn.rs`, before the budget slice at :787-796, mirroring the
   ordering — extract metrics/truncate before emit) so file and non-file tools share one
   cap path.
3. Unit tests in `src/session/executor/helpers/mod.rs` tests: `FileContent` over the cap is
   truncated with `truncated: true`; `GrepMatches` rendered output truncated; short
   content untouched.
4. CHANGELOG one-liner.
