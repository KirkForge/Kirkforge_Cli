# WO 44.31 — Budget guard compares result bytes against the token budget (unit mismatch)

## Status: Planned

## Problem
`check_and_slice` (`src/session/budget.rs:176-224`) treats `budget.remaining()` as a byte
quantity, but the budget is denominated in tokens:

- `TokenBudget` `used`/`ceiling` are token counts — `crates/kf-budget-core/src/budget.rs:91`
  ("ponytail: used/ceiling are token counts"), recorded via
  `budget.record(count_tokens(result))` in `record_tool_usage`
  (`src/session/budget.rs:777-812`, `count_tokens` at :785).
- The guard compares `result.len()` (**bytes**) against `remaining()` (**tokens**)
  (`src/session/budget.rs:186`), then derives the slice sizes from the same mixed units:
  `head = remaining / 2`, `tail = remaining - head` (`:193-194`) feed
  `HeadTailSlicer { head_bytes, tail_bytes }` (`:195-198`) — token counts used as byte
  budgets.

For English source/JSON (~4 bytes/token) this fires slicing ~4× too early: once the state
is `Approaching`/`Over`, any result whose **byte** length exceeds the remaining **token**
count gets sliced even though its token cost is only ~a quarter of the headroom, and the
kept head+tail occupy at most `remaining` bytes ≈ `remaining/4` tokens — the guard never
uses more than ~25% of the actual remaining budget before slicing. The model loses tool
output (offloaded middle + `[output sliced]` markers) far sooner than the configured
ceiling requires. For CJK-heavy content the distortion is ~2-3×.

There is no comment claiming the 1-byte≈1-token equivalence is deliberate; the doc at
`:169-170` says "oversized relative to `budget.remaining()`", i.e. the author believed the
units matched.

## Root cause
The session-side guard was written against `HeadTailSlicer`'s byte-based API
(`head_bytes`/`tail_bytes`) and fed it the token-denominated `remaining()` without a
unit conversion; the producer (`record`) and consumer (`check_and_slice`) of the budget
have never agreed on units.

## Approach
1. Convert once at the boundary in `check_and_slice` (`src/session/budget.rs:186-198`):
   compute the result's token cost with `crate::session::prompt::count_tokens(result)`
   (same estimator `record_tool_usage` uses) and compare that against `remaining()`;
   derive `head_bytes`/`tail_bytes` by splitting `remaining() * BYTES_PER_TOKEN` (or by
   slicing on token count and converting the halves) — the slicer stays byte-based, only
   the budget numbers fed to it change.
2. Keep the existing fail-open behaviors (`slicer error → Keep`, `display.len() >=
   result.len() → Keep`) unchanged.
3. Unit tests: budget with ceiling/used such that `remaining()` = R tokens; a result of
   R tokens but 4R bytes must `Keep` (today it slices); a result of 2R tokens must slice
   with head+tail bounded by the byte conversion.
4. CHANGELOG one-liner.
