# WO 44.37 — Scheduled-job completion poll does blocking disk I/O (chmod + full dir walk) on every event-loop iteration

## Status: Planned

## Problem

`notify_completed_scheduled_jobs` runs a complete synchronous walk of the
jobs directory on **every** iteration of the TUI event loop — at least 8×/s
at idle (125 ms slow-tick, `src/tui/mod.rs:673-674`) and once per streamed
token/key event while busy (`src/tui/mod.rs:904-947` wakes the loop per
event).

- `src/tui/mod.rs:1002-1007` — both job-notification polls are awaited
  unconditionally each iteration.
- `src/tui/commands/jobs.rs:701-706` — `notify_completed_scheduled_jobs`
  calls `job_store()` per invocation.
- `src/tui/commands/jobs.rs:133-138` — `job_store()` builds a `JobStore`
  and calls `ensure_root()`.
- `src/jobs/store.rs:39-53` — `ensure_root()` runs `fs::set_permissions`
  **unconditionally**, even when the root already exists — a chmod(2) per
  call — plus `create_dir_all` when missing.
- `src/jobs/store.rs:122-134` — `list()` does `fs::read_dir` plus a full
  `fs::read` + `serde_json` parse of every job's `job.json`.

All of it is synchronous `std::fs` on the tokio worker that drives the
render loop and input dispatch. With K scheduled jobs that is
8×(1 chmod + 1 read_dir + K reads + K JSON parses) per second for the
whole session lifetime, even sitting idle; on a slow filesystem (NFS
home) each poll stalls rendering and keystroke latency. Under WO 44.36's
closed-channel spin the same call runs at spin rate — thousands of walks
per second.

The poll is also redundant with the existing push path: jobd pushes
`NotifyJobsChanged` after runs (`src/jobs/daemon.rs:195`) → session daemon
broadcasts (`src/daemon/server.rs:436-446`) → the TUI reader sets
`jobs_dirty` (`src/tui/daemon_events.rs:106-109`) → the loop already
refreshes on that flag (`src/tui/mod.rs:996-1001`).

(`notify_completed_jobs` above it only touches the in-memory bash-job
registry — cheap; leave it.)

## Root cause

The completion-notification poll predates the daemon push path and was
never rate-limited: it executes at event-loop rate instead of a slow
interval, and `ensure_root`'s permission fixup was written as an
every-call invariant rather than a create-time one.

## Approach

1. Throttle: keep a `last_scheduled_poll: std::time::Instant` in
   `run_event_loop` (or on `AppState`), skip
   `notify_completed_scheduled_jobs` unless ≥1 s has elapsed; always run
   once on the first iteration. Extract the decision as a pure helper
   (`should_poll(last, now) -> bool`) so it is unit-testable.
2. `ensure_root`: move the `set_permissions` call inside the
   `!self.root.exists()` branch so the chmod happens only on creation.
3. No `spawn_blocking` needed once throttled (1 Hz of a small dir walk is
   fine) — ponytail ceiling: if job counts grow large, move the poll to
   `spawn_blocking`.
