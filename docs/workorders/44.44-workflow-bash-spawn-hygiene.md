# WO 44.44 — Workflow/jobd bash spawns skip env scrub, PATH pin, output cap, process-group kill

## Status: Done

## Problem

`run_bounded_bash` (`src/tools/workflow.rs:247-279`) is a fourth bash spawn path
that never inherited the hardening the foreground/background/PTY paths have:

1. **No secret scrub.** The child inherits the full parent environment. The
   contract comment in `src/session/bash_runner/mod.rs:602-608` says
   `scrub_secrets_from_child_env` is "Applied on EVERY bash spawn path:
   foreground (`run_shell_with_token`), background (`BashJobRegistry::spawn`),
   and the PTY path" — it enumerates three paths; the workflow path is a fourth
   that does not apply it (`workflow.rs:248-253` builds the `Command` with no
   `.env_remove()`). A workflow bash step (template-authored, or command text
   interpolated from `vars` via `interpolate_vars` at `workflow.rs:182-186`)
   can read `ANTHROPIC_API_KEY`/`*_TOKEN` etc. even though the same command
   through the `bash` tool could not. The deny gate (`check_bash_command_str`,
   `workflow.rs:316-324` and `:418-426`) is a command-shape gate, not an env
   gate — `echo "$ANTHROPIC_API_KEY"` is not denied by shape.
2. **No PATH pin.** Foreground bash sets `.env("PATH", model_command_path())`
   (`bash_runner/mod.rs:664`); workflow bash inherits the ambient PATH, so a
   writable cwd earlier in PATH can shadow binaries for these steps.
3. **Unbounded output buffering.** `child.wait_with_output()` (`workflow.rs:258`)
   buffers stdout+stderr in memory with no `MAX_BASH_OUTPUT_BYTES` cap
   (`bash_runner/mod.rs` caps at 1 MiB/stream via `drain_capped`). A step like
   `cat big.bin | base64` or 30 s of `yes` buffers until the step timeout
   kills it — memory exhaustion — and if it *finishes*, the whole blob is
    returned as the step summary into the model context.
4. **Windows: the timeout path hangs the caller entirely.** The WO 43.26
    regression test `run_bash_stuck_step_times_out` never resolves on
    Windows CI — not even its own inner 45s `tokio::time::timeout` fires;
    `tokio::process` + `kill_on_drop` on an msys `sh` tree leaves the
    grandchild holding the pipes (no process-group kill on Windows), and
    the whole test future deadlocks. The test is `#[cfg(unix)]`-gated
    with a disclosure comment until this item lands a Windows-safe kill
    strategy (Job Objects are the native primitive); un-gate the test as
    part of the fix.
4. **No process group.** `kill_on_drop(true)` kills only the direct `sh`
   child. `sh -c "a; b"` grandchildren (the PDEATHSIG/orphan concern from
   43.18/43.23) survive the timeout kill. Foreground bash uses
   `setup_process_group`/`kill_process_group` (`bash_runner/mod.rs:667,738`).
5. **No workdir.** The spawn has no `.current_dir()`; steps run in the process
   CWD. For the TUI that is the project root, but for `jobd` (scheduled jobs)
   it is the *daemon's* CWD (`src/jobs/runner.rs:242-250` reuses
   `TaskSpawnerStepRunner`, so jobd workflow bash steps are affected by all
   five items).

WO 43.26 fixed only the hang class (timeout + cancel select + `kill_on_drop`)
for this path; it did not touch env/PATH/cap/process-group.

## Root cause

The graceful-spawn pattern was reimplemented per-path instead of reused:
`run_bounded_bash` duplicates `run_shell_with_token`'s skeleton without its
`scrub_secrets_from_child_env` / `model_command_path` / `CappedReader` /
process-group layers, and 43.26's fix layered the timeout on the duplicate.

## Approach

1. In `run_bounded_bash`, replace the hand-rolled `wait_with_output` select
   with a call to `run_shell_with_token`
   (`src/session/bash_runner/mod.rs:649`) — it already has token select,
   timeout, kill-on-timeout, capped drains, env scrub, PATH pin, and process
   group. Keep `WORKFLOW_BASH_TIMEOUT_SECS` as the `timeout_secs` and the
   workflow cancel token as the `token`; pass the resolved project/daemon
   workdir explicitly.
2. If full reuse is awkward (return shape), minimally: apply
   `scrub_secrets_from_child_env` + `model_command_path()` +
   `setup_process_group` + drain through `drain_capped`
   (all already `pub(crate)`), and kill via `kill_process_group` on
   timeout/cancel.
3. Pinning tests: (a) a workflow bash step `sh -c 'echo $KF_TEST_SECRET'`
   returns empty when the parent env sets it; (b) a step dumping >1 MiB sees
   the truncation marker, not the full blob.

## Done

All 4 defects fixed in `run_bounded_bash` (`src/tools/workflow.rs`). The
function now reuses the hardened primitives from `bash_runner/mod.rs` and
`process_group.rs` instead of duplicating the foreground bash skeleton.

1. **Secret scrub** — `scrub_secrets_from_child_env(&mut cmd)` called on
   the `Command` before spawn (`workflow.rs:272`), same call the
   foreground/background/PTY paths make. The child no longer inherits
   `ANTHROPIC_API_KEY`/`*_TOKEN` etc.
2. **PATH pin** — `.env("PATH", model_command_path())` (`workflow.rs:271`).
   `model_command_path` widened from private to `pub(crate)` in
   `bash_runner/mod.rs:461` so the workflow path can reach it (single
   helper, no duplication).
3. **Unbounded output** — `wait_with_output()` replaced with
   `drain_capped(stdout/stderr, MAX_BASH_OUTPUT_BYTES)` + `cap_to_string`
   (the same 1 MiB/stream cap the foreground path uses). A stuck `cat
   big.bin | base64` now hits the cap, gets the `[...truncated: N bytes
   omitted...]` marker, and does not OOM. Added `join_drain` helper
   (5 lines, bounded by a 5s join timeout) to await the drain tasks.
4. **Windows: timeout hangs the caller** — added a Windows Job Object
   helper (`process_group.rs:107-193`): `JobGuard` wraps the child in a
   job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so dropping the guard
   on timeout/cancel kills the entire process tree (the grandchild
   holding the pipes). `assign_child_to_job(&child)` is called right
   after spawn (`workflow.rs:285`); the guard drops at the end of the
   timeout/cancel arm. Unix keeps using `setup_process_group` +
   `kill_process_group` (killpg). `windows-sys` added target-gated to
   kf-code's `Cargo.toml` (`[target.'cfg(windows)'.dependencies]`,
   features `Win32_Foundation` + `Win32_System_JobObjects` +
   `Win32_System_Threading`) — already in the lock graph via
   kf-memory-store, zero Linux size impact. The
   `run_bash_stuck_step_times_out` test is un-gated (was `#[cfg(unix)]`)
   and now passes on both platforms.

The `BashOutcome::Output` variant changed from carrying a
`std::process::Output` (with `Vec<u8>` streams) to a struct with
`stdout: String`, `stderr: String`, `status: ExitStatus` (the strings
are already decoded + capped via `cap_to_string`). Two call sites
(`run_bash`, `run_batch`) updated to destructure the named fields.
