# WO 44.45 — Workflow engine error/budget semantics: unguarded eval_condition, dead on_exceeded route, batch-error mislabels siblings

## Status: Planned

## Problem

Three verified defects in the `kf-workflow` engine (`crates/kf-workflow/src/lib.rs`):

1. **`eval_condition` is an unguarded spawn** (`lib.rs:532-542`): runs
   `tokio::process::Command::new("sh").arg("-c").arg(condition).status()`
   with NO timeout, NO `kill_on_drop`, no cancel select — the exact class
   WO 43.26 fixed for step bash, missed here because conditions are a
   separate spawn site. A template with `"condition": "sleep infinity"` (or a
   condition invoking a hung binary) wedges `workflow_run` until the
   executor's outer tool timeout; it is called per ready step at `lib.rs:908`
   before every batch. It also bypasses `check_bash_command_str` entirely —
   the only `sh -c` in the workflow path with no deny gate.

2. **`budget.on_exceeded` routing is dead** (`lib.rs:547-598`): `check_budget`
   inserts a synthetic `StepOutput` for the `on_exceeded` step, then
   immediately `bail!`s (`lib.rs:573,594`). `run()` propagates via `?`
   (`lib.rs:878-886`), so `WorkflowSummary` — the only structure carrying
   `outputs` — is dropped and the caller (`src/tools/workflow.rs:160-127`)
   surfaces only `workflow 'x' failed: workflow budget exceeded`. The
   configured handler output never reaches the model; the feature is a no-op
   that costs validation code (`lib.rs:242-248`) and template faith.

3. **Batch-error handling drops sibling results and mislabels successful
   steps** (`lib.rs:784-849` + `src/tools/workflow.rs:517-523`): the parallel
   `run_batch` implementation collects via `out.push(h.await…??)` — the first
   error returns early, dropping the remaining `JoinHandle`s. Those detached
   subagent tasks keep running (LLM turns, token spend) with results
   discarded. Then `handle_batch_error` inserts `"step failed: {error}"` for
   EVERY task in the batch (`lib.rs:802-822`) — including steps that were
   still running or already succeeded — so downstream steps and the final
   summary attribute one step's error to its siblings. Note the routed
   `on_error` handler step is also marked completed with a canned output
   without ever executing (`lib.rs:824-847`) — if "route to" is meant to run
   the handler, that is part of the same defect.

## Root cause

Error paths grew as afterthoughts around the happy-path scheduler: condition
evaluation predates the 43.26 hardening sweep and was never in its scope;
budget routing was written to insert outputs into a map that the subsequent
`bail!` makes unreachable; batch error handling assumes all-or-nothing
failure in an executor that fans out independent steps.

## Approach

1. `eval_condition`: bound with the workflow step timeout (or a small fixed
   wall), add `kill_on_drop(true)`, and treat a condition timeout as
   `false` (skip) + warning rather than a hang. Route the condition string
   through the same deny gate the runner applies to bash steps (needs a
   runner hook or moving condition eval into `StepRunner`).
2. Budget: on exceed, either (a) return `Ok(WorkflowSummary)` including the
   `on_exceeded` output plus a `budget_exceeded` flag, or (b) keep the bail
   and delete `on_exceeded` from the schema + validation. Pick (a) — the
   field is documented behavior.
3. `run_batch` (src/tools/workflow.rs): join ALL handles, partition
   ok/err, return per-step results; `handle_batch_error` marks only the
   actually-failed steps and preserves succeeded siblings' outputs.
4. Pinning tests: condition `sleep infinity` resolves within the bound;
   budget workflow with `on_exceeded` surfaces the handler output; batch of
   [ok, fail, ok] keeps both ok summaries.
