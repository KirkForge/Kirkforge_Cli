# WO 44.47 — bench verify_task runs unbounded, blocking sh -c with no timeout

## Status: Done

## Problem

`kf_bench::verify_task` (`crates/kf-bench/src/lib.rs:171-210`) runs the task's
verify command via synchronous `std::process::Command::status()` for BOTH
`VerifySpec::TestPasses` (line 185) and `VerifySpec::CommandExitsZero`
(line 206) with no timeout. It is invoked inline from the async bench flow
(`src/session/bench.rs:52-56`) after the (properly timeout-bounded) agent run
(`bench.rs:232-253`). Two failure modes:

1. A verify command that hangs — e.g. `cargo test` whose test binary wedges,
   which is exactly the failure shape this repo's own nextest profiles
   (`ci-fast` 30s slow-timeout, `state.md` "Known flakes") exist to bound —
   blocks `bench run` / the `bench-pr-delta` CI job forever (until the job's
   outer runner timeout, typically 10+ minutes of dead CI).
2. The synchronous `status()` call blocks the tokio worker thread it is
   called on (async-blocking class, WO 43.18's sweep covered tool paths, not
   the bench harness).

Note `VerifySpec::TestPasses` also silently nulls stdout/stderr, so a hung
verify produces no diagnostics at all when it is eventually killed by
external timeout.

## Root cause

The agent-run half of the bench loop got the timeout treatment
(`bench.rs:233`); the verify half predates it and was never included — the
asymmetry is visible in the same file.

## Approach

1. In `crates/kf-bench/src/lib.rs`, switch both arms to
   `tokio::process::Command` with `kill_on_drop(true)`, wrapped in
   `tokio::time::timeout(VERIFY_TIMEOUT_SECS)` (suggest 120s — generous vs
   the nextest `ci-full` 60s per-test budget). On timeout return
   `Ok(false)` is wrong for diagnostics — return an error or log the
   timeout, then treat as failure; keep the boolean contract by logging
   `tracing::warn!` and returning `Ok(false)`.
2. Make `verify_task` async (crate already depends on tokio? if not, it is
   dev-dep only — then instead wrap the sync call at the bench.rs call site
   in `tokio::task::spawn_blocking` + `tokio::time::timeout`, zero new deps).
3. Test: a task whose verify command is `sleep 300` resolves within the
   bound and scores `success=false` (with the timeout logged), using the
   call-site wrapper.

## Done

The async bench flow's verify half is now bounded. `src/session/bench.rs`
gains a `verify_task_bounded` async helper that spawns the verify command
via `tokio::process::Command` with `kill_on_drop(true)` and wraps `child.wait()`
in `tokio::time::timeout(VERIFY_TIMEOUT_SECS)` (120s — generous vs the nextest
`ci-full` 60s per-test budget). On timeout the child is dropped, `kill_on_drop`
reaps it, and the function logs a `tracing::warn!` and returns `false` (a
stuck verify is a verify failure with a clear diagnostic, not a hung bench
loop). `FileContains` has no subprocess and bypasses the bound, delegating
to the sync `kf_bench::verify_task`.

`collect_turn_metrics` gains an optional `precomputed_verify: Option<bool>`
parameter so the async caller (`run_task`) runs the bounded verify before
calling the pure metrics helper and passes the result through. `None`
falls back to the inline sync `verify_task` (preserves all 14 existing
unit tests unchanged). `run_task` calls `verify_task_bounded` only when
`run_error.is_none()` (a failed agent run skips verify, as before).

Why `tokio::process` + `kill_on_drop` rather than `spawn_blocking` +
`std::process` (the WO's alternative): a `spawn_blocking` thread cannot be
cancelled on timeout — dropping the `JoinHandle` does not kill the blocked
thread, so a stuck `sh -c` would outlive the timeout and block tokio
runtime shutdown (the `#[tokio::test]` harness hangs waiting for the
blocking pool to drain). `tokio::process::Command::kill_on_drop` actually
reaps the child. This matches the WO 43.26 workflow-bash pattern
(`src/tools/workflow.rs:248 run_bounded_bash`) exactly.

`kf_bench::verify_task` (crates/kf-bench/src/lib.rs) is unchanged — no new
tokio dependency on the size-optimized kf-bench crate, no signature change
to its 24 upstream dependents (HIGH impact avoided).

Tests:
- `verify_task_bounded_treats_stuck_command_as_failure`: a task whose
  verify is `sleep 300` resolves in ~2s (test timeout) and scores `false`.
  Confirms `kill_on_drop` reaps the child — the test process exits cleanly.
- `verify_task_bounded_passes_through_success`: a `true` verify returns
  `true`.

Deferred: `handle_bench_verify_only` (src/main/handle_bench.rs:256) calls
`kf_bench::verify_only` → `verify_task` synchronously. This is the
interactive CLI subcommand (`bench verify-only`), operator-facing, NOT the
async CI bench job. Not named in the WO Files list. If the CI bench job
ever runs `bench verify-only` unattended, that path needs the same bound.
Tracked here (WO 44.47); no follow-up WO filed because the unattended path
is not current practice.
