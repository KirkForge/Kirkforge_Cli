# WO 45.10 — Event Type Audit (external reviewer claim)

## Status: Planned

## Problem

An external reviewer claimed:
> "KirkForge's EventBus uses a generic `Event { kind: String,
> value: Option<Value> }` — untyped. Codex has typed
> `ItemStarted/ItemCompleted/TurnCompleted` etc. KirkForge should move
> to a typed enum `AgentEvent`."

This audit verifies the claim against the actual code.

## Verdict: PARTIALLY CONFIRMED (the kernel is real; the framing is wrong)

### Evidence — three event systems coexist, only one is string-discriminated

1. **`EventBus` + `Event` — genuinely string-discriminated (the claim's
   target).** `src/shared/event_bus.rs:67`:
   ```rust
   pub struct Event {
       pub kind: String,
       pub schema_version: String,
       pub sequence: u64,
       pub stream_id: String,
       pub timestamp: String,
       pub value: Option<serde_json::Value>,
   }
   ```
   Subscribers register by string kind (`bus.on("verify.lint", ...)`).
   This is a faithful port of the TS `@kirkforge/core-events` `EventBus`
   (module doc line 1). It carries `artifact.*` events (bridged in by
   `EventBusSink`, `src/session/event_sink_bridge.rs:74-80`) and any
   other producer that wants the TS-shape idempotent pub/sub. **This is
   the only untyped event path.** ADR-006 (`docs/adr/006-event-bus.md`)
   documents it as "A typed event bus" in its Decision heading but the
   shipped `Event` struct is string-discriminated (the ADR's typed shape
   was the *verifier* bus, not this generic bus — see point 3).

2. **`TurnEvent` — already a typed enum with 21 variants.**
   `src/session/executor/types.rs:36`:
   ```rust
   pub enum TurnEvent {
       Token(String), Thinking(String),
       ToolStart { name, args }, ToolResult { name, output, success },
       Error(String), Verification { ... },
       CostStats { ... }, CacheStats { ... },
       CompactionReport { ... }, PlanComplete, Recovered { ... },
       PullProgress { ... }, DoomLoopDetected { ... },
       DoomLoopRemediation { ... }, ContinuationRound { ... },
       BashPartialOutput(String), MemoryExtracted { ... },
       TurnComplete,
   }
   ```
   This is the **primary executor→TUI event path**, sent over a typed
   `mpsc` channel (`event_tx`) and consumed by
   `emit_turn_events` (`src/main/turn_events.rs:26`) and
   `dispatch_turn_event` (`src/tui/events.rs`). It is already the typed
   `AgentEvent`-equivalent the reviewer asks for. `ToolStart`/`ToolResult`
   are the `ItemStarted`/`ItemCompleted` analogues; `TurnComplete` is the
   `TurnCompleted` analogue. The reviewer appears to be looking only at
   the TS-ported `EventBus` and missed this.

3. **`BusEvent` + `EventKind` — already a typed enum for tool/verifier
   events.** `src/session/verifier/types.rs:267` + `:91`:
   ```rust
   pub enum BusEvent {
       FileRead(FileReadEvent), FileWrite(FileWriteEvent),
       Edit(EditEvent), BashExec(BashExecEvent),
       LintRun(LintRunEvent), TypeCheck(TypeCheckEvent),
       SecurityScan(SecurityScanEvent), ToolError(ToolErrorEvent),
   }
   pub enum EventKind { FileRead, FileWrite, Edit, BashExec, ... }
   ```
   Verifiers receive `&BusEvent` (typed) via the `Verifier` trait
   (`types.rs:420`). This is the system ADR-006's "typed event bus"
   heading refers to — NOT the generic `EventBus`. WO 9.6 (Done)
   documents the deliberate non-unification of the Rust verifier bus
   from the TS orchestrator bus.

4. **`StreamEvent` — typed enum for adapter→executor streaming.**
   `src/shared/mod.rs:158`:
   ```rust
   pub enum StreamEvent { Text(String), Thinking(String),
       ToolCall(ToolInvocation), Error(String),
       Done { finish_reason: FinishReason, usage: Option<TokenUsage> } }
   ```

### `started → progress* → terminal` lifecycle

- **Implicit, not formal.** There is no enum `TurnState` or enforced
  state machine. `TurnComplete` is emitted "exactly once on every Ok
  exit path from `run_turn_inner`" (`src/session/executor/turn.rs:90`,
  also `loop_.rs:573`) and the TUI treats it as terminal
  (`src/tui/events.rs:511`). But this is a per-path convention, not a
  type-level guarantee — `Error` can repeat mid-turn and nothing
  statically forbids emitting `TurnComplete` twice. The lifecycle holds
  *in practice* (test `tests/turn.rs:311` asserts `TurnComplete` fires
  after mid-stream cancel) but is not encoded in the type system.
- A formal `TurnState` enum (`Started | Streaming | Complete`) tracked
  in the executor would make the lifecycle enforceable rather than
  conventional — but this is a separate, smaller concern than the
  reviewer's framing.

### Root cause

The reviewer looked at one event system (the TS-ported `EventBus`,
`src/shared/event_bus.rs`) and generalized it to "KirkForge's EventBus"
as if it were the only one. KirkForge has **four** event surfaces
(`EventBus`, `TurnEvent`, `BusEvent`, `StreamEvent`) and three are
already typed enums. The genuine residual gap is narrow: the
`EventBus`'s `Event` struct is string-discriminated because it
deliberately mirrors the TS `@kirkforge/core-events` shape (module doc
line 1, ADR-006) for cross-language artifact events.

## Approach (if pursued)

1. Decide whether the `EventBus` `Event` should gain a typed `enum
   BusEventKind` wrapper (typed at the Rust boundary, string-serialized
   at the TS-interop boundary) OR stay string-discriminated by design
   (the TS-port fidelity may be load-bearing for the `artifact.*`
   bridge — WO 36.6).
2. If typed: add `pub enum BusEventKind { ArtifactEmitted,
   ArtifactBlocked, ArtifactUnterminated, ArtifactTruncated, VerifierLint,
   VerifierTypes, ... }` to `src/shared/event_bus.rs`, change
   `Event.kind` to `BusEventKind`, keep `to_string()` for the TS
   serialization path. Update `EventBusSink` (`event_sink_bridge.rs:74`)
   to construct the typed variant instead of `kind.to_string()`.
3. The `TurnEvent` and `BusEvent` paths need **no change** — they are
   already typed. The reviewer's `ItemStarted/ItemCompleted/TurnCompleted`
   already exist as `ToolStart`/`ToolResult`/`TurnComplete`.
4. A formal `TurnState` lifecycle (optional, separate concern):
   `src/session/executor/turn.rs` tracks turn progress implicitly; a
   `TurnState` enum would make the `started → progress* → terminal`
   invariant type-enforced rather than conventional.

## Rejected candidates

- **"KirkForge should move to a typed enum `AgentEvent`" as stated** —
  REFUTED. `TurnEvent` (`types.rs:36`) already IS the typed agent-event
  enum with `ToolStart`/`ToolResult`/`TurnComplete` matching the
  reviewer's cited Codex variants. A rename to `AgentEvent` would be
  cosmetic. The only untyped surface is the TS-interop `EventBus`, which
  is string-discriminated by design (ADR-006, WO 36.6).
- **Unifying all four event systems into one `AgentEvent`** — rejected.
  AGENTS.md §7 explicitly forbids unifying the `Verifier` and
  `BusVerifier` traits in one pass; the same rationale (the systems have
  different sync/async contracts and consumers) applies to the event
  enums. They are separate by design, not by accident (WO 9.6).
