# WO 45.11 — Sandbox Policy Unification (external reviewer claim)

## Status: Planned

## Problem

An external reviewer claimed:
> "KirkForge's sandbox is primarily around Bash. File tools have separate
> guards, MCP has separate policy, plugins have separate policy. Codex's
> filesystem server accepts sandbox policy and rejects operations that violate
> it — one SandboxPolicy consumed by all execution primitives."

This audit verifies the claim against the actual code: how sandbox policy
flows, whether file tools share the bash sandbox, whether MCP/plugins go
through any sandbox, and whether a single `SandboxPolicy` type is consumed by
all execution primitives.

## Verdict: PARTIALLY CONFIRMED

The reviewer's *descriptive* claims about KirkForge are accurate on every
point. The *prescriptive* framing ("one SandboxPolicy consumed by all") is a
real architectural gap, but the name `SandboxPolicy` is already taken by a
plugin-only type that does something narrower — so literal unification would
collide. Details below.

## Root cause (the actual architecture)

KirkForge has **four distinct, non-unified enforcement surfaces**, each with
its own policy type and enforcement point. There is no single type consumed
by all execution primitives.

### Surface 1 — Path-based access control (`PathGuard` + `DenyList` + `ReadGate`)

- **Types**: `src/shared/access/mod.rs:35` (`PathGuard`), `:462` (`ReadGate`),
  `src/shared/access/deny_list.rs` (`DenyList`). `GuardVerdict` at
  `src/shared/access/mod.rs:21`.
- **What it is**: filesystem *access control* — deny-list, sandbox-dir
  containment, symlink guard, extension/dotfile blocks, read-before-edit gate,
  size limits. The module's own header (`src/shared/access/mod.rs:1`) and the
  executor's wrapper (`src/session/executor/sandbox.rs:4-9`) both say
  explicitly: **"not a sandbox"** — it is path scoping, not OS isolation.
- **Who consumes it**: the **file tools**. Each file tool holds its own
  `PathGuard` field and calls `check_read`/`check_write` inline:
  - `read_file` — `src/tools/read_file.rs:7,66` (`path_guard.check_read`)
  - `write_file` — `src/tools/write_file.rs:21,81` (`path_guard.check_write`)
  - `edit_file` — `src/tools/edit_file.rs:20,90` (`path_guard.check_write`)
  - `glob` — `src/tools/glob.rs:8,108` (`path_guard.check_traversal`)
  - `grep` — `src/tools/grep.rs:24,69` (`path_guard.check_read`)
  - `lsp_query` — `src/tools/lsp_query.rs:28,512` (`path_guard.check_read`)
  - `notebook_edit` — `src/tools/notebook_edit.rs:14,59`
  - `read_image` — `src/tools/read_image.rs:42,123`
  - `workflow` — `src/tools/workflow.rs:42` (holds both `DenyList` + `PathGuard`)
- **NOT consumed by**: the bash subprocess spawn path. Bash *does* hold a
  `PathGuard` (`src/tools/bash.rs:60`) but only uses it for the
  `check_bash_command_str` command-string gate (`src/tools/bash.rs:116-122`)
  and the Docker workdir-containment check (`:148-165`); the actual subprocess
  is confined by Surface 2. The executor groups all three into a
  `PathGuardTower` (`src/session/executor/sandbox.rs:15`) for its own
  convenience, but file tools do **not** route through the tower — they hold
  their own clone.

### Surface 2 — OS-level subprocess sandbox (`SandboxConfig` + landlock + seccomp)

- **Type**: `SandboxConfig` at `src/shared/mod.rs:350` (rlimits: CPU/AS/FSIZE,
  `harden`, `no_network`, `block_edits`, `accept_unsandboxed`). Landlock paths
  in `src/session/bash_runner/landlock.rs:149` (`LandlockPaths`). Seccomp filter
  in `src/session/bash_runner/seccomp.rs` (feature-gated).
- **Enforcement point**: `setup_rlimits` at
  `src/session/bash_runner/mod.rs:148` — installs rlimits + `unshare(CLONE_NEWNET)`
  + landlock (`:240-254`) + seccomp (`:261-275`) in a single `pre_exec` hook.
- **Who consumes it**:
  - **bash foreground** — `src/tools/bash.rs:441-448` calls `run_shell_with_token`
    with `Some(&self.sandbox_config)` + `&self.landlock_extra_paths`.
  - **bash background** — `src/session/bash_jobs.rs:155` (`spawn` takes
    `&PathGuard`, `&DenyList`, `&PathGuard`, `Option<&SandboxConfig>`); WO 28.5
    wired landlock+rlimits+`CLONE_NEWNET` into the bg path
    (`src/session/bash_jobs.rs:241`).
  - **plugin tool wrapper** — `src/session/plugin_tools/wrapper.rs:68,278`
    (`sandbox: SandboxConfig` field, `setup_rlimits(&mut command, &self.sandbox, landlock_paths)`).
    WO 43.11 graduated landlock here too.
- **NOT consumed by**: any file tool. `read_file`/`write_file`/`edit_file` do
  not spawn a subprocess, so there is nothing for rlimits/landlock/seccomp to
  bind to — they are pure in-process `std::fs` calls gated only by Surface 1.
- **NOT consumed by**: the standalone `kf-plugin-host` crate spawn paths
  (`crates/kf-plugin-host/src/tool.rs:135`, `hook.rs:67`, `verifier.rs:85`).
  Those use a *separate* `crates/kf-plugin-host/src/rlimits.rs:28` and pass
  `None` for landlock — the lib cannot import the bin's landlock module
  (`crates/kf-plugin-host/src/sandbox.rs:15-22` ponytail ceiling). This is a
  known, documented gap, not an oversight.

### Surface 3 — Plugin trust-tier policy (`SandboxPolicy`)

- **Type**: `SandboxPolicy` at `crates/kf-plugin-host/src/sandbox.rs:13` — a
  **unit struct** with three associated fns (`required_tier`, `permits`,
  `filter`). It maps a `Capability` to a minimum `TrustTier` (ReadOnly / Shell).
- **What it is**: *capability gating*, not filesystem sandboxing. The ponytail
  comment at `crates/kf-plugin-host/src/sandbox.rs:15-22` is explicit: "rlimits
  + trust-tier only, no OS isolation."
- **Who consumes it**: only the plugin system.
  - `src/session/plugin_tools/wrapper.rs:213-219` — checks
    `SandboxPolicy::required_tier` before dispatch, blocks ReadOnly-tier plugins.
  - `crates/kf-plugin-host/src/lib.rs:628` — `SandboxPolicy::filter` at plugin
    load.
- **NOT consumed by**: bash, file tools, or MCP. The name `SandboxPolicy` is
  misleading — it does not carry path or rlimit policy; it carries a
  capability→tier map. ADR-013 (`docs/adr/013-rust-native-plugin-system.md:53`)
  documents this as the plugin host's own concern.

### Surface 4 — MCP (no sandbox)

- **Type**: none. `McpToolWrapper` at `src/session/mcp_tools.rs:26` holds only
  a `full_name`, a `ToolDef`, and an `Arc<McpClientManager>`.
- **Enforcement**: `McpToolWrapper::run` (`src/session/mcp_tools.rs:67-80`)
  calls `self.manager.call_tool(...)` with a 60s defensive timeout and
  returns. **No `PathGuard`, no `DenyList`, no `SandboxConfig`, no
  `SandboxPolicy`.** MCP tools execute on a remote server over a transport;
  the wrapper applies no local filesystem or resource policy to the call.
- **What exists**: `validate_mcp_uri` (`src/session/mcp_resource_tools.rs:7`)
  is a *URI-scheme* allowlist (blocks `file://` outside workspace) — but it
  governs only the `mcp_resource`/`mcp_prompt` *resource* tools, not
  `McpToolWrapper` (the generic tool-call path). MCP *sampling* has an
  approval bus (`src/main/run_session.rs:176-178`), but that is an interactive
  gate, not a sandbox policy. This is a genuine gap the reviewer named
  correctly; tracked separately in WO 45.12.

## What unification would actually look like

There is no single `SandboxPolicy` type to "consume" today. To match Codex's
"one policy consumed by all primitives" model, KirkForge would need:

1. **A new unified policy type** (not the existing plugin-only
   `SandboxPolicy`, which would collide). A `SandboxPolicy` that carries:
   - path scope (today's `PathGuard` + `DenyList` + `ReadGate`),
   - resource limits (today's `SandboxConfig` rlimits),
   - FS confinement (today's `LandlockPaths`),
   - capability tier (today's plugin `SandboxPolicy`), and
   - a network/egress rule (today's `no_network` + the unwired SSRF guard).
2. **A single enforcement chokepoint** every primitive routes through. Today
   there are **five** separate enforcement call sites:
   - file tools: inline `path_guard.check_read/write` (8 tools, each its own clone)
   - bash fg: `run_shell_with_token(..., Some(&sandbox_config), &landlock_extra_paths)`
   - bash bg: `bash_jobs::spawn(..., Option<&SandboxConfig>)`
   - plugin tool: `setup_rlimits(&mut command, &self.sandbox, landlock_paths)` + `SandboxPolicy::required_tier`
   - MCP: nothing.
   A unified design would have one `Sandbox::enforce(&self, op: &Op)` every
   primitive calls before acting. The `tool::Guard` port trait that ADR-073
   (`docs/adr/073-tools-session-layering-ports.md:51-66`) *explicitly deferred*
   (YAGNI: one impl, no second consumer) is the nearest precedent — unification
   would be the moment to resurrect it.
3. **Reconciling two incompatibilities** the reviewer did not name:
   - File tools are *in-process* `std::fs` calls — landlock/seccomp cannot
     apply to them (they bind to a *child* process in `pre_exec`). Unifying
     file tools under the same OS sandbox as bash would require either (a)
     routing all file I/O through a sandboxed helper subprocess (heavy), or
     (b) accepting that the "unified policy" has two *enforcement* modes
     (in-process path guard vs child-process OS sandbox) behind one *policy*
     type. Codex's filesystem server is itself a separate process, which is
     why its model works cleanly; KirkForge's file tools are not.
   - The `kf-plugin-host` lib crate cannot import the bin's landlock module
     (`crates/kf-plugin-host/src/sandbox.rs:15-22`). A unified policy type
     that carries landlock would need landlock extracted into its own crate
     first, or the lib's standalone spawn paths stay rlimits-only forever.

## Rejected candidates

- **"REFUTED — there is a `SandboxPolicy` type"**: rejected. The type exists
  but is plugin-only and does capability→tier mapping, not path/resource
  policy. The reviewer's claim that file/MCP/bash each have *separate* policy
  is correct; the existence of a同名 type does not unify them.
- **"CONFIRMED — Codex's one-policy model is strictly better"**: rejected as
  out-of-scope prescription. This audit verifies the *descriptive* claim about
  KirkForge's architecture, not whether Codex's model is superior. The
  in-process-vs-subprocess mismatch (file tools cannot take landlock) means
  unification is not a trivial "consume one type" change — it is a real design
  decision with tradeoffs, not a bug.
- **WO 45.12 as a sub-item here**: split out. The MCP-uses-no-sandbox finding
  is a distinct, actionable gap (the rest is architectural observation) and
  earns its own workorder so it is not lost inside an audit doc.
