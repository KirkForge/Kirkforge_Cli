# WO 45.31 — Claude compat support gaps: documentation + .mcp.json modal + .claude/agents model field

## Status: Done

## Problem

An external reviewer claimed (CLAIM A): "KirkForge supports
`.claude/` skills/commands/agents and `.mcp.json`. This compatibility
direction is smart — make it an explicit product promise."

Verification against the code shows the **machinery exists and ships**
but the product promise is **undocumented**, and two declared sub-features
of WO 39.2/39.3 are **incomplete in ways the WO status does not disclose**:

1. **Docs**: no mention of `.claude/`, `.mcp.json`, "Claude compat", or
   any compat surface in `README.md`, `docs/TECHNICAL.md`,
   `docs/README.md`, or the ADR index. The features ship dark — users
   cannot discover them, and the reviewer's "make it a product promise"
   is exactly the missing step. This violates the AGENTS.md doc-sync
   rule (architecture/plugin/feature-flag changes must update
   `docs/TECHNICAL.md` in the same commit). WO 39.2/39.3 marked Done
   without that doc pass.

2. **`.mcp.json` approval gate**: `src/main/run_session.rs:582-602`
   uses `eprintln!` to announce the project's servers, then
   **unconditionally calls `record_approval`** on the same run (line
   602) — there is no actual yes/no modal. The phase-1 ponytail
   comment at line 598-601 explicitly defers the modal. So a malicious
   `.mcp.json` is "approved" on the first interactive launch by merely
   running, with the operator's only signal being a stderr line they
   may not see. WO 39.2's gate is *present* (content-hash re-gating at
   `src/session/mcp_project.rs:166`, `is_approved` at :197) but the
   *first-contact prompt* is a no-op. The WO's "approval gate blocks
   first load and admits on approval (persisted per project)" gate
   claim is not met as written.

3. **`.claude/agents` `model` frontmatter field**: WO 39.3 Approach
   item 2 claims "model → per-call model plumbing (exists in
   task.rs)". The field is parsed (`src/session/agents.rs:283`,
   `AgentDef.model`) but the model resolution chain in
   `src/session/task_spawner.rs:220-225` only consults
   `request.model` → `subagent_provider.model` → parent model.
   `agent_def.model` is **never read** in `run_task`. The field is
   dead. Claude agent files that set `model: <name>` silently ignore
   the override.

4. **Non-interactive `.mcp.json` path**: when `non_interactive` is true
   and the project is unapproved, servers are silently dropped
   (`src/main/run_session.rs:608-611`) with only a `tracing::info!`.
   For CI/headless runs this is correct posture, but there is no
   config escape hatch to pre-approve a project non-interactively
   (e.g. an env var `KF_MCP_TRUST_PROJECT=1` or a flag). Operators
   get either "drop silently" or "auto-approve on first interactive
   run" — neither is a real trust decision.

## Root cause

Two layered causes:

- **WO 39.2/39.3 closed without the doc-sync pass** the AGENTS.md
  contract requires, so the compat surface is invisible to anyone who
  doesn't read the source. The reviewer's "make it a product promise"
  is the missing documentation work, not new feature work.
- **The phase-1 deferral markers** (the `ponytail:` comments at
  `run_session.rs:598-601` and the unwired `model` field) were left in
  code but never reified into WO 21+ deferred items, so the
  defer-disclosure rule was violated: the deferral exists in source
  comments but not in `state.md` pending or a tracking WO. This WO
  is the disclosure.

The reviewer's CLAIM A is **PARTIALLY CONFIRMED**: the parsing layer
shipped (skills, commands, agents, .mcp.json all load), but "make it
an explicit product promise" requires the missing docs, and two
declared sub-features are stubs.

## Approach

Three independent edits, each its own gated commit:

1. **Docs pass (small, ~80 LOC of prose)**: add a "Claude ecosystem
   compatibility" section to `docs/TECHNICAL.md` documenting the four
   loaders (`.claude/skills/*/SKILL.md` → skills.rs:126,159;
   `.claude/commands/**/*.md` → skills.rs:160,406;
   `.claude/agents/*.md` → agents.rs:331; `.mcp.json` →
   mcp_project.rs:52), the tool-name alias table (agents.rs:53-67),
   the trust gates (`plugin_trust_workspace` for agents,
   `load_project_mcp_json` + approval for `.mcp.json`), and the
   *honest* limitations: hooks phase 3 still pending (WO 39.4),
   `.mcp.json` first-contact modal is a stub, `.claude/agents`
   `model` field is not yet wired. Add one line to `README.md`
   feature list linking the TECHNICAL.md section. Update the
   `docs/README.md` index if a new doc file is needed (prefer inline
   section in TECHNICAL.md over a new file — ponytail: fewer files).

2. **Wire `agent_def.model` (≤10 LOC)**: in `task_spawner.rs:221`,
   extend the resolution chain to consult the dynamic agent when the
   per-call `request.model` is unset:
   `request.model.or(agent_def.model).or(sub.model).unwrap_or(parent)`.
   Add a test in `task_spawner` tests asserting an agent with
   `model: "X"` and no per-call model selects "X". This closes WO
   39.3's unmet gate item 2.

3. **`.mcp.json` first-contact real gate**: replace the unconditional
   `record_approval` (run_session.rs:602) with a real yes/no prompt.
   The ponytail comment names the dependency — "a real yes/no modal
   lands when the TUI gains a generic prompt component". For the
   **non-TUI / line-mode** path, use the existing stdin line reader
   (already used elsewhere in line_mode) to ask `[y/N]`. For the
   **TUI** path, until the generic modal component exists, route to
   the same stderr-prompt + stdin read (TUI raw mode is off during
   prompt). Add an env override `KF_MCP_AUTO_TRUST_PROJECT=<path>` for
   scripted/CI use so the non-interactive drop is overridable without
   code changes. Tests: simulate "n" → servers not loaded, approval
   not recorded; simulate "y" → servers loaded, approval recorded;
   simulate env override in non-interactive → servers loaded.

Defer-disclosure: item 3 is the larger piece. If scope pressure
forces a split, ship items 1+2 first (docs + model wiring, both
≤10 LOC of real code) and keep item 3 as a separate sub-WO. Item 3
is the security-relevant one — defer it explicitly, do not skip
silently.

## Done

All three gaps fixed (one commit each):

1. **Docs** (commit `ac83c8b1`): expanded the "Claude compatibility
   layer" section in `docs/TECHNICAL.md` to document all four loaders
   (skills, commands, agents, `.mcp.json`) with source file refs, the
   `CLAUDE_TOOL_ALIASES` table, both trust gates
   (`plugin_trust_workspace` for agents; `load_project_mcp_json` +
   approval + content-hash re-gate for `.mcp.json`), and the real
   first-contact prompt + `KF_MCP_AUTO_TRUST_PROJECT` env override.
   Honest limitations: only hooks phase 3 (WO 39.4) remains pending.

2. **`.mcp.json` approval gate** (commit `060f7766`): replaced the
   unconditional `record_approval` stub (`run_session.rs:602`) with a
   real interactive yes/no stdin prompt (`prompt_mcp_approval`). Added
   `KF_MCP_AUTO_TRUST_PROJECT=<path>` env override for CI/scripted use
   (path-canonicalized, per-project — not a blanket trust). The decision
   logic is pure and testable (`decide_unapproved_mcp` in
   `mcp_project.rs`): env override > interactive prompt > non-interactive
   drop. 9 new tests (4 env override + 5 decision logic).

3. **`.claude/agents` `model` field** (commit `7ef505ae`): wired
   `AgentDef.model` into the model resolution chain in
   `task_spawner.rs:run_task_detailed`. Moved the `agent_def` lookup
   before the model resolution; chain is now `request.model →
   agent_def.model → subagent_provider.model → parent`. 6 new tests
   asserting each precedence level. WO 39.3 gate item 2 is now met.

Gate: `scripts/test-fast.sh`, `cargo clippy --all-targets -- -D
warnings`, `cargo fmt --check`, `cargo check --workspace --all-targets`.
