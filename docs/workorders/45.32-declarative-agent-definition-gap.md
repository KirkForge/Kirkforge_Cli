# WO 45.32 — Declarative agent definition: TOML/YAML config layer for subagents

## Status: Done

## Problem

An external reviewer claimed (CLAIM B): "KirkForge lacks a declarative
agent definition model. Claude has agent.md files; OpenCode has
`agent: name/mode/model/tools/permissions/system`. KirkForge should
steal this — simple external API, complicated internal engine."

Verification against the code shows the claim is **PARTIALLY
REFUTED**:

- **The `.claude/agents/*.md` declarative loader DOES ship** (WO 39.3,
  `src/session/agents.rs:331` — `global_registry` reads
  `.claude/agents/` at session start; frontmatter fields `name`,
  `description`, `tools`, `model`; body = system prompt). So a
  Markdown-based declarative agent definition *format exists*. The
  reviewer's "Claude has agent.md files" comparison is already
  implemented, not missing.

- **No config (TOML) declarative agent format exists.** Grep for
  `[agents]`, `[persona`, `agents = [`, `agent_def` across all
  `*.toml` and `src/session/config/` returns nothing. The only
  agent-aware config knobs are `max_persona_turns`
  (config/mod.rs:542) and `subagent_provider.model`
  (task_spawner.rs:220) — these govern the *runtime* of all
  subagents, not the *definition* of one. So a config-file (TOML)
  declarative layer, in the OpenCode style, is genuinely absent.

- **The hardcoded persona preamble set is small and closed**:
  `build_task_prompt` (`src/tools/task.rs:288-303`) has exactly three
  arms — `"explore"`, `"plan"`, and a catch-all `_`. The `task` tool's
  `persona` argument (the user-facing API) accepts any string, and
  unknown names fall through to `build_task_prompt_with_agents`
  (`task.rs:311`) which checks the `.claude/agents` registry. So the
  "complicated internal engine" the reviewer wants is *already
  there* — the registry is the extensibility seam. What's missing is
  a *config-file* on-ramp for users who don't want to drop markdown
  into `.claude/agents/`.

So the reviewer's framing ("KirkForge lacks a declarative agent
definition model") is wrong as stated — the Markdown layer exists.
The *real* gap is narrower: **no TOML/config-file declarative path**,
for users who want agents defined alongside other config rather than
in a `.claude/` tree.

## Root cause

This is not a bug — it's a missing convenience layer. WO 39.3 chose
Markdown (`.claude/agents/*.md`) as the declarative format, matching
Claude. That decision is load-bearing (the compat direction in WO
39.0 is "borrow the ecosystem"). A second, TOML-based declarative
format was never added because the Markdown path covered the stated
need.

The reviewer's "simple external API, complicated internal engine"
principle is sound and *already honored* by the existing design:
the external API is `.claude/agents/*.md` frontmatter, the internal
engine is `AgentRegistry` + `build_task_prompt_with_agents` +
`task_spawner`'s alias-filtered toolset. Adding a TOML on-ramp is a
*third* external API for the same engine — only justified if a real
user wants config-colocated agent defs, not just Markdown ones.

## Approach

Ponytail-first: question whether this WO needs to exist at all. The
Markdown declarative path shipped; the engine is already
"complicated internal". A TOML layer duplicates the on-ramp for a
speculative user preference. **Default: do not build a second
declarative format.** Instead:

1. **Document the existing declarative API** as part of WO 45.31's
   docs pass (the `docs/TECHICAL.md` Claude-compat section already
   covers `.claude/agents/*.md`). This makes the *existing* declarative
   model discoverable — the reviewer's real complaint ("KirkForge
   lacks a declarative agent definition model") is mostly a
   discoverability problem, not a missing-feature problem.

2. **Wire the `model` field** (WO 45.31 item 2). The parsed-but-dead
   `AgentDef.model` is the one real gap in the existing declarative
   model. Fixing it makes the Markdown declarative API actually
   deliver on its frontmatter contract.

3. **Decide on the TOML on-ramp explicitly, not by default.** If a
   user asks for config-colocated agent defs (and only then), add a
   `[agents]` table in `config.toml` that reuses `AgentDef` +
   `AgentRegistry::register` (the registry already exposes
   `register` for programmatic adds — agents.rs:191). Estimated
   ~40-60 LOC: a `Vec<AgentDef>` in `ToolConfig`, a
   `register_config_agents` call in `run_session.rs` before
   `global_registry` is consulted, env-override mirror in
   `env_overrides.rs`. **Defer until asked.** Adding it now is
   speculative surface (YAGNI).

Defer-disclosure: item 3 is the only "new feature" piece, and it is
**explicitly deferred** — not built, not silently skipped. The
disclosure is this WO. Items 1+2 are owned by WO 45.31 (docs + model
wiring) and need no duplicate work here.

## Done

Documentation WO only — no code changed. WO 45.31 (Done, in this
worktree's base) had already shipped the bulk of what 45.32 task #1
asked for: the "Claude compatibility layer" section in `docs/TECHNICAL.md`
documents the `.claude/agents/*.md` format (frontmatter `name` /
`description` / `tools` / `model` + body = system prompt), the
`CLAUDE_TOOL_ALIASES` table, the `plugin_trust_workspace` trust gate,
and the `model` frontmatter wiring (resolution order: per-call `task`
arg → agent `model` → `subagent_provider.model` → parent). This WO
closed the one remaining gap — task #2 — by adding a concrete example
users can copy:

1. **Example agent file** (commit below): added a minimal
   `.claude/agents/code-reviewer.md` example block to the existing
   "Agents" entry in `docs/TECHNICAL.md` (under the Claude compat
   section). The example shows all four frontmatter fields and a
   one-line system prompt, with a note that only `name` is required
   and a pointer to the `task`-tool `persona` arg as the invocation
   seam. Placing the example inline (not as a new file) keeps the
   format and its docs together — no new file to land in the
   `docs/README.md` index.

2. **`config.toml.example` pointer** (same commit): added a comment
   block next to the existing `plugin_trust_workspace` flag noting
   that the same flag gates `.claude/agents/`, with a pointer to the
   TECHNICAL.md compat section for the file format. No new TOML keys
   (the TOML on-ramp the reviewer proposed is YAGNI — Approach item 3
   explicitly defers it until a real user asks for config-colocated
   agent defs; the registry's `AgentRegistry::register` seam already
   exists for that future wiring).

The `model` frontmatter field is wired and documented as supported
