# WO 45.36 — Verifier Architecture Audit (external reviewer CLAIM A)

## Status: Planned

## Problem

An external reviewer claimed:
> "KirkForge's verifier architecture is stronger than OpenCode's —
> build/test/rustfmt/lint/security/git/node/go/python/generic/plugin
> verifiers + VerifierBus + CorrectionLoop + Reducer. But 'verified'
> should be a stronger semantic type — `VerificationReport` with
> `CompletionStatus::Verified(...)` so a model saying 'I think this
> works' can't look like 'the system verified this works.'"

This audit verifies the claim against the actual code.

### 2. Are VerifierBus, CorrectionLoop, Reducer real? — CONFIRMED (with a critical caveat)

- **`VerifierBus`** — `src/session/verifier/bus.rs:97`. Real struct,
  `register()`/`run()`/`has_errors()` API. **Critical caveat:** the
  bus starts EMPTY (`bus.rs:230-237`):
  > "The built-in bus verifier stubs (SecurityBusVerifier,
  > GitBusVerifier) have been removed. The bus starts empty and
  > contains only what the host explicitly registers (plugin
  > verifiers, the TS orchestrator bridge)."

  The 14 built-in verifiers above do NOT register on the
  `VerifierBus`. They register on `VerifierSlots`
  (`verifier/slots.rs:12`) via the async `Verifier` trait
  (`verifier/types.rs:411`). The `VerifierBus` hosts the sync
  `BusVerifier` trait (`bus.rs:106`) — a different trait for plugin
  verifiers and the `TsOrchestratorBridgeVerifier` (the Rust security
  emitter, `bus.rs:414`). Two parallel verifier systems, by design
  (ADR-043, module doc `bus.rs:10-25`; AGENTS.md §7 warns against
  unifying them in one pass).

- **`CorrectionLoop`** — `src/session/verifier/correction.rs:17`.
  Real. The main executor's loop: `run()` (`correction.rs:48`) calls
  `VerifierHandler::verify_event` → matches on `Verdict` →
  auto-applies `Fixable` fixes (`apply_text_fix`/`apply_command_fix`)
  → re-verifies until `Clean`/`Skipped`/`Unfixable` or
  `max_iterations` (default 3, `correction.rs:27`). Bounded by
  `max_iterations`, guarded by `PathGuard`, 5s formatter timeout.

- **`Reducer`** — `crates/kf-orchestrator/src/reducer.rs:1`. Real,
  BUT lives in the `kf-orchestrator` crate (the parallel
  Scout/Coder/Reviewer pipeline), NOT the main executor. Folds a
  delegation's verification state into a `ReducedStatePacket`
  (`kf-routing/src/correction.rs:98`). The main executor's
  `CorrectionLoop` does NOT use the reducer — `bus.rs:377` documents
  "reducer not ported (ReducedStatePacket assembly pending)" and
  `native.rs:349` defers `verify-workspace` with "not implemented
  (reducer not ported)". The reducer is wired only in the
  `kf-orchestrator` path (`delegate.rs:279`). The reviewer listing
  "Reducer" alongside the main executor's bus/loop conflates two
  separate code paths.

### 3. Is "verified" conflated with "completed"? — REFUTED (the specific framing); NARROW GAP exists elsewhere

The reviewer's specific claim: "a model saying 'I think this works'
can't look like 'the system verified this works'."

**This is REFUTED.** Model output and verifier output are distinct
event variants with distinct origins:

- Model self-assessment flows through `TurnEvent::Token(String)` /
  `TurnEvent::Thinking(String)` (`executor/types.rs:37-38`) — the
  streaming assistant text. The model cannot emit a
  `TurnEvent::Verification`.
- `TurnEvent::Verification { message, success, file, line }`
  (`executor/types.rs:49`) is emitted from exactly ONE place:
  `emit_correction_results` (`executor/helpers/outcome.rs:280`),
  which maps `CorrectionResult` → `TurnEvent::Verification`. The
  `CorrectionResult` comes from `CorrectionLoop::run`
  (`correction.rs:48`), driven by real `Verifier` trait impls running
  `cargo build`/`clippy`/`rustfmt`/`git status`/security regexes. No
  model text enters this path.

There is no `CompletionStatus` type in the codebase (grep for
`CompletionStatus` returns zero matches). The reviewer's proposed
`CompletionStatus::Verified(...)` is a hypothetical, not an existing
conflation.

**The NARROW real gap** (different from the reviewer's framing):
`TurnEvent::Verification.success: bool` flattens the `Verdict` enum
and collapses `Skipped` into `success: true`:

- `CorrectionResult.success` is set `true` for `Verdict::Skipped`
  (`correction.rs:59`, with message "verification skipped: ...").
- `CorrectionResult.success` is `true` for `Clean` (no result
  emitted — the loop `break`s at `correction.rs:54` before pushing).
- `CorrectionResult.success` is `true` for a successfully-applied
  `Fixable` fix (`correction.rs:129`).
- `CorrectionResult.success` is `false` for `Unfixable`
  (`correction.rs:148`) and failed fixes (`correction.rs:129`).

So a consumer reading only `TurnEvent::Verification.success` cannot
distinguish "verifier confirmed clean" from "verifier was skipped
(tool not available)" from "verifier auto-fixed a problem". The
`message` text disambiguates, but the boolean alone is ambiguous.
This is a "skipped looks like success" gap, NOT a "model opinion
looks like verifier verdict" gap. The `Verdict` enum at
`verifier/types.rs:371` (`Clean | Fixable | Unfixable | Skipped`) is
already correctly typed at the verdict layer; the conflation happens
one layer up when `CorrectionResult.success: bool` is emitted.

### 4. Would a `VerificationReport` type add value? — MARGINAL

The current separation is mostly sufficient:
- `Verdict` enum (`types.rs:371`) is already a typed discriminant —
  `Clean` ≠ `Skipped` ≠ `Fixable` ≠ `Unfixable`.
- The model's text and the verifier's verdict never share a channel.

A `VerificationReport` type would close the narrow gap above IF it
replaced `TurnEvent::Verification { success: bool }` with a field
carrying the `Verdict` discriminant (or a `CompletionStatus` enum
with `Verified | Skipped | Fixed | Failed` variants). That is a
one-field refinement to `TurnEvent::Verification`, not a new type
system around `CompletionStatus::Verified(...)`. The reviewer's
proposed shape solves a problem that doesn't exist (model-vs-verifier
conflation) and over-scopes the problem that does exist (bool
flattening of the Skipped case).

## Root cause

The reviewer correctly inventoried the verifier components but
mis-diagnosed the conflation: the model's output and the verifier's
output are already type-separated. The genuine residual gap is that
`TurnEvent::Verification.success: bool` collapses `Skipped` into
`true`, which a `Verdict`-carrying event field would fix. The
`CompletionStatus::Verified(...)` framing implies a model-vs-verifier
conflation that the architecture already prevents by construction.

## Approach (if pursued)

1. **Do NOT introduce `CompletionStatus::Verified(...)`** — the
   model-vs-verifier conflation it prevents does not exist. Model
   text and verifier verdicts are already distinct `TurnEvent`
   variants from distinct origins.
2. **Optional narrow fix**: change `TurnEvent::Verification` from
   `{ message, success: bool, file, line }` to carry the `Verdict`
   discriminant (or a small `VerificationOutcome` enum:
   `Clean | Skipped(String) | Fixed(FixSuggestion) | Failed(String)`).
   This closes the "skipped looks like success" gap where
   `correction.rs:59` sets `success: true` for `Skipped`. Update
   `emit_correction_results` (`outcome.rs:280`), `dispatch_turn_event`
   (`tui/events.rs:217`), `emit_turn_events` (`turn_events.rs:125`).
   This is a ~30-line change, not a new type system.
3. **Do NOT unify `Verifier` and `BusVerifier` traits** — AGENTS.md §7
   explicitly warns against this; they have different sync/async
   contracts and consumers (ADR-043, `bus.rs:10-25`).
4. **Do NOT port the reducer into the main executor** without a
   separate workorder — the reducer lives in `kf-orchestrator` for the
   parallel pipeline; the main executor's `CorrectionLoop` is a
   different loop. `bus.rs:377` and `native.rs:349` already disclose
   this deferral.
