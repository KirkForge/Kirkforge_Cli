# WO 45.37 — Worktree Artifact Policy Audit (external reviewer CLAIM B)

## Status: Done

## Problem

An external reviewer claimed:
> "Worktree result handling is implicit, not typed. Need an explicit
> artifact policy: PatchOnly / ApprovalToApply / AutoApply / Commit."

This audit verifies the claim against the actual code.

## Verdict: PARTIALLY CONFIRMED (the policy is implicit; 2 of 4 proposed variants exist)

### 1. How do worktree results actually flow?

The flow spans three files:

1. **`WorktreeSession`** (`src/session/worktree.rs:95`) — creates an
   isolated git worktree (`git worktree add --detach`, line 118) and
   captures the subagent's uncommitted work as a patch string via
   `diff_patch()` (line 185): `git add --all --intent-to-add` then
   `git diff HEAD`. Returns an empty string for a clean worktree.
   `Drop` (line 194) removes the worktree (`git worktree remove
   --force`, with `fs::remove_dir_all` fallback if git fails).

2. **`PipelineResult`** (`src/session/parallel_orchestrator.rs:33`) —
   carries `coder_patch: Option<String>` (line 39), extracted from
   the coder's summary via `SUBAGENT_PATCH_MARKER` and
   `extract_patch()` (line 401, splits at the LAST marker occurrence
   per WO 38.4). `None` when worktree isolation is off or the coder
   produced no changes.

3. **`/workflow` command** (`src/tui/commands/workflow.rs:269`) —
   consumes `coder_patch`:
   - if `auto_apply_patch` is `true`: calls
     `apply_patch_to_parent` (`parallel_orchestrator.rs:412`) which
     runs `git apply` with a 30s timeout. On `Ok`: appends "✅ Coder
     patch applied to parent workspace." On `Err`: sets `success =
     false`, surfaces "❌ Coder patch application failed: ... Patch is
     in the log above; apply manually with `git apply`."
   - if `auto_apply_patch` is `false` (default): appends the patch
     text to the summary with "📝 Coder patch (not auto-applied; apply
     with `git apply` or `/apply`)".

There is NO commit step anywhere in this path. `auto_apply_patch`
applies to the parent's working tree; the user must `git commit`
manually.

### 2. Is the policy implicit or typed? — CONFIRMED implicit

The effective artifact policy is the product of TWO config booleans
in `SessionConfig` (`src/shared/config/session.rs:25`):

- `worktree_enabled: bool` (line 33, default `false`)
- `auto_apply_patch: bool` (line 39, default `false`), documented at
  line 37 as "Only meaningful with `worktree_enabled`."

The behavior is determined by branching in `workflow.rs:269-297` and
the `worktree_enabled` gate at `workflow.rs:257` / `run_session.rs:
165-171`. There is NO enum; the policy is the cross-product of two
bools interpreted by code paths:

| `worktree_enabled` | `auto_apply_patch` | Effective behavior |
|--------------------|--------------------|--------------------|
| `false` | (ignored) | No worktree; coder writes directly to parent working tree. No patch extraction. |
| `true` | `false` | Patch extracted, surfaced as text in TUI summary. User applies manually. |
| `true` | `true` | Patch extracted, `git apply`'d to parent working tree. User commits manually. |

The combination `worktree_enabled=false, auto_apply_patch=true` is
silently meaningless — `auto_apply_patch` is documented as "Only
meaningful with `worktree_enabled`" (`session.rs:37`) but NOT
enforced: nothing prevents the config, and the `workflow.rs:270`
branch checks `auto_apply_patch` independently of whether a
`coder_patch` exists (the `if let Some(patch)` guard at line 269
implicitly covers it, but only because non-worktree runs produce
`coder_patch: None`).

The reviewer's claim "implicit, not typed" is CONFIRMED. There is no
`ArtifactPolicy` enum; the policy emerges from two bools + code
branches.

### 3. Mapping to the proposed enum — 2 of 4 variants exist

The reviewer proposes `PatchOnly / ApprovalToApply / AutoApply / Commit`:

| Proposed variant | Exists? | Current equivalent |
|------------------|---------|--------------------|
| `PatchOnly` | YES | `worktree_enabled=true, auto_apply_patch=false` — patch surfaced as text in summary (`workflow.rs:289-297`) |
| `ApprovalToApply` | NO | There is no per-prompt approval gate. `auto_apply_patch` is a static config setting, not an interactive prompt. The `/apply` slash command is a manual user action, not a policy-driven approval flow. |
| `AutoApply` | YES | `worktree_enabled=true, auto_apply_patch=true` — `git apply` to parent working tree (`workflow.rs:270-288`) |
| `Commit` | NO | Nothing auto-commits. Both `PatchOnly` and `AutoApply` leave the working tree dirty; the user must `git commit` manually. |

So the reviewer's enum has 2 variants that match current behavior
(`PatchOnly`, `AutoApply`) and 2 that do not exist
(`ApprovalToApply`, `Commit`). The two existing variants are
currently booleans, not enum cases.

### 4. What would a typed artifact policy replace?

A typed `ArtifactPolicy` enum would replace the
`worktree_enabled: bool` + `auto_apply_patch: bool` pair with a
single field whose variants encode the valid combinations:

```rust
pub enum ArtifactPolicy {
    /// No worktree; coder writes directly to parent working tree.
    DirectWrite,
    /// Worktree isolation; patch surfaced as text for manual application.
    PatchOnly,
    /// Worktree isolation; patch `git apply`'d to parent working tree.
    AutoApply,
}
```

This makes the 3 valid states explicit and the invalid 4th state
(`worktree_enabled=false, auto_apply_patch=true`) unrepresentable.
The `ApprovalToApply` and `Commit` variants the reviewer proposes are
NEW features that do not exist today — adding them would be feature
work, not a type refactor.

## Root cause

The artifact policy grew incrementally: `worktree_enabled` shipped
first (WO 35.2), then `auto_apply_patch` was added on top (WO 41.1)
as a second bool rather than promoting the pair to an enum. The
result is a policy expressed by a cross-product of booleans +
code-branch interpretation, with one invalid combination silently
accepted and two reviewer-proposed variants (`ApprovalToApply`,
`Commit`) absent entirely. The policy is implicit, as the reviewer
claims — but the reviewer's proposed enum also invents two variants
that have no current implementation.

## Approach (if pursued)

1. Introduce `ArtifactPolicy { DirectWrite, PatchOnly, AutoApply }`
   in `src/shared/config/session.rs` (replacing `worktree_enabled`
   and `auto_apply_patch`).
2. Serde alias `worktree_enabled=true` + `auto_apply_patch=false` →
   `PatchOnly`, `true`/`true` → `AutoApply`, `false`/`_` →
   `DirectWrite` for backward compat with existing configs.
3. Update consumers: `run_session.rs:165`, `workflow.rs:235-297`,
   `cli_dispatch.rs:138`.
4. `ApprovalToApply` and `Commit` are OUT OF SCOPE — they are new
   features (interactive approval gate, auto-commit), not a
   type-refactor of existing behavior. If wanted, they belong in a
   separate workorder that adds the interactive prompt / commit
   logic first, then adds the enum variant.
5. This is a ~50-line config refactor, gated by the existing tests in
   `tests/subagent_lifecycle_test.rs` (which assert both PatchOnly
   and AutoApply paths).

## Done: —

Implemented the typed `ArtifactPolicy` enum (`DirectWrite` / `PatchOnly`
/ `AutoApply`) in `src/shared/config/session.rs`, replacing the
`worktree_enabled: bool` + `auto_apply_patch: bool` pair. The invalid
4th state (worktree off + auto-apply on) is now unrepresentable: the
custom `Deserialize` for `SessionConfig` accepts the legacy two-bool TOML
form for backward compat, mapping the invalid 4th state to `DirectWrite`
(auto_apply silently ignored, matching the old "Only meaningful with
`worktree_enabled`" doc). An explicit `artifact_policy` string always
wins over the legacy bools. `ApprovalToApply` and `Commit` (reviewer's
proposed variants) remain out of scope — no current implementation.

Consumers updated to the enum accessors (`is_worktree_enabled()` /
`is_auto_apply()`): `run_session.rs` (`--worktree` flag → `PatchOnly`),
`workflow.rs` (the consuming branch), `task_spawner.rs` (subagent
worktree gate + tests), `sandbox_posture.rs` (status display + tests),
`tests/subagent_lifecycle_test.rs` (helper). `CONFIG_FIELD_COUNT`
108 → 107 (2 bools → 1 enum); both drift-guard assertions updated.
`config.toml.example` documents the new `artifact_policy` key + legacy
fallback. Added 2 unit tests pinning the legacy-bool mapping and the
accessor gates.

## Rejected candidates

- **`ApprovalToApply` variant** — rejected as a type-refactor
  candidate. No interactive per-prompt approval gate exists in the
  worktree path. `auto_apply_patch` is a static config bool, and
  `/apply` is a manual slash command, not a policy-driven approval
  flow. Adding `ApprovalToApply` is new feature work (an interactive
  prompt before `git apply`), not a type encoding of existing
  behavior. It belongs in a separate workorder if wanted.
- **`Commit` variant** — rejected as a type-refactor candidate.
  Nothing in the codebase auto-commits. Both `PatchOnly` and
  `AutoApply` leave the working tree dirty for manual `git commit`.
  Adding `Commit` is new feature work (auto-commit after `git
  apply`), with its own design questions (commit message source,
  signing, branch target). It is not a type encoding of existing
  behavior.
- **"Replace the two bools with the full 4-variant enum the reviewer
  proposes"** — rejected as scoped. The 4-variant enum mixes 2
  type-refactor candidates (PatchOnly, AutoApply — already
  implementable as bools) with 2 new features (ApprovalToApply,
  Commit). A type refactor should encode only behavior that exists;
  new variants should land with the features they enable, not ahead
  of them.
