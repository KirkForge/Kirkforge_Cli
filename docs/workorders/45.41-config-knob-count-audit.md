# WO 45.41 — Config knob count audit (external reviewer "400 knobs" claim)

## Status: Planned

## Problem

An external reviewer scored KirkForge's architectural simplicity at 7/10
(vs Codex/Claude/OpenCode at 9) and claimed KirkForge has "400 config
knobs" as a danger. This audit verifies the actual count against the
code.

## Verdict: REFUTED — 140 distinct knobs, not 400. A drift-guard test enforces the count.

### Evidence — three config surfaces, all counted at file:line

1. **`Config` struct fields: 108** (enforced by a drift-guard test).
   `src/shared/config/mod.rs:46`:
   ```rust
   pub const CONFIG_FIELD_COUNT: usize = 108;
   ```
   The test `config_field_count_drift_guard`
   (`src/session/config/mod.rs:2452`) asserts three invariants stay in
   sync: the const, the serde-serialized field count, and the
   `merge_toml_into_config` key count. Breakdown by sub-struct
   (documented at `mod.rs:22-31`):
   - `ModelConfig`     34 (33 direct + `subagent_provider` handle) — `src/shared/config/model.rs:86-183`
   - `SecurityConfig`  22 (19 direct + 3 sub-struct handles: `computer_use`, `docker`, `sandbox`) — `src/shared/config/security.rs:38-98`
   - `ToolConfig`      35 — `src/shared/config/tools.rs:114-191`
   - `SessionConfig`   9 — `src/shared/config/session.rs:25-63`
   - `DisplayConfig`   7 — `src/shared/config/display.rs:33-55`

2. **Environment-variable overrides: 96** (91 `KF_CODE_*` + 5 provider API keys).
   `src/session/config/env_overrides.rs:12-628` — counted by the same
   drift-guard test (`mod.rs:2601-2617`, `ENV_OVERRIDE_EXPECTED = 96`).
   The test scans `env_overrides.rs` for `"KF_CODE_"` + API-key string
   literals so it fails if anyone adds/removes a var without updating
   the const.

3. **CLI flags: 23 on the `run` subcommand, 62 across all subcommands.**
   `src/cli.rs:42-191` (the `Run` variant). The other 39 are on
   `Sessions`, `Daemon`, `Jobd`, `Replay`, `Bench`, `Plugin`, `Doctor`,
   `Update`, `Completions` — most are positional args or single flags
   for subcommand-specific state, not agent-behavior knobs.

### Total: 140 distinct config surfaces (108 struct + 96 env − ~64 overlap where an env var shadows a struct field)

The reviewer's "400" is not a real count of anything in this codebase.
The closest plausible miscount sources:
- 108 struct fields × 3 layers (struct + env + CLI) ≈ 324 — still not 400.
- The 5 sub-structs each have a `Default` impl that restates every field
  (108 lines), which a naive `grep pub` over the whole config tree
  would double-count to ~216.
- Including `McpServerConfig`, `LspServerEntry`, `PermissionRule`,
  `ComputerUseConfig`, `DockerConfig`, `SandboxConfig`, `SubagentProvider`,
  `ModelPrice` sub-struct fields adds ~30, but these are nested types,
  not top-level knobs.

None of these reach 400. The drift-guard test is the structural fix:
the number cannot drift without a failing test.

## Root cause

The reviewer estimated without counting. The repo has a documented
`CONFIG_FIELD_COUNT` const with a five-layer invariant test precisely
because uncounted config surfaces drift. The reviewer's number is
~2.9× the real count.

## Approach

No code change. This WO records the audit. If the reviewer's score
needs a written response, the table above (file:line + the
drift-guard test citation) is the response. The "400" claim should
not be repeated without a recount.

If a *real* config-knob reduction is later desired (the score 7/10
is partly a perception problem, partly a real surface), the candidates
are the 15 struct fields intentionally skipped by `merge_toml_into_config`
(mod.rs:2628-2637) — e.g. `summarize_enabled`, `opencode_zen_api_key`,
`docker`, `sandbox` sub-fields. These are config-file-only fields with
no env override and no CLI flag; several (`summarize_enabled`,
`subagent_allowed_models`, `opencode_zen_*`) have no production wiring
and are deletion candidates. That is a separate WO.

## Rejected candidates

- **"Reduce config knobs to improve the score"** — rejected. The
  count is already 108, not 400. Reducing further to chase a
  perception score would remove real functionality (the 5 sub-structs
  each gate a documented feature area). The drift-guard test is the
  right structural answer, not a knob purge.
- **"Count CLI flags + env vars + struct fields as a single 'knob'
  number"** — rejected as a methodology. A struct field with an env
  override and a CLI flag is ONE knob with three access paths, not
  three. The reviewer's framing triple-counts the same setting.
- **"Merge the 5 sub-structs back into one flat `Config`"** — rejected.
  The sub-struct split is the load-bearing organizational unit
  (`ModelConfig`/`SecurityConfig`/`ToolConfig`/`SessionConfig`/`DisplayConfig`
  each map to a feature area with its own default fns and tests).
  Flattening would not change the field count; it would only make the
  file harder to navigate.
