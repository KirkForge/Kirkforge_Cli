### The one real gap: `checkpoint_interval_messages` defaults to 0 (disabled)

`src/shared/config/session.rs:11-13`:
```rust
fn default_checkpoint_interval_messages() -> usize {
    0
}
```

The conversation log supports periodic checkpoints
(`src/session/conversation.rs:155-160`) and `run_session.rs:259` wires
the config value via `with_checkpoint_interval`. But the default is 0,
which means a long session that crashes mid-turn loses everything back
to the last completed tool batch (the executor checkpoints after each
tool batch per the comment at `conversation.rs:27`). For a multi-hour
session with no tool calls in the last stretch (e.g. a long model
thinking block), that could lose substantial work.

This is a **tunable**, not a bug — an operator who sets
`checkpoint_interval_messages = 20` gets periodic checkpoints. But the
default-off posture is the gap that keeps the score at 8 instead of 9.
A default of 20-50 (matching the test fixtures at
`conversation.rs:690,983`) would make crash recovery tighter without
a measurable fsync cost on a 10-message batch.

## Root cause

The 8/10 is fair but the reviewer's reasoning is likely wrong. Most
operational maturity surfaces (signals, crash recovery, terminal
restore, replay, doom-loop, subprocess lifecycle, executor death) are
shipped and tested. The one genuine gap is the default-off periodic
checkpoint — a single-line default change (`session.rs:12`) plus a
test update. The rest of the gap to 9-10 is perception: the reviewer
likely did not find the WO 43/44 shipped work (43.21-43.23, 44.1,
44.36, 44.39) that closed the prior real gaps.

## Rejected candidates

- **"Add a WAL or transactions to the conversation log"** — rejected.
  NDJSON append + `sync_all` per message is already crash-safe (loses
  at most the in-flight line). A WAL adds complexity for no marginal
  durability. Ponytail: the current design is the right one for a
  single-writer append-only log.
- **"Persist executor in-memory state (tool call stacks, in-flight
  verifiers) for true mid-turn resume"** — rejected as out of scope
  for an 8→9 bump. No comparable CLI agent (Codex, Claude Code,
  opencode) does this. The conversation log + trace log already let
  `--resume` + `replay` reconstruct the session. Mid-turn resume
  would require serializing async task state, which is not sound in
  Tokio. Tracked here as a rejected candidate, not a deferred WO.
- **"Raise the score by adding a health-check HTTP endpoint"** —
  rejected. The daemon (`src/daemon/`) already has a ping/health
  surface. A second HTTP endpoint for the TUI process is YAGNI.
- **"Add structured telemetry export (OTLP)"** — rejected. The
  `MetricEvent` enum (`src/shared/metrics.rs:145`) already emits
  OpenTelemetry-style attributes; an OTLP exporter is a deploy-time
  choice, not a maturity gap. The 8/10 score is not about telemetry
  export format.
