# WO 45.43 — Architectural simplicity audit (external reviewer 7/10 score)

## Status: Done

## Problem

An external reviewer scored KirkForge's "architectural simplicity" at
7/10 (vs Codex/Claude/OpenCode at 9). This audit verifies whether the
complexity the reviewer perceived is real or a survey artifact.

## Verdict: PARTIALLY CONFIRMED — the complexity is real but smaller than the 7/10 implies. The reviewer overcounted event systems (WO 45.10 covers this); the genuine residual is the number of config layers and the two-coexistent-verifier-traits design, both deliberate.

### Evidence — how many execution paths / event systems / config layers actually exist

#### Event systems: 4, not "one untyped EventBus"

Already audited in [WO 45.10](45.10-event-type-audit.md). Summary:
- `TurnEvent` — typed enum, 21 variants, the primary executor→TUI path
  (`src/session/executor/types.rs:36`).
- `BusEvent` — typed enum for tool/verifier events
  (`src/session/verifier/types.rs:267`).
- `StreamEvent` — typed enum for adapter→executor streaming
  (`src/shared/mod.rs:158`).
- `EventBus` + `Event` — string-discriminated, deliberately a faithful
  TS-port for cross-language artifact events (`src/shared/event_bus.rs:67`).

3 of 4 are typed. The reviewer's "untyped EventBus" claim generalizes
one surface to all four. The genuine residual (typed-enum-wrap the
`EventBus` `Event` at the Rust boundary) is documented in WO 45.10's
Approach.

#### Execution paths: 3 entry points, 1 main loop

- `src/main/mod.rs` — CLI dispatch → `run_session.rs` or `line_mode.rs`
  or `handle_replay.rs` (the 3 entry points).
- `src/main/run_session.rs:179-242` — resolves resume target, opens
  conversation log, spawns executor, hands off to TUI or line mode.
- `src/session/executor/loop_.rs` — the single agent turn loop
  (`Executor::run`, ~434 lines — one of the top-5 long functions in
  AGENTS.md §7). All turns route through here.
- `src/tui/events.rs:dispatch_turn_event` (~390 lines) — the single
  TUI-side event dispatcher for `TurnEvent`.

There is one main loop, one event dispatcher per surface, one config
load path. The "many execution paths" perception is the 3 entry points
(TUI / line-mode / replay), but they share the executor and config
layer.

#### Config layers: 4 (documented, drift-guarded)

`src/session/config/mod.rs:1-16` documents the layering:
1. Built-in `Default` impls (the 108 struct fields).
2. `KF_CODE_*` env vars (96, `env_overrides.rs`).
3. `config.toml` (`merge_toml_into_config`, 100 keys).
4. CLI flags (23 on `run`, 62 total).

Priority: CLI > env > toml > Default. The drift-guard test
(`mod.rs:2452-2674`) enforces all four stay in sync. This is more
layers than Codex/Claude (which use ~2: config file + CLI), but each
layer has a documented purpose (env for CI/containers, toml for
persistent prefs, CLI for one-shot overrides). The 4-layer split is
deliberate, not accidental.

#### Verifier traits: 2 coexist (documented, deliberate)

AGENTS.md §7:
> The existing `Verifier` trait (`async fn verify(&self, event:
> &BusEvent) -> Verdict`) and the new `BusVerifier` trait (`fn
> verify(&self, ctx: &VerifyContext) -> Vec<VerdictEntry>`) coexist.
> The former is event-driven, the latter is sync and context-based.
> Don't try to unify them in one pass.

- `src/session/verifier/types.rs:411` — `Verifier` (async, event-driven).
- `src/session/verifier/bus.rs:106` — `BusVerifier` (sync, context-based).

This is the genuine complexity the reviewer may have sensed: two
verifier traits with different contracts. Unifying them is explicitly
forbidden by AGENTS.md §7 (WO 9.6 documented the deliberate
non-unification). The 7/10 may reflect this, but the alternative
(unifying) is worse: it would force one contract onto two different
consumer shapes (event bus vs sync verification request).

#### Config sub-structs: 5 + 8 nested types

- 5 top-level sub-structs (`ModelConfig`, `SecurityConfig`, `ToolConfig`,
  `SessionConfig`, `DisplayConfig`).
- 8 nested types (`SubagentProvider`, `ComputerUseConfig`, `DockerConfig`,
  `SandboxConfig`, `McpServerConfig`, `LspServerEntry`, `PermissionRule`,
  `ModelPrice`).

13 total config types. Codex/Claude have fewer (they support fewer
providers/features). This is the real complexity tax of supporting 6
model providers + Docker + landlock + seccomp + plugins + MCP + LSP +
budget + stratum + doom-loop + computer-use. Each feature adds ~1-3
config fields. The 108-field count (WO 45.41) is the sum of feature
surfaces, not architectural over-engineering.

## Root cause

The 7/10 is the shadow of the feature surface, not the architecture.
KirkForge supports more providers and sandboxes than the comparison
tools (6 adapters vs Codex's 2; landlock+seccomp+docker vs Claude's
none; plugin system vs opencode's none). Each feature earns its config
fields. The event-system count (4) and verifier-trait count (2) are
deliberate splits documented in ADRs/WOs and enforced by AGENTS.md §7.
The reviewer's 7/10 reads as "more config than I expected" rather than
"the architecture is convoluted." A 4-layer config with a drift-guard
test is more disciplined than a 2-layer config that drifts silently.

## Approach (if pursued)

No code change recommended for the score. The two candidate
simplifications, both already WO-tracked or ADR-pinned:

1. **Typed `EventBus` boundary** (WO 45.10 Approach): wrap the
   string-discriminated `Event` in a typed `enum BusEventKind` at the
   Rust boundary, keep `to_string()` for the TS-interop serialization.
   Closes the one real "untyped" surface. Small, isolated.

2. **Config sub-struct field pruning** (WO 45.41 Approach): the 15
   struct fields intentionally skipped by `merge_toml_into_config`
   (`mod.rs:2628-2637`) include several with no production wiring
   (`summarize_enabled`, `subagent_allowed_models`, `opencode_zen_*`).
   Deleting those would drop the field count and the perception without
   losing functionality. Separate WO.

Neither is a unification refactor. Both are local simplifications.
The two-verifier-trait split should NOT be unified (AGENTS.md §7).

The 7/10 is the feature-surface shadow, not the architecture.

## Rejected candidates

- **"Unify the 4 event systems into one `AgentEvent` enum"** — rejected.
  WO 45.10 rejected this; AGENTS.md §7 forbids unifying the verifier
  traits; the same rationale applies. The systems have different
  sync/async contracts and consumers (WO 9.6).
- **"Unify the `Verifier` and `BusVerifier` traits"** — rejected.
  AGENTS.md §7 explicitly forbids this in one pass. The async
  event-driven `Verifier` and sync context-based `BusVerifier` serve
  different verification models; unifying would force one contract
  onto both.
- **"Collapse the 4 config layers into 2 (toml + CLI)"** — rejected.
  The env layer is load-bearing for CI/containers (`KF_CODE_DATA_DIR`
  isolation in every e2e test, `KF_CODE_BUDGET_CEILING` for the bench
  runner). Removing it would break the bench harness and the test
  isolation pattern. The 4-layer split is documented and drift-guarded.
- **"Rewrite the executor loop into a state machine"** — rejected.
  `Executor::run` is one of the top-5 long functions (AGENTS.md §7)
  with a refactor-on-touch policy, not a standalone refactor WO. A
  state-machine rewrite is a big-bang refactor of the kind AGENTS.md
  §7 explicitly tells workers NOT to launch. The current loop is long
  but linear and tested; the length is a readability issue, not an
  architectural simplicity issue.
- **"Reduce the 6 model adapters to 2 (ollama + anthropic)"** —
  rejected. The adapters are behind a trait (`ModelAdapter`,
  `src/adapters/mod.rs:357`) and the per-adapter code is isolated.
  Removing adapters would remove real supported providers (Bedrock,
  Vertex, OpenAI-compat, DeepSeek, Gemini) that users have configured.
  The complexity is per-adapter, not architectural.
