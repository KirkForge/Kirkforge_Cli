# Workorder 46.1 — Verifier Verdict-Set Determinism Invariant

## Status: Planned

## Problem

The reviewer's 9 invariant categories included **verifier**. The verifier
surface has *extensive* coverage today — `src/session/verifier/*.rs` carries
300 `#[test]`/`#[tokio::test]` attributes across 26 files, pinning individual
verifier behavior (build, lint, test, git, security, detect, correction).
`kf-testdoctor` even has a `flaky` module (`crates/kf-testdoctor/src/flaky.rs`,
WO 12.5) that runs a single test N times to detect <100% pass rates — but that
tool is a **manual** developer diagnostic, not a CI gate, and it checks
*test infra* flakiness, not *verifier verdict* flakiness.

What is **genuinely missing** is the invariant: the same `VerifyContext`
(diff + tool outputs + config) run through the `VerifierBus` N times must
produce the **same multiset of verdicts** every time. Verifiers are documented
as deterministic (`src/session/verifier/mod.rs:13` "verifiers run
deterministic checks"; `types.rs:405` "A verifier performs deterministic
checks"), but no test pins that claim across the full bus. A verifier that
introduces nondeterminism (e.g. reading `SystemTime::now()`, hashing a
`HashMap` iteration order, spawning and racing) would silently start producing
flaky verdicts and no existing test catches it — only the `flaky` doctor
would, and only if a human runs it.

The closest existing test is `src/session/verifier/tests.rs:785
verdict_cache_different_content_hash_runs_verifier_again`, but that tests the
*cache invalidation* path, not verdict-set determinism.

## Root cause

The verifier bus was built verifier-by-verifier (build, lint, test, git,
security, plugin) with each verifier getting its own unit tests. The
*cross-cutting* property — "the whole bus is deterministic for a fixed input"
— was never asserted because the individual verifiers were each claimed
deterministic in their file header comments. But composition can break
determinism even when each part is deterministic: a `HashMap` of registered
verifiers iterated in arbitrary order, a verifier that shells out to a tool
with a race, a plugin verifier with `SystemTime`. The `VerifierBus::run`
(`src/session/verifier/bus.rs`) iterates `self.verifiers` (a `Vec`, currently
insertion-order-stable, but that's an implementation detail, not a pinned
invariant).

## Approach

Add **2 tests** to `src/session/verifier/bus.rs` `mod tests`:

1. `same_verify_ctx_produces_same_verdict_multiset_across_runs`: build a
   `VerifierBus` with 3-4 stub verifiers (reuse the `StubVerifier` already in
   `bus.rs` tests at line ~880) returning distinct verdicts. Run
   `bus.run(&ctx)` 10 times on the same `VerifyContext`. Collect each run's
   verdicts into a `Vec<VerdictEntry>`, sort by `(source, severity, message,
   file, line)`, and assert all 10 sorted vectors are equal. This pins
   verdict-set determinism.

2. `verifier_insertion_order_does_not_change_verdict_set`: register the same
   4 stub verifiers in 2 different orders; run both buses on the same ctx;
   assert the sorted verdict multisets are equal. This pins that the bus does
   not depend on registration order for the verdict *set* (order of emission
   may differ; the set must not).

Keep it lazy: 2 tests, reuse `StubVerifier` and `make_verify_ctx` already in
the file. No new deps, no new files. If a real verifier later breaks
determinism, these tests stay green (they use stubs); a follow-up WO could
add a property test that exercises real verifiers, but that needs a stable
fixture diff and is out of scope here.
