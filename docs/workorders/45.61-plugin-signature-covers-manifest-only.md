# WO 45.61 — Plugin signature covers manifest only; content-hash ledger bypassed when signatures are on

## Status: Planned

## Problem

The plugin trust model has a gap in its strongest-looking configuration
(default: `plugin_signature_validation = true`). Two trust mechanisms exist
but they cover different surfaces and are **mutually exclusive at the gate**:

1. **Signature verification** (`verify_plugin_signature`,
   `crates/kf-plugin-host/src/lib.rs:544-583`) only hashes and verifies
   `kf-code.toml` — the manifest text (name, capabilities, trust tier). It
   never touches the actual command scripts/binaries the manifest points to.

2. **Content-hash consent ledger** (`bundle_hash` +
   `is_plugin_approved`, `src/session/plugin_tools/approval.rs:60-162`)
   hashes `kf-code.toml` **plus every capability file** (command/hook/
   verifier/skill scripts, `approval.rs:65-85`) and re-gates on mismatch
   (WO 43.17). This is the mechanism that actually covers the executable
   surface.

3. **The ledger is bypassed when signatures are on**:
   `src/session/plugin_tools/loader.rs:235`:
   ```rust
   if cfg.tools.plugin_consent_ledger && !policy.verify_signatures {
   ```
   The `!ws_policy.verify_signatures` condition skips the ledger gate
   entirely for signature-verified plugins. The same bypass is at
   `loader.rs:205` for workspace plugins.

4. **`plugin_signature_validation` defaults to `true`**
   (`src/shared/config/tools.rs:193,227`), so in the default production
   config the ledger is OFF and the signature (manifest-only) is the
   sole gate.

**Attack chain**: a plugin's `kf-code.toml` + `.kf-code.sig` are
cryptographically signed and look like the strongest trust path. But the
script files the manifest references are covered by **neither** mechanism.
An attacker who controls the distribution point (compromised repo, mirror,
release asset) can leave the signed `kf-code.toml` and `.kf-code.sig`
untouched while swapping the referenced command file for malicious code.
The signature passes (it was never in scope for the scripts); the ledger
is skipped (signatures are on). Both gates wave it through.

No ADR, `ponytail:` comment, or WO acknowledges this specific interaction.
WO 43.17 added the ledger but explicitly carved out the signature path
(`loader.rs:203` comment: "Signature-verified plugins opt out"). The
manifest-only signature scope was inherited from the original minisign
implementation and never re-examined when the ledger was added.

## Root cause

The signature verification predates the content-hash ledger (WO 43.17).
When the ledger was added, it was scoped to the non-signature path as a
defense-in-depth layer for unsigned plugins — but the signature path was
never extended to cover the script files the manifest points to. The two
mechanisms cover complementary surfaces (manifest vs scripts) but the gate
makes them mutually exclusive instead of layered.

## Approach

1. **Extend `verify_plugin_signature` to cover the full bundle** — after
   verifying the manifest signature, also compute `bundle_hash` (already
   exists in `approval.rs:60`) over the manifest + all capability files,
   and include that hash in the signed payload (or sign the hash, not the
   manifest bytes directly). This makes the signature cover the executable
   surface, not just the manifest.

   OR (simpler, no signature-format change):

2. **Remove the `!ws_policy.verify_signatures` bypass** — run the
   content-hash ledger **in addition to** signature verification, not
   instead of. A signed plugin must ALSO be in the approved ledger with a
   matching bundle hash. First-load approval prompt remains the same; the
   ledger just also runs for signed plugins. This is a one-line change at
   `loader.rs:235` and `:205` (drop `&& !ws_policy.verify_signatures`).

   The second approach is smaller, doesn't change the signature format,
   and layers the two mechanisms instead of making them exclusive. Pick
   it unless there's a reason signed plugins should skip the ledger (there
   isn't — the ledger covers the scripts the signature doesn't).

3. **Test**: a plugin with a valid manifest signature but a modified
   command script must be rejected (today it passes). Test both the
   data-dir path (`loader.rs:235`) and the workspace path (`loader.rs:205`).

4. **Disclosure**: add a `ponytail:` comment at the gate site documenting
   that the ledger is layered on top of signatures, not bypassed by them.
