# WO 46.1 — FileAuditSink::flush advances hash chain before write succeeds — breaks tamper-evidence on partial failure

## Status: Done

## Problem

**Location:** `src/shared/audit.rs:685-711`

FileAuditSink::flush advances last_hash inside the per-event loop (line 694) BEFORE write_all succeeds. If serde_json::to_string or write_all fails mid-loop, last_hash is partially advanced but buf is NOT cleared. The next flush re-seals the same events with different chain hashes, breaking tamper-evidence. Fix: compute all chain_hash values into a temp vec first, advance last_hash and clear buf only after write_all succeeds; on failure leave both untouched.

## Done

Fixed `FileAuditSink::flush` in `src/shared/audit.rs` to be atomic on
failure: chain hashes are now computed into a local `prev` (cloned from
`last_hash`) while sealing + serializing into a temp `lines` vec; `*last`
is advanced and `buf` is cleared ONLY after `write_all` succeeds. On
serialize or write failure both `last_hash` and `buf` are left untouched,
so the next flush re-attempts from the same starting state and re-seals
the same events with identical chain hashes (tamper-evidence preserved).

Added regression test
`file_sink_flush_failure_leaves_last_hash_and_buf_untouched` (`#[cfg(unix)]`):
forces `write_all` to fail via a read-only directory, asserts `last_hash`
is unchanged and `buf` still holds 2 events after the failed flush, then
restores write access and asserts the retry flush seals from the original
genesis with a verifying chain.
