# WO 46.20 — Never-ending bash job blocks scheduler and graceful shutdown — unshutdownable daemon

## Status: Done

## Problem

**Location:** `src/jobs/daemon.rs:146-197`

run_bash_job polls registry.get(id) until the job leaves Running. If job.timeout is None (default unset), a bash job that never exits keeps Running forever. The daemon blocks on handles await at daemon.rs:190 and sem.acquire at daemon.rs:152. SIGTERM/SIGINT/Shutdown only fires shutdown.notify_one(), but nothing awaits it while the loop is stuck. Process only dies via SIGKILL. Fix: enforce a default timeout on all scheduled jobs.

## Root cause

`job.timeout` is `Option<Duration>` with `#[serde(default)]`, so persisted
jobs that don't set it deserialize to `None`. `BashJobRegistry::spawn`
passes `None` to its watcher (`src/session/bash_jobs.rs:357-366`), which
then waits with no timeout. A never-exiting bash command keeps the
registry record in `JobStatus::Running` forever; the poll loop in
`run_bash_job` (`src/jobs/runner.rs:134-188`) never returns; the
daemon's `handles.await` at `daemon.rs:190-192` never completes; the
outer loop never reaches the `shutdown.notified()` select arm at
`daemon.rs:222-226`. SIGTERM/SIGINT fire `notify_one` but nothing is
awaiting it. Only SIGKILL can free the daemon.

## Fix

Enforce a 300s default timeout on scheduled jobs whose `timeout` is
`None`, applied in the daemon loop *before* spawning `run_job`. The
user-set value is respected as-is; only the unset case is coerced. The
mutation is to the local `due_jobs` clone and is persisted back in the
existing `save` after the run, so the enforced default survives a
daemon restart.

300s is long enough for legitimate short jobs (cron-style health
checks, build sweeps, git pulls) and short enough that a wedged job
frees the daemon within 5 minutes — well under any reasonable
supervision grace period.

The fix lives entirely in `src/jobs/daemon.rs` (the WO's named scope).
`src/jobs/runner.rs` is shared by the TUI "Run now" path
(`src/tui/commands/jobs.rs:539`), which the user may want to allow
running without a default cap, so it is intentionally left untouched.
