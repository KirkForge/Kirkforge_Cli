# WO 46.23 — ResponseCache::put holds sync Mutex across disk write + unbounded in-memory cache

## Status: Done

## Problem

**Location:** `src/adapters/caching.rs:113-135`

self.memory Mutex held during std::fs::write. Disk stall (NFS, full disk) blocks every subsequent stream call. Panic in to_vec poisons the mutex. Also: the in-memory HashMap has no size cap or eviction — unbounded growth with cache_enabled on.

## Root cause

Identified by external model audits (DeepSeek + MiniMax). See
/home/henrik/madlab/github/desktop/ds-bugs.md and mm-bugs.md for full evidence.

## Approach

Read the Problem section's fix recommendation. Implement the minimal
correct fix. Add tests where practical.

## Files

src/adapters/caching.rs

## Gate

`scripts/test-fast.sh` + `cargo clippy --all-targets -- -D warnings` +
`cargo fmt --check`.

## Done

- `put` no longer holds the memory `Mutex` across `std::fs::write`: data is
  cloned out of the lock first, all disk I/O (`create_dir_all` + `to_vec` +
  `fs::write`) runs outside the lock. A disk stall no longer blocks every
  subsequent stream call; a `to_vec` panic can no longer poison the mutex.
- New `insert_memory` helper enforces a 100-entry cap on the in-memory
  `HashMap` with arbitrary (HashMap-order) eviction. The disk-promotion
  path in `get` routes through the same helper so the cap is enforced in
  one place. `ponytail:` comment names the ceiling + upgrade path
  (IndexMap + move-to-back for real LRU if hit-rate ever shows arbitrary
  eviction hurting).
- Test `cache_memory_respects_size_cap` inserts 120 distinct keys and
  asserts the map stays at/below the cap and the newest entry survives.
