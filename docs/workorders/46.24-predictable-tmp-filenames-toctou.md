# WO 46.24 — 9 atomic-write sites use predictable .tmp + no O_NOFOLLOW — TOCTOU symlink race

## Status: Done

## Problem

**Location:** `src/session/carryover.rs:247, src/session/config/mod.rs:315, src/session/conversation.rs:291, src/session/undo.rs:252, src/session/session_index.rs:185, src/jobs/store.rs:96, src/tools/task/persist.rs:84, src/shared/audit.rs:143, src/main/cli_dispatch.rs:73`

An attacker who can write to ~/.local/share/kf-code/ can pre-create the .tmp file as a symlink to ~/.bashrc; next write truncates the target. 9 sites use with_extension('tmp') without O_EXCL. The codebase already has a correct pattern in tools/atomic_write.rs. Fix: adopt a secure_atomic_write helper across all sites.

## Root cause

Identified by external model audits (DeepSeek + MiniMax). See
/home/henrik/madlab/github/desktop/ds-bugs.md and mm-bugs.md for full evidence.

## Deferred (disclosed)

- **`src/shared/audit.rs:143`** — `AuditLog::new` opens the audit log
  with `OpenOptions::new().append(true).create(true).open(p)`. This is
  append-mode, not tmp+rename, so it's a different attack shape: an
  attacker who pre-creates `audit.ndjson` as a symlink to `~/.bashrc`
  makes our appends follow the link (write INTO the target, no
  truncation). The fix is `O_NOFOLLOW` on the open (the file must be a
  regular file or the open fails), via `std::os::unix::fs::OpenOptionsExt`
  with the raw `libc::O_NOFOLLOW` flag. DEFERRED because: (a) it's a
  different fix shape from the tmp+rename migration the workorder
  scoped; (b) `O_NOFOLLOW` is Unix-only (Windows needs a separate
  `FILE_FLAG_OPEN_REPARSE_POINT` path) and the audit sink has Windows
  callers; (c) the audit log is append-only and the attacker already
  needs write access to `~/.local/share/kf-code/` (the threat model is
  "tamper with own audit trail", not "clobber an arbitrary file").
  Remaining work: add `O_NOFOLLOW` to the audit-log open on Unix (one
  `OpenOptionsExt::mode` call) + a Windows equivalent or explicit
  Windows-acceptance note. Tracked here + in `state.md` pending.
- **`src/main/cli_dispatch.rs:73`** — `init_tracing` opens the log file
  with `OpenOptions::new().create(true).append(true).open(&log_file)`.
  Same append-mode shape as the audit log; same DEFERRED fix (O_NOFOLLOW
  on the open). Lower severity than audit (the log file is
  operator-readable debug output, not a security-relevant artifact).
  Tracked here + in `state.md` pending.
