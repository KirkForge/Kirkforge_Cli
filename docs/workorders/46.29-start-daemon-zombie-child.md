# WO 46.29 — start_daemon leaks a zombie child on every invocation

## Status: Done

## Problem

**Location:** `src/daemon/client.rs:316`

std::process::Command::spawn() returns a Child that is dropped on the next line; std Child does NOT auto-reap. Every kf-code sessions (and any other command that auto-starts the daemon) leaves a <defunct> child. Fix: use tokio::process::Command (its Child reaps on Drop) or spawn a detached reaper task.

## Root cause

Identified by external model audits (DeepSeek + MiniMax). See
/home/henrik/madlab/github/desktop/ds-bugs.md and mm-bugs.md for full evidence.

## Done

`start_daemon` (src/daemon/client.rs) now uses `tokio::process::Command`
instead of `std::process::Command`. Dropping the tokio `Child` moves it to the
runtime's orphan queue, which reaps the daemon when it eventually exits — no
`<defunct>` zombie under a still-running parent. `kill_on_drop` stays false
(default), so the daemon still outlives the client. No new dependency: tokio
workspace dep is `features = ["full"]` (includes `process`). The sole caller
`ensure_daemon_running` (already async) gained the matching `.await` — note
`tokio::process::Command::spawn()` itself is sync; only `status()`/`output()`
are async.

Not changed: `daemonize` (daemon/mod.rs) also drops its std `Child`, but it
immediately calls `std::process::exit(0)` — the parent exits, so init reaps.
Not a leak.

Test: none added. A direct reaping test would have to spawn the real binary
and poll /proc for `<defunct>` disappearance — racy and platform-specific.
Drop-reap is an upstream tokio guarantee; existing client tests (R1-R6) cover
the surrounding code.
