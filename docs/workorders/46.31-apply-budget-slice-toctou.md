# WO 46.31 — apply_budget_slice TOCTOU — state read then re-lock

## Status: Done

## Problem

**Location:** `src/session/budget.rs:272-287,319-326`

Lock A reads state, lock B (after release) does the slice. Between, init_from_config can rewrite ceiling/approaching_ratio. User-visible Keep-vs-Sliced outcome silently drifts. Fix: hold one lock across state read + slice.

## Done

Merged the two critical sections in `apply_budget_slice`: the budget
guard is now acquired once and held continuously from the `guard.state()`
read through `check_and_slice` (both `Success` and `FileContent` arms).
A concurrent `init_from_config`/`budget_set` can no longer rewrite
`ceiling`/`approaching_ratio` between the Keep-vs-Sliced decision and
the slice. Safety properties preserved: `maybe_escalate_stratum` locks
only `SESSION_MODE` (no budget nesting → no lock-order inversion under
the held guard), and `drop(guard)` before `dispatch_sliced` is kept in
both arms because listeners may lock the budget (std Mutex is not
reentrant). Net diff: ~6 lines; no signature/behavior change
single-threaded. Existing 8 `apply_budget_slice` tests + all 44
`session::budget` tests green.

Test note (disclosed): no new race test — the TOCTOU window requires an
interleaving point between two lock acquisitions, which has no injection
seam without restructuring production code; any single-threaded test
passes on both old and new code. Fix verified by inspection (single
continuous lock hold) + existing suite.
