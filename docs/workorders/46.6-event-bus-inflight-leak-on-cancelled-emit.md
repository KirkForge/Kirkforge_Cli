# WO 46.6 — EventBus inflight counter leaks when emit future is dropped — graceful_shutdown always times out

## Status: Done

## Problem

**Location:** `src/shared/event_bus.rs:294,313-314`

emit increments inflight under lock, drops lock, awaits handlers. If the emit future is dropped between lock release and re-lock, inflight is never decremented. graceful_shutdown waits for inflight==0; a leaked counter makes it hit the 10s timeout every time. Fix: use a Drop guard that decrements inflight via saturating_sub on drop.

## Root cause

See Problem section — identified by the post-WO-45 area audit + external review.

## Done

Fixed via `InflightGuard` — an RAII Drop guard holding an
`Arc<Mutex<State>>` clone, created inside the prepared block right after
`s.inflight += 1` and bound as `_guard` in `emit`'s scope so it lives
across the handler-await. On drop (normal return OR future cancellation
mid-await), the guard re-locks, does `s.inflight =
s.inflight.saturating_sub(1)`, and wakes drain waiters when
`shutting_down && inflight == 0`. The old manual decrement + drain-waker
block at the post-await site is removed (the guard subsumes both); only
the buffer-entry removal stays explicit (only the normal completion path
should touch the buffer).

Regression test `cancelled_emit_does_not_leak_inflight`: spawns an emit
with a 60s-sleep handler, waits for the handler to start (mpsc oneshot
signal — `Notify::notify_waiters` drops the signal if no waiter is parked
yet), aborts the emit task mid-await, asserts `inflight_count() == 0`,
then asserts `graceful_shutdown` returns within a 2s outer timeout (far
below the 10s leak symptom). Passes in 0.18s. Before the fix this would
leave `inflight` at 1 and trip the 2s timeout.

test). No new deps, no shared-file edits, no API change.
