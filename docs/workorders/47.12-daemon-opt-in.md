# WO 47.12 — Daemon becomes opt-in (~5.6K lines out of the default path)

## Status: Done

## Problem

The daemon owns only session metadata + instance broadcast — all derivable from a directory scan (the non-daemon path already does this). Make the daemon an opt-in feature (--with-daemon or a default-off cargo feature). The 2.5K daemon lines + rbac drag leave the default build.

Source: post-WO-46 size audit (kf-code-review.md, 2026-08-27). The codebase is
~110K production lines vs a ~30K lean-agent baseline; this WO is part of the
"Lean KirkForge" convergence toward ~85-88K.

## Root cause

Accumulation across WO series — features added per-WO with default features
and no size gate at add/remove time; crate boundaries drawn early never
revisited; process artifacts (tests, docs, dev tooling) counted as codebase.

## Approach

Read the Problem section. Implement the minimal correct reduction. Where a WO
deletes code, verify no production consumer breaks (grep + cargo check).
Where it moves code, keep public APIs stable or update all consumers.

## Files

src/daemon/**, Cargo.toml, src/main/cli_dispatch.rs

## Gate

`scripts/test-fast.sh` + `cargo clippy --all-targets -- -D warnings` +
`cargo fmt --check` + `cargo check --workspace --all-targets`. For deletions:
`git grep` proves zero production references before removal.

## Done

Runtime opt-in, not a cargo feature. A default-off cargo feature would
have required cfg-gating well beyond this WO's file list (lib.rs, cli.rs,
run_session.rs, tui/daemon_events.rs, tui/commands/fork.rs, jobs/* — jobd
reuses the daemon protocol helpers) plus a dual-feature CI matrix, and
would hard-break default UX (`kf-code daemon`, `kf-code jobd` error;
`--attach`/`--auto-resume`/picker stop working). Per the worker-prompt
caution, the opt-in is runtime instead:

- `daemon::autostart_enabled()` (mod.rs): `KF_CODE_DAEMON_AUTOSTART=1|true`
  re-enables auto-start; default off. Knob lives beside the existing
  `KF_CODE_DAEMON_TOKEN_FILE`/`KF_CODE_DAEMON_ROLE` readers.
- `try_list_recent`/`try_resolve_id` (client.rs): daemon unreachable +
  auto-start off → fall back to the on-disk session index
  (`list_sessions`/`resolve_session_id`, same newest-first data the daemon
  itself serves). Auto-start attempt failed → same fallback. `--attach`,
  `--auto-resume`, the TUI startup picker, and `/fork` resume keep working
  with no daemon and no spawn.
- Explicit `kf-code daemon` (and `jobd`) unchanged; a running daemon is
  always used (incl. TUI instance-channel push events).
- `--attach`/`--auto-resume` help text reworded (daemon-or-index);
  TECHNICAL.md daemon section documents the contract.
- Cargo.toml / cli_dispatch.rs: no change needed (no new deps; dispatch
  unchanged) though named in Files.

3 new tests: `autostart_is_opt_in` (parse matrix),
`try_list_recent_falls_back_to_disk_when_autostart_disabled` (ordering +
presence), `try_resolve_id_falls_back_to_disk_when_autostart_disabled`
(exact + prefix).

DEFERRED (disclosed): the compile-time excision — "~5.6K lines out of the
default build" via a default-off `daemon` cargo feature dropping src/daemon/**

6+ files outside this WO's scope, and CI (ci-local.sh, test-fast/full,

would never compile/test in CI and rot. Remaining: land the feature gate
with its consumer cfg sites + CI matrix as a dedicated WO. Tracked in
