# WO 47 — Response cache: key omits generation config (wrong-model replays) + 64MiB sync disk reads on the async path

## Status: Done

## Problem

HIGH. (1) CacheKey::new (src/adapters/caching.rs:182) hashes only (model, messages, tools, response_format) — seed, max_tokens, extended_thinking, budget_tokens, provider/endpoint are NOT in the key. Request B with thinking=true+max_tokens=64000 replays request A's cached non-thinking response; two providers sharing a model name share entries. Fix: adapters produce a canonical RequestFingerprint (provider+endpoint+model+generation config) and the cache hashes that. (2) cache.get() does std::fs::metadata + read + serde_json::from_slice synchronously inside async stream() — a hit on a 64MiB entry (MAX_CACHE_FILE_BYTES) stalls the tokio worker on slow storage. Fix: spawn_blocking for the disk tier. (Both GPT #1/#2 and DS M9 — independently confirmed.)

Source: multi-model audit vetting 2026-08-27 (mm-bugs.md, ds-bugs.md, kimi-bugs.md,
sonnet-bugs.md, gpt-bugs.md). Top-severity claims verified against the code at
dbfd8bb0 before filing.

## Done

Both defects fixed in `src/adapters/caching.rs` (commits 739fec47, 31ad3188):

1. **Key**: `CachingAdapter` captures the generation knobs at `set_*`
   call time (seed, max_tokens, extended_thinking, budget_tokens,
   computer_use dims — they reach the inner adapter through the wrapper,
   which previously forwarded without remembering them) and
   `maybe_wrap_cached` pins a provider/endpoint scope from Config
   (anthropic_provider, ollama_host, opencode_zen_endpoint,
   anthropic_api_base, aws_region, gcp_project_id, gcp_region).
   `request_fingerprint()` folds scope + model + knobs into the hashed
   key material. Sibling-site check: `streaming_timeout` is deliberately
   NOT in the key (client-side idle timeout, does not shape the
   response); `computer_use_dims` IS (it rewrites the request).
2. **Disk tier**: `lookup_memory`/`read_disk`/`write_disk` helpers; new
   `get_async`/`put_async` keep the memory tier sync (HashMap lookup)
   and run the disk tier via `tokio::task::spawn_blocking`. `stream()`
   uses the async variants. `put`'s disk write was the same defect
   class (fs::write on a worker inside the forwarder task) — fixed in
   the same pass. Sync `get`/`put` remain for tests.

Wrap-vs-set ordering verified at all 4 `maybe_wrap_cached` call sites:
wrap happens first, the executor pushes `set_*` on the wrapper
(executor/mod.rs:244-266), so capture sees every push.
