# WO 47 — edit_file fuzzy fallback corrupts the trailing newline on multi-line matches

## Status: Done

## Problem

HIGH — data corruption with a repro. src/tools/edit_file.rs:308-316: when old_string matches only after whitespace normalization AND spans ≥2 lines, byte_end = line_byte_end(last_line) includes the line's own \n (newline_positions[line_idx] + 1), so the replacement splices the following line onto the replacement's last line and drops the newline. Verified empirically (CRLF and LF) by DS. Existing CRLF tests only cover single-line fuzzy matches. Fix: line_byte_end(last) = newline_positions[last_line] (no +1); add a multi-line fuzzy CRLF regression test.

## Done

Fixed in src/tools/edit_file.rs: the fuzzy-fallback `line_byte_end` closure now
returns the end of the last matched line's content BEFORE its terminator
(`\n`, or `\r\n` on CRLF) instead of one byte past the `\n`, so the terminator
stays in the file and the following line survives on its own line. The fix
applies uniformly: single-line fuzzy matches (e.g. LF old_string against a
CRLF file) route through the same closure and had the same splice bug —
verified by trace and empirically (no pre-existing test covered it;
`test_fuzzy_fallback_crlf_via_whitespace_normalization` takes the exact-match
path because its old_string is an exact substring).

Regression tests: `test_fuzzy_fallback_multiline_preserves_following_line_lf`,
`test_fuzzy_fallback_multiline_preserves_following_line_crlf`,
`test_fuzzy_fallback_single_line_crlf_preserves_following_line` (all red
pre-fix, green post-fix).
