# WO 47 — Verifiers run sequentially per turn (up to 7 min) + sync preamble reads + unbounded verdict cache

## Status: Done

All three items shipped (one commit each):

1. `verify_event` runs verifiers concurrently via futures-util
   `buffer_unordered(4)` (futures built in a plain loop — a stream closure
   in the future's type trips rustc's higher-ranked Send-inference
   limitation, 5 downstream spawn sites went red). Results re-sorted to
   registration order before the decisive pick, so tie-breaking is
   deterministic. Per-verifier timeout/panic-guard unchanged.
2. `build_stream_preamble` is now async; the top-file reads + minify run
   as one `spawn_blocking` batch (fn's sole call site awaits it).
3. `verdict_cache` is a bounded `VerdictCache` (map + insertion VecDeque,
   FIFO eviction past 256 entries); resolves the `ponytail: unbounded`
   annotation. New test `verdict_cache_is_bounded_with_fifo_eviction`.

Note: the `Verifier` trait is async (`async_trait`), not the sync
`BusVerifier` the problem statement assumed — so bounded-concurrent
futures (not `spawn_blocking` per verifier) is the correct minimal fix;
real verifiers already `spawn_blocking` their cargo subprocesses
internally (types.rs). The dispatch.rs:185 bus-under-mutex concern is a
different path (VerifierBus) and stays deferred (WO 43.26 tail).

## Problem

HIGH perf. (1) VerifierHandler::verify_event runs 14 verifiers SEQUENTIALLY (mm-H22) — worst case ~7min/turn when tools are slow. They're independent — run them concurrently (join_all / JoinSet) bounded by a small semaphore. (2) build_stream_preamble does sync std::fs::read_to_string for up to 50 files per turn (mm-H23) — move to spawn_blocking or batch. (3) verifier_cache is an unbounded HashMap keyed by (PathBuf, u64) (mm-H26) — add a cap with simple eviction.

Source: multi-model audit vetting 2026-08-27 (mm-bugs.md, ds-bugs.md, kimi-bugs.md,
sonnet-bugs.md, gpt-bugs.md). Top-severity claims verified against the code at
dbfd8bb0 before filing.

## Root cause

See Problem — per-site. Cross-cutting theme: invariants enforced at one layer
(pre_run, session daemon) instead of the component that owns the operation;
and WO fixes applied at one site of a duplicated pattern.

## Approach
