# WO 47 — jobd: notify_one loses shutdown/reload + run_bash_job double-completion race

## Status: Done

## Problem

MEDIUM. (1) src/jobs/daemon.rs:105,240,244,348 — the main loop and accept loop both await the SAME Notify woken with notify_one() — exactly one waiter wakes; if the accept loop wins, the scheduler keeps running with a dead socket (same for reload). Fix: notify_waiters() for these broadcast-semantics signals, or separate Notify per loop. (2) src/jobs/runner.rs:164-221 — run_bash_job polls registry.get(id) reading job.status under a DIFFERENT lock acquisition than the mutation: the poll can observe terminal state and call record_run/registry.remove while a concurrent cancel()/watcher completes the same record — remove() KILLS the child racing the watcher's reap. Fix: per-job terminal signal instead of poll-then-mutate; make record_run idempotent keyed on run_id.

Source: multi-model audit vetting 2026-08-27 (mm-bugs.md, ds-bugs.md, kimi-bugs.md,
sonnet-bugs.md, gpt-bugs.md). Top-severity claims verified against the code at
dbfd8bb0 before filing.

## Root cause

See Problem — per-site. Cross-cutting theme: invariants enforced at one layer
(pre_run, session daemon) instead of the component that owns the operation;
and WO fixes applied at one site of a duplicated pattern.

## Done

1. `src/jobs/daemon.rs` — shutdown now reaches both Notify waiters.
   `handle_client`'s Shutdown/QuitAll arms call `notify_waiters()`
   (direct broadcast on the socket path used by `jobd --stop` and the
   tests), and each loop's select arm re-broadcasts
   (`socket_shutdown.notify_waiters()` / `shutdown.notify_waiters()`)
   before breaking, so a `notify_one()` from the shared signal helper
   (`spawn_shutdown_signal_handlers`, src/daemon/mod.rs — outside this
   WO's file scope) still reaches the loop that lost the race. reload
   was deliberately LEFT on `notify_one()`: it has exactly one waiter
   (the scheduler loop; the accept loop never awaits it — the audit's
   "same for reload" did not hold), and notify_one's stored permit
   survives the scheduler being mid-iteration, which notify_waiters
   would drop. Known ceiling (annotated in code): while the scheduler
   is mid-iteration (running due jobs, ≤300s/job under
   DEFAULT_JOB_TIMEOUT), no Notify-based signal can reach it —
   structural while the shared signal helper only holds a Notify;
   pre-existing, strictly narrowed by this fix.
2. `src/jobs/runner.rs` — run_bash_job no longer poll-then-mutates a
   mid-flight record. (a) Cancelled status is flipped by `cancel()`
   BEFORE the child dies; the watcher completes the record (drained
   output, finished_at) within its reap (2s) + drain-join (2s) caps.
   The poll now waits a 5s settle window after the first Cancelled
   sighting, then records from a fresh snapshot — the Cancelled run's
   artifacts carry the drained output instead of an empty mid-cancel
   snapshot. Completed/Failed are set in the same lock acquisition as
   their output (watcher / watchdog) — born final, no grace needed.
   (b) Both `registry.remove(id)` calls dropped: remove() kills a
   still-live child, racing cancel()'s kill and the watcher's reap
   (recycled-pid hazard) and discarding the entry so the watcher's
   final output update was lost. Terminal scheduled-run entries now
   follow the standard registry lifecycle (MAX_JOBS cap eviction in
   spawn() + /jobs clean), same as interactive background jobs.
   (c) The audit's "make record_run idempotent (keyed on run_id)"
   (src/jobs/store.rs — shared file, out of scope) was not needed:
   each invocation records exactly once on exactly one path, run_ids
   are per-invocation (nanos+pid), and record_run's atomic_write is
   keyed by run_id (overwrite, not append) — no duplicate-row vector
   remains once (a)+(b) land. Same for the per-job oneshot/Notify
   (src/session/bash_jobs.rs — shared file): the settle window closes
   the observable race without touching the registry internals.
3. Regression test `cancelled_bash_job_records_drained_output`
   (runner.rs tests): `echo marker; sleep 30` auto-approved, cancelled
   via the global registry mid-run; asserts the recorded run is
   Cancelled AND the stdout artifact contains the marker (empty before
   the fix). All 7 jobs:: tests green.
