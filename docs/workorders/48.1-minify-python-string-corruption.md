# WO 48 — minify_python strips # inside string literals — corrupts source on read AND on disk

## Status: Done

## Problem

P1. src/shared/minify/lang.rs:574 — the # comment stripper is string-blind: "http://x#anchor" truncates to "http://x. Live on the default read_file auto-minify path (>4KiB .py), and the edit_file envelope round-trip can write the corruption back to disk (model edits minified content, edit writes it). Fix: track string literal state (single/double/triple quotes) in the minifier; only strip # outside strings. Regression test: URL-with-fragment literal survives minify+expand round-trip.

Source: post-WO-47 baseline audit (kf-code-review.md, 2026-08-28, HEAD e4725bd6).

## Done

`minify_python` (src/shared/minify/lang.rs) now tracks string-literal state
while scanning — `string_char: Option<char>` + `in_triple`, escape-aware
(backslash consumes the next char), triple close requires a delimiter run of
three. `#` strips only outside literals. Docstring detection/stripping
behavior preserved; the docstring skip scan is also escape-aware now.
Also fixed in the same branch: the old comment-skip idiom
(`while chars.next().is_some() && peek != '\n'`) consumed the char after a
bare `#`-then-newline line; replaced with a peek-based loop that leaves the
newline for the main loop.

Regression tests (lang.rs tests mod):
- `test_minify_python_keeps_hash_in_string_literals`
- `test_minify_python_keeps_hash_in_triple_quoted_strings`
- `test_minify_python_minify_expand_round_trip_url_fragment`

Sibling-site grep (per Approach): rust/js/go/c/java minifiers already
string-aware; AST path string-aware by construction. Ruby/shell minifiers are
line-based and would drop a pathological whole-line `'#'` literal or a
heredoc line starting with `#` — out of WO scope, disclosed for triage.
