# WO 48 — minify_js_like truncates at // inside regex literals — js/ts corruption on the disk write-back chain

## Status: Done

## Problem

P1. src/shared/minify/lang.rs:709 — the // comment stripper is regex-literal-blind: /https?:\/\// truncates at the first // inside the regex, eating the newline. 48.1's sibling-grep claimed js was string-aware — it is, for quotes, but not regex literals. Affects js/ts on the same read_file→edit→write disk chain. Fix: track regex-literal state (a / that follows an operator/(-position opens a regex; division context vs regex context), or simpler: require // to be preceded by whitespace/start/([=:,;! and not be inside a string or regex.

Source: post-WO-48 sweep audit (kf-code-review.md, 2026-08-28, HEAD 9f498f2b).

See Problem. Theme: per-language minifier patches instead of one lexer pass;

## Done

`minify_js_like` (`src/shared/minify/lang.rs`) now tracks regex-literal
state: a `/` opens a regex when the previous non-whitespace token is an
operator/punctuator (`( [ { , ; : = ! + - * % < > & | ^ ~ ?` or
start-of-input) or an expression keyword (`return` `typeof` `instanceof`
`in` `of` `new` `delete` `void` `case` `do` `else` `yield` `await`
`throw`); inside a regex the body is emitted verbatim (`\` escapes skip,
`[...]` classes make `/` literal, an unescaped `/` outside a class
closes, a raw newline bails — regex literals can't span lines, which
bounds misdetection damage to one line). `//` and `/*` still win at
regex position (matches JS lexing: a regex body can't start with `/`
or `*`), so `x = // comment` still strips. Division contexts
(identifier/number/`)`/`]`/quote before the slash) are pushed as-is.

Sibling site (same root cause, on the same write-back chain, required by
the round-trip gate): `fallback_c_like` in `src/shared/minify/expand.rs`
was also regex-blind — its `:` arm inserted a space inside regex bodies
(`/https?: \/\//g`) and its quote handling would mis-fire on regexes
containing quotes. It now shares the same heuristic (`prev_opens_regex`,
`pub(super)` in lang.rs) and emits regex bodies verbatim.

Disclosed ceiling (ponytail: in `prev_opens_regex`): regexes in
division-looking contexts (after `)`, `}`, an identifier, or a number)
stay untracked — a `//`, `/*`, or quote inside one of those can still
corrupt. Tracking those needs a real tokenizer (precedence: `)` is both
call-end and grouping-end). Also template-literal `${...}` innards stay
opaque (pre-existing).
