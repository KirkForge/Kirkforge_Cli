## Problem

## Done

Both mark_read sites sit AFTER the tool body ran with the outcome in
scope — no timing move needed (the WO's "dispatch may mark before the
body" worry didn't materialize). Threaded the existing
`tool_outcome_success` helper into both conditions:

- `spawn_batch` (dispatch.rs): `(name == "read_file" || name ==
  "read_image") && tool_outcome_success(o)` — covers same-batch
  read-then-edit (the intra-batch gate the immediate marking exists for).
- `record_tool_result` (turn.rs): same condition on the `outcome` param —
  covers cross-batch state and direct record calls.

Gate-denied reads never reached either site (they `continue`/return
before marking), so the outcome check covers exactly the I/O-failure
window. Truncated reads (`FileContent { truncated: true }`) still count
as successful — the model saw the file's content.

Regression test `failed_read_does_not_satisfy_read_before_edit_gate`
(tests/dispatch.rs): a `read_file` MockTool returning
`ToolOutcome::Failure` followed by a same-batch `write_file` on the
existing file — write must be denied and the file untouched. Mirror
`test_read_then_write_in_same_batch_passes_read_gate` (successful read)
still green, pinning both directions.
