# WO 48 — call_id missing from the streaming event protocol (WO-10-era parallel-stream mixing)

## Status: Done

## Problem

P1. `TurnEvent::ToolStart` / `ToolResult` / `BashPartialOutput` carry only a
tool *name*. Two parallel same-name calls (the classic case: two `bash` calls
in one batch, both streaming PTY output) are indistinguishable on the wire:
the TUI routes `BashPartialOutput` to "the last streaming tool card"
(tui/events.rs) and pairs `ToolResult` with a placeholder by name prefix
(`remove_tool_placeholder`), so call A's chunks land in call B's card, and a
result finalizes the wrong sibling's placeholder — the ghost-spinner /
mixed-output failure the pre-44.38 era papers over positionally. The model
already assigns every call a unique id (`ToolInvocation.id`); the protocol
just never carried it. Noted in the code itself
(`ponytail: TurnEvent carries no call id ... true fix needs a call_id`,
tui/events.rs, WO 46.35).

## Root cause

The event protocol predates parallel tool dispatch: name + position were
sufficient when tools ran sequentially. WO 15.7 introduced parallel batches,
WO 44.38 moved `ToolStart` to dispatch time, WO 46.35 made the name-based
pairing positional — but streaming identity was never threaded through.

## Approach

Carry `call_id` end to end and route by it; keep name-based fallback for
events with an empty id (back-compat with old replay traces and synthetic
results):

1. `TurnEvent` protocol: `ToolStart`/`ToolResult` gain `call_id: String`;
   `BashPartialOutput(String)` becomes `BashPartialOutput { call_id, text }`.
2. Emitters stamp the model-assigned id (`ToolInvocation.id`) at every site:
   dispatch spawn (2 ToolStart + 2 ToolResult), turn.rs record-time (4),
   pre_run.rs skips (10), helpers/outcome.rs (7). Only synthesized events
   without an invocation would carry an empty id — none exist on these paths.
3. PTY threading: `ToolContext` gains `call_id` (set in `run_prepared_call`
   from the invocation id); the bash PTY arm passes it to `run_with_pty`,
   which stamps every chunk. The channel type is unchanged — the event
   itself carries the id from the forwarding site where it is known.
4. TUI routing: `ConversationState.streaming_tool_index:
   HashMap<call_id, message index>`. `ToolStart` registers its placeholder
   (reusing a chunk-created card if chunks raced ahead); `BashPartialOutput`
   routes by call_id, creating + registering a card for unknown ids;
   `ToolResult` finalizes by call_id and removes the entry. Indexes are
   rebased on mid-deque removal (`rebase_streaming_indexes`) and remapped in
   `prune_display_messages`; cleared on TurnComplete / /clear / compaction /
   fork swap. Empty call_id keeps the legacy name-based paths.
5. Replay: `RecordedToolCall` gains `#[serde(default)] call_id: String` —
   old traces deserialize with "" and pair by name;
   `fill_recorded_tool_result` pairs call_id-first, name-second. The
   stream-json `tool_start`/`tool_result` lines carry `call_id` additively.
