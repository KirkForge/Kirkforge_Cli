# WO 48 — read_file scans to EOF even for offset=100000,limit=20 — O(file) cost for an O(window) request

## Status: Done

## Problem

MEDIUM. src/tools/read_file.rs:93-146 — the streaming loop reads every line to EOF because offset-beyond-length detection and the offset>=raw_total check need raw_total. With max_read_size=0 (unlimited, API-permitted) an offset=900M request scans 900M+ bytes for 10 lines. FIX: when offset>0 and the file is seekable, skip N lines with a counting pass that DISCARDS (no buffering beyond one line) until offset reached — the memory is already bounded, so the win is stopping early when the window is filled AND offset is satisfied (no need for raw_total when the window completes: only the offset-beyond-EOF error needs it, and that can be detected by window-empty + EOF). Keep whole-file semantics for offset=0.

(2026-08-29, branch `wo48.33`, not merged) The streaming loop now breaks as
soon as an offset>0 window fills (≥1 line selected and `selected_lines.len()
>= limit`) — a deep window costs O(offset+limit) reads instead of O(file);
memory was already O(limit) since WO 47.33. The only consumers of the true
total that survive: beyond-EOF error (unreachable on the early-stop path —
it needs window-empty+EOF, which always scans fully, so `raw_total` is exact
there), and the pagination header. Disclosed behavior changes on the
early-stop path: header reads `showing lines A-B of B+` (the `+` marks an
unscanned tail), and `truncated=true` is reported even when the window ends
exactly at EOF (EOF unverified — `ponytail:` comment at the break; one extra
read_until would disambiguate, not worth the branch). `total_bytes` counts
only scanned bytes, so the auto-minify size threshold now applies to the
scanned prefix for offset>0 reads (more honest — only the window is
returned). offset=0 behavior unchanged (full scan retained: whole-file
display + exact pagination header legitimately need `raw_total`).
