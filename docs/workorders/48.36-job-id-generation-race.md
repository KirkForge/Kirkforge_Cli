# WO 48.36 — job-id generation race: two clients can mint the same id

## Status: Done

## Problem

LOW/MEDIUM. `generate_job_id` (src/jobs/schedule.rs) was read-dir →
max-seq → +1 with no reservation: two concurrent callers both read
max_seq=N and both mint `job-{date}-{N+1}`. `atomic_write` prevents
job.json corruption but not logical overwrite — the second save silently
replaces the first job (same id → same dir). Sole caller:
`handle_schedule_command` (src/tui/commands/jobs.rs).

Source: post-WO-48 sweep audit.

## Root cause

Read-then-write with no atomic step between observation and commitment;
the id existed only as a string, not as an on-disk claim.

## Approach

Reservation loop: after computing max_seq, `create_dir` the candidate
`job-{date}-{seq:03}`; on `AlreadyExists`, seq+=1 retry (bounded 1000
attempts). The reserved dir IS the id — `create_dir` is atomic on unix
and Windows (std maps ERROR_ALREADY_EXISTS to ErrorKind::AlreadyExists),
so racers can never hold the same seq. Reserved dir gets 0o700 (parity
with save-created job dirs). `JobStore::save` already creates the dir
only `if !dir.exists()` (src/jobs/store.rs) — it reuses the reservation
as-is; no store change needed.

## Files

src/jobs/schedule.rs

## Gate

cargo check --workspace --all-targets; clippy -p kf-code --all-targets
-D warnings; targeted `jobs::` tests (68 passed); fmt --check.

## Done

Fixed as above. New tests: `generate_job_id_concurrent_calls_get_distinct_ids`
(8 threads, all ids distinct — create_dir is the arbiter),
`generate_job_id_on_missing_dir_creates_it` (generate now creates the
jobs root, previously left to save). Existing increment test unchanged
and green. Known ceiling: a reserved-but-unsaved dir (save failed) keeps
occupying its seq — benign, `/jobs clean` territory, not addressed here.
