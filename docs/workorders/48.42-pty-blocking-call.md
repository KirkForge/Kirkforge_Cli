# WO 48.42 — PTY bash call is fully blocking: no timeout, no Esc cancel, child never killed

## Status: Done

## Problem

P2. `src/tools/bash.rs` called `run_with_pty` synchronously inside the async
`Tool::run` body. `run_with_pty` (`src/session/bash_runner/pty.rs`) blocks on
`reader.read()` and `child.wait()`, so an `interactive: true` call wedges the
tokio worker: `dispatch.rs`'s `handle.await` never completes on
`sleep infinity`, the tool cancel token (`ctx.token`, Esc) is never observed,
no timeout applies, and the PTY child is never killed.

## Root cause

The PTY integration (feature `pty`, default-off) was written as a sync helper
called from async context — none of the race/kill machinery every other bash
spawn path has (`run_shell_with_token`'s token+timeout select, run_docker's
kill-on-drop) exists on it.

## Approach

1. `pty.rs`: `run_with_pty` takes a `std::sync::mpsc::Receiver<()>` kill
   request. After spawn it splits out the vendor `clone_killer()` handle into
   a small std thread that kills on request (portable-pty's documented API
   for signaling independently of the thread blocked in `wait`). The channel
   latches a request that raced ahead of the spawn — mpsc buffers it until
   the watcher starts, so a pre-cancelled call still kills its child. The
   reader loop now breaks on read error (EIO is the post-kill shape) so it
   always reaches `child.wait()` — an early `?` return would zombie the
   killed child.
2. `bash.rs` PTY arm: `run_with_pty` runs via `tokio::task::spawn_blocking`
   (owns clones of cmd/workdir/event_tx/call_id — the 48.31 call_id stamping
   is unchanged inside the closure), and the join is raced in `select!`
   against `ctx.token.cancelled()` and the same `timeout` budget non-PTY bash
   uses (`timeout_secs`, default 30, clamped to 24h). Cancel/timeout send the
   kill request and return `ToolError::Cancelled` / `ToolError::Timeout`.
   Result mapping (exit code, `PTY allocation failed`) preserved; join panic
   maps to `ToolError::Internal`.

Kill ceiling (documented `ponytail:` in pty.rs): unix kill is SIGHUP to the
direct child only — an HUP-ignoring grandchild survives; killpg upgrade if
that ever matters (needs raw libc, a new dep).
