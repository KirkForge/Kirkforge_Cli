# WO 48 — Minify VFS cache keyed on mtime.as_secs() — same-second rewrite serves the stale pre-edit view

## Status: Done

## Problem

P2. src/shared/minify/mod.rs:130-153 — cache key uses mtime seconds; a file rewritten within the same second after an edit serves the stale pre-edit minified content on the next read (edit_file envelope round-trip race). Fix: include nanos (as_nanos) in the key, or key on content hash. Nanos is the smaller fix.

Source: Sweep 5 (kf-code-review.md, 2026-08-29, HEAD fae3ada2). 3 P1 (minify rust/py entry-exit logic — the un-treated half of the 48.x scanner wave), 4 P2. All verified with adversarial round-trip harnesses.

## Done

Fixed in `minify_source_impl` (src/shared/minify/mod.rs): the VFS cache key is
now nanos-granular — `duration_since(UNIX_EPOCH).as_nanos()` instead of
`.as_secs()`, with the LRU static type widened `(PathBuf, u64)` →
`(PathBuf, u128)`. The (path, mtime) shape is unchanged; the key is in-memory
only (grep confirmed no persistence/serialization of the mtime key anywhere —
CachedIndex and friends never see it). Regression test:
`test_same_second_rewrite_serves_fresh_content` — mtimes pinned via
`set_modified` 500ms apart within the same second, so the race is deterministic
(no fs timing). Old secs key → stale hit (test fails); nanos key → fresh
minify (passes).
