## Findings

### 50.01.1 — HIGH — `extract_unresolved_verifier_findings` runs on PRE-compaction history, not post-compaction

- **File**: `src/session/executor/loop_.rs:484`
- **Problem**: The `history` variable at line 295 (`let history = self.conversation.all().to_vec();`) is the PRE-compaction snapshot. After summarization (line 395) or naive truncation (line 462), `self.conversation` is replaced via `replace_all_async`. But at line 484, `extract_unresolved_verifier_findings(&history)` still references the OUTER `history` — the pre-compaction message list. The inner `let history = self.conversation.all();` at line 445 shadows it only within the `if !did_summarize` block and does not extend to line 484. So the "pin unresolved verifier findings in compaction tail" step (WO 22.6-R6) extracts findings from the OLD conversation that was just compacted away, then appends them to the NEW conversation. If the compacted history contained verifier findings that the compaction itself dropped/stubbed, those findings are re-injected from the stale snapshot — defeating the compaction and potentially re-introducing context the summarizer explicitly removed.
- **Impact**: Compaction's token reduction is partially undone by re-pinning findings from the old history. In the summarize path, the LLM summary already incorporated verifier state, so the re-pin duplicates it. In the naive path, stubbed tool results may have contained the verifier findings — extracting from the pre-stub history re-inserts full finding text that compaction intentionally stubbed.
- **Fix**: Re-snapshot the conversation after `replace_all_async` and before `extract_unresolved_verifier_findings`: `let post_history = self.conversation.all().to_vec();` then pass `&post_history`. Or move the extract call to read from `self.conversation.all()` directly.
- **Effort**: S

### 50.01.2 — MEDIUM — `is_read_only_bash` does not block single `&` (background operator)

- **File**: `src/session/executor/helpers/mod.rs:175-183`
- **Problem**: The metacharacter check blocks `>`, `;`, `&&`, `||`, `$(`, and backtick, but does NOT block a single `&` (shell background operator). A command like `cat README.md & rm -rf /tmp/x` would: the first segment `cat README.md ` — wait, actually the pipe-split happens first at line 143 (`trimmed.split('|')`), and `&` is not a pipe. So the whole string `cat README.md & rm -rf /tmp/x` is ONE segment. That segment contains `&` but NOT `&&`. The check at 177 is `seg.contains("&&")` — a single `&` does not match `&&`. So `cat README.md & rm -rf /tmp/x` passes the metacharacter gate if `cat` is in `READ_ONLY_COMMANDS` (it is). The shell would run `cat README.md` in the background and `rm -rf /tmp/x` in the foreground — a mutating command auto-approved as "read-only".
- **Impact**: A read-only-bash classification bypass via the `&` background operator. Under `auto_approve = false`, this only affects whether the bash call is auto-approved vs. asks for approval — the deny-list and bash sandbox still run. Under `auto_approve = true` (operator opt-in), this auto-approves a command with a mutating background/foreground pair. Also affects plan-mode: `is_read_only_bash` gates plan-mode bash, so `cat x & rm y` would run in plan mode.
- **Fix**: Add `seg.contains('&')` to the metacharacter block at line 175-183, or add a separate `seg.contains('&') && !seg.contains("&&")` check if you want to be precise (but `&&` is already blocked, so blocking bare `&` is strictly tighter).
- **Effort**: S

### 50.01.3 — MEDIUM — `bus_event` and `error_event` in `emit_tool_event_and_correct` are dead code

- **File**: `src/session/executor/dispatch.rs:94-174`
- **Problem**: The function builds `bus_event` (lines 94-159) and `error_event` (lines 163-173) as `Option<BusEvent>`, then immediately discards both with `let _ = bus_event;` (line 161) and `let _ = error_event;` (line 174). The actual verifier bus runs via `VerifyContext` (lines 189-240), which constructs its own context from `args` directly — it does not consume `bus_event` or `error_event`. These are ~80 lines of dead code that build `FileReadEvent`, `FileWriteEvent`, `EditEvent`, `BashExecEvent`, and `ToolErrorEvent` structs that are never consumed. This is leftover from the WO 47.14 unification: the old `BusEvent`-driven path was replaced by `VerifyContext`, but the event-construction code was never deleted.
- **Impact**: Dead code — no runtime impact, but misleading. A reader assumes `bus_event` feeds the verifier bus; it does not. The `FileReadEvent` path (lines 95-106) sets `size_bytes: 0` and `truncated: false` as placeholders, which would be wrong if it were live. Maintenance burden and confusion.
- **Fix**: Delete lines 92-174 (the `bus_event` and `error_event` construction + the two `let _ =` lines). The `use crate::session::verifier::types::*;` at line 92 may become unused — check and remove if so.
- **Effort**: S

### 50.01.4 — MEDIUM — `handle_tool_outcome` uses sync `conversation.append()` in two error-recovery paths, blocking the async runtime

- **File**: `src/session/executor/helpers/outcome.rs:162, 199`
- **Problem**: In the `ToolOutcome::Error` and `ToolOutcome::Failure` arms, the error-recovery hint injection calls `conversation.append(recovery_msg)?` (lines 162, 199) — the SYNC `append`, not `append_async`. The sync `append` (conversation.rs:138) does `std::fs::OpenOptions` + `write_all` + `sync_all` on the Tokio worker thread. Every other append in the executor uses `append_async` (which offloads to `spawn_blocking`). These two paths are hit on every tool error/failure, so a slow disk stalls the async runtime on the error path.
- **Impact**: A tool error with a slow/busy disk blocks the Tokio worker thread for the duration of the `sync_all` call. Under a burst of tool errors, this can stall the executor's event loop. Not a correctness bug — the sync append is functionally correct — but an async-hygiene violation in a hot path.
- **Fix**: Change `conversation.append(recovery_msg)?` to `conversation.append_async(recovery_msg).await?` at both sites. The function `handle_tool_outcome` is already `async`, so no signature change needed.
- **Effort**: S

### 50.01.5 — MEDIUM — `emit_correction_results` uses sync `conversation.append()` in a loop

- **File**: `src/session/executor/helpers/outcome.rs:280`
- **Problem**: `emit_correction_results` iterates `results` and calls `conversation.append(Message { ... })?` (sync) for each `CorrectionResult`. This is called after every file-modifying/bash tool call (turn.rs:838, 937). If a verifier returns N correction results, this does N sync `sync_all` calls on the Tokio worker. The function is NOT `async` (line 264), so it cannot use `append_async` without a signature change — but it's called from an `async` context (`emit_correction_results(crs, tc, event_tx, &mut self.conversation).await?` — wait, it's not awaited, it's called without `.await` because it's sync).
- **Impact**: Same as 50.01.4 — sync disk I/O on the async worker. Compounded by N corrections per tool call. A build verifier returning 10 lint findings does 10 `sync_all` calls on the worker thread.
- **Fix**: Make `emit_correction_results` async and use `append_async`. The call sites (turn.rs:838, 937) already `await` other calls in the same expression chain — update them to `.await` this one too.
- **Effort**: S

### 50.01.6 — LOW — `DoomLoopTracker::observe` truncation allocates even for short errors

- **File**: `src/session/executor/loop_.rs:72-85`
- **Problem**: The truncation logic checks `error.len() > Self::ERROR_TRUNCATE` (200 bytes). For errors under 200 bytes (the common case — most tool errors are short), it takes the `else` branch and does `error.to_string()` — a heap allocation cloning the full error string. The `truncated` variable is then used for the window comparison and storage. For a 50-byte error, this clones 50 bytes unnecessarily (the original `error: &str` could be compared directly and only cloned when stored in the window).
- **Impact**: Negligible — one `String` allocation per tool error. The tracker runs once per failed tool call, not in a hot loop. Purely a micro-optimization.
- **Fix**: Compare against `error` directly for the run-count update, and only allocate the truncated `String` when pushing into the window. Or leave as-is — the cost is trivial.
- **Effort**: S

### 50.01.7 — LOW — `extract_bash_metrics` stderr offset uses hard-coded `+9` magic number

- **File**: `src/session/executor/helpers/mod.rs:317`
- **Problem**: The code `message[pos + 9..].len()` computes the stderr length by skipping 9 bytes after `\nstderr:\n`. The string `"\nstderr:\n"` is 9 bytes (`\n` + `stderr:` + `\n` = 1+7+1 = 9). The `+9` is correct but is a magic number — if the separator string changes, this silently breaks. There's also a subtle issue: `stdout_len` is set to `pos` (the position of `\nstderr:\n`), which is the length of everything BEFORE the stderr marker — this includes the exit-code line AND any stdout text. The naming `stdout_len` is misleading because it's really "length of the prefix before stderr", not "stdout length".
- **Impact**: Cosmetic / maintainability. The metrics are used for the verifier bus `BashExecEvent.stdout_len`/`stderr_len`, which feed the git verifier and metrics log. A reader misreading `stdout_len` as "actual stdout byte count" would be wrong if the error message has a multi-line prefix.
- **Fix**: Replace `pos + 9` with `pos + "\nstderr:\n".len()`. Rename `stdout_len` to `prefix_len` or document that it includes the exit-code line.
- **Effort**: S

### 50.01.11 — LOW — `turn_count` increments even on cancelled/errored turns, affecting memory extraction cadence

- **File**: `src/session/executor/turn.rs:133`
- **Problem**: `self.turn_count += 1` runs unconditionally after `run_turn_inner` returns, regardless of whether the turn succeeded, was cancelled, or errored. The memory extraction gate at line 134 (`self.turn_count % EXTRACT_EVERY_N_TURNS == 0`) then fires on the 3rd, 6th, 9th turn count — but if turns 1 and 2 were cancelled (no real user/assistant exchange), the extraction on "turn 3" runs against a history that may not have a meaningful last-assistant message. The `is_preference_like(user_input)` check at line 135 does catch keyword-triggered extraction regardless, but the cadence-based path can fire on a turn that produced no assistant content, making `last_assistant` find an older message.
- **Impact**: Low — the extraction guards `if let (Some(u), Some(a)) = (last_user, last_assistant)` (line 145), so a turn with no assistant message just skips extraction. The only oddity is that the cadence drifts: after 2 cancelled turns, the 3rd real turn gets extraction at count=3 instead of count=1. Not a bug, just imprecise.
- **Fix**: Only increment `turn_count` on `result.is_ok()` and when the turn actually produced assistant content. Or leave as-is — the guard handles it.
- **Effort**: S

### 50.01.12 — LOW — `record_turn_metric` records `tool_calls.len()` which is the REQUESTED count, not the EXECUTED count

- **File**: `src/session/executor/turn.rs:394, 417, 441, 470, 516, 558, 574, 588`
- **Problem**: Every call to `record_turn_metric` passes `tool_calls.len()` as the `tool_calls` metric. But `tool_calls` is the `Vec<ToolInvocation>` that accumulates tool calls across ALL iterations of the turn loop (line 372: `let mut tool_calls: Vec<ToolInvocation> = Vec::new();`). On the `Finished` path (line 394), `tool_calls` may contain calls from a PREVIOUS iteration that were already dispatched — so the metric reports the cumulative count, not the count for this iteration. On the `ParseError` retry path (line 558), `tool_calls` may be empty (the parse failed before dispatch) but a previous iteration may have populated it. The metric `MetricEvent::Turn { tool_calls }` thus over-reports on multi-iteration turns.
- **Impact**: Low — the metrics log over-reports tool-call counts on turns with continuation rounds or parse-error retries. The metric is for observability, not billing. A turn with 1 tool call + 1 continuation round reports `tool_calls: 1` at both the continuation `Finished` and the final `Finished`, but the metric is emitted once per `record_turn_metric` call — and there are multiple calls per turn on some paths.
- **Fix**: Pass `tool_calls_out.len()` (the current iteration's count) instead of `tool_calls.len()` (cumulative). But `tool_calls_out` is local to `stream_iteration` and not returned. Alternatively, document that the metric is cumulative. Or only call `record_turn_metric` once at the end of `run_turn_inner`.
- **Effort**: M

### 50.01.13 — LOW — `is_read_only_bash` trims twice redundantly

- **File**: `src/session/executor/helpers/mod.rs:113-118`
- **Problem**: Line 113: `let trimmed = cmd.trim();`. Line 118: `let trimmed_stripped = trimmed.trim_start();`. Since `trim()` already removes leading whitespace, `trim_start()` on the result is a no-op (unless `trim()` left leading whitespace, which it doesn't). `trimmed_stripped` is always equal to `trimmed`. The variable name `trimmed_stripped` suggests it's doing something different from `trimmed`, but it isn't.
- **Impact**: None — redundant call, no runtime cost beyond one extra scan of an already-trimmed string.
- **Fix**: Delete line 118 and use `trimmed` directly at line 119. Or leave it — it's harmless.
- **Effort**: S

### 50.01.14 — LOW — `symlink_swap_denied` does a blocking `std::fs::symlink_metadata` walk on the async runtime

- **File**: `src/session/executor/dispatch.rs:900-914`
- **Problem**: `symlink_swap_denied` iterates `resolved.components()` and calls `std::fs::symlink_metadata(&acc)` for each component — synchronous filesystem I/O. It's called from `spawn_batch` (line 583) in the Phase 2.5 deferred-file-calls loop, which runs on the executor's async task (not in `spawn_blocking`). For a path with 10 components, this is 10 sync stat calls on the Tokio worker.
- **Impact**: Low — typical paths have 3-8 components, and stat is fast. But on a network filesystem or a cold cache, this stalls the worker. The `ponytail:` comment at line 579 acknowledges the non-atomic window but doesn't note the sync I/O.
- **Fix**: Wrap the walk in `tokio::task::spawn_blocking` and `.await` it. The function is called from an async context. Or accept the sync I/O given the typical component count is small (the `ponytail:` comment style would fit: `ponytail: sync stat walk, ~8 components typical; spawn_blocking if NFS latency matters`).
- **Effort**: S

### 50.01.15 — LOW — `build_stream_preamble` `top_files` spawn_blocking closure moves `top_file_paths` but `stem_file_cap` is captured from outer scope

- **File**: `src/session/executor/stream.rs:96-129`
- **Problem**: The `spawn_blocking` closure at line 96 moves `top_file_paths` (a `Vec<PathBuf>`) and uses `stem_file_cap` (a `Option<usize>` captured from the outer scope at line 58). `stem_file_cap` is `Copy`, so this works — but the closure also calls `crate::shared::minify::minify_source_safe(p, &content)` which is a potentially expensive CPU operation (minification) running on a blocking thread. This is correct (minify on blocking thread is the right call), but the `unwrap_or_default()` at line 129 silently swallows a `JoinError` (panic in the blocking task) — a panic in `minify_source_safe` degrades to an empty top-files set with no log.
- **Impact**: Low — a minification panic silently drops all top files for that turn, making the prompt cache miss. No error is logged. The comment at line 95 says "A panicking read task degrades to an empty top-files set" — so this is intentional, but the lack of a `tracing::warn!` on the `JoinError` makes it invisible.
- **Fix**: Add a `tracing::warn!(error = %e, "top-files spawn_blocking task panicked")` in the `Err` arm of the `unwrap_or_else`. Or leave as-is if silent degradation is the intended contract.
- **Effort**: S
