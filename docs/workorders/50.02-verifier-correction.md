# WO 50.02 — Verifier bus + correction loop deep audit

## Scope

Deep read-only audit of `src/session/verifier/` (25 files, ~13,000 lines
including tests). Covers the WO 47.14 migration from the old async
`Verifier` trait to the sync `BusVerifier` trait: `mod.rs`, `bus.rs`,
`correction.rs`, `types.rs`, `helpers.rs`, `plugin.rs`, `tests.rs`,
`detect.rs`, and all 14 verifier impls (`build.rs`, `lint.rs`, `test.rs`,
`generic_test.rs`, `git.rs`, `rustfmt.rs`, `security.rs`,
`security_emitter.rs`, `python_test.rs`, `python_lint.rs`,
`python_typecheck.rs`, `node_test.rs`, `node_lint.rs`, `go_test.rs`,
`go_vet.rs`).

## Verdict

The WO 47.14 migration is **structurally complete** — no leftover `impl
Verifier`, no live references to `VerifierHandler`/`VerifierSlots`, no
broken re-exports. But the migration **silently dropped four production
behaviors** (verdict cache, concurrent execution, per-verifier timeout,
trufflehog second-opinion on the bus path), left **three `VerifyContext`
fields unused** (`event_kind`, `tool_name`, `content_hash`), never
registered the `TsOrchestratorBridgeVerifier` (14 regex security rules
are dead in production), and left ~1,400 lines of `pub async fn
verify_*` dead code that only tests keep alive. There is also a security
regression in the bus-path entropy scan (first-match-only vs.
all-match) and a severity-classification bug (test failures classified as
`Warning`, not `Error`, so `has_errors()` returns false when only tests
fail).

## Findings

### P0 — `TsOrchestratorBridgeVerifier` never registered (14 regex security rules dead in production)

**File:** `src/session/verifier/bus.rs:440-471`, `src/session/executor/mod.rs:656-692`

The `TsOrchestratorBridgeVerifier` (bus.rs:440) wraps the Rust-native
security emitter (`security_emitter.rs`) which implements 14 regex rules
for obfuscated `eval`/`exec`/`shell`/`vm`/`pickle`/`yaml.load` patterns
in JS/TS/Python files. It is defined, has a `BusVerifier` impl, and is
extensively tested (bus.rs:866-940, security_emitter.rs:259-540) — but
it is **never registered** in `init_default_verifiers`
(executor/mod.rs:656-692). A grep for `TsOrchestratorBridgeVerifier::new`
returns only test call sites (bus.rs:886, 914, 938, 1153).

The `SecurityVerifier` (security.rs:370) that IS registered does
substring + entropy + dangerous-shell checks but does NOT run the 14
regex rules — those live only in `security_emitter.rs`, which only
`TsOrchestratorBridgeVerifier::verify` calls.

**Impact:** a Python file written with `eval("...")` or a JS file with
`window["eval"]("...")` passes the bus verification gate in production.
The old async `verify_security` path (still present as dead code) also
does not run these rules — they were always on the
`TsOrchestratorBridgeVerifier` path. The capability map
(bus.rs:378-406) marks `security` as `Active` with note "Rust regex
emitter (14 rules, WO 29.2)" — this is **overclaiming** since the
emitter is never invoked on the production bus path.

**Fix:** add
`vbus.register(Box::new(crate::session::verifier::bus::TsOrchestratorBridgeVerifier::new("ts-bridge".into())));`
to `init_default_verifiers`, and add `"ts-bridge"` to the
`BUILTIN_BUS_VERIFIERS` keep-list in `rebuild_bus_plugin_verifiers`
(executor/mod.rs:828-843).

### P0 — Bus-path entropy scan only checks the FIRST occurrence of each secret prefix

**File:** `src/session/verifier/security.rs:411-428, 451-462`

The `SecurityVerifier::verify` bus impl (production path) uses
`scan_entropy_token` (security.rs:453) which calls
`content.match_indices(prefix).next()` — only the **first** match. The
old async `verify_security` uses `scan_entropy_prefix` (security.rs:129)
which iterates **all** matches via `for (idx, matched) in
content.match_indices(prefix)`.

**Scenario:** a file contains `sk-placeholder` (low entropy, first
occurrence) on line 1 and `sk-9f8a7d6c5b4e3210ABCDxyzWVUtsrq` (high
entropy, second occurrence) on line 50. The bus path checks only the
first, finds it below the entropy threshold, and moves on — the real
secret on line 50 is **not detected**.

**Fix:** replace `scan_entropy_token` with a loop over
`content.match_indices(prefix)` (or call the existing
`scan_entropy_prefix` and adapt the return type). The existing
`scan_entropy_prefix` already does the right thing — the bus impl should
reuse it instead of the truncated `scan_entropy_token` helper.

### P1 — Test failures classified as `Severity::Warning`, not `Severity::Error`

**Files:** `src/session/verifier/test.rs:191`, `python_test.rs:165`,
`go_test.rs:122`, `node_test.rs:178`, `generic_test.rs:182`

All five test-runner verifiers emit `Severity::Warning` for a test
failure. Build errors (`build.rs:199`) and security findings
(`security.rs:399`) use `Severity::Error`. Git dirty-worktree
(`git.rs:297`) uses `Severity::Error`.

**Impact:** `VerifierBus::has_errors()` (bus.rs:224-226) returns `false`
when only test failures are present. The correction loop
(`correction.rs:92`) only promotes to `VerificationOutcome::Failed` for
`Severity::Error` — test failures without a fix fall through to the
"info" branch (line 106-117) and are reported as `Skipped`, not `Failed`.
The dispatch layer (dispatch.rs:290-296) also gates the
`VerificationOutcome::Failed` vs `Clean` distinction on
`Severity::Error`. A failing test suite is semantically an error (the
code is broken), not a warning.

**Fix:** change `Severity::Warning` → `Severity::Error` in the five
test-runner bus impls. The `FixSuggestion` severity string can stay
`"error"` (it already is).

### P1 — Verdict cache, concurrent execution, per-verifier timeout all lost in migration

**File:** `src/session/verifier/handler.rs` (deleted in WO 47.14),
`src/session/verifier/bus.rs:180-216`

The deleted `VerifierHandler` (handler.rs, 286 lines) had three
production behaviors that the `VerifierBus::run` replacement does not
reproduce:

1. **Verdict cache** (handler.rs:37-75): keyed by `(file_path,
   content_hash)`, FIFO-evicted at 256 entries, only cached
   `Clean`/`Skipped` verdicts. A re-edit of the same file with the same
   content skipped re-running cargo build/clippy/test. The bus path has
   no cache — every file-modifying tool call re-runs all 14 verifiers
   from scratch. The `VerifyContext.content_hash` field
   (bus.rs:99) is populated by dispatch.rs (dispatch.rs:191-198) but
   **never read** by any verifier or the correction loop. The bus.rs
   doc comment (bus.rs:96-98) says "the verdict cache (keyed by
   `(file_path, content_hash)`) still works" — **this is false**.

2. **Concurrent execution** (handler.rs:155-170): verifiers ran with
   `buffer_unordered(4)` so a slow cargo build didn't serialize the
   other verifiers. The bus path (bus.rs:182-215) runs verifiers
   **sequentially** in a single `for` loop. With 14 verifiers and
   subprocess spawns (cargo build, clippy, test, rustfmt, go test,
   pytest, eslint, tsc, etc.), this can add minutes to a turn. WO 47.26
   previously fixed this for the old path — the fix was lost.

3. **Per-verifier 30s timeout** (handler.rs:53-58): each verifier was
   wrapped in a `tokio::time::timeout(VERIFIER_TIMEOUT, ...)`. A wedged
   cargo build or hung pytest would be skipped after 30s, not block the
   turn indefinitely. The bus path has no per-verifier timeout — the
   only timeout is the plugin-verifier 5s watchdog in
   `kf-plugin-host/verifier.rs` (WO 38.3), which does NOT cover the
   14 built-in verifiers. A hung `cargo build` on the bus path blocks
   the `spawn_blocking` thread indefinitely.

**Fix:** (a) restore the verdict cache in `VerifierBus::run` using
`ctx.content_hash` (the field is already there and populated), (b) run
verifiers concurrently via `tokio::task::JoinSet` inside the
`spawn_blocking` closure, (c) add a per-verifier timeout. The old
handler.rs is in git history (commit 3819cf11^) as a reference. At
minimum, the false doc comment on `content_hash` (bus.rs:96-98) must be
corrected.

### P1 — `is_conflict_prone_command` uses substring match — false positives on "emerge"/"converge"/filenames

**File:** `src/session/verifier/git.rs:103-109`

```rust
fn is_conflict_prone_command(command: &str) -> bool {
    let lowered = command.to_lowercase();
    lowered.contains("merge")
        || lowered.contains("rebase")
        || lowered.contains("cherry-pick")
        || lowered.contains("pull")
}
```

`lowered.contains("merge")` matches `emerge`, `converge`, `submerge`,
`cat merge_log.txt`, `echo "merge complete"`. The test at git.rs:641-642
even asserts `assert!(is_conflict_prone_command("MERGE branch"))` — a
bare word with no `git` prefix passes. Compare with
`is_git_modifying_command` (git.rs:81-99) which correctly uses
`git_subcommands_in` to parse the actual git subcommand.

**Impact:** a bash command like `cat merge_report.txt && echo done` that
fails (exit non-zero) would trigger `check_merge_conflicts` unnecessarily
— running `git diff --name-only --diff-filter=U` in the workdir. This is
not a correctness bug (the merge-conflict check returns `Clean` if there
are no conflicts), but it's wasted work and the false-positive surface
grows if the conflict check ever has side effects.

**Fix:** rewrite to use `git_subcommands_in(command).iter().any(|sub|
matches!(sub.as_str(), "merge" | "rebase" | "cherry-pick" | "pull"))`
— same shape as `is_git_modifying_command`.

### P2 — `VerifyContext` fields `event_kind` and `tool_name` populated but never read

**File:** `src/session/verifier/bus.rs:88-95`, `src/session/executor/dispatch.rs:207-208,233-234`

`VerifyContext` has two `Option<String>` fields:
- `event_kind` (bus.rs:91): set by dispatch.rs to `format!("post-tool-{tool_name}")` — e.g. `"post-tool-write_file"`, `"post-tool-bash"`.
- `tool_name` (bus.rs:95): set by dispatch.rs to `tool_name.to_string()` — e.g. `"write_file"`, `"edit_file"`, `"bash"`.

A grep for `ctx.event_kind` or `ctx.tool_name` across
`src/session/verifier/` returns **zero matches**. No verifier reads
either field. They were added in WO 47.14 ("carried over from
`BusEvent::kind()` so event-aware verifiers can gate") but no verifier
actually gates on them. The old `Verifier` trait switched on
`BusEvent::Edit`/`FileWrite`/`BashExec` variants; the new verifiers
switch on `ctx.changed_files.first()` extension or `ctx.bash_command`
presence instead. The fields are dead weight that dispatch.rs populates
on every tool call.

**Fix:** either (a) remove the fields and their dispatch.rs population
(~8 lines), or (b) if future verifiers need them, add a
`#[allow(dead_code)]` and fix the doc comments to say "reserved for
future use" instead of "so event-aware verifiers can gate".

### P2 — `CorrectionLoop::max_iterations` field is dead code

**File:** `src/session/verifier/correction.rs:24,32,42-45,169-171`

`CorrectionLoop` has a `max_iterations: usize` field (default 3), a
`with_max_iterations` builder, and a `max_iterations()` getter. But
`run_from_verdicts` (correction.rs:53-122) **never reads
`self.max_iterations`** — it applies at most one fix (the first
fix-bearing verdict) and returns. The `for entry in verdicts` loop
(correction.rs:63-88) always returns on the first fix-bearing entry via
the double-`return` at lines 82 and 86.

The `with_max_iterations` builder (correction.rs:42-45) also has a
redundant double-set: `self.max_iterations = max; Self { ..self }` —
the field is set, then `Self { ..self }` copies it again. This works but
is confusing; a plain `self` return would suffice.

Three tests are duplicated verbatim between `correction.rs::tests`
(correction.rs:648-665) and `tests.rs` (tests.rs:195-218):
`correction_loop_new_uses_default_max_iterations`,
`correction_loop_with_max_iterations_overrides_default`,
`correction_loop_run_from_verdicts_empty_returns_empty`. Both modules
are `#[cfg(test)]` and both compile, so the tests run twice.

**Fix:** (a) remove `max_iterations` field, `with_max_iterations`, and
`max_iterations()` — they're dead code; (b) remove the duplicate tests
from `tests.rs`; (c) simplify `with_max_iterations` to `pub fn
with_max_iterations(mut self, max: usize) -> Self { self.max_iterations
= max; self }` if the field is kept.

### P2 — `run_from_verdicts` `changed_files` parameter is unused

**File:** `src/session/verifier/correction.rs:53-57,120`

`run_from_verdicts` takes `changed_files: &[PathBuf]` but explicitly
discards it: `let _ = changed_files; // currently unused — kept for
future cache logic` (correction.rs:120). The verdict cache that would
have used it was deleted in the migration (see P1 above). The
dispatch.rs caller (dispatch.rs:278) clones `ctx.changed_files` to pass
here — a wasted clone.

**Fix:** remove the parameter and the clone at the call site, or
restore the cache (see P1).

### P2 — 14 `pub async fn verify_*` functions are dead in production (~1,400 lines)

**Files:** all 14 verifier files

Each verifier file has two implementations:
1. A `pub async fn verify_*` free function that takes `&BusEvent` and
   returns `Verdict` — the old `Verifier`-trait path.
2. A `BusVerifier` impl that takes `&VerifyContext` and returns
   `Vec<VerdictEntry>` — the production path.

The free functions are only called from tests. A grep for `verify_build`,
`verify_lint`, `verify_test`, etc. across `src/` shows all calls are in
`#[cfg(test)] mod tests` blocks. The `BusEvent` type, all event payload
structs (`FileWriteEvent`, `EditEvent`, `BashExecEvent`, etc.), the
`Verdict` enum, `FixSuggestion`, `VerificationError`, and the
`CommandRunner`/`CommandOutcome`/`ExitState`/`SystemCommandRunner` types
exist solely to support these dead functions and their tests.

The types.rs doc comment (types.rs:403-408) acknowledges this: "The
`Verdict` enum and `FixSuggestion` struct are kept because the old
`verify_*` free functions still return `Verdict` (used by unit tests in
each verifier file)."

**Impact:** ~1,400 lines of dead production code + ~2,000 lines of
tests for that dead code. The `BusEvent` construction block in
dispatch.rs (dispatch.rs:94-159, ~66 lines) is also dead — it builds a
`BusEvent` and then discards it with `let _ = bus_event;` (line 161).
Same for `error_event` (dispatch.rs:163-174).

**Fix:** (a) delete the `verify_*` free functions and their tests (the
`BusVerifier` impl tests cover the same logic), (b) delete the
`BusEvent`/payload structs/`Verdict`/`FixSuggestion`/`VerificationError`
types if no other consumer exists, (c) delete the dead `bus_event`/
`error_event` construction in dispatch.rs. This is a large cleanup —
should be its own workorder. The `CommandRunner` trait is still used by
`BuildVerifier`/`LintVerifier`/`TestVerifier` (they take an
`Arc<dyn CommandRunner>`), so that stays.

### P2 — `PluginBusVerifier::priority` field stored but never used

**File:** `src/session/verifier/bus.rs:274,302`

`PluginBusVerifier` stores a `priority: u8` (line 274) but explicitly
discards it: `let _ = self.priority;` (line 302). The old
`VerifierSlots` ordered verifiers by priority; the `VerifierBus` runs
verifiers in registration order with no priority sorting. A plugin
verifier declaring `priority = 7` runs in arbitrary order. The
`add_plugin_verifier` signature (bus.rs:160-176) still takes `priority`
as a parameter — callers pass it, it's stored, it's ignored.

**Fix:** either (a) remove `priority` from `PluginBusVerifier` and
`add_plugin_verifier` (breaking change to the bus API), or (b) sort
`self.verifiers` by priority in `VerifierBus::run` (restoring the old
behavior). Option (b) is safer.

### P2 — `VerifierSource` inconsistency: `go_vet` and `python_typecheck` use `Custom`, others use typed variants

**Files:** `src/session/verifier/go_vet.rs:114`,
`python_typecheck.rs:138`

`GoVetVerifier` emits `VerifierSource::Custom("go_vet".into())` and
`PythonTypecheckVerifier` emits
`VerifierSource::Custom("python_typecheck".into())`. All other test
verifiers use `VerifierSource::Test`; all other lint verifiers use
`VerifierSource::Lint`. There is no `VerifierSource::Typecheck` or
`VerifierSource::GoVet` variant. The `Custom` variant is intended for
user-defined verifiers (bus.rs:32), not built-ins. This means the
`verifier` field in `CorrectionResult` will read `"custom:go_vet"` and
`"custom:python_typecheck"` instead of a clean label.

**Fix:** add `VerifierSource::Typecheck` and
`VerifierSource::GoVet` variants (or reuse `VerifierSource::Lint` for
both since they're lint-class), or accept the `Custom` label and
document it.

### P3 — `NodeLintVerifier` bus path silently reports clean when tools are configured but not invocable

**File:** `src/session/verifier/node_lint.rs:221-222`

The async `verify_node_lint` (node_lint.rs:127-134) has a `Skipped`
path: if eslint/tsc are configured but `npx` can't resolve them
(`bodies.is_empty()`), it returns `Verdict::Skipped("eslint/tsc
configured but not invocable via npx")`. The bus `NodeLintVerifier`
(node_lint.rs:221-222) returns `vec![]` (clean) in the same situation —
no signal that the linter didn't actually run.

**Impact:** the user sees no verification finding when their eslint
config is present but `npx eslint` fails to resolve. The dispatch layer
(dispatch.rs:289-319) only reports non-fixable verdicts — `vec![]`
produces nothing. This is a behavior difference between the two paths
that could mask a misconfigured linter.

**Fix:** return a `VerdictEntry` with `Severity::Warning` and message
"eslint/tsc configured but not invocable via npx" when `!had_failure &&
bodies.is_empty()`, matching the async path's skip message.

### P3 — `security_emitter.rs` tests leak tempdirs via `std::mem::forget(dir)`

**File:** `src/session/verifier/security_emitter.rs:263-271`

The `write_tmp` test helper (security_emitter.rs:263-271) creates a
`tempfile::tempdir()`, writes a fixture file, then
`std::mem::forget(dir)` to prevent cleanup — the comment says "Tests are
short-lived." Every test that calls `write_tmp` leaks a temp directory
in `/tmp`. With 15+ tests in the module, this leaks 15+ tempdirs per
test run. The files are small but the leak accumulates across CI runs.

**Fix:** return `(PathBuf, tempfile::TempDir)` and bind the `TempDir`
in the test so it cleans up on scope exit. The security emitter reads
files lazily, so the `TempDir` must outlive the `emit_security_findings`
call — but the test can drop it after the assertions.

### P3 — `correction.rs` double-return in fix loop is misleading

**File:** `src/session/verifier/correction.rs:81-87`

```rust
if !applied || is_suggestion {
    return results;
}
// A fix was applied — stop (the bus will re-run on the next
// tool call if there are cascading issues).
return results;
```

Both branches return `results`. The `if` condition is irrelevant — the
function always returns after processing the first fix-bearing verdict.
The `for` loop body always exits on the first fix. This is functionally
correct (apply one fix per bus run, let the next tool call re-verify),
but the code reads as if the two returns have different semantics.

**Fix:** remove the `if` and the comment, leaving a single `return
results;` after the `results.push(...)`. Add a comment: "Apply at most
one fix per bus run — the bus re-runs on the next tool call if
cascading issues remain."

### P3 — `catch_unwind` captures `verifier.name()` outside the unwind guard

**File:** `src/session/verifier/bus.rs:194-195`

```rust
let name = verifier.name().to_string();  // outside catch_unwind
let entries = match catch_unwind(AssertUnwindSafe(|| verifier.verify(ctx))) {
```

The comment (bus.rs:183-193) explains that `name()` is captured BEFORE
`catch_unwind` so the panic handler doesn't call verifier code. But if
`name()` itself panics (a buggy plugin verifier whose `name()` reads
from a poisoned lock), the panic unwinds through `VerifierBus::run`,
through the `spawn_blocking` closure, and aborts the task —
`dispatch.rs:259-262` catches this with
`unwrap_or_else(|e| VerifierBus::new())`, but the bus and its 14
registered verifiers are lost for the rest of the session.

**Mitigation:** `name()` is typically `&'static str` for built-ins and
a `String` field for plugins — trivial accessors that won't panic
unless the struct is already corrupt. The risk is theoretical. The WO
47.23 containment contract (panic=abort in release) means this only
matters in dev/test builds.

**Fix:** wrap `name()` in its own `catch_unwind`:
`let name = catch_unwind(AssertUnwindSafe(|| verifier.name().to_string())).unwrap_or_else(|_| "unknown".into());`

### P3 — Bus path `SecurityVerifier` omits trufflehog second-opinion (documented but not flagged as regression)

**File:** `src/session/verifier/security.rs:360-367, 377-448`

The `SecurityVerifier::verify` bus impl (production path) runs
substring + entropy + dangerous-shell checks but does NOT call
`trufflehog_scan`. The comment at line 364-367 says this is intentional
("the Rust regex emitter `TsOrchestratorBridgeVerifier` already covers
the regex-based security rules on the bus") — but
`TsOrchestratorBridgeVerifier` is never registered (see P0 above). So
the bus path has neither trufflehog nor the 14 regex rules. The async
`verify_security` (security.rs:282-358) does call trufflehog (line 335)
— but that function is dead code.

**Impact:** secrets that trufflehog would catch (verified secrets with
known detector patterns — GitHub tokens, AWS keys with verified
metadata, etc.) are missed on the bus path. The substring + entropy
detector catches obvious patterns but misses structured secrets that
trufflehog's detectors specialize in.

**Fix:** either (a) call `trufflehog_scan` from the bus impl (it's
async — would need `spawn_blocking` inside the already-blocking bus
path, or a sync rewrite), or (b) document that trufflehog is
async-path-only and the bus path relies on the regex emitter (which
must then be registered — see P0). Option (b) is the smaller change.

### P3 — `build.rs` / `lint.rs` path comparison may miss matches for relative paths

**File:** `src/session/verifier/build.rs:39-40`, `lint.rs:58-59`

`parse_build_json` does `let resolved = cargo_root.join(file_name); if
resolved == target_path`. The `target_path` comes from
`ctx.changed_files.first()`, which dispatch.rs populates from
`args.get("path")`. Phase-1 resolution (dispatch.rs:348-355) rewrites
the path arg to the canonical absolute path before the tool runs, so
`target_path` should be absolute. `cargo_root.join(file_name)` where
`file_name` is `"src/main.rs"` (cargo's JSON output) produces an
absolute path if `cargo_root` is absolute. The comparison works when
both are absolute and canonical.

**Risk:** if Phase-1 resolution is ever bypassed (e.g., a tool that
doesn't go through `prepare_batch`), `target_path` could be relative
(`src/main.rs`) while `cargo_root.join(file_name)` is absolute — the
`==` comparison fails and the build error is not reported as fixable.
The `Path::eq` operator compares components, not string forms, so
`/foo/bar/src/main.rs` == `/foo/bar/src/main.rs` regardless of
canonicalization — but `src/main.rs` != `/home/user/project/src/main.rs`.

**Fix:** normalize `target_path` against `cargo_root` before
comparison: `if cargo_root.join(file_name) == target_path || resolved
== target_path`. Or canonicalize both before comparing. Low risk since
Phase-1 resolution covers the production path, but worth a defensive
normalize.
