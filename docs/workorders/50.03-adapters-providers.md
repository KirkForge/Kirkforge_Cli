# WO 50.03 — Adapters / Providers deep audit

## Scope

Deep read-only audit of `src/adapters/` (15 files, ~9,400 lines including
tests). Covers: `mod.rs`, `oellama.rs`, `openai_compat/`, `anthropic/`,
`anthropic_bedrock.rs`, `anthropic_vertex.rs`, `bedrock_signing.rs`,
`vertex_auth.rs`, `caching.rs`, `error.rs`, `ollama_ndjson.rs`, `auth.rs`,
`bedrock_vertex_mocks.rs`.

## Verdict

The adapter layer is **the most mature, heavily-tested subsystem in the
repo**. Several prior workorders (43.20, 43.1, 43.22, 46.33, 46.23, 47.20,
47.29, 38.5, 28.13) have already swept through and fixed the obvious
classes of bugs. The audit list items called out in the brief are, with one
exception, **already addressed and tested**. The findings below are
therefore mostly confirmations ("verified correct + here's the test that
pins it") plus a small number of genuinely new observations.

## Audit-list findings

### 1. SigV4 signing (WO 43.20) — manual implementation correctness

**File:** `src/adapters/bedrock_signing.rs`

**Verdict: correct.** The hand-rolled SigV4 implementation matches the AWS
canonical-request spec on every point I checked:

- **Canonical request format** (`bedrock_signing.rs:105`): `POST\n{path}\n\n{canonical_headers}\n{signed_headers}\n{payload_hash}`. The empty query-string line (third `\n`) is correct for Bedrock invoke-with-response-stream, which uses POST with no query string. Headers block ends with a trailing `\n` before the signed-headers list, matching the spec.
- **Canonical headers** (`:88-97`): keys lowercased, sorted, values trimmed, each as `k:v\n`. Correct.
- **Signed headers** (`:98-102`): `;`-joined sorted keys. Correct.
- **Signing key chain** (`:114-121`): `kDate → kRegion → kService → kSigning` via HMAC-SHA256, seeded with `"AWS4" + secret`. Correct.
- **String to sign** (`:111-112`): `AWS4-HMAC-SHA256\n{amz_date}\n{credential_scope}\n{hash}`. Correct.
- **Credential scope** (`:109`): `{date}/{region}/bedrock/aws4_request`. The service name is `bedrock` (not `bedrock-runtime`) — this is the documented value for Bedrock model-invocation signing.
- **Payload hash** (`:69`): `x-amz-content-sha256` header set to the SHA256 of the body AND included in the canonical request. Correct (unsigned-payload is not used).
- **All sent headers are signed** (`:76-86`): `content-length`, `content-type`, `host`, `x-amz-content-sha256`, `x-amz-date`, and conditionally `x-amz-security-token` are all in the `headers` Vec, which is the source for both the canonical-headers block and the assembled `HeaderMap`. reqwest adds nothing unsigned on top of these. The `content-length` inclusion was an explicit fix (mm-H13, WO 47.29) — `sign_request_signs_content_length` test at `:324` pins that `content-length` appears in `SignedHeaders`. This is the most common SigV4 footgun and it is already handled.
- **Session token** (`:84-86`): included only when `AWS_SESSION_TOKEN` is set, and included in both the signed set and the sent headers. `sign_request_includes_security_token_when_set` test pins it.

**Contract gate:** `bedrock_vertex_mocks.rs` spins a wiremock server whose `SigV4Authorization` matcher requires `AWS4-HMAC-SHA256 ... SignedHeaders=...`, and `bedrock_unsigned_request_rejected_by_contract_gate` proves an unsigned request is rejected while a signed one passes. This is a genuine contract test, not theater — the matcher rejects anything lacking the SigV4 prefix.

**Observations (not bugs):**
- `resolve_credentials` (`:172`) reads only `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN` from the environment. The module doc honestly discloses that profile-chain and instance-metadata resolution are MVP-deferred. This is a **documented extension point**, not a regression.
- The `amz_date` is derived from `SystemTime::now()` truncated to whole seconds (`:65`). Two signing calls within the same wall-clock second produce identical `amz_date` values — this is fine for SigV4 (the signature still differs by body/nonce), but a clock skewed >5 min from AWS will be rejected. There is no clock-skew detection; that's a reasonable omission for a CLI.
- `chrono::DateTime::from_timestamp(now.as_secs() as i64, 0)` discards sub-second precision. Correct for the `%Y%m%dT%H%M%SZ` format.
- The signing is computed **once** in `AnthropicBedrockAdapter::stream` (`anthropic_bedrock.rs:111`) before the `send_with_retry` closure. **On retry, the request is re-sent with the SAME signed headers and `x-amz-date`** (the closure captures `signed_request` by reference, and `body_bytes` is the same). AWS accepts a request signed up to ~5 minutes ago, and `send_with_retry` caps at 3 attempts with bounded backoff, so the timestamp will not be stale within a retry window. This is correct but subtle — a comment would help. Not a bug.

**No canonical-request formatting bugs found.**

### 2. Typed AdapterError migration (WO 43.1)

**File:** `src/adapters/error.rs`, all 5 adapter `stream()` sites.

**Verdict: complete.** All five adapters wrap their `send_with_retry` result
through `.map_err(super::classify_transport_error)`:

| Adapter | Site | Wraps? |
|---|---|---|
| Oellama | `oellama.rs:195` | yes |
| OpenAiCompat | `openai_compat/mod.rs:610` | yes |
| Anthropic | `anthropic/mod.rs:193` | yes |
| AnthropicBedrock | `anthropic_bedrock.rs:123` | yes |
| AnthropicVertex | `anthropic_vertex.rs:198` | yes |

**No bare `.await?` on the transport path** in any adapter. The Anthropic
adapter (`anthropic/mod.rs:140-145`) also pre-classifies the missing-API-key
case as a plain `anyhow` error (not `AdapterError::Denied`), which then
falls through `error.rs`'s string probe — it contains neither "denied" nor
"connection refused" so it lands in `KirkForgeError::General`. This is
arguably a misclassification (a missing key is an auth denial, exit 4, not
general exit 1), but it's a pre-existing edge, not a regression from the
typed migration. **Minor finding F1 below.**

The classifier consumer in `src/main/error.rs:55-64` downcasts
`AdapterError` first: `Unreachable`/`ModelNotFound` → exit 3,
`Denied` → exit 4, `Other` falls through to the string probe. The
`is_model_unreachable` helper and the four `classify_*` tests in
`error.rs` pin the mapping. The migration is sound.

`classify_transport_error` (`error.rs:68-109`) itself has a sensible
two-tier strategy: downcast to `reqwest::Error` for kind/status
classification; fall back to a lowercase message probe for the case where
the reqwest root is hidden behind an anyhow context layer. The fallback
covers `connection refused`, `failed to connect`, `dns error`,
`timed out`, `connect error`, `model not found`. Unmatched errors are
returned as **bare anyhow** (NOT wrapped in `Other`) — deliberate, so
the string probe in `main/error.rs` still gets a chance. The
`classify_unmatched_message_passes_through_unwrapped` test pins this.
Good design.

### 3. Retry logic

**File:** `src/adapters/mod.rs:98-181`, `src/shared/mod.rs:1203-1213`

- **Retry-After honored:** `retry_delay` (`mod.rs:116-122`) takes the
  larger of computed backoff and the `Retry-After` seconds form. The
  HTTP-date form is deliberately ignored (comment: "gateways that
  rate-limit bots send seconds"). `send_with_retry` reads the header
  (`:170-173`) and passes it to `retry_delay`. The test
  `retry_delay_honors_retry_after_over_computed_backoff` pins both the
  longer-wins and shorter-falls-back cases. **Correct.**
- **No infinite loop:** `send_with_retry` is bounded by
  `MODEL_MAX_RETRIES = 3` (`:99`). The loop increments `attempt` each
  iteration; the retry guards all require `attempt < MODEL_MAX_RETRIES`
  (`:144`, `:158`); the fourth attempt returns either the error or the
  `error_for_status` result. **No infinite retry path exists.**
- **Backoff has jitter:** `retry_backoff` (`shared/mod.rs:1203`) uses
  `1 << (attempt-1)` seconds as base, plus
  `nanos % (250ms * attempt capped at 1000ms)` of jitter derived from
  wall-clock subsec nanos. The jitter is intentionally **not
  cryptographic** — the comment explains it exists to desynchronize
  parallel subagents hitting a shared gateway, not to defend against
  adversarial timing. Capped, monotonic base, bounded jitter. The
  `backoff_grows_with_capped_jitter` test pins the bounds. **Correct.**
- **Retry classification:** retries on `is_connect()` / `is_timeout()`
  and HTTP 429 / 5xx (`should_retry_status`, `:106-108`). 4xx other than
  429 fails fast. **Correct.**

**One subtle correctness note (not a bug):** on the Bedrock retry path,
`send_with_retry` re-runs the closure which re-sends `signed_request`
with headers captured at closure-build time. The signature is NOT
recomputed per attempt (see §1 above). For a 3-attempt window with
sub-second to ~2s backoff, the original `x-amz-date` stays valid. If the
backoff ever grows to minutes, the stale date would break. Current
backoff caps at ~5s total across 3 attempts, so this is safe today.
Documented here so a future backoff-cap raise doesn't silently break
Bedrock auth.

### 4. SSE parsing

**Files:** `src/adapters/anthropic/sse.rs`, `src/adapters/openai_compat/mod.rs`

- **Partial frames handled:** both parsers buffer raw bytes and only
  parse a frame once its terminator (`\n\n`, `\r\n\r\n`, or `\r\r`) is
  present. The `find_data_frame_start` scan is line-anchored
  (mm-H14/WO 47.29): a `data: ` substring inside a non-data line or a
  JSON payload is NOT parsed as a frame boundary. Tests:
  `sse_data_substring_in_non_data_line_is_not_a_frame` (both parsers),
  `sse_multibyte_char_split_across_chunks` (openai_compat),
  `ndjson_multibyte_char_split_across_chunks` (ollama). **Correct.**
- **Channel close mid-stream:** both parsers route every `tx.send`
  through `send_or_bail` (ollama_ndjson.rs:445), which returns `false`
  on `SendError` and the parser `return`s immediately. No silent
  drain of the upstream body after the consumer is gone. The OpenAI
  parser's `send_done_once` and the `[DONE]`/EOF flush paths all
  respect the boolean. **Correct.**
- **Buffer cap:** both parsers cap the byte buffer at
  `MAX_SSE_BUFFER_BYTES = 8 MiB` (`mod.rs:26`), emitting a
  `StreamEvent::Error` and `return`ing on overflow. The Bedrock
  envelope parser has its own `MAX_ENVELOPE_BUFFER_BYTES` (8 MiB)
  with the same cap-and-clear behavior
  (`anthropic_bedrock.rs:174-187`). **Correct.**
- **EOF truncation semantics (WO 38.5):** if the stream ends without
  `[DONE]`/`message_stop` and no `finish_reason`, the parsers emit
  `Done{Error}` (not `Done{Stop}`) so the executor persists the
  partial instead of laundering a half-reply into a success.
  OpenAI: `parse_openai_compat_stream:360-382` uses
  `pending_finish.unwrap_or(FinishReason::Error)`. Anthropic:
  `sse.rs:244-267` explicitly sends `Done{Error}`. Bedrock
  (`anthropic_bedrock.rs:152, 221-223`): `[DONE]` is only injected
  when `saw_message_stop` was seen, so a mid-stream drop reaches the
  Anthropic parser's EOF path and becomes `Done{Error}`. **Correct
  and consistent across all three Anthropic-family adapters.**
- **CRLF handling:** all three terminator forms (`\n\n`, `\r\n\r\n`,
  `\r\r`) are searched simultaneously and the earliest match wins.
  Tests `sse_accepts_crlf_line_endings`, `sse_cr_only_line_endings_accepted`,
  `ndjson_handles_crlf_line_endings`. **Correct.**
- **Invalid JSON frame handling:** a complete frame with invalid JSON
  emits an `Error` event and the frame is discarded (drained from the
  buffer) so the parser doesn't re-buffer the same bytes forever
  (review.md C5 fix). Tests:
  `sse_invalid_json_frame_is_reported_and_discarded` (openai_compat),
  `malformed_json_line_emits_parse_error_and_continues` (ollama),
  the Anthropic parser's `Err(e)` arm at `sse.rs:218-228`. **Correct.**

**Observations (not bugs):**
- The OpenAI-compat parser's `[DONE]` branch flushes buffered tool
  calls BEFORE emitting `Done` (`openai_compat/mod.rs:143-168`), and the
  late-`finish_reason`-after-`[DONE]` guard (WO 46.33) suppresses the
  spurious "no parseable tool calls" error by requiring
  `!done_emitted`. The regression test
  `finish_reason_tool_calls_after_done_does_not_error` pins this.
  Well-handled.
- The Anthropic parser's EOF path (`sse.rs:244-267`) flushes a pending
  tool with `input.is_none()` as an empty-object invocation so a
  truncated tool attempt is surfaced rather than swallowed (WO 15.11).
  Good defensive choice.

### 5. Caching — stale error replay, cache key

**File:** `src/adapters/caching.rs`

- **No stale error replay:** `cacheable` (`caching.rs:186-188`) rejects
  any stream containing a `StreamEvent::Error` anywhere, plus empty
  streams. The forwarder task's `complete` check
  (`:493-497`) additionally requires the last event to be `Done`
  with a non-`Error` finish_reason AND no `Error` event anywhere.
  Two independent guards. The WO 38.5 tests
  (`cache_skips_streams_containing_any_error`,
  `caching_adapter_skips_stream_containing_error`,
  `caching_adapter_skips_done_with_error_reason`,
  `caching_adapter_skips_cache_when_consumer_drops`,
  `caching_adapter_incomplete_stream_not_cached`) pin all five
  non-cacheable shapes. **Correct.**
- **Cache key correctness:** `CacheKey::new` (`:247-276`) hashes
  `model_scope + messages + tools + response_format`. `model_scope` is
  the `request_fingerprint` from `CachingAdapter`
  (`:357-368`), which folds in: provider/endpoint routing scope,
  `inner.model_info().name`, `seed`, `max_tokens`, `extended_thinking`,
  `budget_tokens`, `computer_use_dims`. The WO 47.20 test
  `caching_adapter_generation_knobs_change_the_fingerprint` pins that
  each of these changes the key, and
  `caching_adapter_different_seed_does_not_replay_cached_stream` +
  `caching_adapter_different_scope_does_not_replay_cached_stream`
  prove two providers serving the same model don't share entries.
  **Correct and well-pinned.**
- **Replay usage zeroing (WO 38.5):** on a cache hit, the replay
  loop (`:444-453`) rewrites `Done{usage: Some(_)}` to
  `Done{usage: None}` so CostStats doesn't double-bill. The
  `caching_adapter_miss_then_hit` test pins `usage == None` on replay.
  **Correct.**
- **Memory cap (WO 46.23):** `insert_memory` enforces a 100-entry cap
  with arbitrary (HashMap-order) eviction; disk I/O is performed
  outside the memory lock. The `ponytail:` comment at `:31-34`
  honestly names the ceiling (not real LRU; upgrade path: IndexMap
  + move-to-back). Test `cache_memory_respects_size_cap` pins the cap
  and the newest-entry-survives invariant. **Correct.**
- **Disk size cap:** `read_disk` (`:101-126`) caps reads at 64 MiB
  and treats oversize as a miss. `cache_returns_none_for_oversized_disk_file`
  writes 64 MiB + 1 byte and asserts miss. Corrupt-file returns None
  (`cache_returns_none_for_corrupt_disk_file`). **Correct.**

**Observations (not bugs):**
- The replay channel is sized `events.len().max(1)` (`:437`). If a
  cached stream is huge (thousands of events), the replay `tokio::spawn`
  task holds the full `Vec<StreamEvent>` in memory and sends one-by-one.
  This is bounded by what was cached, which is bounded by a real turn's
  length — not a leak, just a large-allocation edge. Acceptable.
- The forwarder task (`:471-515`) uses `tokio::select! { biased; _ =
  tx_out.closed() => break, ev = inner.recv() => ... }`. The `biased`
  makes the consumer-drop check fire first, so a dropped consumer
  doesn't keep draining the inner adapter into `events`. Test
  `caching_adapter_aborts_forwarder_on_consumer_drop` proves this with
  a gated counting adapter. Good.

### 6. Vertex token cache

**File:** `src/adapters/anthropic_vertex.rs:40-132`

- **Caching present:** `token_cache: tokio::sync::Mutex<Option<AccessToken>>`
  (`:40`). `cached_access_token` (`:112-132`) checks `is_expired()`
  before fetching; if the cached token is valid, returns its string
  without a network call.
- **Expiry handled:** `AccessToken::is_expired()` carries a 1-minute
  safety margin (per the `vertex_auth.rs` doc comment). The cache
  recomputes `is_expired` on every call, so a token that expires
  mid-session is refreshed on the next `stream()`. The `ceiling:`
  comment at `:111` discloses the one edge: a token whose server sent
  no `expires_in` is cached for the adapter's lifetime — but GCP
  always sends `expires_in`, so this is theoretical.
- **Mutex (not RwLock):** the comment at `:38-40` explains the choice:
  a stampede of concurrent streams coalesces into a single fetch
  because the Mutex serializes the fetch path. Correct for the
  "rare fetch, hot read" pattern. (Note: the cache still holds the
  lock for the duration of the `service_account_token().await`
  network call — a concurrent stream waits for the fetch. That's the
  intended coalescing behavior.)
- **Testing:** the token cache is NOT directly unit-tested — the
  `vertex_auth.rs` `ponytail:` comment (lines 11-16) honestly
  discloses that mocking `yup_oauth2`'s authenticator is not possible
  without an `Authenticator` trait injection, and the
  `bedrock_vertex_mocks.rs` header (lines 21-26) explicitly defers
  Vertex contract tests to WO 28.13 R2-later with the same rationale.
  The two `vertex_auth.rs` tests only assert the failure cases (no
  path/env, nonexistent path). **This is a disclosed deferral, not a
  regression** — but it IS the weakest-tested part of the adapter
  layer. **Finding F2 below.**

## New findings

### F1 — Anthropic missing-API-key misclassifies as General (exit 1), not AccessDenied (exit 4)

**Location:** `src/adapters/anthropic/mod.rs:140-145`, `src/main/error.rs:69-90`

When no Anthropic API key is configured, `stream()` returns
`anyhow!("no Anthropic API key set (...)")`. This is a bare `anyhow`
error — it is NOT wrapped in `AdapterError::Denied`. The classifier in
`main/error.rs` downcasts to `AdapterError` (finds none), then runs the
string probe, which contains neither "denied" / "permission" /
"sandbox" / "blocked" nor "connection refused" / "model not found".
It lands in `KirkForgeError::General` (exit 1).

A missing API key is an auth/permission failure. Exit 4
(`AccessDenied`) would be the correct classification, and the
`hint_access_denied` message ("Check the `security.permission_rules`
and `sandbox` sections...") would be slightly misleading for a key
issue, but exit 4 + a key-specific hint is closer to correct than exit
1 ("general failure"). The same pattern applies to the Bedrock and
Vertex adapters, which surface credential-resolution failures as bare
`anyhow` from `bedrock_signing::resolve_credentials` /
`vertex_auth::service_account_token`.

**Severity:** low. The user still sees the error message verbatim; only
the exit code and hint are suboptimal. The typed-`AdapterError` migration
(WO 43.1) covered the transport-error path but not the
pre-request credential-resolution path.

**Minimal fix:** wrap the credential-resolution errors in
`AdapterError::Denied` (or introduce a new
`AdapterError::MissingCredentials` variant) at the three cloud-adapter
`stream()` sites. Then add `missing_credentials` / `"api key"` to the
string-probe fallback in `main/error.rs` for the untyped tail.

### F2 — Vertex token-cache hit/refresh path has no automated test

**Location:** `src/adapters/anthropic_vertex.rs:112-132`

`cached_access_token` is the most behaviorally complex part of the
Vertex adapter: it holds a `tokio::Mutex`, checks `is_expired`, fetches
on miss, stores, and returns. None of this is exercised by a test.
The `ponytail:` comment in `vertex_auth.rs` and the
`bedrock_vertex_mocks.rs` header both disclose this, citing the need
for an `Authenticator` trait injection to mock `yup_oauth2`.

The disclosed upgrade path is correct. The risk is that a future
change to `cached_access_token` (e.g., swapping `Mutex` for `RwLock`,
or adding a background refresh) could silently break the
coalescing/expiry behavior with no test to catch it.

**Severity:** low-medium. The code reads correct; the risk is
regression-without-detection, not a present bug.

**Minimal fix:** introduce a small `TokenProvider` trait
(`async fn token(&self) -> Result<String>` + an `is_expired` indicator)
with a real `yup_oauth2` impl and a fake in-test impl. Then add tests:
(a) first call fetches, second call hits cache, (b) expired token
triggers refetch, (c) concurrent calls coalesce into one fetch (the
Mutex's reason for existing). This is the upgrade path already named in
`vertex_auth.rs:15-16`.

### F3 — `build_openai_compat_body` tool_choice double-set when both `response_format::JsonObject` and `tool_choice` are present

**Location:** `src/adapters/mod.rs:931-949`

When `response_format == JsonObject` AND `tools` is non-empty AND
`tool_choice.is_some()`, the body's `tool_choice` is set TWICE:
- `:935` sets `body["tool_choice"] = "auto"` (inside the JsonObject arm)
- `:948` sets `body["tool_choice"] = json!("auto")` (the standalone
  `tool_choice.is_some()` block)

The second assignment overwrites the first with a semantically
identical value (`"auto"`), so the observable behavior is correct, but
the code path is confusing: it looks like the `tool_choice.is_some()`
block at `:947-949` is redundant when `response_format` is `JsonObject`.
It is NOT redundant for the case where `response_format` is `None` or
`JsonSchema` and `tool_choice.is_some()` — that's the only path where
`:948` is the sole assignment.

**Severity:** cosmetic / dead-code-smell. No behavior change. The
`:947-949` block could be guarded with `&& !matches!(response_format,
Some(JsonObject))` to make the intent explicit, but that's a
readability fix, not a correctness fix. Not worth a WO on its own;
note for a future `build_openai_compat_body` refactor-on-touch.

### F4 — `retry_backoff` jitter is wall-clock-derived, not random

**Location:** `src/shared/mod.rs:1203-1213`

The jitter is `nanos % cap_ms` where `nanos` is `SystemTime::now()` subsec
nanos. This is a deliberate, documented choice (no new dependency, and
the goal is desynchronizing parallel subagents, not cryptographic
randomness). However:

- Two calls within the same nanosecond (impossible in practice on real
  hardware, but possible in a fast loop on a platform with low-res
  clocks) would get identical jitter.
- The jitter distribution is uniform over `[0, cap_ms)` only if the
  subsec-nanos are uniformly distributed, which they approximately are
  across real wall-clock calls but are NOT across back-to-back calls in
  a tight test loop.

This is **already disclosed** in the function's doc comment and is the
explicit `ponytail:` choice (stdlib before a dep). Not a finding that
needs action; recorded here only because the brief asked about jitter.
The existing `backoff_grows_with_capped_jitter` test correctly bounds
the result by `[base, base+cap]` rather than asserting a specific
distribution, so it's robust to the non-randomness.

## Confirmed-correct items (no action needed)

For completeness, the following brief items were checked and are
verified correct with pinning tests:

- **Anthropic cache-breakpoint cap (4):** `anthropic/mod.rs:294-337`
  counts system + tools breakpoints, then fills remaining budget with
  user messages. `body_cache_breakpoints_capped_at_4` and
  `cache_breakpoint_cap_30_messages_with_tools` pin the cap. The
  regression noted in `cache_breakpoint_cap_30_messages_with_tools`
  (CRIT-1 from WO 20.11.0 — 5 breakpoints tripping Anthropic's limit)
  is fixed.
- **Bedrock envelope byte-space offsets (WO 38.5):** `extract_payload`
  operates on raw bytes, not `from_utf8_lossy` output, so non-UTF8
  preludes/CRCs don't shift offsets. Tests
  `extract_payload_offsets_stay_in_byte_space_with_non_utf8_prelude`
  and `extract_payload_handles_two_frames_with_binary_separator` pin
  it. The multi-frame-per-chunk bug (WO 15.6) is fixed by the
  `while let Some((inner, end)) = extract_payload(...)` drain loop at
  `anthropic_bedrock.rs:191-205`.
- **Bedrock transport-error escaping (WO 44.23):** transport errors
  are JSON-encoded via `serde_json::json!` before being forwarded as
  a `data:` frame, so quotes/newlines in the error Display can't break
  the frame or smuggle extra `data:` lines.
  `parse_bedrock_event_stream_escapes_transport_error_text` pins it.
- **OpenAI-compat base-URL `/v1` de-dup (mm-H15/H16, WO 47.29):** both
  `new` and `with_base_url_and_key` strip exactly one trailing `/v1`
  after the slash trim. `openai_compat_new_strips_only_one_v1` and
  `openai_compat_with_base_url_and_key_strips_one_v1` pin both ctors.
- **Vertex path-segment percent-encoding (mm-H17, WO 47.29):** the
  `PATH_SEGMENT` `AsciiSet` encodes `/`, `?`, `#`, space, `"`, `%`,
  etc. `endpoint_percent_encodes_path_segments` and
  `endpoint_keeps_pchar_ids_unencoded` pin both the encode and the
  no-over-encode cases.
- **OpenAI-compat frame-start line-anchoring (mm-H14, WO 47.29):**
  `find_data_frame_start` requires the `data: ` prefix to be at buffer
  start or after a `\n`/`\r`. Tests in both `openai_compat/mod.rs` and
  `anthropic/sse.rs` pin it.
- **Streaming idle timeout (WO 32.13 ceiling):**
  `STREAM_IDLE_TIMEOUT = 180s` (`mod.rs:38`) with a `ponytail:` comment
  explaining the ceiling and the per-adapter-configurable
