### 1. UTF-8 boundary handling (WO 43.25 / 43.19) — remaining raw byte-slice operations

**Verdict: production code is clean; one test-only slice is technically unsafe.**

The two WO 43 fixes are well-implemented and pinned:

- **PTY tail cut** (`events.rs:656-669`): When `content.len() > PTY_TAIL_BYTES`
  (64 KiB), the code computes `start = total - PTY_TAIL_BYTES` then walks
  backward with `while !last.content.is_char_boundary(start) { start -= 1; }`
  BEFORE slicing `&last.content[start..]`. The regression test
  `bash_partial_output_tail_cut_handles_multibyte_without_panic`
  (`events.rs:2815-2868`) constructs content where the 64 KiB boundary
  lands inside a 4-byte `🎉` and asserts no panic + char-aligned tail.
  **Correct.**

- **`set_cursor_line_col`** (`app.rs:894-918`): Uses `input.chars().enumerate()`
  (char indices, not byte offsets) to find the target line. The comment at
  `:895-900` explicitly names the WO 43.19 fix: the prior impl used
  `char_indices()` (byte offsets) which made `char_idx` exceed the char
  index on multibyte input. Three regression tests pin the fix:
  `set_cursor_line_col_handles_multibyte_on_earlier_line`,
  `set_cursor_line_col_handles_cjk_multibyte`,
  `set_cursor_line_col_handles_combining_char_on_earlier_line`
  (`events.rs:2748-2807`). **Correct.**

I exhaustively checked every remaining byte-slice site in the TUI:

| Site | Slice | Safe? | Why |
|---|---|---|---|
| `events.rs:666` | `last.content[start..]` | yes | `start` walked to char boundary (`is_char_boundary` loop at :663) |
| `events.rs:2863` | `last.content[header_end + 1..]` | yes | `header_end` from `find('\n')` (1-byte ASCII), `+1` is next char start |
| `rendering/mod.rs:112` | `span.content[slice_start..slice_end]` | yes | `slice_start/end` derived from `start.saturating_sub(span_start)` where `start/end` come from `case_fold_with_mapping` which returns original byte offsets at char boundaries |
| `keys/text.rs:84` | `input[..cursor_byte].rfind('\n')` | yes | `cursor_byte` from `cursor_byte()` (`char_indices().nth()`) is a char boundary; `rfind('\n')` returns a `\n` boundary |
| `keys/mod.rs:1257-1283` | `input[line_start..line_end]`, `input[..line_start]`, `input[byte_pos..]` | yes | `line_start/end` from `current_line_bounds` (char-boundary-safe per above); `byte_pos` from `cursor_byte()` |

| `commands/mentions.rs:227,244` | `input[cursor..m.start]`, `input[cursor..]` | yes | `cursor`/`m.start` are byte offsets from the `@`-scan, which lands on ASCII-char boundaries |

**F1 (Low) — `events.rs:1964` test-only byte slice:** In the test
`bash_partial_output_caps_streaming_card_to_tail_budget`, the assert message
formats `&entry.content[..200.min(entry.content.len())]`. If the 200th byte
of the capped content lands inside a multibyte char, this will panic with
"byte index is not a char boundary". The content at that point is the
truncation-marker form (`… [N bytes total, showing last 64K]\n{tail}`), and
the marker prefix is ASCII + the tail is char-aligned (per the WO 43.25
fix), so the 200th byte is almost certainly inside the ASCII marker. But
"almost certainly" is not "never" — a multibyte char immediately after the
`\n` could land at byte 200. **This is test-only code; it would only panic
on a test failure (the assert condition), not in production.** Fix: replace
with `entry.content.chars().take(200).collect::<String>()` or
`&entry.content[..entry.content.char_indices().nth(200).map(|(b,_)| b).unwrap_or(entry.content.len())]`.

**F2 (Low) — `commands/sessions.rs:259` `truncate_id`:** The comment says
"ids are date+seq ASCII so this is safe." This is true for the current
session-ID format (`2026-08-16-session-01`). If a future feature allows
user-named sessions with multibyte chars (e.g. Japanese labels), this would
panic. The fix is one line: use `truncate_to_char_boundary` (already
available from `commands/memory.rs`). Not a current bug — a future-proofing
gap.

### 3. Render cache invalidation — is the cache invalidated at every mutation site?

**Verdict: yes, with one subtle dependency on the render path's own
parameter-snapshot check.**

The `ChatRenderCache` (`app.rs:36-86`) stores per-message `(version, Vec<Line>)`
plus a parameter snapshot (`content_width`, `search_query`, `tool_collapsed`,
`expanded_tools`, `collapsed_messages`). Invalidation happens at two
levels:

**Level 1 — parameter snapshot** (`widgets/chat/mod.rs:131-146`): Every
render call checks `params_match()`. If any of the 5 parameters changed,
the entire cache is cleared and re-snapshotted. This catches:
- terminal resize (content_width change)
- search query change
- Ctrl+T toggle (tool_collapsed change)
- per-entry expand/collapse (expanded_tools / collapsed_messages change)

**Level 2 — entry version** (`widgets/chat/mod.rs:188-201`): Each cache
slot stores `(version, lines)`. The render checks `version == entry.version`
— if a message was mutated (e.g. streaming token appended, which calls
`bump_version()`), its slot is re-rendered. Streaming entries are
explicitly excluded from the cache (`widgets/chat/mod.rs:188-201`) so they
re-render every frame.

**Explicit `clear_entries()` call sites** (the level-1/2 checks don't
cover these because the message list itself changed identity, not just
parameters):

| Site | Why needed | Present? |
|---|---|---|
| `events.rs:446` (CompactionReport) | message list rebuilt from new_messages | yes |
| `events.rs:896` (prune_display_messages) | `drain(0..n_drop)` re-indexes kept entries | yes |
| `commands/fork.rs:191` (resume_conversation_log) | message list swapped to different session | yes |
| `keys/slash_commands.rs:1109` (handle_theme_command) | theme change — cached Lines carry old Style | yes |
| `widgets/chat/mod.rs:138` (params changed) | level-1 parameter check | yes |

**The `/clear` command** (`slash_commands.rs:478-485`) clears
`messages` but does NOT call `chat_render_cache.clear_entries()`. This is
fine because the render path's `entries.resize_with(messages.len(), || None)`
at `widgets/chat/mod.rs:149-153` shrinks the cache to 0 entries when
messages is empty. The next render repopulates from scratch. **Correct,
but only because the resize happens every frame.** If a future change
moved the resize to a conditional path, `/clear` would serve stale slots.

**`handle_persona_complete`** (`mod.rs:1534-1645`) replaces
`state.conversation.messages` at `:1622` but does NOT call
`chat_render_cache.clear_entries()`. This is fine for the same reason —
the render path's `resize_with` grows/shrinks the cache to match, and the
new entries have `version=0` which won't match any stale slot's version.
**Correct, same dependency.**

**F3 (Low) — theme is not in `params_match`:** The cache's parameter
snapshot does NOT include `theme`. A theme change is caught by the
explicit `clear_entries()` in `handle_theme_command` (`slash_commands.rs:1109`),
not by the parameter check. If a future code path changed `state.ui.theme`
without calling `clear_entries()`, the cached Lines would serve stale
colors until the next parameter change forced a full clear. The
`handle_theme_command` is the only theme mutation site today, so this is
safe — but it's a latent coupling. Adding `theme` to the parameter
snapshot (or at least a `theme_generation: u64` counter) would make the
cache self-healing.

### 4. Streaming card routing (call_id) — race conditions in streaming_tool_index

**Verdict: no race conditions. The map is single-threaded (owned by the
event loop task); events are serialized by the channel. All index-rebase
paths are correct and tested.**

`streaming_tool_index: HashMap<String, usize>` maps `call_id → message
index`. It lives on `AppState`, which is owned by `run_event_loop`
(`mod.rs:924`). All mutations happen inside `dispatch_turn_event`, which
is called from `drain_turn_events` (`events.rs:822`), which runs on the
event-loop task. There is no concurrent access — events arrive via a
tokio `mpsc::channel` and are drained sequentially.

The "race" the brief asks about is event-ordering within the channel, not
true thread-level racing. The code handles every ordering:

1. **Normal: ToolStart → chunks → ToolResult.** ToolStart registers the
   card at `events.rs:228-230`. Chunks route via `events.rs:597`. ToolResult
   removes the map entry at `events.rs:561` and rebases at `:572`.
   Tested: `concurrent_same_name_pty_streams_route_to_separate_cards`
   (`events.rs:1409-1509`).

2. **Chunks before ToolStart (race-ahead).** A chunk with an unknown
   `call_id` creates and registers a card at `events.rs:616-625`. The
   later ToolStart finds the existing card and keeps it (`events.rs:202-216`),
   re-marking it streaming. No duplicate. Tested:
   `unknown_call_id_chunk_creates_and_registers_card` (`events.rs:1558-1604`).

3. **Out-of-order ToolResult (parallel batch).** When call-b finalizes
   before call-a, call-b's placeholder is removed at its registered index,
   and `rebase_streaming_indexes` decrements call-a's index. Tested:
   `call_id_tool_results_pair_with_own_placeholder`
   (`events.rs:1515-1552`) and the out-of-order finalization in
   `concurrent_same_name_pty_streams_route_to_separate_cards`
   (`events.rs:1459-1501`).

4. **Late chunk after TurnComplete.** `TurnComplete` clears the map
   (`events.rs:537`) and sets `turn_finished = true` (`events.rs:541`).
   A late `BashPartialOutput` with no live map entry and `turn_finished`
   true is dropped (`events.rs:629`). Tested:
   `late_bash_partial_output_after_turn_complete_is_dropped`
   (`events.rs:1717-1787`).

5. **Legacy empty-call_id events (old replay traces).** The legacy path
   (`events.rs:553-560`) uses name-based matching via
   `remove_tool_placeholder`, which is explicitly guarded to NEVER steal
   an id-registered card (`events.rs:723-730`). Tested:
   `legacy_tool_result_never_steals_call_id_card`
   (`events.rs:1612-1711`).

6. **Prune during streaming.** `prune_display_messages` remaps the
   `streaming_tool_index` with the same `remap` closure used for
   `collapsed_messages` and `expanded_tools` (`events.rs:878-883`).
   Entries pointing at pruned indices are dropped (remap returns None).
   Tested: `prune_clears_chat_render_cache` (`events.rs:2011-2029`) —
   while this test asserts cache clearing, the prune path's remap logic
   is the same closure pattern used for the other index sets.

**F4 (Low, theoretical) — `finalize_streaming_placeholder` stale-index
edge case:** When `ToolResult` arrives with a `call_id`, the function
does `streaming_tool_index.remove(call_id)` at `events.rs:561` (always
removes the map entry). Then it checks `is_streaming_card` at `:565-569`.
If the card at `idx` is NOT streaming (somehow already finalized), it
falls back to `remove_tool_placeholder` (name matching) at `:573-580`.
If that ALSO fails (returns None), the map entry is gone but the
placeholder is still in the deque. This would strand the placeholder as
a ghost "streaming" row. In practice this path is unreachable: a
`ToolResult` always follows a `ToolStart` which sets `streaming = true`,
so `is_streaming_card` is always true. The fallback is defense-in-depth.
**Not a bug — a theoretical edge case in defensive code.**

### 5. Doom-loop banner — does the selection highlight match the actual action?

**Verdict: yes, verified by two regression-pin tests.**

The banner renders `DoomLoopAction::ALL` iteratively
(`doom_banner.rs:142-161`), highlighting the entry where
`i == selection.index`. The `Enter` key handler
(`keys/mod.rs:152-154`) calls `state.doom.doom_loop_selection.selected()`,
which returns `DoomLoopAction::ALL[self.index % ALL.len()]`
(`doom_banner.rs:72-74`). The render and the key handler read from the
same `state.doom.doom_loop_selection` field, and both index into the same
`DoomLoopAction::ALL` const array. They cannot disagree.

The WO 43.31 bug (where `render_if_active` passed a hardcoded
`DoomLoopSelection { index: 0 }` and the banner always highlighted "Break"
while Enter ran the user's hidden choice) is fixed by passing
`app_state.doom.doom_loop_selection` at `doom_banner.rs:172`. Two tests
pin this:

- `doom_banner_highlights_stored_selection_not_hardcoded_zero`
  (`doom_banner.rs:235-280`) — renders with `index: 1` and asserts
  `[ Plan` is highlighted, `[ Break` is not.
- `render_if_active_highlights_stored_app_state_selection`
  (`doom_banner.rs:303-333`) — end-to-end: builds an `AppState` with
  `doom_loop_selection.index = 1`, calls `render_if_active`, asserts the
  buffer contains `[ Plan` not `[ Break`.

**Esc on the doom banner maps to `DoomLoopAction::Continue`**
(`keys/mod.rs:156-158`), which dismisses the warning without canceling
the generation. This is the documented behavior — Esc is "cancel the
warning", not "cancel the generation". The user picks "Break" to cancel
the generation. Correct.

### 6. Terminal restoration on panic (WO 38.2) — does the panic hook correctly restore the terminal before abort?

**Verdict: yes, correct ordering, tested.**

The panic hook (`mod.rs:166-191`) is installed via `PANIC_HOOK_ONCE.call_once`
BEFORE `enable_raw_mode()` (`mod.rs:582-583`), so it is active for every
later panic. The hook body (`panic_hook_with`, `mod.rs:179-191`):

1. `disable_raw_mode()` (`:185`) — exits raw mode first
2. `force_terminal_reset(&mut *w)` (`:188`) — writes raw ANSI escape
   sequences directly to stdout (bypasses crossterm's state tracking, so
   it works even when the terminal is in a corrupted state):
   - `\x1b[?2004l` — disable bracketed paste
   - `\x1b[?1000l\x1b[?1002l\x1b[?1003l\x1b[?1006l\x1b[?1015l` — disable mouse
   - `\x1b[?1049l\x1b[?47l` — leave alternate screen (xterm + vt100)
   - `\x1b[?1l` — disable cursor-key application mode
   - `\x1b[0m` — reset all text attributes
   - `\x1b[?25h` — show cursor
   - `\x1b[2J\x1b[H` — clear screen + home cursor
3. `previous(info)` (`:189`) — chains to the previous hook (prints the
   panic message) AFTER the reset, so the message lands on a clean
   cooked-mode screen.

The ordering is critical: reset FIRST, then report. The test
`panic_hook_resets_terminal_before_reporting` (`mod.rs:1834-1873`) drives
the hook with an in-memory buffer and a fake "previous hook" that writes
`<PANIC-REPORTED>`, then asserts that `\x1b[?1049l`, `\x1b[?25h`, and
`\x1b[2J` all appear BEFORE `<PANIC-REPORTED>` in the output.

**Why a hook and not just `TerminalGuard`**: the release profile uses
`panic = "abort"`, and `Drop` never runs on the abort path — but the panic
hook does (the runtime invokes it, then aborts). The comment at
`mod.rs:160-165` explains this. `TerminalGuard::drop` (`mod.rs:89-116`)
mirrors the same reset sequence for the normal-exit path.

**`force_terminal_reset` is best-effort** (`mod.rs:136-153`): each
`write_all` is `let _ = w.write_all(...)` — errors are swallowed. The test
`force_terminal_reset_does_not_panic_on_closed_writer` (`mod.rs:1792-1807`)
drives it with a `BrokenWriter` that always returns `BrokenPipe` and
asserts no panic. This is the right behavior for shutdown code — there is
nothing useful to do with a write error at this point.

**One observation (not a bug):** `force_terminal_reset` writes `\x1b[2J`
(clear screen) which wipes the primary screen's scrollback. This is
aggressive but correct for a panic — the priority is "terminal is usable",
not "preserve scrollback". The panic message follows immediately on the
clean screen.

## Additional findings (not on the audit list)

### F5 (Low) — `handle_input_key` Ctrl+C: cancel-channel-dropped path sets should_exit but doesn't push a system message

`keys/mod.rs:1218-1230`: When `ctx.cancel_tx.send(())` fails (executor
gone), the code sets `state.session.should_exit = true` and returns
`Ok(())` but does NOT push a system message explaining the exit. The
user's terminal will just close. Compare with the persona-cancel path
(`:1203-1216`) which pushes "⛔ Persona cancelled." and the
generation-cancel path (`:1239-1247`) which pushes "⛔ Generation
cancelled. Press Ctrl+C again to quit." The cancel-channel-dropped branch
is a "the executor is already dead" edge case, so a message would only
flash briefly before the TUI tears down. Acceptable, but inconsistent
with the other two branches.

### F6 (Low) — `handle_executor_channel_closed` pushes a system entry the user may not see

`mod.rs:344-354`: When the executor channel closes, the function pushes
a system entry ("⚠️ Session executor exited unexpectedly…") and returns
`true` so the caller sets `should_exit`. The entry is pushed into
`state.conversation.messages`, but the loop breaks immediately after
(`mod.rs:985-987`) and falls through to teardown. The entry may not be
rendered (the loop's `if !state.dirty { continue; }` check at `:1192`
would skip the final render). In practice, `handle_executor_channel_closed`
calls `state.mark_dirty()` (`:352`), and the `if first_executor_event`
check at `:1096` would have set dirty if an event was consumed — but the
closed-channel case is `first_executor_event = None` (the `recv()` returned
`None`), so the `if first_executor_event.is_some()` gate at `:1096` is
false. The `handle_executor_channel_closed` call at `:1048` sets
`should_exit = true`, and the `mark_dirty` inside the helper sets dirty.
The next iteration's `if state.session.should_exit { break Ok(()); }`
at `:985` breaks BEFORE the render check at `:1192`. So the system entry
is pushed but never rendered. The user sees the terminal restore to
cooked mode with no explanation. The `eprintln` in `teardown`'s
`tracing::warn` goes to the log file, not the terminal. **Minor UX gap**
— the user's terminal just closes. Putting the message on `eprintln!`
AFTER teardown (so it appears in cooked mode) would be more helpful.

### F7 (Low) — `run_session_picker_sync` does not install a panic hook for its own session

`mod.rs:206-235`: This function calls `install_panic_hook()` at `:211`,
which uses `PANIC_HOOK_ONCE.call_once`. If `run_tui` already installed the
hook, the `call_once` is a no-op (fine). If the picker runs standalone
(before `run_tui`), the hook is installed for the picker's session. But
the picker creates its own `TerminalGuard` at `:216` and does NOT have a
`teardown` function — it relies on `_guard`'s drop. If `event::read()`
panics inside the loop, the panic hook fires (good), but the `Terminal`
object is dropped without explicit `disable_raw_mode` / `LeaveAlternateScreen`
— the panic hook handles raw mode + alt screen, so this is fine. **No bug.**

### F8 (Informational) — `widgets/chat/mod.rs` u16 scroll clamp

`widgets/chat/mod.rs:354-367`: The `scroll_u16` clamp to `u16::MAX` is
documented with a `ponytail:` ceiling comment (":354-362"): ratatui 0.30's
`Paragraph::scroll` takes `u16`, so conversations with >65,535 wrapped
lines silently wrap the view. The comment names the upgrade path (ratatui
0.31+ exposes `scroll((u32, u32))`). This is a known limitation, not a
bug — it's properly documented with a `ponytail:` spec pin.

### F9 (Informational) — `render_app` z-order is explicit and tested

`mod.rs:1347-1512`: The z-order (chat → overlays → slash menu → file
completer → input → status → session picker → approval dialog → command
palette → help overlay → doom banner) is rendered in order, so later
widgets paint over earlier ones. The doom banner is last, so it sits on
top of everything. The key routing in `dispatch_kb_events`
(`mod.rs:1211-1238`) routes to the doom banner first, then approval, then
regular input — matching the z-order. The selftest `doom_loop_banner`
(`selftest.rs:509-531`) verifies the banner renders over the chat. The
`modal_captures_keys` predicate (`mod.rs:1280-1287`) and the WO 48.28
paste-gate test (`mod.rs:2189-2281`) verify paste respects the same
modal set. **Correct and well-tested.**

### F10 (Informational) — `approval_dialog_area` bounds guard

`components/approval.rs:472-506`: Returns `None` when `area.height < 4`
or `area.width < 20`, preventing the "yeeted on approval" crash where the
prior `.clamp(10, area.height)` panicked when `area.height < 10` (min >
max). The `debug_assert!` at `:500-504` is a defensive invariant check.
The help overlay has the same guard (`help_overlay.rs:29-32`). **Correct.**

### F11 (Informational) — selftest harness exercises the production render path

`selftest.rs:39-46`: `render_to_string` calls `super::render_app(f, state)`
— the exact same function `render_frame` calls in production
(`mod.rs:1334`). The harness feeds `TurnEvent`s through the production
`dispatch_turn_event` (`selftest.rs:98-99`). 25+ scenarios cover:
streaming stress (500 tokens), word-wrap, tool cards, tool grouping,
approval dialog, budget indicator, scroll, slash menu, search, doom
banner, empty state, Unicode (emoji/CJK/combining char) at wide and
narrow geometry, and key-dispatch scenarios (Ctrl+C two-press, Esc
cancel-only, invisible-textbox dirty mark). **This is genuine
end-to-end coverage, not theater.**
