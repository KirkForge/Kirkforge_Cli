# WO 50.05 — Tools & Task System deep-read audit (2026-09-05)

## Status: Open (audit only — findings, no fixes applied)

Auditor: read-only deep pass over `src/tools/**` and `src/tools/task/**`.
Every file in the assigned segment was read line-by-line. Findings are
ranked by severity. Line numbers are accurate as of the audited commit.

---

## Summary

The tools layer is mature and well-tested. The inter-subagent messaging
tools (`send_message`, `list_agents`, `update_task`) share the
`TaskManager` `Arc<Mutex>` and follow the established lock-order
(task_manager → handle.pending_messages), so they are race-safe against
the worker closure. The subagent depth limit, however, has a real
**bypass via `workflow_run`** and a separate **reset-on-step** behavior
that under-counts nesting. The `edit_file` fuzzy matcher has a known
class of edge cases around CRLF + trailing-whitespace interaction that
is partially mitigated but not fully closed. The `web_fetch` SSRF
surface is the strongest part of the layer — layered guards with
documented ceilings.

| Severity | Count |
|----------|-------|
| HIGH     | 1     |
| MEDIUM   | 4     |
| LOW      | 6     |

## HIGH

### H1 — `workflow_run` resets `subagent_depth` to 0, bypassing the nesting ceiling

**Location:** `src/tools/workflow.rs:474, 545, 631, 704` (four sites);
`src/session/executor_adapter.rs:125`; `src/tools/workflow.rs:619-633`
(batch agent steps).

The `task` tool enforces `max_subagent_depth` at
`src/tools/task/task_tool.rs:221-231`:

```rust
let next_depth = ctx.subagent_depth + 1;
if next_depth > self.max_subagent_depth {
    return ToolOutcome::Error { ... };
}
```

But every `workflow_run` code path that constructs a `TaskRequest` or a
per-step `ToolContext` hardcodes `subagent_depth: 0`:

- `TaskSpawnerStepRunner::run_step` (`workflow.rs:474`) — agent steps
- `TaskSpawnerStepRunner::run_tool` (`workflow.rs:545`) — tool steps
- `run_batch` agent branch (`workflow.rs:631`) — parallel agent steps
- `run_batch` tool branch (`workflow.rs:704`) — parallel tool steps
- `ExecutorAdapter::execute` (`executor_adapter.rs:125`) — orchestrator
  roles

**Impact.** A subagent running at depth 3 (the default ceiling) can
call `workflow_run`, which spawns its own agent/tool steps at depth 0.
Those steps can themselves call `task` to spawn a fresh subagent tree
from depth 0 again — unbounded recursion through the workflow tool. The
`InProcessTaskSpawner::run_task_detailed` faithfully threads
`request.subagent_depth` into the executor
(`task_spawner.rs:549`), but it never independently checks the ceiling;
it trusts the caller. The only enforcement point is the `task` tool
itself, and the workflow tool hands it a reset depth.

**Concrete attack shape.** A model at depth 3 calls
`workflow_run("loop")` whose template has one agent step whose prompt
is "call task(persona='coder') to run workflow_run('loop')". The
inner `task` call sees `ctx.subagent_depth == 0` (workflow reset it),
so the depth guard passes, and the inner subagent can again call
`workflow_run`, and so on — each cycle minting a fresh depth-0
context. With `max_turns > 1` per step this is also an unbounded
token sink.

**Fix shape.** Thread `ctx.subagent_depth + 1` into every workflow
`TaskRequest`/`ToolContext` site (the four sites above plus the
adapter). The workflow tool already receives `ctx: &ToolContext` in
`run`; it just doesn't propagate `ctx.subagent_depth`. The
`TaskSpawnerStepRunner` stores `cancel_token` but not depth — add a
`subagent_depth: usize` field populated from `ctx.subagent_depth + 1`
in `run_workflow`'s `WorkflowRunArgs`. Same for the adapter: it should
read the parent executor's depth and increment, not hardcode 0.

## MEDIUM

### M1 — `TaskManager::set_status` can race the worker closure on `result`/`error`

**Location:** `src/tools/task/mod.rs:537-577` (`set_status`),
`:581-590` (`set_completed`), `:594-602` (`set_failed`); worker at
`src/tools/task/task_tool.rs:335-356`.

The worker closure (background path) writes `handle.result` /
`handle.error` under `manager.lock()`. `update_task`'s
`set_completed`/`set_failed` also write those fields under
`manager.lock()`. The lock makes each write atomic, but there is no
**compare-and-set**: if the worker is about to write `Ok(summary)` and
a concurrent `update_task(status="completed", note="X")` fires first,
the worker then overwrites `result` with its own summary, silently
clobbering the subagent's self-reported status. The reverse race
(update_task after worker) is the intended direction and is fine.

This is documented loosely ("the one path that writes
result/error/cancel_requested from outside the worker closure") but
the **race resolution direction is unspecified** — last-writer-wins,
and the two writers disagree on which is last.

**Fix shape.** Either (a) have `set_completed`/`set_failed` no-op if
`handle.is_terminal()` (matches `send_message`'s terminal guard at
`:505-507`), or (b) document the race as "subagent self-report wins
only if it fires before the worker records the spawner's summary" and
add a test pinning the documented direction. Option (a) is safer and
matches the existing `send_message` precedent.

### M2 — `set_status("running")` on a terminal task resurrects it; the worker may still be tearing down

**Location:** `src/tools/task/mod.rs:548-553`.

`set_status("running")` clears `result`/`error`/`cancel_requested` and
sets `started = true`. A subagent that has already returned
(`run_task` resolved, worker closure about to lock the manager and
write its summary) can be flipped back to `Running` by a peer's
`update_task` call between the spawner's return and the worker's lock
acquire. The worker then writes `result` over the resurrected state,
which is at least consistent — but `task_output` polled in the window
sees `Running` for a task whose subagent is gone, and
`completed.notify_waiters()` was already fired by the earlier
`set_completed`/`set_failed`, so a second wait on `completed` never
fires.

**Fix shape.** Reject `set_status` on a handle whose worker has
already notified (add a `worker_finalized: AtomicBool` flipped by the
worker right before `notify_waiters()`), or simply reject any
`set_status` transition out of a terminal state (the `is_terminal`
guard that `send_message`/`cancel` use). The current code allows
terminal → running, which is the only path that can mislead
`task_output` waiters.

### M3 — `edit_file` fuzzy fallback: single-line old_string with no trailing newline can splice the following line

**Location:** `src/tools/edit_file.rs:267-326` (fuzzy span
computation).

The fuzzy matcher maps `n_start` (line index in normalized content)
back to original-content byte offsets via `line_byte_start` and
`line_byte_end`. `line_byte_end(n_start + o_lines.len() - 1)` returns
the offset *before* the last matched line's terminator — this is the
WO 47.22 fix and it is correct for multi-line spans. But there is an
edge case when `old_string` is a single line (`o_lines.len() == 1`)
supplied **without** its trailing newline and the file line has
trailing whitespace: the normalized match succeeds, `byte_start` is
the line start, `byte_end` is the offset before the `\n` (or `\r\n`).
The replacement swaps `[byte_start, byte_end)` with `new`, which is
correct *only* if `new` is meant to replace the line body without its
terminator.

The test `test_fuzzy_fallback_single_line_crlf_preserves_following_line`
(`edit_file.rs:807-842`) pins the case where `old_string` includes the
`\n` (so `o_lines.len() == 2` after `.lines()`, the last being empty).
It does **not** cover the case where `old_string` is exactly the line
body (no terminator) and `new` is the replacement body. In that case
the replacement is correct, but the diff reviewer (`review_diff`,
`:514-550`) counts the *normalized* deletion ratio, which can flag a
legitimate single-line whitespace-tolerant edit as "deletes N lines
but old_string is only 1 line" if `new` happens to insert newlines.

This is a **low-frequency corruption risk**, not a confirmed
corruption — the byte-offset math is correct after WO 47.22 — but the
diff-review heuristic interacts poorly with the fuzzy path because
`review_diff` sees the *original* `old_string` (with trailing
whitespace) but the actual replacement span is the *normalized* span.
A false-positive diff-review block on a valid fuzzy edit leaves the
model unable to apply a correct edit without disabling `diff_review`.

**Fix shape.** Either (a) add a test for `old_string` == line body
(no terminator) + `new` with embedded newlines, pinning the expected
diff-review behavior, or (b) pass the normalized `old_string` to
`review_diff` when the edit came from the fuzzy path so the deletion
ratio is computed against the actual replaced span. Option (b) is
more correct.

### M4 — `bash` env scrubbing does not strip `*PASS` (only `_PASS`)

**Location:** `src/session/bash_runner/mod.rs:569-580`
(`SECRET_ENV_SUFFIXES`).

The suffix list includes `_PASS` but not bare `PASS` or `*PASSPHRASE`.
An env var named `DB_PASS` (no underscore-prefix variant some tools
use) — wait, `DB_PASS` does end with `_PASS`, so it IS scrubbed. But
`PASSPHRASE` (no underscore) and `GPG_PASSPHRASE` — the latter ends
with `_PASSPHRASE`, not in the list. `GPG_PASSPHRASE` is a common
credential shape for code-signing setups. The exact-match list
(`SECRET_ENV_EXACT`) includes `TOKEN`/`SECRET`/`API_KEY` but not
`PASSPHRASE`.

This is a **gap, not a leak today**: the most common shapes
(`*_API_KEY`, `*_TOKEN`, `*_SECRET`, `*_PASSWORD`, `*_ACCESS_KEY`,
`*_PRIVATE_KEY`, `*_CREDENTIAL`, `*_PASS`, `*_CONN_STRING`,
`*_CONNECTION_STRING`) cover the vast majority of real-world secret
env names. But `PASSPHRASE` and `KEY` (bare, as in `OPENSSL_KEY`) are
not covered. The scrub is a defense-in-depth layer; the model can
still `cat ~/.ssh/id_rsa` if path-guard allows it, so this is not the
primary boundary.

**Fix shape.** Add `_PASSPHRASE`, `_KEYFILE`, and bare `PASSPHRASE`
to the suffix/exact lists, or document that the scrub is a heuristic
and the real boundary is `PathGuard` + landlock (the comment at
`:602-611` already implies this). Low priority unless an audit
demands it.

## LOW

### L1 — `TaskHandle.notes` is a plain `Vec<String>`, not under a mutex

**Location:** `src/tools/task/mod.rs:275` (`pub notes: Vec<String>`),
`:519-525` (`append_note`), `list_agents.rs:81`
(`guard.get(&e.id).map(|h| h.notes.len())`).

`notes` lives on `TaskHandle` and is mutated via
`TaskManager::append_note` under the `task_manager` mutex. `list_agents`
reads `h.notes.len()` under the same mutex. So access is serialized —
no data race. But `TaskHandle` is `Clone` (line 255) and the
`cancel_handles()` / `pending_messages` pattern deliberately shares
`Arc`'d fields across threads. `notes` is a plain `Vec`, so if a
future caller clones the handle and reads `notes` without the manager
lock (e.g. the spawner turn loop surfacing notes in a turn), they get
a snapshot that can be stale or torn if a concurrent `append_note` is
mid-push. No such caller exists today — the spawner only reads
`pending_messages` (Arc<Mutex>) and the cancel flag (Arc<AtomicBool>),
never `notes` — so this is a **latent risk**, not a current bug.

**Fix shape.** If the spawner ever needs to read notes mid-run, wrap
`notes` in `Arc<Mutex<Vec<String>>>` like `pending_messages`. Until
then, add a doc comment on `notes` saying "only access under
`task_manager` lock; not shared with the spawner turn loop."

### L2 — `drain_pending_messages` uses `unwrap_or_else(|e| e.into_inner())` (poison-tolerant)

**Location:** `src/tools/task/mod.rs:332-343`.

Every `pending_messages.lock()` in the task module uses
`.unwrap_or_else(|e| e.into_inner())` to survive mutex poison. This is
the codebase convention (AGENTS.md §7 notes it for the undo stack) and
is correct for a tool whose liveness matters more than its consistency
on panic. But `drain_pending_messages` is called by the spawner turn
loop, and a poisoned mutex means some other thread panicked while
holding the lock — the drained messages may be a partial state. The
alternative (propagating the poison) would hang the subagent, which is
worse. Acceptable; noted only for completeness.

### L3 — `list_agents` reads `notes.len()` but not `notes` content

**Location:** `src/tools/task/list_agents.rs:81`.

`list_agents` surfaces `(N notes)` but not the note text. A subagent
that wants to read a peer's progress notes has no tool to do so — it
must infer from `list_agents`'s count + `task_output` (which returns
the terminal summary, not notes). This is a **feature gap, not a
bug**. The `update_task` docstring says notes "surface in
`list_agents`", but `list_agents` only shows the count. Either the
docstring overclaims or the tool under-delivers.

**Fix shape.** Either (a) make `list_agents` include the last note (or
all notes, truncated) in its output, or (b) fix the `update_task`
docstring to say "notes count surfaces in `list_agents`; note text is
not currently exposed to other subagents."

### L4 — `web_fetch` `extract_host` percent-decodes but `host_is_literal_internal_ip` does not re-parse the decoded form for IPv6 brackets

**Location:** `src/tools/web_fetch.rs:451-461` (`extract_host`),
`:346-354` (`host_is_literal_internal_ip`).

`extract_host` strips `[` `]` from IPv6 literals (line 452-454) and
percent-decodes the host. `host_is_literal_internal_ip` then calls
`host.parse::<IpAddr>()`. For a percent-encoded IPv6 literal like
`http://%5b%3a%3a%31%5d/` (which decodes to `[::1]` then strips to
`::1`), this works. But for a *non-percent-encoded* bracketed IPv6
literal with userinfo, e.g. `http://user:pass@[::1]/`, `extract_host`
correctly strips userinfo via `rsplit('@')` then strips brackets, so
`::1` reaches the parse. This path is tested indirectly by
`rejects_ipv4_mapped_v6_metadata_literal` (`:959-975`). The gap: a
URL like `http://[::1%eth0]/` (zone-id) parses as an `IpAddr`? —
`"::1%eth0".parse::<IpAddr>()` returns `Err` on stable Rust, so the
literal-IP guard returns `false` (not internal), and the request
falls through to `host_resolves_to_internal_ip`, which also fails the
`host.parse::<IpAddr>()` check at `:377` and proceeds to
`resolver.resolve("::1%eth0:80")` — `getaddrinfo` on a zone-id IPv6
is platform-dependent. On Linux glibc, `::1%eth0` resolves to `::1`,
so the rebinding guard catches it. On a platform where it doesn't
resolve, `host_resolves_to_internal_ip` returns `true` (fail-closed
on resolver error, WO 38.3). So the zone-id path fails closed. This
is a **non-issue in practice** but the analysis is non-obvious; a
comment would help.

### L5 — `atomic_write` does not fsync the parent directory

**Location:** `src/tools/atomic_write.rs:20-26` (ceiling comment).

Already documented as a deliberate ceiling (hard power loss after
rename can lose the directory entry update). Not a bug; the tradeoff
is explicitly accepted. Noted only because the audit asks about
atomic_write specifically — the helper is correct for its stated
contract.

### L6 — `validate_tool_args` does not validate `enum` / `const` schema constraints

**Location:** `src/tools/mod.rs:24-76`.

The validator checks `required` keys and `type` (string/number/etc),
but not `enum` (e.g. `lsp_query`'s `operation` enum) or `const`. A
model passing `{"operation": "bogus"}` to `lsp_query` passes
`validate_tool_args` and is rejected only inside `LspQuery::run`'s
match arm. This is fine — the tools themselves validate enum values —
but it means `validate_tool_args` is a coarse gate. Not a bug;
documented for awareness.

## Positive findings (things that are correct and worth noting)

1. **`send_message` / `list_agents` / `update_task` lock discipline.**
   All three take `task_manager.lock()` first, then (for `send_message`)
   `handle.pending_messages.lock()` nested. The worker closure takes
   `task_manager.lock()` only. The spawner turn loop drains
   `pending_messages` via `Arc::clone` without the manager lock. Lock
   order is consistent (manager → pending_messages); no deadlock path
   found.

2. **`TaskManager::cancel` kills exactly the owned bash jobs.** WO 37.1
   minted a process-global `NEXT_TASK_ID` counter
   (`task/mod.rs:39`), so two managers never produce colliding
   `task-N` owner tags. `cancel_by_owner` is dispatched as a detached
   tokio task when a runtime is up (`:470-476`), and the test
   `task_cancel_kills_owned_bash_jobs_spares_main_session`
   (`:1226-1302`) pins the behavior. This is solid.

3. **`web_fetch` SSRF layering.** Four guards in order: scheme allowlist
   → deny-list → literal-internal-IP → DNS-resolve-and-check →
   DNS-pinned client. Each guard fails closed (malformed URL → denied;
   resolver error → denied). Redirects are disabled
   (`:113`) with a documented ceiling. The IPv4-mapped IPv6 path is
   handled (`is_internal_addr:401-403`). The pinned-client build
   failure fails closed (`:517-518`, WO 47.33). This is the
   best-defended surface in the segment.

4. **`edit_file` fuzzy CRLF fix (WO 47.22).** The byte-offset math at
   `:284-316` correctly uses `match_indices('\n')` rather than
   `str::lines()`, so CRLF lines are not undercounted. The
   `line_byte_end` closure strips the `\r` before the `\n` only when
   present. The five fuzzy CRLF tests (`:613-842`) pin the behavior
   across single/multi-line, LF/CRLF, with/without trailing
   whitespace. This was a real corruption bug that is now fixed and
   pinned.

5. **`atomic_write` O_EXCL + random tmp name.** WO 46.24 migrated the
   predictable-`.tmp` sites to this helper. `create_new(true)` is
   `O_EXCL|O_CREAT` (`:58`), the tmp name includes pid + nanos + a
   monotonic counter (`:37-42`), and the helper preserves the target's
   Unix mode on overwrite (`:66-69`, tested at `:243-277`). The
   `write_file` `anchored_write_target` re-verify
   (`write_file.rs:175-180`) closes the symlink-swap-between-check-and-
   rename race (WO 47.34). Good.

6. **`read_file` streaming + early-stop.** WO 47.33 / 48.33: the
   `BufReader::read_until` loop retains only the `[offset, offset+limit)`
   window in memory, stops scanning once the window fills (for
   `offset > 0`), and discloses the unknown tail as `"N+"` in the
   header. The `whole` buffer is cleared the moment the file outgrows
   `limit` lines (`:128-129`). This is O(limit) memory for partial
   reads and byte-exact for whole-file reads. Well-engineered.

7. **`task` tool `max_turns` clamp (WO 48.34).** The model-supplied
   `max_turns` is floored at 1 then clamped to `max_turns_ceiling`
   (`task_tool.rs:191-199`), and the agent-frontmatter `maxTurns`
   override is clamped to the same ceiling (`:204-212`). The test
   `task_max_turns_clamped_to_configured_ceiling` (`:627-667`) pins
   `u64::MAX → 32`. Solid.

8. **Cascade cancel propagation (WO 38.4).** `cascade_parent_cancel`
   (`task/mod.rs:56-70`) watches the parent token and translates it
   onto the nested handle's flag+token. The test
   `outer_cancel_stops_nested_background_task`
   (`task_tool.rs:987-1096`) pins the full cascade. The `done` Notify
   retires the watcher when the nested task finishes normally, so
   watchers don't pile up. Correct.

## Escalation

None. The HIGH finding (H1) is a real bypass but requires the model to
construct a self-referential workflow template, which is a
jailbreak-shaped prompt rather than an accidental regression. The
MEDIUM findings are race-shape and heuristic-interaction issues that
deserve fixes but are not exploitable in normal use.
