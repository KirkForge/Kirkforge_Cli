# WO 50.06 — Session Persistence Deep-Read Audit

## Status: Open (audit findings)

## Scope

Deep-read audit of the session persistence and infrastructure layer of
KirkForge-Cli. Every line of the assigned segment was read. Findings are
organized by severity: bugs, risks, and observations.

---

## 1. Conversation Log Corruption Recovery

**Files:** `src/session/conversation.rs` (1396 lines)

### 1a. Crash-safe append — SOUND

The append path (`append` / `append_async`) serializes the message, writes
the line + `\n`, calls `sync_all()`, and only then updates the in-memory
vector. A crash during the write loses at most the message being appended
(lines 138-163, 167-198). This is correct.

### 1b. Torn-final-line healing — SOUND, well-tested

`open()` detects corrupt lines via `load_messages()`, which returns
`(messages, corrupt)`. When `corrupt=true` AND there are valid messages,
the log is **healed** — atomically rewritten from the valid messages
(lines 56-73). This prevents the O_APPEND fusion bug where a torn tail
fragment would merge with the next append and corrupt both. Test
`test_open_heals_torn_final_line_on_disk` (lines 786-834) pins this,
including a regression guard that a subsequent append parses cleanly.

### 1c. Checkpoint restore — SOUND with a minor edge case

When the log is fully corrupt (no valid messages), `restore_from_checkpoint`
is called (lines 83-96). It tries checkpoints newest-first, falling back to
older ones if the latest is also corrupt (lines 344-379). The restore writes
the checkpoint contents atomically to the main log path via
`write_atomic_static` (line 388-399), which uses `atomic_write` (O_EXCL +
random tmp + rename, WO 46.24).

**Minor edge case (LOW):** If a checkpoint is restored, the in-memory
`messages_since_checkpoint` is set to 0 (line 110), but the checkpoint
interval is also set to 0 at construction (line 80, 109). This means
**periodic checkpointing is disabled after restore** — only the executor's
post-batch checkpoint will fire. This is safe (the executor checkpoints after
each tool batch), but a long-running session that never triggers a tool batch
would have no periodic checkpoints. In practice this is a non-issue because
the executor always checkpoints after tool batches, but the `open()` path
does not carry forward the caller's desired `checkpoint_interval` — the
caller must re-apply `with_checkpoint_interval()` after `open()`.

### 1d. UTF-8 tolerance — SOUND (WO 43.21)

`load_messages` uses `read_until(b'\n')` + `String::from_utf8_lossy`, but
critically it checks `std::str::from_utf8(&raw).is_err()` **before** the
lossy conversion (line 495) and skips the line if the strict parse fails.
This means invalid UTF-8 bytes are treated as corrupt (skipped), not silently
mutated into U+FFFD. Test at lines 1369-1395 pins this.

### 1e. Async append race — LOW RISK

`append_async` (lines 167-198) moves the path clone into `spawn_blocking`
but updates `self.messages.push(msg)` **after** the blocking task completes.
If two `append_async` calls are concurrent on the same `ConversationLog`,
the in-memory vector could receive messages out of order relative to disk
(the disk writes are serialized by the OS via O_APPEND, but the in-memory
push happens in completion order, not submission order). In practice, the
executor is single-threaded for conversation appends, so this is not
triggered. The sync `append` is order-preserving by construction.

## 2. Session Fork

**Files:** `src/session/session_fork.rs` (432 lines)

### 2a. Fork file tracking — SOUND

`ForkManager` loads existing forks from `<sessions>/forks/<id>/fork.json`
on construction (lines 56-89), so forks survive restarts. Unparseable
metadata is skipped with a warning (lines 70-76). Fork IDs are chosen by
scanning for the next non-colliding directory (lines 104-109), preventing
reuse of an existing fork's ID or corruption of its log.

### 2b. Fork referencing a deleted parent — LOW RISK, handled in tree

A `Fork` struct stores `parent_session: String` (line 27), which is the
session ID at creation time. If the parent session is later deleted
(`delete_session`), the fork's `fork.json` still references it. The fork's
conversation log is self-contained (copied at creation time, lines 130-132),
so opening the fork still works. `build_fork_tree` in `session_index.rs`
(lines 673-689) handles orphans by listing them as root nodes — they are
not silently dropped. **However**, there is no active cleanup of orphaned
forks; they persist indefinitely unless the user manually deletes them.

### 2c. Fork conversation log — uses ConversationLog::open, inherits healing

`create_fork` opens a fresh `ConversationLog` at `fork_path` (line 120) and
appends messages one by one (lines 130-132). Each append calls `sync_all`,
so a crash during fork creation leaves a partial fork log. The fork's
`fork.json` is written **after** all messages are appended (line 147), so
a crash before the metadata write leaves a fork directory with a
conversation log but no `fork.json` — `load_existing_forks` will skip it
(line 63-64 checks `meta_path.is_file()`). This is safe: the stale directory
is skipped on next load, and `create_fork` removes any existing
`conversation.ndjson` before writing (lines 117-119).

## 3. Config Merge & Env Overrides

**Files:** `src/session/config/mod.rs` (1697 lines), `merge.rs` (671 lines),
`env_overrides.rs` (260 lines), `diff.rs` (424 lines)

### 3a. Env overrides applied in production — SOUND (WO 43.32 fix pinned)

`load_config()` (lines 108-139) calls `apply_env_overrides(&mut cfg)` at
line 136 — this is the **production** path, not gated behind `#[cfg(test)]`.
The test `load_config_honors_env_overrides` (lines 498-528) explicitly pins
this: "Before the fix, `apply_env_overrides` was `#[cfg(test)]`-only and
`load_config` never called it." This was a real bug that was fixed and
pinned.

### 3b. Generic overlay — SOUND, well-designed (WO 47.2)

Both the config file and env var layers funnel through
`merge_toml_into_config` (lines 28-63 in merge.rs). The overlay serializes
the current Config to TOML, inserts each key one at a time via `insert_path`
(which merges sub-tables rather than replacing them), and decodes back via
serde. A key with a bad value type is silently skipped — the per-key trial
decode (lines 49-57) means one wrong line in config.toml cannot wipe other
customizations. Test `bad_typed_key_does_not_wipe_sibling_keys` pins this.

### 3c. Alias precedence — SOUND

`KF_CODE_COMPACTION_USE_HEURISTIC` wins over the legacy
`KF_CODE_COMPACTION_USE_LLM` regardless of env iteration order (env_overrides.rs
lines 112-118 re-insert it last). The file-layer alias is handled in
`merge_toml_into_config` (merge.rs lines 31-33): if the primary is present,
the alias is removed before the overlay loop.

### 3d. memory_auto_populate flatten collision — handled explicitly

`memory_auto_populate` is declared by both `ToolConfig` and `DisplayConfig`.
The custom `SessionConfig` Deserialize hides it from one side, and
serialization writes the other's copy (last writer wins). The merge layer
handles this by removing the key from the overlay table and applying it to
both fields directly (merge.rs lines 40-42, 58-61). This prevents the two
fields from drifting.

### 3e. Path normalization — SOUND

`normalize()` (merge.rs lines 100-157) expands tildes, clears empty paths to
None (for Option-path fields), and clamps numeric knobs. `sandbox_dir` and
`cache_dir` keep `Some("")` as the documented unsandboxed escape hatch.
Clamps prevent zero/negative values that would cause divide-by-zero or
infinite loops in consumers.

### 3f. Potential issue: `apply_env_overrides` iterates ALL env vars

`apply_env_overrides` (env_overrides.rs line 92) iterates `std::env::vars_os()`
— every environment variable in the process. For each, it checks `config_key()`
which strips `KF_CODE_` prefix. This is O(N_env_vars) per config load. In a
CI environment with hundreds of env vars this is still fast (the check is a
prefix match), but it means any env var starting with `KF_CODE_` will be
attempted as a config override. If a user has `KF_CODE_SOME_INTERNAL_VAR` set,
it will be silently coerced and applied to the config if the key matches an
existing field. This is by design (WO 47.2 derives keys automatically), but
it means adding a new Config field makes it automatically env-overridable
without updating the KEY_MAP.

## 4. Hook stdin-JSON Contract (WO 39.4)

**Files:** `src/session/hooks.rs` (2333 lines)

### 4a. JSON payload piping — SOUND

The `HookPayload` struct (lines 100-111) serializes to a single JSON object
matching Claude Code's hook contract: `hook_event_name`, `session_id`,
`tool_name`, `tool_input`, `tool_response`. `skip_serializing_if` keeps the
wire shape minimal — non-tool events emit only `hook_event_name` +
`session_id`; pre-tool events omit `tool_response`.

The payload is written to the hook subprocess's STDIN in `run_hook_script`
(lines 960-966): `stdin.write_all(stdin_json.as_bytes()).await` followed by
`stdin.shutdown().await`. The stdin handle is taken from the child before
the write, so the child sees EOF after the write completes. The comment at
line 956 correctly notes the payload is small (well under the OS pipe
buffer), so the write cannot deadlock.

### 4b. Event-name mappings — SOUND, bijective

`kf_to_claude_event` (lines 155-165) and `claude_to_kf_event` (lines 172-182)
are exact inverses for all six supported events:
- `pre-tool` ↔ `PreToolUse`
- `post-tool` ↔ `PostToolUse`
- `pre-turn` ↔ `UserPromptSubmit`
- `session-start` ↔ `SessionStart`
- `post-turn` ↔ `Stop`
- `pre-compact` ↔ `PreCompact`

Events with no Claude equivalent (`post-tool-bash`, `post-compact`) keep
their kf-code name. Claude events with no kf-code equivalent (`SessionEnd`,
`Notification`, `SubagentStop`) return `None` and are skipped during
settings.json parsing. Test `test_claude_event_mapping_round_trip` (lines
2137-2155) pins the bijection.

### 4c. Two paths for stdin JSON — potential inconsistency, LOW RISK

There are two paths that build the stdin JSON:

1. **`run_decision_inner`** (line 720): builds `stdin_json` from
   `HookPayload::from_ctx(ctx)` — this uses the full `HookContext` which
   includes `tool_result` for post-tool events.

2. **`spawn_hook_script`** (line 575, used by fire-and-forget `run`):
   builds `stdin_json` via `stdin_json_from_env_vars(event_name, &env_vars)`
   — this reconstructs a `HookContext` from env vars via
   `env_vars_to_ctx`, then calls `HookPayload::from_ctx`.

Both paths converge on `HookPayload::from_ctx`, so the JSON shape is
consistent. The fire-and-forget path relies on the caller having set the
`KF_*` env vars correctly via `ctx_to_env_vars` (line 671 in
`run_with_context`). This is correct — `run_with_context` calls `run` with
the env vars derived from the context, and `run` calls `spawn_hook_script`
which reconstructs the context from those same env vars.

**Observation:** The reconstruction path (`env_vars_to_ctx` →
`HookPayload::from_ctx`) loses the `compact_stats` field — `env_vars_to_ctx`
(lines 855-870) does not parse `KF_COMPACT_STATS` or similar. This means
compaction hooks fired via the fire-and-forget path do not receive compact
stats in the JSON payload. However, compaction hooks use
`run_with_context` which calls `run` (fire-and-forget), so this is a real
gap: **compact stats are not available in the STDIN JSON payload for
shell hooks**. The in-process post-hooks (Rust) do receive `compact_stats`
via the `HookContext` directly. This is a minor inconsistency — shell
compaction hooks get the stats via `KF_TOOL_ARGS_JSON` (which carries the
JSON object with the stats fields), but not in the structured
`tool_input`/`tool_response` fields of the Claude payload.

### 4d. Claude settings.json reader — SOUND

`load_claude_hooks_config` (lines 222-250) reads a JSON file, extracts the
`hooks` key, and calls `parse_claude_hooks_obj` (lines 256-303). The parser
flattens Claude's nested `hooks[EventName][]` → `{matcher, hooks[]}` →
`{type:"command", command:"..."}` structure into one `ClaudeHookEntry` per
command. The matcher tool name is translated via `alias_for` (line 292), so
`PreToolUse` with `matcher:"Bash"` becomes `pre-tool-bash`. Non-`command`
hook types are silently skipped (line 280). Unknown Claude event names are
skipped (line 263). Test `test_parse_claude_hooks_translates_events_and_matchers`
(lines 2172-2248) pins all translations.

### 4e. Trust gate — SOUND

`HookRunner::load_claude_hooks_config` (lines 476-508) refuses to load
workspace hooks when `trust_workspace` is false (lines 477-484), mirroring
`AgentRegistry::load_from_dir`. This prevents a dropped `.claude/hooks.json`
from running arbitrary commands without operator opt-in.

## 5. MCP Client

**Files:** `src/session/mcp_client/mod.rs` (2311 lines), `manager.rs` (352
lines), `http.rs` (1045 lines), `error.rs` (110 lines), `spawn.rs` (48 lines)

### 5a. Protocol version — correct, pinned to "2024-11-05"

The `initialize` request (lines 110-122) sends `"protocolVersion": "2024-11-05"`.
This is the MCP spec version that introduced the streamable-HTTP transport.
The HTTP transport module header (http.rs line 4) references "MCP 2024-11-05
and later drafts."

**Observation:** The MCP protocol has evolved past 2024-11-05 (the spec
now has `2025-06-18` and later versions with additional features). The
client does not negotiate — it sends a fixed version. A server that
requires a newer version would fail the handshake. This is safe (the client
only uses features from 2024-11-05) but limits compatibility with
newer-only servers.

### 5b. Timeouts — comprehensive, multi-layered

- **Startup timeout:** 10 seconds for the `initialize` handshake (line 98,
  `STARTUP_TIMEOUT`). If the server doesn't respond, the client is dropped.
- **Request timeout:** 30 seconds per JSON-RPC round-trip (line 158,
  `REQUEST_TIMEOUT`). Both the write and the response wait are bounded.
- **Reader idle timeout:** 10 seconds (production) / 300ms (test) (lines
  168-173). **Armed only while `pending` is non-empty** (line 850) — an
  idle-but-healthy stdio server stays connected, but a hung in-flight
  request is bounded. This is the WO 43.23 fix.
- **Outer tool timeout:** `McpToolWrapper::run` has a 60-second outer
  timeout (mcp_tools.rs line 104) in case the manager's reconnect path
  gets stuck.
- **HTTP client timeout:** 60-second reqwest client builder (http.rs line 63).
- **Sampling approval timeout:** 300 seconds (line 1024) — bounded so a
  hung approval handler doesn't block the MCP reader.

All timeout branches properly remove the pending-map entry to prevent
leaks (WO 43.37 fix, lines 1229, 1246, 1251).

### 5c. Server crash handling — SOUND

When the reader task exits (EOF, read error, idle timeout with request in
flight, oversized line), it calls `fail_all_pending` (line 900) which
drains the pending map and sends `McpError::Disconnected` to every
in-flight waiter. The `alive` flag is set to false (line 901).

The manager's `call_tool` (manager.rs lines 171-227) checks `is_alive()`
first (line 204). If dead, it takes a write lock and attempts a reconnect
(line 216). The write lock prevents concurrent callers from racing to
reconnect. If reconnect fails, the caller gets `ToolError::Internal`.

**Drop path (StdioMcpClient):** signals background tasks to stop, takes
the child handle, calls `kill_process_group`, and spawns a best-effort
reap task (lines 1347-1374). If no Tokio runtime is available, the child
is killed but not reaped (best-effort).

**Drop path (McpHttpTransport):** signals shutdown, which causes the SSE
reader to call `fail_all_pending` at its shutdown branches (http.rs line
297-300, WO 46.22 fix).

### 5d. Reconnect loses sampling context — documented limitation

`set_sampling` (manager.rs lines 240-247) installs the sampling context on
currently-connected clients only. A client that reconnects after a crash
loses the context until the session reinstalls it. The `ponytail:` comment
at line 237 documents this: "per-session sampling is best-effort, matching
the reconnect path's simplicity." This is a known limitation, not a bug.

### 5e. Stdin pipe write — no deadlock risk

The MCP client's `send_request` writes the request line to stdin inside
a `tokio::time::timeout(REQUEST_TIMEOUT, ...)` (lines 1226-1237). The
stdin mutex is held during the write, which could block if the server is
not reading. However, the write is a single line (well under the pipe
buffer), and the timeout bounds the wait. If the write times out, the
pending-map entry is removed (line 1229) and `McpError::Timeout` is
returned.

### 5f. MCP env hardening — SOUND

The MCP server subprocess is spawned with `env_clear()` (line 425) followed
by `curated_env` (line 426), which forwards only PATH/HOME/USER/locale plus
the server's explicit `env_vars`. PATH is sanitized via
`bash_runner::sanitized_path` (line 431) to prevent shadowing. This mirrors
the kf-plugin-host curated_env pattern and prevents API key exfiltration
via `printenv`.

### 5g. HTTP transport SSE reader — robust

The SSE reader task (http.rs `run_sse_reader`) handles:
- Session ID extraction from the first SSE event
- `Last-Event-ID` header for reconnection
- Bearer token auth on GET and POST
- Max SSE data length cap (1MB, line 30)
- Shutdown signal via oneshot
- POST-level errors surfaced immediately by removing the pending waiter

## 6. Process Group Management (PDEATHSIG)

**Files:** `src/session/process_group.rs` (360 lines)

### 6a. PDEATHSIG on Linux — SOUND, tested

`setup_process_group` (lines 33-53) calls `setpgid(0, 0)` and
`prctl(PR_SET_PDEATHSIG, SIGKILL)` in the pre-exec hook. This means the
child dies when the parent dies — even on `panic = "abort"` or SIGKILL,
where no Drop handlers run. Test `child_dies_when_parent_aborts` (lines
296-342) pins this by forking a helper that spawns a sleep child and then
aborts; the test polls `kill(pid, 0)` until ESRCH.

### 6b. Windows Job Object — SOUND

On Windows, `assign_child_to_job` creates a Job Object with
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and assigns the child to it (lines
200-215). Dropping the `JobGuard` closes the handle, killing the entire
process tree. This is the WO 44.44 fix for the WO 43.26 regression where
grandchildren survived and kept pipes open.

### 6c. Non-Unix fallback — no-op

On non-Unix, `setup_process_group` and `kill_process_group` are no-ops
(lines 56, 75-79). `kill_process_group` falls back to `start_kill()`. This
means on non-Unix/non-Windows targets, grandchildren can survive — but
the only such target in practice is Windows, which has the Job Object path.

## 7. Session Index

**Files:** `src/session/session_index.rs` (1309 lines)

### 7a. Index format — SOUND, atomic writes

The session index is NDJSON at `<data_dir>/sessions/.index.ndjson` (line 59).
Each line is a serialized `SessionEntry`. The index is written atomically via
`atomic_write` (lines 179-201, WO 46.24 O_EXCL + random tmp). If the index is
missing or corrupt, `load_or_refresh` falls back to a full directory scan
(lines 72-83, 207-220).

### 7b. Search — reads session files, LOW risk

`session_content_matches` (lines 240-276) reads the entire session file into
memory and does a substring match on each line. For a multi-GB session log,
this could be slow. The fast path (raw substring on the JSON line) covers
most cases, but the fallback parse per line adds overhead. This is
acceptable for the expected session count (tens to low hundreds), but a
user with hundreds of large sessions would experience slow search.

### 7c. Fork tree — handles cycles, orphans

`build_fork_tree` (lines 550-692) builds a recursive tree from session
entries and fork metadata. It handles:
- **Cycles:** a `visited` HashSet prevents infinite recursion (lines 622, 641-643).
- **Orphans:** forks whose parent is not in the session set are listed as
  roots (lines 673-689), never silently dropped.
- **Parse errors:** unparseable fork.json is skipped with a warning (lines 576-582).

## 8. Carryover Profile

**Files:** `src/session/carryover.rs` (859 lines)

### 8a. Persistence — SOUND, atomic

`save_carryover` (lines 245-281) prunes to top-5 tools, top-3 paths, top-5
warnings, then writes via `atomic_write` (WO 46.24). Corrupt or missing
file falls back to `Default` (lines 214-231).

### 8b. Path condensation — LOW risk

`condense_path` (lines 186-202) keeps only the last 2 path components for
paths > 40 chars. This is lossy by design (the carryover is a hint, not a
log), but a path like `/home/user/project/src/deep/nested/file.rs` becomes
`nested/file.rs`, which could be ambiguous across projects. Acceptable for
a ~55-token carryover block.

## 9. Memory Store

**Files:** `src/session/memory/mod.rs` (1398 lines), `extract.rs` (16197 bytes)

### 9a. Dedup gate — SOUND, lexical only

`upsert` (lines 210-257) compares new fact tokens against existing facts
via Jaccard similarity (default threshold 0.85). Near-duplicates are
skipped. The `ponytail:` comment at line 206 correctly notes the ceiling:
lexical Jaccard misses synonym-only paraphrases. This is a known limitation,
not a bug.

### 9b. Eviction — O(n) scan, fine for 200 entries

When `facts.len() > max_facts` (default 200), the first alphabetically is
evicted (lines 249-254). This is O(n) per upsert — fine for 200 entries.
The `ponytail:` comment at line 198 documents this.

### 9c. mtime cache — SOUND (WO 38.9 item 4)

`all_cached` (lines 117-128) compares the directory's mtime against a
cached value. If unchanged, returns cached facts without re-reading. This
is correct for the expected use case (facts change infrequently). A
file-level mtime check would be more precise but unnecessary at this scale.

## 10. Other Findings

### 10a. Git sanitation — SOUND

`src/session/git_sanitation.rs` (1179 lines) scans for large files, secrets,
merge-conflict markers, and untracked debris. The `SCAN_CAP_BYTES` is 10MB
(line 25), documented as a ceiling. Secret patterns are specific enough to
avoid false positives (line 31-45). Content scanning is case-insensitive.

### 10b. Error recovery — SOUND

`src/session/error_recovery.rs` (884 lines) classifies Rust compile errors
into structured `ErrorHint` variants (borrow conflict, missing import, type
mismatch, missing method). Regexes are compiled once via `OnceLock` (lines
19-23). The hints are appended to the error message as "Hint:" prefixed
text.

### 10c. Adapter swap — SOUND

`src/session/adapter_swap.rs` (423 lines) handles mid-session model
switching. The `maybe_swap` method classifies the user input and swaps the
adapter if the suggested model differs. The old adapter is dropped
(`std::mem::replace`, line 107), releasing in-flight connections. The
`force_swap` method bypasses routing for `/model <name>`.

### 10d. Skills loader — SOUND

`src/session/skills.rs` (1452 lines) loads SKILL.md files with YAML
frontmatter. Plugin skills are loaded via `PluginRegistry`. Folded plugins
whose cargo feature is ON get their skills registered directly (lines
173-187). The `tokenize_args` method (lines 70-108) is a simple POSIX-like
shell tokenizer with quote and escape support.

### 10e. Agents loader — SOUND, with parsed-but-not-wired fields

`src/session/agents.rs` (929 lines) loads `.claude/agents/*.md` files.
Several frontmatter fields are parsed but not wired: `hooks`, `mcp_servers`,
`memory` (lines 66-79). Each has a `ponytail:` comment documenting the
upgrade path. This is intentional deferral, not a bug.

### 10f. Parallel orchestrator — SOUND

`src/session/parallel_orchestrator.rs` (1711 lines) runs the
scout→coder→reviewer pipeline through kf-orchestrator's `ModelClient` seam.
The pipeline-level cancel flag (line 194) closes the window where a cancel
during scout had no way to stop coder/reviewer from starting (WO 38.4).

### 10g. Task spawner — SOUND, unique temp dirs

`src/session/task_spawner.rs` (1421 lines) uses a process-global task
counter for temp dir uniqueness (lines 99-105, WO 38.4), not a clock —
preventing collisions when two `task` calls land in the same millisecond.
`TempDirGuard` (lines 84-90) ensures cleanup on all error paths and panics.

### 10h. ExecutorAdapter — SOUND

`src/session/executor_adapter.rs` (338 lines) implements `ModelClient` by
running each `TaskBrief` as an isolated subagent session. The
`ORCHESTRATOR_MAX_TURNS` constant (line 25, = 8) is a ceiling, not a fixed
cost. The `Emission` correctly sums token counts across turns and echoes
the delegation mode in `format`.

### 10i. Sandbox posture — SOUND

`src/session/sandbox_posture.rs` (182 lines) derives the active sandbox
layers from config + compile-time cfg. The checklist correctly mirrors the
bash-runner gates (Landlock on Linux, seccomp as opt-in feature, network
namespace requires `harden && no_network`).

### 10j. Router — SOUND, simple

`src/session/router.rs` (432 lines) classifies user messages into
simple/medium/complex tiers using keyword heuristics. The `resolve_tier_model`
function (lines 171-187) returns `None` when neither the routing map nor
default model can supply a model, so callers can no-op instead of building
an adapter for an empty name.

### 10k. Plugin tools — SOUND

`src/session/plugin_tools/` (5 files) wraps plugin tools in `Tool` trait
implementations. The two-path dispatch (compiled-in vs external, ADR-050) is
cleanly separated. The `approval` module handles plugin consent. The
`wrapper` module invokes plugin scripts with sandboxed cwd, curated env,
timeout, and process-group cleanup.
