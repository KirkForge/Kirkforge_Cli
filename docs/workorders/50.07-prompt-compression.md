## 1. The folded MiddleStrategy (WO 47.6)

**Files:** `compaction.rs:85-352`, `microcompaction.rs:46-119`

### 1a. Fold correctness — SOUND for StubPerSlot

`compact_to_budget` now delegates to `process_middle` with
`MiddleStrategy::StubPerSlot` (compaction.rs:147-160). The fold's stated
contract (compaction.rs:162-171) is that `StubPerSlot` reproduces the old
deterministic per-slot stubbing byte-for-byte. Reading both paths:

- The shared `stub_middle` (compaction.rs:282-316) stubs Tool results via
  the shared `stub_tool_result` (preserving `tool_name` + `tool_call_id`),
  condenses Assistant turns (preserving `tool_calls`), keeps User/System
  verbatim — identical to the inline pre-fold behavior pinned by the
  `slice_selects_correct_messages_for_compaction` and
  `slice_keeps_tool_call_tool_result_pairs_intact` tests
  (compaction.rs:930-981, 1033-1112).
- The anchor/middle/tail split is shared via `anchor_len` and
  `working_set_start = messages.len() - tail_size`
  (compaction.rs:197-234). Tail sizing for `StubPerSlot` still goes through
  `budget_tail_size` (compaction.rs:253-277), preserving the over-budget
  tail expansion.

The `compact_to_budget_with_none_matches_compact` test
(compaction.rs:746-758) pins that `compact_to_budget(_, _, None)` is
byte-identical to the test-only `compact` wrapper. **No behavioral drift
detected on the StubPerSlot path.**

### 1b. Fold correctness — SOUND for CollapseToSummary, with one wording divergence (BY DESIGN)

`maybe_microcompact` delegates to `process_middle` with
`CollapseToSummary` and supplies a `collapse_fn` closure that produces the
full summary-message content (microcompaction.rs:74-105). The closure wraps
the heuristic/LLM fork's output in `[Context summary — {N} earlier messages
compressed]\n{summary}` (microcompaction.rs:103).

The `collapse_middle` arm (compaction.rs:324-352) takes the closure's
return verbatim and emits it as a single `Role::System` message. This
matches the pre-fold microcompaction shape. The `ProcessMiddleResult`
reports `summarised_messages = middle.len()` (compaction.rs:331) — note
this field is `#[allow(dead_code)]` (compaction.rs:361-362) and is only
surfaced through the `MicrocompactResult`, which does not expose it. **No
loss of information.**

**Wording divergence (BY DESIGN, not a bug):** the executor's LLM arm
(loop_.rs:378-384) supplies its own `collapse_fn` that uses
`"messages compressed"` instead of microcompaction's `"earlier messages
compressed"`. The `collapse_middle` doc comment (compaction.rs:318-323)
explicitly documents this divergence: "The LLM arm (loop_.rs) uses
'messages compressed'; the heuristic arm (maybe_microcompact) uses 'earlier
messages compressed'." This is intentional and documented — **not a
regression**. But it means the `[Context summary — …]` prefix wording is
caller-dependent, which could surprise someone grepping logs who assumes
one canonical phrase.

### 1c. Edge case — `working_set_start <= anchor` short-circuit (CORRECT)

`process_middle` for `CollapseToSummary` has an explicit guard
(compaction.rs:220-222): if `working_set_start <= anchor`, it returns a
no-op. This reproduces `maybe_microcompact`'s pre-fold `tail_start <=
anchor` early return (microcompaction.rs:65-67). The
`no_compact_when_history_too_short` test (microcompaction.rs:389-391) and
`preserves_anchor_system` (microcompaction.rs:420-433) pin this. **No
drift.**

### 1d. Edge case — StubPerSlot noop boundary is `keep_tail_min`, CollapseToSummary is `keep_tail_min + 1`

The noop boundary differs between the two strategies
(compaction.rs:189-195):

- `CollapseToSummary`: noop when `messages.len() <= keep_tail_min + 1`
  (mirrors microcompaction's old `messages.len() <= keep_tail + 1`).
- `StubPerSlot`: noop when `messages.len() <= keep_tail_min` (mirrors
  compact_to_budget's old `messages.len() <= preserve_recent`).

This is **correct and intentional** — the two paths historically had
different noop thresholds because CollapseToSummary needs at least one
message in the middle to summarize, while StubPerSlot operates per-slot and
only needs the middle to be non-empty (i.e. len > keep_tail). The fold
preserves both. Pinned by `short_input_below_tail_is_no_op`
(compaction.rs:504-513) and `no_compact_when_history_too_short`
(microcompaction.rs:389-391). **No drift.**

### 1e. Tail sizing divergence — BY DESIGN

`CollapseToSummary` uses a flat `keep_tail_min` tail (compaction.rs:203-207)
— it does NOT grow the tail from a budget. `StubPerSlot` uses
`budget_tail_size`. This is the documented contract
(compaction.rs:199-207) and matches the pre-fold behavior: microcompaction
never had budget-aware tail growth, compact_to_budget always did. **No
drift.**

### 1f. RISK (LOW) — `budget_tail_size` underflow guard

In `budget_tail_size` (compaction.rs:253-277), the while-loop condition is
`tail_size < messages.len() - anchor` (compaction.rs:265). If `anchor >
messages.len()`, this underflows to a huge usize and the loop runs. In
practice `anchor` is 0 or 1 and `messages.len()` is always ≥ 1 when this is
called (the noop guard at compaction.rs:193 ensures `messages.len() >
keep_tail_min ≥ 1`), so `messages.len() - anchor` cannot underflow. **Not
reachable**, but the subtraction is unguarded. A future caller that passes
a malformed message list (e.g. a slice where `anchor_len` incorrectly
returns 1 for an empty list) would panic. The `anchor_len` implementation
(compaction.rs:77-83) is safe (returns 0 for empty), so this is not
exploitable today. **LOW risk — defensive `saturating_sub` would be
cleaner.**

## 2. The escalation ladder in `build_messages_with_compaction`

**File:** `mod.rs:526-693`

### 2a. Ladder structure — SOUND, all four rungs present

The escalation ladder (mod.rs:646-693) is:

1. **Rung 1 — CollapseToSummary** (microcompaction): mod.rs:664-676. Calls
   `maybe_microcompact`; if `result.tokens_after <= budget`, returns
   immediately. Otherwise stores `adjusted = result.messages` and falls
   through.
2. **Rung 2 — Minify**: mod.rs:678-683. Calls `minify_old_messages`; if
   the adjusted list is now under budget, returns.
3. **Rung 3 — StubPerSlot** (stub old tool results): mod.rs:685-689. Calls
   `stub_old_tool_results`; if under budget, returns.
4. **Rung 4 — Truncate**: mod.rs:692. `truncate_to_budget` always
   succeeds (hard cut).

The ladder is **correctly ordered cheapest-to-most-aggressive** and each
rung works on the output of the previous one (mod.rs:662: `adjusted =
messages.clone()` is the seed; Rung 1 may replace it, Rungs 2-3 mutate it
in place). Rung 4 is unconditional. **The fall-through to truncate is
correct.**

### 2b. RISK (MEDIUM) — Rung 2 reads indices from the ORIGINAL `messages`, writes into `adjusted`

`minify_old_messages(messages, &mut adjusted)` (mod.rs:875-908) iterates
over the ORIGINAL `messages` slice but writes into `adjusted`, which may be
shorter (Rung 1 collapsed the middle). The `i < adjusted.len()` guard
(mod.rs:900) prevents the index-out-of-bounds panic that WO 43.29 fixed.
The test `test_minify_old_messages_no_panic_when_adjusted_shorter_than_messages`
(mod.rs:1284-1315) pins this with `budget=0` and 20 middle messages.

**However**, there is a subtle correctness issue: when `adjusted` is
shorter than `messages`, the minify step **silently skips** minification of
high-index messages (those beyond `adjusted.len()`). This is safe (no
panic, no corruption), but it means Rung 2 can be a **partial no-op** when
Rung 1 collapsed the middle — the very messages that Rung 1 collapsed into
a summary are the ones Rung 2 tries to minify, and the index guard skips
them. In practice this is fine because Rung 1's summary message is already
compact, but the code's intent (minify old non-tool messages) is only
partially achieved after a collapse. **Not a bug, but worth a comment
clarifying the intent.** The existing comment at mod.rs:656-658 partially
explains this ("the `i < adjusted.len()` guard prevents indexing past the
shorter collapsed list").

### 2c. RISK (LOW) — Rung 2's `savings > 20` threshold can skip useful minification

`minify_old_messages` only writes the minified content if
`minified.len() < msg.content.len() && savings > 20` (mod.rs:898-904). The
hard 20-byte threshold means a message that minifies from 100 → 82 bytes
(18 bytes saved, 18% reduction) is **skipped**. For a conversation with
many small assistant messages, this leaves tokens on the table. The
threshold is a reasonable ponytail heuristic (avoid churn for negligible
savings), but it interacts with the budget check: if Rung 2 doesn't
minify enough messages, it falls through to Rung 3 (stub) which is more
aggressive. **Not a bug — the ladder catches it.**

### 2d. Rung 3 stubbing — SOUND, preserves last 2 tool results

`stub_old_tool_results` (mod.rs:910-929) collects all Tool-role message
indices, computes `preserve_from = tool_indices.len().saturating_sub(2)`,
and stubs everything before that. The stub check
`messages[i].content != compaction::TOOL_RESULT_STUB` (mod.rs:923) avoids
double-stubbing (idempotency). **Correct.**

### 2e. Rung 4 truncate — SOUND with a budget-based heuristic

`truncate_to_budget` (mod.rs:931-949) keeps `keep_count = (budget * 4) /
20` messages (i.e. budget/5 messages by the 4-tokens-per-message
heuristic). It always keeps `messages[0]` (the system/cache stem) and the
last `keep_count` messages. The `truncated.len() < 2` guard (mod.rs:945)
falls back to the full list if the budget is so small that only the system
message would survive — preventing an empty history. **Correct, and the
`test_truncate_to_budget_empty_context_no_panic` test pins the edge case.**

### 2f. OBSERVATION — Rung 1's `result.tokens_after <= budget` check uses the collapsed list

When Rung 1 produces a `MicrocompactResult`, the ladder checks
`result.tokens_after <= budget` (mod.rs:672) and returns if true. If false,
it sets `adjusted = result.messages` and falls through. But the budget
check at mod.rs:642 already failed (otherwise we wouldn't be here), and
Rung 1's summary might still be over budget. The fall-through to Rung 2
(minify) will try to minify the summary message itself — but the summary is
already a short `[Context summary — …]` string, so `synthetic_extension_for`
(mod.rs:961-991) will return `"txt"` (no code fence, no `fn `), and the
minifier returns it unchanged. Rung 3 (stub) will then stub any old tool
results in the collapsed list. This is correct but slightly wasteful —
Rung 2 is a guaranteed no-op on a collapsed list with no code blocks.
**Not a bug.**

## 3. Token estimation and cache invalidation

**Files:** `mod.rs:24-79`, `compaction.rs:121-128`, `conversation.rs:138-169`

### 3a. Two token-counting paths — SOUND, with a documented fallback

`count_tokens` (mod.rs:24-33) uses `kf_budget_core::estimate_tokens`
(cl100k_base BPE) when the `budget` feature is on, and
`fallback_estimate_tokens` (bytes/4 + CJK/Hangul per-char) when it's off
(ADR-0017 minimal builds). The fallback is documented as ±20% on
mixed-script text (mod.rs:39-41) with CJK extension-B+ (4-byte) chars
counted via bytes only. Tests at mod.rs:2184-2224 pin CJK, Hangul, and jamo
counting. **Correct for the minimal-build path.**

### 3b. `estimate_message_tokens` cache — SOUND, all mutation sites invalidate

`estimate_message_tokens` (mod.rs:63-79) returns `m.token_count` directly
when `Some`, bypassing the BPE pass. The cache is populated in
`ConversationLog::append` and `append_async` (conversation.rs:140, 169)
when `token_count.is_none()`. The five sites that mutate `content` all set
`token_count = None`:

- `truncate_tool_results` (mod.rs:824) — truncates tool output content
- `dedup_adjacent_tool_results` (mod.rs:858) — replaces dup content
- `minify_old_messages` (mod.rs:902) — replaces with minified content
- `stub_tool_result` (compaction.rs:69) — replaces with stub marker
- `stub_middle` assistant condense (compaction.rs:306) — replaces prose

**All mutation sites are covered.** Tests
`dedup_adjacent_tool_results_clears_token_count_cache` and
`truncate_tool_results_clears_token_count_cache` (mod.rs:2226-2251) pin
this. **No stale-cache bug.**

### 3c. RISK (LOW) — `build_with_top_files` invalidates the stem cache but not token_count

`build_with_top_files` (mod.rs:463-501) appends file bodies to the system
message content and sets `self.cached_system = None` (mod.rs:497) to
invalidate the `SystemStemKey` cache. But it does NOT set
`msg.token_count = None` on the mutated message — the message was just
built by `build()` which returns a cached `Message` with `token_count:
None` (mod.rs:281), so this is fine in practice. **Not a bug, but the
invalidation is implicit — a future change that populates `token_count` on
the stem would create a stale cache here.**

### 3d. RISK (LOW) — `attach_pending_image` does not invalidate `token_count`

`attach_pending_image` (mod.rs:717-763) mutates `user_msg.content_parts`
but does not touch `user_msg.content` or `token_count`. Since
`estimate_message_tokens` only counts `content` + `thinking` +
`tool_calls` (mod.rs:67-78) and does NOT count `content_parts`, the cache
remains correct. **But** if a future change adds `content_parts` to the
token estimate, this mutation site would need invalidation. **Not a bug
today — latent risk if the estimate expands.**

### 3e. OBSERVATION — tool_calls token estimate uses `serde_json::to_string`

`estimate_message_tokens` (mod.rs:69-77) serializes `tool_calls` to JSON
and counts tokens on the serialized string. This overestimates slightly
(the provider doesn't receive the raw JSON — it receives the structured
tool_calls), but overestimation is the safe direction for budget checks.
**Correct for budget purposes; slightly pessimistic.**

`test_strip_test_blocks_block_comment_odd_quotes`
(lang.rs:1819-1937) pin all these edge cases. **No corruption detected.**

### 4c. RISK (LOW) — char-literal heuristic in `strip_test_blocks` misclassifies lifetimes

The char-literal detection (lang.rs:527-540) uses a heuristic:
- `'\x'` (backslash + char + quote) → 4 bytes
- `'x'` (char + quote) → 3 bytes
- otherwise → 1 byte (treated as a lifetime like `'a`)

This is correct for the common cases, but a malformed `'a'b'` (two char
literals with no operator) would consume `'a'` as 3 bytes and leave `b'`
which could confuse the brace counter if a `{` or `}` follows. In
practice, malformed Rust won't appear in production code being minified,
and the minifier is applied to conversation history (already-valid code)
or to files on disk (assumed valid). **LOW risk — the heuristic is
defensive, not a parser.**

### 4e. RISK (LOW) — Python triple-quote docstring detection uses `chars.clone().nth(1)`

The triple-quote detection (lang.rs:724, 749) uses
`chars.clone().nth(1) == Some(q)` to peek two chars ahead. This clones the
`Peekable` iterator each time, which is O(1) for `Chars` but slightly
wasteful. More importantly, the `is_docstring` check
(lang.rs:753-756) uses `out.rsplit('\n').next()` to get the current line —
this is O(line length) per triple-quote opener. For very long lines with
many triple-quoted strings, this could be slow. **Not a correctness bug —
performance only, and lines are typically short.**

### 4f. JS/TS minifier — SOUND with regex-vs-division heuristic

`minify_js_like` (lang.rs:857-958) tracks:
- Regex literals via `prev_opens_regex` (lang.rs:832-855) — a
  keyword/punctuator heuristic that decides whether `/` opens a regex or
  is division
- Char classes inside regexes (lang.rs:893-900)
- String/template literals with backticks (lang.rs:906-925)
- Block and line comments (lang.rs:927-936)

The `prev_opens_regex` heuristic (lang.rs:832-855) is documented as a
ponytail heuristic ("keyword-list, not a tokenizer" — lang.rs:829-831).
It handles: `(`, `,`, `;`, `=`, `!`, `+`, `-`, `*`, `%`, `<`, `>`, `&`,
`|`, `^`, `~`, `?`, `{`, `[` → regex; identifiers/numbers/`)`/`]`/`}`/
quotes → division; and expression keywords (`return`, `typeof`, etc.) →
regex. Tests `test_minify_js_keeps_regex_literal_with_double_slash`,
`test_minify_js_regex_round_trip_envelope`, and
`test_minify_js_division_and_comments_unaffected` (lang.rs:2215-2265) pin
both directions. **No corruption detected for the tested cases.**

### 4g. RISK (MEDIUM) — JS regex heuristic fails for `)` and `}` contexts

The `prev_opens_regex` heuristic (lang.rs:853) returns `false` for `)`,
`]`, `}`, and quotes — treating `/` after these as division. This is
correct for `if (x) /regex/` ... no wait, `if (x)` is followed by a
statement, and `/regex/` CAN follow `)`. The heuristic says `)` → division
context, which is WRONG for `if (x) /regex/.test(y)`. However, this is the
documented ceiling (lang.rs:829-831: "regexes after `)`/`}` or an
identifier (division-looking contexts) stay untracked; a `//` or quote
inside one of those can still corrupt"). The safe-direction trade-off is
that misclassifying a regex as division means the regex body gets
comment/string-processed, which CAN corrupt. But in practice, regexes
directly after `)` without a semicolon are rare in the code being minified
(conversation history). **MEDIUM risk — documented ceiling, but a real
regex-after-paren case would corrupt.**

### 4k. RISK (LOW) — Ruby `<<` heredoc detection vs left-shift

`ruby_scan_code` (lang.rs:1174-1203) opens a heredoc when it sees `<<`
not preceded by `<` and not followed by `<`. This correctly rejects `<<<`
but could misfire on `a << b` (left shift) — the code checks
`chars.get(i + 2) != Some(&'<')` but doesn't check if the `<<` is
preceded by an identifier (shift context). The comment at lang.rs:1098-1100
acknowledges this: "`x <<y` (shift with no space) and `%` after other
operators read as heredoc/literal openings — over-opening only skips
stripping, it never deletes literal content." The safe-direction trade-off
is that false heredoc openings make the minifier keep lines verbatim (no
harm), while false non-openings would strip comments from heredoc bodies
(harm). The code errs on the safe side. **LOW risk — documented ceiling.**

`fallback_c_like` (expand.rs:228-423) and `fallback_python`

- `::` scope resolution preserved (expand.rs:371-375, WO 48.26)
- Colons in ternaries/labels/map-keys not padded (expand.rs:388-398)
- Regex literal protection (expand.rs:243-267, WO 48.12)
- Backtick/template literal protection (expand.rs:275-291, WO 48.38)

Tests `fallback_c_like_colons_round_trip_byte_identical`,

### 4m. OBSERVATION — `fallback_c_like` colon handling for `case 1: x`

The colon arm (expand.rs:380-398) has a special case: if the next char is
a space, it eats the space and re-adds exactly one (expand.rs:380-384).
This normalizes `case 1:  x` (double space) to `case 1: x`. For
identifier-glued colons (`map[string]int`), the `is_alphanumeric` check
(expand.rs:394) prevents padding. **Correct, but the logic is subtle — a
comment would help future readers.**

### 4n. VFS cache — SOUND, nanos-granular mtime, safe-variant bypass

`minify_source_impl` (mod.rs:130-168) caches by `(path, mtime_nanos)`.
The nanos granularity (WO 48.48) prevents same-second stale cache hits.
The `preserve_tests` variant bypasses the cache entirely (mod.rs:150-155)
to avoid serving a test-stripped entry from the plain variant
(WO 48.8). Tests `test_safe_variant_bypasses_test_stripped_cache` and
`test_same_second_rewrite_serves_fresh_content` (mod.rs:476-540) pin both.
**Correct.**

### 4o. RISK (LOW) — VFS cache `unwrap_or_else` on poisoned lock

The cache access uses `VFS_CACHE.lock().unwrap_or_else(|e| e.into_inner())`
(mod.rs:151, 163) — poison recovery. This is the repo-wide convention
(AGENTS.md §7: "mutex poison recovery"), so it's consistent. But it means
a panicking thread could leave the cache in an inconsistent state. In
practice the cache only does `HashMap` ops which don't panic mid-operation,
so this is safe. **LOW risk — follows repo convention.**

## 5. The LLM summarizer fallback path

**Files:** `summarizer.rs:176-293`, `executor/loop_.rs:336-480`

### 5a. LLM failure handling — SOUND, all three failure modes return `fell_back=true`

`summarize_conversation` (summarizer.rs:176-293) handles:
- **No messages** (summarizer.rs:184-193): returns `fell_back=true`,
  `error=Some("No messages")`.
- **Too few turns** (summarizer.rs:195-207): returns `fell_back=true`,
  `error=Some("Not enough turns")`.
- **HTTP error** (summarizer.rs:284-291): returns `fell_back=true`,
  `error=Some("HTTP error: …")`.
- **JSON parse error** (summarizer.rs:275-282): returns `fell_back=true`,
  `error=Some("JSON parse error: …")`.
- **Empty summary** (summarizer.rs:226): filtered to `None`, falls
  through to `fell_back=true`.
- **Compression ratio below threshold** (summarizer.rs:244-257): returns
  `fell_back=true`, `error=Some("Compression ratio … below threshold")`.
- **Zero tokens_before** (summarizer.rs:230-241): returns `fell_back=true`,
  `error=Some("Cannot compute compression ratio")` — prevents divide-by-zero.

**All failure paths set `fell_back=true` and `summary=None`.** The
executor checks `if let Some(ref summary) = result.summary` (loop_.rs:370)
— when summary is None, it logs the error (loop_.rs:432-438) and falls
through to `compact_to_budget` (loop_.rs:444-480). **The fallback to
heuristic/truncation is correct.**

### 5b. RISK (MEDIUM) — LLM arm falls to `compact_to_budget` (StubPerSlot), NOT to the heuristic summarizer

When the LLM summarizer fails, the executor falls through to
`compact_to_budget` (loop_.rs:447), which uses `MiddleStrategy::StubPerSlot`
— the deterministic per-slot stubbing path, NOT the heuristic
`CollapseToSummary` path from microcompaction. This is a more aggressive
fallback (stub each tool result, condense each assistant turn) than the
heuristic summary (one `[Context summary]` message). The user asked:
"Does it fall back to heuristic?" — **Strictly, no.** It falls back to the
naive per-slot stubbing, which is the documented "last-resort deterministic
path" (compaction.rs:1-29). The heuristic summarizer is only used by
microcompaction (Rung 1 of `build_messages_with_compaction`), not by the
executor's `/compact` path. **This is by design but could be surprising —
the LLM arm and the heuristic arm are on different code paths.**

### 5c. RISK (LOW) — `min_compression_ratio` check uses `tokens_after` from the summary only

The compression ratio check (summarizer.rs:242-257) computes
`compression = 1.0 - (tokens_after / tokens_before)` where
`tokens_after` is the token count of the SUMMARY TEXT ALONE
(summarizer.rs:229), not of the full post-compaction message list. This
means the ratio doesn't account for the anchor + tail messages that will
accompany the summary. In practice this is fine — the summary is the only
variable-size part, and the anchor + tail are fixed. **Not a bug, but the
ratio is an approximation.**

### 5d. OBSERVATION — `summarize_conversation` does not honor a cancel token

The HTTP call (summarizer.rs:213-218) uses a 30-second timeout but no
cancel token. If the user hits Esc during summarization, the HTTP call
runs to completion (or timeout). The executor's cancel mechanism
(loop_.rs:508-520) drains stale Escs before the next turn, but the
in-flight summarization is not cancellable. **Not a bug — the 30s timeout
bounds it, and summarization is a synchronous pre-turn step.**

### 5e. OBSERVATION — `deterministic_compaction_summary` is misnamed

`deterministic_compaction_summary` (microcompaction.rs:217-333) is called
the "LLM-style" summary in the doc comment (microcompaction.rs:208-216),
but it's actually a deterministic heuristic — it never calls an LLM. The
name is `deterministic_compaction_summary` (correct), but the doc says
"structured LLM-style compaction summary" which could mislead. The
`use_llm` flag in `maybe_microcompact` (microcompaction.rs:79-99) decides
between this structured heuristic and the simpler
`heuristic_summary` (microcompaction.rs:127-176) — neither calls an LLM.
The actual LLM call is only in `summarize_conversation` (summarizer.rs),
invoked from the executor, not from microcompaction. **Naming is
confusing but not a bug.**

### 6c. RISK (LOW) — `StoreData::remove` is O(n) per eviction

The `order.retain(|k| k != key)` (store.rs:66) is O(n) per remove, and

### 6d. Content-type detection — SOUND, layered and conservative

### 6e. RISK (LOW) — `detect_content_type` misclassifies HTML starting with `<`

The HTML check (content.rs:159-164) fires for ANY content starting with

practice, content starting with `<` is almost always markup. **LOW risk —
the fallback to PlainText handles the edge case via per-domain overrides
