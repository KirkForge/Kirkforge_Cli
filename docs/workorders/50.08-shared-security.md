# WO 50.08 — Deep-read security audit: `src/shared/`

## Status: Audit complete — findings below

## Scope

Deep line-by-line read of the `src/shared/` module (the pure-logic seam
layer shared between tools, session, and TUI):

- `src/shared/mod.rs` (1287 lines)
- `src/shared/config/{mod,model,tools,display,security,session}.rs`
- `src/shared/access/{mod,deny_list}.rs`
- `src/shared/bash_safety.rs` (1515 lines)
- `src/shared/audit.rs` (2103 lines)
- `src/shared/event_bus.rs` (869 lines)
- `src/shared/memory.rs`, `metrics.rs`, `permission.rs` (2326 lines),
  `sandbox_policy.rs`, `test_util.rs`, `session_mode.rs`, `shell.rs`,
  `undo.rs`
- `src/shared/minify/mod.rs` (interface only; lang/expand are WO 50.07)

The audit looked for: path-traversal / symlink bypasses, bash deny-list
gaps and encoding bypasses, audit-log tamper vectors, config fields
parsed but unused or unsafe defaults, permission-rule compound-clause
evaluation errors, and event-bus dead producers/consumers.

## Summary

The shared module is **well-defended for a tripwire layer**. The code is
honest about its own ceiling: comments throughout (`ponytail:` notes in
`bash_safety.rs:169-178`, `permission.rs:317-327`, `sandbox_policy.rs`)
state plainly that the deny-list / pattern gates are a *tripwire*, not a
boundary, and that landlock + `--no-network` are the real enforcement.
That framing is correct and keeps a reviewer from over-trusting the
string-matching gates. The defects below are real but low-severity given
that framing — the highest is the `FileAuditSink` tamper-window, which
undermines the audit trail itself rather than the sandbox.

Findings are ordered by severity (Critical → Info).

## Findings

### F1 — `FileAuditSink` opens without `O_NOFOLLOW` (MEDIUM, tamper-window)

**Location:** `src/shared/audit.rs:720-724` (`FileAuditSink::flush`)

`AuditLog::new` (the simple NDJSON sink at `audit.rs:143-149`) correctly
applies `libc::O_NOFOLLOW` on Unix so a pre-created symlink at the audit
path cannot redirect appends. But `FileAuditSink::flush` — the hash-chained
tamper-evident sink — opens with a bare `OpenOptions::new().append(true).
create(true).open(&self.file_path)` and **no** `O_NOFOLLOW`:

```rust
let result = std::fs::OpenOptions::new()
    .append(true)
    .create(true)
    .open(&self.file_path)
    .and_then(|mut f| f.write_all(content.as_bytes()));
```

A symlink planted at `self.file_path` (e.g. `~/.local/share/kf-code/audit.jsonl`
→ `/dev/null` or an attacker-controlled file) would redirect the
hash-chained writes, defeating tamper-evidence even though the chain
hashes still verify. The simple `AuditLog` was hardened (the comment at
`audit.rs:150-152` documents the Unix-only fix and the Windows upgrade
path); `FileAuditSink` was not.

**Root cause:** `FileAuditSink` was ported from the TS `core-events`
implementation (WO 29.4) and the `O_NOFOLLOW` hardening added later
(WO 43.21 crash-robustness work) only touched `AuditLog`, not the
chained sink.

**Fix:** mirror the `AuditLog::new` open path — add
`#[cfg(unix)] { use std::os::unix::fs::OpenOptionsExt; opts.custom_flags(libc::O_NOFOLLOW); }`
before `.open()`. Same Windows caveat applies (documented at
`audit.rs:150-152`): the Posix-only flag leaves the Windows append path
unprotected; the upgrade path is a per-component `openat2(RESOLVE_NO_SYMLINKS)`
walk, out of scope here.

**Impact:** an attacker who can plant a symlink at the audit path (requires
write access to the audit directory, typically `~/.local/share/kf-code/`)
can redirect or hole-punch the tamper-evident log. This is a
local-attacker-with-data-dir-access threat model; landlock/seccomp contain
the *model* but not a malicious local user. Severity MEDIUM because the
audit log is the tamper-evidence primitive — defeating it by symlink is
exactly the class of attack the chain hash exists to detect.

### F2 — `verify_chain` reads the audit file with no `O_NOFOLLOW` (MEDIUM, tamper-evasion)

**Location:** `src/shared/audit.rs:654-678` (`FileAuditSink::verify_chain`),
`src/shared/audit.rs:784-824` (`resume_chain`)

Both `verify_chain` and `resume_chain` use `std::fs::read_to_string` /
`std::fs::read_to_string(file_path)` on `self.file_path` without any
symlink check. An attacker who swaps `audit.jsonl` for a symlink to a
pristine copy (or to `/dev/null`) can make `verify_chain` return `true`
on a tampered or emptied log. `create_audit_sink` calls `verify_chain`
at startup (`audit.rs:844`) and only *warns* on failure — so a swap
post-tamper that points the path at a clean file passes the startup
check silently.

**Root cause:** same as F1 — the `O_NOFOLLOW` hardening was applied to
the *write* path (`AuditLog::new`) but not to the *read* paths of the
chained sink.

**Fix:** read via `File::open` with `O_NOFOLLOW` on Unix (and
`symlink_metadata` reject before read on both platforms), or
`stat`-then-`fstat` dev/inode consistency check. The
`resume_chain` truncating write (`audit.rs:806`, `audit.rs:820`) also
lacks `O_NOFOLLOW`.

**Impact:** complements F1 — F1 lets writes be redirected, F2 lets
verification be fooled. Together they break the "tamper-evident" property
the chain hash is meant to provide, for an attacker with data-dir write
access. Same MEDIUM threat model.

### F3 — `PathGuard::check_write` does not re-check deny list on canonical target (LOW-MEDIUM, symlink-assisted bypass)

**Location:** `src/shared/access/mod.rs:240-406` (`check_write`)

`check_traversal` (and therefore `check_read`) has an explicit
**canonical-target deny-list re-check** at `access/mod.rs:149-157`:

```rust
// 3b. When we follow symlinks, the original deny-list check may not
//     have caught the canonical target. Re-check the resolved path so
//     a symlink inside the sandbox cannot point to a denied file.
if self.follow_symlinks && self.deny_list.is_path_denied(&canonical) {
    return GuardVerdict::Denied(...);
}
```

`check_write` has **no equivalent re-check**. It checks the deny list on
the *literal* path (step 1, `mod.rs:242-244`), then canonicalizes for the
sandbox/allowed-dir containment check (step 2, step 6), but never re-runs
`deny_list.is_path_denied` on the canonicalized path. When
`follow_symlinks` is true (operator opt-in, default false) and an
existing path is a symlink whose *name* is not denied but whose *target*
is (e.g. `safe_link → secret.pem`), `check_write` will allow the write
because:

1. Step 1 deny-list check passes (the symlink name `safe_link` is clean).
2. Step 6 symlink guard (`mod.rs:350-366`) only fires for the *existing*
   file's own `symlink_metadata` — and it rejects the symlink outright
   ("Cannot write through symlink"). **But** the existing-file symlink
   check at `mod.rs:350` runs *after* the deny-list check and *only*
   rejects if `path.exists()` and is a symlink. For a write to a
   *new* path whose *parent* is a symlink to a denied directory, no
   re-check happens — the canonical parent is used only for the
   `starts_with(sandbox)` containment test, not for the deny list.

`check_read` was hardened for exactly this case (test
`test_check_read_rechecks_deny_list_on_canonical_target` at
`mod.rs:1101-1126`); `check_write` was not.

**Root cause:** the canonical-recheck was added to `check_traversal`/
`check_read` (WO 28.1 era) but not mirrored into `check_write`, which has
a different control-flow shape (async, parent-dir fallback for new files).

**Fix:** after resolving the canonical path (or canonical parent for new
files) in `check_write`, re-run `self.deny_list.is_path_denied(&canonical)`
and deny if it matches. Add a test mirroring
`test_check_read_rechecks_deny_list_on_canonical_target` for the write
path.

**Impact:** LOW-MEDIUM. Requires `follow_symlinks: true` (default false)
AND a symlink planted inside the sandbox whose target is a denied path.
The existing-file symlink write guard (`mod.rs:350-366`) catches direct
writes through a symlink; the gap is the *parent-directory-symlink* case
for new files. Given `follow_symlinks` defaults off, this is a narrow
config-required bypass.

### F4 — `check_traversal`/`check_read` canonicalize before sandbox check, but sandbox `canonicalize()` is not O_NOFOLLOW-safe (LOW, TOCTOU)

**Location:** `src/shared/access/mod.rs:139-147`, `mod.rs:159-171`

`check_traversal` calls `path.canonicalize()` (step 3) which follows
symlinks by definition, then compares `canonical.starts_with(&sb)` where
`sb = sandbox.canonicalize()`. The `canonicalize()` calls are not
guarded against a symlink swap between the deny-list check (step 1) and
the canonicalization (step 3). A classic TOCTOU: the path is a regular
file at deny-list-check time, then swapped to a symlink pointing outside
the sandbox before `canonicalize()` runs.

**Mitigated by:** the `follow_symlinks: false` default rejects symlinks
at step 2 (`mod.rs:123-136`) *before* canonicalization, so the swap must
happen in the window between `path.exists()` (step 1.5, `mod.rs:116`)
and the symlink-metadata check (step 2). With `follow_symlinks: true`,
the window is between the deny-list check and `canonicalize()` — wider,
but the canonical-target deny-list re-check (step 3b) catches the
obvious "symlink to a denied file" case.

**Root cause:** `canonicalize()` is inherently TOCTOU-prone; the only
fully-safe pattern is `openat2(RESOLVE_BENEATH)` or a per-component
`O_NOFOLLOW` walk. This is a known ceiling (the `AuditLog` comment at
`audit.rs:150-152` references the same Posix-only upgrade path).

**Impact:** LOW. Requires a concurrent local attacker winning a filesystem
race inside the sandbox dir. The real boundary (landlock) caps the blast
radius to sandbox-allowed paths regardless. Documenting the TOCTOU window
is the honest fix; closing it is the `openat2` upgrade path.

### F5 — Bash deny-list does not catch `eval` of a decoded payload without `$()`/backtick (LOW, documented ceiling)

**Location:** `src/shared/bash_safety.rs:179-185` (`contains_shell_expansion_evasion`)

The evasion detector catches `${IFS}`, `$IFS`, `$'`, `$(`, and backticks.
It does **not** catch a bare `eval` combined with a here-doc or a
variable already holding a decoded payload:

```bash
X=$(echo cm0gLXJmIC8K | base64 -d)   # blocked: $( detected
eval "$(echo cm0gLXJmIC8K | base64 -d)"  # blocked: $( detected
# but:
X='rm -rf /'                         # NOT blocked (no expansion)
eval $X                              # NOT blocked by expansion check
```

`eval $X` has no `${IFS}`, no `$(`, no backticks — `$X` is plain
variable expansion, which the tripwire does not flag. The
dangerous-pattern scan (step 5) does not see `rm -rf /` because it is
inside the variable, not the command string.

**This is explicitly documented as a ceiling** (`bash_safety.rs:169-178`,
`bash_safety.rs:447-456`): the deny-list is a tripwire, not a boundary;
"the real boundary is landlock (WO 27.1) which confines the filesystem
blast radius, plus `--no-network` for exfiltration." The comment names
"variable indirection" as a known uncaught bypass and an allowlist as
the only non-theatrical command gate.

**Impact:** LOW given the documented framing. A model payload that uses
`eval $X` with a pre-loaded destructive variable bypasses the string
tripwire, but landlock still confines the filesystem damage to
sandbox-allowed paths, and `--no-network` blocks exfil. No code change
recommended — the ceiling is correctly documented. Listing here so the
audit is complete.

### F6 — `normalize_for_safety` does not strip `$()` / backtick content from the normalized form (LOW, normalization gap)

**Location:** `src/shared/bash_safety.rs:108-156` (`normalize_for_safety`)

The normalizer strips single/double quotes, backslash escapes, comments,
and lowercases — but leaves `$(` and backticks **intact in the output**
(the comment at `bash_safety.rs:106-107` says backticks are "intentionally
left intact because they denote command substitution"). This is fine for
the *evasion* detector (step 4, `contains_shell_expansion_evasion`, which
checks the raw command anyway), but it means the *dangerous-pattern* scan
(step 5) on the normalized form sees the literal `$(...)` or `` `...` ``
as text. A payload like `echo $(rm -rf /)` has `rm -rf /` inside the
`$()`, and the normalized form is `echo $(rm -rf /)` — the
`rm -rf /` substring *is* present, so step 5's `normalized.contains("rm -rf /")`
catches it. Good.

**But:** a payload like `r''m $(echo -n 'rm -rf /' | sh)` normalizes to
`rm $(echo -n rm -rf / | sh)` — the `rm -rf /` is split across the
`$(...)` boundary and the inner `rm -rf /` appears as `rm -rf /` inside
the substitution. Step 5 *does* catch this because `normalized.contains`
is a substring scan. The gap is only for payloads where the destructive
literal is reconstructed at runtime (e.g. `eval $(printf 'rm%s-rf%s/' '' '')`)
— which F5 already covers as a documented ceiling.

**Impact:** INFO. The normalizer's "leave `$()` and backticks intact"
choice is correct for the substring scan; the only bypasses are runtime
reconstruction, which is the documented tripwire ceiling. No change.

### F7 — `deny_list` glob matching is path-separator-agnostic on Windows (LOW, platform gap)

**Location:** `src/shared/access/deny_list.rs:68-73` (`is_path_denied`)

`is_path_denied` uses `globset::GlobMatcher` against
`path.to_string_lossy()`. The deny patterns are written with forward
slashes (`**/.ssh/**`, `/etc/shadow`). On Windows, a path like
`C:\Users\me\.ssh\id_rsa` uses backslashes — `globset` matches `**` as
"any chars including path separators" but its default `**` semantics
treat `\` as a separator only on Windows builds. `to_string_lossy()` on
Windows yields `C:\Users\me\.ssh\id_rsa`, and `globset`'s Windows
behavior for `**/.ssh/**` against backslash paths is
platform-dependent (globset does normalize separators, but the
leading `/etc/shadow` pattern is a Unix absolute path that will never
match a Windows `C:\...` path — which is fine, `/etc/shadow` doesn't
exist on Windows).

The more concerning case: a Windows path `C:\Users\me\.ssh\config`
should be denied by `**/.ssh/**`. `globset` does match `\` under `**` on
Windows, so this works. But an attacker who uses a mixed-separator path
(`C:/Users/me/.ssh/config`) on Windows gets a path whose `to_string_lossy()`
preserves the forward slashes — also matched. So the deny list is
sound on Windows for the default patterns.

**Impact:** INFO. No gap found after close reading; `globset` handles
both separators. The `DANGEROUS_REDIRECTION_TARGETS` list in
`bash_safety.rs:199-223` explicitly includes both Windows backslash
forms (`c:\\windows`) and Git-Bash forward-slash forms (`/c/windows/`),
so the bash gate is also cross-platform aware. No change.

### F8 — `AuditEntry::Tool` does not record a `run_id` / `trace_id` (INFO, observability gap)

**Location:** `src/shared/audit.rs:19-36`

The hash-chained `AuditEvent` (`audit.rs:402-423`) carries `trace_id`
and `policy_hash`; the simple NDJSON `AuditEntry::Tool` carries only
`session_id`. There is no `RunId` join key on the simple audit record,
so correlating a destructive tool call to the canonical run identity
(WO 45.1, `RunId` in `mod.rs:793-835`) requires parsing the session ID
out of the log. `AuditEntry::Hook` also lacks `trace_id`.

**Impact:** INFO. Not a security defect — an observability gap. The
hash-chained sink (`AuditEvent`) is the richer record; the simple
`AuditLog` is the legacy/best-effort path. Folding `run_id` into
`AuditEntry` would be an additive change. No action required for this
audit.

### F9 — `event_bus` typed kinds: `ArtifactUnterminated` has no production producer (INFO, dead variant)

**Location:** `src/shared/event_bus.rs:69-87` (`BusEventKind`)

The four typed `Artifact*` variants:
- `ArtifactEmitted` — produced by `executor_adapter.rs:274,332`.
- `ArtifactBlocked` — produced (test at `event_sink_bridge.rs:109`).
- `ArtifactTruncated` — produced (test at `event_sink_bridge.rs:148`;

production" — the variant exists ahead of the producer, which is the
documented pattern.

**Impact:** INFO. A dead enum variant with no producer; consumers
subscribing to it simply never fire. No security impact. The
`Other(String)` escape hatch means an `artifact.unterminated` string
emitted by a TS-port producer would still flow. No change.

### F10 — `Config` field count drift guard is manual (INFO, latent drift risk)

**Location:** `src/shared/config/mod.rs:15-57` (`CONFIG_FIELD_COUNT`)

The const `CONFIG_FIELD_COUNT = 111` is maintained by hand with a
running WO-history of bumps. The drift-guard test (referenced in the
comment, lives in `session::config`) checks it against the serde field
count. This is a correct and tested mechanism — but it depends on every
new field bumping the const. The comment documents this clearly
("When you add a field ... increment this constant"). The WO 27.2-R2
note (`mod.rs:37-40`) records a past drift of +5 that the "known-broken"
test hid for several WO cycles — so the mechanism has failed before and
was repaired.

**Impact:** INFO. The mechanism is sound and tested; the risk is
human-error on the bump, which the drift-guard catches. No change.

### F11 — `SandboxConfig::merge_with` lets a plugin *raise* limits but inherits `harden` from global (INFO, correct-by-design)

**Location:** `src/shared/mod.rs:418-438` (`SandboxConfig::merge_with`)

`merge_with` overlays a plugin manifest's `ResourceLimits` on the global
default. The comment (`mod.rs:420-425`) states "The `harden` flag is
inherited from the global (a per-plugin manifest cannot disable
hardening — only raise limits)." Inspecting the impl: `harden`,
`no_network`, `block_edits`, `accept_unsandboxed` are all taken from
`self` (the global), not from `limits`. Only `cpu_limit_secs`,
`memory_limit_mb`, `filesize_limit_mb` take the `Some` from the plugin.
This is correct: a plugin cannot disable hardening or network isolation,
only raise rlimits. Good.

**Impact:** INFO. Verified correct. No change.

### F12 — `is_gitignored` is fail-open and has a 2s timeout (INFO, documented)

**Location:** `src/shared/access/mod.rs:78-100` (`PathGuard::is_gitignored`)

The method spawns `git check-ignore --quiet` with a 2s timeout and
returns `false` (not ignored → allow the write) on any error, timeout,
or git-unavailable. The comment at `mod.rs:71-77` documents this as
intentional fail-open: "the block happens only when we can positively
confirm the dotfile is git-ignored."

This is the correct choice for a dotfile-write gate (fail-open prevents
blocking all writes in a non-repo), but it means a slow filesystem or a
`git` binary that hangs can let a git-ignored dotfile write through.
The 2s timeout bounds the hang. The gate only applies to dotfiles
(`mod.rs:316-324`), so the blast radius is "writing to a dotfile that
gitignore would have blocked" — not a sandbox escape.

**Impact:** INFO. Documented fail-open with a bounded timeout; only
guards dotfile writes. No change.

## What was verified as correct

These were specifically checked and found sound:

- **`check_traversal` deny-list re-check on canonical target**
  (`access/mod.rs:149-157`): correctly re-runs `is_path_denied` on the
  canonicalized path when `follow_symlinks` is true. Pinned by
  `test_check_traversal_rechecks_deny_list_on_canonical_target`.
- **`check_read` size limit uses canonical metadata** (`mod.rs:186-209`):
  measures the canonical target, not the symlink — a tiny symlink to a
  huge file is correctly rejected. Pinned by
  `test_check_read_size_limit_follows_symlink_target`.
- **`check_write` rejects writing through an existing symlink**
  (`mod.rs:350-366`): `symlink_metadata` check before any write.
- **`check_write` for new files resolves the parent** (`mod.rs:272-283`):
  cannot create a file outside the sandbox via a non-existent path whose
  parent resolves outside — the parent canonicalization fails-closed.
- **Bash allowlist compound-clause check** (`bash_safety.rs:354-378`):
  every clause's head must prefix-match; `&&`/`||`/`;`/`|`/`\n`/`\r` and
  lone `&` (WO 44.20) all split. Pinned by `allowlist_denies_background_separator_payload`.
- **Bash allowlist redirection-`&` exception** (`bash_safety.rs:410-433`):
  `>&`, `&>`, and fd-dup `2>&1` are NOT treated as separators —
  legitimate redirections stay one clause. Pinned by
  `split_compound_clauses_keeps_ampersand_in_redirection`.
- **Permission rule deny-on-non-string** (`permission.rs:272-279`): a
  `Deny` rule with a non-string arg value fails CLOSED (honors user
  intent); `Allow`/`Ask` rules skip. Pinned by
  `test_evaluate_non_string_key_fails_closed_for_deny`.
- **Permission rule compound-clause: deny trips on ANY clause, allow
  requires ALL** (`permission.rs:314-367`): the asymmetry is correct —
  a deny must fire on a hidden second clause; an allow must not
  authorize a chained payload. Pinned by
  `test_evaluate_compound_allow_blocked_cargo_test_curl` and
  `test_evaluate_deny_command_trips_on_any_clause`.
- **Permission deny patterns: `*`→`**` promotion + prefix match +
  case-insensitive** (`permission.rs:314-343`): deny rules promote lone
  `*` to `**` (cross-slash), apply a prefix match for patterns ending in
  `/`/space/tab, and lowercase both sides. Pinned by
  `test_evaluate_deny_command_uppercase_pattern_blocks`.
- **`glob_match` is linear-time NFA** (`permission.rs:122-167`): the
  previous recursive backtracker was exponential on overlapping `**`
  (a config-authored DoS on the tool-call permission path, WO 47.34);
  the NFA state-set simulation is linear. Pinned by
  `glob_match_overlapping_double_stars_stay_linear`.
- **Audit log per-entry flush + `sync_data`** (`audit.rs:230-243`):
  survives SIGKILL / `panic=abort`. Pinned by
  `audit_log_crash_all_entries_present_without_drop`.
- **Audit chain torn-tail handling** (`audit.rs:784-824`): a partial
  final line (SIGKILL mid-write) is truncated back to the last good
  line, not treated as tamper. Pinned by
  `file_audit_sink_torn_tail_resumes_and_verify_chain_true`.
- **Audit chain flush atomicity on write failure** (`audit.rs:690-731`):
  `last_hash` and `buf` are left untouched on `write_all` failure, so
  the next flush re-seals the same events with identical chain hashes.
  Pinned by `file_sink_flush_failure_leaves_last_hash_and_buf_untouched`
  (WO 46.1).
- **`scrub_free_text` regex** (`audit.rs:1005-1060`): scrubs
  `NAME=value` for credential-shaped names and bare token literals
  (`Bearer`, `sk-`, `ghp_`, `github_pat_`, `glpat-`, `AIza`, `ya29.`,
  `AKIA`, `xox[bp]-`). The `AIza` length guard (35 chars) avoids
  false-positive on `AIzaphenia`. Pinned by
  `scrub_free_text_redacts_all_token_literals` and
  `scrub_free_text_redacts_bare_provider_tokens`.
- **`truncate_string` UTF-8 boundary** (`audit.rs:983-996`): slices on a
  char boundary, not a byte boundary. Pinned by
  `test_truncate_string_respects_utf8_boundaries`.
- **Event bus `InflightGuard`** (`event_bus.rs:197-219`): RAII decrement
  on Drop handles future cancellation mid-await — `graceful_shutdown`
  no longer parks on a oneshot that never fires. Pinned by
  `cancelled_emit_does_not_leak_inflight`.
- **Event bus no-silent-drop invariant** (`event_bus.rs:695-772`): every
  emit is either delivered or rejected with an explicit `Err`; no event
  vanishes under saturation. Pinned by
  `emit_faster_than_drain_never_silently_drops` + proptest.
- **Event bus end-of-emit buffer removal matches full identity**
  (`event_bus.rs:347-362`): uses the full idempotency hash
  (kind+stream_id+sequence+value+timestamp), not (sequence, kind) alone
  — two streams sharing sequence+kind cannot steal each other's
  in-flight entries. Pinned by
  `emit_removal_matches_full_identity_not_sequence_kind` (WO 47.28).
- **`SandboxConfig` manual `Default`** (`mod.rs:451-465`): does NOT
  derive `Default` (which would zero the rlimit fields and SIGXCPU-kill
  every subprocess). WO 27.2-R2 root cause for 11 "known-broken" tests.
- **`DenyList` default blocks cloud metadata endpoints**
  (`deny_list.rs:111-116`): AWS (`169.254.169.254`), GCP
  (`metadata.google.internal`), Alibaba (`100.100.100.200`).
- **`DANGEROUS_REDIRECTION_TARGETS` includes Windows + Git-Bash/WSL
  forms** (`bash_safety.rs:199-223`): `c:\\windows`, `/c/windows/`,

- **`normalize_for_safety` mid-word `#`** (`bash_safety.rs:142-144`): a

- **`process substitution `<(``** (`bash_safety.rs:576-578`): blocked
  as evasion. Pinned by
  `check_bash_command_str_blocks_process_substitution_without_literal`.
