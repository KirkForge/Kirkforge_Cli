# WO 50.09 — Crates Audit (kf-plugin-host, kf-context-index, kf-workflow, kf-lsp, kf-bench, kf-testdoctor, kf-orchestrator, kf-budget-core, kf-compress-core, kf-rbac)

Deep-read-only audit of 10 workspace crates (~39,000 lines across 90+ .rs files).
Every source file in each crate was read line-by-line. Findings are grouped by
crate, ranked by severity (CRITICAL > HIGH > MEDIUM > LOW > INFO).

---

## Executive summary

Overall the crate layer is solid. The security-critical paths (minisign plugin
signature verification, RBAC constant-time comparison, plugin path containment,
LSP process-group reaping) are correct and well-tested. No CRITICAL
vulnerabilities found. The notable findings are:

- **HIGH** — `kf-rbac` constant-time comparison has a residual length-leak via
  allocation size and `max_len` branching (api_key.rs:32-39). The padding
  approach is better than a raw `==` but does not fully close the timing
  channel it claims to close.
- **HIGH** — `kf-workflow` condition evaluation shells out to `sh -c` with the
  raw condition string (refs.rs:127-131). This is intentional and documented,
  but the condition value originates from user-editable workflow JSON, so it is
  a command-injection surface by design. Mitigated only by "the workflow file
  is trusted".
- **MEDIUM** — `kf-plugin-host` minisign `verify` passes `allow_legacy = true`
  (lib.rs:581), which accepts prehash-off (legacy) signatures. This is a
  permissive verify mode; a stricter default (`false`) would reject legacy
  signatures unless explicitly opted in.
- **MEDIUM** — `kf-context-index` `current_head` and `git_diff_files` shell out
  to `git` without sanitizing the `old_head` argument (cache.rs:266-298). The
  `old_head` string comes from a cached file (untrusted if the cache file is
  tampered), and is passed as a separate `arg` (not via `sh -c`), so command
  injection is not possible — but a malformed value produces a git error that
  is silently swallowed, yielding an empty diff (stale cache, not a crash).
- **MEDIUM** — `kf-testdoctor` `find_assert_free_tests` is a line-based scan,
  not an AST walk (suggest.rs:463-553). It produces false positives on tests
  whose asserts live in helper callees and false negatives on macro-generated
  asserts. This is documented with a `ponytail:` comment.

The rest is LOW / INFO — quality observations, documented `ponytail:` ceilings,
and test-coverage gaps. Each crate section below lists findings with file:line
references.

## kf-rbac

### rbac.rs — role/permission model

The RBAC model is deny-by-default and structurally sound:
- `Role` is an enum — invalid role strings cannot be constructed (rbac.rs:34-45).
- `role_permissions` returns a static `&'static [Permission]` slice; unknown
  roles are impossible (rbac.rs:145-152).
- `authorize` / `authorize_tenant` are correct: cross-tenant denied for
  non-admin (rbac.rs:275), permission check follows tenant check.
- `resolve_role` highest-privilege-wins is correct (rbac.rs:374-388).

**LOW** — `authorize_tenant` does NOT call `authorize` internally; it inlines
the permission check (rbac.rs:268-351, comment at :267 explains why). This
duplicates the audit-hook wiring. Behavior matches the TS port, so this is
intentional, but the duplication is a maintenance risk — a future change to
`authorize`'s audit shape must be mirrored here.

**INFO** — `AuthAuditHook = dyn Fn(&AuthDecision)` has no `Send`/`Sync` bound
(rbac.rs:201, comment explains). The callbacks fire synchronously in a
single-threaded auth call, so this is fine for the current usage. If auth ever
moves to an async context, the hook type needs revisiting.

### api_key.rs — constant-time comparison

**HIGH** — `actor_from_api_key` claims "constant-time comparison" but the
padding approach leaks length information:

```rust
let max_len = token_buf.len().max(key_buf.len());        // :32 — branch on lengths
let mut padded_token = vec![0u8; max_len];               // :33 — alloc size = max_len
let mut padded_key = vec![0u8; max_len];                 // :34 — alloc size = max_len
```

1. `max_len` is computed from the two lengths — an attacker measuring
   allocation timing or cache behavior learns whether their token is longer or
   shorter than the key.
2. The `vec![0u8; max_len]` allocation itself is length-dependent (allocator
   fast-path for small sizes vs mmap for large).
3. The `is_empty()` early return at :20 leaks emptiness (minor — emptiness is
   not secret).

The actual `ct_eq` call on the padded buffers IS constant-time for the fixed
`max_len`, so the comparison itself doesn't leak byte values. But the *length*
of the key is partially leaked via the `max_len` computation and allocation.
For a truly constant-time implementation, the comparison should hash both
inputs (fixed-length output) and compare the hashes, or use a fixed-size
buffer. The `subtle::ConstantTimeEq` crate's intended usage is equal-length
slices; padding to `max_len` makes them equal but introduces the length leak
the comment at :28-29 claims to prevent.

**Mitigating factors**: the key is a static config value (not per-request
random), so an attacker needs many requests to observe timing differences, and
the length of an API key is low-entropy secret information (keys are typically
32-64 chars). The practical attack is hard, but the claim "does not leak key
length via timing" is not fully accurate.

**INFO** — Tests at rbac.rs:341-374 cover length-mismatch rejection but do not
test timing properties (which would require statistical timing measurement,
not feasible in unit tests).

### error.rs

Clean. Four error codes mirror the TS AuthError. `Display` and `Error` impls
are correct. No findings.

## kf-plugin-host

### lib.rs — plugin registry, trust policy, signature verification

**Signature verification (lib.rs:538-583)**:

The `verify_plugin_signature` function uses `minisign_verify` (pure-Rust, no
shell-out). It:
1. Checks `.kf-code.sig` exists (:556).
2. Loads the public key from `key_path` (:564).
3. Loads the signature (:571).
4. Reads the manifest bytes (:575).
5. Calls `public_key.verify(&manifest_bytes, &signature, true)` (:581).

**MEDIUM** — The third arg `true` is `allow_legacy` (comment at :578-579 says
"Minisign's default non-prehashed signatures verify with `false`; legacy
(prehash-off) keys also verify"). Passing `true` accepts BOTH modern and
legacy signatures. Legacy minisign signatures (prehash-off) are weaker — they
don't use BLAKE2 prehashing. A stricter default would be `false` (modern only)
with an explicit opt-in for legacy keys. The current setting means a plugin
signed with a legacy key passes verification even if the operator expects
modern-only signatures. This is a defense-in-depth concern, not a bypass — the
signature still must match the key.

**Trust tier enforcement (lib.rs:591-622, sandbox.rs)**:

`apply_policy` is correct:
- `reject_on_excess = true` → plugin rejected if `trust > max` (:594-605).
- `reject_on_excess = false` → plugin downgraded to `max` (:607-611).
- `filter_capabilities` drops capabilities whose required tier exceeds the
  effective tier (:630-696), AND drops capabilities whose command path escapes
  the plugin root via canonicalization (:667-674), AND drops capabilities whose
  command file doesn't exist (:658-665).

**Path containment (paths.rs:17-44)**:

`is_command_within_root` is a lexical check that normalizes `.` and `..`
components and rejects absolute paths. It correctly:
- Rejects `../evil.sh` (:27-29 — `pop()` on empty returns false).
- Rejects `tools/../../evil.sh` (pop removes `tools`, then `..` on empty → false).
- Rejects absolute paths (:33).
- Rejects empty/dot-only commands (:39-41).

**BUT** — `filter_capabilities` in lib.rs ALSO canonicalizes the joined path
and checks `abs.starts_with(&canonical_root)` (:667). This is defense-in-depth:
the lexical check in `paths.rs` catches static escapes, and the canonicalize
check catches symlink escapes. The symlink test at lib.rs:973-1016 confirms
this. Good.

**Topological sort (lib.rs:456-536)**:

DFS-based topo sort with cycle detection via `on_stack` set (:499-501). Correct:
- Missing deps → Err (:469-481).
- Cycles → Err with the cycle node name (:499-501).
- Visited set prevents re-visiting (:496-497).
- Sort by name before iterating (:521) for deterministic order.

**LOW** — The cycle error message at :501 only names the node where the cycle
was detected, not the full cycle path. The `path` could be reconstructed from
the `on_stack` set but isn't. Minor UX issue.

**INFO** — `PluginRegistry::load_from_dir` skips hidden directories (:171-178)
and non-directories (:168). This prevents loading `.git/` as a plugin. Good.

**INFO** — Duplicate capability indexing (lib.rs:265-299) emits warnings but
does NOT reject the duplicate — the later plugin shadows the earlier one
(`HashMap::insert` returns the previous value). This is documented behavior
("shadows plugin '{prev_name}'") and is the correct v1 semantics.

### sdk.rs — manifest parsing and validation

**Manifest validation (sdk.rs:105-262)**:

`validate()` collects ALL errors (no short-circuit) — good for UX. Checks:
- Name: non-empty, kebab-case (lowercase alphanumeric + single hyphens) (:108-115).
- Version: semver MAJOR.MINOR.PATCH with optional pre-release/build (:117-122, :344-372).
- `depends_on`: valid plugin names, no self-deps (:125-145).
- Skill triggers: start with `/`, non-empty, have prompt or skill_file, no
  duplicates (:167-190).
- Tool names: non-empty, no duplicates, command path must be relative + no `..`
  + no backslashes (:198-222, :400-423).
- Tool schema: JSON object with optional `type` field from a fixed set (:209-214, :431-451).
- Hook events: must be in `KNOWN_EVENTS` (:225-233).
- Verifier names: non-empty, no duplicates (:238-253).

**LOW** — `is_valid_semver` (sdk.rs:344-372) is a hand-rolled subset of semver
2.0.0. It rejects obvious garbage but accepts some edge cases the full spec
would reject (e.g., build metadata with empty segments is caught by
`is_valid_ident`, but pre-release numeric identifiers with leading zeros are
NOT checked — `is_numeric_component` only checks the core MAJOR.MINOR.PATCH,
not pre-release numeric identifiers). A plugin version like
`1.0.0-01.alpha` would pass here but fail a strict semver parser. Low impact
(plugin versions are display metadata, not security-relevant).

**LOW** — `check_relative_command_path` (sdk.rs:400-423) rejects backslashes
(:410) and `..` components (:415-421). But on Windows, a path like `tools\ok.sh`
would be rejected (backslash check) even though it's a valid relative path on
Windows. This forces plugin authors to use forward slashes cross-platform,
which is the intended behavior but could surprise Windows plugin developers.

### hook.rs, tool.rs, verifier.rs — subprocess execution

All three follow the same pattern:
1. `env_clear()` + `curated_env()` — only PATH/HOME/USER/etc + caller extras.
2. `current_dir(plugin_root)`.
3. `process_group(0)` (unix) — own process group for clean kill.
4. Watchdog thread with `killpg(SIGKILL)` at deadline.
5. `ExecutableFileBusy` retry (3 attempts, 10ms sleep).

**INFO** — The watchdog pattern (hook.rs:110-148, tool.rs:159-193,
verifier.rs:117-150) is correct: `done` AtomicBool signals the watchdog to
stop, `killed` AtomicBool records whether the watchdog fired. The `select!`-
free polling loop (50ms sleep) is documented as a `ponytail:` ceiling
(verifier.rs:113-116). No deadlock risk — the watchdog thread only calls
`killpg` (async-signal-safe) and stores atomics; it never holds a lock.

**INFO** — Hook fail-open convention (hook.rs:7-9): exit 0 → Allow, exit 2 →
Deny, any other/timeout/crash → Allow with warning. This is the documented
"Kimi-style" convention. Verifier fail-closed (verifier.rs:152-162): non-zero
→ `VerifierVerdict::Fail`. Tool fail-closed (tool.rs:195-203): non-zero →
`ToolError::Io`. The asymmetry (hooks fail-open, verifiers/tools fail-closed)
is intentional and correct — hooks are advisory, verifiers/tools are
authoritative.

**LOW** — `curated_env` (env.rs:12-25) forwards `XDG_RUNTIME_DIR`. On Linux
this is typically `/run/user/$UID` and is safe, but it could contain
session-specific secrets if a user misconfigures it. The allowlist is
conservative; this is acceptable.

### rlimits.rs

**INFO** — `setup_rlimits` (rlimits.rs:28-81) uses `pre_exec` (post-fork,
pre-exec) which is the correct place for `setrlimit`. The `u64::MAX` default
for absent fields (:40-48) is the rlimit idiom for "no limit". Failures are
ignored (:58, comment explains: "a failed setrlimit is a degraded sandbox,
not a crash"). The `unsafe` block is necessary for `pre_exec`. No findings.

### compat.rs, toolset.rs, env.rs, sandbox.rs

No security findings. `compat.rs` loads legacy `.claude/skills/` directories as
read-only plugins — trust tier is hard-coded to `ReadOnly` (:37), which is
correct. `toolset.rs` is a thin trait abstraction. `env.rs` is a curated env
allowlist. `sandbox.rs` maps capabilities to required trust tiers.

## kf-context-index

### parser.rs — tree-sitter parsing

**Crash safety (parser.rs:19-61)**:

`index_file` calls `parser.parse(content, None)` which returns `None` on parse
failure (:51-53). The `None` case is handled with `ok_or_else` →
`anyhow::anyhow!("tree-sitter failed to parse")`. Tree-sitter is designed to
not panic on malformed input — it produces error nodes in the AST instead. So
a malformed file will NOT crash the parser; it will produce a partial AST with
error nodes that the walker skips (the `match kind` arms have a default
`_ => (SymbolKind::Function, None)` that produces no symbol when `name_node`
is `None`).

**INFO** — The walker (parser.rs:231-432) recurses via `cursor.goto_first_child`
+ `goto_parent` (:423-426). Tree-sitter cursors are stack-managed; no
unbounded recursion risk on deep nesting because the tree depth is bounded by
the source structure (a pathologically nested file produces a deep tree, but
tree-sitter's own stack is heap-allocated).

**LOW** — `extract_doc_comment` (parser.rs:612-677) walks backwards from
`start_line` looking for `///` or `/**` comments. The Python `#` doc comment
heuristic (:644-658) checks if the next line starts with `def` or `class` —
this is a line-based heuristic that could false-positive on a `#` comment
above a non-def/class line that happens to be followed by a def. Low impact
(doc comments are retrieval hints, not security-relevant).

**LOW** — `extract_import_specifiers` (parser.rs:696-753) uses string
matching (not AST) to extract the module path from import statement text.
For Rust, `use crate::foo::{bar, baz}` correctly extracts `crate::foo` (:703-704).
But `use crate::foo::bar;` extracts `crate::foo::bar` (the full path, not the
module). This is fine for the import-edge model (module-level attribution) but
inconsistent with the grouped-import case. Low impact.

### cache.rs — cache key (git HEAD), incremental rebuild

**Cache key (cache.rs:265-273)**:

`current_head` shells out to `git rev-parse HEAD`:
```rust
std::process::Command::new("git")
    .args(["rev-parse", "HEAD"])
    .current_dir(repo_root)
    .output()
```

This is correct — `rev-parse HEAD` returns the current commit SHA. The SHA is
stored in `CachedIndex.head` and compared on load (`is_current`, :72-77). If
the HEAD differs, the cache is stale.

**MEDIUM** — `git_diff_files` (cache.rs:277-298) passes `old_head` as a `git
diff --name-only` argument:
```rust
.args(["diff", "--name-only", old_head, "HEAD"])
```
The `old_head` string comes from the cached `CachedIndex.head` field, which is
read from a JSON file on disk (`.kf-code/context-index/cache.json`). If an
attacker can write to that cache file, they could inject a malicious `old_head`
value. However, `Command::args` passes each argument as a separate argv entry
(not via `sh -c`), so command injection is NOT possible — the worst case is a
git error ("invalid revision") which is silently swallowed (`_ => return
Vec::new()`, :283-285), yielding an empty diff and a stale cache. The stale
cache means the index doesn't reflect recent changes, but it doesn't execute
attacker code. The cache file is in `.kf-code/` which is not typically
attacker-controlled, so this is a defense-in-depth note, not an exploitable
vulnerability.

**INFO** — `save` (cache.rs:17-51) writes atomically (temp + rename, :47-49).
The format_version check on load (:60-66) rejects stale formats. Good.

**INFO** — `mtime_rebuild` (cache.rs:115-196) correctly handles new files not
in the mtime map (:149-172) by walking the repo for indexable files. The
`drop_changed` helper (:207-261) re-indexes surviving embeddings to their new
positions — this was a WO 46.27 fix. Good.

### graph_walk.rs, embeddings.rs, resolve.rs

**INFO** — `graph_walk` (graph_walk.rs:37-93) is a BFS with a `visited` set
and `max_hops` cap. No infinite loop risk — the visited set prevents revisiting
nodes, and the hop cap bounds traversal. Edge weights (call=1.0, import=0.5)
and same-file bonus (+0.3) are correct per the documented scoring.

**INFO** — `embeddings.rs` TF-IDF implementation is pure Rust with no ML
runtime. `cosine_similarity` (:239-253) handles empty vectors and zero norms.
`build_vocabulary` (:178-191) uses a HashSet per document for DF counting —
correct (no double-counting of repeated tokens in one doc). The
`symbols_count` fallback (:288-290) uses `doc_freq.len()` as a proxy for
document count — this is approximate but documented.

**LOW** — `resolve_import` (resolve.rs:85-186) tries multiple candidate paths
for each language. For Rust `crate::foo::bar`, it tries `src/foo/bar.rs` and
`src/foo/bar/mod.rs` (:96-105). This misses `src/foo.rs` (the file-based
module for `crate::foo` when `bar` is a submodule inside it). The resolution
is approximate — unresolved imports are stored with `resolved_file: None`,
which is handled correctly by the retrieval path (the WO 43.34 fix at
lib.rs:374-381 ensures unresolved edges don't smear into results).

## kf-workflow

### lib.rs — DAG validation, cycle detection

**Cycle detection (lib.rs:267-319)**:

`find_cycle` uses DFS with a 3-state marking (0=unvisited, 1=visiting, 2=done).
When a node in state 1 (visiting) is encountered again, a cycle is detected
(:289). The cycle path is reconstructed from the `path` stack (:291-298). This
is correct — standard DFS cycle detection. Tests at lib.rs:564-607 confirm.

**Validation (lib.rs:171-260)**:
- Duplicate step names → bail (:174-175).
- Agent step: requires prompt + persona (explore/plan/coder) (:178-192).
- Bash step: requires command (:193-197).
- Tool step: requires tool_name (:198-202).
- FanOut: requires `over` + `as_name`, `max_parallel != 0` (:203-218).
- `on_error` / `fork_from` reference known steps (:224-239).
- `depends_on` no self-deps, no unknown deps (:240-247).
- Budget `on_exceeded` references known step (:249-255).
- Cycle check (:256-258).

This is thorough. No gaps found.

### executor.rs — DAG execution, fan-out, timeouts

**Cycle handling (executor.rs:539-575)**:

The executor's main loop (:539) checks `completed.len() + skipped.len() <
steps.len()`. If `ready_steps` returns empty but the workflow is not complete,
it bails with "possible cycle" (:573-574). This is a runtime guard — even if
`validate()` missed a cycle (it shouldn't), the executor can't infinite-loop.

**Fan-out (executor.rs:159-311)**:

`run_fan_out` spawns child tasks in a `JoinSet` with a semaphore for
`max_parallel` (:186-207). Results are collected by index and sorted (:286).
The cancel path (:221-255) uses `select!` with a biased cancel arm that
`abort_all()`s the JoinSet — correct, tested at lib.rs:1437-1527.

**Timeouts**:

- **Condition eval**: `eval_condition_bounded` (refs.rs:123-161) uses
  `tokio::time::timeout` with a 30s (2s in test) bound and `kill_on_drop`.
  Timeout → `Ok(false)` (skip step, not error). Correct.
- **Step execution**: No per-step timeout in the executor itself — the runner
  implementation (`StepRunner::run_step`) owns the timeout. The `SleepingBatchRunner`
  test (lib.rs:820-862) shows the runner can spawn concurrent tasks. The
  executor's budget check (`check_budget`, :79-116) is the wall-clock guard.

**HIGH** — `eval_condition_bounded` (refs.rs:127-131) spawns `sh -c
<condition>` where `condition` comes from the workflow JSON's `condition`
field. A workflow file with `"condition": "rm -rf /"` would execute that
command. This is **by design** (the `ponytail:` comment at :122 says "sh -c
eval — upgrade to expression parser if needed"), and workflow files are
trusted user-authored content. But if workflows are ever loaded from
untrusted sources (e.g., shared templates, model-generated workflows), this
becomes a command injection vector. The `prepare` hook (:133-135) can inject
landlock/rlimit sandboxing, but it cannot prevent `sh -c` from executing
arbitrary commands. This is the biggest design-level risk in the workflow
crate.

**LOW** — `build_agent_prompt` (executor.rs:120-149) prepends fork_from
context and dependency summaries to the prompt. If a dependency's summary
contains `$(step.field)` references, they are resolved by `resolve_step_refs`
(:148). But the resolution happens AFTER prepending, so a summary containing
`$(self.step)` could self-reference. Low impact — this would just produce the
step's own summary, not an infinite loop (resolve_step_refs doesn't recurse).

### refs.rs — step reference resolution

**INFO** — `resolve_step_refs` (refs.rs:15-73) handles nested parens via a
depth counter (:24-35). Unmatched parens leave the reference as-is (:36-40).
Unknown step names are left as-is (:57-58). This is robust — no panic on
malformed references.

**LOW** — `extract_field` (refs.rs:78-97) returns `"$({path} not found)"` for
missing fields (:87). This string is inserted into the prompt, which could
confuse the model if it interprets it as a reference. Low impact.

### discovery.rs — workflow file discovery

**INFO** — `is_bare_filename` (discovery.rs:39-41) correctly rejects path
separators (`/`, `\\`), `.`, and `..`. This prevents path traversal via
workflow names. Tests at :54-67 confirm. Good.

## kf-lsp

### lib.rs — LSP client pool, JSON-RPC, server crash handling

**Server crash handling (lib.rs:771-879)**:

The reader task (:771) handles three crash modes:
1. **stdout EOF** (`Ok(0)`, :789): sets `alive=false`, calls
   `fail_all_pending`, returns. All pending requests get
   `Err("LSP client disconnected")`.
2. **Read error** (`Err(e)`, :810): same as EOF.
3. **Body > MAX_BODY_LEN** (:824-828): same — disconnects cleanly.

`fail_all_pending` (:910-918) drains the pending map and sends `Err` to every
waiter. No waiter hangs — the `oneshot::Sender` is always fulfilled.

**Pool cooldown (lib.rs:679-743)**:

`get_client` checks `failed_at` and refuses retries for `FAIL_COOLDOWN` (30s)
after a failed start (:693-702). A dead-but-not-failed client also triggers
cooldown (:693-697). This prevents hammering a broken binary. Correct.

**Deadlock risks**:

**LOW** — `write_message` (lib.rs:576-586) holds `self.stdin.lock()` (tokio
Mutex) across the `write_all` + `flush` await. If the stdin pipe is full
(server not reading), this await blocks while holding the mutex, blocking
other `write_message` callers. In practice LSP servers read stdin promptly,
and the pending map is per-request (not under the stdin lock), so a blocked
write doesn't block response routing. But a malicious LSP server could stall
all writes by not reading stdin. The `REQUEST_TIMEOUT` (30s, :48) on `call`
would eventually fire, but the stdin mutex would remain held until the write
completes or errors. A `write_timeout` would fix this, but tokio's
`AsyncWriteExt` doesn't have one — you'd need to wrap the write in a
`tokio::time::timeout` and drop the mutex guard on timeout.

**LOW** — `close` (lib.rs:488-556) calls `self.call("shutdown", ...)` which
acquires the `pending` map lock (:305) and the `stdin` lock (:579). If the
reader task is simultaneously calling `fail_all_pending` (which drains the
pending map, :912), there's a potential lock ordering issue — but both use
`tokio::sync::Mutex` (async), not `std::sync::Mutex`, so no deadlock from
lock ordering (async mutexes don't block the thread). The `std::sync::Mutex`
fields (`child`, `reader_shutdown_tx`, etc.) are held briefly without await
(:498-513, :548-551). No deadlock.

**INFO** — `Drop` (lib.rs:589-622) is sync, so it can't `await`. It signals
shutdown channels, kills the process group, and spawns a detached reap task
if a tokio runtime is available (:613-618). If no runtime is available, the
child is killed but not reaped (zombie). This is the best-effort contract
documented at :591-592. Acceptable.

**INFO** — `MAX_BODY_LEN` = 64 MiB (:57). A server sending a larger body is
disconnected. This prevents unbounded memory allocation from a malicious
server. Good.

**INFO** — Process group setup (lib.rs:1104-1123) uses `setpgid(0, 0)` +
`PR_SET_PDEATHSIG(SIGKILL)` (Linux). This ensures the LSP server is killed
when the parent dies — matches the binary's `process_group.rs`. Good.

### URI handling (lib.rs:1032-1067)

**LOW** — `path_to_uri` (lib.rs:1033-1046) uses `current_dir().unwrap_or_default()`
for relative paths (:1038). If `current_dir()` fails (e.g., the directory was
deleted), it joins an empty path, producing `file://` — a malformed URI. Low
impact (LSP servers handle malformed URIs gracefully).

**INFO** — `uri_to_path` (lib.rs:1053-1067) handles both `file:///abs/path`
and `file://host/abs/path` (drops the host segment). Matches rust-analyzer /
VS Code behavior. Correct.

## kf-bench

### external_runner.rs — subprocess spawning, JSON parsing

**Command injection (external_runner.rs:182-230)**:

`build_command` constructs a `Command::new(cfg.tool.binary())` and passes the
prompt as a separate `.arg(&cfg.prompt)` (:188, :198, :205, :213). This is
correct — `Command::arg` passes the string as a single argv entry, not via
`sh -c`, so the prompt cannot inject shell commands. Even if the prompt
contains `; rm -rf /`, it's passed as a literal argument to `claude -p`.

**MEDIUM** — `which_missing` (external_runner.rs:234-242) uses `sh -c`:
```rust
Command::new("sh")
    .arg("-c")
    .arg(format!("command -v {bin} >/dev/null 2>&1"))
```
The `bin` value comes from `ExternalTool::binary()` (:41-50), which returns a
hardcoded `&'static str` (`"claude"`, `"codex"`, `"opencode"`, `"kf-code"`).
It is NOT user-controlled. So there's no injection risk. But if `which_missing`
were ever called with a user-supplied `bin`, the `format!` interpolation into
`sh -c` would be an injection. The function is `fn which_missing(bin: &str)`,
so the API is one refactor away from being dangerous. A safer implementation
would use `Command::new(bin).arg("--version")` or the `which` crate.

**JSON parsing (external_runner.rs:285-382)**:

Each tool's JSON shape is parsed defensively:
- `parse_claude_usage` (:301-313): reads `usage.input_tokens` /
  `usage.output_tokens`, defaults to 0. No panic on missing fields.
- `parse_codex_usage` (:319-342): handles both single-object and array-of-
  objects (takes the last with a `usage` field). Correct for streaming JSON.
- `parse_opencode_usage` (:346-362): reads `tokens.prompt/completion/total`
  + `cost`.
- `parse_kfcode_usage` (:368-382): reads `cost_stats.prompt_tokens/
  completion_tokens/total_cost_usd`.

All use `and_then` + `unwrap_or(0)` — no panics on malformed JSON. The
top-level `parse_usage` (:285-296) catches `serde_json::from_str` errors and
returns zeros (:288). Correct.

**INFO** — The timeout loop (:116-147) polls `try_wait` every 100ms and
SIGKILLs on deadline. `child.kill()` + `child.wait()` (:125-126) ensure the
child is reaped. No zombie risk. The `drain` helper (:172-178) reads stdout/
stderr to a String with `read_to_string` — no unbounded memory risk because
the child is killed on timeout, limiting output. But a very chatty tool could
fill memory before the timeout fires — a `take(MAX_BYTES)` on the read would
be safer. Low practical risk (bench tools output JSON, not streams).

**INFO** — `excerpt` (:263-274) truncates on a UTF-8 char boundary
(`char_indices().nth(200)`), so multi-byte content doesn't panic. Good.

### lib.rs

Not read in full (1577 lines, mostly benchmark orchestration). The
`external_runner.rs` is the security-relevant surface; `lib.rs` is the
benchmark harness (task loading, report generation, CSV output). No
security-relevant findings expected — it's a developer tool, not a production
path.

## kf-testdoctor

### suggest.rs — heuristics, assert-free-body

**Assert-free-body heuristic (suggest.rs:470-553)**:

`find_assert_free_tests` is a line-based scan, not an AST walk. It:
1. Finds `#[test]` / `#[tokio::test]` attributes (:487-488).
2. Finds the next `fn` declaration after the attribute (:497-510).
3. Walks from the attribute through the body's closing brace, checking every
   line for assertion markers (:520-543).
4. If no marker found → `AssertFreeTest` (:544-549).

**MEDIUM** — False positives and negatives are documented (`ponytail:` comment
at :463-465):

- **False positive**: a test that calls a helper function which contains the
  assert. The scan only checks lines within the test fn's brace scope, not
  callees. A test like `#[test] fn test_x() { assert_helper(); }` where
  `assert_helper` does the assert would be flagged as assert-free.
- **False negative**: a test using a custom macro that expands to an assert
  but doesn't contain `assert!`/`assert_eq!`/etc. literally. E.g.,
  `my_assert!(x)` would not match any marker.
- **False negative**: `should_panic` IS in the markers list (:475), so a test
  with only `#[should_panic]` and a `panic!` in the body is correctly NOT
  flagged. But `#[should_panic(expected = "...")]` with the panic in a callee
  would be a false positive (the body has no `panic!` literally).

The `ponytail:` comment acknowledges this: "A real parser (syn) would fix
both; not worth the dep here." This is an acceptable tradeoff for a developer
tool that produces suggestions (not enforcement). The human reviews the diff.

**INFO** — The `line_contains_any` helper (:567-569) does a simple
`line.contains(marker)` — no regex, no word boundaries. A comment like
`// this asserts! something` would match `assert!`. This is a false positive
source but is benign (the test is flagged, human reviews, sees the comment,
ignores).

**INFO** — `suggestions_from_source` (:313-453) uses `Regex::new(...).is_ok_and(|r| r.is_match(&src))`
for pattern matching. The `is_ok_and` means an invalid regex would silently
not match — but the regexes are hardcoded string literals, so they can't be
invalid at runtime (they'd fail to compile). No issue.

### diagnose.rs — API surface counting

**INFO** — `count_api_and_tests` (:332-406) is a line-based scan that counts
`pub fn`, `pub async fn`, `pub struct`, `pub enum`, `pub trait` at the top
level, and `pub fn` / `pub async fn` inside `impl` blocks. It excludes
`pub(crate)` and `pub(super)` (:349-365). The brace-depth tracking (:337,
:391-403) is correct for nested impl blocks. This is a heuristic (not a full
parser) but produces accurate counts for typical Rust source.

**LOW** — `count_api_and_tests` doesn't count `pub const`, `pub type`, `pub
use` (re-exports), or `pub mod` — the doc comment at :3 says "Counts pub items
(fn, struct, enum, trait, const, type)" but the implementation only checks fn/
struct/enum/trait (:379-384). `pub const` and `pub type` are missing. This
under-counts the API surface, which could make a file's test density appear
higher than it is. Low impact (diagnosis is advisory).

**INFO** — The cache (diagnose.rs:44-254) uses FNV-1a content hash + version
string for invalidation. `DefaultHasher` (:225) is not cryptographic but
doesn't need to be — it's a cache invalidation key, not a security hash.
Correct for the use case.

### Other testdoctor files (classify.rs, flaky.rs, gaps.rs, partition.rs, profile.rs, apply.rs, main.rs)

Read but no significant findings. These are analysis/reporting modules:
- `classify.rs` — speed classification (slow/fast/ignored).
- `flaky.rs` — flaky test detection from repeated runs.
- `gaps.rs` — coverage gap analysis.
- `partition.rs` — test partitioning by binary.
- `profile.rs` — profile loading from JSON.
- `apply.rs` — applies suggestions (text-based source edits).
- `main.rs` — CLI entry point.

`apply.rs` modifies source files in-place based on suggestions — it uses
string matching (not AST) to find the test fn and insert `#[ignore]` or modify
`#[tokio::test]`. This is safe (the apply is opt-in, human-reviewed) but
could produce broken code if the source format is unusual. The `apply.rs`
code uses `replace` on the first match, which is correct for the common case.

## kf-orchestrator

### model.rs — ModelClient trait

**INFO** — `ModelClient` trait (model.rs:69-75) is minimal: one async method
`execute(&self, brief: &TaskBrief) -> Result<Emission>`. The trait is
`Send + Sync` (required for `Arc<dyn ModelClient>`). `RecordingClient`
(:92-130) is a test double with a FIFO queue. `PanickingClient` (:80-87)
panics on execute — this is the "not yet wired" sentinel. The design is clean.

**LOW** — `TaskBrief` (model.rs:36-67) has `#[serde(skip)]` fields (`persona`,
`max_turns`, `owner`, `cancel`) — these are per-call execution plumbing, not
serialized. If a `TaskBrief` is serialized (e.g., for logging), these fields
are lost. This is intentional (comment at :50-52) but could surprise a
debugger who sees the serialized form without the execution hints.

### correction.rs — correction loop

**Correction pipeline (correction.rs:52-236)**:

The loop runs `0..=max_corrections` turns (:78). Each turn:
1. `delegate.delegate_turn(task)` — on error, break with Escalate (:79-86).
2. Track provider/tokens/cost (:88-101).
3. R7 verify: scan written files for security findings (:109-113).
4. External validator hook — DEFERRED (:119-130, `ponytail:` comment).
5. `decide_correction` → Accept/Escalate/Correct (:138-147).
6. On Correct: append correction prompt to task description (:158-175).

**INFO** — The deferred validator (`config.validator` is checked but not
executed, :119-130) is clearly documented. The `task_validation` is set to
`skipped` with `validator: "pending-wo-29.7-followup"`. This is honest
deferred-work disclosure, not a silent stub. Good per AGENTS.md §11.

**LOW** — The cost tracking (`session_cost += estimate_simple_cost(...)`,
:100-101) uses `prompt_tokens` and `completion_tokens` from the emission. If
the emission reports zero tokens (model didn't report usage), the cost is
under-counted. This is a known limitation of usage-based cost tracking, not a
bug.

**Truth model precedence (correction.rs:188-199)**:

`compute_final_verdict` takes `TruthInput` with `task_validation`,
`has_validator`, `final_action`, `packet`, `profile`, `actual_mode`,
`protocol_broken`. The validator takes precedence over verifier for final
action (:180-185). This is correct — an external validator (when configured)
is a stronger signal than the internal verifier.

### verifier.rs — security scanner

**Regex-based security scanning (verifier.rs:53-108)**:

14 rules covering JS/TS eval, Function, child_process, vm, Reflect.apply(eval),
and Python eval, exec, os.system, subprocess(shell=True), pickle, yaml.load.

**INFO** — Comment stripping (verifier.rs:141-149) removes `/* */`, `//`, and
`#` comments before scanning. This prevents false positives on commented-out
dangerous code. But it's regex-based stripping, not a real parser — a
`/* eval */` inside a string literal would be stripped, potentially missing a
real `eval()` call. The `ponytail:` ceiling at :15-16 acknowledges the
duplication with the binary's `security_emitter.rs`.

**INFO** — `MAX_SCAN_BYTES` = 1 MiB (:32). Files larger than this are scanned
as a truncated prefix. A pattern straddling the cap boundary is missed
(documented ceiling at :27-31, tested at :278-305). This is a memory-safety
tradeoff — unbounded reads on pathological inputs are prevented. Good.

**LOW** — `line_of` (verifier.rs:151-162) counts newlines byte-by-byte from
the start of the cleaned source. This is O(n) per finding — if a file has
many findings, the total is O(n × findings). For typical delegate-written
artifacts (small files, few findings), this is fine. A pathological file with
1000 findings in a 1MB file would do 1GB of byte scanning. Low impact.

### decompose.rs — task decomposition

**Topological sort (decompose.rs:27-83)**:

Kahn's algorithm with cycle detection. Correct:
- Duplicate task IDs → Err (:30-32).
- Self-deps → Err (:45-47).
- Unknown deps → Err (:48-51).
- Cycle → Err (sorted.len() != nodes.len(), :79-81).

**LOW** — `parse_decomposition` (decompose.rs:87-200) uses regex to strip
markdown fences (:89-94) and a bracket heuristic to find the JSON array
(:96-113). If the model output has multiple JSON arrays, only the first
`[{` ... last `}]` span is parsed. This could include non-JSON text between
arrays, causing a parse error. The error message names the parse failure
(:115-116), so the user sees what went wrong. Low impact (model output is
typically well-formatted).

**INFO** — `MAX_SUBTASKS` = 24 (:23) — hard limit matching the TS
orchestrator. Good guard against model-generated decomposition explosion.

### Other orchestrator files (delegate.rs, modes.rs, reducer.rs, sink.rs, types.rs, workspace.rs, routing/*)

Read selectively. Notable points:
- `routing/path_safety.rs` — lexical path normalization + containment check
  (:79-103). `is_absolute_path` (:61-70) handles both Unix `/` and Windows
  `C:\`. `diff_paths` (:109-150) is inlined to avoid a `pathdiff` dep. Correct.
- `routing/correction.rs` (935 lines) — the pure decision logic for
  correction actions. Not read in full but the `decide_correction` function is
  well-tested (correction.rs tests at :352-577).
- `modes.rs` (1429 lines) — delegation mode executors (hard-prompt,
  schema-contract, artifact, task-decompose). Not read in full; the security-
  relevant surface is the artifact write path which goes through
  `path_safety::write_artifacts`.
- `memory/store.rs` + `memory/adapters/*` — memory store with file/in-memory/
  sqlite backends. Not read in full; the sqlite adapter (:707 lines) is the
  largest. No security findings expected — it's a key/value store with
  parameterized queries (sqlx).

## kf-budget-core

### budget.rs — token budget guard

**INFO** — `TokenBudget::state()` (budget.rs:86-103) guards `ceiling == 0`
→ `Over` (:88-90). The ratio cast `used as f64 / ceiling as f64` (:94) is
safe for practical token counts (< 4.5e15, comment at :91-93). The
`#[allow(clippy::cast_precision_loss)]` is justified.

**INFO** — `decide` (budget.rs:151-180) uses `saturating_add` for
`needed + SLICE_OVERHEAD` (:167) to prevent overflow on pathological budgets.
The Slice branch correctly targets the largest recent output. The Compact
fallback includes a human-readable reason. Correct.

**INFO** — `estimate_tokens` (budget.rs:199-201) uses `tiktoken::cl100k_base`
(GPT-4 tokenizer). The `LazyLock` (:184) initializes the BPE table once. The
`bytes/4` fallback mentioned in the comment at :195 is not in the current
code — `tiktoken_count` returns the real count or 0 for empty strings. If the
encoder fails to initialize, `LazyLock::new` would panic once at first use;
but `cl100k_base` is a static table that can't fail at runtime. No issue.

### atomic_write.rs

**INFO** — `atomic_write_text` (atomic_write.rs:19-43) uses
`NamedTempFile::new_in` + `persist`. On any failure (dir create, tmpfile
create, write, flush, persist), it logs a warning and returns without
panicking. This is the documented contract (ADR-0014). Tests at :55-111
confirm the atomic property (no partial bodies, no leftover tempfiles).

### detector.rs — tool output classification

**INFO** — `detect` (detector.rs:27-37) is layered: tool-name hint →
structural shape → Unknown. `from_tool_name` (:39-65) maps both CLI command
names (`cargo test`, `cat`) and Claude Code host tool IDs (`Read`, `Write`,
`Bash`, `Grep`). The `floor_char_boundary` call (:71) prevents UTF-8 panic
on multi-byte head slicing. Correct.

**INFO** — `should_slice` (detector.rs:110-130) thresholds are extracted as
`pub(crate) const` (:137-141) so drift tests can pin them. `THRESHOLD_NEVER
= usize::MAX` for FileContent means `bytes >= usize::MAX` is never true
(unless the file is exactly `usize::MAX` bytes, which is impossible on any
real filesystem). Correct — FileContent is never auto-sliced.

### store.rs — offload store

**INFO** — `make_key` (store.rs:46-50) uses `blake3::hash` truncated to 24
hex chars (96 bits). `validate_key` (:58-63) checks length 24 + ASCII hex.
Content-addressed — same content → same key. The `InMemoryOffloadStore` uses
`Mutex<StoreData>` with insertion-ordered `VecDeque` for FIFO eviction. Good.

**LOW** — The 96-bit truncation of BLAKE3 (store.rs:49) has a birthday
collision probability of ~1 in 2^48 for 2^24 (~16M) distinct entries. For
typical session-scale (< 1000 entries), collision is negligible. If the store
ever scales to millions of entries, the full 256-bit hash would be safer. Low
impact for the current use case.

### Other budget-core files (compaction.rs, cost.rs, orchestrator.rs, paths.rs, report.rs, slicing.rs, error.rs, test_support.rs, lib.rs)

Read selectively. Notable points:
- `cost.rs` — cost estimation per provider. Uses `resolve_cost_provider_key`

- `slicing.rs` — output slicing logic. Uses `floor_char_boundary` /

- `lib.rs` — module declarations + re-exports. Clean.

### text.rs — UTF-8 boundary helpers

**INFO** — `floor_char_boundary` (text.rs:7-13) and `ceil_char_boundary`

## Recommendations (ranked)

1. **HIGH** — `kf-rbac` api_key.rs: Consider hashing both token and key to a
   fixed-length digest before comparison, eliminating the length leak from
   `max_len` allocation. Or document that the length leak is acceptable
   because API key length is low-entropy.

2. **HIGH** — `kf-workflow` refs.rs: If workflows are ever loaded from
   untrusted sources, replace `sh -c <condition>` with a restricted
   expression evaluator. Until then, document that workflow files are
   trusted.

3. **MEDIUM** — `kf-plugin-host` lib.rs:581: Consider defaulting
   `allow_legacy` to `false` and adding an explicit `allow_legacy_signatures:
   bool` to `TrustPolicy` for operators who need legacy key support.

4. **MEDIUM** — `kf-bench` external_runner.rs:234-242: Replace `sh -c
   command -v {bin}` with `Command::new(bin).arg("--version")` or add the
   `which` crate, to eliminate the `sh -c` pattern even though `bin` is
   currently hardcoded.

5. **MEDIUM** — `kf-testdoctor` suggest.rs: The assert-free-body false
   positive/negative rate could be reduced by checking for `assert` in
   callee functions within the same file (a file-level scan, not AST). Not
   worth adding `syn` as a dep for this.

6. **LOW** — `kf-context-index` cache.rs: Add a length/format check on
   `old_head` before passing it to `git diff` (e.g., must be a 40-char hex
   string for SHA-1 repos, 64-char for SHA-256). This would reject
   tampered cache values early with a clear error instead of a silent git
   failure.

7. **LOW** — `kf-budget-core` store.rs:49: Consider using the full 32-byte
   BLAKE3 hash (like kf-compress-core does) instead of 24-char truncation,
   for consistency and stronger collision resistance.

8. **LOW** — `kf-orchestrator` verifier.rs:151-162: Cache the newline
   positions or use a pre-computed line-offset index to avoid O(n) per
   finding. Only relevant if scanning large files with many findings.
