# WO 50.10 — Deep-Read Audit: CLI, Main, Daemon, Jobs

## Scope

Deep read (every line) of the CLI definition, binary root, all subcommand
handlers, line mode, turn-event recording, Chrome launcher, the daemon
feature surface (session daemon + jobs daemon), and the jobs data model /
runner / scheduler. All findings below cite `file:line`.

Segment files:

- `src/cli.rs`, `src/main/mod.rs`, `src/main/cli_dispatch.rs`
- `src/main/run_session.rs`, `src/main/handle_bench.rs`
- `src/main/handle_plugin.rs`, `src/main/handle_doctor.rs`
- `src/main/handle_update.rs`, `src/main/error.rs`
- `src/main/turn_events.rs`, `src/main/chrome_launcher.rs`
- `src/line_mode.rs`, `src/main/handle_replay.rs`, `src/main/handle_sessions.rs`
- `src/daemon/{mod.rs,paths.rs,client.rs,server.rs}`
- `src/jobs/{mod.rs,store.rs,runner.rs,schedule.rs,daemon.rs,client.rs}`

## Summary

The segment is mature and well-documented. The daemon feature-gate (WO 47.12)
is implemented correctly everywhere it appears — the `#[cfg(not(feature =
"daemon"))]` fallbacks in `run_session.rs` are exhaustive, the `Daemon`/`Jobd`
subcommands vanish from the clap enum when the feature is off, and `lib.rs`
gates the entire `daemon` module. Tests cover the no-daemon fallback paths on
both Unix and Windows stubs.

The audit surfaced **no critical bugs**. Findings are a mix of low-severity
hardening opportunities, one spec-drift observation, and one security-adjacent
concern about the update mechanism. Each is annotated with severity and
"worth fixing?" recommendation.

## Findings

### F1 — `handle_update.rs`: SHA256 verified, but no signature verification (MEDIUM)

**Files**: `src/main/handle_update.rs:54-60, 178-188`

The update mechanism downloads the archive and `SHA256SUMS.txt`, then verifies
the archive hash against the expected line:

```rust
let sums = download_sha256sums(&client, &latest).await?;
let expected = parse_sha256sums_line(&sums, &archive)
    .ok_or_else(|| anyhow!("no checksum entry ..."))?;
verify_sha256(&archive_bytes, &expected)?;
```

`verify_sha256` (`handle_update.rs:178-188`) is a correct SHA-256 comparison
and `parse_sha256sums_line` (`:93-108`) correctly rejects malformed lines
(64-hex-char check, binary-mode `*file` handling).

**The concern**: both the archive and `SHA256SUMS.txt` are fetched from
`github.com/KirkForge/Kirkforge_Cli/releases/download/...` over HTTPS. A MITM
that can tamper with the archive can also tamper with `SHA256SUMS.txt` to match
— the checksum file is fetched from the same origin as the binary. The
SHA256 check protects against transport corruption and partial downloads, but
**not** against an attacker who controls the release artifact store. A
detached signature (minisign / GPG) over `SHA256SUMS.txt` — the project
already depends on `minisign` in dev-deps (`Cargo.toml:269`) and
`kf-plugin-host` ships a signed-manifest path — would close this. This is
**not a regression**: the existing `scripts/install.sh` has the same trust
model, and self-update mirrors it. But it is worth a future WO because
`kf-code update` is the one path that fetches + replaces the binary in place
without an operator re-reading the checksums file.

**Severity**: MEDIUM (defense-in-depth gap, not an exploitable bug).
**Worth fixing?** Yes — track a follow-up WO for detached-signature
verification; the minisign dep is already present in the workspace.

### F2 — `handle_update.rs`: `replace_binary` is not atomic on Windows (LOW, documented)

**File**: `src/main/handle_update.rs:226-247`

`replace_binary` writes the new bytes to a sibling temp file, sets 0o755, and
`rename` over the target. The Windows guard at `:227-229` bails explicitly:

```rust
if std::env::consts::OS == "windows" {
    anyhow::bail!("in-place self-update is not supported on Windows; use the release .zip");
}
```

On Unix the `rename(2)` is atomic. The temp file is created via
`tempfile::NamedTempFile::new_in(dir)` then `.keep()` — the `keep()` call
(`:232`) materialises the file on disk before the chmod + rename. This is
correct. The only nit: if the process is killed between `write_all` (`:234`)
and `rename` (`:244`), a stale temp file is left in the exe's directory.
`NamedTempFile::keep()` deliberately gives up auto-cleanup, so this is a
documented trade-off, not a leak. No action needed.

**Severity**: LOW (documented, Unix-only correct path).
**Worth fixing?** No — the Windows bail is intentional and the Unix path is
correct.

### F3 — `handle_update.rs`: `extract_binary` shells out to `tar` (LOW)

**File**: `src/main/handle_update.rs:193-220`

Extraction spawns `tar -xzf - -C <tmpdir>` and pipes the archive bytes to its
stdin. The comment at `:190-192` documents why (avoids adding flate2+tar deps
that bloat the release binary). The `tar` binary is present on every
Linux/macOS but **not guaranteed** in minimal containers (e.g.
`FROM scratch`, distroless). On such a host `kf-code update` fails with
"failed to spawn tar". This matches the install.sh contract (which also
shells out to `tar`), so it is a known ceiling, not a bug. The error message
is actionable via the `with_context("failed to spawn tar")` chain.

**Severity**: LOW (documented ceiling; matches install.sh).
**Worth fixing?** No — the ponytail comment at `:190-192` explicitly
accepts the `tar` dep on the host over a flate2 binary-size hit.

### F4 — `error.rs`: string-probe fallback still classifies session-layer denials (CORRECT, with a footgun)

**File**: `src/main/error.rs:29-92`

The `From<anyhow::Error>` impl (`:30-92`) first downcasts three typed errors
(`ManifestError` → ConfigParse, `ToolError` → AccessDenied, `AdapterError` →
ModelUnreachable/AccessDenied), then falls back to a lowercased
`format!("{e:#}")` substring match (`:69-90`). The `ponytail:` comment at
`:35-46` documents this is intentional for session-layer sandbox/path-policy
denials that still arrive as bare `anyhow` — their producers are not yet
typed. The string probes match `"denied"`, `"permission"`, `"sandbox"`,
`"blocked"`, `"outside the allowed area"`, `"not permitted"` (`:78-84`).

This is **correct and working**. The footgun: the classification is only as
good as the error message wording. A future refactor that rewords a sandbox
denial to e.g. "access restricted by policy" would silently reclassify to
`General` (exit 1) instead of `AccessDenied` (exit 4). The test at
`error.rs:175-247` covers the downcast paths but does **not** pin the string
probes — a wording drift would not be caught by the suite. Consider adding
one string-probe pin test per probe phrase.

**Severity**: LOW (latent; no current drift).
**Worth fixing?** Optional — add probe-phrase pin tests so a future
rewording fails loudly. Tracked by the existing `ponytail:` comment, so the
debt is already disclosed.

### F6 — `line_mode.rs` / `main/line_mode.rs`: `--read-stdin-full` correctly reads all stdin (NO ISSUE)

**Files**: `src/line_mode.rs:175-209`, `src/main/line_mode.rs:227-229`

`LineReader::Plain::read_full` (`line_mode.rs:187-209`) flips the flag off
on first call, then `read_to_string` the entire stdin and trims. The second
call returns `None` (EOF) because `read_full` is now false and `read_line`

`run_line_mode(... read_stdin_full)` → `line_reader.set_read_full(...)`
(`main/line_mode.rs:229`).

### F7 — `main/line_mode.rs`: Ctrl-C exits 130 (CORRECT)

**File**: `src/main/line_mode.rs:244, 557-563`

`exited_via_sigint` is set on SIGINT receipt (`:258`) and on the post-turn
cancelled flag check (`:497`). At the end of `run_line_mode`, if
`exited_via_sigint` is true, the function calls `std::process::exit(130)`
(`:562`) — the conventional 128+SIGINT exit code. This is correct.

The SIGINT handler (`spawn_line_mode_sigint_handler`, `:53-71`) sets the
cancel flag and notifies the main loop's `shutdown` `Notify`. The main loop
races `next_line` against `shutdown.notified()` (`:249-261`) so a blocked
stdin read is interruptible. Per-turn cancellation (`:460-479`) installs a
fresh `CancellationToken` and cancels it on shutdown notify, so in-flight tool
calls abort and `kill_on_drop` reaps children. This mirrors the TUI teardown
contract. The `line_mode_sigint_handler_flips_shutdown_path` test
(`:1056-1111`) pins the mid-turn cancellation contract.

### F8 — `jobs/schedule.rs`: cron expressions correctly parsed and normalised (NO ISSUE)

**File**: `src/jobs/schedule.rs:229-298`

`parse_schedule` (`:229-259`) handles `@hourly`/`@daily`/`@weekly`/`@restart`/
`@once <ISO>` aliases and raw 5- or 6-field cron. The normalisation
(`:291-298`) prepends `0 ` (seconds field) to 5-field expressions so the
`cron` crate can parse them. `parse_five_field_cron` test (`:405-412`)
confirms `"0 9 * * 1-5"` becomes `"0 0 9 * * 1-5"`. The
`parse_six_field_cron_left_alone` test (`:414-421`) confirms 6-field is left
alone. `invalid_cron_rejected` (`:425-428`) rejects garbage. The `@once`
parser (`:245-251`) preserves tag case via slicing the original string (not
the lowercased copy) — the `parse_once_preserves_tag_case` test (`:383-392`)
pins this.

`compute_next_run` (`:301-331`) correctly handles `Once` (returns the time
if `>= after`, else `None`), `Restart` (returns `after`), and `Cron` (uses
the `cron` crate's `.after()` iterator). Timezone handling (`:321-329`)
converts `after` to the configured tz, evaluates the cron in local time, then
converts back to UTC — so `0 9 * * *` fires at 9am in the user's timezone,
not UTC. Correct.

### F9 — `jobs/daemon.rs`: overlapping jobs run concurrently, bounded by a semaphore (CORRECT, with a note)

**File**: `src/jobs/daemon.rs:157-237`

When a job's `next_run` falls within `[last_check, now]`, it is collected into
`due_jobs` (`:168-176`) and each due job is `tokio::spawn`ed with a
`semaphore.acquire()` permit (`:191`). The semaphore is sized by
`config.tools.max_concurrent_scheduled_jobs.max(1)` (`:157`). So **a job that
overlaps with itself** (e.g. a 5-min job on a 1-min cron) will spawn a second
instance once a permit is free; the runner does not track "is this job id
already running". This is the documented design — the comment at `:26-34`
notes the default 300s timeout prevents a never-ending job from wedging the
daemon, and `max_concurrent_scheduled_jobs` bounds the parallelism.

**The note**: there is no per-job mutual exclusion. If two firings of the
same job overlap and the job writes to shared state (e.g. the same file,
the same git branch), they race. The `JobStore` is append-only per run
(`runs/<run_id>/`), so run artifacts don't collide, but the job's *effect*
(e.g. `git push`) can. This is an operator concern, not a daemon bug — the
semaphore bounds total concurrency, not per-job. A future WO could add a
`skip_if_running` flag, but the current contract is "cron semantics" (a
missed run fires next time, overlapping runs are allowed), which is what
cron itself does.

**Severity**: LOW (documented cron semantics; operator must set
`max_concurrent_scheduled_jobs=1` for serial execution).
**Worth fixing?** Optional — document the per-job overlap behavior in the
jobs README; no code change needed.

### F10 — `jobs/store.rs`: `create_run` TOCTOU between create and chmod (LOW)

**File**: `src/jobs/store.rs:181-195, 254-264`

`create_run` creates `stdout`/`stderr`/`run.json` via `create_private_file`
(`:184-186`), which does `File::create` then `set_permissions(0o600)`
(`:254-264`). On Unix, the file is briefly world-readable (umask default
0o022 → 0o644) between `create` and `set_permissions`. The window is tiny
(one syscall pair) and the directory itself is 0o700 (`:174-178`), so only
the owner can traverse into `runs/` anyway — a same-uid attacker who can
read the file in that window can already read the parent dir. So the TOCTOU
is not exploitable in practice given the 0o700 dir. The
`save`/`record_run` paths use `atomic_write` (O_EXCL + random tmp name),
which is the hardened path (WO 46.24). `create_private_file` is the older
pattern.

**Severity**: LOW (mitigated by 0o700 parent dir).
**Worth fixing?** Optional — migrate `create_private_file` to
`OpenOptions::custom_flags(O_EXCL)` + 0o600 mode in one call, or accept the
0o700 dir as sufficient defense. The existing pattern is not a regression.

### F11 — `jobs/daemon.rs`: scheduler uses `last_check` as the lower bound, preventing missed-run double-fire (CORRECT)

**File**: `src/jobs/daemon.rs:153, 167-176, 235, 260`

`last_check` is updated to `now` only **after** a pass completes (`:235`,
`:260`). On the next pass, `compute_next_run(&j.schedule, last_check, ...)`
returns the next firing strictly after `last_check`. This means:
- If the daemon was asleep for an hour and 60 minutely jobs are due, they
  all fire once (the filter is `t <= now` for the single pass), then
  `last_check = now` and the next pass sees only future firings.
- A one-shot `Once(t)` whose `t` fell inside the sleep window fires exactly
  once (because `compute_next_run` returns `None` for `t < after` on the
  next pass), then the job is disabled (`:217-219`).

This is correct cron catch-up semantics. No double-fire.

### F12 — `daemon/server.rs`: `handle_instance_register` releases the concurrency permit before the push loop (CORRECT, WO 46.19)

**File**: `src/daemon/server.rs:286-289`

The InstanceRegister handshake holds the 16-slot concurrency permit for auth
+ version check, then `drop(permit)` (`:286`) before entering the long-lived
push loop. The comment at `:279-286` explains why: holding the permit for the
connection lifetime would starve all 16 slots once 16 TUIs attach, blocking
new `kf-code run --attach`. This is correct and load-bearing.

### F28 — `handle_update.rs`: `UPDATE_TIMEOUT` is 30s for both check and download (LOW)

**File**: `src/main/handle_update.rs:111-128`

`UPDATE_TIMEOUT` is 30s (`:113`). The same timeout is used for the GitHub
API tag fetch (`:131-147`), the archive download (`:149-161`), and the
SHA256SUMS download (`:163-175`). For a large release archive on a slow
connection, 30s may be too short — the `reqwest::Client::timeout` is the
total request time, not per-byte. A 30MB archive over a 1Mbps link takes
~240s. The WO 38.3 comment (`:110-112`) documents the 30s bound was added
because the update client previously had **no** bound and hung forever. The
fix was correct for the check path but may be too aggressive for the
download path. A longer download timeout (or a per-phase timeout) would be
more robust.

**Severity**: LOW (the timeout is a fix, not a bug; 30s may be tight for
slow links).
**Worth fixing?** Optional — split into a 10s API-check timeout and a
300s download timeout, or document the 30s ceiling in `kf-code update
--help`.

## Cross-cutting observations

### CC1 — The daemon feature-gate (WO 47.12) is correctly implemented everywhere

Audited every `cfg(feature = "daemon")` and `cfg(not(feature = "daemon"))`
site (14 + 3 = 17 occurrences across 7 files). All are paired correctly:
- `lib.rs:13` gates the `daemon` module.
- `cli.rs:235,248` gate the `Daemon`/`Jobd` enum variants.
- `cli.rs:646,654` gate the parse tests.
- `cli_dispatch.rs:224,238` gate the match arms.
- `run_session.rs:11,217,242,282,330` gate the daemon client imports
  and the three fallback branches (`--attach`, `--auto-resume`, recent
  list) + the `try_touch` call.
- `jobs/mod.rs:10,12,18` gate `client`/`daemon`/`run_job_daemon`.
- `tui/commands/fork.rs:215,231,238` and `tui/mod.rs:45,537,743,1289`
  gate the TUI daemon integration.

The `#[cfg(not(feature = "daemon"))]` fallbacks in `run_session.rs`
(`:228`, `:257`, `:285`) call `session_index` directly and produce the
same newest-first data the daemon serves. The Windows stub in
`daemon/client.rs` (`:566-646`) serves the same on-disk index. The
contract is consistent: no-daemon builds (Unix or Windows) get the
on-disk index; daemon builds get the daemon with auto-start opt-in.

**Minimal build (no-default-features) would compile**: the `daemon` module
is excised, the `Daemon`/`Jobd` subcommands vanish, `kf-rbac` is not
linked, and the `run_session` fallbacks take over. The `jobs` data model
(`runner`/`schedule`/`store`) stays compiled for the TUI slash commands,
which use `JobStore` directly (no socket). This matches the WO 47.12
contract documented in `Cargo.toml:280-289`.

### CC2 — Error classification is two-layered (typed downcast + string probe) and stable

The `error.rs` classifier is the single source of truth for exit codes.
Typed downcasts handle the migrated producers (ManifestError, ToolError,
AdapterError); string probes handle the unmigrated session-layer denials.
The `ponytail:` comment at `:35-46` discloses the debt. The exit-code
contract is pinned by `after_help` in `cli.rs:28` and by the
`--output json` path in `cli_dispatch.rs:280-290`. No drift observed.

### CC3 — The jobs scheduler is cron-correct with bounded concurrency

`compute_next_run` uses the `cron` crate's `.after()` iterator with
timezone conversion. `last_check` as the lower bound prevents double-fire
after a sleep. `max_concurrent_scheduled_jobs` bounds parallelism. Per-job
overlap is allowed (cron semantics), not prevented. The default 300s
timeout (`DEFAULT_JOB_TIMEOUT`) prevents a never-ending job from wedging
the daemon. The `skip_if_empty`/`auto_write`/`auto_dirs` policy fields are
declared in `ScheduledJob` but **not yet enforced** in `runner.rs` —
the runner ignores them. This is a known deferral (the fields are
`#[serde(default)]` so they round-trip without effect).

### CC4 — The update mechanism is the weakest security link

`handle_update.rs` is the only path that fetches + replaces the binary
in place. The SHA256 check is correct but does not protect against an
attacker who can replace both the archive and `SHA256SUMS.txt` (same
origin, HTTPS-only). A detached minisign signature over `SHA256SUMS.txt`
would close this; the `minisign` dev-dep is already present. The 30s
timeout (`UPDATE_TIMEOUT`) may be too short for slow downloads. These
are the two most worth a follow-up WO.
