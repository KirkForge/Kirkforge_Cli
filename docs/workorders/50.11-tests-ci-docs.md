# WO 50.11 — Deep-read audit: tests, CI, and docs

- **Status:** Done (audit only — findings reported, no code changes)
- **Scope:** `.github/workflows/`, `scripts/`, `.config/nextest.toml`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `docs/TECHNICAL.md`, `docs/adr/`, `docs/workorders/README.md`, `docs/README.md`, `AGENTS.md`, `CLAUDE.md`, `config.toml.example`, `README.md`, `state.md`, `lessons.md`, `CHANGELOG.md`, `tests/`, `benches/`
- **Method:** Read-only deep audit. Every file in the scope was read end-to-end. Spot-claims were verified against the code with `grep`/`cargo test`/`git log`.

## Summary

The CI/scripts/test infra is in good shape — the ADR-074 tier architecture
(merge/PR/nightly) is implemented correctly and the nextest profile system is
consistent. The ADR cross-reference drift test passes (94 ADR files = 94 index
rows). The `readme_drift` test passes (961 claimed = 961 actual by the test's
counting method). WO 43.20's aws-sigv4 removal is confirmed (zero aws crates in
the lockfile). WO 47.4's fold is confirmed (10 crates, no inter-crate edges).

The findings are mostly **doc drift** — TECHNICAL.md and AGENTS.md §7 lag the
WO 47.14 verifier unification and the batch4 config-field additions. One
**state.md inaccuracy** (main≠dev locally) and one **stale .gitignore entry**
round out the list. No CI gaps, no flaky-test infrastructure problems, no
duplicate-dependency regressions found.

Findings are grouped by severity: HIGH (load-bearing doc claims that now
mislead a worker), MEDIUM (stale-but-harmless), LOW (cosmetic).

## HIGH — load-bearing doc drift

### H1. AGENTS.md §7: "Verifier + BusVerifier coexist" is FALSE (WO 47.14 unified them)

`AGENTS.md` §7 ("Codebase patterns") says:

> The existing `Verifier` trait (`async fn verify(&self, event: &BusEvent) -> Verdict`) and the new `BusVerifier` trait (`fn verify(&self, ctx: &VerifyContext) -> Vec<VerdictEntry>`) coexist. The former is event-driven, the latter is sync and context-based. Don't try to unify them in one pass.

This is **stale**. `state.md` and `CHANGELOG.md` both record WO 47.14 as DONE
(2026-09-04): "all 14 built-in verifiers migrated to BusVerifier;
Verifier/VerifierSlots/VerifierHandler deleted. One verifier architecture."

Verified against code:
- `grep -rn "trait Verifier\b" src/ crates/` → only `BusVerifier` survives (`src/session/verifier/bus.rs:123`).
- `src/session/verifier/bus.rs:15` doc: "`VerifierHandler`/`VerifierSlots` are deleted."
- `src/session/executor/mod.rs:649`: "BusVerifier impls (WO 47.14). The old VerifierSlots/VerifierHandler…"

A worker reading §7 today would believe two verifier systems coexist and
avoid touching either. The pattern should be rewritten to reflect the single
`BusVerifier` trait.

### H2. AGENTS.md §7: CorrectionResult fields are stale (WO 45.36)

`AGENTS.md` §7 says:

> `CorrectionResult` is a struct with `{verifier, success, message, fix}` fields — not an enum. There is no `CorrectionResult::Failed`.

The actual struct (`src/session/verifier/correction.rs:181`) is now:

```rust
pub struct CorrectionResult {
    pub verifier: String,
    pub outcome: VerificationOutcome,   // was: success: bool
    pub message: String,
    pub fix: Option<FixSuggestion>,
    pub file: Option<std::path::PathBuf>,    // new (WO 45.36)
    pub line: Option<u32>,                    // new (WO 45.36)
}
```

`success: bool` was replaced by `outcome: VerificationOutcome` (WO 45.36, which
distinguishes `Skipped` from `Clean`/`Fixed`/`Suggestion`/`Failed`). The §7
pattern should be updated: the field is `outcome`, not `success`, and `file` +
`line` are now present.

### H3. config.toml.example missing 3 new config fields (batch4 + subagent audit)

`config.toml.example` does NOT document these fields that exist in the Config
struct and are recorded in `state.md`/`CHANGELOG.md`:

| Field | Where defined | Added by | CONFIG_FIELD_COUNT |
|-------|---------------|----------|---------------------|
| `subagent_fallback_model` (top-level ModelConfig) | `src/shared/config/model.rs:194` | batch4 model-fallback | 110 → 111 |
| `subagent_provider.fallback_model` (per-provider) | `src/shared/config/model.rs` | batch4 model-fallback | (same bump) |
| `tools.max_subagent_depth` (default 3, clamped 0–10) | `src/shared/config/tools.rs:67` | subagent audit 2026-09-04 | 109 → 110 |

`CONFIG_FIELD_COUNT` is now 111 (`src/shared/config/mod.rs:57`), enforced by
`config_field_count_drift_guard`. The example file documents
`max_subagent_turns` (WO 48.34) but not the three above. An operator copying
the example would not know these fields exist.

### H4. state.md "CI / branch state" is stale (main ≠ local dev)

`state.md` line 468 claims:

> **main == dev == origin/main == origin/dev at `357ac36e`** (2026-08-29).

Verified against git (2026-09-05):
- `origin/main` = `9ceff9cc` (ahead of the claimed `357ac36e` by ~15 commits).
- `origin/dev` = `9ceff9cc` (same as origin/main — the branch flow was honored
  for the push, but the pin was never updated).
- **local `dev` = `2a40886d`** — BEHIND `origin/dev` by ~10 commits (the
  batch4 merges: model-fallback, subagent-messaging, plugin-hardening,
  agent-frontmatter, CLI polish).

So the claim is doubly stale: the SHA is wrong (357ac36e → 9ceff9cc) AND local
dev is behind origin/dev. A worker following the "worktree discipline" rule
(`git fetch && git reset --hard origin/dev`) would recover, but the state.md
claim misleads anyone reading it without fetching first.

The "CI GREEN" claim on the next line (`run 33238035710`, head `357ac36e`) is
also stale — that run validated the WO 48 final wave, not the batch4 merges
that are now on origin/main. The latest origin/main commit (`9ceff9cc`) has
not had its CI run cited.

## MEDIUM — stale-but-harmless

### M1. TECHNICAL.md: `max_continuation_rounds` default is 20, not 5

`docs/TECHNICAL.md:692`:

> `ToolConfig.max_continuation_rounds` (default 5, clamped 0–50) caps how many times…

The actual default is **20**:
- `src/shared/config/tools.rs:299`: `assert_eq!(cfg.max_continuation_rounds, 20);`
- `config.toml.example:316`: `# max_continuation_rounds = 20` (comment says "Default: 20, max: 50").

TECHNICAL.md is off by 4×. Minor (it's an approximate doc), but a worker
quoting "default 5" in a WO would be wrong.

### M2. TECHNICAL.md: bench task TOML example shows `category` field that no task has

`docs/TECHNICAL.md:1787` shows:

```toml
category = "C"            # A–H, matching the spec categories
```

But **zero** of the 30 bench tasks in `benches/tasks/*.toml` have a `category`
field (`grep -l "category" benches/tasks/*.toml` → no matches). The field was
either never added or was removed. The "Implemented task mapping" table (line
1807+) does list categories, but they are not in the TOML files themselves.
The example is misleading — a contributor adding a task would add a `category`
field expecting it to be used, but nothing reads it.

### M3. TECHNICAL.md: "Cost: £0.12" (pound sign) in scoring example

`docs/TECHNICAL.md:1762`:

```
Cost:               £0.12
```

The rest of the document uses dollars (e.g. "$0.12" context). The £ is likely
a typo. Cosmetic, but the benchmark scoring block is the public scoreboard
format — it should be consistent.

### M4. ADR-074 body text has stale timeout/structure claims (amendment corrects them)

`docs/adr/074-ci-architecture-reset.md` main body (lines 72-104) cites:
- `ci-fast` profile = `kind(lib)`, **60s** slow-timeout
- `ci-full` profile = **120s** slow-timeout
- `e2e` profile = **600s** slow-timeout
- PR gate diagram: `static → fast-tests, clippy, targeted-integration`
- Merge gate diagram: includes `platform-build`

The **amendment (2026-08-29, lines 157-169)** corrects the timeouts to
ci-fast=30s, ci-full=60s, e2e=300s and adds the nightly job growth. But the
main body was never updated, so a reader who stops at the body gets wrong
numbers. Additionally:
- `targeted-integration` in the PR diagram is not a real job — the actual
  ci-pr.yml has `minimal-build` (WO 48.9) which the ADR body doesn't mention.
- `platform-build` in the merge diagram is contradicted by the ADR's own text
  ("release compile validation — in nightly, not here") — the diagram lists
  it, the prose disclaims it.
- The amendment says nightly count is 8 (correct: coverage, ollama,
  subprocess-lifecycle, e2e-exhaustive, feature-combos, audit, mutants,
  release-build = 8 jobs), but the main body's nightly list (line 111) shows
  only 5.

The amendment is accurate; the body is not. A clean fix would fold the
amendment into the body and delete the "Amendment" section.

### M5. .gitignore still lists `lessons.md` as ignored (it's tracked)

`.gitignore:25` lists `lessons.md` under "Agent work files (per-session, not
tracked)". But `git ls-files lessons.md` confirms it IS tracked, and
`AGENTS.md` §7 correctly says "lessons.md is TRACKED on dev (the 'gitignored'
claim went stale)". The `.gitignore` entry is inert (git doesn't apply ignore
rules to already-tracked files) but it's misleading — a contributor might
`git rm --cached lessons.md` thinking they're respecting the ignore rule, or
a fresh clone would track it anyway. The line should be removed and the
"not tracked" comment corrected.

### M6. docs/workorders/README.md: "three most recent series" is stale (four live)

`docs/workorders/README.md:9`:

> Only the three most recent series are kept live.

Actual live series in `docs/workorders/`: 46 (39 files), 47 (37 files), 48
(51 files), **49** (5 files) = **four** series. Series 49 was added but the
"three most recent" line wasn't updated. The "Active series" section below it
does list Series 49 correctly — only the count claim is wrong.

## LOW — cosmetic / informational

### L1. `.config/nextest.toml`: `integration` profile is unused

The `integration` profile (120s slow-timeout, `kind(test) - binary(e2e)`) is
defined in `.config/nextest.toml:67` but is NOT referenced by any CI workflow
or script. The nightly job uses `--profile nightly --test integration_test`
instead. The profile is harmless (nextest ignores unused profiles) but it's
dead config. Either wire it into a job or remove it.

### L2. TECHNICAL.md test-function count is slightly stale

`docs/TECHNICAL.md:53`:

> The workspace has ~5,100 test functions (~4,110 under `src/`, ~1,005 under `crates/`).

Actual (by the `readme_drift` test's counting method: `#[test]` followed by a
line starting with `fn `):
- `src/`: 3138 `#[test]` + 1030 `#[tokio::test]` = **4168** (claim: ~4,110, off by ~58)
- `crates/`: **961** (claim: ~1,005, off by ~44)
- Total: **5129** (claim: ~5,100, close)

The "~" makes this technically not wrong, but the split is stale. The crates/
number (961) is pinned by the `readme_drift` test and is authoritative.

### L3. ADR numbering gap: 069 is missing

ADR numbers skip from 068 to 070. There is no `docs/adr/069-*.md` file and no
index row. This appears to be a reserved/skipped number (the README index
doesn't list it either, so the drift test passes). Documenting it here so a
future auditor doesn't file a "missing ADR" workorder — it's intentional or
was reclaimed, not lost.

### L4. `requires_model` field present in only 15 of 30 bench tasks

The bench TOML format (TECHNICAL.md:1788) documents `requires_model` as a
field. 15 of 30 tasks have it set to `true`; the other 15 omit it entirely
(defaulting to `false`/absent). This is consistent (the field is optional) but
the TECHNICAL.md example shows it without noting it's optional. Minor — the
loader handles absence correctly.

### L5. CLAUDE.md is a verbatim copy of the AGENTS.md gitnexus block

`CLAUDE.md` is exactly the `<!-- gitnexus:start -->…<!-- gitnexus:end -->`
block from `AGENTS.md` (verified with `diff` — identical). This is by design
(so Claude Code users get the same gitnexus guardrails without reading the
full AGENTS.md worker contract). Not a problem, just noting it: editing one
requires editing both to keep them in sync.
