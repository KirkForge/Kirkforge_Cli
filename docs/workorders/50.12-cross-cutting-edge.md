# WO 50.12 — Cross-cutting audit: error handling, async, resources, concurrency, Windows, config, dead code

- **Status:** Done (audit only — findings reported, no code changes)
- **Scope:** concern-specific, cross-cutting — every check below was run
  across the entire `src/` tree (and `crates/` where the concern reached there).
  Not file-scoped like WO 50.01–50.11; this is the edge audit.
- **Method:** Read-only deep audit. Each concern was grep-checked
  end-to-end; spot-claims were verified against the code by reading the
  surrounding context. Test modules (`#[cfg(test)]` blocks + `#[test]`/
  `#[tokio::test]` fn bodies) were stripped before counting
  `unwrap`/`expect`/`panic!` so the numbers reflect production code.
  Audited against HEAD (post-batch4-merge; `state.md` records `main`/`dev`
  at `9ceff9cc` after WO 50.11 closed).
- **Auditor:** deep-read-only subagent (20+ minute budget), 2026-09-05.

## Summary

The codebase is in good shape on the cross-cutting axis. The headline
finding is a **real correctness bug** in the bash landlock pre_exec hook
(eprintln + format! allocate in an async-signal-unsafe context), and a
**doc-drift / config-field-coverage** finding that compounds the WO 50.11
H3 finding (config.toml.example is missing ~40 fields, not just the 3
already filed). The remaining findings are MEDIUM/LOW — stale
`#[allow(dead_code)]` annotations, one production `panic=abort` hazard on
an internal invariant, and one minor memory-ordering style inconsistency.

Findings are grouped by severity: HIGH (load-bearing correctness), MEDIUM
(stale-but-harmless / contract drift), LOW (cosmetic).

A clean-tree fast-gate run was NOT attempted (this is a docs-only audit);
the findings are reported for a follow-up WO to act on.

## HIGH — load-bearing correctness

### H1. `eprintln!` + `format!` in landlock `apply_landlock` (pre_exec hook) — async-signal-unsafe

`src/session/bash_runner/landlock.rs:234`, `:244`, `:255`, `:267`, `:283`
call `eprintln!("landlock: warning: cannot add system dir {dir:?}")` (and
sibling variants). These run inside `apply_landlock`, which is documented
as "MUST be called from a pre_exec closure (post-fork, pre-exec). All path
resolution is already done — this function only opens fds and makes
syscalls, no heap allocation." (`landlock.rs:200-202`).

`eprintln!` is NOT async-signal-safe:
- It calls `format!`/`{}` formatting, which **allocates** on the heap
  (`String`/`Vec` growth).
- The stdlib `Write` impl for `Stderr` takes a `Mutex` lock on the stderr
  handle.
- In a multithreaded parent at fork time, another thread may have been
  mid-`malloc` or mid-`stderr.lock()` when `fork()` returned — the child
  inherits those held locks, and the next allocation or stderr write can
  deadlock the child forever (the classic "async-signal-safety" rule).

The same pattern exists in `src/session/bash_runner/mod.rs:186`, `:200`,
`:214`, `:247`, `:266`, `:303`, `:317`, `:331` — `eprintln!` calls in the
`pre_exec` closure (lines 171-340). The comment at `mod.rs:175-177` says:

> // we warn (via stderr — the only async-signal-safe channel in
> // pre_exec) and proceed

The author's mental model is "stderr = async-signal-safe", which is
**incorrect for `eprintln!`**. The truly async-signal-safe primitive is
`libc::write(2, b"...\n")` directly (no formatting, no Mutex). The
codebase already does this correctly elsewhere — `process_group.rs:38`
uses `#[allow(unused_must_use)] { setpgid(0, 0); }` (raw syscall, no
format). The landlock/mod.rs `eprintln!` sites should be converted to a
small `unsafe fn warn_fd2(msg: &[u8])` helper that calls
`libc::write(libc::STDERR_FILENO, msg.as_ptr() as *const _, msg.len())`
and pre-format the messages at parent-time (before fork) where
allocation is allowed.

Severity: HIGH because the deadlock window is narrow but real (a fork
mid-`tracing::info!` in the parent would orphan the child), and because
the codebase explicitly calls out pre_exec's async-signal-safety
constraints for `seccomp` (`mod.rs:165-168`: "must not run inside the
async-signal-safe pre_exec closure") but violates the same rule for
landlock warnings.

Note: this is Linux-only code (`mod landlock` is `#[cfg(target_os =
"linux")]` per `mod.rs:12`), so Windows is unaffected. But the
`mod.rs` rlimit `eprintln!` sites (186/200/214/303/317/331) are in the
Unix arm of `setup_rlimits`, so they affect macOS + Linux.

## MEDIUM — stale-but-harmless / contract drift

### M1. `task_tool.rs:271` — production `panic=abort` on internal invariant

`src/tools/task/task_tool.rs:271`:

```rust
TaskConcurrencyMode::Queue => {
    let sem = self.bg_semaphore.clone();
    sem.acquire_owned()
        .await
        .unwrap_or_else(|_| panic!("bg_semaphore closed unexpectedly"))
}
```

With `panic = "abort"` (root `Cargo.toml`), this `panic!` kills the whole
CLI. The `bg_semaphore` is `Arc<tokio::sync::Semaphore>` constructed with
`Semaphore::new(4)` (`task_tool.rs:41,53,77,97`); `close()` is never
called anywhere in the codebase, and the Arc outlives any single
`acquire_owned` call (the semaphore is owned by `self` which is the
long-lived `TaskTool`). So the panic is currently unreachable.

But: it's a `panic=abort` hazard if the semaphore lifetime ever changes,
and the `Reject` arm at line 258-264 already handles the
semaphore-closed case gracefully (returns `Failure(InvalidArgs)`). The
`Queue` arm should do the same — return a `Failure` with a "background
semaphore closed" message instead of killing the process. The current
asymmetry is a contract smell: Reject handles closure, Queue panics.

Severity: MEDIUM because the panic is unreachable today, but the code is
one refactor away from a real `panic=abort` kill, and the sibling arm
shows the right pattern.

### M2. Stale `#[allow(dead_code)]` on `LandlockPaths` struct

`src/session/bash_runner/landlock.rs:148` marks the `LandlockPaths` struct
`#[allow(dead_code)]`. But the struct has 4 fields (`workspace`,
`home`, `xdg_dirs`, `extra`), all `pub(crate)`, and ALL four are read in
`apply_landlock` (`landlock.rs:216,240,251,263`). The struct itself is
constructed by `resolve_paths` (line 192) and stored as
`Option<landlock::LandlockPaths>` in `bash_runner/mod.rs:152`. None of
it is dead.

The annotation is likely a vestige of an earlier version where some
fields were unused. It should be removed — `cargo check` confirms no
dead-code warning fires without it (the struct is `pub(crate)` and used
across the module boundary). Leaving it silences future real
dead-code warnings if someone adds a new unused field.

Severity: MEDIUM because it's a stale annotation that defeats the
dead-code lint for the struct's fields.

### M4. `unwrap_success_content` in `task/test_helpers.rs` is genuinely dead

`src/tools/task/test_helpers.rs:118-124` defines:

`grep -rn 'unwrap_success_content' src/` returns only the definition —

Either wire it into the test bodies that manually destructure

Severity: MEDIUM — small dead-code island, but it's in a test_helpers

### M5. Memory-ordering inconsistency: `Ordering::Release` in `line_mode.rs`, `Ordering::SeqCst` everywhere else

The project's dominant convention for cancel/shutdown `AtomicBool`
stores is `Ordering::SeqCst` (see `tui/keys/mod.rs:1204`,
`tui/commands/workflow.rs:128`, `tools/task/mod.rs:64,467,545,546,...`,
`tui/commands/persona.rs:331`, `tools/task/task_tool.rs:325,345,352` —
~30 sites).

`src/main/line_mode.rs` uses `Ordering::Release` for the matching
stores: lines `68, 474, 791, 1021, 1067, 1093`. The loads use
`Ordering::Acquire` (lines `496, 612, 674, 708, 1104`). Release/Acquire
pairing is correct for a one-shot signal that doesn't publish other
data alongside the flag — and is slightly more efficient than SeqCst.
So this is not a bug.

But: it's inconsistent with the rest of the codebase. A reader who
grep-checks cancel patterns sees `SeqCst` everywhere and may assume
`Release` is wrong. The convention should be unified — either flip
line_mode.rs to `SeqCst` (matches the majority, no measurable perf
difference for a one-shot signal) or document why line_mode.rs uses
the lighter ordering.

Severity: MEDIUM — style/convention drift, not a correctness bug.

### M6. `microcompaction::BoxCollapseFn` lacks `+ Send` (consistency, not a bug)

`src/session/prompt/microcompaction.rs:23`:

```rust
type BoxCollapseFn = Box<dyn Fn(&[Message]) -> String>;
```

The sibling `src/session/executor/loop_.rs:11` has the `+ Send` version:

```rust
type BoxCollapseFn = Box<dyn Fn(&[Message]) -> String + Send>;
```

The microcompaction closure is created and consumed locally
(`microcompaction.rs:74-112`) — it never crosses an `.await` and is
never stored in a struct field or sent to another thread. So the
missing `+ Send` is fine. But the two type aliases with the same name
and different `Send` bounds is a consistency smell — a future refactor
that moves the closure into a struct or across threads would silently
fail to compile in microcompaction but work in loop_.rs. Either unify
both to `+ Send` or rename one to avoid the name collision.

Severity: MEDIUM — not a bug today, but a refactor footgun.

## LOW — cosmetic / informational

### L1. Default deny-list is Unix-only; Windows secret paths aren't denied

`src/shared/access/deny_list.rs:106-109` hardcodes Unix paths:

```rust
"/etc/shadow".into(),
"/etc/sudoers".into(),
"/etc/passwd".into(),
"/etc/kubernetes/**".into(),
```

On Windows, these globs never match (the paths don't exist), so the
default deny list provides no protection for Windows secret locations
like `C:\Windows\System32\config\SAM`, `C:\Windows\System32\config\SECURITY`,
`%USERPROFILE%\AppData\Roaming\Microsoft\Credentials\*`,
`C:\Users\*\AppData\Local\Microsoft\Credentials\*`.

The `bash_safety.rs:195-219` dangerous-redirection-targets list DOES
include Windows paths (`%systemroot%`, `%userprofile%`, `c:\windows`,
`c:\programdata`) — so the bash tool's redirection gate is
Windows-aware, but the file-tool deny list is not.

Severity: LOW because (a) the project's primary platform is Linux/macOS
(WO 47.12 daemon-opt-in made Windows a second-tier target), (b) the
PathGuard sandbox + landlock-equivalent (rlimits) + the bash redirection
gate are the real boundary, and the deny list is defense-in-depth. But
a Windows user copying the default config gets no deny-list protection
for Windows-specific secret paths.

### L2. `tui/components/approval.rs:891` — `panic!` in test helper, not production

`src/tui/components/approval.rs:891`:

```rust
.unwrap_or_else(|| panic!("no line contains the path; lines={lines:?}"));
```

This is inside a `#[test]` fn (the `assert!(path_line.contains("path"))`
follows). With `panic = "abort"`, a test panic still unwinds (cargo
test runs with `panic=unwind` regardless of the release profile). Not
a production hazard — listed here only because the audit grep flagged
it and the next auditor should not re-verify.

### L3. Mutex-poison `.expect()` calls are defensible (not findings)

The audit grep flagged ~15 `.lock().expect("... mutex poisoned")` sites
in `src/shared/audit.rs` (lines 554,562,576,583,681,691,695,909) and
`src/shared/event_bus.rs` (lines 209,284,292,307,347,367,373,405,414).
These are the canonical "poison = a thread panicked while holding the
lock, the data may be inconsistent, abort" pattern. With
`panic = "abort"` the poison case is unreachable in release (a panic
kills the process before the mutex can poison), and in dev/test the
expect message is useful for debugging. Not a finding — documented
here so the next auditor doesn't re-flag them.

### L4. Static-regex `.expect("... regex ...")` calls are defensible (not findings)

~15 sites in `src/tools/web_fetch.rs`, `src/session/verifier/security_emitter.rs`,
`src/session/error_recovery.rs` use `Regex::new(r"...")
.expect("static regex literal")` or `RE.get_or_init(|| Regex::new(r"...").expect(...))`.
These compile regex literals whose syntax is known at compile time
(cannot fail at runtime). The `expect` is a "this can't fail" guard,
not a runtime hazard. Standard Rust pattern. Not a finding.

### L5. CLI-entry-point `println!`/`eprintln!` are legitimate (not findings)

`src/main/handle_bench.rs` (34 `println!`), `src/main/line_mode.rs`
(30), `src/main/cli_dispatch.rs` (15 `eprintln!`), `src/main/run_session.rs`
(11 `eprintln!`), `src/main/handle_plugin.rs` (13 `println!`), etc. are
all CLI user-facing output (report rendering, error messages, status
lines), not debug spam. AGENTS.md §5 forbids "debug spam
(`println!`, `eprintln!`, `dbg!`, `tracing::debug!` left on in
committed code)" — the key word is "debug". CLI output that the user
sees is not debug spam. Not a finding.

The `eprintln!` in `src/session/bash_runner/mod.rs:355` (Windows
non-Unix `setup_rlimits` warning, `OnceLock`-deduplicated) is also
legitimate — it's a user-facing warning at first call, not in pre_exec.

## What was verified CLEAN (no findings)

These were checked and are correct — listing them so a future auditor
doesn't re-verify:

1. **No `Box<dyn Error>` leftovers** — `grep -rn 'Box<dyn Error\|dyn
   Error>' src/` returns zero hits. The project uses `anyhow::Error`
   consistently. WO 43.1's typed-adapter-error migration is complete.
2. **No `Rc` in async** — `grep -rn '\bRc\b\|std::rc::Rc' src/` (excluding
   comments/tests) returns zero hits. No `Send` issues from `Rc`.
3. **No `dbg!` in production code** — `grep -rn 'dbg!(' src/` returns
   zero hits outside test code.
4. **No `println!`/`eprintln!` in committed non-CLI production code**
   (outside the pre_exec finding H1). The only production `eprintln!`
   sites are: CLI entry points (legitimate user-facing output — see L5),
   the Windows `setup_rlimits` once-shot warning (legitimate — see L5),
   and the pre_exec landlock/rlimit sites (H1 — the finding).
5. **`std::sync::Mutex` across `.await` is not a problem** — the daemon
   server uses `tokio::sync::Mutex` (WO 46.19 fix confirmed at
   `daemon/server.rs:10,87,96`). The verifier bus uses the
   extract/run-on-blocking/replace pattern (WO 43.26, confirmed at
   `dispatch.rs:254-262`) — the sync `Mutex` is held only for
   extract/replace (microseconds), not across the run. The response
   cache (`caching.rs:140-179`) does the disk write on
   `spawn_blocking` (WO 47.20) — the sync `Mutex` is held only for the
   in-memory insert. All three WO fixes are in.
6. **`std::thread::sleep` in async** — the 7 sites flagged by grep are
   all in test code or in non-async std threads (`tui/mod.rs:317` is in
   a `std::thread::spawn` keyboard-reader loop, not an async context;
   `process_group.rs:340`, `pty.rs:123/128`, `atomic_write.rs:89/116`,
   `jobs/runner.rs:605` are all in `#[test]` or `#[ignore]`-tagged test
   helpers). No production async function calls `std::thread::sleep`.
7. **`tokio::spawn` fire-and-forget tasks** — the streaming-parser
   spawns (`adapters/caching.rs:438,471`, `adapters/oellama.rs:209`,
   `adapters/anthropic_bedrock.rs:127`, `adapters/anthropic/mod.rs:196,706,...`,
   `adapters/openai_compat/mod.rs:625`, `adapters/anthropic_vertex.rs:201`)
   all exit when their `tx.send()` returns `Err` (receiver dropped), so
   they don't leak. The MCP HTTP `_reader_task`/`_poster_task` are
   stored in `Mutex<Option<JoinHandle>>` and signalled to shut down via
   `shutdown_tx` in `Drop` (WO 46.22 fix at `mcp_client/http.rs:291-303`);
   they're detached (not awaited in production Drop) but the shutdown
   signal is the contract.
8. **Temp directories on error paths** — `task_spawner.rs:84-90`
   `TempDirGuard` is an RAII `Drop` that `remove_dir_all`s on all
   exit paths (error, cancel, panic). `atomic_write.rs:46-49` cleans
   up the `.tmp` file on write failure. The `worktree.rs` worktree
   lifecycle is owned by the subagent handle.
9. **`AtomicBool` `Ordering::Relaxed` for the glob cancel flag is
   correct** — `glob.rs:39,64` uses `Relaxed` for the walker cancel
   flag. This is correct: no data is published alongside the flag, so
   no acquire/release pairing is needed; the only consequence of stale
   visibility is the walker reads one more directory entry before
   noticing cancellation. Documented behavior.
10. **`Ordering::SeqCst` for task cancel flags is correct** — the
    `tools/task/mod.rs` cancel flags (`cancel_requested`, `started`)
    use `SeqCst` consistently for store + load, which is the safe
    default for cross-thread signaling.
11. **Daemon state lock discipline is clean** — `tokio::sync::Mutex`,
    acquired with `state.lock().await` at the top of each handler
    branch, dropped at scope end. No nested locks. The WO 46.19 fix
    (don't hold the state mutex across `write_response .await`) is in
    — the handler clones what it needs, drops the lock, then writes.
12. **Audit-sink lock discipline is clean** — `MemoryAuditSink::write`
    (audit.rs:553) locks `last_hash`, drops it, then locks `events`
    (sequential, no nesting). `FileAuditSink::flush` (audit.rs:691)
    locks `buffer` then `last_hash` (nested), but no other site locks
    them in the opposite order — confirmed by grep. `FileAuditSink::write`
    (audit.rs:680) drops `buffer` before calling `flush`, so no
    re-entrancy. The `rotate()` call inside `flush` (audit.rs:698) does
    filesystem I/O while holding both locks, which is a stall risk

13. **`CONFIG_FIELD_COUNT = 111` is enforced** — the
    `config_field_count_drift_guard` test (`session/config/mod.rs:1307`)
