# Workorder 8.8 — Plugin Manifest Schema Validation

## Status: Planned

## Problem
Plugin manifests (`kirkforge.toml`) are parsed with serde but not validated against a schema. A malformed manifest (e.g., `command` pointing to a nonexistent file, `schema` that isn't valid JSON Schema, `trust` with an invalid tier) is only caught at load time with a generic error. There's no upfront validation or helpful error messages.

## Root cause
The manifest parser (`crates/kirkforge-plugin/src/lib.rs`) deserializes and does basic type checking but doesn't validate semantic constraints.

## Files to touch
- `crates/kirkforge-plugin/src/lib.rs` — add `PluginManifest::validate() -> Result<(), Vec<ValidationError>>`:
  - `name` is non-empty, alphanumeric + hyphens
  - `version` is valid semver
  - `api_version` is `V1`
  - `trust` is a valid `TrustTier`
  - For each `Capability::Tool`: `command` is a relative path, `schema` is a valid JSON Schema object
  - For each `Capability::Hook`: `event` is a known event name, `command` is a relative path
  - For each `Capability::Skill`: `trigger` starts with `/`
  - For each `Capability::Verifier`: `name` is non-empty
  - No duplicate capability names/triggers
- `crates/kirkforge-plugin-host/src/lib.rs` — call `validate()` during `load_one` and include validation errors in the warnings
- `crates/kirkforge-plugin/src/lib.rs` — add unit tests for `validate()` with good and bad manifests

## Approach
1. Implement `validate()` as a pure function returning a list of errors
2. Call it in `load_one` before the trust-policy check
3. Collect validation errors as warnings (don't reject the plugin — let the user see all issues at once)
4. Add tests for each validation rule

## Gate
```
cargo fmt --check && cargo check --workspace --all-targets --all-features &&
cargo clippy --all-targets --all-features -- -D warnings &&
cargo test --locked --workspace --no-fail-fast --all-features
```
