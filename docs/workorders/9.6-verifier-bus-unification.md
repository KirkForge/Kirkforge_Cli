# Workorder 9.6 — Verifier Bus Code Unification

## Status: Done

## Problem
Two independent verifier buses coexist:
1. **Rust runtime bus** (`src/session/verifier/`): `lint.rs`, `rustfmt.rs`,
   `security.rs`, `git.rs`, `build.rs`, `test.rs`, `plugin.rs` — event-driven
   via the `Verifier` trait (`async fn verify(&self, event: &BusEvent) ->
   Verdict`).
2. **TS plugin orchestrator bus** (`npm/kirkforge-plugin/packages/orchestrator/`):
   `lint`/`types`/`security`/`graph`/`imports`/`changes` emitters + reducer +
   correction-loop.

ADR-007 documents the seam; ADR-028 (KVB verifier bus bridge) is "Accepted
(partially implemented)" — the Rust `VerifierBus` can register plugin
verifiers via `add_plugin_verifier`, but the TS plugin orchestrator bus is
still a separate system. A reviewer seeing "two verifier buses" can't tell
if they're unified or not. The code-level unification is multi-day design
work, correctly deferred until now.

## Root cause
The TS orchestrator was built first (the "Vix merge" half). The Rust runtime
bus was built second (the Claude-Code half). They were never unified because
unification requires deciding which bus is authoritative and bridging the
other into it — a design decision, not a mechanical merge.

## Files to touch
- `src/session/verifier/bus.rs` — extend `VerifierBus` to host TS plugin
  orchestrator verifiers as first-class citizens. The existing
  `add_plugin_verifier` path shells out to the plugin process; the
  unification path should let the TS orchestrator's emitters register
  directly (via a thin adapter that translates TS emitter events to
  `BusVerifier` verdicts) OR run the TS orchestrator in-process via the
  Node SDK bridge
- `npm/kirkforge-plugin/packages/orchestrator/src/` — add a `BridgeEmitter`
  that wraps the Rust `VerifierBus` verdicts and feeds them into the TS
  reducer, so a single correction loop can act on both Rust and TS verdicts
- `docs/adr/0028-kvb-verifier-bus-bridge.md` — update from "Accepted
  (partially implemented)" to "Accepted" when the bridge code ships
- `docs/TECHNICAL.md` — document the unified bus

## Approach
1. Decide the authoritative bus: the Rust `VerifierBus` (it's in-process,
   faster, and the executor already queries it). The TS orchestrator becomes
   a *source* of verdicts, not a separate bus.
2. Build a `TsOrchestratorBridge` that runs the TS orchestrator's emitters
   via the Node SDK bridge (or in-process if `kirkforge-plugin` can be
   loaded as a WASM/FFI module — check feasibility) and feeds verdicts into
   the Rust `VerifierBus`
3. The correction loop in `verifier/correction.rs` already acts on
   `VerifierBus` verdicts — once TS verdicts are in the bus, the correction
   loop handles them automatically
4. Test: a plugin that declares a `security` verifier via the TS orchestrator
   → the Rust correction loop acts on its verdicts
