# Workorder 9.8 — Seccomp/rlimit Sandbox Hardening

## Status: Done

Shipped rlimits only (seccomp deferred to future work — ADR-054
documents why: a BPF compiler is too heavy for the size-optimized
binary). `SandboxConfig` in `SecurityConfig` with `harden`,
`cpu_limit_secs` (default 300), `memory_limit_mb` (default 2048),
`filesize_limit_mb` (default 512). `--harden` CLI flag mirrors
`--docker`. Applied in a `pre_exec` hook (post-fork, pre-exec) via
`libc::setrlimit` — no new deps (`libc` was already a direct dep).
Ignored when `--docker` is set (Docker already enforces `--memory` and
`--cpus`). Windows no-op with a one-shot `OnceLock` warning. 1 ignored
test (`bash_harden_kills_cpu_burn_with_sigxcpu`) verified the rlimit
fires: child killed by SIGXCPU in 1.1s. ADR-054.

## Problem
The sandbox is path-based (`PathGuard`, deny-list, permission rules) plus
optional Docker isolation (`--docker` flag, WO P2-6b). But outside Docker,
the bash tool runs with full process privileges — no seccomp syscall
filter, no rlimit memory/CPU cap, no cgroup isolation. The ChatGPT
sixth-pass review named "Docker execution, ephemeral workspaces, Git
worktrees, resource limits" as the sandboxing bar. Docker + worktree
shipped; the *non-Docker* resource-limit path did not. A user who doesn't
want Docker overhead has no lightweight sandbox hardening.

## Root cause
Seccomp/rlimit/cgroup are Linux-specific, require `libc` or `nix` crate
bindings, and add real complexity to the bash runner. The Docker path was
easier to ship (fork+exec `docker run`). The non-Docker hardening was
deferred as "P2, requires platform-specific code."

## Files to touch
- `src/tools/bash.rs` — when `DockerConfig.enabled` is false but
  `SandboxConfig.harden` is true, apply rlimits (`setrlimit` for
  `RLIMIT_CPU`, `RLIMIT_AS`, `RLIMIT_FSIZE`) before `exec`-ing the child.
  On Linux, optionally apply a seccomp filter that blocks `ptrace`,
  `perf_event_open`, `unshare` (the "no privilege escalation" set)
- `src/shared/mod.rs` — add `SandboxConfig { harden: bool, cpu_limit_secs:
  u64, memory_limit_mb: u64, filesize_limit_mb: u64 }` (or reuse the
  existing `DockerConfig` fields with a `mode: Docker | Harden | None`)
- `Cargo.toml` — add `nix` crate (already in workspace? check) for
  `setrlimit`/`seccomp` bindings. Gate behind a `sandbox` feature.
- `src/session/worktree.rs` — when `--worktree` + `--harden` are both set,
  the worktree session also gets rlimits applied
- `docs/adr/` — new ADR for the non-Docker sandbox hardening

## Approach
1. Check if `nix` crate is already in the workspace dep tree (it may be,
  via `kirkforge-lsp` or another crate). If not, add it behind a `sandbox`
  feature.
2. Implement `apply_rlimits(cpu, memory, filesize)` using
  `nix::sys::resource::setrlimit`
3. Implement `apply_seccomp()` using `nix::sys::socket` + seccomp BPF (or
  the `seccomp` crate if simpler). Block the "no privilege escalation" set.
4. In `bash.rs`, before spawning the child: if `harden`, fork →
  `apply_rlimits` → `apply_seccomp` → `exec`. This is Unix-only; on
  Windows, `harden` is a no-op with a warning.
5. Test: `#[cfg(unix)] #[ignore = "requires setrlimit"]` test that spawns
  a bash call with `harden=true`, verifies the child can't allocate beyond
  the memory limit (a `yes | head -c 1G` call gets killed)
